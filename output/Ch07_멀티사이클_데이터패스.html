Chapter 07

멀티사이클 데이터패스

단일 사이클 프로세서의 한계를 진단하고, 하드웨어 자원을 공유하면서 클럭 주파수를 높이는 멀티사이클 데이터패스의 설계 원리를 학습합니다. 이 챕터는 Part 4의 파이프라인 프로세서로 넘어가기 위한 핵심 교량 역할을 합니다.

학습 목표

  • 단일 사이클 프로세서의 임계 경로(critical path) 병목과 자원 낭비 문제를 분석할 수 있다.
  • 멀티사이클 설계의 핵심 아이디어인 단계 분할과 자원 공유 원리를 설명할 수 있다.
  • A/B 레지스터, ALUOut, MDR 등 중간 레지스터의 역할과 배치 근거를 설명할 수 있다.
  • 멀티사이클 데이터패스의 전체 구조를 SystemVerilog로 구현할 수 있다.
  • 단일 사이클과 멀티사이클 데이터패스의 트레이드오프를 정량적으로 비교할 수 있다.

7.1 단일 사이클의 한계 — 왜 개선이 필요한가

Chapter 06에서 우리는 RV32I 단일 사이클 프로세서를 완성하고, Basys 3 FPGA에서 피보나치 수열을 실행하는 데 성공하였다. 모든 명령어가 정확히 하나의 클럭 사이클 안에 완료되는 단순하고 직관적인 구조였다. 그런데 이 프로세서의 합성 결과를 자세히 살펴보면, 한 가지 심각한 문제가 드러난다. 바로 가장 느린 명령어가 전체 시스템의 속도를 결정한다는 것이다.

임계 경로 분석: 모든 것은 LW 명령어에 달려 있다

단일 사이클 프로세서에서 각 명령어의 실행 경로를 추적해 보자. Chapter 06에서 배운 데이터패스를 떠올리면, 명령어 인출(Instruction Fetch)부터 결과 기록(Write-Back)까지 조합 논리(combinational logic)가 직렬로 연결되어 있다. 클럭의 상승 에지(rising edge)에서 PC가 갱신되면, 그 순간부터 다음 상승 에지 직전까지 모든 조합 논리가 안정화(settle)되어야 한다. 이때 가장 긴 경로를 임계 경로(Critical Path)라 부른다.

각 모듈의 전파 지연(propagation delay)을 가정해 보자. 이해를 돕기 위해 이상적인 수치를 사용한다.

모듈 전파 지연 비고
IMEM (명령어 메모리) 200 ps BRAM 읽기 지연
Decode + Register Read 100 ps 디코더 + 레지스터 파일 읽기
ALU 200 ps 32비트 가산기 + MUX 체인
DMEM (데이터 메모리) 200 ps BRAM 읽기 지연
Register Write 100 ps MUX + 레지스터 파일 쓰기 셋업

이제 명령어 유형별 실제 경로 길이를 살펴보자.

명령어 유형 사용 모듈 총 지연
R-타입 (ADD, SUB 등) IMEM → Decode/RegRead → ALU → RegWrite 600 ps
I-타입 연산 (ADDI 등) IMEM → Decode/RegRead → ALU → RegWrite 600 ps
S-타입 (SW) IMEM → Decode/RegRead → ALU → DMEM 700 ps
B-타입 (BEQ) IMEM → Decode/RegRead → ALU 500 ps
LW (로드) IMEM → Decode/RegRead → ALU → DMEM → RegWrite 800 ps

LW 명령어는 다섯 개의 모듈을 모두 순차적으로 통과해야 한다. IMEM에서 명령어를 인출하고, 디코더와 레지스터 파일에서 베이스 주소를 읽고, ALU에서 실효 주소를 계산하고, DMEM에서 데이터를 읽고, 마지막으로 레지스터 파일에 결과를 기록한다. 이 경로가 800 ps로 가장 길기 때문에, 클럭 주기는 최소 800 ps 이상이어야 한다.

클럭 주파수 병목: 빠른 명령어도 느리게 동작한다

여기서 핵심적인 비효율이 드러난다. R-타입 명령어(ADD 등)는 실제로 600 ps면 충분한데, 클럭 주기가 800 ps로 설정되어 있으므로 200 ps 동안 아무 일도 하지 않고 대기한다. B-타입 분기 명령어는 더 심각하여, 500 ps면 완료될 작업에 300 ps를 허비한다. Basys 3의 Artix-7 FPGA에서 실제로 합성해 보면, 단일 사이클 프로세서의 최대 동작 주파수는 대략 20~30 MHz 수준이다. 이는 FPGA의 잠재력에 비해 상당히 낮은 수치이다.

비유: 단체 등산

10명이 함께 등산하는 상황을 생각해 보자. 가장 느린 사람의 속도에 맞추어 전체 그룹이 이동해야 하므로, 다른 9명은 계속 기다려야 한다. 단일 사이클 프로세서도 마찬가지다. 가장 느린 명령어(LW)에 맞추어 클럭을 설정하면, 빠른 명령어들은 그저 시간을 낭비할 뿐이다.

자원 낭비: 사용하지 않는 하드웨어

비효율은 시간에만 국한되지 않는다. 하드웨어 자원 측면에서도 낭비가 존재한다. 단일 사이클 데이터패스에는 명령어 메모리(IMEM)와 데이터 메모리(DMEM)가 별도로 존재한다. 이 설계를 하버드 구조(Harvard Architecture)라 부르며, 동시에 명령어 인출과 데이터 접근이 가능하다는 장점이 있다. 그러나 한 사이클 안에서 IMEM은 명령어 인출 단계에서만, DMEM은 메모리 접근 단계에서만 사용된다. 나머지 시간 동안 각 메모리는 유휴(idle) 상태이다.

마찬가지로, PC+4를 계산하기 위한 별도의 가산기(adder)가 존재한다. ALU가 이미 덧셈을 수행할 수 있음에도 불구하고, 동시에 다른 연산을 수행해야 하므로 추가 하드웨어가 필요하다. 이 가산기는 PC+4 계산 이외에는 전혀 사용되지 않는다.

실무 팁

FPGA 설계에서 자원 사용률(resource utilization)은 비용과 직결된다. Basys 3의 Artix-7 XC7A35T는 BRAM 36Kb 블록을 50개 보유한다. IMEM과 DMEM을 각각 별도로 할당하면 BRAM을 두 배로 소모하는데, 특히 메모리가 큰 프로그램을 탑재해야 할 때 이 낭비가 심각해진다. 멀티사이클 구조에서는 하나의 메모리를 시분할(time-sharing)하여 이 문제를 해결한다.

세 가지 문제의 요약

정리하면, 단일 사이클 프로세서는 다음 세 가지 근본적 한계를 지닌다.

  1. 임계 경로 병목: 가장 느린 명령어(LW)가 클럭 주기를 결정하여, 모든 명령어의 실행 속도를 제한한다.
  2. 시간 낭비: 빠른 명령어(R-타입, B-타입)도 LW의 클럭 주기만큼 기다려야 하므로, 사이클의 상당 부분이 유휴 시간이다.
  3. 하드웨어 자원 낭비: IMEM/DMEM 분리, 별도 PC 가산기 등 기능이 중복되는 하드웨어가 존재한다.

이 세 가지 문제를 동시에 해결하는 방법이 바로 멀티사이클 설계이다. 다음 절에서 그 핵심 아이디어를 살펴보겠다.

수강생 단골 질문

Q: 단일 사이클에서 클럭 주기를 명령어마다 다르게 설정할 수는 없나요?

A: 동기식(synchronous) 설계에서 클럭 주파수는 하나로 고정됩니다. 명령어마다 클럭 주기를 바꾸려면 비동기식(asynchronous) 설계가 필요한데, 이는 타이밍 검증이 극도로 어렵고 현대 FPGA/ASIC 설계 흐름과 맞지 않습니다. 대신 멀티사이클 설계에서는 명령어마다 사용하는 사이클 수를 다르게 하여 이 문제를 우회합니다.

면접 포인트

"단일 사이클 프로세서의 가장 큰 단점은 무엇인가?" 라는 질문에 대해, 임계 경로가 가장 느린 명령어에 의해 결정되므로 클럭 주파수가 낮아진다는 점과, 하드웨어 자원 활용률이 낮다는 점을 모두 언급하면 좋은 점수를 받을 수 있다. 추가로 "이를 해결하기 위해 멀티사이클, 파이프라인 구조가 도입된다"까지 말하면 완벽하다.

7.2 멀티사이클의 핵심 아이디어 — 단계 분할과 자원 공유

7.1절에서 단일 사이클 프로세서의 세 가지 한계를 확인하였다. 이제 그 해결책으로 멀티사이클(Multicycle) 설계 방식을 도입한다. 멀티사이클의 핵심은 놀랍도록 단순하다. 하나의 명령어를 여러 클럭 사이클에 걸쳐 실행하고, 사이클마다 하나의 주요 동작만 수행한다. 이렇게 하면 클럭 주기를 가장 긴 단계(step)에 맞추면 되므로, 전체 명령어의 임계 경로에 맞출 필요가 없다.

비유: 코스 요리와 뷔페

단일 사이클 프로세서는 뷔페와 같다. 모든 음식(모듈)을 한 번에 차려 놓고, 손님(명령어)이 한 바퀴 돌면서 필요한 것을 모두 가져간다. 문제는 가장 많이 먹는 손님(LW)의 식사 시간에 맞춰 모든 손님이 기다려야 한다는 점이다.

멀티사이클 프로세서는 코스 요리와 같다. 한 요리사(공유 ALU)가 한 접시(단계)씩 순서대로 준비한다. 전채 → 수프 → 메인 → 디저트로 나누어 서빙하듯, 명령어 실행도 IF → ID → EX → MEM → WB로 나눈다. 요리사는 한 명이지만, 접시마다 다른 일을 하므로 도구를 재사용할 수 있다. 그리고 코스가 적은 요리(B-타입은 3코스)는 빨리 끝나고, 코스가 많은 요리(LW는 5코스)만 오래 걸린다.

비유의 한계: 실제 프로세서에서는 한 사이클에 정확히 하나의 주요 동작만 수행하며, 각 단계의 결과는 중간 레지스터에 저장되어야 한다. 요리에서는 중간 결과를 접시에 담아두듯, 하드웨어에서는 레지스터에 래치(latch)한다.

단계 분할: 명령어 실행을 5단계로 나누기

단일 사이클에서 하나의 긴 조합 논리 경로를 이루던 작업을 다섯 개의 짧은 단계로 분할한다. 각 단계는 하나의 클럭 사이클에 해당하며, 단계의 이름은 파이프라인에서도 동일하게 사용될 것이다.

단계 약칭 수행 작업 사용 자원
명령어 인출 IF (Instruction Fetch) 메모리에서 명령어를 읽어 IR에 저장, PC+4 계산 Memory, ALU
명령어 해독 ID (Instruction Decode) 명령어 디코딩, 레지스터 파일 읽기, 즉치수 생성 Register File, ImmGen
실행 EX (Execute) ALU 연산 수행 또는 메모리 주소 계산 ALU
메모리 접근 MEM (Memory Access) 데이터 메모리 읽기(LW) 또는 쓰기(SW) Memory
결과 기록 WB (Write-Back) 연산 결과 또는 로드 데이터를 레지스터에 기록 Register File

이 분할의 핵심 이점은 각 단계의 최대 지연이 200 ps라는 것이다. 따라서 클럭 주기를 800 ps가 아닌 200 ps로 설정할 수 있으며, 이는 클럭 주파수를 이론적으로 4배 향상시킨다 (실제로는 레지스터 오버헤드 때문에 약간 줄어든다).

자원 공유: 하나의 메모리, 하나의 ALU

단계 분할의 두 번째 이점은 하드웨어 자원 공유가 가능해진다는 것이다. 각 단계에서 사용하는 모듈을 살펴보면, 같은 모듈이 서로 다른 단계에서 재사용된다.

메모리 공유: IF 단계에서는 명령어를 읽고, MEM 단계에서는 데이터를 읽거나 쓴다. 두 작업은 서로 다른 사이클에서 일어나므로, 하나의 통합 메모리로 충분하다. 이 구조를 프린스턴 구조(Princeton Architecture) 또는 폰 노이만 구조(Von Neumann Architecture)라 부른다. 명령어와 데이터가 같은 메모리에 존재하므로, 메모리 용량을 두 배로 효율적으로 사용할 수 있다.

수강생 단골 질문

Q: 프린스턴 구조와 하버드 구조 중 어느 것이 더 좋은 건가요?

A: 상황에 따라 다릅니다. 하버드 구조(Harvard Architecture)는 명령어 메모리와 데이터 메모리가 분리되어 있어 동시 접근이 가능하므로, 파이프라인이나 단일 사이클에서 유리합니다. 프린스턴 구조(Princeton Architecture)는 메모리가 하나이므로 면적과 비용이 절감되지만, 명령어와 데이터를 동시에 접근할 수 없습니다. 멀티사이클에서는 동시 접근이 필요 없으므로 프린스턴 구조를 채택할 수 있습니다. 다만, Basys 3 FPGA에서는 BRAM이 듀얼 포트(dual-port)를 지원하므로, 교육 목적으로 하버드 구조를 유지하면서도 멀티사이클의 다른 이점을 얻을 수 있습니다. 본 교재에서는 통합 메모리(프린스턴) 기준으로 설명하되, 하버드 변형도 함께 소개합니다.

ALU 공유: IF 단계에서 PC+4를 계산하고, EX 단계에서 실제 연산을 수행하며, 분기 명령어에서는 분기 목표 주소를 계산한다. 단일 사이클에서는 이 세 가지 연산을 동시에 수행해야 하므로 별도의 가산기가 필요했지만, 멀티사이클에서는 서로 다른 사이클에 수행되므로 하나의 ALU로 충분하다.

중간 결과 레지스터: 단계 사이의 "릴레이 바통"

자원을 공유하면 새로운 문제가 생긴다. 한 단계에서 생성된 결과를 다음 단계에서 사용해야 하는데, 단일 사이클처럼 조합 논리가 직결되어 있지 않으므로 결과를 어딘가에 저장해야 한다. 이것이 바로 중간 결과 레지스터(Intermediate Register)의 역할이다.

멀티사이클 데이터패스에는 다음 다섯 개의 중간 레지스터가 도입된다.

레지스터 역할 저장 시점 사용 시점
IR (Instruction Register) 인출된 명령어를 명령어 실행이 끝날 때까지 유지 IF 단계 ID, EX, MEM, WB 전 단계
MDR (Memory Data Register) 메모리에서 읽은 데이터(로드 값)를 저장 MEM 단계 WB 단계
A 레지스터 파일의 rs1 데이터를 임시 저장 ID 단계 EX 단계
B 레지스터 파일의 rs2 데이터를 임시 저장 ID 단계 EX 단계, MEM 단계 (SW 데이터)
ALUOut ALU 연산 결과를 다음 사이클까지 보존 EX 단계 MEM 단계 (주소), WB 단계 (결과)

이 레지스터들은 릴레이 경주의 바통과 같다. 한 주자(단계)가 달린 결과물을 바통(레지스터)에 담아 다음 주자(단계)에게 전달한다. 바통이 없으면 결과가 사라져 다음 단계에서 데이터를 잃게 된다.

강사 꿀팁

중간 레지스터의 필요성을 학생에게 직관적으로 전달하는 방법이 있다. "단일 사이클에서는 ALU 입력에 레지스터 파일 출력이 직접 연결되어 있었다. 그런데 멀티사이클에서는 ID 단계(레지스터 읽기)와 EX 단계(ALU 연산) 사이에 클럭 경계가 있다. 클럭이 바뀌면 레지스터 파일의 입력 주소가 바뀔 수 있으므로, 읽은 값을 A/B 레지스터에 래치해 두어야 한다." 이렇게 설명하면 중간 레지스터의 존재 이유가 명확해진다.

MUX의 증가: 자원 공유의 대가

자원을 공유하면 "이번 사이클에는 이 입력을, 다음 사이클에는 저 입력을 선택하라"는 선택 논리가 필요하다. 이것이 멀티플렉서(MUX)의 증가로 나타난다.

  • IorD MUX: 메모리 주소로 PC(명령어 인출)를 쓸지, ALUOut(데이터 접근)을 쓸지 선택
  • ALUSrcA MUX: ALU의 A 입력으로 PC를 쓸지, A 레지스터를 쓸지 선택
  • ALUSrcB MUX: ALU의 B 입력으로 B 레지스터, 상수 4, 즉치수 중 무엇을 쓸지 선택
  • PCSrc MUX: 다음 PC 값으로 ALU 직접 출력(PC+4)을 쓸지, ALUOut(분기 목표)을 쓸지 선택
  • MemtoReg MUX: 레지스터에 기록할 데이터로 ALUOut(연산 결과)을 쓸지, MDR(로드 데이터)을 쓸지 선택

MUX가 늘어나면 제어 신호도 함께 증가한다. 단일 사이클의 조합 논리 제어와 달리, 멀티사이클에서는 유한 상태 기계(FSM, Finite State Machine)가 상태별로 제어 신호를 출력한다. FSM 제어 유닛의 상세 설계는 Chapter 08에서 다룬다.

명령어별 사이클 수: CPI의 등장

멀티사이클의 중요한 특성 중 하나는, 명령어마다 소요되는 사이클 수가 다르다는 것이다. 이를 CPI(Cycles Per Instruction, 명령어당 사이클 수)라 부른다.

명령어 유형 사용 단계 CPI
R-타입 (ADD, SUB 등) IF → ID → EX → WB 4
I-타입 연산 (ADDI 등) IF → ID → EX → WB 4
LW (로드) IF → ID → EX → MEM → WB 5
SW (스토어) IF → ID → EX → MEM 4
B-타입 (BEQ 등) IF → ID → EX 3
JAL / JALR IF → ID → EX → WB 4

단일 사이클에서는 CPI가 항상 1이었지만 클럭 주기가 길었다. 멀티사이클에서는 CPI가 3~5로 증가하지만 클럭 주기가 짧아진다. 프로세서의 전체 성능은 다음 공식으로 비교한다.

실행 시간 = 명령어 수 (N) × CPI × 클럭 주기 (Tclk)

어느 쪽이 더 빠른지는 프로그램의 명령어 믹스(instruction mix)에 달려 있다. LW가 많은 프로그램에서는 멀티사이클의 평균 CPI가 높아져 이득이 줄어들고, 분기가 많은 프로그램에서는 CPI=3인 분기의 비율이 높아 멀티사이클이 유리할 수 있다. 이 성능 비교는 7.4절에서 정량적으로 다시 살펴본다.

실무 팁

RISC-V의 공식 벤치마크인 CoreMark를 기준으로 하면, 일반적인 프로그램의 명령어 믹스는 대략 R/I-타입 50%, Load 20%, Store 10%, Branch 18%, Jump 2% 정도이다. 이 경우 멀티사이클의 평균 CPI는 약 3.9가 된다. (0.50×4 + 0.20×5 + 0.10×4 + 0.18×3 + 0.02×4 = 3.94)

7.3 멀티사이클 데이터패스 설계

앞 절에서 멀티사이클의 핵심 아이디어인 단계 분할, 자원 공유, 중간 레지스터를 이해하였다. 이제 이 아이디어를 실제 데이터패스 회로로 구체화한다. 본 절에서는 멀티사이클 데이터패스의 전체 구조를 설계하고, 각 구성 요소의 역할과 연결 관계를 상세히 설명한다. SystemVerilog 구현 코드도 함께 제시하므로, 시뮬레이션까지 직접 수행할 수 있을 것이다.

전체 구조 개관

멀티사이클 데이터패스의 전체 구조를 그림 7.3에 나타낸다. 단일 사이클 데이터패스(그림 6.3)와 비교하면 다음 변화를 확인할 수 있다.

  1. IMEM과 DMEM이 하나의 Memory로 통합되었다. IorD MUX가 주소를 선택한다.
  2. PC+4 전용 가산기가 사라지고 ALU가 그 역할을 대신한다. IF 단계에서 ALU에 PC와 상수 4를 입력하여 PC+4를 계산한다.
  3. 5개의 중간 레지스터(IR, MDR, A, B, ALUOut)가 추가되었다.
  4. 5개의 MUX(IorD, ALUSrcA, ALUSrcB, PCSrc, MemtoReg)가 추가 또는 확장되었다.
  5. 제어 유닛이 FSM 기반으로 변경되었다 (상세 설계는 Ch08).

구성 요소 1: 프로그램 카운터 (PC)

PC는 단일 사이클과 동일하게 32비트 레지스터이지만, 갱신 방식이 달라진다. 단일 사이클에서는 매 사이클 무조건 PC가 갱신되었으나, 멀티사이클에서는 특정 단계에서만 PC를 갱신해야 한다. 이를 위해 두 가지 제어 신호가 사용된다.

  • PCWrite: 무조건 PC 갱신 (IF 단계 완료 시)
  • PCWriteCond: 조건부 PC 갱신 (분기 성공 시, ALU의 Zero 플래그와 AND)

PC의 실제 인에이블 신호는 PC_en = PCWrite | (PCWriteCond & Zero)로 결합된다. 


// PC 인에이블: 무조건 쓰기 OR (조건부 쓰기 AND ALU Zero)
assign pc_en = pc_write | (pc_write_cond & alu_zero);

always_ff @(posedge clk or negedge rst_n) begin
   if (!rst_n)
      pc_reg <= 32'h0000_0000;  // 리셋 시 PC = 0
   else if (pc_en)
      pc_reg <= pc_next;
end

구성 요소 2: 통합 메모리와 IorD MUX

통합 메모리(Unified Memory)는 프린스턴 구조의 핵심이다. 하나의 메모리가 명령어 인출과 데이터 접근을 모두 담당하며, IorD(Instruction or Data) MUX가 메모리 주소를 선택한다.

  • IorD = 0: PC를 주소로 사용 (IF 단계 — 명령어 인출)
  • IorD = 1: ALUOut을 주소로 사용 (MEM 단계 — 데이터 접근)

// 메모리 주소 선택 MUX (IorD)
assign mem_addr = i_or_d ? alu_out_reg : pc_reg;

// 통합 메모리 — 동기 읽기/쓰기
logic [31:0] memory [0:4095]; // 16KB (4K 워드)

always_ff @(posedge clk) begin
   if (mem_read)
      mem_data_out <= memory[mem_addr[13:2]]; // 워드 정렬
end

always_ff @(posedge clk) begin
   if (mem_write)
      memory[mem_addr[13:2]] <= b_reg; // 스토어 데이터 = B 레지스터
end
실무 팁

FPGA에서 메모리를 logic [31:0] memory [0:4095];로 선언하면 Vivado가 자동으로 BRAM(Block RAM)으로 추론(infer)한다. 단, 비동기 읽기(combinational read)로 선언하면 BRAM이 아닌 분산 RAM(Distributed RAM)으로 추론될 수 있으므로 주의해야 한다. 위 코드처럼 동기 읽기(always_ff)를 사용하면 BRAM으로 확실하게 추론된다. 멀티사이클에서는 메모리 읽기 결과를 다음 사이클에 사용하므로 동기 읽기가 자연스럽게 맞아떨어진다.

구성 요소 3: 명령어 레지스터 (IR)와 메모리 데이터 레지스터 (MDR)

메모리에서 읽은 데이터는 두 가지 용도로 사용된다. IF 단계에서 읽은 것은 명령어이고, MEM 단계에서 읽은 것은 로드 데이터이다. 이 둘을 구분하기 위해 별도의 레지스터를 사용한다.

IR(Instruction Register)은 명령어를 저장하며, 명령어 실행이 완료될 때까지 값을 유지해야 한다. 따라서 IRWrite 인에이블 신호가 IF 단계에서만 활성화된다. 반면, MDR(Memory Data Register)은 매 사이클 자동으로 갱신된다. 실제로 의미 있는 값이 들어가는 것은 MEM 단계뿐이며, 다른 단계에서 MDR의 값은 무시된다. 


// 명령어 레지스터 (IR) — IRWrite로 제어
always_ff @(posedge clk or negedge rst_n) begin
   if (!rst_n)
      ir_reg <= 32'h0000_0013;  // NOP (ADDI x0, x0, 0)
   else if (ir_write)
      ir_reg <= mem_data_out;
end

// 메모리 데이터 레지스터 (MDR) — 매 사이클 갱신
always_ff @(posedge clk) begin
   mdr_reg <= mem_data_out;
end
수강생 단골 질문

Q: MDR은 왜 인에이블 신호 없이 매 사이클 갱신하나요? IR처럼 제어하면 안 되나요?

A: MDR에 인에이블을 두어도 기능적으로 동일하게 동작합니다. 그러나 MDR의 값은 LW 명령어의 WB 단계에서만 사용되고, 다른 시점에는 무시됩니다. 따라서 매 사이클 갱신하더라도 잘못된 값이 레지스터 파일에 기록될 위험이 없습니다. 인에이블을 생략하면 제어 신호 하나를 줄일 수 있어 설계가 간결해집니다. 단, IR은 다릅니다. IR의 값은 모든 단계에서 디코딩에 사용되므로, IF 이후에 메모리에서 다른 값이 읽히더라도 IR이 바뀌면 안 됩니다.

구성 요소 4: 레지스터 파일, A 레지스터, B 레지스터

레지스터 파일 자체는 단일 사이클과 동일하다. 32개의 32비트 레지스터로 구성되며, x0은 항상 0으로 고정된다. 비동기 읽기, 동기 쓰기 방식을 따른다.

ID 단계에서 레지스터 파일의 rs1, rs2 출력을 읽으면, 이 값을 다음 사이클(EX 단계)까지 보존해야 한다. 이를 위해 A 레지스터와 B 레지스터가 존재한다. A에는 rs1 데이터가, B에는 rs2 데이터가 저장된다. 


// 레지스터 파일 — 비동기 읽기, 동기 쓰기
assign rs1_data = (rs1_addr == 5'd0) ? 32'd0 : reg_file[rs1_addr];
assign rs2_data = (rs2_addr == 5'd0) ? 32'd0 : reg_file[rs2_addr];

always_ff @(posedge clk) begin
   if (reg_write && (rd_addr != 5'd0))
      reg_file[rd_addr] <= reg_write_data;
end

// A/B 레지스터 — ID 단계에서 래치
always_ff @(posedge clk) begin
   a_reg <= rs1_data;
   b_reg <= rs2_data;
end

A/B 레지스터가 매 사이클 갱신되어도 문제가 없는 이유는 MDR과 동일하다. 이 값이 실제로 사용되는 것은 EX 단계뿐이며, 다른 단계에서는 ALUSrcA/ALUSrcB MUX가 다른 입력을 선택하므로 A/B의 값은 무시된다.

구성 요소 5: 즉치수 생성기 (Immediate Generator)

즉치수 생성기는 IR에 저장된 명령어에서 즉치수(Immediate)를 추출하고 부호 확장(Sign Extension)한다. Chapter 04에서 설계한 것과 동일한 논리이지만, 입력이 IMEM 출력이 아닌 IR 레지스터의 출력이라는 점이 다르다. IR이 명령어를 유지하고 있으므로, 즉치수 생성기의 출력도 안정적으로 유지된다. 


// 즉치수 생성기 — IR에서 직접 추출
always_comb begin
   case (opcode)
      // I-타입: ADDI, LW, JALR 등
      7'b0010011, 7'b0000011, 7'b1100111:
         imm_ext = {{20{ir_reg[31]}}, ir_reg[31:20]};

      // S-타입: SW 등
      7'b0100011:
         imm_ext = {{20{ir_reg[31]}}, ir_reg[31:25], ir_reg[11:7]};

      // B-타입: BEQ 등
      7'b1100011:
         imm_ext = {{19{ir_reg[31]}}, ir_reg[31], ir_reg[7],
                     ir_reg[30:25], ir_reg[11:8], 1'b0};

      // U-타입: LUI, AUIPC
      7'b0110111, 7'b0010111:
         imm_ext = {ir_reg[31:12], 12'd0};

      // J-타입: JAL
      7'b1101111:
         imm_ext = {{11{ir_reg[31]}}, ir_reg[31], ir_reg[19:12],
                     ir_reg[20], ir_reg[30:21], 1'b0};

      default:
         imm_ext = 32'd0;
   endcase
end

구성 요소 6: 공유 ALU와 ALUOut 레지스터

공유 ALU는 멀티사이클 설계의 핵심이다. 하나의 ALU가 매 사이클 다른 용도로 사용된다.

단계 ALU A 입력 ALU B 입력 연산 결과 용도
IF PC 4 (상수) ADD PC+4 → 다음 PC 후보
EX (R-타입) A (rs1) B (rs2) 명령어에 따라 연산 결과 → ALUOut
EX (LW/SW) A (rs1) 즉치수 ADD 메모리 주소 → ALUOut
EX (BEQ) A (rs1) B (rs2) SUB Zero 플래그 → 분기 판정

ALU의 입력은 ALUSrcA와 ALUSrcB MUX에 의해 선택된다. ALUSrcA는 PC와 A 레지스터 중 하나를, ALUSrcB는 B 레지스터, 상수 4, 즉치수 중 하나를 선택한다.

ALU 연산 결과는 ALUOut 레지스터에 저장된다. 이 레지스터의 역할은 두 가지이다. 첫째, EX 단계의 연산 결과를 MEM 또는 WB 단계까지 보존한다. 둘째, 분기 명령어에서 계산된 목표 주소를 PC에 기록하기 위해 한 사이클 동안 유지한다. 


// ALU 입력 선택
assign alu_a = alu_src_a ? a_reg : pc_reg;

always_comb begin
   case (alu_src_b)
      2'b00:   alu_b = b_reg;     // R-타입: rs2
      2'b01:   alu_b = 32'd4;     // IF: 상수 4
      2'b10:   alu_b = imm_ext;   // I/S/B-타입: 즉치수
      default: alu_b = b_reg;
   endcase
end

// ALU 연산
always_comb begin
   alu_zero = 1'b0;
   case (alu_op)
      4'b0000: alu_result = alu_a + alu_b;       // ADD
      4'b0001: alu_result = alu_a - alu_b;       // SUB
      4'b0010: alu_result = alu_a & alu_b;       // AND
      4'b0011: alu_result = alu_a | alu_b;       // OR
      4'b0100: alu_result = alu_a ^ alu_b;       // XOR
      // ... (SLT, SLTU, SLL, SRL, SRA 생략)
      default: alu_result = alu_a + alu_b;
   endcase
   alu_zero = (alu_result == 32'd0);
end

// ALUOut 레지스터 — 매 사이클 ALU 결과 저장
always_ff @(posedge clk) begin
   alu_out_reg <= alu_result;
end

구성 요소 7: PC 소스 MUX (PCSrc)

PC에 기록될 다음 값은 세 가지 후보 중 하나이다.

  • PCSrc = 00: ALU 직접 출력 (PC+4, IF 단계에서 즉시 갱신)
  • PCSrc = 01: ALUOut (분기 목표 주소, EX 단계에서 계산된 결과)
  • PCSrc = 10: 점프 주소 (JAL/JALR)

// PC 소스 MUX
always_comb begin
   case (pc_src)
      2'b00:   pc_next = alu_result;     // PC+4
      2'b01:   pc_next = alu_out_reg;    // 분기 목표
      2'b10:   pc_next = {alu_out_reg[31:28], ir_reg[25:0], 2'b00}; // 점프
      default: pc_next = alu_result;
   endcase
end

구성 요소 8: Write-Back MUX (MemtoReg)

레지스터 파일에 기록할 데이터는 명령어 유형에 따라 다르다.

  • MemtoReg = 00: ALUOut (R-타입, I-타입 연산 결과)
  • MemtoReg = 01: MDR (LW로 메모리에서 읽은 데이터)
  • MemtoReg = 10: PC (JAL/JALR의 복귀 주소)

하버드 변형: 분리 메모리로 구현할 때

앞서 설명한 통합 메모리(프린스턴 구조)는 교과서적인 멀티사이클 데이터패스의 표준 형태이다. 그러나 Basys 3 FPGA에서 실제로 구현할 때는 하버드 변형을 선택할 수도 있다. Basys 3의 BRAM은 듀얼 포트를 지원하므로, IMEM과 DMEM을 별도로 유지하면서도 나머지 멀티사이클 이점(공유 ALU, 짧은 클럭 주기)을 그대로 얻을 수 있다.

하버드 변형에서는 IorD MUX가 필요 없어지고, 대신 IMEM과 DMEM에 별도의 읽기/쓰기 인에이블 신호를 공급한다. IF 단계에서는 IMEM을, MEM 단계에서는 DMEM을 활성화한다. 이 변형의 장점은 메모리 구조가 단일 사이클과 동일하여 이행(migration)이 쉽다는 것이다.

강사 꿀팁

학생들에게 "프린스턴과 하버드 중 어느 것을 구현할지"를 과제로 선택하게 하면 두 구조의 트레이드오프를 체감할 수 있습니다. 프린스턴은 면적 절감, 하버드는 구현 용이성이 장점입니다. 실습 환경이 Basys 3라면 하버드 변형을 권장합니다. BRAM이 충분하기 때문입니다.

전체 제어 신호 목록

멀티사이클 데이터패스가 올바르게 동작하려면, FSM 제어 유닛이 각 단계에서 적절한 제어 신호를 출력해야 한다. 다음 표에 전체 제어 신호를 정리한다. 각 신호의 상세한 상태별 값은 Chapter 08에서 FSM을 설계할 때 확정한다.

제어 신호 비트 폭 역할
PCWrite 1 무조건 PC 갱신
PCWriteCond 1 조건부 PC 갱신 (분기 성공 시)
IorD 1 메모리 주소 선택 (0: PC, 1: ALUOut)
MemRead 1 메모리 읽기 인에이블
MemWrite 1 메모리 쓰기 인에이블
IRWrite 1 명령어 레지스터 쓰기 인에이블
RegWrite 1 레지스터 파일 쓰기 인에이블
MemtoReg 2 Write-Back 데이터 선택
ALUSrcA 1 ALU A 입력 선택
ALUSrcB 2 ALU B 입력 선택
ALUOp 4 ALU 연산 코드
PCSrc 2 PC 소스 선택

총 12개의 제어 신호가 존재하며, 이 중 일부는 단일 사이클에도 있었지만(RegWrite, MemWrite 등), IorD, IRWrite, PCWriteCond, ALUSrcB의 확장 등이 멀티사이클에서 새로 추가된 것이다. 제어 신호의 수가 증가했지만, FSM의 각 상태에서 출력값이 고정되므로 설계 복잡도는 관리 가능한 수준이다.

면접 포인트

"멀티사이클 데이터패스에서 단일 사이클 대비 추가되는 하드웨어는 무엇인가?"라는 질문에 대해, 중간 레지스터 5개(IR, MDR, A, B, ALUOut)와 MUX 증가(IorD, ALUSrcA/B 확장, PCSrc, MemtoReg), 그리고 FSM 제어 유닛을 언급하되, 제거되는 하드웨어(DMEM 중복, PC+4 전용 가산기)도 함께 설명하면 균형 잡힌 답변이 된다.

스스로 점검

7.4 단일 사이클 vs 멀티사이클 데이터패스 비교

이제 두 구조를 정량적으로 비교할 준비가 되었다. 단순히 "멀티사이클이 더 낫다"가 아니라, 각 구조의 장단점과 적용 시나리오를 공학적으로 분석하는 것이 이 절의 목표이다.

구조적 비교: 하드웨어 면적

하드웨어 면적 측면에서 멀티사이클의 이점은 명확하다.

구성 요소 단일 사이클 멀티사이클 변화
메모리 모듈 IMEM + DMEM (2개) 통합 Memory (1개) 50% 절감
ALU + 가산기 ALU + PC Adder (2개) 공유 ALU (1개) 50% 절감
중간 레지스터 없음 IR, MDR, A, B, ALUOut (5개) 증가
MUX 4개 5개 이상 소폭 증가
제어 유닛 조합 논리 FSM (순차 논리) 복잡도 증가

중간 레지스터 5개의 면적은 32비트 레지스터 5개, 즉 160개의 플립플롭(flip-flop)에 해당한다. 이는 Basys 3의 41,600개 FF 중 0.4%에 불과하다. 반면, 메모리 모듈을 하나로 줄이면 BRAM 블록을 절반으로 절감할 수 있다. 따라서 전체적으로 멀티사이클이 면적 효율에서 유리하다.

성능 비교: 실행 시간 분석

면적에서는 멀티사이클이 유리하지만, 성능은 단순하지 않다. 성능 비교의 핵심 공식을 다시 살펴보자.

실행 시간 = 명령어 수 (N) × 평균 CPI × 클럭 주기 (Tclk)

구체적인 수치로 비교해 보겠다. 다음과 같은 프로그램이 있다고 가정한다.

명령어 유형 비율 단일 사이클 CPI 멀티사이클 CPI
R/I-타입 연산 50% 1 4
LW 20% 1 5
SW 10% 1 4
Branch 18% 1 3
Jump 2% 1 4

단일 사이클: 평균 CPI = 1.0, Tclk = 800 ps
실행 시간 = N × 1.0 × 800 = 800N ps

멀티사이클: 평균 CPI = 0.50×4 + 0.20×5 + 0.10×4 + 0.18×3 + 0.02×4 = 3.94
클럭 주기를 200 ps + 레지스터 오버헤드 약 20 ps = 220 ps로 가정하면,
실행 시간 = N × 3.94 × 220 = 867N ps

이 예시에서 멀티사이클은 단일 사이클보다 약 8% 느리다. 충격적인 결과일 수 있지만, 이는 레지스터 오버헤드와 높은 CPI 때문이다. 클럭 주기가 더 짧아지면(예: 200 ps 정확히) 두 구조의 성능은 거의 동일해진다.

실무 팁

실제 FPGA에서는 라우팅 지연(routing delay)과 셋업 타임(setup time) 등의 오버헤드가 존재한다. 단일 사이클의 800 ps 경로에서도 레지스터 오버헤드가 포함되므로, 실제 비교는 이론 수치보다 멀티사이클에 유리할 수 있다. Vivado에서 두 구조를 합성하여 WNS(Worst Negative Slack)를 비교하는 것이 가장 정확한 성능 비교 방법이며, 이는 Chapter 12.5에서 파이프라인까지 포함하여 3종 비교를 수행한다.

그렇다면 멀티사이클은 왜 배우는가?

성능만 놓고 보면 멀티사이클이 단일 사이클보다 반드시 좋다고 말하기 어렵다. 그렇다면 왜 이 구조를 학습하는 것일까? 그 이유는 크게 세 가지이다.

  1. 파이프라인의 전제 이해: 파이프라인은 멀티사이클의 각 단계를 동시에 실행하는 구조이다. 멀티사이클에서 IF, ID, EX, MEM, WB로 나누어 실행하는 경험이 없으면, 파이프라인의 "왜 레지스터를 삽입하는가?"라는 근본적 질문에 답하기 어렵다. 멀티사이클의 중간 레지스터(IR, A, B, ALUOut, MDR)는 파이프라인 레지스터의 직접적 선조(ancestor)이다.
  2. FSM 기반 제어 학습: 멀티사이클의 FSM 제어 유닛은 디지털 설계의 핵심 패턴이다. "상태에 따라 제어 신호를 다르게 출력한다"는 개념은 버스 프로토콜(Chapter 16~17), 캐시 미스 처리(Chapter 15), 예외 처리(Chapter 19) 등 이후 모든 복잡한 제어 로직의 기반이 된다.
  3. 면적 최적화 기법: 자원 공유는 ASIC/FPGA 설계에서 항상 중요한 최적화 기법이다. 면적 제약이 엄격한 IoT 프로세서나 임베디드 컨트롤러에서는 멀티사이클 구조가 실제로 채택된다.
비유: 수동 변속기와 자동 변속기

멀티사이클은 수동 변속기와 같다. 현대 자동차의 대부분은 자동 변속기(파이프라인)를 사용하지만, 수동 변속기를 배우면 엔진과 변속기의 관계를 체감할 수 있고, 자동 변속기가 왜 그렇게 동작하는지 직관적으로 이해할 수 있다. 마찬가지로, 멀티사이클을 이해하면 파이프라인의 설계 근거를 자연스럽게 파악할 수 있다.

중간 레지스터 도입 근거: "왜 하필 여기에 레지스터를?"

중간 레지스터의 배치 위치는 임의적인 것이 아니라, 각 단계의 경계에 놓인다. 이 원리를 이해하면 파이프라인 레지스터의 배치도 자연스럽게 따라온다.

단계 경계 중간 레지스터 파이프라인 레지스터 (Ch09 예고)
IF → ID IR (명령어 유지) IF/ID 레지스터
ID → EX A, B (레지스터 데이터 유지) ID/EX 레지스터
EX → MEM ALUOut (연산 결과 유지) EX/MEM 레지스터
MEM → WB MDR (메모리 데이터 유지) MEM/WB 레지스터

위 표를 보면, 멀티사이클의 중간 레지스터가 파이프라인 레지스터와 정확히 1:1로 대응됨을 알 수 있다. 차이점은 멀티사이클에서는 한 명령어가 순차적으로 이 레지스터들을 사용하고, 파이프라인에서는 여러 명령어가 동시에 각기 다른 레지스터를 사용한다는 것이다. 이 대응 관계를 머릿속에 새기면, Chapter 09에서 파이프라인 레지스터를 설계할 때 매우 수월해질 것이다.

면접 포인트

"단일 사이클, 멀티사이클, 파이프라인 프로세서의 차이점을 설명하시오"는 프로세서 설계 면접의 고전적 질문이다. 핵심 답변 구조는 다음과 같다.

  • 단일 사이클: CPI=1, 긴 클럭, 자원 중복, 조합 논리 제어
  • 멀티사이클: CPI=3~5, 짧은 클럭, 자원 공유, FSM 제어
  • 파이프라인: 이상적 CPI=1, 짧은 클럭, 파이프라인 레지스터, 해저드 처리 필요

여기에 "파이프라인은 멀티사이클의 각 단계를 동시에 실행하는 것"이라는 한 마디를 추가하면 세 구조의 관계를 명확히 보여줄 수 있다.

Basys 3 합성 예측

실제 FPGA 합성 결과의 정확한 수치는 Chapter 12.5에서 세 구조를 모두 합성하여 비교하겠지만, 여기서 멀티사이클의 예상 수치를 정리해 둔다.

항목 단일 사이클 (Ch06 결과) 멀티사이클 (예상)
최대 클럭 주파수 ~25 MHz ~80-100 MHz
LUT 사용량 ~2,500 ~1,800 (ALU/가산기 공유)
FF 사용량 ~200 ~360 (중간 레지스터 추가)
BRAM 사용량 2블록 (IMEM + DMEM) 1블록 (통합 메모리)

멀티사이클의 클럭 주파수가 단일 사이클의 3~4배로 예상되는 것은, 임계 경로가 전체 데이터패스(~40 ns)에서 가장 긴 단계(~10-12 ns)로 줄어들기 때문이다. LUT 절감은 PC+4 가산기 제거와 메모리 주소 디코딩 단순화에서 비롯된다.

  • 멀티사이클의 평균 CPI가 4이고 클럭 주파수가 단일 사이클의 4배라면, 전체 성능은 동일한가?
  • 멀티사이클의 중간 레지스터 IR, A, B, ALUOut, MDR은 각각 파이프라인의 어떤 레지스터에 대응하는가?
  • LW가 전체 명령어의 30%를 차지하는 프로그램에서 멀티사이클의 평균 CPI는 얼마인가? (나머지: R/I 40%, SW 10%, Branch 18%, Jump 2%)

7.5 본 챕터 요약 및 다음 단계

이 챕터에서는 단일 사이클 프로세서의 한계를 분석하고, 멀티사이클 데이터패스의 설계 원리와 전체 구조를 학습하였다. 핵심 내용을 정리하면 다음과 같다.

핵심 개념 정리

  • 단일 사이클의 한계: 임계 경로가 가장 느린 명령어(LW)에 의해 결정되어 클럭 주파수가 낮아지고, IMEM/DMEM 분리와 PC 전용 가산기로 인해 하드웨어 자원이 낭비된다.
  • 멀티사이클의 핵심 아이디어: 명령어 실행을 IF → ID → EX → MEM → WB의 5단계로 분할하고, 사이클마다 하나의 단계만 수행한다. 이를 통해 클럭 주기를 가장 긴 단계에 맞출 수 있다.
  • 자원 공유: 통합 메모리(프린스턴 구조)로 IMEM/DMEM을 하나로 합치고, 공유 ALU로 PC+4 계산과 연산을 모두 처리한다.
  • 중간 레지스터: IR, MDR, A, B, ALUOut — 각 단계의 결과를 다음 사이클까지 보존하는 "릴레이 바통" 역할을 한다.
  • MUX 증가: 자원 공유의 대가로 IorD, ALUSrcA, ALUSrcB, PCSrc, MemtoReg MUX가 추가되며, FSM이 상태별로 이를 제어한다.
  • CPI와 성능: 멀티사이클의 CPI는 3~5로 증가하지만 클럭 주기가 크게 짧아지므로, 전체 성능은 명령어 믹스에 의존한다.
  • 파이프라인과의 관계: 멀티사이클의 중간 레지스터(IR/A,B/ALUOut/MDR)는 파이프라인 레지스터(IF/ID, ID/EX, EX/MEM, MEM/WB)와 1:1 대응한다. 멀티사이클의 순차 실행을 동시 실행으로 전환하면 파이프라인이 된다.
강사 꿀팁

학생들에게 "멀티사이클을 배우는 진짜 이유는 파이프라인을 이해하기 위해서"라는 메시지를 반복적으로 전달하십시오. 멀티사이클 자체의 성능 이점보다는, "단계 분할 → 중간 레지스터 → 파이프라인 레지스터"라는 개념적 흐름이 교육의 핵심입니다. 이 챕터를 건너뛰면 파이프라인 해저드(Ch10~11)에서 학생들의 이해도가 급격히 떨어지는 경향이 있습니다.

핵심 정리

  • 단일 사이클의 임계 경로는 LW 명령어에 의해 결정되며, 이는 전체 클럭 주파수를 제한한다.
  • 멀티사이클은 명령어 실행을 여러 단계로 나누어 클럭 주기를 짧게 하고, 하드웨어를 공유한다.
  • 5개의 중간 레지스터(IR, MDR, A, B, ALUOut)가 단계 간 데이터를 전달하며, 이는 파이프라인 레지스터의 원형이다.
  • 프린스턴 구조(통합 메모리)와 하버드 구조(분리 메모리) 양쪽 모두 멀티사이클에서 구현 가능하다.
  • 멀티사이클의 제어는 FSM(유한 상태 기계) 기반이며, 이는 Chapter 08에서 설계한다.

연습문제

  1. [기억] 멀티사이클 데이터패스에 추가되는 5개의 중간 레지스터 이름과 각각의 역할을 나열하시오.
  2. [이해] IorD MUX가 필요한 이유를 단일 사이클과 비교하여 설명하시오.
  3. [적용] 다음 명령어 믹스에서 멀티사이클의 평균 CPI를 계산하시오: R-타입 40%, LW 25%, SW 15%, Branch 15%, Jump 5%.
  4. [분석] 멀티사이클에서 ALUOut 레지스터를 제거하면 어떤 명령어의 실행에 문제가 발생하는지 분석하시오.
  5. [평가] BRAM 블록이 4개만 남은 FPGA에서 프린스턴 구조와 하버드 구조 중 어느 것을 선택해야 하는지, 근거를 들어 판단하시오.

다음 챕터 예고

Chapter 08에서는 이 챕터에서 설계한 데이터패스를 제어하는 FSM(유한 상태 기계)을 설계한다. 각 명령어 유형별로 FSM의 상태 전이도(state transition diagram)를 그리고, 상태별 제어 신호 출력을 SystemVerilog로 구현한다. 데이터패스(이번 챕터)와 FSM 제어 유닛(다음 챕터)이 결합되면, 멀티사이클 RV32I 프로세서가 완성되어 시뮬레이션에서 프로그램을 실행할 수 있게 된다. 또한 단일 사이클 대비 실제 성능 비교도 수행할 것이다.
