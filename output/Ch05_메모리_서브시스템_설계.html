Chapter 05

메모리 서브시스템 설계

프로세서가 명령어를 가져오고 데이터를 읽고 쓰려면, 반드시 메모리가 필요합니다. 이 챕터에서는 RV32I 단일 사이클 프로세서의 명령어 메모리(IMEM)와 데이터 메모리(DMEM)를 설계하고, 주소 공간을 체계적으로 분할하는 메모리 맵(Memory Map)을 구성합니다.

학습 목표

  • 하버드 구조(Harvard Architecture)와 프린스턴 구조(Von Neumann Architecture)의 차이를 설명할 수 있다.
  • $readmemh와 COE 파일을 사용하여 명령어 메모리를 초기화할 수 있다.
  • 바이트 인에이블(byte enable) 로직을 설계하여 LB/LBU/LH/LHU/LW/SB/SH/SW 명령어를 구현할 수 있다.
  • IMEM, DMEM, MMIO 영역으로 구성된 메모리 맵을 설계할 수 있다.
  • 로드-스토어 시퀀스를 검증하는 테스트벤치를 작성할 수 있다.

5.1 이 챕터에서 만들 모듈 — 전체 데이터패스 내 위치

Chapter 04에서 우리는 ALU, 레지스터 파일, 즉치수 생성기를 설계하였습니다. 이 세 모듈은 프로세서의 "연산 엔진"에 해당합니다. 그러나 프로세서가 실제로 동작하려면, 연산 대상인 명령어와 데이터를 저장하고 공급하는 메모리가 반드시 필요합니다. 이번 챕터에서는 바로 그 메모리 서브시스템(Memory Subsystem)을 설계합니다.

하버드 구조 vs 프린스턴 구조

프로세서와 메모리를 연결하는 방식에는 크게 두 가지 구조가 있습니다. 첫째, 프린스턴 구조(Von Neumann Architecture)는 명령어와 데이터가 하나의 메모리를 공유하는 방식입니다. 구조가 단순하지만, 하나의 포트로 명령어 인출(Instruction Fetch)과 데이터 접근(Data Access)을 동시에 수행할 수 없으므로 성능 병목이 발생할 수 있습니다. 둘째, 하버드 구조(Harvard Architecture)는 명령어 메모리와 데이터 메모리를 물리적으로 분리하여 독립된 접근 경로를 제공합니다. 동일 사이클에 명령어 인출과 데이터 접근을 동시에 수행할 수 있어 성능상 유리합니다.

비유: 프린스턴 구조는 하나의 도서관 창구에서 대출(데이터 읽기)과 반납(데이터 쓰기)과 도서 목록 조회(명령어 인출)를 한 줄로 처리하는 것과 같습니다. 하버드 구조는 대출 창구와 목록 조회 창구를 분리한 것입니다. 동시에 두 가지 업무가 진행되므로 대기 시간이 줄어듭니다.

우리가 설계하는 RV32I 단일 사이클 프로세서는 하버드 구조를 채택합니다. 그 이유는 명확합니다. 단일 사이클 프로세서에서는 한 클럭 사이클 안에 명령어 인출(IF)과 메모리 접근(MEM) 단계가 모두 완료되어야 합니다. 만약 명령어 메모리와 데이터 메모리가 동일한 포트를 공유한다면, 같은 사이클에 명령어를 읽으면서 동시에 Load/Store 데이터를 처리하는 것이 불가능합니다. 따라서 IMEM(Instruction Memory)과 DMEM(Data Memory)을 분리하여 각각 독립된 주소 버스와 데이터 버스를 갖도록 설계합니다.

🎯 면접 포인트

Q: 하버드 구조와 폰 노이만 구조의 차이는 무엇이며, 현대 프로세서는 어떤 구조를 사용합니까?

A: 하버드 구조는 명령어 메모리와 데이터 메모리가 분리되어 동시 접근이 가능하고, 폰 노이만 구조는 통합 메모리를 사용합니다. 현대 프로세서는 L1 캐시 수준에서는 하버드 구조(I-Cache/D-Cache 분리)를, L2 이하에서는 통합 메모리를 사용하는 수정된 하버드 구조(Modified Harvard Architecture)를 채택합니다.

5.2 명령어 메모리 (IMEM) 설계

명령어 메모리(Instruction Memory, IMEM)는 프로세서가 실행할 프로그램을 저장하는 읽기 전용 메모리입니다. 프로그램 카운터(PC)가 주소를 제공하면, IMEM은 해당 주소의 32비트 명령어를 출력합니다. 실행 중에 프로그램 코드가 변경되지 않으므로, IMEM은 ROM(Read-Only Memory)으로 동작합니다.

설계 요구사항 정리

IMEM 설계 전에 요구사항을 명확히 합시다. 첫째, 용량은 16KB(4096워드)로 설정합니다. Basys 3 보드의 Artix-7 XC7A35T에는 36Kb Block RAM(BRAM)이 50개 있으며, 16KB는 BRAM 약 4개를 사용하여 충분히 수용 가능합니다. 둘째, 데이터 폭은 32비트(1워드)입니다. RV32I의 모든 명령어는 32비트 고정 길이이므로, 한 번의 접근으로 하나의 완전한 명령어를 읽을 수 있습니다. 셋째, 읽기 방식은 비동기 읽기(조합 논리)입니다. 단일 사이클 프로세서에서 IMEM 읽기에 클럭 지연이 있으면 안 되므로, 주소가 변경되면 즉시 명령어가 출력되어야 합니다.

💡 실무 팁

Vivado에서 비동기 읽기 메모리를 기술하면 분산 RAM(Distributed RAM, LUTRAM)으로 추론될 수 있습니다. 16KB 크기에서 LUTRAM은 LUT 자원을 상당량 소모합니다. BRAM을 강제하려면 동기 읽기로 변경하되, 파이프라인 프로세서(Ch09 이후)에서는 이것이 자연스럽습니다. 단일 사이클에서는 우선 비동기 읽기를 사용하고, 합성 결과를 확인하여 조정합니다.

IMEM 내부 구조

PC는 바이트 주소(byte address)를 출력합니다. 예를 들어 첫 번째 명령어의 주소는 0x00000000, 두 번째 명령어는 0x00000004, 세 번째는 0x00000008입니다. 그러나 IMEM 내부의 메모리 배열은 워드 단위로 인덱싱됩니다. 따라서 PC 값을 4로 나누어(하위 2비트 제거) 워드 주소로 변환해야 합니다. SystemVerilog에서는 비트 슬라이싱 pc_i[ADDR_WIDTH+1:2]으로 간단히 처리합니다.

SystemVerilog 구현

아래 코드는 IMEM의 전체 SystemVerilog 구현입니다. 핵심 요소를 하나씩 살펴보겠습니다.


module instruction_memory #(
   parameter ADDR_WIDTH = 12,                    // 주소 비트 수 (12비트 = 4096 워드)
   parameter MEM_DEPTH  = 2**ADDR_WIDTH,         // 메모리 깊이 (4096 워드 = 16 KB)
   parameter INIT_FILE  = "program.hex"          // 초기화 파일 경로
)(
   input  logic [31:0] pc_i,                     // PC 입력 (바이트 주소)
   output logic [31:0] instr_o                   // 명령어 출력 (32비트)
);

   // 메모리 배열: 32비트 × MEM_DEPTH 워드
   logic [31:0] mem [0:MEM_DEPTH-1];

   // 메모리 초기화 ($readmemh)
   initial begin
      for (int i = 0; i < MEM_DEPTH; i++)
         mem[i] = 32'h0000_0013;  // NOP (ADDI x0, x0, 0)
      $readmemh(INIT_FILE, mem);
   end

   // 비동기 읽기: PC[13:2]를 워드 주소로 사용
   assign instr_o = mem[pc_i[ADDR_WIDTH+1:2]];

endmodule

코드 분석 포인트:

1. 파라미터화 설계: ADDR_WIDTH와 INIT_FILE을 파라미터로 선언하여, 인스턴스화 시 메모리 크기와 초기화 파일을 유연하게 변경할 수 있습니다. 합성 시 다른 크기의 메모리가 필요하면 파라미터만 조정하면 됩니다.

2. $readmemh 시스템 태스크: $readmemh는 시뮬레이션 시작 시 16진수 텍스트 파일을 메모리 배열에 로드합니다. 파일의 각 줄에는 32비트 16진수 값이 하나씩 들어갑니다. 예를 들어, addi x1, x0, 5 명령어의 기계어 0x00500093을 첫 줄에 기록합니다. $readmemh 호출 전에 모든 메모리를 NOP(0x00000013, 즉 addi x0, x0, 0)으로 초기화하여, 프로그램 영역을 벗어난 주소에서도 안전한 명령어가 실행되도록 합니다.

3. 비동기 읽기: assign 문으로 구현된 조합 논리 읽기입니다. 클럭 에지를 기다리지 않고, PC 값이 변경되면 전파 지연(propagation delay)만큼의 시간 후에 즉시 명령어가 출력됩니다.

FPGA 합성: COE 파일 초기화

시뮬레이션에서는 $readmemh가 잘 동작하지만, Vivado에서 BRAM IP를 사용하여 합성할 때는 COE(Coefficient) 파일을 사용합니다. COE 파일의 형식은 다음과 같습니다.


; Vivado BRAM 초기화 파일 (program.coe)
; 세미콜론(;)은 주석
memory_initialization_radix = 16;
memory_initialization_vector =
00500093,
00A00113,
002081B3,
00000013;

memory_initialization_radix는 진법(16=16진수)을 지정하고, memory_initialization_vector에 각 워드의 초기값을 쉼표로 구분하여 나열합니다. 마지막 값은 세미콜론으로 끝납니다. Vivado의 IP Catalog에서 Block Memory Generator IP를 생성할 때, "Other Options" 탭에서 이 COE 파일을 지정하면 BRAM이 해당 초기값으로 합성됩니다.

❓ 수강생 단골 질문

Q: $readmemh로 작성한 코드를 Vivado에서 합성하면 BRAM이 초기화되나요?

A: Vivado 2020.1 이후 버전에서는 $readmemh가 포함된 initial 블록도 BRAM 초기화로 변환합니다. 다만 IP Catalog의 Block Memory Generator를 사용할 때는 COE 파일이 공식 방법입니다. 두 방법 모두 익혀 두면 상황에 따라 유연하게 대처할 수 있습니다.

.hex 파일 생성 방법

그렇다면 program.hex 파일은 어디서 만들까요? 두 가지 경로가 있습니다.

방법 1: RARS 시뮬레이터 사용 — Chapter 03에서 다룬 RARS(RISC-V Assembler and Runtime Simulator)에서 어셈블리 프로그램을 작성한 뒤, "File → Dump Memory" 메뉴로 Hexadecimal Text 형식의 파일을 추출합니다.

방법 2: riscv-gnu-toolchain 사용 — C 또는 어셈블리 소스를 크로스 컴파일한 뒤, riscv32-unknown-elf-objcopy 명령으로 바이너리를 추출하고, 별도 스크립트로 HEX 텍스트로 변환합니다.


# 어셈블리 소스 컴파일 및 HEX 변환 예시
riscv32-unknown-elf-as -o program.o program.s
riscv32-unknown-elf-ld -T linker.ld -o program.elf program.o
riscv32-unknown-elf-objcopy -O verilog program.elf program.hex
📌 강사 꿀팁

수업 중에는 RARS를 사용하여 간단한 프로그램(3~5줄)부터 시작하세요. addi 3개로 레지스터 값을 설정하고, add로 결과를 확인하는 것만으로도 IMEM 동작을 검증할 수 있습니다. riscv-gnu-toolchain은 Chapter 22(소프트웨어 스택 연동)에서 본격적으로 다룹니다.

5.3 데이터 메모리 (DMEM) 설계

데이터 메모리(Data Memory, DMEM)는 프로그램 실행 중에 변수, 배열, 스택 등을 저장하는 읽기-쓰기 메모리(RAM)입니다. IMEM과 달리 DMEM은 Store 명령어(SW, SH, SB)로 데이터를 쓰고, Load 명령어(LW, LH, LHU, LB, LBU)로 데이터를 읽습니다. DMEM 설계의 핵심 도전은 다양한 접근 크기(바이트, 하프워드, 워드)를 모두 지원해야 한다는 것입니다.

비유: DMEM은 사물함(locker)과 같습니다. 전체 사물함(워드)을 통째로 열 수도 있고(LW/SW), 반쪽만 열 수도 있으며(LH/SH), 한 칸만 열 수도 있습니다(LB/SB). 중요한 점은, 반쪽이나 한 칸만 열 때 나머지 부분의 내용이 훼손되면 안 된다는 것입니다. 이것이 바로 바이트 인에이블(byte enable)의 역할입니다. 다만, 이 비유는 사물함의 "칸"이 물리적으로 독립된 것처럼 보일 수 있지만, 실제 메모리에서는 하나의 워드 내 바이트들이 주소적으로 연속이라는 점이 다릅니다.

RV32I 로드/스토어 명령어 정리

RV32I 명령어 세트에서 메모리 접근과 관련된 명령어는 총 8개입니다. 이들은 모두 funct3 필드로 접근 크기와 부호 확장 여부를 구분합니다.

명령어 funct3 접근 크기 확장 방식 설명
LB 3'b000 1바이트 부호 확장 바이트를 읽고 MSB로 상위 24비트 채움
LH 3'b001 2바이트 부호 확장 하프워드를 읽고 MSB로 상위 16비트 채움
LW 3'b010 4바이트 없음 전체 워드 읽기
LBU 3'b100 1바이트 제로 확장 바이트를 읽고 상위 24비트를 0으로 채움
LHU 3'b101 2바이트 제로 확장 하프워드를 읽고 상위 16비트를 0으로 채움
SB 3'b000 1바이트 — rs2의 하위 바이트를 메모리에 저장
SH 3'b001 2바이트 — rs2의 하위 하프워드를 메모리에 저장
SW 3'b010 4바이트 — rs2의 전체 워드를 메모리에 저장

여기서 중요한 패턴 하나를 발견할 수 있습니다. funct3의 비트 2(funct3[2])가 부호 확장(0)과 제로 확장(1)을 결정합니다. 이 한 비트가 Load 확장 로직을 크게 단순화합니다.

리틀 엔디언 바이트 순서

RISC-V는 리틀 엔디언(little-endian) 바이트 순서를 사용합니다. 32비트 워드 0x12345678이 메모리 주소 0x100에 저장될 때, 각 바이트의 배치는 다음과 같습니다.

주소 바이트 값 위치
0x100 0x78 LSB (Byte 0, 최하위 바이트)
0x101 0x56 Byte 1
0x102 0x34 Byte 2
0x103 0x12 MSB (Byte 3, 최상위 바이트)

리틀 엔디언에서 가장 낮은 주소에 최하위 바이트(Least Significant Byte)가 저장됩니다. 이 순서는 직관에 반할 수 있으나, 하드웨어 설계에서는 바이트 오프셋과 비트 위치가 자연스럽게 대응되어 회로가 단순해지는 장점이 있습니다.

바이트 인에이블 메모리 구조

DMEM을 4개의 바이트 뱅크(byte bank)로 구성합니다. 각 뱅크는 8비트 폭의 독립된 메모리 배열입니다. 워드 쓰기(SW)는 4개 뱅크를 모두 활성화하고, 바이트 쓰기(SB)는 해당 바이트 뱅크 하나만 활성화합니다. 이 구조가 바로 바이트 인에이블(byte enable)이며, Xilinx BRAM에서 WEA[3:0] 포트와 직접 대응됩니다.

바이트 쓰기 인에이블 생성 로직

스토어 명령어의 funct3[1:0]과 주소의 addr[1:0](바이트 오프셋)에 따라 활성화할 바이트 뱅크가 결정됩니다.


// 바이트 쓰기 인에이블 생성
always_comb begin
   byte_we = 4'b0000;
   if (mem_write_i) begin
      case (funct3_i[1:0])
         2'b00: begin  // SB: 1바이트 쓰기
            case (byte_offset)
               2'b00: byte_we = 4'b0001;  // Byte 0
               2'b01: byte_we = 4'b0010;  // Byte 1
               2'b10: byte_we = 4'b0100;  // Byte 2
               2'b11: byte_we = 4'b1000;  // Byte 3
            endcase
         end
         2'b01: begin  // SH: 2바이트 쓰기
            case (byte_offset[1])
               1'b0: byte_we = 4'b0011;   // 하위 하프워드
               1'b1: byte_we = 4'b1100;   // 상위 하프워드
            endcase
         end
         2'b10: begin  // SW: 4바이트 전체 쓰기
            byte_we = 4'b1111;
         end
         default: byte_we = 4'b0000;
      endcase
   end
end

로드 데이터 확장 로직

메모리에서 워드를 읽은 후, funct3에 따라 해당 바이트 또는 하프워드를 추출하고 확장합니다. 핵심은 funct3[2]가 부호 확장(0)과 제로 확장(1)을 구분한다는 점입니다.


// 로드 데이터 확장 (부호/제로)
always_comb begin
   rdata_o = 32'h0;
   case (funct3_i)
      3'b000: begin  // LB: 부호 확장 바이트
         case (byte_offset)
            2'b00: rdata_o = {{24{mem_word[7]}},  mem_word[7:0]};
            2'b01: rdata_o = {{24{mem_word[15]}}, mem_word[15:8]};
            2'b10: rdata_o = {{24{mem_word[23]}}, mem_word[23:16]};
            2'b11: rdata_o = {{24{mem_word[31]}}, mem_word[31:24]};
         endcase
      end
      3'b001: begin  // LH: 부호 확장 하프워드
         case (byte_offset[1])
            1'b0: rdata_o = {{16{mem_word[15]}}, mem_word[15:0]};
            1'b1: rdata_o = {{16{mem_word[31]}}, mem_word[31:16]};
         endcase
      end
      3'b010: rdata_o = mem_word;  // LW: 전체 워드
      3'b100: begin  // LBU: 제로 확장 바이트
         case (byte_offset)
            2'b00: rdata_o = {24'b0, mem_word[7:0]};
            2'b01: rdata_o = {24'b0, mem_word[15:8]};
            2'b10: rdata_o = {24'b0, mem_word[23:16]};
            2'b11: rdata_o = {24'b0, mem_word[31:24]};
         endcase
      end
      3'b101: begin  // LHU: 제로 확장 하프워드
         case (byte_offset[1])
            1'b0: rdata_o = {16'b0, mem_word[15:0]};
            1'b1: rdata_o = {16'b0, mem_word[31:16]};
         endcase
      end
      default: rdata_o = mem_word;
   endcase
end

이 확장 로직에서 {{24{mem_word[7]}}}는 SystemVerilog의 반복 연결(replication) 문법입니다. mem_word[7](바이트의 MSB, 즉 부호 비트)를 24번 반복하여 상위 24비트를 채웁니다. 만약 원래 값이 0xA5(이진수 10100101)라면, MSB가 1이므로 0xFFFFFFA5로 부호 확장됩니다. 반면 LBU(제로 확장)에서는 단순히 24'b0으로 채워 0x000000A5가 됩니다.

❓ 수강생 단골 질문

Q: SB 명령어로 바이트 하나만 저장할 때, 같은 워드의 다른 바이트가 덮어쓰이지 않나요?

A: 아닙니다. 바이트 인에이블 구조 덕분에, 활성화된 바이트 뱅크만 갱신되고 나머지 뱅크는 이전 값을 유지합니다. 예를 들어 SB로 Byte 0만 쓰면 byte_we = 4'b0001이므로 Byte 1, 2, 3은 변경되지 않습니다. 이것은 4개의 독립된 8비트 메모리 배열로 구현되어 있기에 가능합니다.

🎯 면접 포인트

Q: 리틀 엔디언과 빅 엔디언의 차이를 설명하고, RISC-V는 어떤 방식을 사용합니까?

A: 리틀 엔디언은 최하위 바이트(LSB)를 가장 낮은 주소에 저장하고, 빅 엔디언은 최상위 바이트(MSB)를 가장 낮은 주소에 저장합니다. RISC-V 기본 사양은 리틀 엔디언을 사용합니다. 리틀 엔디언은 주소 오프셋과 비트 위치의 대응이 단순하여, 바이트/하프워드/워드 접근 시 하드웨어 설계가 간결해지는 장점이 있습니다.

5.4 메모리 맵 설계

지금까지 IMEM과 DMEM을 각각 독립적인 모듈로 설계하였습니다. 그러나 프로세서 관점에서 보면, 이 두 메모리와 향후 추가될 주변 장치(UART, GPIO, Timer 등)가 모두 하나의 통합된 주소 공간에 배치되어야 합니다. 이를 메모리 맵(Memory Map)이라 합니다. 메모리 맵은 32비트 주소 공간을 여러 영역으로 분할하고, 각 영역을 해당 하드웨어 모듈에 연결하는 체계입니다.

비유: 메모리 맵은 건물의 층별 안내도와 같습니다. 1층(0x0000번지대)은 도서관(IMEM), 2층(0x10000번지대)은 연구실(DMEM), 3층(0x40000번지대)은 사무실(MMIO)입니다. 엘리베이터(주소 버스)는 층 번호(주소 상위 비트)를 보고 어느 층으로 갈지 결정합니다. 이 "층 판별 장치"가 바로 주소 디코더입니다.

주소 공간 설계

우리 프로세서의 메모리 맵을 다음과 같이 설계합니다. Basys 3 FPGA의 BRAM 자원(50개 × 36Kb = 약 225KB)과 향후 확장성을 고려한 배치입니다.

영역 시작 주소 종료 주소 크기 용도
IMEM 0x0000_0000 0x0000_3FFF 16 KB 명령어 저장 (ROM)
DMEM 0x0001_0000 0x0001_3FFF 16 KB 데이터 저장 (RAM)
MMIO 0x0004_0000 0x0004_FFFF 64 KB 주변 장치 레지스터
미사용 기타 — — 접근 시 무응답 (Reserved)

이 배치에서 주목할 점이 있습니다. IMEM의 시작 주소가 0x0000_0000인 이유는 RISC-V 사양에서 리셋 후 PC의 초기값이 구현 정의(implementation-defined)이며, 일반적으로 0x0000_0000 또는 0x8000_0000을 사용하기 때문입니다. 우리는 간결한 0x0000_0000을 채택합니다. DMEM과 MMIO 사이에 여유 공간을 둔 것은, 향후 메모리 확장이나 추가 주변 장치 배치를 위한 것입니다.

주소 디코더 설계

주소 디코더(Address Decoder)는 CPU가 출력한 주소의 상위 비트를 검사하여, 어떤 메모리 영역에 접근하는지 판별합니다. 각 영역에 대한 선택 신호(chip select)를 생성하여 해당 모듈을 활성화합니다.


// 주소 디코더 (메모리 맵)
module address_decoder (
   input  logic [31:0] addr_i,        // CPU 주소 출력
   output logic        imem_sel_o,    // IMEM 선택 신호
   output logic        dmem_sel_o,    // DMEM 선택 신호
   output logic        mmio_sel_o     // MMIO 선택 신호
);

   always_comb begin
      // 기본값: 모든 선택 해제
      imem_sel_o = 1'b0;
      dmem_sel_o = 1'b0;
      mmio_sel_o = 1'b0;

      // 상위 16비트로 영역 판별
      case (addr_i[31:16])
         16'h0000: imem_sel_o = 1'b1;  // 0x0000_xxxx → IMEM
         16'h0001: dmem_sel_o = 1'b1;  // 0x0001_xxxx → DMEM
         16'h0004: mmio_sel_o = 1'b1;  // 0x0004_xxxx → MMIO
         default:  ;                    // 미사용 영역: 무응답
      endcase
   end

endmodule

주소 디코더는 순수한 조합 논리로 구현되며, 하드웨어 비용이 극히 낮습니다. 상위 16비트 비교기 3개와 멀티플렉서로 구성됩니다.

읽기 데이터 멀티플렉서

Load 명령어 실행 시, 선택된 영역의 읽기 데이터를 CPU로 전달해야 합니다. 주소 디코더의 선택 신호를 사용하여 멀티플렉서를 구성합니다.


// 읽기 데이터 MUX
always_comb begin
   case (1'b1)  // 원-핫(one-hot) 선택
      imem_sel: cpu_rdata = imem_rdata;
      dmem_sel: cpu_rdata = dmem_rdata;
      mmio_sel: cpu_rdata = mmio_rdata;
      default:  cpu_rdata = 32'hDEAD_DEAD;  // 미사용 영역 접근 감지용
   endcase
end

미사용 영역 접근 시 0xDEAD_DEAD와 같은 특수 패턴을 반환하면, 디버깅 과정에서 잘못된 주소 접근을 쉽게 식별할 수 있습니다. 실제 제품에서는 버스 에러(bus error) 응답을 반환하는 것이 일반적이며, 이는 Chapter 16(AMBA AHB)에서 HRESP 신호로 구현합니다.

💡 실무 팁

메모리 맵 설계 시 주소 영역 간에 충분한 간격을 두십시오. 예를 들어, IMEM(0x0000)과 DMEM(0x10000) 사이에 60KB의 여유가 있습니다. 프로젝트가 성장하면서 메모리 크기를 늘리거나 새로운 영역을 추가할 때, 이 여유 공간이 리팩토링 비용을 크게 줄여줍니다. 산업 현장에서 "주소 충돌(address collision)"로 인한 디버깅에 소요되는 시간은 상상 이상입니다.

MMIO(Memory-Mapped I/O) 개념

MMIO(메모리 맵 입출력, Memory-Mapped I/O)는 주변 장치의 제어 레지스터를 메모리 주소 공간에 매핑하여, Load/Store 명령어로 주변 장치를 제어하는 방식입니다. 예를 들어, GPIO 출력 레지스터가 0x0004_0000에 매핑되어 있다면, sw x1, 0(x10)으로 LED를 켤 수 있습니다. MMIO 방식의 장점은 별도의 I/O 명령어가 불필요하다는 것입니다. 이 영역의 실제 주변 장치 구현은 Chapter 17(APB 브리지와 주변 장치 연결)에서 다룹니다.

❓ 수강생 단골 질문

Q: 하버드 구조인데 왜 메모리 맵에 IMEM과 DMEM이 같은 주소 공간에 있나요?

A: 좋은 질문입니다. 하버드 구조에서 IMEM과 DMEM은 물리적으로 분리된 접근 포트를 가집니다. PC는 항상 IMEM 포트로만 접근하고, Load/Store 주소는 DMEM 포트로만 접근합니다. 메모리 맵에서 같은 주소 공간에 표시하는 것은 논리적 주소 배치를 나타낸 것이며, 실제 하드웨어에서는 PC 경로와 데이터 경로가 완전히 독립적입니다. 메모리 맵의 주소 디코더는 데이터 경로 측에서만 사용됩니다.

🎯 면접 포인트

Q: Memory-Mapped I/O와 Port-Mapped I/O(I/O 포트 방식)의 차이는 무엇입니까?

A: MMIO는 주변 장치 레지스터를 메모리 주소 공간에 매핑하여 Load/Store로 접근합니다. Port-Mapped I/O는 별도의 I/O 주소 공간과 전용 IN/OUT 명령어를 사용합니다(x86의 방식). RISC-V를 포함한 대부분의 현대 아키텍처(ARM, MIPS)는 MMIO를 사용하며, 이는 별도의 I/O 명령어가 필요 없고, 기존 메모리 접근 인프라를 재사용할 수 있다는 장점이 있습니다.

5.5 메모리 테스트벤치

설계한 IMEM과 DMEM이 올바르게 동작하는지 검증하는 것은 설계 자체만큼 중요합니다. 특히 DMEM의 바이트 인에이블과 부호 확장 로직은 경우의 수가 많아, 체계적인 테스트 없이는 미묘한 버그를 놓치기 쉽습니다. 이 절에서는 로드-스토어 시퀀스를 검증하는 SystemVerilog 테스트벤치를 작성합니다.

비유: 테스트벤치는 설계의 "건강 검진"입니다. 혈압(워드 접근)만 재고 끝낼 수 있지만, 혈당(바이트 접근), 심전도(부호 확장), 스트레스 검사(연속 접근)까지 해야 진정으로 건강한 설계인지 확인할 수 있습니다.

테스트 전략

DMEM 테스트벤치는 다음 6가지 시나리오를 순차적으로 검증합니다.

시나리오 검증 항목 핵심 포인트
1. IMEM 읽기 $readmemh 초기화 확인 PC 변경에 따른 명령어 출력
2. SW/LW 워드 단위 쓰기-읽기 기본 데이터 무결성
3. SB/LB/LBU 바이트 단위 접근 부호 확장 vs 제로 확장
4. SH/LH/LHU 하프워드 단위 접근 하프워드 부호 확장 정확성
5. 연속 주소 인접 워드 간 간섭 없음 주소 디코딩 정확성
6. 바이트 독립성 SB가 다른 바이트에 영향 없음 바이트 인에이블 독립성

테스트벤치 구조

테스트벤치의 핵심 구성 요소는 자동 검증 태스크(check_result)입니다. 기대값과 실제값을 비교하고, PASS/FAIL을 출력하며, 최종 통계를 집계합니다.


// 검증 태스크: 기대값과 실제값 비교
task automatic check_result(
   input string test_name,
   input logic [31:0] expected,
   input logic [31:0] actual
);
   test_total++;
   if (expected === actual) begin
      test_pass++;
      $display("[PASS] %s: expected=0x%08h, actual=0x%08h",
               test_name, expected, actual);
   end else begin
      test_fail++;
      $display("[FAIL] %s: expected=0x%08h, actual=0x%08h",
               test_name, expected, actual);
   end
endtask

=== 연산자는 4-상태 비교(4-state equality)로, x나 z 상태까지 정확히 비교합니다. 리셋 직후 메모리 값이 x일 수 있으므로, == 대신 ===을 사용하여 의도치 않은 PASS를 방지합니다.

바이트 부호 확장 검증의 핵심

테스트 시나리오 3에서 가장 중요한 검증은 부호 확장 경계값입니다. 0x7F(+127)와 0x80(-128)를 각각 저장한 후, LB와 LBU로 읽어 결과를 비교합니다.


// 부호 확장 경계값 테스트
// SB: 0x80 저장 (이진수: 10000000, MSB=1)
dmem_store(32'h0001_0012, 32'h0000_0080, F3_B);

// LB: 부호 확장 → 0xFFFFFF80 (-128)
dmem_load(32'h0001_0012, F3_B, read_data);
check_result("LB 0x80 sign-ext", 32'hFFFF_FF80, read_data);

// LBU: 제로 확장 → 0x00000080 (+128)
dmem_load(32'h0001_0012, F3_BU, read_data);
check_result("LBU 0x80 zero-ext", 32'h0000_0080, read_data);

동일한 메모리 값 0x80이 LB로 읽으면 0xFFFFFF80(음수 -128), LBU로 읽으면 0x00000080(양수 128)으로 완전히 다른 결과를 냅니다. C 언어의 char(signed)와 unsigned char의 차이가 바로 이 하드웨어에서 비롯됩니다.

시뮬레이션 실행

VCS를 사용한 시뮬레이션 명령은 다음과 같습니다.


# VCS 시뮬레이션 실행
vcs -sverilog ch05_instruction_memory.sv \
              ch05_data_memory.sv \
              ch05_memory_tb.sv \
    -o memory_sim
./memory_sim

# Vivado Simulator 사용 시
xvlog --sv ch05_instruction_memory.sv ch05_data_memory.sv ch05_memory_tb.sv
xelab memory_tb -s memory_sim
xsim memory_sim -R

📌 강사 꿀팁

5.6 본 챕터 요약 및 다음 단계

이 챕터에서는 RV32I 프로세서의 메모리 서브시스템을 구성하는 세 가지 핵심 모듈을 설계하였습니다. 명령어 메모리(IMEM), 데이터 메모리(DMEM), 그리고 메모리 맵(주소 디코더)입니다. 각 모듈의 설계 원리를 이해하고, 합성 가능한 SystemVerilog 코드를 작성하며, 테스트벤치로 동작을 검증하였습니다.

핵심 정리

  • 하버드 구조: IMEM과 DMEM을 분리하여 동일 사이클에 명령어 인출과 데이터 접근을 동시 수행. 단일 사이클 프로세서의 필수 구조.
  • IMEM 설계: 읽기 전용, 비동기 읽기(조합 논리), $readmemh(시뮬레이션) 또는 COE 파일(FPGA)로 초기화. PC 바이트 주소를 워드 주소로 변환(pc[13:2]).
  • DMEM 바이트 인에이블: 4개 바이트 뱅크로 구성. funct3[1:0]과 addr[1:0]으로 쓰기 인에이블 생성. SB/SH/SW 차별 처리.
  • 부호 확장 vs 제로 확장: funct3[2] 비트로 구분. LB/LH는 부호 확장, LBU/LHU는 제로 확장. 동일 메모리 값이 해석에 따라 다른 32비트 결과를 냄.
  • 리틀 엔디언: 최하위 바이트(LSB)가 가장 낮은 주소에 저장. RISC-V 기본 바이트 순서.
  • 메모리 맵: 32비트 주소 공간을 IMEM/DMEM/MMIO로 분할. 주소 상위 비트 비교로 디코딩. MMIO로 주변 장치를 Load/Store 명령어로 제어.
  • 테스트벤치: 워드/하프워드/바이트 접근, 부호 확장 경계값, 바이트 독립성을 체계적으로 검증. === 연산자로 4-상태 비교.

연습문제

  1. [기억] RV32I에서 바이트 로드 명령어의 부호 확장(LB)과 제로 확장(LBU)을 구분하는 funct3 비트는 어느 것인가?
  2. [이해] 리틀 엔디언 바이트 순서에서 32비트 값 0xABCD1234가 주소 0x100에 저장될 때, 주소 0x101에 위치한 바이트 값은 무엇인가?
  3. [적용] DMEM 주소 0x10008에 SW로 0x00FF80C0을 저장한 후, 주소 0x1000A에서 LH로 읽으면 레지스터에 어떤 32비트 값이 저장되는가? 바이트 오프셋과 부호 확장 과정을 단계별로 보이시오.
  4. [분석] 만약 DMEM을 바이트 뱅크 4개 대신 단일 32비트 배열(logic [31:0] mem[])로 구현한다면, SB 명령어를 지원하기 위해 어떤 추가 로직이 필요한가? 바이트 뱅크 방식과 비교하여 장단점을 분석하시오.
  5. [평가] 우리 메모리 맵에서 IMEM 16KB, DMEM 16KB는 Basys 3의 BRAM 자원(50개 × 36Kb) 중 어느 정도를 사용하는가? 만약 IMEM을 32KB로 확장하면 DMEM과 캐시(Ch13~14)에 할당 가능한 BRAM이 얼마나 남는가?
