FPGA 합성 최적화와 타이밍 클로저

시뮬레이션에서 완벽하게 동작하던 RV32I 파이프라인 프로세서를 실제 FPGA에 올리려면, 합성(Synthesis)과 구현(Implementation)이라는 새로운 관문을 통과해야 합니다. 이 챕터에서는 Vivado의 합성 전략을 이해하고, XDC 제약 파일을 작성하며, 타이밍 분석(Timing Analysis)을 수행하여 Basys 3에서 50MHz 동작을 달성하는 전 과정을 다룹니다.

학습 목표

  • Vivado의 합성 전략 옵션(성능 우선, 면적 우선, 리타이밍)을 비교하고 프로젝트에 적합한 전략을 선택할 수 있다.
  • XDC 제약 파일에서 클록 제약, I/O 타이밍, 거짓 경로를 작성할 수 있다.
  • report_timing 결과에서 WNS/TNS를 해석하고 임계 경로를 식별할 수 있다.
  • LUT, BRAM, DSP 사용량을 분석하고 면적-속도 트레이드오프를 평가할 수 있다.
  • 타이밍 위반 발생 시 합성 옵션 변경 또는 RTL 수정을 통해 타이밍 클로저를 달성할 수 있다.
📌 강사 꿀팁

이 챕터부터 "시뮬레이션에서는 되는데 FPGA에서는 안 된다"는 경험을 하게 됩니다. 이것은 정상입니다. 산업 현장에서도 타이밍 클로저는 가장 많은 반복(iteration)이 필요한 작업입니다. 처음부터 한 번에 성공하는 것이 아니라, 분석 → 수정 → 재합성의 반복을 통해 목표에 도달합니다. 이 과정 자체가 FPGA 설계의 핵심 역량입니다.

20.1 Vivado 합성 전략

Chapter 19까지 우리는 RV32I 파이프라인 프로세서, L1 캐시, AMBA 버스, 주변 장치, 예외/인터럽트 처리까지 모두 설계하고 시뮬레이션으로 검증하였습니다. 이제 이 설계를 실제 FPGA 하드웨어에서 동작시켜야 합니다. 그 첫 번째 단계가 바로 합성(Synthesis)입니다.

합성이란 무엇인가

합성은 RTL(Register-Transfer Level) 코드를 FPGA의 기본 구성 요소인 LUT(Look-Up Table), FF(Flip-Flop), BRAM(Block RAM), DSP48E1 등으로 변환하는 과정입니다. 이 과정에서 합성 도구(Vivado Synthesis)는 코드의 의도를 해석하고, 가능한 한 효율적인 하드웨어 구조로 매핑(mapping)합니다.

비유: 합성은 건축 설계도(RTL 코드)를 실제 건축 자재(LUT, FF, BRAM)로 변환하는 과정과 같습니다. 설계도에 "넓은 거실"이라고 적혀 있어도, 실제 시공 시에는 기둥의 간격, 벽돌의 크기, 철근의 배치를 구체적으로 결정해야 합니다. 합성 도구는 이 "시공 계획"을 자동으로 생성합니다. 다만, 건축가(설계자)가 자재 특성을 잘 알수록 더 효율적인 설계가 가능하듯, FPGA 리소스 특성을 이해하면 합성 결과가 크게 달라집니다.

Vivado 합성 플로우

Vivado에서 RTL 소스가 비트스트림(Bitstream)이 되기까지는 크게 네 단계를 거칩니다.

  1. Synthesis(합성): RTL 코드를 읽어 넷리스트(Netlist)를 생성합니다. 이 단계에서 조합 로직 최적화, 리소스 매핑, FSM 인코딩 등이 수행됩니다.
  2. Implementation(구현): 넷리스트를 실제 FPGA 칩의 물리적 위치에 배치(Place)하고 연결(Route)합니다. 타이밍 최적화의 핵심 단계입니다.
  3. Bitstream Generation(비트스트림 생성): 배치·배선 결과를 FPGA에 다운로드할 수 있는 바이너리 파일(.bit)로 변환합니다.
  4. Programming(프로그래밍): 비트스트림을 Basys 3 보드에 다운로드하여 실제 동작을 확인합니다.

합성 전략 옵션

Vivado는 다양한 합성 전략(Synthesis Strategy)을 제공합니다. Vivado GUI의 Settings → Synthesis → Strategy에서 선택하거나, Tcl 명령으로 직접 지정할 수 있습니다. 우리 프로젝트에서 주로 고려할 전략은 다음과 같습니다.

전략 설명 적용 시나리오
Vivado Synthesis Defaults 기본 설정. 면적과 성능의 균형을 추구 첫 합성 시 기준점 확보
Flow_PerfOptimized_high 성능(속도) 최적화 우선. 더 많은 LUT를 사용하더라도 타이밍을 개선 타이밍 위반이 발생할 때
Flow_AreaOptimized_high 면적(리소스) 최적화 우선. LUT 사용량을 최소화 리소스 부족 시
Flow_AreaOptimized_medium 중간 수준의 면적 최적화 면적과 성능 모두 중요할 때

리타이밍(Retiming) 활성화

리타이밍(Retiming)은 합성 도구가 레지스터(FF)의 위치를 조합 로직 경계에서 자동으로 이동시켜 타이밍을 개선하는 기법입니다. 예를 들어, 한 경로에 조합 로직이 밀집되어 있고 다른 경로에는 여유가 있을 때, 레지스터를 조합 로직 쪽으로 이동시켜 두 경로의 지연을 균등하게 만듭니다.

Vivado에서 리타이밍을 활성화하려면 다음 Tcl 명령을 사용합니다.

# Vivado Tcl 콘솔에서 실행
# 합성 시 리타이밍 활성화
synth_design -top fpga_top -part xc7a35tcpg236-1 -retiming

# 또는 프로젝트 설정에서:
set_property STEPS.SYNTH_DESIGN.ARGS.RETIMING true [get_runs synth_1]
💡 실무 팁

리타이밍은 파이프라인 레지스터가 이미 삽입되어 있는 설계에서 가장 효과적입니다. 우리의 5단계 파이프라인 프로세서는 IF/ID, ID/EX, EX/MEM, MEM/WB 레지스터가 존재하므로 리타이밍의 좋은 후보입니다. 다만, 리타이밍 후 시뮬레이션과 합성 결과의 사이클 수가 달라질 수 있으므로, 리타이밍 적용 후 반드시 합성 후 시뮬레이션(Post-Synthesis Simulation)을 실행하여 기능 동등성을 확인하십시오.

리소스 공유(Resource Sharing)

리소스 공유(Resource Sharing)는 서로 다른 시점에 사용되는 동일 유형의 연산기를 하나로 통합하는 최적화 기법입니다. 예를 들어, 멀티플렉서의 서로 다른 분기에서 각각 가산기를 사용하는 경우, 합성 도구가 이를 하나의 가산기와 입력 멀티플렉서 조합으로 변환할 수 있습니다.

// 리소스 공유 전: 가산기 2개 사용
assign result = sel ? (c + d) : (a + b);

// 리소스 공유 후: 가산기 1개 + MUX
// (합성 도구가 자동으로 변환하거나, 설계자가 명시적으로 작성)
assign op1    = sel ? c : a;
assign op2    = sel ? d : b;
assign result = op1 + op2;

Vivado에서 리소스 공유를 제어하려면 다음 속성을 사용합니다.

# 리소스 공유 활성화 (기본값)
set_property STEPS.SYNTH_DESIGN.ARGS.RESOURCE_SHARING auto [get_runs synth_1]

# 리소스 공유 비활성화 (타이밍 우선 시)
set_property STEPS.SYNTH_DESIGN.ARGS.RESOURCE_SHARING off [get_runs synth_1]

FSM 인코딩 전략

우리 설계에는 여러 FSM(유한 상태 기계, Finite State Machine)이 포함되어 있습니다. 캐시 미스 처리 FSM, AHB-to-APB 브리지 FSM, 인터럽트 처리 FSM 등이 대표적입니다. Vivado는 FSM을 감지하면 자동으로 인코딩 방식을 결정하지만, 설계자가 명시적으로 지정할 수도 있습니다.

인코딩 방식 상태 수 N일 때 FF 수 장점 단점
One-Hot N개 전이 로직 간단, 속도 우수 FF 소모량 많음
Sequential(Binary) log₂(N)개 FF 절감 디코딩 로직 복잡
Gray log₂(N)개 인접 전이 시 1비트만 변경 비순차 전이에 비효율 
// FSM 인코딩을 합성 속성으로 지정하는 방법
(* fsm_encoding = "one_hot" *)
typedef enum logic [4:0] {
   S_IDLE    = 5'b00001,
   S_COMPARE = 5'b00010,
   S_ALLOCATE= 5'b00100,
   S_WRITEBACK=5'b01000,
   S_FILL    = 5'b10000
} cache_state_t;

Q: 합성 전략을 바꾸면 기능이 달라질 수 있나요?

A: 기능 자체는 달라지지 않습니다. 합성 전략은 동일한 기능을 구현하되, 사용하는 리소스의 양과 타이밍 성능을 다르게 최적화합니다. 다만, 리타이밍을 적용하면 레지스터 위치가 바뀌어 파이프라인 지연(latency)이 달라질 수 있으므로, 합성 후 기능 검증은 반드시 필요합니다.

Vivado Tcl 스크립트를 이용한 자동화

프로젝트 규모가 커지면, GUI에서 매번 설정을 바꾸는 것보다 Tcl 스크립트로 합성 과정을 자동화하는 것이 효율적입니다. 아래는 우리 프로젝트에 적합한 합성 자동화 스크립트의 핵심 부분입니다.

# -------------------------------------------------------
# Vivado 합성 자동화 스크립트 (비프로젝트 모드)
# -------------------------------------------------------

# 1. 소스 파일 읽기
read_verilog -sv [glob ../rtl/*.sv]

# 2. XDC 제약 파일 읽기
read_xdc ../constraints/basys3_timing.xdc

# 3. 합성 실행 (성능 최적화 + 리타이밍)
synth_design -top fpga_top -part xc7a35tcpg236-1 \
  -retiming \
  -directive PerformanceOptimized

# 4. 합성 후 리포트 생성
report_utilization -file reports/post_synth_util.rpt
report_timing_summary -file reports/post_synth_timing.rpt

# 5. 구현 (배치·배선)
opt_design -directive Explore
place_design -directive ExtraTimingOpt
phys_opt_design -directive AggressiveExplore
route_design -directive AggressiveExplore

# 6. 구현 후 리포트
report_utilization -file reports/post_impl_util.rpt
report_timing_summary -file reports/post_impl_timing.rpt
report_timing -max_paths 10 -file reports/critical_paths.rpt

# 7. 비트스트림 생성
write_bitstream -force output/fpga_top.bit

20.2 XDC 제약 파일 작성

합성 도구가 아무리 뛰어나더라도, 목표를 알려주지 않으면 최적화할 수 없습니다. "이 설계가 50MHz에서 동작해야 한다", "이 핀에 클록이 들어온다", "이 경로는 타이밍 분석에서 제외해도 된다" 등의 정보를 합성 도구에 전달하는 것이 바로 제약 파일(Constraint File)의 역할입니다. Vivado에서는 XDC(Xilinx Design Constraints) 형식을 사용합니다.

비유: XDC 제약 파일은 건축의 "설계 기준서"와 같습니다. 건축 설계도(RTL)만으로는 건물을 지을 수 있지만, "이 건물은 8도 지진에도 버텨야 한다(타이밍 제약)", "정문은 남쪽에 배치해야 한다(핀 배치 제약)", "이 복도는 내진 검사 대상이 아니다(거짓 경로)" 같은 기준이 있어야 시공자(합성 도구)가 올바른 판단을 내릴 수 있습니다.

XDC 제약의 세 가지 범주

XDC 제약은 크게 세 가지 범주로 나뉩니다.

  1. 타이밍 제약(Timing Constraints): 클록 주기, 입출력 지연, 거짓 경로 등 타이밍 분석의 기준을 정의합니다.
  2. I/O 제약(I/O Constraints): 각 포트가 연결될 FPGA 핀 번호와 전기적 특성(IOSTANDARD)을 지정합니다.
  3. 물리 제약(Physical Constraints): 특정 모듈을 FPGA 칩의 특정 영역에 배치하거나, 멀티사이클 경로를 지정합니다.

클록 제약: create_clock

가장 중요한 제약은 클록 정의입니다. 합성 도구는 이 제약을 기준으로 모든 레지스터 간 경로의 타이밍을 검사합니다.

# Basys 3 온보드 100MHz 클록 정의
create_clock -name sys_clk -period 10.000 [get_ports { clk_100mhz }]

# 의미 분석:
#   -name sys_clk    : 이 클록의 이름을 "sys_clk"으로 지정
#   -period 10.000   : 클록 주기 10ns (= 100MHz)
#   [get_ports ...]  : 클록이 입력되는 포트를 지정

우리 설계에서는 100MHz 온보드 클록을 MMCM(Mixed-Mode Clock Manager) 또는 간단한 분주기를 통해 50MHz로 변환합니다. MMCM을 사용하는 경우 Vivado가 자동으로 생성 클록(Generated Clock)을 추론하지만, 수동 분주기를 사용하는 경우 명시적으로 정의해야 합니다.

# 수동 분주기 사용 시 생성 클록 정의
create_generated_clock -name cpu_clk \
  -source [get_ports clk_100mhz] \
  -divide_by 2 \
  [get_pins u_clk_wiz/clk_div2_reg/Q]

I/O 타이밍 제약

FPGA 외부에서 들어오는 입력 신호와 외부로 나가는 출력 신호에 대해서도 타이밍을 정의해야 합니다. set_input_delay와 set_output_delay를 사용합니다.

# UART 입력: 클록 대비 최대 3ns 지연으로 도착
set_input_delay  -clock sys_clk -max 3.0 [get_ports { uart_rxd }]
set_input_delay  -clock sys_clk -min 0.0 [get_ports { uart_rxd }]

# UART 출력: 클록 에지 후 최대 3ns 이내에 안정화
set_output_delay -clock sys_clk -max 3.0 [get_ports { uart_txd }]
set_output_delay -clock sys_clk -min 0.0 [get_ports { uart_txd }]

거짓 경로(False Path) 설정

거짓 경로(False Path)는 타이밍 분석에서 제외해야 하는 경로입니다. 가장 대표적인 예가 비동기 리셋 신호와 비동기 입력(스위치, 버튼)입니다. 이 신호들은 클록과 동기화되지 않으므로, 타이밍 분석에 포함하면 불필요한 위반(violation)이 보고됩니다.

# 비동기 리셋: 타이밍 분석에서 제외
set_false_path -from [get_ports { rst_n }]

# 슬라이드 스위치: 비동기 입력
set_false_path -from [get_ports { sw[*] }]

# LED 출력: 사람이 관찰하므로 타이밍 무관
set_false_path -to [get_ports { led[*] }]
💡 실무 팁

거짓 경로를 남용하면 위험합니다. 실제로 타이밍이 중요한 경로를 false path로 설정하면, 합성 도구가 해당 경로를 최적화하지 않아 하드웨어에서 비정상 동작이 발생합니다. 반드시 비동기 경로이거나, 물리적으로 동시에 활성화되지 않는 경로만 false path로 지정하십시오. 의심스러운 경우에는 set_max_delay로 느슨한 제약을 거는 것이 더 안전합니다.

핀 배치와 I/O 표준

Basys 3 보드의 각 핀에 대해 PACKAGE_PIN(물리적 핀 번호)과 IOSTANDARD(전기적 표준)를 지정해야 합니다. Basys 3는 3.3V 로직을 사용하므로 LVCMOS33을 표준으로 사용합니다.

# 클록 핀 설정
set_property -dict { PACKAGE_PIN W5  IOSTANDARD LVCMOS33 } [get_ports { clk_100mhz }]

# LED[0] 핀 설정
set_property -dict { PACKAGE_PIN U16  IOSTANDARD LVCMOS33 } [get_ports { led[0] }]

# 스위치[0] 핀 설정
set_property -dict { PACKAGE_PIN V17  IOSTANDARD LVCMOS33 } [get_ports { sw[0] }]

# 리셋 버튼 (풀업 저항 활성화)

비트스트림 생성 시 적용할 설정도 XDC에 포함합니다. 특히 압축(Compress) 옵션은 비트스트림 파일 크기를 줄여 프로그래밍 시간을 단축합니다.

# 전원 전압 설정

# 비트스트림 압축 활성화

🎯 면접 포인트

Q: FPGA 설계에서 XDC(또는 SDC) 파일의 역할은 무엇이며, 클록 제약을 정의하지 않으면 어떻게 됩니까?

A: XDC/SDC는 합성·구현 도구에 설계의 타이밍 요구사항과 물리적 제약을 전달합니다. 클록 제약이 없으면 도구는 타이밍 분석을 수행하지 않거나 임의의 기본값을 사용하여, 실제 동작 주파수에서 타이밍 위반이 발생해도 경고하지 못합니다. 결과적으로 시뮬레이션에서는 정상이지만 FPGA에서 비정상 동작하는 "시뮬레이션-하드웨어 불일치" 문제가 발생합니다.

20.3 타이밍 분석과 클로저 기법

합성과 구현이 완료되면, 이제 가장 중요한 질문에 답해야 합니다. "이 설계가 목표 주파수에서 정상 동작할 수 있는가?" 이 질문에 답하는 과정이 바로 정적 타이밍 분석(STA, Static Timing Analysis)입니다.

Setup Time과 Hold Time

디지털 회로에서 플립플롭(FF)이 데이터를 올바르게 캡처하려면, 두 가지 조건이 충족되어야 합니다.

  • 셋업 시간(Setup Time, Tsu): 클록의 캡처 에지(보통 상승 에지) 이전에 데이터가 안정되어 있어야 하는 최소 시간입니다.
  • 홀드 시간(Hold Time, Th): 클록의 캡처 에지 이후에도 데이터가 안정적으로 유지되어야 하는 최소 시간입니다.

이 두 조건 중 하나라도 위반되면, 플립플롭은 메타스테이빌리티(Metastability) 상태에 빠져 출력이 불확정(0도 1도 아닌 중간 전압)이 됩니다. 이는 시뮬레이션에서는 절대 나타나지 않지만, 실제 FPGA에서는 간헐적인 오동작으로 나타나 디버깅이 극히 어렵습니다.

슬랙(Slack)의 의미

슬랙(Slack)은 타이밍 여유를 나타내는 핵심 지표입니다. 셋업 슬랙을 수식으로 표현하면 다음과 같습니다.

Setup Slack = T_clk_period
            - T_clk_to_q    (발신 FF의 출력 지연)
            - T_comb_logic   (조합 로직 전파 지연)
            - T_setup        (수신 FF의 셋업 시간)
            - T_clock_uncertainty (클록 불확실성)
  • Slack ≥ 0: 타이밍 충족(Timing Met). 데이터가 제 시간에 도착합니다.
  • Slack < 0: 타이밍 위반(Timing Violation). 데이터가 늦게 도착하여 셋업 조건을 만족하지 못합니다.

WNS와 TNS

Vivado는 수만 개의 타이밍 경로를 분석한 뒤, 두 가지 핵심 지표를 보고합니다.

지표 의미 목표
WNS (Worst Negative Slack) 모든 경로 중 가장 나쁜(가장 작은) 슬랙 값 WNS ≥ 0
TNS (Total Negative Slack) 음수 슬랙을 가진 모든 경로의 슬랙 합 TNS = 0
WHS (Worst Hold Slack) 홀드 타이밍의 최악 슬랙 WHS ≥ 0
THS (Total Hold Slack) 음수 홀드 슬랙의 합 THS = 0

타이밍 클로저(Timing Closure)란 WNS ≥ 0 이고 TNS = 0인 상태, 즉 모든 경로가 타이밍 요구사항을 만족하는 상태를 달성하는 것을 말합니다.

report_timing 사용법

Vivado에서 타이밍 분석 결과를 확인하는 핵심 명령은 report_timing과 report_timing_summary입니다.

# 전체 타이밍 요약 보고서
report_timing_summary

# 상위 10개 임계 경로 상세 보고
report_timing -max_paths 10 -sort_by slack

# 특정 클록 도메인의 타이밍만 확인
report_timing -from [get_clocks cpu_clk] -to [get_clocks cpu_clk] -max_paths 5

# 특정 모듈을 통과하는 경로 확인
report_timing -through [get_cells u_soc/u_cpu/u_alu/*] -max_paths 5

다음은 report_timing 출력의 핵심 부분을 읽는 방법입니다.

Slack (MET) :             1.234ns  (required time - arrival time)
  Source:                 u_cpu/ex_mem_reg/alu_result_reg[15]/C
                            (rising edge-triggered flip-flop clocked by cpu_clk)
  Destination:            u_cpu/mem_wb_reg/wb_data_reg[15]/D
                            (rising edge-triggered flip-flop clocked by cpu_clk)
  Path Group:             cpu_clk
  Path Type:              Setup (Max at Slow Process Corner)
  Requirement:            20.000ns  (cpu_clk rise@20.000ns - cpu_clk rise@0.000ns)
  Data Path Delay:        17.856ns  (logic 8.234ns + route 9.622ns)
  Logic Levels:           12  (LUT6=8 CARRY4=3 MUXF7=1)
  Clock Uncertainty:      0.035ns

이 보고서에서 핵심적으로 확인해야 할 항목은 다음과 같습니다.

  • Slack (MET/VIOLATED): 양수면 충족, 음수면 위반입니다.
  • Data Path Delay: 총 지연은 logic(로직 지연)과 route(배선 지연)으로 구분됩니다. 로직 지연이 크면 RTL 수정이, 배선 지연이 크면 배치 최적화가 필요합니다.
  • Logic Levels: 경로에 포함된 조합 로직의 단계 수입니다. 이 값이 크면 파이프라인 레지스터 삽입을 고려해야 합니다.
  • Source/Destination: 임계 경로의 시작점과 끝점 레지스터입니다. 이를 통해 어떤 모듈의 어떤 연산이 병목인지 식별합니다.

타이밍 클로저 기법

타이밍 위반이 발생했을 때, 해결 전략은 위반의 심각도에 따라 다릅니다.

경미한 위반 (|WNS| ≤ 1ns)

도구 옵션 변경만으로 해결 가능한 경우가 많습니다.

  1. 합성 전략 변경: Flow_PerfOptimized_high로 변경
  2. 물리 최적화 추가: phys_opt_design -directive AggressiveExplore
  3. 리타이밍 활성화: synth_design -retiming
  4. 배치 전략 변경: place_design -directive ExtraTimingOpt

심각한 위반 (|WNS| > 1ns)

RTL 수준의 수정이 필요합니다.

  1. 임계 경로에 파이프라인 레지스터 삽입: 가장 효과적인 방법이지만, 기능 변경(레이턴시 증가)이 수반됩니다.
  2. 조합 로직 분할(Logic Balancing): 한 경로에 집중된 로직을 여러 경로로 분산합니다.
  3. 캐시 크기 축소: 팬아웃(fanout)과 배선 혼잡도를 줄여 간접적으로 타이밍을 개선합니다.
  4. 목표 주파수 하향: 최후의 수단으로 50MHz → 40MHz로 낮춥니다.
// 임계 경로 분할 예제: EX 스테이지의 긴 조합 로직
// [수정 전] 분기 비교 + 타겟 주소 계산이 한 사이클에 완료
assign branch_taken  = (rs1_data == rs2_data);  // 비교기
assign branch_target = pc_ex + imm_ex;           // 가산기

// [수정 후] 비교 결과를 1사이클 일찍 계산 (ID 스테이지로 이동)
// 이 경우 포워딩 로직도 함께 수정해야 함 (Ch11 참조)
always_ff @(posedge clk) begin
   branch_taken_reg <= (rs1_data_fwd == rs2_data_fwd);
end
🎯 면접 포인트

Q: Setup Time Violation과 Hold Time Violation이 발생하면 각각 어떻게 해결합니까?

A: Setup Violation은 데이터 경로가 너무 길어서 발생하므로, (1) 클록 주파수를 낮추거나, (2) 임계 경로에 파이프라인 레지스터를 삽입하거나, (3) 조합 로직을 줄이는 방법으로 해결합니다. Hold Violation은 데이터가 너무 빨리 변해서 발생하므로, (1) 배선 지연을 의도적으로 추가(버퍼 삽입)하거나, (2) 배치를 조정하여 해결합니다. FPGA에서 Hold Violation은 배치·배선 도구가 대부분 자동으로 해결하므로, 설계자가 직접 수정하는 경우는 드뭅니다.

❓ 수강생 단골 질문

Q: "로직 지연(logic delay)"과 "배선 지연(route delay)" 중 어느 쪽이 더 문제인가요?

A: Artix-7 같은 최신 FPGA에서는 배선 지연이 전체 지연의 50~70%를 차지합니다. 따라서 로직 단계 수(Logic Levels)를 줄이는 것도 중요하지만, 배치 최적화를 통해 관련 로직을 물리적으로 가까이 배치하는 것이 실질적 효과가 큽니다. Vivado의 place_design -directive ExtraTimingOpt 옵션이 이 역할을 합니다.

20.4 리소스 최적화

타이밍 클로저와 함께 FPGA 설계에서 반드시 관리해야 하는 또 다른 축이 리소스 사용량(Resource Utilization)입니다. Basys 3의 XC7A35T는 교육용 FPGA로서 리소스가 제한적이므로, 우리 설계가 칩 안에 들어갈 수 있는지 사전에 확인하고 필요시 최적화해야 합니다.

XC7A35T 리소스 사양

먼저 우리가 사용하는 FPGA 칩의 정확한 리소스를 확인합시다.

💡 실무 팁

합성 전에 리소스를 예측하는 것은 중요하지만, 실제 합성 결과와는 차이가 날 수 있습니다. Vivado의 report_utilization 명령으로 실제 사용량을 반드시 확인하십시오. 특히 합성 도구가 의도와 다르게 BRAM 대신 LUTRAM을 사용하거나, 그 반대로 추론하는 경우가 흔합니다. 합성 로그에서 "INFO: [Synth 8-3971] The RAM ... will be implemented on BRAM" 같은 메시지를 확인하여 의도한 대로 추론되었는지 검증해야 합니다.

면적-속도 트레이드오프

FPGA 설계에서는 항상 면적(Area)과 속도(Speed)가 상충합니다. 이 트레이드오프를 이해하고 설계 결정에 반영하는 것이 핵심입니다.

최적화 방향 면적 영향 속도 영향 예
파이프라인 레지스터 추가 FF ↑ 클록 주파수 ↑ EX 스테이지 분할
리소스 공유 LUT ↓ MUX 추가로 약간 ↓ 가산기 공유
캐시 연관도 증가 LUT ↑, BRAM ↑ 미스율 ↓ → 성능 ↑ DM → 2-way SA
One-hot FSM 인코딩 FF ↑ 전이 로직 ↓ → 속도 ↑ 캐시 FSM
BRAM → LUTRAM 변환 LUT ↑, BRAM ↓ 비동기 읽기 가능 레지스터 파일

BRAM 추론 코딩 패턴

리소스 최적화에서 가장 중요한 것은 BRAM 추론(BRAM Inference)을 올바르게 유도하는 것입니다. Vivado가 코드를 BRAM으로 추론하려면 특정 코딩 패턴을 따라야 합니다.

// ★ BRAM 추론 가능: 동기 읽기 + 동기 쓰기 (Read-First 모드)
always_ff @(posedge clk) begin
   if (we)
      mem[addr] <= din;
   dout <= mem[addr];  // 동기 읽기 → BRAM 추론
end

// ✗ BRAM 추론 불가: 비동기 읽기
// (LUTRAM으로 합성됨 → LUT 소모량 급증)
assign dout = mem[addr];  // 비동기 읽기 → LUTRAM

BRAM과 LUTRAM의 차이를 정리하면 다음과 같습니다.

특성 BRAM LUTRAM (분산 RAM)
용량 36Kb / 블록 64비트 / LUT
읽기 방식 동기 읽기만 가능 비동기 읽기 가능
소비 리소스 전용 BRAM 블록 Slice LUT
적합한 용도 캐시 데이터, 메모리, FIFO 레지스터 파일, 소규모 테이블
접근 지연 1사이클 조합 지연만
❓ 수강생 단골 질문

Q: 레지스터 파일을 BRAM으로 구현하면 LUTRAM보다 효율적이지 않나요?

A: 용량 면에서는 그렇지만, 기능적 제약이 있습니다. 레지스터 파일은 같은 사이클에 2개 읽기 + 1개 쓰기(2R1W)가 필요합니다. BRAM은 최대 True Dual Port(2포트)만 지원하므로 2R1W를 직접 구현하려면 BRAM 2개가 필요합니다. 또한 BRAM은 동기 읽기만 가능하여, 단일 사이클 프로세서에서는 1사이클 지연이 추가됩니다. 파이프라인에서는 ID 스테이지에서 읽기를 수행하면 동기 읽기가 자연스럽지만, 포워딩과의 상호작용이 복잡해집니다. 따라서 32×32 레지스터 파일은 LUTRAM이 최적입니다.

report_utilization 읽기

합성 또는 구현 후, report_utilization 명령으로 실제 리소스 사용량을 확인합니다.

# 리소스 사용량 보고서 생성
report_utilization -file reports/utilization.rpt

# 계층별(모듈별) 사용량 확인
report_utilization -hierarchical -file reports/hier_util.rpt

보고서의 핵심 부분은 다음과 같은 형태입니다.

+----------------------------+------+-------+-----------+-------+
|          Site Type          | Used | Fixed | Available | Util% |
+----------------------------+------+-------+-----------+-------+
| Slice LUTs                 | 10234|     0 |     20800 | 49.20%|
|   LUT as Logic             |  9876|     0 |     20800 | 47.48%|
|   LUT as Memory (LUTRAM)   |   358|     0 |      9600 |  3.73%|
| Slice Registers            | 14680|     0 |     41600 | 35.29%|
| Block RAM Tile             |    30|     0 |        50 | 60.00%|
| DSPs                       |     0|     0 |        90 |  0.00%|
+----------------------------+------+-------+-----------+-------+

여기서 주의해야 할 점은 Util%가 80%를 넘으면 배치·배선 도구가 최적의 위치를 찾기 어려워져 타이밍 성능이 급격히 저하된다는 것입니다. 따라서 LUT 사용률 70% 이하, BRAM 사용률 80% 이하를 목표로 관리하는 것이 바람직합니다.

시뮬레이션과 FPGA 불일치 사전 대비

📌 강사 꿀팁

시뮬레이션에서 완벽하게 동작하던 설계가 FPGA에서 오동작하는 것은 매우 흔한 경험입니다. 이것은 여러분의 설계가 잘못된 것이 아니라, 시뮬레이션이 포착하지 못하는 물리적 현상이 존재하기 때문입니다. 산업 현장에서도 FPGA 포팅(porting) 시 최소 1~2주의 디버깅 기간을 계획합니다.

시뮬레이션과 FPGA 사이에서 불일치가 발생하는 대표적인 원인과 해결책을 정리합니다.

# 불일치 원인 증상 해결책
1 초기화 미비 시뮬레이션에서는 X가 0으로 처리되지만, FPGA에서는 임의의 값 모든 레지스터에 명시적 리셋 값 할당
2 래치(Latch) 추론 always_comb에서 모든 분기를 커버하지 않으면 래치 생성 합성 경고에서 "inferred latch" 검색, default 분기 추가
3 비동기 리셋 해제 리셋 해제 시점이 클록 에지와 겹쳐 메타스테이빌리티 발생 2단 동기화기(sync_reset 모듈) 사용
4 클록 도메인 교차 서로 다른 클록 도메인 간 신호 전달 시 데이터 손실 2단 동기화기 또는 비동기 FIFO 사용
5 타이밍 위반 간헐적 오동작, 온도/전압에 따라 달라지는 증상 타이밍 클로저 달성 확인, WNS/TNS 점검
6 블로킹/논블로킹 할당 혼용 시뮬레이션과 합성에서 다른 순서로 실행 순차 로직은 <=, 조합 로직은 = 엄수
7 BRAM 초기화 누락 명령어 메모리가 비어 있어 CPU가 유효하지 않은 명령어 실행 COE 파일로 BRAM 초기화, $readmemh는 시뮬레이션 전용

트러블슈팅 체크리스트

FPGA에서 설계가 동작하지 않을 때, 다음 체크리스트를 순서대로 점검하십시오.

  1. 합성 경고 확인: Vivado 메시지 탭에서 "Warning"과 "Critical Warning"을 모두 검토합니다. 특히 "inferred latch", "multi-driven net", "unconnected port" 경고에 주의합니다.
  2. 타이밍 보고서 확인: report_timing_summary에서 WNS ≥ 0, TNS = 0인지 확인합니다.
  3. 리셋 동작 확인: 리셋 버튼을 누른 후 LED가 초기 상태로 돌아가는지 확인합니다. 리셋이 정상 동작하지 않으면 sync_reset 모듈을 점검합니다.
  4. 클록 확인: 50MHz 클록이 올바르게 생성되는지 확인합니다. MMCM의 locked 출력을 LED에 연결하여 시각적으로 확인할 수 있습니다.
  5. 점진적 검증: 전체 SoC가 아닌, 개별 모듈부터 FPGA에서 동작을 확인합니다. LED 점멸 → UART 송신 → CPU 코어 → 전체 SoC 순으로 검증합니다.
  6. ILA 삽입: Chapter 21에서 다룰 ILA(Integrated Logic Analyzer)를 사용하여 내부 신호를 실시간으로 관찰합니다.

최상위 모듈 구조

Basys 3에 프로세서를 탑재하는 최상위 모듈의 구조를 살펴봅시다. 이 모듈은 클록 생성, 리셋 동기화, CPU 코어 인스턴스화를 담당합니다.

module fpga_top (
   input  logic        clk_100mhz,  // Basys 3 100MHz 온보드 클록
   input  logic        rst_n,       // Center Button (액티브 로우)
   input  logic [15:0] sw,          // 슬라이드 스위치
   output logic [15:0] led,         // LED
   input  logic        uart_rxd,    // UART 수신
   output logic        uart_txd     // UART 송신
);

   logic clk_cpu;       // 50MHz CPU 클록
   logic pll_locked;    // PLL 잠금 상태
   logic rst_sync_n;    // 동기화된 리셋

   // 1단계: 클록 생성 (100MHz → 50MHz)
   clk_wizard_wrapper u_clk_wiz (
      .clk_100mhz (clk_100mhz),
      .rst_n       (rst_n),
      .clk_50mhz  (clk_cpu),
      .locked      (pll_locked)
   );

   // 2단계: 리셋 동기화
   sync_reset u_sync_rst (
      .clk         (clk_cpu),
      .rst_async_n (rst_n & pll_locked),
      .rst_sync_n  (rst_sync_n)
   );

   // 3단계: CPU SoC 인스턴스
   riscv_soc u_soc (
      .clk      (clk_cpu),
      .rst_n    (rst_sync_n),
      .gpio_in  (sw),
      .gpio_out (led),
      .uart_rx  (uart_rxd),
      .uart_tx  (uart_txd)
   );

endmodule
// 리셋 동기화 모듈: 비동기 리셋의 안전한 해제
module sync_reset (
   input  logic clk,
   input  logic rst_async_n,  // 비동기 리셋 (액티브 로우)
   output logic rst_sync_n    // 동기화된 리셋 (액티브 로우)
);

   logic rst_meta;

   (* ASYNC_REG = "TRUE" *)  // Vivado 배치 최적화 힌트
   always_ff @(posedge clk or negedge rst_async_n) begin
      if (!rst_async_n) begin
         rst_meta   <= 1'b0;
         rst_sync_n <= 1'b0;
      end else begin
         rst_meta   <= 1'b1;
         rst_sync_n <= rst_meta;
      end
   end

endmodule

타이밍 실패 시 대응 전략

만약 50MHz에서 타이밍 클로저에 실패한다면, 다음 전략을 단계적으로 적용합니다.

단계 전략 예상 효과 부작용
1 합성 전략을 Flow_PerfOptimized_high로 변경 WNS 0.5~1.0ns 개선 LUT 사용량 약간 증가
2 리타이밍 활성화 레지스터 재배치로 WNS 개선 합성 후 기능 검증 필요
3 phys_opt_design -directive AggressiveExplore 물리 최적화로 배선 지연 감소 구현 시간 증가
4 임계 경로 RTL 수정 (파이프라인 레지스터 삽입) 근본적 해결 레이턴시 증가, 기능 재검증
5 캐시 크기 축소 (4KB → 2KB) 배선 혼잡도 감소 캐시 미스율 증가
6 목표 주파수 하향 (50MHz → 40MHz) 확실한 해결 성능 20% 저하
🎯 면접 포인트

Q: FPGA 설계와 ASIC 설계의 주요 차이점은 무엇입니까?

A: 핵심 차이는 다음과 같습니다. (1) 구조: FPGA는 LUT/FF/BRAM 등 미리 제조된 프로그래밍 가능 로직을 사용하고, ASIC은 트랜지스터 수준에서 맞춤 설계합니다. (2) 성능: ASIC이 동일 기능 대비 동작 주파수, 전력 효율에서 10배 이상 우수합니다. (3) 비용: FPGA는 초기 비용이 낮고(NRE 없음) 소량 생산에 유리하며, ASIC은 마스크 제작 비용(수억~수십억 원)이 크지만 대량 생산 시 단가가 낮습니다. (4) 유연성: FPGA는 필드에서 재프로그래밍이 가능하지만, ASIC은 제조 후 변경 불가합니다. (5) 설계 플로우: FPGA는 합성 → P&R → 비트스트림이고, ASIC은 합성 → P&R → 검증 → 테이프아웃 → 팹 제조로 훨씬 길고 복잡합니다.

20.6 본 챕터 요약 및 다음 단계

이 챕터에서는 RTL 설계를 실제 FPGA 하드웨어에서 동작시키기 위한 합성 최적화와 타이밍 클로저의 전 과정을 다루었습니다. 시뮬레이션에서 FPGA로 넘어가는 이 단계는 많은 설계자가 어려움을 겪는 구간이지만, 체계적인 접근과 반복적인 분석-수정 과정을 통해 반드시 달성할 수 있습니다.

핵심 정리

  • 합성(Synthesis)은 RTL 코드를 LUT/FF/BRAM/DSP 등 FPGA 기본 요소로 변환하는 과정이며, Flow_PerfOptimized_high, Flow_AreaOptimized_high 등 전략에 따라 면적-속도 트레이드오프가 달라진다.
  • 리타이밍(Retiming)은 레지스터 위치를 자동 조정하여 타이밍을 개선하는 기법으로, 파이프라인 레지스터가 존재하는 설계에서 효과적이다.
  • XDC 제약 파일은 타이밍 제약(create_clock), I/O 제약(set_property PACKAGE_PIN), 물리 제약(set_false_path)의 세 범주로 구성되며, 합성 품질에 결정적 영향을 미친다.
  • 슬랙(Slack)은 타이밍 여유를 나타내며, WNS ≥ 0 이고 TNS = 0이면 타이밍 클로저가 달성된 것이다. report_timing에서 로직 지연과 배선 지연의 비율을 확인하여 최적화 방향을 결정한다.
  • Basys 3(XC7A35T)에서 BRAM이 가장 제약적인 리소스이며, 캐시 크기 결정 시 BRAM 예산을 먼저 확인해야 한다. LUT 사용률 70%, BRAM 사용률 80% 이내를 목표로 관리한다.
  • 시뮬레이션과 FPGA 불일치의 주요 원인은 초기화 미비, 래치 추론, 비동기 리셋 해제, 타이밍 위반이며, 합성 경고 확인 → 타이밍 보고서 점검 → 점진적 검증 순서로 트러블슈팅한다.
  • 타이밍 위반 시 도구 옵션 변경(경미) → RTL 수정(심각) → 목표 주파수 하향(최후) 순서로 단계적으로 대응한다.

    Slack (VIOLATED): -1.5ns

    logic [31:0] mem [0:1023];

   if (we) mem[waddr] <= wdata;

assign rdata = mem[raddr];  // 비동기 읽기
