4.2 ALU 설계: 10가지 연산

산술 논리 장치(ALU, Arithmetic Logic Unit)는 프로세서에서 실제 계산을 수행하는 유일한 모듈입니다. 덧셈, 뺄셈, 논리 연산, 시프트, 비교 — 모든 연산이 이 한 곳을 통과합니다. Chapter 03에서 분석한 R 타입 명령어 10개(ADD, SUB, AND, OR, XOR, SLL, SRL, SRA, SLT, SLTU)가 바로 ALU가 처리해야 할 연산 목록입니다.

비유: ALU는 만능 계산기입니다. 덧셈 버튼을 누르면 덧셈, 비교 버튼을 누르면 비교를 수행합니다. 어떤 버튼을 누를지(어떤 연산을 수행할지)는 제어 유닛(Control Unit)이 결정합니다. 이번 챕터에서는 계산기 본체만 만들고, 버튼을 누르는 로직(제어 유닛)은 Chapter 06에서 설계합니다.

ALU가 지원해야 할 10가지 연산

RV32I의 ALU 연산은 크게 네 가지 범주로 나뉩니다. 각 연산에 4비트 제어 코드(alu_ctrl[3:0])를 할당합니다. 이 코드는 나중에 제어 유닛이 명령어의 opcode, funct3, funct7 필드를 조합하여 생성할 것입니다.

범주 연산 alu_ctrl 동작 사용 명령어 예시
산술 ADD4'b0000A + BADD, ADDI, LW, SW
SUB4'b0001A - BSUB, BEQ, BNE
논리 AND4'b0010A & BAND, ANDI
OR4'b0011A | BOR, ORI
XOR4'b0100A ^ BXOR, XORI

ALU 블록 다이어그램

SystemVerilog 구현

ALU는 순수한 조합 논리(combinational logic) 회로입니다. 클록이 필요 없고, 입력이 바뀌면 출력이 즉시(약간의 전파 지연 후) 변합니다. SystemVerilog에서는 always_comb 블록으로 이를 표현합니다.


module alu (
   input  logic [31:0] operand_a,   // 첫 번째 피연산자 (rs1 데이터)
   input  logic [31:0] operand_b,   // 두 번째 피연산자 (rs2 또는 즉치수)
   input  logic [3:0]  alu_ctrl,    // ALU 제어 신호
   output logic [31:0] alu_result,  // 연산 결과
   output logic        alu_zero     // 결과가 0일 때 1 (분기 판정용)
);

   // 시프트량: 하위 5비트만 사용 (RV32I는 32비트)
   logic [4:0] shamt;
   assign shamt = operand_b[4:0];

   always_comb begin
      case (alu_ctrl)
         // === 산술 연산 ===
         4'b0000: alu_result = operand_a + operand_b;                        // ADD
         4'b0001: alu_result = operand_a - operand_b;                        // SUB

         // === 논리 연산 ===
         4'b0010: alu_result = operand_a & operand_b;                        // AND
         4'b0011: alu_result = operand_a | operand_b;                        // OR
         4'b0100: alu_result = operand_a ^ operand_b;                        // XOR

         // === 시프트 연산 ===
         4'b0101: alu_result = operand_a << shamt;                           // SLL
         4'b0110: alu_result = operand_a >> shamt;                           // SRL
         4'b0111: alu_result = $signed(operand_a) >>> shamt;                 // SRA

         // === 비교 연산 ===
         4'b1000: alu_result = {31'b0, $signed(operand_a) < $signed(operand_b)};  // SLT
         4'b1001: alu_result = {31'b0, operand_a < operand_b};                     // SLTU

         default: alu_result = 32'b0;
      endcase
   end

   // 제로 플래그
   assign alu_zero = (alu_result == 32'b0);

endmodule

핵심 설계 포인트 해설

시프트량(shamt)을 5비트로 제한하는 이유: RV32I는 32비트 레지스터를 사용하므로, 유효한 시프트량은 0~31(5비트)입니다. RISC-V 스펙은 시프트 명령어에서 operand_b의 하위 5비트만 시프트량으로 사용하도록 정의합니다. 상위 비트는 무시됩니다. 이를 위해 shamt = operand_b[4:0]으로 명시적으로 추출합니다.

SRA(산술 우측 시프트)의 $signed 캐스팅: SystemVerilog에서 >>> 연산자는 피연산자가 signed로 선언되었을 때만 산술 시프트(부호 비트 확장)를 수행합니다. logic 타입은 기본적으로 부호가 없으므로(unsigned), $signed(operand_a)로 캐스팅해야 합니다. 이 부분을 놓치면 SRA가 SRL과 동일하게 동작하는 버그가 발생합니다.

SLT/SLTU의 비교 결과 표현: 비교 연산의 결과는 참(1) 또는 거짓(0)입니다. 이를 32비트 alu_result에 넣기 위해 {31'b0, 비교결과} 연결(concatenation)을 사용합니다. SLT는 $signed 비교, SLTU는 unsigned 비교입니다. 예를 들어, 0xFFFFFFFF는 SLT에서는 -1이므로 1보다 작지만, SLTU에서는 4,294,967,295이므로 1보다 큽니다.

제로 플래그(alu_zero)의 용도: 분기 명령어(BEQ, BNE)는 두 레지스터 값을 비교하여 분기 여부를 결정합니다. BEQ의 경우 rs1 - rs2 == 0이면 분기합니다. ALU에서 SUB 연산을 수행한 후 결과가 0인지 확인하는 것이 제로 플래그의 역할입니다.

💡 실무 팁

Vivado에서 이 ALU를 합성하면, 덧셈/뺄셈에는 캐리 체인(carry chain)이, 시프트에는 멀티플렉서 기반 배럴 시프터(barrel shifter)가 추론됩니다. DSP48E1 슬라이스를 사용하도록 강제할 수도 있지만, 단순 32비트 연산에서는 LUT 기반 구현이 더 효율적입니다. DSP48E1은 곱셈(M 확장, Chapter 24)을 위해 남겨 두십시오.

❓ 수강생 단골 질문

Q: always_comb 안에서 case문의 default는 왜 필요한가요? 10가지 연산만 있으면 되는 것 아닌가요?

A: alu_ctrl은 4비트이므로 16가지 조합이 가능하지만, 실제로 사용하는 것은 10가지뿐입니다. default가 없으면 Vivado는 미정의 입력에 대해 래치(latch)를 추론할 수 있습니다. 래치는 조합 논리에서 의도하지 않은 상태 유지를 만들어 타이밍 분석을 어렵게 합니다. always_comb 블록에서 반드시 모든 경우에 출력을 할당해야 합니다. 이것은 합성 가능한 코드의 필수 규칙입니다.

🎯 면접 포인트

Q: always_ff와 always_comb의 차이를 설명하시오.

always_ff는 순차 논리(sequential logic)를 기술하며, 감도 리스트에 클록 에지(posedge clk)를 사용합니다. 합성 시 플립플롭(Flip-Flop)으로 추론됩니다. always_comb는 조합 논리(combinational logic)를 기술하며, 감도 리스트를 자동으로 추론합니다. 합성 시 LUT(Look-Up Table)로 추론됩니다. ALU는 클록 없이 입력 변화에 즉시 반응해야 하므로 always_comb을 사용합니다.

🔍 스스로 점검

다음 입력에 대해 ALU의 출력을 예측해 보십시오: operand_a = 32'hFFFF_FFF0, operand_b = 32'd4, alu_ctrl = 4'b0111 (SRA). 정답: $signed(32'hFFFF_FFF0)은 -16이고, 4비트 산술 우측 시프트하면 -1, 즉 32'hFFFF_FFFF가 됩니다. 만약 SRL(4'b0110)이었다면 32'h0FFFF_FFF이 됩니다.

4.3 레지스터 파일 설계

레지스터 파일(Register File)은 프로세서가 연산에 사용하는 데이터를 임시로 저장하는 고속 저장소입니다. RV32I는 32개의 32비트 범용 레지스터(x0~x31)를 정의합니다. 모든 명령어는 이 레지스터들에서 데이터를 읽고, 연산 결과를 다시 레지스터에 기록합니다.

비유: 레지스터 파일은 사무실 책상 위의 서류함입니다. 32개의 칸이 있고, 각 칸에 32비트 데이터 한 장을 넣을 수 있습니다. 0번 칸(x0)에는 항상 빈 종이(0)가 들어 있어서, 누가 다른 종이를 넣으려 해도 즉시 빈 종이로 교체됩니다. 메모리(DMEM)가 창고라면, 레지스터 파일은 손이 닿는 곳에 있는 서류함이므로 접근 속도가 훨씬 빠릅니다.

레지스터 파일의 요구 사항

단일 사이클 프로세서의 레지스터 파일은 한 클럭 사이클 내에 다음 세 가지를 모두 처리해야 합니다.

  1. 읽기 포트 2개: rs1과 rs2 주소에 해당하는 레지스터 데이터를 동시에 출력합니다. R 타입 명령어(ADD x3, x1, x2)는 두 개의 소스 레지스터를 동시에 읽어야 합니다.
  2. 쓰기 포트 1개: rd 주소에 해당하는 레지스터에 결과를 기록합니다. 단, x0에 대한 쓰기는 무시됩니다.
  3. x0 = 0 보장: RISC-V 스펙에서 x0 레지스터는 하드와이어드 제로(hardwired zero)로 정의됩니다. 어떤 명령어가 x0에 쓰기를 시도하더라도, 읽을 때 항상 0이 반환되어야 합니다.

LUTRAM vs BRAM: 비동기 읽기가 필수인 이유

여기서 매우 중요한 FPGA 설계 결정이 필요합니다. Xilinx FPGA에서 메모리를 구현하는 방법은 크게 두 가지입니다.

속성 LUTRAM (분산 RAM) BRAM (블록 RAM)
읽기 방식 비동기 (주소 → 즉시 데이터 출력) 동기 (주소 → 다음 클럭에 데이터 출력)
구현 자원 LUT (Look-Up Table) 전용 36Kb 블록
용량 소규모 (수십~수백 비트) 대규모 (최대 36Kb/블록)
단일 사이클 적합성 적합 부적합 (1사이클 지연)

왜 비동기 읽기여야 하는가? 단일 사이클 프로세서에서는 한 클럭 사이클 내에 명령어 인출(IF) → 디코딩(ID) → 레지스터 읽기 → ALU 연산 → 메모리 접근 → 기록(WB)이 모두 완료되어야 합니다. 만약 레지스터 파일 읽기에 한 사이클이 소요되면, 전체 동작에 두 사이클 이상이 필요해져서 "단일 사이클" 설계가 불가능합니다.

BRAM은 동기 읽기만 지원하므로, 단일 사이클 프로세서의 레지스터 파일에는 LUTRAM(비동기 읽기)을 사용해야 합니다. Basys 3의 Artix-7 FPGA에서 32x32비트 레지스터 파일은 약 32개의 LUT를 소비하며, 전체 LUT 20,800개 대비 0.15%에 불과하므로 자원 부담이 거의 없습니다.

SystemVerilog 구현


module register_file (
   input  logic        clk,          // 시스템 클록
   input  logic        rst_n,        // 비동기 리셋 (액티브 로우)

   // 읽기 포트 1 (비동기)
   input  logic [4:0]  rs1_addr,     // 소스 레지스터 1 주소
   output logic [31:0] rs1_data,     // 소스 레지스터 1 데이터

   // 읽기 포트 2 (비동기)
   input  logic [4:0]  rs2_addr,     // 소스 레지스터 2 주소
   output logic [31:0] rs2_data,     // 소스 레지스터 2 데이터

   // 쓰기 포트 (동기)
   input  logic [4:0]  rd_addr,      // 목적지 레지스터 주소
   input  logic [31:0] rd_data,      // 기록할 데이터
   input  logic        reg_wr_en     // 쓰기 인에이블
);

   // 32개 x 32비트 레지스터 배열
   logic [31:0] registers [0:31];

   // --- 동기 쓰기 로직 ---
   always_ff @(posedge clk or negedge rst_n) begin
      if (!rst_n) begin
         for (int i = 0; i < 32; i++) begin
            registers[i] <= 32'b0;
         end
      end else if (reg_wr_en && (rd_addr != 5'b0)) begin
         registers[rd_addr] <= rd_data;  // x0이 아닐 때만 쓰기
      end
   end

   // --- 비동기 읽기 로직 ---
   assign rs1_data = (rs1_addr == 5'b0) ? 32'b0 : registers[rs1_addr];
   assign rs2_data = (rs2_addr == 5'b0) ? 32'b0 : registers[rs2_addr];

endmodule

핵심 설계 포인트 해설

x0 보호의 이중 방어: x0이 항상 0이 되도록 두 곳에서 보호합니다. 첫째, 쓰기 로직에서 rd_addr != 5'b0 조건으로 x0에 대한 쓰기를 차단합니다. 둘째, 읽기 로직에서 (rs1_addr == 5'b0) ? 32'b0 : ...로 x0을 읽을 때 항상 0을 반환합니다. 쓰기 차단만으로도 기능적으로 충분하지만, 읽기에서도 명시적으로 0을 반환하면 리셋 전이나 시뮬레이션 초기화 전에도 x0이 항상 0임을 보장합니다.

비동기 리셋(negedge rst_n)의 선택 이유: FPGA 설계에서 비동기 리셋은 전원 인가 시 레지스터를 확실하게 초기화합니다. Xilinx Artix-7의 플립플롭은 비동기 리셋 핀을 내장하고 있으므로 추가 로직 없이 사용할 수 있습니다. 다만, 리셋 해제 타이밍은 동기화해야 합니다(리셋 동기화기, reset synchronizer). 이는 Chapter 20에서 다시 다룹니다.

for 루프의 합성: always_ff 안의 for 루프는 반복 횟수가 컴파일 시점에 확정되므로 합성 가능합니다. 합성 도구는 이를 32개의 독립적인 플립플롭 리셋 로직으로 풀어냅니다(unroll). 반면, 반복 횟수가 변수에 의존하는 루프는 합성 불가하므로 주의해야 합니다.

💡 실무 팁

Vivado에서 레지스터 파일의 합성 결과를 확인하려면 Synthesized Design → Schematic을 열어 보십시오. 비동기 읽기 + 동기 쓰기 패턴이 정확하면 RAM32M 프리미티브(LUTRAM)가 추론됩니다. 만약 RAMB36E1(BRAM)이 추론되었다면, 읽기 로직에 레지스터가 끼어 있는지 확인하십시오.

❓ 수강생 단골 질문

Q: 같은 클럭 에지에서 같은 레지스터를 읽고 쓰면 어떻게 되나요? 이전 값이 읽히나요, 새 값이 읽히나요?

A: 현재 설계에서는 이전 값(old value)이 읽힙니다. 쓰기는 클럭 상승 에지에서 발생하지만, 읽기는 비동기(조합 논리)이므로 클럭 에지 이전의 값을 출력합니다. 단, 파이프라인 프로세서(Chapter 12)에서는 이 동작이 WB-ID 해저드를 유발할 수 있어 별도의 포워딩 로직이 필요합니다. 이 주제는 그때 자세히 다룹니다.

🎯 면접 포인트

Q: 레지스터 파일을 BRAM 대신 LUTRAM으로 구현하는 이유는?

BRAM은 동기 읽기만 지원합니다. 즉, 주소를 입력한 후 다음 클럭 에지에서야 데이터가 출력됩니다. 단일 사이클 프로세서에서는 한 클럭 사이클 내에 레지스터 읽기 → ALU 연산 → 결과 기록이 모두 완료되어야 하므로, 비동기 읽기가 가능한 LUTRAM을 사용해야 합니다. 32x32비트 레지스터 파일의 LUTRAM 비용은 매우 적으므로(Artix-7 기준 LUT 약 32개), 자원 효율성 면에서도 합리적인 선택입니다.

🔍 스스로 점검

다음 시나리오를 생각해 보십시오: reg_wr_en = 1, rd_addr = 5'd0, rd_data = 32'hDEADBEEF일 때, 쓰기가 수행되는가? 그리고 직후에 rs1_addr = 5'd0으로 읽으면 어떤 값이 나오는가? (답: 쓰기 조건에서 rd_addr != 5'b0이 거짓이므로 쓰기가 수행되지 않으며, x0을 읽으면 항상 0이 반환됩니다.)

4.4 즉치수 생성기 설계

즉치수 생성기(Immediate Generator)는 32비트 명령어에서 즉치수(immediate) 필드를 추출하고, 이를 32비트로 부호 확장(sign extension)하는 조합 논리 회로입니다. Chapter 03에서 공부한 6가지 명령어 타입(R/I/S/B/U/J)은 각각 다른 위치에 즉치수 비트를 배치합니다. 즉치수 생성기의 역할은 이 다양한 배치를 하나의 통일된 32비트 출력으로 변환하는 것입니다.

비유: 즉치수 생성기는 6개국 언어로 쓰인 주문서를 한국어로 통일 번역하는 번역기입니다. I 타입 주문서는 12비트 영역에 숫자가 있고, B 타입은 13비트가 여기저기 흩어져 있고, U 타입은 상위 20비트에만 숫자가 있습니다. 번역기는 각 형식을 인식하고, 최종적으로 32비트 한국어(부호 확장된 즉치수)로 출력합니다. 단, 이 비유에는 한 가지 한계가 있습니다 — 실제 번역과 달리 즉치수 생성기는 비트의 물리적 재배열이므로, 의미 변환이 아닌 위치 변환에 가깝습니다.

왜 비트 재배열이 필요한가

RISC-V 설계자들은 디코더 하드웨어를 단순화하기 위해, 모든 명령어 타입에서 rs1, rs2, rd 필드를 같은 비트 위치에 배치했습니다. 그 대가로 즉치수 비트가 타입마다 다른 위치에 흩어지게 되었습니다. 이 "비용"을 지불하는 것이 즉치수 생성기입니다. 즉치수 비트가 항상 같은 위치에 있었다면 이 모듈이 필요 없겠지만, 레지스터 필드의 일관성이라는 더 큰 이점을 얻기 위한 트레이드오프입니다.

6가지 타입별 즉치수 구조

각 타입별로 즉치수가 어떻게 구성되는지 상세히 살펴보겠습니다.

타입 즉치수 비트 수 범위 비트 소스 (inst 필드) 특이점
I 12비트 -2048 ~ +2047 inst[31:20] 가장 단순한 형태
S 12비트 -2048 ~ +2047 inst[31:25], inst[11:7] 두 필드로 분리됨
B 13비트 -4096 ~ +4094 inst[31], inst[7], inst[30:25], inst[11:8] LSB=0 (2바이트 정렬), 비트 재배열
U 20비트 (상위) 상위 20비트 inst[31:12] 하위 12비트는 0
J 21비트 -1048576 ~ +1048574 inst[31], inst[19:12], inst[20], inst[30:21] LSB=0 (2바이트 정렬), 복잡한 재배열
R 없음 - - 즉치수를 사용하지 않음

부호 확장(Sign Extension)이란: 12비트 즉치수를 32비트로 확장할 때, 단순히 상위 비트를 0으로 채우면 음수를 표현할 수 없습니다. 예를 들어, 12비트 값 0xFFF(-1)를 32비트로 확장할 때, 상위 20비트를 최상위 비트(부호 비트)인 1로 채워야 0xFFFF_FFFF(-1)가 됩니다. RISC-V에서는 모든 타입의 즉치수에서 inst[31]이 부호 비트입니다. 이 일관성 덕분에 부호 확장 로직이 단순해집니다.

B 타입과 J 타입에서 LSB가 항상 0인 이유: RISC-V 명령어는 최소 2바이트(16비트) 정렬을 요구합니다(RV32C 압축 명령어 확장 때문). 따라서 분기/점프 대상 주소의 최하위 비트는 항상 0이므로, 인코딩에 포함하지 않고 하드웨어에서 0을 붙입니다. 이를 통해 1비트를 절약하여 더 넓은 분기 범위를 확보합니다.

SystemVerilog 구현


module imm_gen (
   input  logic [31:0] inst,        // 32비트 명령어 전체
   input  logic [2:0]  imm_sel,     // 즉치수 타입 선택
   output logic [31:0] imm_out      // 32비트 부호 확장된 즉치수
);

   always_comb begin
      case (imm_sel)
         // I 타입: imm[11:0] = inst[31:20]
         3'b000: imm_out = {{20{inst[31]}}, inst[31:20]};

         // S 타입: imm[11:5]=inst[31:25], imm[4:0]=inst[11:7]
         3'b001: imm_out = {{20{inst[31]}}, inst[31:25], inst[11:7]};

         // B 타입: 비트 재배열 + LSB=0
         3'b010: imm_out = {{19{inst[31]}}, inst[31], inst[7],
                            inst[30:25], inst[11:8], 1'b0};

         // U 타입: 상위 20비트 배치, 하위 12비트=0
         3'b011: imm_out = {inst[31:12], 12'b0};

         // J 타입: 복잡한 비트 재배열 + LSB=0
         3'b100: imm_out = {{11{inst[31]}}, inst[31], inst[19:12],
                            inst[20], inst[30:21], 1'b0};

         // R 타입 또는 기본값
         default: imm_out = 32'b0;
      endcase
   end

endmodule

구현 코드 상세 해설

각 타입별 즉치수 생성 코드를 하나씩 분석하겠습니다.

I 타입: {{20{inst[31]}}, inst[31:20]}

가장 단순한 형태입니다. inst[31:20] 12비트를 즉치수로 추출하고, {20{inst[31]}}로 부호 비트를 20번 복제하여 상위 20비트를 채웁니다. {20{inst[31]}}은 SystemVerilog의 복제 연산자(replication operator)로, inst[31]이 1이면 20'hFFFFF, 0이면 20'h00000이 됩니다.

B 타입: {{19{inst[31]}}, inst[31], inst[7], inst[30:25], inst[11:8], 1'b0}

B 타입은 가장 주의가 필요한 부분입니다. 비트가 명령어 내에서 비순차적으로 배치되어 있기 때문입니다. 즉치수의 비트 구성은 다음과 같습니다: imm[12] = inst[31](부호 비트), imm[11] = inst[7], imm[10:5] = inst[30:25], imm[4:1] = inst[11:8], imm[0] = 0(2바이트 정렬). 13비트 즉치수를 19비트 부호 확장하여 32비트로 만듭니다.

J 타입: {{11{inst[31]}}, inst[31], inst[19:12], inst[20], inst[30:21], 1'b0}

J 타입도 복잡한 재배열을 거칩니다. imm[20] = inst[31], imm[19:12] = inst[19:12], imm[11] = inst[20], imm[10:1] = inst[30:21], imm[0] = 0. 21비트 즉치수를 11비트 부호 확장합니다.

💡 실무 팁

즉치수 생성기의 합성 결과는 순수한 배선(wiring)에 가깝습니다. 비트를 재배열하고 부호 비트를 복제하는 것이므로, 실제로는 멀티플렉서 몇 개와 배선으로 구현됩니다. 이 모듈의 전파 지연은 매우 작아서 임계 경로에 영향을 주는 경우는 거의 없습니다.

❓ 수강생 단골 질문

Q: B 타입과 J 타입의 비트 재배열이 너무 복잡합니다. 외워야 하나요?

A: 외울 필요는 전혀 없습니다. 이 비트 배치는 RISC-V 스펙 문서(Volume I, Table 2.3)에 명확히 정의되어 있으며, 구현할 때마다 스펙을 참조하면 됩니다. 중요한 것은 "왜 이렇게 배치했는가"를 이해하는 것입니다: rs1, rs2, rd 필드를 고정 위치에 두기 위한 트레이드오프이며, 부호 비트가 항상 inst[31]에 있다는 일관성을 유지하기 위함입니다. 이 두 가지 원칙만 기억하면 됩니다.

🎯 면접 포인트

Q: RISC-V에서 부호 확장은 어떻게 구현되며, 왜 모든 즉치수의 부호 비트가 inst[31]에 있는가?

RISC-V ISA 설계자는 의도적으로 모든 명령어 타입에서 즉치수의 최상위 비트(부호 비트)를 inst[31]에 배치했습니다. 이 덕분에 부호 확장 로직이 단 하나의 비트(inst[31])만 복제하면 되어 하드웨어가 단순해집니다. 또한 부호 확장은 임계 경로(critical path)에서 빠르게 수행되어야 하는데, 팬아웃(fan-out)이 하나의 비트에서만 발생하므로 타이밍에 유리합니다.

🔍 스스로 점검

다음 32비트 명령어를 B 타입이라고 가정하고, 즉치수를 직접 추출해 보십시오: inst = 32'b1_000001_01010_01001_000_0110_0_1100011. 정답: inst[31]=1, inst[7]=0, inst[30:25]=000001, inst[11:8]=0110이므로 imm = {19{1}, 1, 0, 000001, 0110, 0} = 32'hFFFFF80C = -2036(10진수). 직접 손으로 풀어보는 것이 가장 확실한 이해 방법입니다.

4.5 단위 모듈 테스트벤치 작성

모듈을 설계했으면 반드시 검증해야 합니다. "시뮬레이션에서 동작하지 않는 설계는 실리콘에서도 동작하지 않는다"는 것은 디지털 설계의 철칙입니다. 이 절에서는 ALU와 레지스터 파일에 대한 단위 테스트벤치(unit testbench)를 SystemVerilog로 작성합니다.

비유: 테스트벤치는 자동차 공장의 품질 검사 라인입니다. 엔진(ALU)을 조립한 후 바로 자동차에 장착하지 않고, 검사대에 올려 다양한 조건(고속, 저속, 역회전 등)에서 정상 동작하는지 확인합니다. 단위 테스트는 각 부품을 개별적으로 검사하는 과정이고, 통합 테스트(Chapter 06)는 부품들을 조립한 후 전체 시스템을 검사하는 과정입니다.

테스트벤치의 기본 구조

SystemVerilog 테스트벤치는 합성 대상이 아닌 시뮬레이션 전용 코드입니다. 따라서 $display, $finish, initial 블록, 시간 지연(#) 등 합성 불가 구문을 자유롭게 사용할 수 있습니다. 테스트벤치의 기본 구조는 다음과 같습니다.

  1. DUT(Design Under Test) 인스턴스화: 검증 대상 모듈을 테스트벤치 내부에 인스턴스화합니다.
  2. 입력 자극(stimulus) 생성: initial 블록에서 입력 신호를 시간 순서대로 변경합니다.
  3. 결과 검증: 출력을 기대값과 비교하여 PASS/FAIL을 판정합니다.
  4. 결과 보고: 테스트 통계(총 개수, 통과, 실패)를 출력합니다.

ALU 테스트벤치

ALU 테스트벤치는 10가지 연산 각각에 대해 정상 입력과 경계값(boundary value)을 테스트합니다. 경계값 테스트는 오버플로, 언더플로, 최대 시프트량 등 극단적인 입력을 검증합니다.


`timescale 1ns / 1ps

module alu_tb;

   logic [31:0] operand_a;
   logic [31:0] operand_b;
   logic [3:0]  alu_ctrl;
   logic [31:0] alu_result;
   logic        alu_zero;

   // DUT 인스턴스
   alu u_alu (
      .operand_a  (operand_a),
      .operand_b  (operand_b),
      .alu_ctrl   (alu_ctrl),
      .alu_result (alu_result),
      .alu_zero   (alu_zero)
   );

   // ALU 제어 코드 상수
   localparam logic [3:0] ALU_ADD  = 4'b0000;
   localparam logic [3:0] ALU_SUB  = 4'b0001;
   localparam logic [3:0] ALU_AND  = 4'b0010;
   localparam logic [3:0] ALU_SLT  = 4'b1000;
   localparam logic [3:0] ALU_SLTU = 4'b1001;
   // ... (나머지 상수 정의)

   // 테스트 통계
   int pass_count = 0;
   int fail_count = 0;

   // 검증 태스크
   task automatic check(
      input string test_name,
      input [31:0] expected_result,
      input        expected_zero
   );
      #1; // 조합 논리 안정화 대기
      if (alu_result !== expected_result || alu_zero !== expected_zero) begin
         $display("[FAIL] %s", test_name);
         fail_count++;
      end else begin
         $display("[PASS] %s: result=0x%08h", test_name, alu_result);
         pass_count++;
      end
   endtask

   initial begin
      // --- ADD 테스트 ---
      operand_a = 32'd10; operand_b = 32'd20; alu_ctrl = ALU_ADD;
      check("ADD: 10+20", 32'd30, 1'b0);

      // 오버플로 테스트
      operand_a = 32'hFFFF_FFFF; operand_b = 32'd1; alu_ctrl = ALU_ADD;
      check("ADD: overflow", 32'd0, 1'b1);

      // --- SLT vs SLTU 핵심 테스트 ---
      operand_a = 32'hFFFF_FFFF; operand_b = 32'd1; alu_ctrl = ALU_SLT;
      check("SLT: -1 < 1 (signed)", 32'd1, 1'b0);

      operand_a = 32'hFFFF_FFFF; operand_b = 32'd1; alu_ctrl = ALU_SLTU;
      check("SLTU: 0xFFFFFFFF < 1 (unsigned)", 32'd0, 1'b1);

      // ... (나머지 10가지 연산 테스트)

      $display("통과: %0d, 실패: %0d", pass_count, fail_count);
      $finish;
   end

endmodule

테스트벤치 핵심 기법 해설

task automatic의 사용: automatic 키워드는 태스크의 지역 변수가 각 호출마다 독립적으로 할당되도록 합니다. 이를 지정하지 않으면 static(기본값)으로 동작하여, 동시 호출 시 변수가 공유되는 문제가 발생할 수 있습니다.

#1 지연의 의미: ALU는 조합 논리이므로 입력 변경 후 출력이 즉시 변하지만, 시뮬레이터는 이벤트 큐(event queue) 기반으로 동작합니다. #1(1ns 지연)을 삽입하면 시뮬레이터가 모든 조합 논리 전파를 완료한 후 결과를 읽게 됩니다.

!== vs != 연산자: !==는 4-상태(0, 1, x, z) 정밀 비교입니다. !=는 x나 z가 포함되면 결과가 x가 되어 버그를 놓칠 수 있습니다. 테스트벤치에서는 항상 === / !==를 사용하는 것이 안전합니다.

레지스터 파일 테스트벤치

레지스터 파일 테스트벤치는 순차 논리(클록 기반)이므로, 클록 생성기와 리셋 시퀀스가 추가됩니다. 핵심 검증 항목은 다음과 같습니다.

  1. 리셋 후 초기값: 모든 레지스터가 0으로 초기화되었는가?
  2. 정상 쓰기/읽기: 특정 레지스터에 쓴 후 올바르게 읽히는가?
  3. x0 쓰기 보호: x0에 쓰기를 시도한 후에도 0이 유지되는가?
  4. 두 포트 동시 읽기: rs1과 rs2가 서로 다른 레지스터를 동시에 읽을 수 있는가?
  5. 쓰기 비활성: reg_wr_en = 0일 때 쓰기가 무시되는가?
  6. 비동기 읽기: 주소 변경 후 클록 없이 즉시 데이터가 변하는가?

module register_file_tb;

   logic        clk;
   logic        rst_n;
   logic [4:0]  rs1_addr, rs2_addr, rd_addr;
   logic [31:0] rs1_data, rs2_data, rd_data;
   logic        reg_wr_en;

   register_file u_rf ( .* );  // 포트 자동 연결

   // 클록 생성: 10ns 주기 (100MHz)
   initial clk = 1'b0;
   always #5 clk = ~clk;

   // 쓰기 태스크
   task automatic write_reg(input [4:0] addr, input [31:0] data);
      @(posedge clk);
      rd_addr = addr; rd_data = data; reg_wr_en = 1'b1;
      @(posedge clk);
      reg_wr_en = 1'b0;
   endtask

   initial begin
      // 리셋
      rst_n = 1'b0; reg_wr_en = 1'b0;
      repeat(3) @(posedge clk);
      rst_n = 1'b1;
      @(posedge clk);

      // 테스트 1: x0 읽기 (항상 0)
      rs1_addr = 5'd0; #1;
      assert(rs1_data == 32'd0) else $error("x0 != 0");

      // 테스트 2: x1에 쓰기 후 읽기
      write_reg(5'd1, 32'hDEAD_BEEF);
      rs1_addr = 5'd1; #1;
      assert(rs1_data == 32'hDEAD_BEEF) else $error("x1 write fail");

      // 테스트 3: x0에 쓰기 시도 (무시되어야 함)
      write_reg(5'd0, 32'h1234_5678);
      rs1_addr = 5'd0; #1;
      assert(rs1_data == 32'd0) else $error("x0 protection fail");

      // ... (추가 테스트)
      $finish;
   end

endmodule

❓ 수강생 단골 질문

Q: assert문과 if문 비교 — 어떤 것을 사용해야 하나요?

A: 둘 다 유효한 검증 방법이지만, assert는 시뮬레이터가 실패 횟수를 자동으로 집계하고, Vivado의 시뮬레이션 로그에서 경고로 표시되는 장점이 있습니다. 반면, 우리 테스트벤치처럼 task 기반의 $display + 수동 카운팅 방식은 출력 형식을 자유롭게 제어할 수 있고, 모든 시뮬레이터에서 동일하게 동작합니다. 산업계에서는 UVM(Universal Verification Methodology) 프레임워크의 uvm_error/uvm_fatal을 주로 사용하지만, 이 교재의 범위에서는 위 두 가지로 충분합니다.

📌 강사 꿀팁

학생들이 테스트벤치 작성을 귀찮아하는 경우가 많습니다. "테스트벤치 없이 합성하면 Vivado는 통과하지만, 실리콘에서 동작하지 않을 수 있습니다"라고 강조하십시오. 실무에서 검증(Verification) 엔지니어의 수가 설계(Design) 엔지니어보다 2~3배 많다는 사실을 언급하면 동기 부여가 됩니다.

🔍 스스로 점검

ALU 테스트벤치에서 SLT와 SLTU의 차이를 검증하는 테스트 케이스를 직접 추가해 보십시오. operand_a = 0x80000000, operand_b = 0x00000001일 때, SLT 결과와 SLTU 결과가 각각 무엇인지 예측하고 시뮬레이션으로 확인하십시오. (힌트: SLT에서 0x80000000은 -2,147,483,648이고, SLTU에서는 2,147,483,648입니다.)

4.6 본 챕터 요약 및 다음 단계

이 챕터에서 우리는 RV32I 프로세서 데이터패스의 세 가지 핵심 모듈을 설계하고 검증했습니다. 이 모듈들은 아직 서로 연결되지 않은 독립적인 부품이지만, Chapter 06에서 제어 유닛과 함께 통합되면 실제로 명령어를 실행할 수 있는 프로세서가 됩니다.

각 모듈을 설계하면서 우리는 단순히 코드를 작성하는 것을 넘어, FPGA에서의 합성 결과(LUTRAM vs BRAM), 하드웨어 트레이드오프(비동기 읽기 vs 동기 읽기), 그리고 ISA 설계 철학(부호 비트 일관성, 비트 재배열의 이유)까지 이해했습니다.

핵심 정리

  • ALU: 10가지 연산(ADD, SUB, AND, OR, XOR, SLL, SRL, SRA, SLT, SLTU)을 always_comb로 구현. SRA는 $signed 캐스팅 필수. 시프트량은 하위 5비트만 사용.
  • 레지스터 파일: 32x32비트, 비동기 읽기(LUTRAM) + 동기 쓰기 구조. BRAM은 동기 읽기만 지원하므로 단일 사이클에 부적합. x0 쓰기 보호는 쓰기 조건과 읽기 MUX에서 이중으로 구현.
  • 즉치수 생성기: 6가지 타입(R/I/S/B/U/J)별 비트 추출 및 부호 확장. 모든 타입에서 inst[31]이 부호 비트 — RISC-V ISA의 의도적 설계.
  • 테스트벤치: 경계값 분석 기반 단위 테스트. always_comb → #1 후 검증. always_ff → @(posedge clk) 후 검증.
  • Gradual Reveal: 이번 챕터는 데이터패스 점진적 공개 5단계 중 1단계. 아직 메모리와 제어 유닛이 남아 있음.

연습문제

  1. [이해] ALU에서 SRL과 SRA의 차이를 설명하시오. operand_a = 32'hF000_0000을 4비트 우측 시프트할 때 각각의 결과를 계산하시오.
  2. [이해] 레지스터 파일의 읽기를 비동기로, 쓰기를 동기로 구현하는 이유를 FPGA 합성 관점에서 설명하시오. 만약 읽기도 동기(BRAM)로 구현하면 단일 사이클 프로세서에서 어떤 문제가 발생하는가?
  3. [적용] 즉치수 생성기에서 B 타입 즉치수를 추출하는 코드를 직접 작성하시오. 다음 명령어의 즉치수 값을 수동으로 계산하시오: BEQ x1, x2, -8 (opcode=1100011, funct3=000).
  4. [적용] ALU 테스트벤치에 SLL 연산의 경계값 테스트를 3개 이상 추가하시오. (시프트량 0, 31, 그리고 operand_b의 상위 비트가 1인 경우를 포함할 것.)
  5. [분석] 현재 ALU 설계에서 default 분기를 제거하면 Vivado 합성 결과에 어떤 변화가 발생하는가? 합성 경고 메시지를 확인하고, 래치(latch) 추론 여부를 분석하시오.
  6. [분석] 레지스터 파일에서 x0 보호를 읽기 쪽(assign)에서만 구현하고, 쓰기 쪽의 rd_addr != 5'b0 조건을 제거하면 기능적으로 문제가 있는가? 전력 소비 관점에서는 어떤 차이가 있는가?
  7. [평가] RISC-V의 즉치수 비트 배치 방식을 ARM이나 MIPS의 방식과 비교하시오. RISC-V가 레지스터 필드 위치를 고정하고 즉치수 비트를 흩뜨리는 트레이드오프의 장단점을 논하시오.
