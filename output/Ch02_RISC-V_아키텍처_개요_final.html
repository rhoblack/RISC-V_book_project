Chapter 02

RISC-V ISA 기초: 레지스터, 메모리, 명령어 형식

프로세서를 설계하기 위해서는 그 프로세서가 "이해하는 언어", 즉 명령어 집합 구조(ISA, Instruction Set Architecture)를 먼저 파악해야 합니다. 이 챕터에서는 RISC-V가 탄생한 배경과 설계 철학부터 시작하여, 32개의 범용 레지스터 구조, 바이트 주소 기반 메모리 모델, 그리고 6가지 명령어 형식을 체계적으로 학습합니다. 챕터 말미의 실습 절에서는 실제 32비트 명령어를 직접 인코딩하고 디코딩하는 경험을 통해 이후 RTL 설계의 든든한 기반을 마련합니다.

학습 목표

  • LO-1: RISC-V의 설계 철학 3가지(단순성, 모듈성, 개방성)를 열거할 수 있다.
  • LO-2: 레지스터 파일 구조(32개 범용 레지스터, x0 고정 0, ABI 명칭)를 설명할 수 있다.
  • LO-3: 메모리 모델(바이트 주소 지정, 리틀 엔디언, 정렬 규칙)의 차이를 구별할 수 있다.
  • LO-4: R, I, S, B, U, J 6가지 명령어 형식을 식별하고 각 필드 배치를 설명할 수 있다.
  • LO-5: 주어진 어셈블리 명령어를 32비트 2진수로 인코딩하고, 반대로 디코딩을 수행할 수 있다.

2.1 RISC-V의 탄생과 설계 철학

2010년 UC 버클리의 크리스토스 코지라키스(Krste Asanović) 교수 연구팀은 새로운 프로세서 교육 과정을 준비하면서 기존 ISA의 복잡한 라이선스 문제와 역사적 유산이 누적된 복잡성에 좌절감을 느꼈습니다. x86은 수십 년에 걸쳐 쌓인 하위 호환성의 짐을 안고 있었고, ARM은 상용 라이선스 비용이 상당했습니다. MIPS는 교육용으로 적합했지만 모바일·임베디드 환경에서의 실무 적용성이 떨어졌습니다. 결국 이 팀은 "처음부터 다시 만들자"는 결론에 도달했고, 그렇게 탄생한 것이 RISC-V(리스크 파이브, RISC-V)입니다. 이름의 'V'는 버클리 팀이 설계한 다섯 번째 RISC 프로젝트임을 의미하는 동시에 로마 숫자 5를 뜻합니다.

설계 철학 1: 단순성(Simplicity)

RISC-V의 기본 정수 명령어 집합인 RV32I는 기본 명령어 40개에 Zicsr(6개)과 Zifencei(1개) 확장을 포함하면 총 47개의 명령어로 구성되어 있습니다. 이는 x86-64의 수천 개, ARM Cortex-A 시리즈의 수백 개와 비교할 때 놀라울 만큼 작은 수입니다. 설계자들은 "기능을 추가하는 것보다 불필요한 기능을 제거하는 것이 더 어렵다"는 원칙을 고수했습니다. 단순한 ISA는 곧 단순한 디코더(Decoder)와 실행 유닛(Execution Unit)으로 이어지며, 이는 전력 소모 감소, 검증 용이성, 그리고 교육 목적의 명확성이라는 삼중 효과를 낳습니다.

이 교재에서 구현할 RV32I 파이프라인 프로세서도 이 47개 명령어를 완전히 지원하는 것을 목표로 합니다. 챕터 3에서 각 명령어를 상세히 분류하겠지만, 오늘 학습하는 6가지 명령어 형식만 이해하면 어떤 명령어를 처음 보더라도 그 구조를 파악할 수 있습니다.

설계 철학 2: 모듈성(Modularity)

RISC-V의 두 번째 핵심 철학은 모듈형 확장입니다. 기본 정수 ISA(RV32I)를 토대로, 응용 목적에 따라 표준 확장(Extension)을 선택적으로 추가하는 방식입니다.

비유 — USB-C와 표준 확장: RISC-V를 USB-C 커넥터에 비유할 수 있습니다. USB-C 포트 자체는 기본 규격(RV32I)이고, Thunderbolt 지원, DisplayPort Alt Mode, USB 3.2 등은 선택적 확장(M, F, D, C, V 확장)에 해당합니다. 커넥터 모양이 동일하기 때문에 어떤 장치에나 꽂을 수 있지만, 장치가 지원하는 기능에 따라 실제 동작은 달라집니다. 마찬가지로 RISC-V 소프트웨어는 기본 ISA만으로도 동작하며, 하드웨어가 추가 확장을 지원할 경우 더욱 고성능·고기능 연산이 가능합니다. 다만 이 비유에는 한계가 있습니다. USB-C는 물리적 커넥터 표준이고 RISC-V는 명령어 집합 표준이므로, 추상화 수준이 다릅니다.

주요 표준 확장의 의미를 간략히 정리하면 다음과 같습니다. M 확장은 곱셈·나눗셈 명령어(Multiply/Divide), A 확장은 원자적 명령어(Atomic Instructions)로 멀티코어 동기화에 사용됩니다. F/D 확장은 각각 단정밀도/배정밀도 부동소수점(Floating Point) 연산을 추가하고, C 확장은 16비트 압축 명령어(Compressed Instructions)로 코드 밀도를 높입니다. V 확장은 벡터(Vector) 연산으로 SIMD(Single Instruction Multiple Data, 단일 명령 다중 데이터) 처리 능력을 제공합니다. 이들의 조합을 표기할 때 흔히 "RV32IMAC", "RV64GC" 같은 형태를 사용합니다. 여기서 'G'는 IMAFD의 약어로, 범용 리눅스 환경에 필요한 최소 조합을 의미합니다.

설계 철학 3: 개방성(Openness)

세 번째이자 가장 혁신적인 철학은 개방 표준(Open Standard)입니다. RISC-V ISA 명세서는 누구나 무료로 사용할 수 있으며, 라이선스 비용 없이 하드웨어 구현이 가능합니다. 이는 ARM이나 MIPS의 라이선스 모델과 근본적으로 다릅니다. 개인 연구자부터 스타트업, 대기업, 국가 기관까지 동일한 조건으로 RISC-V를 구현할 수 있습니다. 2024년 기준 SiFive, Andes Technology, 알리바바(T-Head), 화웨이, 삼성전자, NVIDIA 등 수백 개의 기업이 RISC-V 기반 칩을 설계하고 있습니다.

이 교재에서 여러분이 설계하는 RV32I 파이프라인 프로세서도 법적·경제적 부담 없이 FPGA에 구현하고, 수정하고, 공유할 수 있습니다. 바로 이 개방성이 RISC-V를 교육용 ISA로 최적으로 만드는 핵심 이유 중 하나입니다.

💡 실무 팁 — RISC-V 확장 문자열 읽기

칩 데이터시트나 컴파일러 옵션에서 "rv32imac_zicsr_zifencei"와 같은 문자열을 자주 볼 수 있습니다. 알파벳 확장 코드 뒤에 등장하는 z로 시작하는 확장(Zicsr, Zifencei 등)은 2021년 이후 표준화된 세분화 확장입니다. Zicsr은 CSR(Control and Status Register) 명령어, Zifencei는 명령어 펜스(Fence) 명령어를 각각 분리하여 명시합니다. 펜스(Fence)란 메모리 접근 순서를 보장하는 동기화 명령어입니다. GCC나 Clang에서 -march=rv32imac_zicsr 형태로 타깃 아키텍처를 지정할 때 유용합니다.

❓ 수강생 단골 질문

Q: RISC-V가 좋다면 ARM은 이제 없어지는 건가요?

A: 그렇지 않습니다. ARM은 수십 년간 축적된 소프트웨어 생태계, 최적화된 IP(Intellectual Property, 지식재산) 코어, 검증된 물리 설계 라이브러리를 보유하고 있습니다. 스마트폰과 같이 전력 효율과 성능이 극단적으로 중요한 분야에서는 당분간 ARM이 지배적 위치를 유지할 것입니다. RISC-V는 IoT 엣지 디바이스, 도메인 특화 가속기, 교육·연구 분야에서 빠르게 성장하고 있습니다. 두 ISA는 "경쟁"보다 "공존"에 가깝고, 설계자는 응용 요구사항에 따라 적합한 ISA를 선택합니다.

🎯 면접 포인트 — ISA 라이선스와 개방 표준의 의미

"RISC-V의 개방 표준이 산업에 미치는 영향을 설명하시오"는 반도체 설계 직군 면접에서 자주 등장하는 질문입니다. 핵심 답변 포인트는 세 가지입니다: (1) 라이선스 비용 제거로 스타트업과 학술 기관의 진입 장벽 감소, (2) 벤더 종속성(Vendor Lock-in) 해소로 공급망 다변화 가능, (3) 투명한 명세서로 인한 보안 감사 및 커스터마이징 용이성. 반대로 단점도 말할 수 있어야 합니다: ARM 대비 성숙하지 않은 소프트웨어 생태계, 상용 구현체(IP Core)의 상대적 부족이 여기에 해당합니다.

2.2 레지스터 파일: x0~x31과 PC

프로세서 내부에서 연산이 이루어지는 "작업 공간"은 레지스터(Register)입니다. RV32I는 32비트 너비의 범용 레지스터(General-Purpose Register) 32개와 별도의 프로그램 카운터(Program Counter, PC)를 갖습니다. 메모리는 방대하지만 접근 속도가 느린 반면, 레지스터는 프로세서 클럭 사이클 내에 즉시 읽고 쓸 수 있는 고속 임시 저장소입니다.

비유 — 요리사의 조리대 서랍 32개: 레지스터 파일을 요리사 조리대에 달린 32개의 서랍으로 생각해 보십시오. 재료(데이터)를 멀리 있는 창고(메모리)에서 꺼내 서랍에 올려놓고 요리(연산)를 진행합니다. 서랍 번호 0번(x0)은 자물쇠가 채워진 특별한 서랍으로, 어떤 물건을 넣어도 꺼내면 항상 비어 있습니다. 즉, x0은 항상 숫자 0을 반환하는 특수 레지스터입니다. PC는 현재 읽고 있는 레시피(프로그램)의 페이지를 가리키는 책갈피(클립)에 해당합니다. 이 비유의 한계: 실제 레지스터 파일은 한 클럭 사이클에 2개를 동시에 읽고 1개를 쓸 수 있지만, 물리적 서랍으로는 이런 동시 접근이 불가능합니다.

레지스터 번호와 ABI 명칭

RISC-V 명세서는 레지스터를 x0부터 x31까지 번호로 정의합니다. 그러나 실제 어셈블리 프로그래밍과 컴파일러 출력에서는 각 레지스터의 역할에 따른 ABI(Application Binary Interface) 명칭을 사용하는 것이 관례입니다. ABI 명칭은 소프트웨어 계층 간 레지스터 사용 규약을 정의하므로, RTL 설계자도 이를 이해해야 어셈블리 테스트벤치를 읽고 디버깅할 수 있습니다.

x0 레지스터의 특별한 역할

x0(zero)은 RISC-V 설계 철학의 단순성을 보여주는 좋은 예입니다. 이 레지스터는 하드와이어드(Hardwired)되어 항상 0을 출력합니다. 하드와이어드(Hardwired)란 회로적으로 고정 연결되어 소프트웨어로 변경할 수 없는 상태를 뜻합니다. 쓰기 시도는 무시됩니다. 이 하나의 레지스터로 여러 유사 명령어 필요성이 사라집니다. 예를 들어 레지스터 초기화는 addi rd, x0, 0으로, 레지스터 복사는 addi rd, rs, 0으로, 무조건 분기는 jalr x0, 0(rs)로 표현할 수 있습니다. ARM의 경우 이런 목적을 위한 별도 명령어(MOV, CLR 등)가 필요한 것과 대조적입니다.

프로그램 카운터(PC)

프로그램 카운터(Program Counter, PC)는 현재 실행 중인 명령어의 메모리 주소를 담고 있는 전용 레지스터입니다. RV32I에서 모든 명령어는 4바이트(32비트) 크기이므로, 일반적인 순차 실행에서 PC는 매 사이클 4씩 증가합니다(PC ← PC + 4). 분기(Branch)나 점프(Jump) 명령어는 PC를 특정 주소로 갱신하여 프로그램 흐름을 바꿉니다. 파이프라인 설계에서 PC 관리는 해저드(Hazard) 처리와 직결되므로 챕터 9~11의 파이프라인 챕터에서 상세히 다룹니다.

리셋(Reset) 직후 PC의 초기값은 구현에 따라 다르지만, RISC-V 특권 명세(Privileged Specification)는 0x00000000 또는 플랫폼 정의 부트 주소에서 시작하도록 규정합니다. 이 교재의 Basys 3 FPGA 구현에서는 명령어 메모리 시작 주소인 0x00000000을 리셋 PC로 사용합니다.

레지스터 파일 SystemVerilog 구현

다음은 RV32I 레지스터 파일의 SystemVerilog 구현입니다. 2개의 읽기 포트와 1개의 쓰기 포트를 갖는 구조로, FPGA의 분산 RAM(Distributed RAM)으로 자동 추론됩니다. 분산 RAM이란 FPGA의 LUT(Look-Up Table)를 소규모 메모리로 활용하는 방식입니다. 

// 레지스터 파일 — 32개 범용 레지스터
module register_file (
   input  logic        clk,
   input  logic        we3,      // 쓰기 인에이블
   input  logic [4:0]  ra1, ra2, // 읽기 포트 주소
   input  logic [4:0]  wa3,      // 쓰기 포트 주소
   input  logic [31:0] wd3,      // 쓰기 데이터
   output logic [31:0] rd1, rd2  // 읽기 데이터
);
   logic [31:0] rf [31:0];       // 32x32 레지스터 배열
   // x0은 항상 0 — 쓰기 시 무시됨
   always_ff @(posedge clk)
      if (we3 && wa3 != 5'b0) rf[wa3] <= wd3;
   // 비동기 읽기 (FPGA에서 분산 RAM 추론)
   assign rd1 = (ra1 != 5'b0) ? rf[ra1] : 32'b0;
   assign rd2 = (ra2 != 5'b0) ? rf[ra2] : 32'b0;
endmodule

위 코드에서 핵심 포인트를 짚어봅니다. 쓰기 동작은 always_ff 블록 내에서 클럭 상승 에지에 동기화되어 수행됩니다. 조건 wa3 != 5'b0은 x0에 대한 쓰기를 하드웨어적으로 방지합니다. 읽기 동작은 assign 문으로 구현된 조합 논리(Combinational Logic)로, 클럭과 무관하게 즉시 값을 출력합니다. 읽기 주소가 0인 경우 항상 32비트 0을 반환하도록 명시적으로 처리합니다. 이 구현은 "새로 쓴 값을 같은 사이클에 읽을 수 없다"는 레지스터 읽기/쓰기 충돌(Read-After-Write Hazard) 시나리오를 만들며, 이는 챕터 10의 포워딩(Forwarding) 설계에서 중요하게 다루어집니다.

💡 실무 팁 — Caller-Saved vs Callee-Saved 구분법

함수 호출 규약(Calling Convention)에서 레지스터 보존 의무는 혼란을 일으키기 쉽습니다. 간단한 기억법: Caller-Saved(호출자 보존)은 "내가 함수를 호출하기 전에 내가 직접 백업해야 하는 레지스터"입니다(t0-t6, a0-a7, ra). Callee-Saved(피호출자 보존)은 "내가 호출받은 함수 안에서 사용하면 반드시 복원해야 하는 레지스터"입니다(s0-s11, sp). RTL 테스트벤치 작성 시 컴파일러가 생성한 어셈블리를 분석할 때 이 구분이 필수적입니다.

❓ 수강생 단골 질문

Q: x0에 값을 쓰면 어떻게 되나요? 오류가 발생하나요?

A: 오류는 발생하지 않습니다. x0에 대한 쓰기 명령어는 실행되지만, 하드웨어가 해당 쓰기를 조용히 무시합니다(위 코드의 wa3 != 5'b0 조건 참고). 읽을 때는 항상 0이 반환됩니다. 이는 버그가 아니라 의도된 동작으로, 결과를 버릴 필요가 있을 때 목적지 레지스터를 x0으로 지정하는 프로그래밍 관용구에 활용됩니다. 예: sw 명령어처럼 결과값이 없는 명령어도 내부적으로 rd 필드를 갖는데, 이를 x0으로 설정하면 의미 없는 쓰기가 자동으로 무력화됩니다.

🔍 스스로 점검 — 레지스터 구조 이해도 확인

다음 질문에 답할 수 있다면 2.2절을 충분히 이해한 것입니다:

  1. RV32I 레지스터는 몇 개이며, 각각 몇 비트인가?
  2. x0에 값 5를 쓰는 명령어(addi x0, x0, 5)를 실행한 뒤 x0을 읽으면 무엇이 나오는가?
  3. 함수에서 s0(x8) 레지스터를 사용하려면 진입 시 어떤 작업이 필요한가?
  4. 위 SystemVerilog 코드에서 읽기 포트가 동기식이 아닌 조합 논리로 구현된 이유는?
📌 강사 꿀팁 — 레지스터 ABI 명칭 암기 강요 금지

x0~x31의 ABI 명칭(zero, ra, sp, ...)을 수업 초반에 통째로 암기시키는 것은 역효과를 낳습니다. 학습자가 어셈블리 코드를 처음 접할 때 필요한 레지스터의 ABI 명칭만 그때그때 참조표로 확인하게 하십시오. 챕터 3(명령어 세트)과 챕터 4(데이터패스) 실습을 거치며 자연스럽게 익혀집니다. 대신 "x0은 항상 0", "a0-a7은 함수 인수", "s0-s11은 함수 안에서 보존 필요"라는 세 가지 핵심 그룹의 역할은 첫 수업에서 반드시 이해시키십시오.

2.3 메모리 모델과 주소 공간

레지스터가 프로세서 내부의 고속 작업 공간이라면, 메모리(Memory)는 프로그램과 대용량 데이터를 보관하는 외부 저장소입니다. RISC-V의 메모리 모델은 단순하면서도 실무에서 반드시 이해해야 할 몇 가지 규칙으로 이루어져 있습니다. 이 절을 마치면 리틀 엔디언 오류, 정렬 위반 등 임베디드 디버깅의 단골 함정을 사전에 인식하고 예방할 수 있게 됩니다.

바이트 주소 지정 방식

RISC-V 메모리는 바이트 주소 지정(Byte-Addressable) 방식을 사용합니다. 즉, 메모리의 각 주소는 1바이트(8비트) 데이터를 가리킵니다. RV32I의 주소 공간은 32비트이므로, 이론적으로 232바이트 = 4GiB의 메모리를 직접 주소 지정할 수 있습니다. 실제로 주소 0x00000000부터 0xFFFFFFFF까지 약 43억 개의 바이트 위치가 존재합니다.

32비트 단어(Word)를 메모리에서 읽거나 쓸 때는 4개의 연속 바이트 주소를 사용합니다. 예를 들어 주소 0x00000100에 저장된 32비트 단어는 바이트 주소 0x100, 0x101, 0x102, 0x103에 걸쳐 위치합니다.

리틀 엔디언 바이트 순서

복수의 바이트로 이루어진 데이터를 메모리에 배치할 때, 바이트의 순서를 엔디언(Endianness)이라 합니다. RISC-V는 기본적으로 리틀 엔디언(Little-Endian) 방식을 사용합니다. 리틀 엔디언이란 최하위 바이트(Least Significant Byte, LSB)가 가장 낮은 주소에, 최상위 바이트(Most Significant Byte, MSB)가 가장 높은 주소에 저장되는 방식입니다.

비유 — 뒤에서부터 싣는 택배 상자: 리틀 엔디언을 이해하는 직관적 방법은 택배 상자에 번호를 붙이는 상황을 생각하는 것입니다. 4자리 물품 번호 "1234"를 상자 번호 순서대로 기록할 때, 빅 엔디언(Big-Endian)은 "상자1=1, 상자2=2, 상자3=3, 상자4=4"처럼 큰 자리부터 씁니다. 리틀 엔디언은 반대로 "상자1=4, 상자2=3, 상자3=2, 상자4=1"처럼 작은 자리(낮은 자릿수)부터 씁니다. 즉, 주소가 낮은 쪽에 작은 단위(LSB)가 먼저 옵니다. x86, ARM(기본), RISC-V 모두 리틀 엔디언을 채택하고 있어, 오늘날 PC와 임베디드 시장에서 사실상 표준입니다. 이 비유의 한계: 실제 메모리의 각 바이트는 0~255 범위의 8비트 값이지, 한 자리 숫자가 아닙니다.

구체적인 예로, 32비트 값 0xDEADBEEF를 주소 0x1000에 저장하면 메모리 배치는 다음과 같습니다:

바이트 주소 저장값 (16진수) 설명
0x10000xEF최하위 바이트 (LSB)
0x10010xBE두 번째 바이트
0x10020xAD세 번째 바이트
0x10030xDE최상위 바이트 (MSB)

시뮬레이터나 메모리 덤프 툴에서 주소 0x1000을 확인하면 EF BE AD DE 순으로 보이는 것이 바로 리틀 엔디언의 시각적 특성입니다. 처음 보면 "거꾸로 된 것 같다"는 느낌을 주지만, 이 교재의 실습을 3~4번 해보면 자연스럽게 익숙해집니다.

메모리 정렬 규칙

RISC-V는 하드웨어 구현을 단순화하기 위해 정렬된 메모리 접근(Aligned Memory Access)을 권장합니다. 정렬 규칙이란 n바이트 데이터는 n의 배수 주소에서 시작해야 함을 의미합니다:

  • 바이트(1byte): 임의 주소 접근 가능 — 정렬 제한 없음
  • 하프워드(2byte, lh/sh): 2의 배수 주소 (주소 & 0x1 == 0)
  • 워드(4byte, lw/sw): 4의 배수 주소 (주소 & 0x3 == 0)

RISC-V의 기본 명세는 비정렬 접근(Misaligned Access)에 대해 구현 선택 사항으로 남겨두었습니다. 하드웨어가 비정렬 접근을 지원하지 않는 경우, 접근 미스정렬 예외(Load Address Misaligned Exception)가 발생합니다. 이 교재의 간단화된 RV32I 구현에서는 정렬된 접근만 지원하는 것으로 가정합니다.

💡 실무 팁 — 엔디언 관련 디버깅 실수 방지

SystemVerilog 시뮬레이션에서 메모리 초기화 파일(.mem 또는 .hex)을 작성할 때 엔디언을 혼동하는 실수가 빈번합니다. Vivado의 $readmemh 함수는 파일의 각 행을 메모리의 연속 주소에 저장하는데, 이때 행 내의 바이트 순서는 빅 엔디언(가장 왼쪽 = MSB)입니다. 반면 실제 RV32I 프로세서는 리틀 엔디언으로 데이터를 해석합니다. lw 명령어 동작을 검증하는 테스트벤치를 작성할 때는 .mem 파일에 데이터를 쓰는 방식이 프로세서의 엔디언 해석 방향과 일치하는지 반드시 확인하십시오.

❓ 수강생 단골 질문

Q: 비정렬 접근이 왜 문제가 되나요? 그냥 허용하면 안 되나요?

A: 비정렬 접근을 하드웨어에서 지원하는 것 자체는 가능합니다. 다만 구현이 복잡해집니다. 정렬된 32비트 워드 접근은 단일 메모리 트랜잭션으로 처리됩니다. 비정렬 32비트 접근은 최소 2번의 메모리 트랜잭션이 필요하고, 읽어온 바이트들을 정렬 오프셋에 따라 재조합하는 시프터(Shifter)와 머지(Merge) 로직이 추가로 필요합니다. AHB 버스 인터페이스에서도 비정렬 트랜잭션은 별도 처리 프로토콜을 따릅니다. 교육용 프로세서에서는 이 복잡성을 배제하고 정렬 접근만 가정하는 것이 일반적입니다.

🎯 면접 포인트 — 엔디언과 네트워크 프로토콜

"빅 엔디언과 리틀 엔디언의 차이를 설명하고, 네트워크 통신에서 어떤 엔디언을 사용하는지 말하시오"는 시스템 소프트웨어 및 임베디드 직군에서 자주 나오는 면접 질문입니다. 핵심 답변: TCP/IP를 비롯한 대부분의 네트워크 프로토콜은 빅 엔디언(네트워크 바이트 순서, Network Byte Order)을 표준으로 채택합니다. x86/ARM/RISC-V는 리틀 엔디언이므로, 네트워크 패킷을 처리하는 임베디드 코드에서는 반드시 htonl()/ntohl() 같은 바이트 스왑 함수를 사용해야 합니다. 이를 누락하면 패킷 헤더의 길이/포트 필드가 잘못 해석되는 미묘한 버그로 이어집니다.

2.4 명령어 형식 개관: 6가지 타입

레지스터와 메모리라는 무대가 준비되었습니다. 이제 이 무대 위에서 연기할 배우, 즉 명령어를 만나볼 차례입니다. 프로세서가 레지스터와 메모리를 어떻게 조작하는지는 명령어의 구조를 이해해야만 알 수 있습니다.

이제 RISC-V ISA의 핵심 구조인 명령어 형식(Instruction Format)을 살펴볼 차례입니다. 처음 접하는 분은 "6가지나 외워야 하나?"라는 부담감이 생길 수 있습니다. 하지만 안심하십시오. 이 6가지를 한꺼번에 외울 필요는 전혀 없습니다. 지금은 전체 지도(Map)를 파악하는 단계입니다. 각 형식의 세부 사항은 챕터 3에서 명령어를 실제로 구현하면서 자연스럽게 익혀집니다. 오늘의 목표는 "패턴 6개만 기억하면 RV32I의 모든 명령어를 해독할 수 있다"는 자신감을 갖는 것입니다.

비유 — 택배 송장 6가지 양식: 물류센터에서는 화물 유형에 따라 다른 송장 양식을 씁니다. 일반 소포 양식, 특급 배송 양식, 반품 양식, 항공 화물 양식 등이 각각 다른 필드 배치를 가집니다. 하지만 모두 동일한 32칸 박스를 기본 단위로 삼습니다. RISC-V 명령어도 마찬가지입니다. 모든 명령어는 정확히 32비트이고, 6가지 "양식"에 따라 비트들이 다르게 배치됩니다. 어떤 양식인지는 최하위 7비트(opcode)를 보면 알 수 있습니다. 이 비유의 한계: 실제 택배 송장은 가변 길이이지만, RISC-V 기본 명령어는 항상 32비트 고정 길이입니다.

공통 필드: opcode와 funct 코드

6가지 형식에서 공통으로 등장하는 필드들이 있습니다. opcode(연산 코드, Operation Code)는 비트 [6:0]에 위치하며 명령어의 기본 유형을 식별합니다. funct3은 비트 [14:12]에 위치하며 같은 opcode 내에서 세부 동작을 구별합니다. funct7은 비트 [31:25]에 위치하며 R-type에서 추가적인 동작 구별에 사용됩니다. rd는 목적지 레지스터(Destination Register), rs1/rs2는 소스 레지스터(Source Register)이며 각각 5비트(32개 레지스터 번호 표현)를 사용합니다.

R-type: 레지스터-레지스터 연산

R-type(Register-type)은 두 소스 레지스터(rs1, rs2)의 값을 연산하여 목적지 레지스터(rd)에 저장하는 형식입니다. 즉치수(Immediate) 필드가 없고, 대신 funct7과 funct3로 14가지 이상의 산술·논리 연산을 구분합니다.

비트 위치 [31:25] [24:20] [19:15] [14:12] [11:7] [6:0]
필드명 funct7 rs2 rs1 funct3 rd opcode
비트 수 7 5 5 3 5 7

대표 명령어: add, sub, and, or, xor, sll, srl, sra, slt, sltu

I-type: 즉치수 연산 및 로드

I-type(Immediate-type)은 하나의 소스 레지스터(rs1)와 12비트 부호 있는 즉치수(Signed Immediate)를 결합하여 연산하거나 메모리에서 값을 불러오는 형식입니다. 12비트 즉치수는 부호 확장(Sign Extension)되어 32비트로 사용됩니다. 부호 확장(Sign Extension)이란 짧은 비트 수의 값을 더 긴 비트 수로 변환할 때, 최상위 비트(부호 비트)를 상위 비트에 반복 복사하는 연산입니다. 예를 들어 12비트 값 0xFFF(= -1)를 32비트로 부호 확장하면 0xFFFFFFFF(= -1)가 됩니다. 표현 범위는 -2048 ~ +2047입니다.

비트 위치 [31:20] [19:15] [14:12] [11:7] [6:0]
필드명 imm[11:0] rs1 funct3 rd opcode
비트 수 12 5 3 5 7

대표 명령어: addi, lw, lh, lb, jalr, slli, srli, srai

참고: 시프트 명령어(SLLI, SRLI, SRAI)는 I-type이지만, 즉치수 상위 비트를 funct7처럼 사용하여 시프트 방향과 종류를 구분합니다. 이 특수 인코딩은 챕터 3에서 상세히 다룹니다.

S-type: 스토어(메모리 저장)

S-type(Store-type)은 레지스터 값을 메모리에 저장하는 명령어 형식입니다. rs1은 기저 주소(Base Address), rs2는 저장할 데이터를 담은 레지스터입니다. 12비트 즉치수가 rs1과 더해져 유효 주소(Effective Address)를 형성합니다. 중요한 점은 즉치수 비트가 두 부분으로 나뉘어 저장된다는 것입니다: 상위 7비트(imm[11:5])는 [31:25]에, 하위 5비트(imm[4:0])는 [11:7]에 위치합니다. 이렇게 분리된 이유는 rs1과 rs2의 위치를 R-type, I-type과 동일하게 유지하여 레지스터 파일 읽기 로직을 공유할 수 있도록 하기 위함입니다.

비트 위치 [31:25] [24:20] [19:15] [14:12] [11:7] [6:0]
필드명 imm[11:5] rs2 rs1 funct3 imm[4:0] opcode
비트 수 7 5 5 3 5 7

대표 명령어: sw, sh, sb

여기까지 R-type, I-type, S-type 세 가지 형식을 익혔습니다. 이미 절반 이상을 넘었습니다! 나머지 B-type, U-type, J-type은 이미 배운 형식의 변형이므로 부담을 덜어도 됩니다.

B-type: 조건부 분기

B-type(Branch-type)은 두 레지스터(rs1, rs2)를 비교하여 조건이 참이면 PC에 오프셋(Offset)을 더해 분기(Branch)하는 형식입니다. S-type과 동일한 필드 배치를 기반으로 하지만, 즉치수 비트의 배치 방식이 다릅니다. B-type의 분기 오프셋은 항상 짝수(2의 배수)이므로, 최하위 비트(imm[0])는 항상 0이어서 명령어에 인코딩하지 않습니다. 대신 13비트 부호 있는 오프셋(최하위 비트는 항상 0이므로 12비트만 인코딩)으로 ±4KiB 범위의 분기를 표현합니다.

비트 위치 [31] [30:25] [24:20] [19:15] [14:12] [11:8] [7] [6:0]
필드명 imm[12] imm[10:5] rs2 rs1 funct3 imm[4:1] imm[11] opcode

대표 명령어: beq, bne, blt, bge, bltu, bgeu

💡 B-type 비트 배치가 어렵게 느껴진다면

B-type과 J-type의 즉치수 비트 배치가 한 번에 이해되지 않더라도 전혀 걱정할 필요가 없습니다. 숙련된 엔지니어도 이 부분은 레퍼런스 카드를 참조하며 작업합니다. 중요한 것은 '왜 이렇게 배치했는가'의 설계 의도를 이해하는 것이며, 비트 위치는 필요할 때 표를 보면 됩니다.

U-type: 상위 즉치수

U-type(Upper Immediate-type)은 20비트 즉치수를 레지스터의 상위 20비트에 적재하는 단순한 형식입니다. 하위 12비트는 0으로 채워집니다. 32비트 상수를 레지스터에 로드할 때 lui로 상위 20비트를 설정한 뒤 addi로 하위 12비트를 더하는 2명령어 시퀀스를 사용합니다.

비트 위치 [31:12] [11:7] [6:0]
필드명 imm[31:12] rd opcode
비트 수 20 5 7

대표 명령어: lui, auipc

J-type: 무조건 점프

J-type(Jump-type)은 jal(Jump And Link) 명령어 전용 형식입니다. 21비트 오프셋(최하위 비트 생략하여 20비트 인코딩)으로 현재 PC에서 ±1MiB 범위의 점프를 표현합니다. B-type과 유사하게 즉치수 비트가 흩어진 방식으로 인코딩되어 있으며, 분기 대상 주소(Branch Target Address)는 항상 2의 배수여야 하므로 imm[0]은 인코딩하지 않습니다. 점프 후 반환 주소(PC+4)는 rd 레지스터에 저장됩니다.

비트 위치 [31] [30:21] [20] [19:12] [11:7] [6:0]
필드명 imm[20] imm[10:1] imm[11] imm[19:12] rd opcode

대표 명령어: jal

주의: JALR(Jump And Link Register)은 레지스터 기반 간접 점프이므로 I-type에 속합니다. J-type은 JAL 전용입니다.

💡 실무 팁 — B-type과 J-type 즉치수 비트가 흩어진 이유

B-type과 J-type에서 즉치수 비트가 연속적이지 않고 흩어진 배치는 처음 보면 매우 이상하게 느껴집니다. 이 설계의 이유는 하드웨어 디코더의 단순화에 있습니다. 모든 6가지 형식에서 rs1은 [19:15], rs2는 [24:20], rd는 [11:7]로 고정됩니다. 즉치수 비트를 배치할 때 이 레지스터 필드를 피해야 하므로, 즉치수 비트가 빈 공간을 채우는 형태가 됩니다. 또한 모든 형식에서 imm의 최상위 비트(부호 비트)는 항상 비트 [31]에 위치하도록 설계되어, 부호 확장(Sign Extension) 로직을 단일 멀티플렉서(Multiplexer)로 처리할 수 있습니다. 이는 "디코더 복잡성 최소화"라는 RISC-V 설계 철학의 직접적 구현입니다.

❓ 수강생 단골 질문

Q: S-type과 B-type이 왜 이렇게 비슷하게 생겼나요?

A: S-type과 B-type은 의도적으로 유사하게 설계되었습니다. 두 형식 모두 레지스터 비교 혹은 데이터 저장을 위해 rs1과 rs2 두 소스 레지스터를 필요로 하며, rd 필드가 없다는 공통점을 갖습니다. 차이점은 즉치수 해석 방식입니다. S-type의 imm[4:0]이 위치한 [11:7] 필드를 B-type에서는 imm[4:1]과 imm[11]로 재구성합니다. 이 설계 덕분에 저장(Store) 명령어와 분기(Branch) 명령어의 디코더 로직 대부분을 공유할 수 있습니다. RTL 구현에서 이 구조적 유사성이 얼마나 큰 도움이 되는지는 챕터 4 즉치수 생성기(ImmGen) 설계에서 직접 확인하게 됩니다.

🎯 면접 포인트 — RISC-V가 6가지 명령어 형식을 사용하는 이유

"RISC-V 명령어 형식이 6가지인 이유와 각 형식의 설계 원칙을 설명하시오"는 아키텍처 이해도를 평가하는 면접 질문입니다. 핵심 답변: (1) 모든 형식이 32비트 고정 길이로 디코더와 명령어 메모리 정렬이 단순해진다. (2) rs1, rs2, rd 필드 위치가 모든 형식에서 고정되어 레지스터 파일 읽기를 명령어 디코딩 이전에 시작할 수 있다(파이프라인 이점). (3) 즉치수 부호 비트가 항상 bit[31]에 위치하여 부호 확장 로직이 단일화된다. 이 세 가지 설계 원칙이 하드웨어 단순성을 극대화하면서 필요한 모든 연산 유형을 커버한다고 설명하면 우수한 답변입니다.

📌 강사 꿀팁 — 6가지 형식 도입 순서

6가지 형식을 R → I → S → B → U → J 순으로 순차 설명하되, S-type 직후 "S-type은 B-type과 구조가 거의 동일하다"고 선제적으로 언급하면 학습자가 B-type을 새로 배우는 부담감을 크게 줄일 수 있습니다. U-type과 J-type은 가장 단순한 구조이므로 마지막에 배치하면 심리적 성취감을 극대화할 수 있습니다. 6가지 형식을 한 장의 참조 표(Reference Card)로 정리하여 챕터 3 실습 내내 옆에 두도록 안내하십시오.

💡 실무 팁 — 16진수 ↔ 2진수 빠른 변환

명령어 비트 패턴 작업에서 16진수와 2진수를 빠르게 변환하는 것은 필수 기술입니다. 16진수 한 자리는 정확히 4비트(nibble)에 해당합니다. 0x0=0000, 0x1=0001, ..., 0x7=0111, 0x8=1000, 0x9=1001, 0xA=1010, 0xB=1011, 0xC=1100, 0xD=1101, 0xE=1110, 0xF=1111. 32비트 명령어 0x007302B3은 16진수 8자리이므로, 각 자리를 4비트로 변환하면 32비트 2진수를 즉시 얻을 수 있습니다. Python에서는 bin(0x007302B3)으로 빠르게 확인 가능합니다.

실습 1: R-type 인코딩 — add x5, x6, x7

add x5, x6, x7은 x6 + x7의 결과를 x5에 저장하는 R-type 명령어입니다. 단계적으로 인코딩해 보겠습니다.

  1. opcode 결정: 정수 레지스터-레지스터 연산의 opcode는 0110011 (7비트, 0x33)
  2. funct3 결정: add는 funct3 = 000
  3. funct7 결정: add는 funct7 = 0000000 (sub는 0100000으로 구별)
  4. 레지스터 번호 결정: rd = x5 = 00101, rs1 = x6 = 00110, rs2 = x7 = 00111
  5. 비트 배치 (R-type):
[31:25] funct7 [24:20] rs2 [19:15] rs1 [14:12] funct3 [11:7] rd [6:0] opcode
0000000 00111 00110 000 00101 0110011

전체 32비트: 0000000 00111 00110 000 00101 0110011

이를 4비트씩 묶으면:

비트 그룹2진수16진수
[31:28]00000
[27:24]00000
[23:20]01117
[19:16]00113
[15:12]00000
[11:8]00102
[7:4]1011B
[3:0]00113

최종 결과: 0x007302B3

검증: RISC-V 어셈블러나 riscv32-unknown-elf-objdump로 확인하면 동일한 인코딩이 출력됩니다.

실습 2: I-type 디코딩 — 0x00A30293 해독

이번에는 반대 방향입니다. 16진수 명령어 코드 0x00A30293이 주어졌을 때, 이 명령어가 무엇인지 해독해 보겠습니다.

먼저 32비트 2진수로 변환합니다:

0x00A30293 = 0000 0000 1010 0011 0000 0010 1001 0011

  1. opcode 확인 [6:0]: 비트 [6:0] = 0010011 = 0x13 → 정수 즉치수(Immediate) 연산 명령어
  2. 형식 판단: opcode 0010011은 I-type
  3. rd 추출 [11:7]: 비트 [11:7] = 00101 = 5 → x5
  4. funct3 추출 [14:12]: 비트 [14:12] = 000 → ADDI
  5. rs1 추출 [19:15]: 비트 [19:15] = 00110 = 6 → x6
  6. imm[11:0] 추출 [31:20]: 비트 [31:20] = 000000001010 = 0x00A = 10 (양수이므로 부호 확장 시 상위 비트가 모두 0으로 채워져 값이 변하지 않습니다)

해독 결과: addi x5, x6, 10

즉, "x6의 값에 10을 더하여 x5에 저장하라"는 명령어입니다. 만약 실행 전 x6 = 20이라면, 실행 후 x5 = 30이 됩니다.

실습 3: B-type 인코딩 — beq x10, x11, 16

beq x10, x11, 16은 x10 == x11이면 현재 PC에서 +16 바이트 떨어진 주소로 분기하는 명령어입니다. B-type은 즉치수 비트 배치가 특이하므로 주의를 기울여야 합니다.

  1. opcode: 조건 분기 opcode = 1100011 (0x63)
  2. funct3: beq = 000
  3. rs1 = x10: 01010
  4. rs2 = x11: 01011
  5. 오프셋 16 = 0b10000 분해:
    16진수 16 = 이진수 00000000010000 (14비트, bit0은 항상 0)
    imm[12] = 0, imm[11] = 0, imm[10:5] = 000000, imm[4:1] = 1000

B-type 비트 배치 규칙에 따라:

[31] imm[12] [30:25] imm[10:5] [24:20] rs2 [19:15] rs1 [14:12] funct3 [11:8] imm[4:1] [7] imm[11] [6:0] opcode
0 000000 01011 01010 000 1000 0 1100011

전체 32비트: 0 000000 01011 01010 000 1000 0 1100011 = 0000 0000 1011 0101 0000 1000 0110 0011

16진수: 0x00B50863

검증 방법: RISC-V 어셈블러 또는 온라인 도구(예: riscv.verificationexcellence.com)에서 beq x10, x11, 16을 입력하면 동일한 결과가 나옵니다.

Q: 실제로 개발할 때도 이렇게 수동으로 인코딩하나요?

A: 실무에서는 어셈블러나 컴파일러가 자동으로 인코딩하므로 수동 인코딩이 필요한 경우는 매우 드뭅니다. 그러나 RTL 하드웨어 설계자로서 다음 상황에서는 비트 수준 이해가 필수입니다: (1) 명령어 디코더 로직 설계 및 검증, (2) 시뮬레이션 파형에서 프로그램 카운터와 명령어 레지스터 값을 분석할 때, (3) 테스트벤치 어셈블리 코드가 예상대로 동작하지 않을 때 디버깅, (4) CSR(Control and Status Register) 접근 명령어의 비트 필드 확인. 지금 이 훈련은 미래의 디버깅 시간을 크게 단축시켜 줍니다.

핵심 정리

  • RISC-V는 단순성·모듈성·개방성을 핵심 설계 철학으로 하는 개방 표준 ISA이다. RV32I 기본 명령어 집합은 47개로 구성되며, M/A/F/D/C/V 확장을 선택적으로 추가할 수 있다.
  • 레지스터 파일은 32개의 32비트 범용 레지스터(x0~x31)로 구성된다. x0은 하드와이어드되어 항상 0을 반환하며, 쓰기는 무시된다.
  • ABI 명칭(ra, sp, t0~t6, s0~s11, a0~a7)은 각 레지스터의 역할과 함수 호출 규약상 보존 의무를 정의한다.
  • RV32I 메모리는 바이트 주소 지정 방식으로 4GiB 공간을 가지며, 다중 바이트 데이터는 리틀 엔디언으로 저장된다. 워드(4byte) 접근은 4의 배수 주소 정렬이 필요하다.
  • 모든 RV32I 명령어는 32비트 고정 길이이며, R·I·S·B·U·J 6가지 형식 중 하나를 따른다. rs1/rs2/rd 필드와 imm 부호 비트의 위치가 형식 간에 고정되어 디코더 로직이 단순화된다.
  • 명령어 인코딩은 opcode → 형식 판단 → 필드별 비트 추출·조합의 순서로 수행된다. 디코딩은 반대 방향으로 동일한 절차를 따른다.

문제 2 해답

문제 3 해답

(a) sub x3, x1, x2 — R-type

  1. opcode = 0110011 (R-type 정수 레지스터 연산)
  2. funct3 = 000, funct7 = 0100000 (sub)
  3. rd = x3 = 00011, rs1 = x1 = 00001, rs2 = x2 = 00010
  4. 비트 배치: 0100000 00010 00001 000 00011 0110011
  5. 16진수: 0x402081B3

(b) lw x8, -4(x2) — I-type

  1. opcode = 0000011 (로드 명령어)
  2. funct3 = 010 (lw)
  3. rd = x8 = 01000, rs1 = x2 = 00010
  4. imm = -4 = 12비트 2의 보수 표현 111111111100
  5. 비트 배치: 111111111100 00010 010 01000 0000011
  6. 16진수: 0xFFC12403

(c) sw x8, 12(x2) — S-type

  1. opcode = 0100011 (스토어 명령어)
  2. funct3 = 010 (sw)
  3. rs1 = x2 = 00010 (기저 주소), rs2 = x8 = 01000 (저장할 데이터)
  4. imm = 12 = 000000001100 → imm[11:5] = 0000000, imm[4:0] = 01100
  5. 비트 배치: 0000000 01000 00010 010 01100 0100011
  6. 16진수: 0x00812623

문제 4 해답

(a) 0x004282B3

  1. 2진수 변환: 0000 0000 0100 0010 1000 0010 1011 0011
  2. opcode [6:0] = 0110011 → R-type
  3. rd [11:7] = 00101 = x5
  4. funct3 [14:12] = 000, funct7 [31:25] = 0000000 → add
  5. rs1 [19:15] = 00101 = x5, rs2 [24:20] = 00100 = x4
  6. 결과: add x5, x5, x4

(b) 0xFFF30313

  1. 2진수 변환: 1111 1111 1111 0011 0000 0011 0001 0011
  2. opcode [6:0] = 0010011 → I-type (즉치수 연산)
  3. rd [11:7] = 00110 = x6
  4. funct3 [14:12] = 000 → addi
  5. rs1 [19:15] = 00110 = x6
  6. imm [31:20] = 111111111111 = -1 (부호 확장하면 0xFFFFFFFF = -1)
  7. 결과: addi x6, x6, -1

(c) 0x00112623

  1. 2진수 변환: 0000 0000 0001 0001 0010 0110 0010 0011
  2. opcode [6:0] = 0100011 → S-type (스토어)
  3. funct3 [14:12] = 010 → sw
  4. rs1 [19:15] = 00010 = x2 (기저 주소)
  5. rs2 [24:20] = 00001 = x1 (저장할 데이터)
  6. imm[11:5] = [31:25] = 0000000, imm[4:0] = [11:7] = 01100 → imm = 000000001100 = 12

  • 주소 0x2001: 0x12
  • 주소 0x2002: 0xCD

문제 6 해답

B-type 즉치수 비트 흩어진 배치의 비판적 평가:

장점:

  • (1) rs1, rs2 필드 위치가 다른 형식(R, I, S-type)과 동일하게 유지되어 레지스터 파일 읽기 로직을 공유할 수 있습니다.
  • (2) 부호 비트가 항상 bit[31]에 고정되어 부호 확장 하드웨어가 단일화됩니다.

단점:

  • (1) 어셈블러 및 디스어셈블러 구현 시 즉치수 조립/분해 로직이 복잡해집니다.
