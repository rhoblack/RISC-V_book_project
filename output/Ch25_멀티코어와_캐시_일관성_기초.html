Chapter 25

멀티코어와 캐시 일관성 기초

지금까지 여러분은 단일 코어 RV32I 파이프라인 프로세서를 설계하고 FPGA 위에서 C 프로그램까지 실행하는 데 성공했습니다. 이 챕터는 교재의 마지막 여정으로, "하나의 코어를 넘어 여러 코어가 협력하려면 무엇이 더 필요한가?"라는 질문에 답합니다. 멀티코어 시대의 핵심 과제인 캐시 일관성(Cache Coherence) 문제와 원자 연산(Atomic Operation)의 기초를 살펴보며, 여러분이 앞으로 나아갈 방향을 제시합니다.

학습 목표

  • 멀티코어 환경에서 캐시 일관성 문제가 발생하는 원인을 설명할 수 있다.
  • MESI 프로토콜의 4가지 상태와 상태 전이 규칙을 분석할 수 있다.
  • MESI 캐시 라인 상태 추적기를 SystemVerilog로 설계할 수 있다.
  • RISC-V A 확장의 LR/SC 명령어 동작 원리를 설명할 수 있다.
  • LR/SC 기반 스핀락(Spinlock)을 구현하고, 원자 연산의 하드웨어 지원 메커니즘을 설계할 수 있다.

25.1 멀티코어 설계 과제

지난 20년간 프로세서 성능 향상의 주된 방향은 "클록 주파수를 높이는 것"에서 "코어 수를 늘리는 것"으로 전환되었습니다. 2006년경 전력 장벽(Power Wall)에 부딪힌 이후, 인텔·AMD·ARM·RISC-V 진영 모두 멀티코어(Multicore) 아키텍처를 채택하고 있습니다. 여러분이 지금까지 만든 단일 코어 프로세서를 두 개, 네 개로 복제하면 멀티코어가 되는 것일까요? 하드웨어적으로는 가능합니다. 그러나 각 코어가 자체 캐시를 가지는 순간, 단순 복제만으로는 해결할 수 없는 근본적인 문제가 등장합니다. 바로 캐시 일관성(Cache Coherence) 문제입니다.

왜 캐시 일관성이 문제인가

Chapter 13~14에서 우리는 L1 명령어 캐시와 데이터 캐시를 설계했습니다. 캐시는 주 메모리(Main Memory)의 복사본을 코어 가까이에 보관하여 접근 지연(latency)을 줄이는 장치입니다. 단일 코어에서는 캐시와 메모리 사이에 "누가 최신 값을 가지고 있는가"에 대한 혼란이 없습니다 — 캐시가 항상 유일한 관찰자이기 때문입니다.

그러나 두 개 이상의 코어가 각자의 L1 캐시를 보유하면 상황이 달라집니다. Core 0이 변수 X를 자신의 캐시에서 5로 수정했다고 가정하겠습니다. 이때 Core 1의 캐시에는 여전히 X = 3(수정 전 값)이 남아 있습니다. Core 1이 X를 읽으면 오래된 값 3을 얻게 되며, 이는 프로그램의 정확성을 심각하게 훼손합니다. 이 현상을 캐시 비일관성(Cache Incoherence)이라 합니다.

비유: 회사에서 공유 문서를 편집하는 상황을 떠올려 보십시오. 직원 A가 보고서의 3페이지를 수정하고 저장했지만, 직원 B는 아직 수정 전 버전을 열어 놓고 있습니다. B가 자신의 화면을 "최신"이라 믿고 작업하면 충돌이 발생합니다. 구글 독스(Google Docs) 같은 실시간 협업 도구가 이 문제를 해결하듯, 멀티코어 프로세서에서는 캐시 일관성 프로토콜이 이 역할을 합니다. 다만, 이 비유에는 한계가 있습니다 — 하드웨어 캐시 일관성 프로토콜은 소프트웨어 협업 도구와 달리, 나노초 단위로 동작하는 하드와이어드 상태 기계(FSM)로 구현되며, 모든 메모리 접근에 대해 자동으로 작동합니다.
🔍 스스로 점검

여기까지 읽었다면, 다음 질문에 답해 보십시오: "단일 코어 시스템에서는 캐시 일관성 문제가 왜 발생하지 않는가?" 만약 "캐시가 하나뿐이므로 복사본 간 불일치가 원천적으로 없다"라고 답했다면 올바르게 이해한 것입니다. (단, 단일 코어에서도 DMA나 I/O 장치가 메모리에 직접 쓰면 유사한 문제가 발생할 수 있습니다 — Ch14.6에서 잠시 언급한 바 있습니다.)

캐시 일관성 프로토콜의 두 가지 접근법

캐시 일관성을 보장하는 프로토콜은 크게 두 가지 방식으로 분류됩니다.

구분 스누핑 기반 (Snooping-based) 디렉터리 기반 (Directory-based)
동작 방식 모든 캐시가 공유 버스를 감시(snoop)하여 다른 코어의 메모리 접근을 탐지 중앙 디렉터리가 각 캐시 라인의 공유 상태를 추적
장점 구현이 간단, 소규모 코어 수(2~8)에서 효율적 대규모 코어 수(16~수백)에서도 확장 가능
단점 버스 대역폭이 병목, 코어 수 증가 시 확장성 제한 디렉터리 저장 오버헤드, 지연 시간 증가
대표 사례 Intel 초기 멀티코어, ARM Cortex-A9 MPCore AMD EPYC (Infinity Fabric), RISC-V BOOM (TileLink)

이 챕터에서는 교육 목적상 스누핑 기반 프로토콜에 집중합니다. 그 이유는 (1) 개념이 직관적이며, (2) 여러분이 Chapter 16에서 설계한 공유 버스(AHB)를 스누핑 매체로 자연스럽게 활용할 수 있고, (3) 소규모 멀티코어(2~4코어)에 적합하기 때문입니다.

MESI 프로토콜 개요

스누핑 기반 프로토콜 중 가장 널리 사용되는 것이 MESI 프로토콜입니다. MESI는 각 캐시 라인이 가질 수 있는 네 가지 상태의 약자입니다.

상태 이름 의미 메모리와 일치?
M Modified (수정됨) 이 캐시만 최신 복사본을 보유. 메모리의 값은 오래됨. 아니오
E Exclusive (독점) 이 캐시만 복사본을 보유하지만, 메모리와 동일한 값. 예
S Shared (공유) 여러 캐시가 동일한 값을 보유. 메모리와도 일치. 예
I Invalid (무효) 이 캐시 라인은 유효하지 않음. 사용 불가. 해당 없음

Chapter 14에서 여러분이 설계한 Write-Back 캐시의 상태 비트를 떠올려 보십시오. Valid 비트와 Dirty 비트 두 개로 캐시 라인의 상태를 관리했습니다. MESI는 이를 확장한 것입니다.

Ch14 상태 Valid Dirty MESI 대응
유효 + 수정됨 1 1 Modified (M)
유효 + 깨끗함 1 0 Exclusive (E) 또는 Shared (S)
무효 0 - Invalid (I)

결정적인 차이는 Exclusive와 Shared의 구분입니다. 단일 코어에서는 "다른 캐시가 같은 데이터를 가지고 있는가"를 알 필요가 없었지만, 멀티코어에서는 이 정보가 핵심입니다. Exclusive 상태의 캐시 라인에 쓰기를 하면 버스 트랜잭션 없이 조용히(silently) Modified로 전이할 수 있어 성능이 향상됩니다. 반면 Shared 상태에서 쓰기를 하려면 다른 캐시의 복사본을 무효화(Invalidate)해야 하므로 버스 트랜잭션이 필요합니다.

MESI 상태 전이

MESI 프로토콜의 핵심은 상태 전이 규칙입니다. 각 캐시 라인은 두 종류의 이벤트에 반응합니다: (1) 로컬 프로세서의 요청(PrRd: 프로세서 읽기, PrWr: 프로세서 쓰기)과 (2) 버스에서 관찰되는 다른 코어의 트랜잭션(BusRd: 버스 읽기, BusRdX: 버스 읽기+무효화).

주요 상태 전이를 하나씩 살펴보겠습니다. 이 내용은 Chapter 08에서 FSM 제어 유닛을 설계할 때 배운 상태 기계 분석 방법과 동일한 접근법입니다.

(1) Invalid → Exclusive (읽기 미스, 단독): 프로세서가 읽기를 요청했으나 캐시에 해당 라인이 없습니다(미스). 버스에 BusRd를 발행하여 메모리에서 데이터를 가져옵니다. 이때 다른 캐시에 동일한 라인이 없으면 Exclusive로 전이합니다.

(2) Invalid → Shared (읽기 미스, 공유): 위와 동일하지만, 다른 캐시에 이미 해당 라인이 존재합니다. 이 경우 Shared로 전이합니다.

(3) Exclusive → Modified (로컬 쓰기): 이 캐시만 유일한 복사본을 가지고 있으므로, 다른 캐시에 알릴 필요 없이 바로 Modified로 전이합니다. 이것이 E 상태의 핵심 이점 — 무음 전이(Silent Transition)입니다.

(4) Shared → Modified (로컬 쓰기): 다른 캐시에도 복사본이 있으므로, BusRdX(Bus Read Exclusive)를 발행하여 다른 모든 복사본을 무효화한 후 Modified로 전이합니다.

(5) Modified → Shared (다른 코어 읽기): 다른 코어가 BusRd를 발행하면, 수정된 데이터를 메모리에 기록(Flush)하고 Shared로 전이합니다. 이 과정을 라이트백(Write-Back) 또는 플러시(Flush)라 합니다.

(6) Shared → Invalid (다른 코어 쓰기): 다른 코어가 BusRdX를 발행하면, 자신의 복사본을 무효화합니다. 이후 해당 데이터가 필요하면 다시 캐시 미스가 발생합니다.

💡 실무 팁

MESI 프로토콜의 변형으로 MOESI(AMD에서 사용)와 MESIF(Intel에서 사용)가 있습니다. MOESI는 Owned 상태를 추가하여 Modified → Shared 전이 시 메모리 라이트백을 생략할 수 있게 합니다. MESIF는 Forward 상태를 추가하여 Shared 라인 중 하나만 데이터 공급 책임을 갖게 합니다. 실무에서 어떤 변형을 선택할지는 버스 대역폭, 메모리 지연, 코어 수에 따른 트레이드오프 분석이 필요합니다.

MESI 상태 추적기 구현

이론을 코드로 옮겨 보겠습니다. 아래는 단일 캐시 라인에 대한 MESI 상태 추적기입니다. Chapter 08에서 설계한 FSM 제어 유닛과 동일한 패턴 — always_ff로 상태 레지스터를 관리하고, always_comb로 다음 상태와 출력을 결정하는 이중 블록 FSM — 을 사용합니다. 


module mesi_tracker (
   input  logic       clk,
   input  logic       rst_n,
   // 프로세서 요청 (로컬 코어)
   input  logic       pr_rd,        // 프로세서 Read 요청
   input  logic       pr_wr,        // 프로세서 Write 요청
   // 버스 스누핑 입력 (다른 코어의 버스 트랜잭션)
   input  logic       bus_rd,       // 다른 코어의 Read 관찰
   input  logic       bus_rdx,      // 다른 코어의 Read-Exclusive
   // 메모리 응답
   input  logic       mem_shared,   // 다른 캐시에도 복사본 존재 여부
   // 상태 출력
   output logic [1:0] state,        // 현재 MESI 상태
   // 버스 동작 출력
   output logic       do_flush,     // 수정된 데이터를 메모리에 기록
   output logic       do_bus_rd,    // 버스 Read 트랜잭션 발생
   output logic       do_bus_rdx,   // 버스 Read-Exclusive 트랜잭션 발생
   output logic       do_invalidate // 자신의 캐시 라인을 무효화
);

   // MESI 상태 인코딩
   localparam logic [1:0] MODIFIED  = 2'b00;
   localparam logic [1:0] EXCLUSIVE = 2'b01;
   localparam logic [1:0] SHARED    = 2'b10;
   localparam logic [1:0] INVALID   = 2'b11;

   logic [1:0] state_next;

   // 상태 레지스터
   always_ff @(posedge clk or negedge rst_n) begin
      if (!rst_n)
         state <= INVALID;  // 리셋 시 Invalid
      else
         state <= state_next;
   end

   // 다음 상태 및 출력 결정
   always_comb begin
      state_next    = state;
      do_flush      = 1'b0;
      do_bus_rd     = 1'b0;
      do_bus_rdx    = 1'b0;
      do_invalidate = 1'b0;

      case (state)
         MODIFIED: begin
            if (bus_rd) begin
               state_next = SHARED;
               do_flush   = 1'b1;
            end
            else if (bus_rdx) begin
               state_next    = INVALID;
               do_flush      = 1'b1;
               do_invalidate = 1'b1;
            end
         end

         EXCLUSIVE: begin
            if (pr_wr)
               state_next = MODIFIED;  // Silent 전이!
            else if (bus_rd)
               state_next = SHARED;
            else if (bus_rdx) begin
               state_next    = INVALID;
               do_invalidate = 1'b1;
            end
         end

         SHARED: begin
            if (pr_wr) begin
               state_next = MODIFIED;
               do_bus_rdx = 1'b1;  // 다른 복사본 무효화
            end
            else if (bus_rdx) begin
               state_next    = INVALID;
               do_invalidate = 1'b1;
            end
         end

         INVALID: begin
            if (pr_rd) begin
               do_bus_rd = 1'b1;
               state_next = mem_shared ? SHARED : EXCLUSIVE;
            end
            else if (pr_wr) begin
               state_next = MODIFIED;
               do_bus_rdx = 1'b1;
            end
         end

         default: state_next = INVALID;
      endcase
   end
endmodule

이 모듈은 Chapter 08의 FSM 패턴을 그대로 따릅니다. localparam으로 상태를 정의하고, always_ff에서 상태 레지스터를 업데이트하며, always_comb에서 전이 조건과 출력을 결정합니다. 실제 프로세서에서는 이 모듈이 캐시 라인마다 하나씩 존재하며, 캐시 컨트롤러 FSM과 연동하여 동작합니다.

❓ 수강생 단골 질문

Q: MESI에서 Exclusive 상태가 왜 필요한가요? Modified와 Shared만 있으면 안 되나요?

A: 좋은 질문입니다. Exclusive 상태 없이 MSI(Modified-Shared-Invalid) 프로토콜로도 캐시 일관성을 보장할 수 있습니다. 그러나 MSI에서는 Shared 상태의 라인에 쓰기를 할 때 항상 버스 트랜잭션 (무효화 방송)이 필요합니다. Exclusive 상태는 "이 캐시만 유일한 복사본"이라는 정보를 추적하여, 쓰기 시 버스 트랜잭션을 생략(Silent Transition)할 수 있게 합니다. 이는 특히 단일 스레드 프로그램이나 스레드 간 공유가 적은 데이터에서 상당한 성능 이점을 제공합니다.

🎯 면접 포인트

Q: "MESI 프로토콜의 네 가지 상태를 설명하고, E 상태의 장점은?"

핵심 답변: M(Modified)은 이 캐시만 최신 데이터를 보유하며 메모리와 불일치, E(Exclusive)는 이 캐시만 보유하되 메모리와 일치, S(Shared)는 여러 캐시가 동일한 값을 보유, I(Invalid)는 유효하지 않은 상태입니다. E 상태의 핵심 장점은 로컬 쓰기 시 버스 트랜잭션 없이 M으로 전이할 수 있다는 것(Silent Transition)입니다. 이는 단일 스레드 워크로드에서 불필요한 버스 트래픽을 제거하여 성능을 향상시킵니다.

스누핑 프로토콜의 하드웨어 구현 개요

실제 하드웨어에서 스누핑 프로토콜은 다음과 같은 구성 요소로 이루어집니다.

(1) 스누프 필터(Snoop Filter): 각 캐시 컨트롤러에는 공유 버스의 트랜잭션을 감시하는 스누프 로직이 포함됩니다. 버스에 BusRd 또는 BusRdX가 나타나면, 자신의 캐시 태그(Tag)를 검색하여 해당 라인을 보유하고 있는지 확인합니다. Chapter 13에서 설계한 태그 비교기(Tag Comparator)가 이 역할을 수행합니다.

(2) 상태 비트 확장: Chapter 14의 Valid + Dirty 비트를 MESI의 2비트 상태로 교체합니다. 캐시 SRAM의 태그 필드에 상태 비트를 추가하면 되므로, 하드웨어 오버헤드는 캐시 라인당 1비트 증가(Valid+Dirty = 2비트 → MESI = 2비트이므로 비트 수는 동일하지만, 인코딩이 변경)에 불과합니다.

(3) 버스 인터페이스 확장: Chapter 16에서 설계한 AHB 버스를 스누핑이 가능하도록 확장해야 합니다. 모든 캐시 컨트롤러가 버스 트랜잭션을 관찰할 수 있어야 하며, 필요 시 데이터 공급(Intervention)이나 대기(Wait) 신호를 삽입할 수 있어야 합니다.

📌 강사 꿀팁

MESI 프로토콜을 처음 가르칠 때, 상태 전이도를 한꺼번에 보여주면 학생들이 압도됩니다. 다음 순서로 점진적으로 소개하는 것이 효과적입니다: (1) 먼저 MI(Modified-Invalid) 2상태 프로토콜로 시작, (2) S(Shared) 상태를 추가하여 MSI 3상태로 확장, (3) E(Exclusive)를 추가하여 MESI 완성. 각 단계에서 "왜 새로운 상태가 필요한가?"를 질문하면 학습 효과가 극대화됩니다.

멀티코어 설계의 추가 과제

캐시 일관성 외에도 멀티코어 설계에는 여러 도전이 존재합니다. 이 절에서는 핵심 과제를 간략히 소개합니다.

메모리 일관성 모델(Memory Consistency Model): 캐시 일관성(Coherence)이 "하나의 주소에 대한 값의 일관성"을 보장한다면, 메모리 일관성(Consistency)은 "여러 주소에 대한 연산 순서"를 정의합니다. RISC-V는 RVWMO(RISC-V Weak Memory Ordering)라는 약한 메모리 순서 모델을 채택하고 있습니다. 이는 하드웨어에 더 많은 최적화 여지를 주지만, 소프트웨어가 메모리 펜스(FENCE) 명령어로 순서를 명시해야 합니다.

인터커넥트 대역폭(Interconnect Bandwidth): 코어 수가 증가하면 공유 버스의 대역폭이 병목이 됩니다. 4코어 이상에서는 크로스바(Crossbar) 스위치나 링(Ring) 인터커넥트, 메시(Mesh) 네트워크-온-칩(Network-on-Chip, NoC)을 사용합니다.

동기화 기본 요소(Synchronization Primitives): 멀티코어에서 공유 데이터에 안전하게 접근하려면 원자 연산(Atomic Operation)이 필요합니다. 이것이 바로 다음 절에서 다룰 RISC-V A 확장의 LR/SC 명령어입니다.

🔍 스스로 점검

다음 시나리오에서 MESI 상태 변화를 추적해 보십시오: (1) Core 0이 주소 A를 읽음 (캐시 미스, 다른 캐시에 없음) → 상태는? (2) Core 1이 주소 A를 읽음 (캐시 미스) → Core 0과 Core 1의 상태는? (3) Core 0이 주소 A에 쓰기 → 두 코어의 상태는? 정답: (1) E, (2) 둘 다 S, (3) Core 0: M, Core 1: I

25.2 스핀락과 원자 연산

25.1절에서 우리는 멀티코어 환경에서 캐시 일관성을 유지하는 방법을 살펴보았습니다. 캐시 일관성 프로토콜이 해결하는 것은 "하드웨어 수준에서 메모리 값의 일관성"입니다. 그러나 소프트웨어 수준에서는 또 다른 문제가 남아 있습니다. 두 코어가 동시에 같은 공유 변수를 수정하려 할 때, 어떻게 하나의 코어만 접근하도록 보장할 수 있을까요? 이것이 바로 상호 배제(Mutual Exclusion) 문제이며, 그 해결에는 원자 연산(Atomic Operation)이 필요합니다.

왜 일반 Load/Store로는 부족한가

다음과 같은 "잠금 획득" 코드를 생각해 보겠습니다. 


// 의사 코드: 일반 Load/Store로 잠금 시도 (위험!)
retry:
   LW   t0, 0(a0)      // lock 변수 읽기
   BNEZ t0, retry       // lock == 1이면 재시도
   SW   t2, 0(a0)       // lock = 1 설정 (잠금)
   // ... 임계 영역 ...

이 코드는 단일 코어에서는 문제없이 동작합니다. 그러나 멀티코어에서는 치명적인 결함이 있습니다. Core 0이 LW로 lock = 0을 읽은 직후, Core 1도 LW로 lock = 0을 읽을 수 있습니다. 두 코어 모두 "잠금이 풀려 있다"고 판단하고 동시에 임계 영역(Critical Section)에 진입하게 됩니다. 문제의 근본 원인은 "읽기"와 "쓰기"가 별개의 명령어로 분리되어 있어, 그 사이에 다른 코어가 개입할 수 있다는 것입니다.

비유: 공중전화 부스를 생각해 보십시오. "비어 있는지 확인"하고 "들어가서 문 잠그기"가 하나의 동작이 아니라 두 단계로 나뉘어 있다면, 두 사람이 동시에 빈 부스를 발견하고 동시에 들어가려 할 수 있습니다. 원자 연산은 "확인+잠금"을 하나의 나눌 수 없는 동작으로 만듭니다. 하드웨어 관점에서는, 이 "나눌 수 없는 동작"이 캐시 라인에 대한 독점적 접근을 보장하는 프로토콜을 통해 구현됩니다.

RISC-V A 확장: LR/SC 명령어

RISC-V는 원자 연산을 위해 A(Atomic) 확장을 정의합니다. A 확장에는 두 가지 메커니즘이 있습니다: (1) LR/SC (Load-Reserved / Store-Conditional)와 (2) AMO (Atomic Memory Operation). 이 절에서는 LR/SC에 집중합니다. LR/SC는 LL/SC(Load-Linked / Store-Conditional)라고도 불리며, ARM, MIPS 등 다른 아키텍처에서도 유사한 메커니즘을 제공합니다.

명령어 형식 동작
LR.W rd, (rs1) R 타입 (A 확장) 메모리[rs1]의 값을 rd에 로드하고, 해당 주소에 예약(Reservation)을 설정
SC.W rd, rs2, (rs1) R 타입 (A 확장) 예약이 유효하면 rs2를 메모리[rs1]에 저장하고 rd=0(성공), 아니면 rd=비영(실패)

LR.W는 일반 Load와 비슷하지만, 추가로 해당 메모리 주소에 "예약"을 설정합니다. SC.W는 조건부 Store입니다 — LR.W 이후 아무도 해당 주소를 수정하지 않았으면 저장에 성공하고(rd = 0), 누군가 수정했으면 저장에 실패합니다(rd = 비영). 이 메커니즘을 통해 "읽기 + 조건부 쓰기"가 논리적으로 원자적 연산이 됩니다.

LR/SC 기반 스핀락 구현

이제 LR/SC를 사용하여 안전한 스핀락(Spinlock)을 구현해 보겠습니다. 


// RISC-V 어셈블리: LR/SC 기반 스핀락
// a0 = lock 변수의 주소, t2 = 1 (잠금 값)

   LI    t2, 1            // t2 = 1 (잠금 설정 값)
retry:
   LR.W  t0, (a0)         // t0 = lock, 예약 설정
   BNEZ  t0, retry         // lock != 0이면 스핀 (이미 잠김)
   SC.W  t1, t2, (a0)      // lock = 1 시도 (조건부)
   BNEZ  t1, retry         // SC 실패하면 재시도
   // === 임계 영역(Critical Section) 진입 ===
   // ... 공유 데이터 접근 ...
   // === 임계 영역 종료 ===
   FENCE                   // 메모리 펜스
   SW    zero, 0(a0)       // lock = 0 (잠금 해제)

동작 순서를 단계별로 추적하겠습니다.

단계 1 — LR.W: lock 변수를 읽고 예약을 설정합니다. 예약은 해당 캐시 라인에 대한 "감시"를 의미합니다. 다른 코어가 이 캐시 라인에 쓰기를 하면 예약이 무효화됩니다.

단계 2 — BNEZ: lock이 이미 1(잠김)이면 다시 LR.W로 돌아가 스핀(Spin)합니다. "스핀"이란 잠금이 풀릴 때까지 반복적으로 확인하는 것입니다.

단계 3 — SC.W: lock = 0(풀림)이었다면, lock = 1로 설정을 시도합니다. LR.W와 SC.W 사이에 다른 코어가 개입하지 않았으면 SC가 성공하고(t1 = 0), 다른 코어가 개입했으면 SC가 실패합니다(t1 = 비영).

단계 4 — BNEZ: SC가 실패했으면 처음부터 재시도합니다.

핵심 통찰: LR/SC 쌍은 하드웨어적으로 "낙관적 동시성 제어(Optimistic Concurrency Control)"를 구현합니다. 잠금을 먼저 획득하는 것이 아니라, 일단 작업을 진행한 후 충돌이 없었는지 SC로 확인합니다. 충돌이 발생하면 재시도합니다. 이는 경쟁(Contention)이 적을 때 매우 효율적입니다.

❓ 수강생 단골 질문

Q: LR/SC와 CAS(Compare-And-Swap)의 차이는 무엇인가요? x86의 CMPXCHG와는 어떻게 다른가요?

A: CAS(예: x86의 CMPXCHG)는 "현재 값이 기대 값과 같으면 새 값으로 교체"하는 단일 명령어입니다. LR/SC는 두 명령어로 나뉘어 있지만, CAS에 없는 중요한 장점이 있습니다 — ABA 문제에 면역입니다. CAS는 "값이 A → B → A로 변했을 때" A로 복원된 것을 감지하지 못하지만, LR/SC는 값의 변화가 아니라 "해당 캐시 라인에 대한 쓰기 발생 여부"를 감시하므로, 값이 원래대로 복원되어도 SC가 실패합니다. 반면, LR/SC는 라이브락(Livelock) — 여러 코어가 동시에 LR→SC를 반복하여 누구도 성공하지 못하는 상황 — 의 위험이 있으므로, RISC-V 스펙은 SC가 최종적으로 성공할 수 있도록 하드웨어가 보장하도록 권장합니다.

LR/SC의 하드웨어 구현

LR/SC를 하드웨어로 구현하려면 다음 구성 요소가 필요합니다.

(1) 예약 레지스터(Reservation Register): 각 코어(또는 하드웨어 스레드)마다 하나의 예약 레지스터를 유지합니다. 이 레지스터는 예약 유효 비트(1비트)와 예약 주소(30비트, 워드 정렬 기준)로 구성됩니다. LR.W 실행 시 예약을 설정하고, SC.W 실행 시 또는 다른 코어의 스누핑에 의해 예약이 해제됩니다.

(2) 스누프 연동: 캐시 일관성 프로토콜의 스누핑 메커니즘과 연동하여, 다른 코어가 예약된 주소에 쓰기를 하면 예약을 무효화합니다. 이는 25.1절에서 설명한 MESI 프로토콜의 무효화(Invalidate) 이벤트와 자연스럽게 결합됩니다.

(3) SC 결과 생성: SC.W 실행 시 예약이 유효하고 주소가 일치하면 메모리 쓰기를 수행하고 rd에 0(성공)을 기록합니다. 예약이 무효이거나 주소가 불일치하면 메모리 쓰기를 수행하지 않고 rd에 비영(실패)을 기록합니다.

아래는 교육용으로 단순화한 LR/SC 실행 유닛의 SystemVerilog 구현입니다. 


module lr_sc_unit (
   input  logic        clk,
   input  logic        rst_n,
   // 파이프라인 인터페이스
   input  logic        ex_lr_w,       // LR.W 명령어 실행 중
   input  logic        ex_sc_w,       // SC.W 명령어 실행 중
   input  logic [31:0] ex_addr,       // 메모리 주소
   input  logic [31:0] ex_wdata,      // SC.W 기록 데이터
   // 스누핑 입력 (다른 코어의 메모리 접근 감시)
   input  logic        snoop_valid,
   input  logic [31:0] snoop_addr,
   input  logic        snoop_write,   // 다른 코어의 쓰기 여부
   // 메모리 인터페이스 출력
   output logic        mem_rd,
   output logic        mem_wr,
   output logic [31:0] mem_addr,
   output logic [31:0] mem_wdata,
   // SC.W 결과
   output logic        sc_success,
   output logic        sc_result_valid
);

   // 예약 레지스터
   logic        reservation_valid;
   logic [31:0] reservation_addr;

   // 주소 일치 판정 (워드 정렬)
   logic addr_match;
   assign addr_match = reservation_valid &&
                        (reservation_addr[31:2] == ex_addr[31:2]);

   // 예약 레지스터 관리
   always_ff @(posedge clk or negedge rst_n) begin
      if (!rst_n) begin
         reservation_valid <= 1'b0;
         reservation_addr  <= 32'h0;
      end
      else begin
         if (ex_sc_w)
            reservation_valid <= 1'b0;  // SC 실행 → 예약 해제
         else if (snoop_valid && reservation_valid &&
                  snoop_addr[31:2] == reservation_addr[31:2] &&
                  snoop_write)
            reservation_valid <= 1'b0;  // 스누핑 무효화
         else if (ex_lr_w) begin
            reservation_valid <= 1'b1;  // 새 예약 설정
            reservation_addr  <= ex_addr;
         end
      end
   end

   // 메모리 인터페이스 및 SC 결과
   always_comb begin
      mem_rd          = 1'b0;
      mem_wr          = 1'b0;
      mem_addr        = ex_addr;
      mem_wdata       = ex_wdata;
      sc_success      = 1'b0;
      sc_result_valid = 1'b0;

      if (ex_lr_w)
         mem_rd = 1'b1;
      else if (ex_sc_w) begin
         sc_result_valid = 1'b1;
         if (addr_match) begin
            mem_wr     = 1'b1;
            sc_success = 1'b1;  // rd ← 0 (성공)
         end
         // 실패 시 mem_wr = 0, rd ← 1 (실패)
      end
   end
endmodule

이 모듈의 핵심은 reservation_valid와 reservation_addr로 구성된 예약 레지스터입니다. LR.W가 실행되면 예약이 설정되고, SC.W 실행 시 또는 다른 코어의 스누핑 쓰기에 의해 예약이 해제됩니다. SC.W는 예약이 유효할 때만 실제 메모리 쓰기를 수행합니다.

💡 실무 팁

실제 프로세서에서 LR/SC 구현 시 주의할 점이 있습니다. RISC-V 스펙(Section 8.2)은 LR과 SC 사이의 코드가 16개 이하의 명령어여야 하며, 시스템 호출·캐시 미스·인터럽트 등에 의해 예약이 임의로 무효화될 수 있다고 명시합니다. 따라서 소프트웨어는 SC 실패를 항상 처리할 준비가 되어 있어야 합니다. 또한 예약 세분화(Reservation Granularity)는 캐시 라인 크기와 일치시키는 것이 일반적입니다 — 이렇게 하면 캐시 일관성 프로토콜의 무효화 이벤트를 그대로 예약 무효화에 활용할 수 있습니다.

LR/SC와 파이프라인 통합 고려사항

지금까지 만든 5단계 파이프라인 프로세서에 LR/SC를 통합하려면 다음 사항을 고려해야 합니다.

(1) 디코더 확장: Chapter 06에서 설계한 명령어 디코더에 A 확장 opcode(0101111, AMO)를 추가합니다. funct5 필드로 LR.W(00010)와 SC.W(00011)를 구분합니다.

(2) MEM 스테이지 수정: LR.W는 MEM 스테이지에서 일반 Load처럼 동작하되, 예약 레지스터를 추가로 설정합니다. SC.W는 MEM 스테이지에서 예약 확인 후 조건부로 Store를 수행합니다.

(3) 해저드 처리: LR.W와 SC.W 사이에 다른 메모리 명령어가 있으면, 포워딩 유닛(Chapter 10)이 올바르게 처리해야 합니다. SC.W의 결과(성공/실패)가 rd에 기록되므로, 이후 BNEZ 명령어와의 데이터 해저드도 처리해야 합니다.

🎯 면접 포인트

Q: "LR/SC와 CAS(Compare-And-Swap)의 차이점, 그리고 각각의 장단점을 설명하시오."

핵심 답변: LR/SC는 두 명령어로 구성되며 "주소 감시 기반"이고, CAS는 단일 명령어로 "값 비교 기반"입니다. LR/SC의 장점은 ABA 문제에 면역이라는 것이고, 단점은 라이브락 가능성과 구현 복잡성입니다. CAS의 장점은 단순한 인터페이스(단일 명령어)이고, 단점은 ABA 문제에 취약하다는 것입니다. RISC-V는 두 가지 모두 지원합니다(LR/SC + AMO). 면접에서는 "왜 RISC-V가 CAS 대신 LR/SC를 기본으로 채택했는가?"를 물을 수 있는데, 이는 RISC 철학(단순한 명령어)과 확장성(다양한 크기의 원자 연산 구현 용이) 때문입니다.

AMO(Atomic Memory Operation) 명령어 개요

RISC-V A 확장은 LR/SC 외에도 AMO(Atomic Memory Operation) 명령어군을 제공합니다. AMO는 읽기-수정-쓰기를 단일 명령어로 수행합니다.

명령어 동작 용도
AMOSWAP.W rd = mem[rs1]; mem[rs1] = rs2 스핀락, 세마포어
AMOADD.W rd = mem[rs1]; mem[rs1] = rd + rs2 원자적 카운터 증가
AMOAND.W rd = mem[rs1]; mem[rs1] = rd AND rs2 비트 필드 클리어
AMOOR.W rd = mem[rs1]; mem[rs1] = rd OR rs2 비트 필드 설정
AMOXOR.W rd = mem[rs1]; mem[rs1] = rd XOR rs2 비트 토글
AMOMIN[U].W rd = mem[rs1]; mem[rs1] = min(rd, rs2) 최솟값 갱신
AMOMAX[U].W rd = mem[rs1]; mem[rs1] = max(rd, rs2) 최댓값 갱신

AMO 명령어는 하드웨어적으로 캐시 라인에 대한 독점적 접근을 확보한 상태에서 읽기-수정-쓰기를 수행합니다. LR/SC보다 구현이 복잡할 수 있지만, 소프트웨어 인터페이스가 단순하고 라이브락 문제가 없습니다.

📌 강사 꿀팁

학생들에게 "LR/SC로 AMOADD를 구현해 보라"는 과제를 내면 두 메커니즘의 관계를 깊이 이해할 수 있습니다. 답안은 다음과 같습니다: retry: LR.W t0, (a0) / ADD t1, t0, a1 / SC.W t2, t1, (a0) / BNEZ t2, retry. 이 패턴은 "모든 AMO는 LR/SC로 구현 가능"하다는 것을 보여줍니다. 반대로 "LR/SC는 AMO로 대체할 수 없는 경우가 있는가?"도 좋은 토론 주제입니다(답: 다중 위치 원자 연산 등).

멀티코어 RISC-V 생태계와 미래 방향

이 챕터에서 다룬 내용은 멀티코어 프로세서 설계의 빙산의 일각입니다. 여러분이 앞으로 탐구할 수 있는 방향을 소개합니다.

RISC-V 멀티코어 오픈소스 프로젝트: UC Berkeley의 Chipyard 프레임워크는 BOOM(Berkeley Out-of-Order Machine)과 Rocket 코어를 조합한 멀티코어 SoC를 생성할 수 있습니다. TileLink 프로토콜이 캐시 일관성을 담당하며, 이는 이 챕터에서 배운 MESI의 디렉터리 기반 변형입니다.

이기종 멀티코어(Heterogeneous Multicore): ARM의 big.LITTLE과 유사하게, RISC-V에서도 고성능 코어(예: BOOM)와 저전력 코어(예: Rocket)를 조합하는 설계가 가능합니다. SiFive의 Intelligence X280 프로세서가 이 접근법을 채택하고 있습니다.

하드웨어-소프트웨어 공동 설계: 운영체제의 스케줄러, 컴파일러의 메모리 순서 최적화, 동기화 라이브러리 설계는 모두 하드웨어의 메모리 모델과 원자 연산 지원에 의존합니다. 하드웨어 엔지니어가 이러한 소프트웨어 계층을 이해하면, 더 효율적인 프로세서를 설계할 수 있습니다.

다음 질문에 답해 보십시오: (1) LR.W와 SC.W 사이에 다른 코어가 해당 주소에 쓰기를 하면 SC.W의 결과는? (2) LR.W와 SC.W 사이에 인터럽트가 발생하면 어떻게 되는가? (3) 스핀락에서 FENCE 명령어의 역할은 무엇인가? 정답: (1) SC 실패(rd = 비영), (2) 예약이 무효화될 수 있으므로 SC 실패 가능, SW는 재시도 루프로 처리, (3) 임계 영역 내의 메모리 접근이 잠금 해제 이전에 완료되도록 순서를 보장

핵심 정리

  • 캐시 일관성 문제: 멀티코어 환경에서 각 코어의 L1 캐시가 동일 주소에 대해 서로 다른 값을 보유할 수 있으며, 이를 해결하기 위해 스누핑 기반 또는 디렉터리 기반 일관성 프로토콜이 필요하다.
  • MESI 프로토콜: Modified(수정됨), Exclusive(독점), Shared(공유), Invalid(무효) 네 상태로 각 캐시 라인의 공유 상태를 추적하며, Exclusive 상태는 로컬 쓰기 시 버스 트랜잭션 없이 Modified로 전이할 수 있는 성능 이점을 제공한다.
  • 원자 연산의 필요성: 일반 Load/Store로는 멀티코어 환경에서 상호 배제를 보장할 수 없으며, "읽기 + 조건부 쓰기"를 원자적으로 수행하는 메커니즘이 필수적이다.
  • RISC-V LR/SC: Load-Reserved는 예약을 설정하고, Store-Conditional은 예약이 유효할 때만 저장을 수행한다. 이는 ABA 문제에 면역인 낙관적 동시성 제어 메커니즘이다.
  • 하드웨어 구현: 예약 레지스터(유효 비트 + 주소)와 스누핑 연동을 통해 LR/SC를 구현하며, 이는 기존 파이프라인의 MEM 스테이지와 캐시 컨트롤러에 자연스럽게 통합된다.
