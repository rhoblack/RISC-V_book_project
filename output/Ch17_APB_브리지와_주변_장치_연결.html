Chapter 17

APB 브리지와 주변 장치 연결

Chapter 16에서 설계한 AHB 버스는 프로세서 코어와 고속 메모리를 연결하는 고속도로 역할을 합니다. 그러나 UART, GPIO, 타이머처럼 상대적으로 느린 주변 장치를 모두 AHB에 직접 연결하면, 복잡한 핸드셰이크 로직이 불필요하게 각 슬레이브에 반복됩니다. 이 챕터에서는 저속 주변 장치를 위한 경량 버스인 APB(Advanced Peripheral Bus) 프로토콜을 이해하고, AHB-to-APB 브리지를 설계한 뒤, UART·GPIO·타이머 컨트롤러를 구현하여 Basys 3 보드에서 "Hello RISC-V" 메시지를 PC로 전송하는 마일스톤을 달성합니다.

학습 목표

  • APB 프로토콜의 SETUP/ACCESS 2단계 핸드셰이크를 설명할 수 있다.
  • AHB-to-APB 브리지의 FSM을 설계하고 SystemVerilog로 구현할 수 있다.
  • APB 슬레이브 인터페이스를 갖춘 UART, GPIO, 타이머 컨트롤러를 구현할 수 있다.
  • 레지스터 맵 기반의 소프트웨어 드라이버 수준 접근(MMIO)을 검증할 수 있다.
  • 주변 장치에서 발생하는 인터럽트 신호의 흐름을 분석하고 Chapter 19와의 연결점을 식별할 수 있다.

17.1 APB 프로토콜 이해

Chapter 16에서 우리는 AMBA AHB-Lite 버스를 설계하였습니다. AHB는 파이프라인 전송, 버스트 모드, 웨이트 스테이트 등 고성능 통신에 적합한 풍부한 기능을 제공하지만, 그만큼 슬레이브 측 구현이 복잡합니다. UART처럼 한 번의 전송에 수십~수백 클럭이 소요되는 저속 장치에 이런 복잡한 인터페이스를 적용하는 것은 과잉 설계(over-engineering)입니다.

이런 상황을 위해 ARM은 AMBA 패밀리의 일부로 APB(Advanced Peripheral Bus)를 정의하였습니다. APB는 AHB와 비교하여 다음과 같은 특성을 갖습니다.

특성 AHB-Lite APB
전송 방식 파이프라인 (주소·데이터 중첩) 비파이프라인 (2단계 순차)
최소 전송 사이클 1사이클 (파이프라인 후) 2사이클 (SETUP + ACCESS)
버스트 전송 지원 (INCR, WRAP) 미지원 (단일 전송만)
슬레이브 복잡도 높음 (HTRANS, HBURST 등 처리) 낮음 (PSEL, PENABLE만 감시)
적합한 장치 SRAM, DMA, 고속 IP UART, GPIO, Timer, SPI
비유: Chapter 16에서 AHB를 "고속도로"에 비유하였습니다. APB는 그 고속도로에서 빠져나온 뒤 목적지까지 연결되는 "이면도로"입니다. 이면도로에는 복잡한 진입로(ramp)나 추월 차선이 필요 없습니다. 신호등 하나(PENABLE)와 차선 선택(PSEL)만으로 충분합니다. AHB-to-APB 브리지는 고속도로와 이면도로를 잇는 "나들목(interchange)"에 해당합니다.

APB 핵심 신호

APB 프로토콜은 AMBA 2 APB Specification에 정의되어 있으며, 이후 AMBA 3에서 PREADY와 PSLVERR 신호가 추가되었습니다. 우리가 구현하는 APB는 AMBA 3 기준(APB3)이며, 다음 신호들을 사용합니다.

신호 방향 폭 설명
PCLK 입력 1 APB 클럭 (AHB의 HCLK과 동일)
PRESETn 입력 1 비동기 리셋 (액티브 로우)
PSEL Master→Slave 1 (슬레이브당) 슬레이브 선택. PSEL=1이면 해당 슬레이브가 선택됨
PENABLE Master→Slave 1 전송 활성화. SETUP→ACCESS 전이 시 1로 상승
PWRITE Master→Slave 1 전송 방향. 1=쓰기, 0=읽기
PADDR Master→Slave 32 주소 버스
PWDATA Master→Slave 32 쓰기 데이터
PRDATA Slave→Master 32 읽기 데이터
PREADY Slave→Master 1 슬레이브 준비 완료. ACCESS 단계에서 1이면 전송 종료

2단계 핸드셰이크: SETUP과 ACCESS

APB의 모든 전송은 정확히 두 단계로 진행됩니다. 이것이 APB의 핵심이자, AHB보다 단순한 이유입니다.

SETUP 단계 (T1): 브리지(APB Master)가 PSEL=1, PENABLE=0으로 설정하면서 PADDR, PWRITE, PWDATA(쓰기 시)를 안정시킵니다. 이 단계에서 슬레이브는 주소와 제어 신호를 "준비"합니다.

ACCESS 단계 (T2 이후): 다음 클럭에서 PENABLE=1로 상승합니다. 슬레이브가 PREADY=1을 반환하면 전송이 완료됩니다. 읽기 전송인 경우 이 시점에서 PRDATA가 유효해야 합니다. 슬레이브가 추가 시간이 필요하면 PREADY=0을 유지하여 웨이트 스테이트(wait state)를 삽입할 수 있습니다. 대부분의 간단한 주변 장치는 PREADY를 항상 1로 고정하여 웨이트 없이 2사이클 만에 전송을 완료합니다.

❓ 수강생 단골 질문

Q: APB는 왜 최소 2사이클이 필요한가요? AHB처럼 파이프라인으로 1사이클에 처리하면 안 되나요?

A: APB의 설계 철학은 "슬레이브를 최대한 단순하게"입니다. 파이프라인 전송을 지원하려면 슬레이브가 현재 데이터 단계와 다음 주소 단계를 동시에 처리해야 하므로 로직이 복잡해집니다. APB 대상 장치는 어차피 저속이므로, 2사이클의 오버헤드는 전체 시스템 성능에 거의 영향을 미치지 않습니다. 대신 슬레이브 설계가 극도로 간단해져서, FIFO나 상태 레지스터만 있으면 쉽게 APB 호환 IP를 만들 수 있습니다.

읽기 전송 vs 쓰기 전송

쓰기 전송과 읽기 전송의 차이는 PWRITE 신호의 값과 데이터 방향뿐입니다. 쓰기 시에는 마스터가 PWDATA를 SETUP 단계에서 설정하고, 읽기 시에는 슬레이브가 PRDATA를 ACCESS 단계의 PREADY=1 시점까지 유효하게 드라이브합니다. 타이밍 구조(SETUP → ACCESS)는 동일합니다.

💡 실무 팁

APB 슬레이브를 설계할 때, 레지스터 읽기 로직은 always_comb으로 구현하는 것을 권장합니다. PSEL && PENABLE && !PWRITE 조건에서 PRDATA를 조합적으로 출력하면, PREADY를 항상 1로 고정할 수 있어 웨이트 스테이트가 불필요합니다. 반대로 always_ff로 읽기를 구현하면 1사이클 지연이 추가되어 PREADY 제어가 필요해집니다.

🔍 스스로 점검

여기까지 읽었다면, 다음 질문에 답해 보십시오: APB 전송에서 PSEL=1이고 PENABLE=0인 상태의 이름은 무엇이며, 이 상태가 왜 필요합니까? 만약 SETUP 단계 없이 바로 PENABLE=1로 시작한다면, 슬레이브에 어떤 문제가 생길 수 있을까요?

17.2 AHB-to-APB 브리지 설계

프로세서 코어는 AHB 마스터로서 모든 메모리와 주변 장치에 접근합니다. 그런데 APB 슬레이브들은 AHB 프로토콜을 이해하지 못합니다. AHB-to-APB 브리지(이하 "브리지")는 이 두 프로토콜 세계를 연결하는 변환기(translator)입니다. 브리지는 AHB 측에서는 슬레이브로 동작하고, APB 측에서는 마스터로 동작합니다.

비유: 영어와 한국어를 동시에 구사하는 통역사를 떠올려 보십시오. 영어 화자(AHB 마스터)의 말을 듣고(AHB 슬레이브 역할), 한국어 화자(APB 슬레이브)에게 전달(APB 마스터 역할)합니다. 통역사는 상대방의 응답 속도에 맞춰 "잠시만요"(HREADY=0)라고 영어 화자에게 알려줄 수도 있습니다.

브리지 FSM: 3-상태 설계

브리지의 핵심은 3-상태 유한 상태 기계(FSM)입니다. 상태는 IDLE, SETUP, ACCESS로 구성되며, APB 프로토콜의 2단계 핸드셰이크를 그대로 반영합니다.

각 상태에서의 동작을 상세히 살펴보겠습니다.

IDLE 상태: APB 버스는 유휴 상태입니다. PSEL=0, PENABLE=0입니다. AHB 측에서 유효한 전송(HTRANS=NONSEQ)이 들어오면, 브리지는 AHB의 주소(HADDR)와 제어 신호(HWRITE)를 내부 레지스터에 래치하고 SETUP으로 전이합니다. 이때 HREADY_OUT=1을 유지하여 AHB 마스터가 주소를 전달할 수 있게 합니다.

SETUP 상태: 래치된 주소를 PADDR로 출력하고, 주소 디코딩을 통해 해당 슬레이브의 PSEL을 활성화합니다. PENABLE=0입니다. 이 상태는 정확히 1사이클만 유지되며, 무조건 ACCESS로 전이합니다. AHB 측에서는 HREADY_OUT=0으로 설정하여 마스터를 대기시킵니다.

ACCESS 상태: PENABLE=1로 상승합니다. 슬레이브의 PREADY 응답을 기다립니다. PREADY=1이면 전송이 완료되고, 읽기 데이터가 유효합니다. 이 시점에서 HREADY_OUT=1을 반환하여 AHB 마스터에게 완료를 알립니다. 만약 AHB 측에서 새로운 전송이 대기 중이면 SETUP으로, 그렇지 않으면 IDLE로 복귀합니다.

주소 디코딩: APB 슬레이브 선택

브리지는 여러 APB 슬레이브 중 하나를 선택해야 합니다. 주소의 상위 비트를 기준으로 디코딩합니다. 우리 시스템의 APB 주소 맵은 다음과 같습니다.

슬레이브 주소 범위 PSEL 인덱스 디코딩 비트
UART 0x4000_0000 ~ 0x4000_0FFF PSEL[0] PADDR[13:12] = 2'b00
GPIO 0x4000_1000 ~ 0x4000_1FFF PSEL[1] PADDR[13:12] = 2'b01
Timer 0x4000_2000 ~ 0x4000_2FFF PSEL[2] PADDR[13:12] = 2'b10
예약 0x4000_3000 ~ 0x4000_3FFF PSEL[3] PADDR[13:12] = 2'b11

각 슬레이브에 4KB(12비트)의 주소 공간을 할당하였습니다. 이 공간은 대부분의 간단한 주변 장치가 필요로 하는 레지스터 수(수십 개)를 충분히 수용합니다.

SystemVerilog 구현

아래는 브리지의 핵심 구현입니다. 전체 코드는 code_examples/ch17_ahb_to_apb_bridge.sv를 참조하십시오.


// FSM 상태 정의
typedef enum logic [1:0] {
   ST_IDLE   = 2'b00,     // 유휴: APB 전송 없음
   ST_SETUP  = 2'b01,     // 설정: PSEL=1, PENABLE=0
   ST_ACCESS = 2'b10      // 접근: PSEL=1, PENABLE=1
} state_t;

state_t state, next_state;

// AHB 주소 단계 캡처 — 유효한 전송일 때만 래치
always_ff @(posedge hclk or negedge hreset_n) begin
   if (!hreset_n) begin
      addr_reg  <= '0;
      write_reg <= 1'b0;
   end else if (hready_out && (htrans == HTRANS_NONSEQ)) begin
      addr_reg  <= haddr;
      write_reg <= hwrite;
   end
end

// FSM 다음 상태 로직
always_comb begin
   next_state = state;
   case (state)
      ST_IDLE:
         if (htrans == HTRANS_NONSEQ && hready_out)
            next_state = ST_SETUP;
      ST_SETUP:
         next_state = ST_ACCESS;   // 항상 1사이클
      ST_ACCESS:
         if (pready)
            next_state = valid_reg ? ST_SETUP : ST_IDLE;
      default: next_state = ST_IDLE;
   endcase
end

// HREADY 제어: ACCESS에서 PREADY 전달
always_comb begin
   case (state)
      ST_IDLE:   hready_out = 1'b1;
      ST_SETUP:  hready_out = 1'b0;  // 1사이클 대기
      ST_ACCESS: hready_out = pready; // 슬레이브 응답 전달
      default:   hready_out = 1'b1;
   endcase
end
🎯 면접 포인트

Q: AHB-to-APB 브리지의 역할은 무엇이며, 왜 필요합니까?

A: 브리지는 고성능 AHB 버스와 저속 APB 버스 사이의 프로토콜 변환기입니다. AHB는 파이프라인 전송을 지원하지만, APB는 2단계 비파이프라인 전송을 사용합니다. 브리지가 AHB 측에서 HREADY를 LOW로 유지하여 웨이트 스테이트를 삽입하는 동안, APB 측에서는 SETUP/ACCESS 시퀀스를 수행합니다. 이를 통해 저속 주변 장치의 인터페이스 로직을 대폭 단순화할 수 있습니다.

💡 실무 팁

실무에서 AHB-to-APB 브리지는 ARM에서 제공하는 IP(CoreLink SSE 등)를 사용하는 경우가 많습니다. 그러나 브리지의 내부 동작을 이해하지 못하면, 버스 타이밍 위반이나 데드락(deadlock) 상황을 디버깅하기 어렵습니다. 이 챕터에서 직접 구현하는 이유는 프로토콜 변환의 원리를 체득하기 위함입니다.

🔍 스스로 점검

브리지 FSM에서 SETUP 상태가 항상 1사이클인 이유를 설명할 수 있습니까? 만약 SETUP 단계를 생략하고 IDLE에서 바로 ACCESS로 전이한다면, APB 슬레이브에 어떤 문제가 발생할까요?

17.3 APB Slave: UART 컨트롤러

UART(Universal Asynchronous Receiver/Transmitter)는 프로세서와 외부 장치 간 직렬 통신의 가장 기본적인 형태입니다. 두 개의 와이어(TX, RX)만으로 양방향 통신이 가능하며, Basys 3 보드에는 FTDI FT2232 칩을 통한 USB-UART 브리지가 내장되어 있습니다. FPGA에서 "Hello RISC-V" 메시지를 PC의 터미널로 전송하는 것이 이번 Part 6의 마일스톤입니다.

비유: UART 통신은 모스 부호를 주고받는 것과 유사합니다. 송신자는 일정한 속도(보드레이트)로 한 글자씩 "점과 대시"(0과 1)를 보냅니다. 수신자는 동일한 속도로 신호를 해석합니다. 양쪽이 속도를 맞추지 않으면(보드레이트 불일치), 메시지가 깨집니다. "시작합니다"(시작 비트)와 "끝났습니다"(정지 비트) 신호로 각 글자의 경계를 표시합니다.

UART 프레임 구조: 8N1

우리가 구현하는 UART는 가장 일반적인 8N1 포맷을 사용합니다.

구성 요소 비트 수 값 설명
유휴(Idle) - HIGH (1) 전송 없을 때 TX 라인 상태
시작 비트(Start) 1 LOW (0) 새 바이트 전송의 시작 표시
데이터 비트(Data) 8 LSB 먼저 실제 전송 데이터 (8비트)
패리티(Parity) 0 - 없음 (N = No parity)
정지 비트(Stop) 1 HIGH (1) 바이트 전송 종료 표시

따라서 1바이트를 전송하는 데 총 10비트(1 시작 + 8 데이터 + 1 정지)가 필요합니다. 115200 baud에서 1바이트 전송 시간은 약 86.8 마이크로초(10 / 115200)입니다.

보드레이트 생성기

UART 송수신의 핵심은 보드레이트 생성기(Baud Rate Generator)입니다. 시스템 클럭(Basys 3: 100 MHz)을 분주하여 UART 비트 속도에 맞는 타이밍 신호를 생성합니다. 정확한 샘플링을 위해 16배 오버샘플링(oversampling) 기법을 사용합니다.

분주 값 계산 공식은 다음과 같습니다.

BAUD_DIV = CLK_FREQ / (BAUD_RATE × 16)

Basys 3에서 115200 baud를 사용할 경우: 100,000,000 / (115,200 × 16) ≈ 54. 이 값을 BAUD_DIV 레지스터에 설정합니다.

❓ 수강생 단골 질문

Q: 16배 오버샘플링은 왜 필요한가요? 1배(보드레이트 정확히)로 샘플링하면 안 되나요?

A: 1배 샘플링은 수신 측에서 정확히 비트 경계에 맞춰 샘플해야 합니다. 그런데 송수신 클럭이 독립적이므로, 미세한 주파수 차이로 인해 비트의 가장자리(edge)에서 샘플하게 될 위험이 있습니다. 16배 오버샘플링을 사용하면, 시작 비트의 하강 에지를 감지한 후 8틱(= 반 비트 주기) 뒤에 비트 중앙을 샘플할 수 있습니다. 이렇게 하면 최대 ±3% 주파수 오차까지 허용됩니다.

레지스터 맵

UART 컨트롤러는 소프트웨어가 MMIO(Memory-Mapped I/O)로 접근하는 레지스터 맵을 제공합니다.

오프셋 이름 접근 설명
0x00 TX_DATA W 송신 데이터 [7:0]. 쓰면 TX FIFO에 삽입
0x04 RX_DATA R 수신 데이터 [7:0]. 읽으면 RX FIFO에서 추출
0x08 STATUS R [0] TX Empty, [1] TX Full, [2] RX Valid, [3] RX Full
0x0C CTRL R/W [0] TX_EN, [1] RX_EN
0x10 BAUD_DIV R/W 보드레이트 분주 값 [15:0]
0x14 INT_EN R/W 인터럽트 활성화 [0] TX_EMPTY, [1] RX_VALID
0x18 INT_STATUS R/W1C 인터럽트 상태 (1을 쓰면 클리어)

송수신 FIFO

UART 컨트롤러는 송신(TX)과 수신(RX) 각각 8엔트리 FIFO를 내장합니다. FIFO가 없으면 소프트웨어는 매 바이트 전송 완료를 폴링(polling)하며 기다려야 합니다. 115200 baud에서 1바이트당 약 87마이크로초가 소요되므로, 100 MHz CPU가 약 8,700사이클을 낭비하게 됩니다. 8엔트리 FIFO가 있으면 8바이트를 연속으로 쓰고 다른 작업을 수행할 수 있어, CPU 활용도가 크게 향상됩니다.

송신(TX) FSM

TX 경로는 4-상태 FSM으로 구현됩니다: TX_IDLE → TX_START → TX_DATA → TX_STOP.

TX_IDLE: TX FIFO에 데이터가 있고 TX가 활성화되어 있으면, FIFO에서 1바이트를 꺼내 시프트 레지스터에 로드하고 TX_START로 전이합니다.

TX_START: TX 라인을 LOW로 구동합니다(시작 비트). 16개의 보드레이트 틱(= 1비트 시간)이 지나면 TX_DATA로 전이합니다.

TX_DATA: 시프트 레지스터의 비트를 LSB부터 순서대로 TX 라인에 출력합니다. 각 비트는 16틱 동안 유지됩니다. 8비트 모두 전송하면 TX_STOP으로 전이합니다.

TX_STOP: TX 라인을 HIGH로 구동합니다(정지 비트). 16틱 후 TX_IDLE로 복귀하여 다음 바이트를 처리합니다.

수신(RX) FSM

RX 경로도 유사한 4-상태 FSM을 사용하지만, 외부에서 들어오는 비동기 신호를 처리해야 하므로 두 가지 추가 요소가 필요합니다.

2단 동기화기(2-stage synchronizer): 외부 RX 신호는 FPGA 클럭과 비동기이므로, 직접 사용하면 메타안정성(metastability) 문제가 발생합니다. 2단 플립플롭 체인을 통과시켜 안정된 신호를 얻습니다.

중앙 샘플링(mid-bit sampling): 시작 비트의 하강 에지를 감지한 후, 8틱(반 비트 주기)을 기다려 비트의 중앙에서 샘플링합니다. 이렇게 하면 에지 근처의 불안정한 값을 피할 수 있습니다.

"Hello RISC-V" 소프트웨어 드라이버 의사 코드

아래는 UART를 통해 문자열을 전송하는 소프트웨어 드라이버의 의사 코드입니다. Chapter 22에서 실제 C 코드로 구현합니다.


// "Hello RISC-V" 전송 의사 코드 (C 스타일)
// UART_BASE = 0x4000_0000

void uart_putchar(char c) {
   // STATUS 레지스터의 TX_FULL(비트 1)이 0이 될 때까지 대기
   while (*(volatile uint32_t *)(UART_BASE + 0x08) & 0x02);
   // TX_DATA에 문자 쓰기
   *(volatile uint32_t *)(UART_BASE + 0x00) = (uint32_t)c;
}

void uart_puts(const char *s) {
   while (*s)
      uart_putchar(*s++);
}

// 사용: uart_puts("Hello RISC-V\r\n");
🔍 스스로 점검

UART TX FIFO의 깊이가 8인 경우, "Hello RISC-V\r\n" 문자열(14바이트)을 전송할 때 최소 몇 번 TX_FULL 상태를 폴링해야 합니까? FIFO 없이 매 바이트마다 폴링하는 경우와 비교하여 CPU 효율이 얼마나 개선되는지 생각해 보십시오.

17.4 APB Slave: GPIO 컨트롤러

GPIO(General-Purpose Input/Output)는 프로세서가 외부 세계와 디지털 신호를 주고받는 가장 기본적인 인터페이스입니다. Basys 3 보드에는 16개의 LED, 16개의 슬라이드 스위치, 5개의 푸시 버튼이 있으며, 이들은 모두 GPIO로 제어할 수 있습니다.

비유: GPIO는 "만능 리모컨"과 같습니다. 리모컨의 각 버튼(비트)이 출력 모드이면 TV를 켜고 끌 수 있고(LED 제어), 입력 모드이면 TV의 상태를 확인할 수 있습니다(스위치 읽기). 하나의 리모컨으로 여러 장치를 제어하듯, 하나의 GPIO 레지스터로 여러 핀을 개별적으로 제어합니다.

레지스터 맵

오프셋 이름 접근 설명
0x00 GPIO_DIR R/W 방향 레지스터. 비트=1이면 출력, 비트=0이면 입력
0x04 GPIO_OUT R/W 출력 데이터 레지스터. DIR=1인 핀에만 유효
0x08 GPIO_IN R 입력 데이터 레지스터. 동기화된 외부 핀 값 반영
0x0C GPIO_INT_EN R/W 인터럽트 활성화. 비트=1인 입력 핀의 상승 에지 감지

방향 레지스터(GPIO_DIR)가 GPIO 컨트롤러의 핵심입니다. 32비트 중 각 비트가 하나의 GPIO 핀에 대응합니다. 해당 비트를 1로 설정하면 출력 모드, 0으로 설정하면 입력 모드입니다. Basys 3 보드에서의 전형적인 설정은 다음과 같습니다.


// Basys 3 GPIO 초기 설정 예시 (C 스타일)
#define GPIO_BASE 0x40001000

// 하위 16비트를 출력(LED), 상위 16비트를 입력(SW)으로 설정
*(volatile uint32_t *)(GPIO_BASE + 0x00) = 0x0000FFFF;

// LED에 패턴 출력
*(volatile uint32_t *)(GPIO_BASE + 0x04) = 0x0000A5A5;

// 스위치 값 읽기
uint32_t sw_val = *(volatile uint32_t *)(GPIO_BASE + 0x08) >> 16;

입력 동기화: 메타안정성 방지

Basys 3의 슬라이드 스위치와 푸시 버튼은 사용자가 물리적으로 조작하는 장치입니다. 이 신호들은 FPGA의 시스템 클럭(100 MHz)과 아무런 동기 관계가 없는 비동기 신호입니다. 비동기 신호를 플립플롭의 데이터 입력에 직접 연결하면, 셋업 타임(setup time) 또는 홀드 타임(hold time) 위반이 발생하여 플립플롭이 메타안정(metastable) 상태에 빠질 수 있습니다.

메타안정 상태란 플립플롭의 출력이 0도 1도 아닌 중간 전압에 머무르는 현상으로, 이 값이 후속 로직에 전파되면 예측 불가능한 동작을 유발합니다. 이를 방지하기 위해 2단 동기화기(2-stage synchronizer)를 사용합니다.


// 2단 동기화기 — 외부 비동기 입력을 시스템 클럭에 동기화
logic [GPIO_WIDTH-1:0] gpio_in_sync_0;
logic [GPIO_WIDTH-1:0] gpio_in_sync_1;

always_ff @(posedge pclk or negedge preset_n) begin
   if (!preset_n) begin
      gpio_in_sync_0 <= '0;
      gpio_in_sync_1 <= '0;
   end else begin
      gpio_in_sync_0 <= gpio_in;        // 1단: 메타안정 가능
      gpio_in_sync_1 <= gpio_in_sync_0; // 2단: 안정화된 값
   end
end
// gpio_in_sync_1을 GPIO_IN 레지스터 값으로 사용

첫 번째 플립플롭(gpio_in_sync_0)이 메타안정 상태에 빠지더라도, 두 번째 플립플롭(gpio_in_sync_1)에 도달하기 전에 한 클럭 주기 동안 안정화될 확률이 매우 높습니다(100 MHz에서 MTBF > 수십 년). 2단이면 실용적으로 충분하지만, 극도의 신뢰성이 요구되는 환경에서는 3단을 사용하기도 합니다.

Q: GPIO에서 출력 핀에 대한 읽기(read-back)는 가능한가요?

A: 네, 가능합니다. GPIO_IN 레지스터를 읽으면, 방향과 관계없이 물리적 핀의 현재 상태를 읽을 수 있습니다. 출력으로 설정된 핀에서 GPIO_IN을 읽으면 실제로 핀에 출력되고 있는 값을 확인할 수 있어, 디버깅에 유용합니다. 다만 우리 구현에서는 단순화를 위해 GPIO_IN은 동기화된 외부 입력만 반영합니다. 실무 GPIO IP에서는 별도의 read-back 경로를 제공하는 경우가 많습니다.

💡 실무 팁

Basys 3의 푸시 버튼은 디바운싱(debouncing)이 필요합니다. 물리적 버튼을 누르면 접촉면의 탄성으로 인해 수 밀리초 동안 0과 1이 여러 번 반복됩니다(바운싱). 간단한 디바운서는 N밀리초(예: 10ms) 동안 동일한 값이 유지될 때만 입력을 반영하는 카운터 기반 필터입니다. 이 챕터에서는 디바운싱을 생략하지만, FPGA 실습 시에는 반드시 추가하십시오.

🔍 스스로 점검

2단 동기화기를 사용하는 이유를 "메타안정성"이라는 용어를 포함하여 한 문장으로 설명할 수 있습니까? 3단 동기화기를 사용하면 무엇이 달라지며, 왜 보통 2단으로 충분한지 설명할 수 있습니까?

17.5 APB Slave: 타이머/카운터

타이머(Timer)는 프로세서 시스템에서 가장 기본적이면서도 중요한 주변 장치입니다. 운영 체제의 태스크 스케줄링, 실시간 측정, 주기적 인터럽트 생성 등 거의 모든 시스템 소프트웨어가 타이머에 의존합니다. 이 절에서 설계하는 타이머의 인터럽트 신호(timer_irq)는 Chapter 19에서 프로세서의 mip.MTIP(Machine Timer Interrupt Pending) 비트와 연결되어, RISC-V 표준 타이머 인터럽트 메커니즘의 핵심 입력이 됩니다.

비유: 타이머는 주방에서 사용하는 "요리 타이머"와 같습니다. 목표 시간(비교 레지스터)을 설정하고 시작 버튼(EN)을 누르면, 카운터가 증가하다가 목표에 도달하면 "삐-" 소리(인터럽트)를 냅니다. 자동 재시작(AUTO_RELOAD) 모드는 알람이 울린 후 자동으로 다시 카운트를 시작하는 반복 타이머에 해당합니다.

레지스터 맵

오프셋 이름 접근 설명
0x00 TIM_CTRL R/W [0] EN, [1] AUTO_RELOAD, [2] IE (인터럽트 활성화)
0x04 TIM_COUNT R/W 현재 카운터 값 (32비트). 쓰기 시 직접 설정 가능
0x08 TIM_CMP R/W 비교 값. COUNT == CMP 시 이벤트 발생
0x0C TIM_PRESCALE R/W 프리스케일러 분주 값. 카운트 속도 조절
0x10 TIM_INT_STATUS R/W1C 인터럽트 펜딩 상태. 1을 쓰면 클리어

프리스케일러

프리스케일러(Prescaler)는 시스템 클럭을 분주하여 카운터의 증가 속도를 조절합니다. 100 MHz 시스템에서 PRESCALE=0이면 매 클럭(10 ns)마다, PRESCALE=99이면 100클럭(1 마이크로초)마다 카운터가 1 증가합니다. 프리스케일러 없이 32비트 카운터만 사용하면 최대 측정 범위가 약 43초(2^32 × 10 ns)입니다. 프리스케일러를 사용하면 이 범위를 크게 확장할 수 있습니다.

비교 레지스터와 인터럽트

카운터 값(TIM_COUNT)이 비교 값(TIM_CMP)과 일치하면, 다음 동작이 발생합니다.

인터럽트 생성: TIM_INT_STATUS[0]이 1로 세트됩니다. TIM_CTRL[2](IE)가 1이면, timer_irq 출력이 활성화됩니다.

카운터 동작: AUTO_RELOAD=1이면 카운터가 0으로 리셋되어 다시 시작합니다. AUTO_RELOAD=0이면 카운터가 CMP 값에서 정지합니다.

인터럽트 클리어는 W1C(Write-1-to-Clear) 방식입니다. 소프트웨어가 TIM_INT_STATUS에 1을 쓰면 해당 펜딩 비트가 클리어됩니다. 이는 인터럽트 서비스 루틴(ISR)에서 인터럽트 처리 완료를 하드웨어에 알리는 표준적인 방법입니다.

SystemVerilog 핵심 코드


// 32비트 업카운터 + 비교기
logic count_match;
assign count_match = (count_reg == cmp_reg);

always_ff @(posedge pclk or negedge preset_n) begin
   if (!preset_n)
      count_reg <= '0;
   else if (apb_write && paddr == ADDR_TIM_COUNT)
      count_reg <= pwdata;           // 소프트웨어 직접 설정
   else if (prescale_tick) begin
      if (count_match) begin
         if (auto_reload)
            count_reg <= '0;          // 자동 재시작
      end else
         count_reg <= count_reg + 1;
   end
end

// 인터럽트 로직 (W1C)
always_ff @(posedge pclk or negedge preset_n) begin
   if (!preset_n)
      int_pending <= 1'b0;
   else if (apb_write && paddr == ADDR_TIM_INT_STAT && pwdata[0])
      int_pending <= 1'b0;           // W1C 클리어
   else if (prescale_tick && count_match)
      int_pending <= 1'b1;           // 비교 일치 → 펜딩 세트
end

assign timer_irq = int_pending & int_enable;

Chapter 19 의존성: 인터럽트 경로

타이머 인터럽트(timer_irq)는 다음과 같은 경로로 프로세서에 전달됩니다. 이 전체 경로는 Chapter 19에서 완성합니다.

timer_irq → mip.MTIP → (mie.MTIE & mstatus.MIE) → 트랩 진입 → mtvec

현재 챕터에서는 timer_irq 신호의 생성까지 담당하며, 이 신호가 CSR(Chapter 18)과 트랩 메커니즘(Chapter 19)을 통해 프로세서의 정상 실행 흐름을 중단시키는 과정은 Part 7에서 다룹니다.

🎯 면접 포인트

Q: W1C(Write-1-to-Clear) 방식의 인터럽트 상태 레지스터는 왜 사용합니까? 소프트웨어가 0을 써서 클리어하면 안 되나요?

A: W1C는 멀티비트 상태 레지스터에서 특정 비트만 선택적으로 클리어할 수 있습니다. 예를 들어 인터럽트 상태 레지스터의 비트 0과 비트 2가 동시에 세트된 상태에서, ISR이 비트 0만 처리했다면 0x01을 쓰면 비트 0만 클리어되고 비트 2는 유지됩니다. "0을 써서 클리어" 방식(W0C)을 사용하면, 비트 0을 클리어하기 위해 0xFFFFFFFE를 써야 하는데, 이 과정에서 read-modify-write 원자성 문제가 발생할 수 있습니다. W1C는 단순한 쓰기만으로 특정 비트를 안전하게 클리어할 수 있어, 대부분의 인터럽트 컨트롤러에서 표준적으로 사용됩니다.

💡 실무 팁

RISC-V 공식 스펙에서 타이머는 mtime과 mtimecmp 메모리 맵 레지스터로 정의됩니다 (CLINT 사양). 우리 구현은 이를 단순화한 것이지만, 동작 원리(카운터 + 비교 → 인터럽트)는 동일합니다. SiFive FE310 등의 실제 RISC-V SoC도 동일한 패턴을 사용합니다.

🔍 스스로 점검

100 MHz 시스템에서 정확히 1초 주기의 인터럽트를 생성하려면, PRESCALE과 CMP 레지스터를 각각 어떤 값으로 설정해야 합니까? 조합이 여러 개 가능하다면, 어떤 기준으로 최적의 조합을 선택할 수 있을까요?

17.6 전체 주변 장치 통합 시뮬레이션

지금까지 설계한 AHB-to-APB 브리지, UART, GPIO, 타이머를 하나의 주변 장치 서브시스템(Peripheral Subsystem)으로 통합하고, 소프트웨어 드라이버 수준의 접근이 올바르게 동작하는지 시뮬레이션으로 검증합니다. 아래 그림은 전체 시스템 블록 다이어그램입니다.

통합 Top 모듈 구조

peripheral_top 모듈은 브리지와 세 개의 APB 슬레이브를 내부적으로 연결합니다. 핵심 설계 결정은 PRDATA 멀티플렉서입니다. APB에는 AHB의 HRDATA처럼 슬레이브 선택에 따라 읽기 데이터를 선택하는 표준 메커니즘이 없으므로, 브리지 내부 또는 Top 모듈에서 PSEL 신호를 기준으로 멀티플렉서를 구현해야 합니다.


// 읽기 데이터 멀티플렉서 — 선택된 슬레이브의 PRDATA를 브리지에 전달
always_comb begin
   prdata_mux = 32'h0;
   pready_mux = 1'b1;

   if (psel[0]) begin           // UART (0x4000_0000)
      prdata_mux = prdata_uart;
      pready_mux = pready_uart;
   end else if (psel[1]) begin  // GPIO (0x4000_1000)
      prdata_mux = prdata_gpio;
      pready_mux = pready_gpio;
   end else if (psel[2]) begin  // Timer (0x4000_2000)
      prdata_mux = prdata_timer;
      pready_mux = pready_timer;
   end
end

테스트벤치 설계 전략

통합 테스트벤치에서는 AHB 마스터의 동작을 태스크(task)로 추상화합니다. 실제 프로세서 대신 테스트벤치가 AHB 버스 트랜잭션을 생성하므로, 소프트웨어 드라이버가 하드웨어에 접근하는 것과 동일한 방식으로 검증할 수 있습니다.


// AHB 쓰기 태스크 — MMIO 쓰기를 모사
task ahb_write(input logic [31:0] addr, input logic [31:0] data);
   @(posedge hclk);
   haddr  <= addr;
   htrans <= HTRANS_NONSEQ;
   hwrite <= 1'b1;
   hsize  <= 3'b010;        // 워드 (32비트)
   @(posedge hclk);
   hwdata <= data;
   htrans <= HTRANS_IDLE;
   @(posedge hclk);
   while (!hready_out) @(posedge hclk);
endtask

검증 시나리오

테스트벤치는 다음 세 가지 시나리오를 순차적으로 실행합니다. 전체 코드는 code_examples/ch17_peripheral_tb.sv를 참조하십시오.

시나리오 1: GPIO LED 출력. GPIO_DIR에 0x0000_FFFF를 쓰고(하위 16비트 출력), GPIO_OUT에 0x0000_1234를 쓴 후, 물리적 출력 핀이 예상 값과 일치하는지 확인합니다.

시나리오 2: UART 문자 송신. BAUD_DIV를 설정하고 TX_DATA에 문자 'H'(0x48)를 쓴 후, STATUS 레지스터를 폴링하여 TX FIFO가 비워질 때까지 기다립니다. UART 루프백(TX→RX 연결)을 통해 수신까지 확인할 수 있습니다.

시나리오 3: 타이머 인터럽트. TIM_CMP=100, PRESCALE=0으로 설정한 후 타이머를 활성화합니다. 100클럭 후 timer_irq가 활성화되는지 확인하고, W1C 방식으로 클리어한 후 비활성화되는지 검증합니다.

Q: 테스트벤치에서 AHB 태스크를 사용하는 것과, 실제 프로세서를 연결하여 프로그램을 실행하는 것의 차이는 무엇인가요?

A: AHB 태스크 방식은 프로세서의 동작과 무관하게 버스 트랜잭션만 검증하므로, 주변 장치 자체의 정확성을 빠르게 확인할 수 있습니다. 프로세서 연결 방식은 실제 소프트웨어가 컴파일되어 실행되므로, 링커 스크립트, 스타트업 코드, 메모리 맵 전체가 올바른지까지 검증합니다. 단계적으로, 먼저 태스크 방식으로 주변 장치를 검증한 후(이 챕터), Chapter 22에서 프로세서와 연결하여 전체 소프트웨어 스택을 검증합니다.

17.7 본 챕터 요약 및 다음 단계

이번 챕터에서는 저속 주변 장치를 위한 APB 프로토콜을 이해하고, AHB-to-APB 브리지를 통해 UART, GPIO, 타이머를 프로세서 시스템에 통합하였습니다. Part 6(AMBA 버스 인터커넥트)의 완성과 함께, 우리 RV32I SoC는 이제 외부 세계와 통신할 수 있는 실용적인 시스템으로 성장하였습니다.

핵심 정리

  • APB 프로토콜은 SETUP(PSEL=1, PENABLE=0)과 ACCESS(PSEL=1, PENABLE=1) 2단계 핸드셰이크로 동작하며, 최소 2사이클에 전송을 완료한다. AHB 대비 슬레이브 구현이 극도로 단순하다.
  • AHB-to-APB 브리지는 IDLE/SETUP/ACCESS 3-상태 FSM으로 구현된다. AHB 측에서는 HREADY를 제어하여 웨이트 스테이트를 삽입하고, APB 측에서는 PSEL/PENABLE 시퀀스를 생성한다.
  • UART 컨트롤러는 8N1 포맷, 16배 오버샘플링, 8엔트리 TX/RX FIFO를 구현한다. 보드레이트 분주 레지스터로 통신 속도를 설정하며, Basys 3의 USB-UART(핀 A18/B18)에 연결된다.
  • GPIO 컨트롤러는 방향 레지스터(GPIO_DIR)로 각 핀의 입출력을 제어한다. 외부 비동기 입력은 2단 플립플롭 동기화기로 메타안정성을 방지한다.
  • 타이머/카운터는 프리스케일러 + 32비트 업카운터 + 비교 레지스터로 구성된다. COUNT==CMP 시 인터럽트를 발생시키며, W1C 방식으로 클리어한다.
  • UART와 타이머의 인터럽트 신호(uart_irq, timer_irq)는 Chapter 19에서 프로세서의 CSR(mip/mie)과 연결되어 완전한 인터럽트 처리 흐름을 형성한다.

연습문제

  1. [기억] APB 전송의 SETUP 단계에서 PSEL, PENABLE, PWRITE 신호의 값을 각각 명시하시오. ACCESS 단계와의 차이점은 무엇인가?
  2. [이해] AHB-to-APB 브리지 FSM에서 ACCESS 상태가 PREADY=0일 때 자기 자신으로 전이(self-loop)하는 이유를 설명하시오. 이 메커니즘이 없으면 어떤 문제가 발생하는가?
  3. [적용] Basys 3의 100 MHz 시스템 클럭에서 9600 baud UART 통신을 위한 BAUD_DIV 값을 계산하시오. 계산 결과에 반올림 오차가 있다면, 실제 보드레이트와 목표 보드레이트의 오차율(%)을 구하시오.
  4. [적용] 타이머를 사용하여 정확히 500 ms 주기의 LED 깜빡임을 구현하기 위한 PRESCALE과 CMP 레지스터 값의 조합을 두 가지 제시하시오. 각 조합의 장단점을 설명하시오.
  5. [분석] 현재 설계에서 프로세서가 UART TX_DATA에 연속으로 9바이트를 쓴다고 가정하자. 8엔트리 TX FIFO가 가득 찼을 때 9번째 쓰기는 어떻게 처리되는가? 데이터 손실을 방지하기 위한 소프트웨어 및 하드웨어 해결책을 각각 제시하시오.
  6. [분석] GPIO 컨트롤러의 2단 동기화기가 도입하는 입력 지연(레이턴시)은 몇 클럭 사이클인가? 버튼 디바운서를 추가하면 총 지연은 어떻게 변하는가?
  7. [평가] 현재 시스템에서 APB 슬레이브가 추가될 때마다 PRDATA 멀티플렉서와 주소 디코더를 수동으로 수정해야 한다. 이 접근법의 확장성 문제를 분석하고, SystemVerilog의 generate 구문이나 파라미터화를 이용한 개선 방안을 제시하시오.
