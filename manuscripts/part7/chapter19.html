Chapter 19

예외/인터럽트와 파이프라인 통합

Chapter 18에서 CSR 레지스터(mstatus, mtvec, mepc, mcause, mie, mip)를 구현했습니다. 이 레지스터들은 "예외가 발생하면 어떤 정보를 기록할 것인가"를 정의합니다. 이제 질문은 이것입니다: 파이프라인에서 5개 명령어가 동시에 실행되는 도중에 예외가 발생하면, 프로세서는 어느 명령어까지 완료하고 어느 명령어를 취소해야 할까요? 하드웨어가 mepc에 복귀 주소를 저장하지 않으면, 소프트웨어(OS)는 예외 처리 후 어디로 돌아갈지 알 수 없습니다. 하드웨어가 mcause에 원인을 기록하지 않으면, 소프트웨어는 무슨 문제인지 파악할 수 없습니다. 예외 처리에서 하드웨어의 역할은 "즉각적이고 정확한 상태 저장"이며, 이것은 소프트웨어로 대체할 수 없습니다. 이 장에서는 동기 예외와 비동기 인터럽트를 파이프라인에 통합하고, 정확한 예외(Precise Exception)를 보장하는 설계를 완성합니다. 이 장을 마치면 Part 7(AMBA + CSR + 예외/인터럽트)이 모두 완성됩니다.

학습 목표

  • Ch12 파이프라인의 스톨/플러시 메커니즘을 재확인하고, 예외/인터럽트 통합의 전제 조건을 설명할 수 있다. [L2]
  • 동기 예외(Illegal Instruction, Misaligned Access, ECALL)의 발생 조건을 식별하고, 각 스테이지별 감지 로직을 설계할 수 있다. [L3]
  • 비동기 인터럽트(Timer, External, Software)의 수락 조건을 분석하고, mie/mip 기반 우선순위 판정 로직을 설계할 수 있다. [L4]
  • 트랩 진입(mepc 저장, mtvec 점프)과 복귀(MRET) 메커니즘을 분석하고, CSR 상태 전이를 추적할 수 있다. [L4]
  • 파이프라인에서 정확한 예외(Precise Exception)를 보장하는 통합 설계를 분석하고, CSR 해저드 처리 방안을 평가할 수 있다. [L4]
  • ECALL 및 타이머 인터럽트 시나리오의 테스트벤치를 해석하고 응답 시간을 측정할 수 있다. [L3]
  • Part 7(AMBA + CSR + 예외) 통합 시스템을 종합 분석하고, Part 8(FPGA 구현)과의 연결을 예측할 수 있다. [L4]

이 장은 총 7개 절로 나뉩니다. 먼저 파이프라인을 복습(19.1)하고, 동기 예외(19.2)와 비동기 인터럽트(19.3)를 순서대로 배운 후, 트랩 메커니즘(19.4)과 파이프라인 통합(19.5)을 거쳐 검증(19.6)하고 마무리(19.7)합니다. 이 장을 완료하면, Part 7(AMBA + CSR + 예외)이 모두 완성됩니다.

이 장에서는 16개 예외와 11개 인터럽트를 모두 외울 필요가 없습니다. 우리가 실제로 구현하는 것은 Illegal Instruction, Load/Store Misaligned, ECALL 예외와 Timer Interrupt 하나입니다. 나머지는 같은 메커니즘의 반복이므로, 흐름을 이해하면 언제든 확장할 수 있습니다. 세부 타입은 참조 테이블로 제공됩니다.

19.1 파이프라인 구조 핵심 복습

예외와 인터럽트를 파이프라인에 통합하기 전에, Ch12에서 완성한 5단계 파이프라인의 핵심 구조를 1페이지로 복습합니다. 이미 배운 내용이므로 새로운 개념은 없습니다. 이 절의 목표는 하나: 플러시(flush)와 스톨(stall) 메커니즘을 정확히 기억하는 것입니다. 예외 처리는 본질적으로 "새로운 종류의 플러시"이기 때문입니다.

5단계 파이프라인 구조

Ch09에서 설계한 파이프라인은 다음 5단계로 구성됩니다.

스테이지 역할 핵심 동작
IF (Instruction Fetch) 명령어 인출 PC가 가리키는 주소에서 명령어를 메모리(I-Cache)에서 읽음
ID (Instruction Decode) 명령어 해독 opcode/funct3/funct7 분석, 레지스터 파일 읽기, 제어 신호 생성
EX (Execute) 실행 ALU 연산, 분기 판정, 주소 계산
MEM (Memory Access) 메모리 접근 D-Cache 읽기/쓰기
WB (Write Back) 결과 쓰기 레지스터 파일에 결과 기록

플러시(Flush)와 스톨(Stall): 두 가지 제어 메커니즘

파이프라인 제어의 핵심은 두 가지 신호입니다.

  • 스톨(Stall): 파이프라인을 일시 정지합니다. PC와 파이프라인 레지스터가 현재 값을 유지합니다. Ch10에서 Load-Use 해저드 시, Ch13~14에서 캐시 미스 시 사용했습니다.
  • 플러시(Flush): 파이프라인 레지스터의 내용을 NOP(32'h0000_0013)으로 교체합니다. Ch11에서 분기 예측 실패 시 IF/ID와 ID/EX 레지스터를 플러시했습니다. 이것은 해당 명령어를 "취소"하는 효과를 냅니다.

Ch12에서 확정한 우선순위를 기억하십시오: flush > icache_stall > dcache_stall > load_use_stall. 예외 처리는 이 우선순위 체계에 "예외 플러시"를 추가하는 것입니다. 메커니즘 자체는 이미 알고 있습니다 — 다만 플러시 범위가 확대될 뿐입니다.

❓ 수강생 단골 질문

Q: 분기 플러시와 예외 플러시는 어떻게 다른가요?

A: 분기 플러시는 IF/ID, ID/EX 두 레지스터만 클리어합니다(분기 판정이 EX에서 이루어지므로). 예외 플러시는 예외 발생 스테이지 이후의 모든 파이프라인 레지스터를 클리어합니다. 또한 예외 플러시 시 PC는 분기 목표가 아니라 mtvec(트랩 핸들러 주소)로 변경됩니다. 메커니즘은 같고, 범위와 목적지가 다릅니다.

Ch18 CSR과의 연결

Ch18에서 구현한 7개 CSR 중 예외 처리에 직접 관여하는 것은 다음 6개입니다.

CSR 주소 예외 처리에서의 역할
mstatus 0x300 MIE 비트: 전역 인터럽트 활성화/비활성화
mtvec 0x305 트랩 핸들러 시작 주소
mepc 0x341 예외 발생 명령어의 PC 저장 (복귀 주소)
mcause 0x342 예외/인터럽트 원인 코드
mie 0x304 인터럽트 개별 활성화 (MEIE, MTIE, MSIE)
mip 0x344 인터럽트 Pending 상태 (외부 신호 반영)

Ch17에서 구현한 타이머의 timer_irq 출력이 mip.MTIP(비트 7)에 연결되고, UART의 인터럽트 출력이 mip.MEIP(비트 11)에 연결됩니다. Part 6에서 만든 주변 장치의 인터럽트 신호가 이 장에서 실제로 처리됩니다.

19.2 동기 예외 처리

지금부터 파이프라인에 예외 처리를 추가합니다. 하지만 이것은 새로운 메커니즘이 아닙니다. Ch11에서 분기 예측 실패 시 플러시를 배웠습니다. 예외 처리도 동일한 플러시입니다 — 다만 PC가 분기 목표가 아니라 mtvec(트랩 핸들러 주소)로 바뀔 뿐입니다. 이미 아는 것의 확장입니다.

동기 예외란?

동기 예외(Synchronous Exception)는 특정 명령어의 실행으로 인해 발생하는 비정상 이벤트입니다. "동기"라는 이름은 명령어 실행과 동시에(synchronously) 발생한다는 뜻입니다. 같은 명령어를 같은 상태에서 다시 실행하면 반드시 같은 예외가 발생합니다.

비유: 프로그래밍에서 try-except 블록을 떠올려 보십시오. int("abc")를 실행하면 반드시 ValueError가 발생합니다. 하드웨어 예외도 마찬가지입니다 — 지원하지 않는 명령어를 실행하면 반드시 Illegal Instruction 예외가 발생합니다.

한계: 소프트웨어 예외는 스택 추적(stack trace)을 출력하지만, 하드웨어 예외는 스택 추적 없이 mtvec으로 즉시 점프합니다. 또한 소프트웨어 예외는 try 블록 내에서만 감지되지만, 하드웨어 예외는 어떤 명령어든 발생할 수 있습니다.

RV32I에서 구현하는 동기 예외 3종

RISC-V 스펙은 16가지 이상의 예외 코드를 정의하지만, 이 교재에서 구현하는 예외는 다음 3종입니다. 나머지는 같은 메커니즘으로 확장 가능하므로, 이 3가지만 완전히 이해하면 충분합니다.

예외 mcause 코드 감지 스테이지 발생 조건
Illegal Instruction (불법 명령어) 2 ID 디코더가 인식하지 못하는 opcode/funct3/funct7 조합
Load/Store Address Misaligned (주소 비정렬) 4 (Load) / 6 (Store) EX 워드 접근 시 addr[1:0] != 00, 하프워드 접근 시 addr[0] != 0
ECALL (환경 호출) 11 ID opcode = 1110011, funct3 = 000, imm = 0

각 스테이지에서의 예외 감지

각 스테이지는 자기 담당 예외 1~2종류만 감지합니다. 5단계 전체가 복잡해 보이지만, 실제로는 직교적(orthogonal)입니다.

ID 스테이지: Illegal Instruction과 ECALL을 감지합니다. 디코더가 명령어 필드를 분석하는 시점이므로, "이 명령어가 유효한가?"를 판단할 수 있습니다. IF 스테이지에서는 아직 명령어를 디코딩하지 않았으므로 불법 명령어를 감지할 수 없습니다. 


// ====== ID 스테이지: 예외 감지 (조합 로직) ======
logic id_illegal_instr;
logic id_ecall;
logic id_ebreak;

// 불법 명령어: 디코더가 인식하지 못하는 인코딩
assign id_illegal_instr = ~valid_opcode;  // valid_opcode는 디코더 출력

// ECALL: opcode=1110011, funct3=000, imm[11:0]=0
assign id_ecall = (id_opcode == 7'b1110011) &&
                  (id_funct3 == 3'b000) &&
                  (id_instr[31:20] == 12'b0);

// EBREAK: opcode=1110011, funct3=000, imm[11:0]=1
assign id_ebreak = (id_opcode == 7'b1110011) &&
                   (id_funct3 == 3'b000) &&
                   (id_instr[31:20] == 12'b1);

EX 스테이지: 주소 비정렬을 감지합니다. ALU에서 메모리 주소를 계산한 후, 정렬 조건을 확인합니다. 분기 대상 주소의 비정렬도 여기서 감지합니다. 


// ====== EX 스테이지: 주소 정렬 확인 ======
logic ex_load_misaligned;
logic ex_store_misaligned;
logic ex_branch_misaligned;

// 워드(LW/SW): addr[1:0]이 00이어야 함
// 하프워드(LH/SH): addr[0]이 0이어야 함
// 바이트(LB/SB): 항상 정렬됨

always_comb begin
   ex_load_misaligned  = 1'b0;
   ex_store_misaligned = 1'b0;

   if (ex_mem_read) begin  // 로드 명령어
      case (ex_funct3[1:0])
         2'b10: ex_load_misaligned = |alu_result[1:0];  // Word
         2'b01: ex_load_misaligned = alu_result[0];     // Halfword
         default: ex_load_misaligned = 1'b0;            // Byte
      endcase
   end

   if (ex_mem_write) begin  // 스토어 명령어
      case (ex_funct3[1:0])
         2'b10: ex_store_misaligned = |alu_result[1:0]; // Word
         2'b01: ex_store_misaligned = alu_result[0];    // Halfword
         default: ex_store_misaligned = 1'b0;           // Byte
      endcase
   end

   // 분기/점프 대상 주소: 항상 2바이트 정렬 (RV32I는 4바이트 정렬)
   ex_branch_misaligned = ex_branch_taken && |branch_target[1:0];
end

예외 정보의 파이프라인 전파

예외가 감지되면, 해당 스테이지에서 즉시 처리하지 않습니다. 대신 예외 정보(발생 여부, 예외 코드, 예외 발생 PC)를 파이프라인 레지스터에 태깅하여 WB 스테이지까지 전달합니다. WB에서 해당 명령어가 "가장 오래된 미완료 명령어"가 되었을 때 비로소 트랩을 발생시킵니다.

왜 즉시 처리하지 않을까요? 파이프라인에는 항상 여러 명령어가 동시에 실행 중이기 때문입니다. EX 스테이지에서 예외를 감지했을 때, 그보다 앞선(프로그램 순서상 이전의) 명령어가 MEM이나 WB 스테이지에서 아직 완료되지 않았을 수 있습니다. 만약 그 앞선 명령어도 예외를 발생시킨다면, 프로그램 순서상 먼저인 예외를 우선 처리해야 합니다. 이것이 정확한 예외(Precise Exception)의 핵심이며, 19.5절에서 자세히 다룹니다. 


// ====== 파이프라인 레지스터에 예외 정보 태깅 ======
// ID/EX 레지스터에 추가되는 필드
always_ff @(posedge clk or negedge rst_n) begin
   if (~rst_n || flush_id_ex) begin
      id_ex_except      <= 1'b0;
      id_ex_except_code <= 4'h0;
      id_ex_except_pc   <= 32'h0;
   end else if (~stall) begin
      id_ex_except      <= id_illegal_instr || id_ecall || id_ebreak;
      id_ex_except_code <= id_ecall  ? 4'd11 :
                            id_ebreak ? 4'd3  :
                                        4'd2;   // Illegal Instruction
      id_ex_except_pc   <= id_pc;
   end
end

// EX/MEM 레지스터: 이전 예외 전파 + 새 예외 병합
always_ff @(posedge clk or negedge rst_n) begin
   if (~rst_n || flush_ex_mem) begin
      ex_mem_except      <= 1'b0;
      ex_mem_except_code <= 4'h0;
      ex_mem_except_pc   <= 32'h0;
   end else if (~stall) begin
      // EX에서 새 예외 발생 시 → EX 예외 우선 (동일 명령어의 중복 예외이므로)
      if (ex_branch_misaligned) begin
         // 분기/점프 대상 주소 비정렬 (mcause=0, Instruction Address Misaligned)
         ex_mem_except      <= 1'b1;
         ex_mem_except_code <= 4'd0;
         ex_mem_except_pc   <= ex_pc;
      end else if (ex_load_misaligned || ex_store_misaligned) begin
         ex_mem_except      <= 1'b1;
         ex_mem_except_code <= ex_load_misaligned ? 4'd4 : 4'd6;
         ex_mem_except_pc   <= ex_pc;
      end else begin
         // ID에서 전파된 예외 유지
         ex_mem_except      <= id_ex_except;
         ex_mem_except_code <= id_ex_except_code;
         ex_mem_except_pc   <= id_ex_except_pc;
      end
   end
end

타이밍 다이어그램을 보십시오. 예외가 발생하면 프로세서는 4사이클 안에 처리를 완료합니다: ①예외 감지 → ②플러시 신호 → ③mepc/mcause 저장 → ④mtvec으로 점프. 매우 빠르고 체계적인 과정입니다.

💡 실무 팁

상용 프로세서(ARM Cortex, Intel x86)에서도 예외 정보를 파이프라인 끝(커밋 스테이지)까지 전파하는 방식을 사용합니다. 이를 "예외 태깅(Exception Tagging)"이라 합니다. 이렇게 해야 투기적 실행(Speculative Execution)에서 잘못된 경로의 예외를 무시할 수 있습니다.

🎯 면접 포인트

"동기 예외와 비동기 인터럽트의 차이를 설명하시오." 핵심 답변: 동기 예외는 특정 명령어의 실행으로 발생하며 결정적(deterministic)입니다. 같은 명령어를 같은 상태에서 재실행하면 동일한 예외가 발생합니다. 비동기 인터럽트는 외부 신호에 의해 발생하며 명령어와 무관합니다. 둘 다 mtvec으로 점프하여 처리되지만, 예외는 mepc에 해당 명령어의 PC를, 인터럽트는 다음 명령어의 PC를 저장합니다.

🔍 스스로 점검

다음 빈칸을 채워 보십시오.

  • Illegal Instruction 예외는 ___(IF/ID/EX/MEM/WB) 스테이지에서 감지된다. → ID
  • Load Misaligned 예외는 ___(IF/ID/EX/MEM/WB) 스테이지에서 감지된다. → EX
  • 예외 정보는 즉시 처리하지 않고 ___ 스테이지까지 전파한다. → WB
  • 예외 처리의 핵심 3단계: ①예외 ___ → ②파이프라인 ___ → ③PC를 ___로 변경 → 감지, flush, mtvec

19.3 비동기 인터럽트 처리

인터럽트는 예외와 거의 같은 메커니즘을 따릅니다. 유일한 차이: 예외는 발생하면 반드시 처리하지만, 인터럽트는 mstatus.MIE 비트로 지금 받을지 말지 선택할 수 있습니다. 나머지 흐름(flush → mtvec 점프)은 동일합니다.

인터럽트란?

비동기 인터럽트(Asynchronous Interrupt)는 현재 실행 중인 명령어와 무관하게, 외부 또는 내부 장치에서 발생하는 신호입니다. "비동기"라는 이름은 프로세서 명령어 실행과 무관하게(asynchronously) 아무 시점에나 도착할 수 있다는 뜻입니다.

비유: 업무 전화 중에 긴급 전화가 걸려옵니다. 현재 통화(명령어 실행)를 마무리하고 → 긴급 전화(트랩 핸들러)에 응대하고 → 원래 통화로 복귀합니다. mepc는 "어디까지 얘기했는지" 메모이고, MRET은 "긴급 전화를 끊고 원래 통화로 돌아가기"입니다.

한계: 전화와 달리, 프로세서는 인터럽트를 거절할 수 있습니다(mstatus.MIE=0). 또한 여러 긴급 전화가 동시에 오면, 우선순위 인코더가 가장 긴급한 하나만 선택합니다.

RV32I의 3가지 인터럽트 소스

인터럽트 mcause 코드 mip 비트 mie 비트 소스
Machine External Interrupt (MEI) 0x8000_000B (11) mip[11] (MEIP) mie[11] (MEIE) UART, GPIO 등 외부 장치 (Ch17)
Machine Software Interrupt (MSI) 0x8000_0003 (3) mip[3] (MSIP) mie[3] (MSIE) 소프트웨어가 프로그램적으로 발생
Machine Timer Interrupt (MTI) 0x8000_0007 (7) mip[7] (MTIP) mie[7] (MTIE) 타이머 (Ch17.5)

mcause[31] = 1이면 인터럽트, 0이면 예외입니다. 하위 비트는 인터럽트 번호를 나타냅니다.

인터럽트 수락 조건: 3중 게이트

인터럽트가 실제로 처리되려면 다음 세 조건이 모두 만족해야 합니다.

  1. mip[N] = 1: 해당 인터럽트가 Pending 상태 (하드웨어가 자동 설정)
  2. mie[N] = 1: 해당 인터럽트가 개별 활성화 (소프트웨어가 설정)
  3. mstatus.MIE = 1: 전역 인터럽트가 활성화 (소프트웨어가 설정)

논리적으로 표현하면: irq_pending[N] = mip[N] & mie[N] & mstatus.MIE

우선순위 인코더

여러 인터럽트가 동시에 Pending되면, 우선순위 인코더가 하나만 선택합니다. RISC-V 특권 스펙의 권장 우선순위: MEI(외부, 11) > MSI(소프트웨어, 3) > MTI(타이머, 7) 


// ============================================================
// 인터럽트 컨트롤러 (Interrupt Controller)
// Chapter 19 — 비동기 인터럽트 우선순위 판정
// ============================================================
module interrupt_controller (
   input  logic        clk,
   input  logic        rst_n,

   // --- 인터럽트 소스 (Ch17 주변 장치) ---
   input  logic        timer_irq,       // 타이머 인터럽트 (Ch17.5)
   input  logic        external_irq,    // 외부 인터럽트 (UART 등)
   input  logic        software_irq,    // 소프트웨어 인터럽트

   // --- CSR 레지스터 입력 ---
   input  logic [31:0] mie,             // 인터럽트 개별 활성화
   input  logic        mstatus_mie,     // 전역 인터럽트 활성화

   // --- 출력 ---
   output logic [31:0] mip,             // 하드웨어 반영 값 (csr_unit.mip의 해당 비트에 연결)
   output logic        irq_pending,     // 처리 가능한 인터럽트 존재
   output logic [3:0]  irq_code         // 최우선 인터럽트 코드
);

   // ====== mip 레지스터 업데이트 ======
   // mip는 외부 인터럽트 신호를 직접 반영 (하드웨어 제어)
   always_comb begin
      mip      = 32'h0;  // 기본값
      mip[3]   = software_irq;   // MSIP
      mip[7]   = timer_irq;      // MTIP
      mip[11]  = external_irq;   // MEIP
   end

   // ====== 인터럽트 활성화 판정 ======
   logic [31:0] enabled_irq;
   assign enabled_irq = mie & mip & {32{mstatus_mie}};

   // ====== 우선순위 인코더 ======
   // RISC-V 권장: MEI(11) > MSI(3) > MTI(7)
   always_comb begin
      irq_pending = |enabled_irq;
      if (enabled_irq[11])      irq_code = 4'd11; // External
      else if (enabled_irq[3])  irq_code = 4'd3;  // Software
      else if (enabled_irq[7])  irq_code = 4'd7;  // Timer
      else begin
         irq_code    = 4'd0;
         irq_pending = 1'b0;
      end
   end
endmodule

인터럽트 처리 시점: 명령어 경계

동기 예외는 해당 명령어 실행 도중에 발생하지만, 비동기 인터럽트는 명령어 경계(instruction boundary)에서만 처리합니다. 즉, 현재 실행 중인 명령어의 WB 스테이지가 완료된 후에 인터럽트를 수락합니다. 이렇게 하면 인터럽트 발생 전의 모든 명령어가 정상적으로 완료되어, 정확한 프로세서 상태를 보장할 수 있습니다.

인터럽트와 예외의 mepc 저장 규칙도 다릅니다:

  • 동기 예외: mepc = 예외를 발생시킨 명령어의 PC. 예외는 해당 명령어를 에뮬레이션하거나 수정한 후 같은 PC에서 재실행(retry)할 수 있어야 하기 때문입니다.
  • 비동기 인터럽트: mepc = 다음에 실행할 명령어의 PC. 인터럽트는 현재 명령어가 이미 완료된 상태이므로, 다음 명령어부터 이어가면(continue) 됩니다.
❓ 수강생 단골 질문

Q: 인터럽트가 도착했는데 mstatus.MIE = 0이면 어떻게 되나요?

A: mip 비트는 여전히 1로 설정됩니다(인터럽트가 Pending 상태). 하지만 mstatus.MIE = 0이므로 프로세서는 이를 무시하고 현재 명령어를 계속 실행합니다. 나중에 소프트웨어가 mstatus.MIE를 1로 설정하면, 그 시점에서 Pending된 인터럽트가 처리됩니다. 트랩 핸들러 진입 시 하드웨어가 자동으로 MIE = 0으로 설정하므로, 핸들러 실행 중에 같은 인터럽트가 중첩되는 것을 방지합니다.

19.4 트랩 진입/복귀 메커니즘

19.2~19.3에서 예외와 인터럽트가 "무엇"인지 배웠습니다. 이제 프로세서가 실제로 어떤 절차를 밟아 현재 작업을 중단하고 핸들러로 전환하는지 — 그리고 핸들러 종료 후 어떻게 원래 위치로 돌아오는지를 다룹니다. Ch18에서 배운 CSR들이 여기서 핵심 역할을 합니다.

트랩 진입 시퀀스 (6단계)

트랩(예외 또는 인터럽트)이 발생하면, 하드웨어는 다음 6단계를 자동으로 수행합니다. 소프트웨어는 이 과정에 개입하지 않습니다.

비유: 비행기에 문제가 발생하면 블랙박스(Flight Data Recorder)가 자동으로 사건 직전의 고도, 속도, 방향을 기록합니다. 프로세서의 CSR도 마찬가지입니다 — 예외 발생 순간의 PC(mepc), 원인(mcause), 이전 인터럽트 상태(mstatus.MPIE)를 하드웨어가 자동으로 기록합니다.

한계: 블랙박스는 사건 후 분석용이지만, CSR은 실시간으로 사건을 처리하는 데 사용됩니다. 트랩 핸들러는 CSR 값을 읽어서 예외 원인을 파악하고 즉시 대응합니다.
  1. mepc ← 예외 발생 PC: 동기 예외는 해당 명령어 PC, 비동기 인터럽트는 다음 명령어 PC를 저장
  2. mcause ← 원인 코드: 예외 코드(2, 4, 6, 11 등) 또는 인터럽트 코드(비트 31 = 1)
  3. mstatus.MPIE ← mstatus.MIE: 현재 인터럽트 활성화 상태를 백업
  4. mstatus.MIE ← 0: 핸들러 실행 중 인터럽트 비활성화 (중첩 방지)
  5. mstatus.MPP ← 현재 특권 수준: M-mode 전용이므로 항상 2'b11
  6. PC ← mtvec: 트랩 핸들러 시작 주소로 점프

트랩 진입 하드웨어 구현


// ====== 트랩 진입 시퀀스 (trap_taken 신호 활성 시) ======
always_ff @(posedge clk or negedge rst_n) begin
   if (~rst_n) begin
      csr_mepc    <= 32'h0;
      csr_mcause  <= 32'h0;
      csr_mstatus <= 32'h0;
   end else if (trap_taken) begin
      // Step 1: mepc ← 예외/인터럽트 발생 PC
      csr_mepc <= trap_mepc;

      // Step 2: mcause ← 원인 코드
      csr_mcause <= trap_mcause;

      // Step 3~5: mstatus 업데이트
      csr_mstatus[7]     <= csr_mstatus[3]; // MPIE ← MIE
      csr_mstatus[3]     <= 1'b0;           // MIE ← 0
      csr_mstatus[12:11] <= 2'b11;          // MPP ← M-mode
   end
end

// Step 6: PC ← mtvec (Direct 모드)
assign trap_pc = {csr_mtvec[31:2], 2'b00};

트랩 복귀: MRET 명령어

트랩 핸들러의 마지막 명령어는 MRET(Machine Return)입니다. MRET은 트랩 진입의 역순을 수행합니다:

  1. PC ← mepc: 예외 발생 지점(또는 다음 명령어)으로 복귀
  2. mstatus.MIE ← mstatus.MPIE: 인터럽트 활성화 상태 복원
  3. mstatus.MPIE ← 1: MPIE를 1로 설정

// ====== MRET 실행 시퀀스 ======
always_ff @(posedge clk or negedge rst_n) begin
   if (~rst_n) begin
      // 리셋 처리
   end else if (mret_instr) begin
      // Step 2: MIE ← MPIE (인터럽트 재활성화)
      csr_mstatus[3] <= csr_mstatus[7]; // MIE ← MPIE
      // Step 3: MPIE ← 1
      csr_mstatus[7] <= 1'b1;
   end
end

// Step 1: PC ← mepc
assign mret_pc = csr_mepc;

트랩 핸들러 어셈블리 예제

하드웨어가 CSR을 자동 저장한 후, 소프트웨어(트랩 핸들러)가 실행됩니다. 다음은 최소한의 트랩 핸들러 구현입니다. 


# =================================================
# Minimal Trap Handler for RISC-V RV32I
# =================================================

.section .text.trap_handler
.align 4

trap_handler:
  # ---- Step 1: 범용 레지스터 저장 ----
  addi sp, sp, -64           # 스택 공간 할당
  sw   ra, 0(sp)             # return address 저장
  sw   a0, 4(sp)
  sw   a1, 8(sp)
  sw   t0, 12(sp)
  sw   t1, 16(sp)

  # ---- Step 2: 예외 원인 읽기 ----
  csrr a0, mcause            # a0 = mcause

  # ---- Step 3: 원인별 분기 ----
  bltz a0, handle_interrupt  # mcause[31]=1 → 인터럽트
  # mcause[31]=0 → 동기 예외
  li   t0, 2
  beq  a0, t0, handle_illegal
  li   t0, 4
  beq  a0, t0, handle_load_misaligned
  li   t0, 11
  beq  a0, t0, handle_ecall
  j    handle_unknown

handle_illegal:
  # Illegal Instruction 처리
  # mepc를 다음 명령어로 이동 (현재 명령어 건너뛰기)
  csrr t0, mepc
  addi t0, t0, 4
  csrw mepc, t0
  j    restore_and_return

handle_load_misaligned:
  # Load Misaligned 처리 (에러 코드 기록)
  j    restore_and_return

handle_ecall:
  # ECALL 처리 (시스템 콜)
  csrr t0, mepc
  addi t0, t0, 4             # ECALL 다음 명령어로 복귀
  csrw mepc, t0
  j    restore_and_return

handle_interrupt:
  # 인터럽트 처리 (mcause에서 번호 추출)
  andi a0, a0, 0xFF          # 하위 8비트 = 인터럽트 번호
  li   t0, 7
  beq  a0, t0, handle_timer_irq
  j    restore_and_return

handle_timer_irq:
  # 타이머 인터럽트: 타이머 재설정 등
  j    restore_and_return

handle_unknown:
  j    .                     # 미지원 예외: 무한 루프
  # 실제 시스템에서는 에러 로그 기록 후 재부팅 등의 처리가 필요합니다

# ---- 복귀 ----
restore_and_return:
  lw   t1, 16(sp)
  lw   t0, 12(sp)
  lw   a1, 8(sp)
  lw   a0, 4(sp)
  lw   ra, 0(sp)
  addi sp, sp, 64
  mret                       # PC ← mepc
💡 실무 팁

ECALL 핸들러에서 mepc를 4만큼 증가시키는 이유: ECALL은 "환경 호출"이므로 같은 명령어를 재실행할 이유가 없습니다. 반면 Load Misaligned는 주소를 수정한 후 같은 명령어를 재시도할 수 있으므로, mepc를 변경하지 않을 수 있습니다. 예외 종류에 따라 mepc 조정 여부가 달라집니다.

  • MRET 실행 시: PC ← ___, mstatus.MIE ← ___ → mepc, MPIE
  • 트랩 핸들러에서 mcause[31]을 확인하는 이유: ___와 ___를 구분하기 위해 → 인터럽트, 예외

19.5 파이프라인과 예외 처리 통합

지금부터 배우는 것은 이미 배운 파이프라인에 예외를 추가하는 것입니다. Ch11에서 배운 플러시 메커니즘은 그대로 사용됩니다. 19.2~19.4에서 배운 세 가지(예외 감지, 인터럽트 판정, 트랩 시퀀스)를 하나로 연결하는 것이 이 절의 전부입니다. 각 부품은 이미 완성되었습니다 — 지금은 신호 흐름만 추적하면 됩니다.

이 절은 챕터의 최고 난이도 구간입니다. 그러나 새로운 개념이 4개(정확한 예외, 예외 전파, CSR 해저드, 통합 플러시)뿐이고, 나머지는 이전 절에서 배운 것의 결합입니다. 하나씩 단계적으로 진행합니다.

정확한 예외(Precise Exception)

정확한 예외(Precise Exception)란 다음 두 조건을 만족하는 예외 처리를 말합니다:

  1. 예외를 발생시킨 명령어 이전의 모든 명령어는 완전히 완료된 상태여야 한다.
  2. 예외를 발생시킨 명령어 이후의 모든 명령어는 아무런 부작용(side effect)을 남기지 않아야 한다.
비유: 영화 촬영 중 배우가 대사를 크게 틀렸습니다. 감독이 "컷!"을 외칩니다. 그 장면 이전까지 촬영된 분량은 유효합니다(완료된 명령어). 그 장면 이후의 촬영분은 모두 버려집니다(플러시된 명령어).

한계: 실제 영화와 달리 CPU의 플러시는 파이프라인 깊이만큼 시간이 필요합니다. 또한 "버린다"는 것은 물리적 삭제가 아니라 valid 비트를 끄는 논리적 취소입니다.

타이밍 다이어그램을 보십시오. 예외가 발생하면 프로세서는 4사이클 안에 처리를 완료합니다: ①예외 감지 → ②플러시 신호 → ③mepc/mcause 저장 → ④mtvec으로 점프. 매우 빠르고 체계적인 과정입니다.

WB 스테이지 커밋 방식

19.2절에서 설명한 대로, 예외 정보는 파이프라인 레지스터를 통해 WB까지 전파됩니다. WB 스테이지에서 해당 명령어가 파이프라인의 가장 앞(프로그램 순서상 가장 오래된)에 도달했을 때, 비로소 트랩을 발생시킵니다.

이 방식의 장점:

  • 프로그램 순서가 보장됩니다. WB에 먼저 도착한 명령어가 프로그램 순서상 앞선 명령어입니다.
  • 동시에 여러 예외가 존재할 때(예: IF에서 접근 오류 + EX에서 미정렬), WB에 먼저 도착한 것이 우선됩니다.
  • 투기적으로 실행된 명령어(분기 후 경로)의 예외는 WB에 도달하기 전에 플러시되므로 자연스럽게 무시됩니다.

// ====== WB 스테이지: 트랩 커밋 판정 ======
logic wb_trap_taken;
logic [31:0] wb_trap_mepc;
logic [31:0] wb_trap_mcause;

// 동기 예외 판정 (파이프라인에서 전파된 정보)
logic wb_sync_except;
assign wb_sync_except = mem_wb_except;  // MEM/WB 레지스터에서 전파

// 비동기 인터럽트 판정 (명령어 경계에서 샘플링)
// CSR 해저드 방지를 위해 irq_sample_valid 조건 포함 (19.5절 CSR 해저드 참조)
logic wb_async_irq;
logic irq_sample_valid;
assign irq_sample_valid = ~csr_write_in_wb;  // CSR 쓰기 완료 대기
assign wb_async_irq = irq_pending &&
                      irq_sample_valid &&
                      ~mem_wb_except;
// 동기 예외가 없고, CSR 업데이트 완료 후에만 인터럽트 수락

// 트랩 발생 여부
assign wb_trap_taken = wb_sync_except || wb_async_irq;

// mepc 결정
assign wb_trap_mepc = wb_sync_except ? mem_wb_except_pc :
                                       mem_wb_pc + 32'd4;
// 동기 예외: 해당 명령어 PC
// 비동기 인터럽트: 다음 명령어 PC

// mcause 결정
assign wb_trap_mcause = wb_sync_except ?
   {1'b0, 27'h0, mem_wb_except_code} :       // 예외: [31]=0
   {1'b1, 27'h0, irq_code};                  // 인터럽트: [31]=1

통합 플러시 로직

트랩이 발생하면, 파이프라인의 모든 명령어를 플러시해야 합니다. 분기 플러시(IF/ID, ID/EX만 클리어)와 달리, 예외 플러시는 전체 파이프라인을 클리어합니다. 


// ====== 통합 플러시 로직 ======
// 예외 플러시는 분기 플러시보다 우선
logic trap_flush;
assign trap_flush = wb_trap_taken;

// 파이프라인 레지스터별 플러시
assign flush_if_id  = trap_flush || branch_flush;
assign flush_id_ex  = trap_flush || branch_flush;
assign flush_ex_mem = trap_flush;
assign flush_mem_wb = trap_flush;

// PC 선택: trap_flush > branch_flush > 정상 PC+4
assign next_pc = trap_flush   ? trap_pc :
                 branch_flush ? branch_target :
                                pc_plus_4;

Ch12에서 확정한 플러시 우선순위에 예외가 추가됩니다: trap_flush > branch_flush > icache_stall > dcache_stall > load_use_stall

CSR 해저드: CSR 수정 중 인터럽트

마지막으로, CSR 명령어와 인터럽트 사이의 해저드를 다룹니다. 예를 들어 CSRRS mie, (1<<7)로 타이머 인터럽트를 활성화하는 도중에 timer_irq 신호가 도착하면 어떻게 될까요?

CSR 명령어의 결과는 WB 스테이지에서 실제로 반영됩니다. 따라서 인터럽트 샘플링도 WB 이후에 수행하면 CSR 값의 일관성을 보장할 수 있습니다.

  • 규칙: CSR 쓰기 명령어가 WB를 완료할 때까지 해당 CSR의 새 값을 인터럽트 판정에 사용하지 않는다.
  • 구현: 인터럽트 샘플링은 WB 스테이지의 CSR 업데이트 이후 1사이클 지연으로 수행한다.

// ====== CSR 해저드 방지: 인터럽트 샘플링 지연 ======
// CSR 쓰기 명령어가 WB에 있으면, 인터럽트 샘플링을 1사이클 지연
logic csr_write_in_wb;
assign csr_write_in_wb = mem_wb_csr_write;

// irq_sample_valid와 wb_async_irq는 위의 WB 트랩 커밋 섹션에서 정의됨:
//   assign irq_sample_valid = ~csr_write_in_wb;
//   assign wb_async_irq = irq_pending && irq_sample_valid && ~mem_wb_except;

이 코드의 사이클 단위 동작을 구체적으로 보겠습니다.

사이클 WB 스테이지 CSR 상태 인터럽트 판정
N CSRRS mie, x10 (WB 진입) mie = 이전 값 (MTIE=0) csr_write_in_wb = 1 → 샘플링 억제
N+1 CSRRS 커밋 완료 mie = 새 값 (MTIE=1) csr_write_in_wb = 0 → 새 mie 값으로 판정
N+2 다음 명령어 mie = 새 값 (MTIE=1) timer_irq 대기 중이면 인터럽트 수락

핵심은 Cycle N에서 irq_sample_valid = 0이므로, 아직 반영되지 않은 mie 값을 기반으로 인터럽트를 판정하는 오류를 방지한다는 것입니다. Cycle N+1이 되어야 CSR 쓰기가 실제로 반영되므로, 그때부터 정확한 판정이 가능합니다.

🎯 면접 포인트

"CSR 해저드란 무엇이며, 어떻게 해결하는가?" 핵심 답변: CSR 쓰기 명령어(CSRRS 등)가 WB 스테이지에 있을 때, 새 CSR 값이 아직 레지스터에 반영되지 않은 상태에서 인터럽트 판정을 수행하면 잘못된 결과가 발생합니다. 해결 방법: csr_write_in_wb 신호가 활성화된 동안 인터럽트 샘플링을 1사이클 억제합니다(irq_sample_valid = ~csr_write_in_wb). CSR 쓰기가 커밋된 후에야 새 값으로 인터럽트를 판정합니다.

이 절에서 다룬 통합 설계의 핵심을 면접 관점에서 정리합니다. 다음 두 질문은 시스템 설계 면접에서 가장 자주 등장하는 주제입니다.

🎯 면접 포인트

"정확한 예외(Precise Exception)란 무엇이며, 왜 중요한가?" 핵심 답변: 정확한 예외란 예외 발생 시 해당 명령어 이전은 모두 완료, 이후는 모두 취소된 상태를 보장하는 것입니다. 이것이 중요한 이유: 트랩 핸들러가 정확한 프로세서 상태를 바탕으로 예외를 처리하고 올바르게 복귀할 수 있어야 하기 때문입니다. 정확한 예외 없이는 디버깅이 불가능하고, 가상 메모리(page fault)도 구현할 수 없습니다.

🎯 면접 포인트

"파이프라인에서 동시에 두 개의 예외가 발생하면 어떻게 처리하는가?" 핵심 답변: 각 스테이지의 예외 정보를 파이프라인 레지스터에 태깅하여 WB까지 전파합니다. WB에서 "프로그램 순서상 가장 오래된 명령어"의 예외만 처리합니다. 나머지 예외는 트랩 플러시에 의해 자동으로 취소됩니다. 핸들러가 복귀하면 취소된 명령어가 재실행되어 필요 시 다시 예외가 발생합니다.

테스트 시나리오 4가지

다음 4가지 시나리오를 순서대로 검증합니다. 난이도가 점진적으로 증가하므로, 첫 번째부터 확실히 성공시키고 다음으로 넘어가십시오.

아래 시나리오 코드는 개념 설명용입니다. 각 시나리오가 독립적으로 핵심 동작을 보여주도록 단순화되어 있습니다. 실제 시뮬레이션에서는 이 장 끝의 전체 소스 코드(ch19_exception_tb.sv)의 task 기반 구조를 사용하십시오. 대응 관계: 시나리오 1 → test_ecall(), 시나리오 2 → test_load_misaligned(), 시나리오 3 → test_timer_interrupt(), 시나리오 4 → test_csr_hazard().

시나리오 1: ECALL 명령어 실행 (난이도 ★☆☆☆☆)

가장 단순한 예외입니다. ECALL 명령어를 실행하면 트랩 핸들러로 진입합니다. 


// ====== 시나리오 1: ECALL 테스트 ======
initial begin
   // 명령어 메모리 초기화
   imem[0] = 32'h00A00293;  // addi x5, x0, 10
   imem[1] = 32'h00000073;  // ecall
   imem[2] = 32'h00128293;  // addi x5, x5, 1 (복귀 후 실행)

   // mtvec 설정: 트랩 핸들러 주소
   force dut.csr_unit.mtvec = 32'h0000_0100;

   // 시뮬레이션 실행
   repeat(20) @(posedge clk);

   // 검증
   assert(dut.csr_unit.mepc == 32'h0000_0004)
      else $error("ECALL: mepc mismatch (expected 0x04)");
   assert(dut.csr_unit.mcause == 32'd11)
      else $error("ECALL: mcause should be 11");

   $display("=== Scenario 1: ECALL PASSED ===");
end

시나리오 2: Load Misaligned 예외 (난이도 ★★☆☆☆)


// ====== 시나리오 2: Load Misaligned 테스트 ======
// li x10, 0x0001    → x10 = 1 (홀수 주소)
// lw x11, 0(x10)    → Word 로드: addr[1:0] = 01 → 예외!
initial begin
   imem[0] = 32'h00100513;  // addi x10, x0, 1
   imem[1] = 32'h00052583;  // lw x11, 0(x10)  ← 비정렬!

   repeat(20) @(posedge clk);

   assert(dut.csr_unit.mcause == 32'd4)
      else $error("Load Misaligned: mcause should be 4");

   $display("=== Scenario 2: Load Misaligned PASSED ===");
end

시나리오 3: 타이머 인터럽트 (난이도 ★★★☆☆)


// ====== 시나리오 3: Timer Interrupt 테스트 ======
initial begin
   // mie.MTIE = 1, mstatus.MIE = 1 설정
   force dut.csr_unit.mie = 32'h0000_0080;     // 비트 7
   force dut.csr_unit.mstatus[3] = 1'b1;        // MIE

   // 정상 명령어 실행 중 인터럽트 발생
   imem[0] = 32'h00100093;  // addi x1, x0, 1
   imem[1] = 32'h00200113;  // addi x2, x0, 2
   imem[2] = 32'h00300193;  // addi x3, x0, 3

   // Cycle 5에서 timer_irq 활성화
   repeat(5) @(posedge clk);
   force timer_irq = 1'b1;

   repeat(10) @(posedge clk);

   // 검증: mcause[31]=1 (인터럽트), [3:0]=7 (타이머)
   assert(dut.csr_unit.mcause == 32'h8000_0007)
      else $error("Timer IRQ: mcause should be 0x80000007");

   // 검증: mepc = 다음 명령어 PC (현재 명령어 완료 후)
   $display("=== Scenario 3: Timer Interrupt PASSED ===");
   release timer_irq;
end

시나리오 4: CSR 해저드 (난이도 ★★★★☆)


// ====== 시나리오 4: CSR 해저드 테스트 ======
// CSRRS mie, (1<<7) 실행 중 timer_irq 도착
// → mie 업데이트 완료(WB) 후 인터럽트 샘플링 확인
initial begin
   // 초기: mie.MTIE = 0, mstatus.MIE = 1
   force dut.csr_unit.mie = 32'h0;
   force dut.csr_unit.mstatus[3] = 1'b1;

   // CSRRS mie, x10 (x10 = 0x80, 비트7 = MTIE)
   imem[0] = 32'h08000513;  // addi x10, x0, 0x80
   imem[1] = 32'h30452073;  // csrrs mie, x10   ← MTIE 활성화
   imem[2] = 32'h00000013;  // nop
   imem[3] = 32'h00000013;  // nop

   // CSRRS가 EX에 있을 때 timer_irq 도착
   repeat(3) @(posedge clk);
   force timer_irq = 1'b1;

   repeat(15) @(posedge clk);

   // 검증: CSRRS WB 완료 후에만 인터럽트 수락
   $display("=== Scenario 4: CSR Hazard PASSED ===");
   release timer_irq;
end

축하합니다. Part 7이 완성되었습니다. 여러분은 AMBA 버스(Ch16~17) 위에서 파이프라인 프로세서가 실행되고, CSR(Ch18)로 시스템 상태를 관리하며, 예외와 인터럽트(Ch19)로 비정상 흐름을 처리하는 — 완전한 프로세서 시스템을 이해하게 되었습니다. Part 8에서는 이 프로세서를 실제 FPGA 보드에 구현하여, 여러분이 만든 CPU 위에서 C 프로그램이 실행되는 것을 직접 눈으로 확인할 것입니다.

Ch16~Ch19 통합 신호 흐름

Part 7의 4개 챕터는 독립된 주제가 아니라, 하나의 시스템을 완성하는 연속적인 계층입니다. 다음 신호 흐름이 Part 7 전체를 관통합니다:

  1. Ch16 (AMBA AHB): 프로세서와 메모리/주변 장치를 연결하는 버스 인프라를 구축합니다. AHB의 버스트 전송과 중재 메커니즘이 모든 데이터 이동의 기반입니다.
  2. Ch17 (APB 주변 장치): AHB-APB 브리지를 통해 타이머(timer_apb)와 UART(uart_apb)를 연결합니다. 타이머가 timer_irq 신호를 생성합니다.
  3. Ch18 (CSR): timer_irq가 mip.MTIP 비트에 반영됩니다. mie, mstatus, mtvec, mepc, mcause가 인터럽트 판정과 트랩 처리의 상태 저장소 역할을 합니다.
  4. Ch19 (예외/인터럽트): 인터럽트 컨트롤러가 mie.MTIE & mip.MTIP & mstatus.MIE를 판정합니다. 트랩 발생 시 mepc/mcause 저장 + 파이프라인 플러시 + mtvec으로 점프합니다.

정확한 예외와 AMBA 일관성의 연결

정확한 예외(Precise Exception)가 왜 AMBA 버스 시스템에서 중요한지 생각해 봅시다. 만약 예외가 부정확하다면(imprecise), 트랩 핸들러가 실행될 때 AHB 버스 상의 미완료 트랜잭션(outstanding transaction)이 남아 있을 수 있습니다. 정확한 예외를 보장함으로써, 트랩 진입 시점에서 WB까지 완료된 명령어의 버스 트랜잭션은 모두 정상적으로 종료된 상태가 보장됩니다. 이것이 Part 8에서 FPGA에 합성할 때 시스템의 안정성을 보장하는 근거입니다.

Part 7 마일스톤: 타이머 인터럽트 기반 LED 깜빡임

Part 7의 모든 계층이 수렴하는 최종 마일스톤은 "타이머 인터럽트로 LED를 깜빡이는 것"입니다. 이 단순해 보이는 동작이 다음을 모두 요구합니다:

  • Ch16: AHB 버스를 통한 GPIO 접근
  • Ch17: APB 타이머가 주기적으로 timer_irq 생성
  • Ch18: CSR(mie.MTIE = 1, mstatus.MIE = 1) 설정
  • Ch19: 인터럽트 수락 → 트랩 핸들러에서 LED 토글 → MRET 복귀

Part 8(FPGA 구현)에서 이 마일스톤을 실제 보드에서 검증합니다.

🔍 스스로 점검

Part 7 전체를 종합 분석해 보십시오.

  • AMBA 버스: AHB(고속 버스) 위에 APB(저속 주변장치 브리지)를 연결하여 주변 장치 접근
  • 파이프라인: 5단계(IF/ID/EX/MEM/WB)에서 명령어가 동시에 실행
  • CSR: mstatus/mtvec/mepc/mcause 등으로 프로세서 시스템 상태 관리
  • 예외/인터럽트: 비정상 상황 발생 시 감지 → flush → mtvec으로 점프
  • 정확한 예외가 AMBA 일관성에 중요한 이유: WB까지 완료된 명령어의 버스 트랜잭션이 모두 종료되어야 트랩 핸들러가 안전하게 실행 가능

핵심 정리

  • 동기 예외는 명령어 실행과 동시에 발생하며(Illegal Instruction, Misaligned Access, ECALL), 각 스테이지에서 감지한 후 WB까지 전파하여 처리한다.
  • 비동기 인터럽트는 외부 신호에 의해 발생하며(Timer, External, Software), mip[N] & mie[N] & mstatus.MIE가 모두 1일 때 명령어 경계에서 수락한다.
  • 트랩 진입 시 하드웨어가 자동으로 mepc, mcause, mstatus를 저장하고 PC를 mtvec으로 변경한다. MRET으로 복귀 시 PC ← mepc, MIE ← MPIE로 복원한다.
  • 정확한 예외를 보장하려면 예외 정보를 WB까지 전파하고, WB에서 프로그램 순서상 가장 오래된 명령어의 예외만 처리한다.
  • 플러시 우선순위: trap_flush > branch_flush > icache_stall > dcache_stall > load_use_stall

연습문제

  1. [이해] 동기 예외와 비동기 인터럽트의 차이점을 3문장 이내로 설명하시오.
    정답 보기

    (1) 예외(동기)는 명령어 실행 중 발생하는 오류이고, 인터럽트(비동기)는 외부 장치에서 오는 신호이다. (2) 예외는 항상 즉시 처리해야 하지만, 인터럽트는 mstatus.MIE 비트로 수락/거절을 선택할 수 있다. (3) 둘 다 mtvec으로 점프하여 핸들러에서 처리된다.

  2. [이해] mcause = 0x8000_0007일 때, 이것이 예외인지 인터럽트인지 판별하고, 구체적으로 어떤 이벤트인지 답하시오.
    정답 보기

    mcause[31] = 1이므로 인터럽트이다. 하위 코드 7은 Machine Timer Interrupt(MTI)이다.

  3. [적용] Illegal Instruction 예외가 IF 스테이지에서 감지될 수 없는 이유를 설명하고, 실제 감지 스테이지와 그 근거를 제시하시오.
    정답 보기

    IF 스테이지는 메모리에서 명령어 비트 패턴을 가져올 뿐, 디코딩하지 않는다. 명령어가 유효한지 판단하려면 opcode/funct3/funct7을 해석해야 하므로, ID 스테이지에서 디코더가 인식하지 못하는 인코딩을 감지한다.

  4. [적용] Timer Interrupt가 발생했을 때, 프로세서가 인터럽트를 수락하기 위해 충족해야 하는 3가지 조건을 CSR 비트로 명시하시오.
    정답 보기

    (1) mip.MTIP = 1 (타이머 인터럽트 대기 중), (2) mie.MTIE = 1 (타이머 인터럽트 허용), (3) mstatus.MIE = 1 (전역 인터럽트 활성화). 세 조건이 모두 참일 때 인터럽트를 수락한다.

  5. [분석] 파이프라인에서 IF 스테이지의 명령어가 접근 오류 예외를 발생시키고, 동시에 EX 스테이지의 명령어가 주소 미정렬 예외를 발생시켰다. (a) 어떤 예외를 먼저 처리해야 하는지와 그 이유, (b) 나머지 예외의 처리 방법, (c) 이를 구현하기 위한 하드웨어 설계 고려사항을 서술하시오.
    정답 보기

    (a) EX 스테이지의 미정렬 예외를 먼저 처리한다. 프로그램 순서상 EX의 명령어가 IF의 명령어보다 먼저 실행된 것이므로, 정확한 예외 보장을 위해 먼저 발생한 예외를 우선한다. (b) IF의 명령어는 EX 예외 처리 시 플러시되므로 자연스럽게 취소된다. 핸들러가 복귀(MRET)하면 해당 명령어가 재실행되어 같은 예외가 다시 발생할 수 있다. (c) 각 스테이지에서 예외 신호를 파이프라인 레지스터에 태깅하여 WB까지 전파하고, WB에서 가장 오래된 명령어의 예외만 처리한다.

SVch19_exception_unit.sv


// ============================================================================
// 예외 처리 유닛 (Exception Unit)
// Chapter 19 — 예외/인터럽트와 파이프라인 통합
// ============================================================================
// 파이프라인 각 스테이지에서 발생하는 동기 예외를 감지하고,
// 비동기 인터럽트 수락 여부를 판정한다.
// WB 스테이지에서 최종 트랩 커밋을 수행한다.
// ============================================================================

`timescale 1ns / 1ps

module exception_unit (
   // --- 클럭/리셋 ---
   input  logic        clk,
   input  logic        rst_n,

   // --- ID 스테이지 예외 입력 ---
   input  logic        id_illegal_instr,
   input  logic        id_ecall,
   input  logic        id_ebreak,
   input  logic [31:0] id_pc,

   // --- WB 스테이지 전파 입력 ---
   // 참고: EX 스테이지 예외(Load/Store/Branch Misaligned) 태깅은
   // 파이프라인 레지스터 로직(top 모듈)에서 처리합니다.
   // 19.2절 인라인 코드의 EX/MEM 병합 로직을 참조하십시오.
   input  logic        mem_wb_except,
   input  logic [3:0]  mem_wb_except_code,
   input  logic [31:0] mem_wb_except_pc,
   input  logic [31:0] mem_wb_pc,
   input  logic        mem_wb_csr_write,

   // --- 비동기 인터럽트 입력 ---
   input  logic        ext_irq,
   input  logic        timer_irq,
   input  logic        sw_irq,

   // --- CSR 상태 입력 ---
   input  logic        mstatus_mie,
   input  logic        mie_meie,
   input  logic        mie_mtie,
   input  logic        mie_msie,
   input  logic [31:0] mtvec,

   // --- 출력: 트랩 제어 ---
   output logic        trap_taken,
   output logic [31:0] trap_pc,
   output logic [31:0] trap_mepc,
   output logic [31:0] trap_mcause,

   // --- 출력: 파이프라인 플러시 ---
   output logic        trap_flush,

   // --- 출력: 예외 전파 (파이프라인 레지스터 태깅) ---
   output logic        id_except_out,
   output logic [3:0]  id_except_code_out,
   output logic [31:0] id_except_pc_out
);

   // ====== ID 스테이지 예외 감지 ======
   assign id_except_out = id_illegal_instr || id_ecall || id_ebreak;
   always_comb begin
      if (id_ecall)
         id_except_code_out = 4'd11;
      else if (id_ebreak)
         id_except_code_out = 4'd3;
      else if (id_illegal_instr)
         id_except_code_out = 4'd2;
      else
         id_except_code_out = 4'd0;   // 예외 없음 (id_except_out=0이면 무시됨)
   end
   assign id_except_pc_out = id_pc;

   // ====== 인터럽트 판정 ======
   logic mei_pending, msi_pending, mti_pending;
   assign mei_pending = ext_irq   && mie_meie && mstatus_mie;
   assign msi_pending = sw_irq    && mie_msie && mstatus_mie;
   assign mti_pending = timer_irq && mie_mtie && mstatus_mie;

   logic        irq_pending;
   logic [3:0]  irq_code;

   always_comb begin
      irq_pending = 1'b0;
      irq_code    = 4'd0;
      if (mei_pending)      begin irq_pending = 1'b1; irq_code = 4'd11; end
      else if (msi_pending) begin irq_pending = 1'b1; irq_code = 4'd3;  end
      else if (mti_pending) begin irq_pending = 1'b1; irq_code = 4'd7;  end
   end

   // ====== WB 스테이지: 트랩 커밋 판정 ======
   logic wb_sync_except;
   logic wb_async_irq;
   logic irq_sample_valid;

   assign wb_sync_except   = mem_wb_except;
   assign irq_sample_valid = ~mem_wb_csr_write;
   assign wb_async_irq     = irq_pending && irq_sample_valid &&
                             ~mem_wb_except;

   assign trap_taken = wb_sync_except || wb_async_irq;
   assign trap_flush = trap_taken;

   assign trap_mepc = wb_sync_except ? mem_wb_except_pc :
                                       mem_wb_pc + 32'd4;

   assign trap_mcause = wb_sync_except ?
      {1'b0, 27'h0, mem_wb_except_code} :
      {1'b1, 27'h0, irq_code};

   assign trap_pc = {mtvec[31:2], 2'b00};

endmodule

SVch19_trap_controller.sv


// ============================================================================
// 트랩 컨트롤러 (Trap Controller)
// Chapter 19 — 트랩 진입/복귀 CSR 관리
// ============================================================================

`timescale 1ns / 1ps

module trap_controller (
   input  logic        clk,
   input  logic        rst_n,

   input  logic        trap_taken,
   input  logic [31:0] trap_mepc,
   input  logic [31:0] trap_mcause,

   input  logic        mret_instr,

   input  logic [31:0] csr_mtvec,
   input  logic [31:0] csr_mepc,
   input  logic [31:0] csr_mstatus,

   output logic        csr_we,
   output logic [11:0] csr_waddr,
   output logic [31:0] csr_wdata,

   output logic        pc_redirect,
   output logic [31:0] pc_next,

   output logic        pipeline_flush
);

   localparam CSR_MSTATUS = 12'h300;
   localparam CSR_MEPC    = 12'h341;
   localparam CSR_MCAUSE  = 12'h342;

   typedef enum logic [2:0] {
      S_IDLE,
      S_TRAP_MEPC,
      S_TRAP_MCAUSE,
      S_TRAP_MSTATUS,
      S_MRET_MSTATUS
   } state_t;

   state_t state, state_next;

   logic [31:0] saved_mepc;
   logic [31:0] saved_mcause;

   always_ff @(posedge clk or negedge rst_n) begin
      if (~rst_n) begin
         state        <= S_IDLE;
         saved_mepc   <= 32'h0;
         saved_mcause <= 32'h0;
      end else begin
         state <= state_next;
         if (state == S_IDLE && trap_taken) begin
            saved_mepc   <= trap_mepc;
            saved_mcause <= trap_mcause;
         end
      end
   end

   always_comb begin
      state_next     = state;
      csr_we         = 1'b0;
      csr_waddr      = 12'h0;
      csr_wdata      = 32'h0;
      pc_redirect    = 1'b0;
      pc_next        = 32'h0;
      pipeline_flush = 1'b0;

      case (state)
         S_IDLE: begin
            if (trap_taken) begin
               state_next     = S_TRAP_MEPC;
               pipeline_flush = 1'b1;
            end else if (mret_instr) begin
               state_next     = S_MRET_MSTATUS;
               pipeline_flush = 1'b1;
            end
         end

         S_TRAP_MEPC: begin
            csr_we    = 1'b1;
            csr_waddr = CSR_MEPC;
            csr_wdata = saved_mepc;
            state_next = S_TRAP_MCAUSE;
         end

         S_TRAP_MCAUSE: begin
            csr_we    = 1'b1;
            csr_waddr = CSR_MCAUSE;
            csr_wdata = saved_mcause;
            state_next = S_TRAP_MSTATUS;
         end

         S_TRAP_MSTATUS: begin
            csr_we    = 1'b1;
            csr_waddr = CSR_MSTATUS;
            csr_wdata = {csr_mstatus[31:13],
                         2'b11,
                         csr_mstatus[10:8],
                         csr_mstatus[3],
                         csr_mstatus[6:4],
                         1'b0,
                         csr_mstatus[2:0]};
            pc_redirect = 1'b1;
            pc_next     = {csr_mtvec[31:2], 2'b00};
            state_next  = S_IDLE;
         end

         S_MRET_MSTATUS: begin
            csr_we    = 1'b1;
            csr_waddr = CSR_MSTATUS;
            csr_wdata = {csr_mstatus[31:13],
                         2'b11,
                         csr_mstatus[10:8],
                         1'b1,
                         csr_mstatus[6:4],
                         csr_mstatus[7],
                         csr_mstatus[2:0]};
            pc_redirect = 1'b1;
            pc_next     = csr_mepc;
            state_next  = S_IDLE;
         end

         default: state_next = S_IDLE;
      endcase
   end

endmodule
