**권장 개선:**
```markdown
(20.1절 다음에 추가)

### 비유: 블랙박스는 "투명해질 수 있다"

실제로, Vivado는 합성 과정을 여러 로그 파일로 기록합니다:
- `synth_1.rpt` — 합성 리포트 (게이트 수, LUT 사용량)
- `utilization_placed.rpt` — 배치 후 리소스 사용률

**실무팁:** 합성 실패 시, 먼저 `synth_1.rpt`를 열어 "ERROR" 키워드를 검색하세요.
도구가 무엇을 거부했는지 명확히 나옵니다.
```

**효과:** 학습자의 무력감(블랙박스)을 주도권(투명화 가능)으로 전환.

<aside class="tip">
  <strong>💡 실무 팁: 타이밍 위반은 "정상"입니다</strong>
  <p>
    현업 FPGA 엔지니어들은 타이밍 위반을 "설계 완성 후 자동으로 정규 과정"으로 봅니다.

</aside>

### 불안 지점 4: "리소스 부족하면 설계가 못 들어가지 않을까?"

| 항목 | 평가 | 강화 필요 |
|------|------|----------|
| **현재 메시지** | "LUT 7.5%, BRAM 10%, FF 2.3%" (수치) | ✅ 명확함 |
| **안심 톤** | "여유가 많다" | ✅ 긍정적 |
| **최악 대처 메시지** | 없음 | ⚠️ 추가 권장 |

**권장 개선:**
```markdown
(20.4절 마지막에 추가)

### 만약 리소스가 부족하다면?

Basys 3의 현재 설계는 LUT, BRAM, FF 모두에서 여유가 있습니다.
하지만 만약 미래에 더 많은 기능(예: 부동소수점 연산, 더 큰 캐시)을 추가한다면?

**최악의 경우 대처 방법:**
1. **파이프라인 심화:** IMEM/DMEM 읽기를 2사이클로 분리 → LUTRAM 불필요, LUT 감소
2. **메모리 축소:** I-Cache 2KB → 1KB (히트율 약간 감소, LUT 30% 감소)
3. **FSM 최적화:** 바이너리 인코딩으로 FF 감소

이러한 대처들은 모두 "성능 약간 감소 vs 리소스 획기적 감소"의 거래입니다.
Basys 3의 광대한 리소스 여유 덕에, 대부분의 경우 문제가 되지 않습니다.
```

**효과:** "리소스 부족 두려움" → "최악의 경우도 대처 방법이 있다" (통제감 회복).

| **성공 확률** | ⭐⭐ (30~40%) — 추측 필요 |

**개선 방안:**
```markdown
(20.1절 "5가지 핵심 합성 옵션" 끝에 추가)

## 요약: 각 옵션의 효과

| 옵션 | 주효과 | 부효과 |
|------|--------|-------|
| Retiming | 속도 향상 | FF 증가, 디버깅 어려움 |
| FSM Encoding | 면적 감소(바이너리) / 속도 향상(원-핫) | 트레이드오프 선택 필요 |
| Keep Hierarchy | 부분 최적화 제어 | 전역 최적화 포기 |
| Gated Clock | 전력 절감 | 유용성 제한적 (FPGA) |
| Resource Sharing | 면적 감소 | 속도 저하 |

**핵심:** 면적 감소만 목표라면 FSM Encoding(바이너리), 속도 향상이 목표라면 Retiming을 선택하세요.
```

**개선 효과:** 문제 1의 정답(FSM Encoding 바이너리)이 명확해져, 학습자가 "내가 맞게 이해했나?" 확신을 얻음.
