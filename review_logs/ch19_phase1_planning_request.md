- 19.1 예외와 인터럽트의 개념: 1500~2500자
  - 부제: "파이프라인 실행 중 예상 밖의 일이 발생한다면?"

  - 내용: RISC-V 예외 타입(Illegal instruction, Memory access, Breakpoint 등), 인터럽트 소스(Timer, External, Software), mcause 맵핑

- 19.2 예외 처리 파이프라인: 2000~3000자
  - 부제: "파이프라인이 잠깐 멈추고 전환한다"

- 19.3 인터럽트 처리와 우선순위: 1500~2500자
  - 부제: "프로세서가 언제 인터럽트를 받아들일까?"
  - 내용: mie/mip 비트 매칭, Global Interrupt Enable (MIE), 우선순위 테이블
  - 포함: Timer interrupt 시뮬레이션 시나리오, Race condition 방지

- 19.4 본 장 요약 및 Part 7 정리: 1000~1500자
  - 내용: 예외/인터럽트 흐름도, Part 7(AMBA+CSR+예외) 통합 이해, Part 8(FPGA 구현) 예고

#### 4. 주요 비유 개발
- **예외 ≈ "프로그램 실행 중 오류 발생"**: 파이썬 코드 실행 중 ValueError 발생
  - 한계 명시: "소프트웨어 예외는 스택 추적을 출력하지만, 하드웨어 예외는 즉시 핸들러로 점프"

- **인터럽트 ≈ "전화 중 긴급 전화 받기"**: 현재 일을 잠깐 멈추고 처리
  - 한계 명시: "전화와 달리, 프로세서는 '거절할 수도' 있다 (MIE 비트로 제어)"

- **flush ≈ "파이프라인의 모든 명령어 삭제"**: 음료 흐르는 통로에서 불순물 제거
  - 한계 명시: "실제로는 valid 비트를 끄는 것이지, 물리적으로 삭제하지는 않음"

#### 5. 본 장 특별 주의사항
- Ch18(CSR) 복습 필수: mtvec, mepc, mie, mip, mcause 역할
- 예외와 인터럽트는 개별 처리가 아니라 "통합 흐름"으로 학습
- Part 7 마일스톤: AMBA 버스(Ch16~17) + CSR(Ch18) + 예외 처리(Ch19) 통합

#### 2. 학습 흐름 설계

**도입** (호기심 유발):
- 질문: "프로세서가 실행 중에 문제가 생기면 어떻게 될까?"
- 실제 예제: "프로그래머가 실수로 0으로 나누거나, 존재하지 않는 주소에 접근하면?"

**개념** (단계적 확대):
1. 예외와 인터럽트의 정의 및 구분
2. RISC-V 예외 타입 (16개, mcause 코드)

4. 파이프라인 각 스테이지에서의 예외 처리

**예시** (구체적 시나리오):
- "Illegal instruction 예외 발생 → 파이프라인 flush → mtvec으로 점프"
- "Timer interrupt 신호 → mie/mip 확인 → 처리 가능하면 예외처럼 처리"

**실습** (동작 검증):
- 시뮬레이션: Illegal instruction 예외 발생 및 처리
- 테스트벤치: Timer interrupt 시나리오 검증

**정리** (통합 학습):
- Part 7(AMBA+CSR+예외) 통합 시스템 이해
- "다음은 Part 8에서 FPGA에 실제로 구현할 것"

#### 3. 인지 부하 분석

**신규 개념** (절당 평균 3~4개):
- 19.1: 예외(新) + 인터럽트(新) + 16개 타입(新) = 3개
- 19.2: flush 메커니즘(新) + 파이프라인 적용(新) = 2개
- 19.3: 인터럽트 우선순위(新) + mie/mip 매칭(새로운 활용) = 2개
- 19.4: 종합 분석(누적) = 0개 신규

**인지 부하 완화**:
- 예외 타입 16개 외우기 금지 → 참조 테이블 제공
- mcause 코드 암기 금지 → 프로세서가 자동으로 생성
- 파이프라인 5단계 × 예외 감지 = 직교적 이해 (각 단계별 1가지만)

#### 4. 연습문제 설계 (총 5개, L2~L4 분포)

**L2 (이해)**:
1. "예외와 인터럽트의 차이점을 3문장으로 설명하시오"
   - 정답: 예외는 명령어 실행 중 오류/트랩, 인터럽트는 외부 신호. 예외는 항상 처리, 인터럽트는 MIE로 제어 가능. 모두 mtvec으로 점프.

2. "mcause[31]=1일 때 의미하는 바는?"
   - 정답: 인터럽트 (vs 예외). 나머지 비트는 인터럽트 번호.

**L3 (적용)**:
3. "Illegal instruction 예외가 IF 스테이지에서 감지될 수 없는 이유는?"
   - 정답: IF는 메모리에서 명령어를 가져올 뿐, 디코딩하지 않음. ID 스테이지에서 명령어 형식 검사.

4. "Timer interrupt와 Software interrupt를 동시에 받으면 우선순위는?"
   - 정답: Timer interrupt (우선순위 7) > Software interrupt (우선순위 3). 우선순위 인코더로 판정.

**L4 (분석)**:
5. "파이프라인 flush 중에 새로운 예외가 발생하면 어떻게 처리할까? 이를 방지하기 위한 설계 고려사항은?"
   - 정답: flush 신호가 활성일 때는 새 예외 신호를 무시하거나, mepc를 flush 이전 값으로 유지. 우선순위: 먼저 발생한 예외가 우선.

#### 5. 학습 흐름의 "점프 포인트" 관리

- 19.1 끝 → 19.2 시작: "이제 이 예외/인터럽트들이 파이프라인 내에서 어떻게 처리되는지 배울 것"
- 19.2 끝 → 19.3 시작: "예외는 항상 처리하지만, 인터럽트는 선택적이다. 이제 그 선택 메커니즘을 배울 것"
- 19.3 끝 → 19.4 시작: "개별 컴포넌트(파이프라인, AMBA, CSR, 예외)를 모두 배웠다. 이제 이들을 통합하는 방법을 배울 것"

## Teammate 3: 교육심리전문가 (Educational Psychologist)

### 임무
불안 관리 및 감정 곡선 설계

### 요청사항

#### 1. 불안 지점 식별

**A. 추상성과 시각적 이해 어려움 (매우 높음)**
- 파이프라인 + 예외 신호 = 동시성의 개념
- 지금까지는 "순차적 명령어"였는데, 이제는 "5개 명령어가 동시에 움직이며 예외까지 처리"
- 학습자: "이게 정말 한 사이클에 일어나는 거야?" → 혼동

**B. 파이프라인 복잡도 증가 (높음)**
- 이미 배운 파이프라인에 flush, 우선순위, 타이밍이 추가됨
- 학습자: "또 다시 FSM을 배워야 해?" → 피로감

**C. 예외 타입의 정보 과부하 (중간)**
- 16개 예외 타입과 11개 인터럽트 소스 = 27개 케이스
- 학습자: "모두 다 외워야 하나?" → 불안

**D. 실무 연관성 불명확 (중간)**
- 프로세서 설계자 입장: "왜 예외를 처리해야 할까?"
- 학습자: "이게 실제로 어디에 쓰이지?" → 동기 상실

#### 2. 감정 곡선 설계 (호기심 → 불안 → 이해 → 성취감)

**호기심** (도입, 19.1):
- 장면: "당신이 프로세서라면, 실행 중 문제가 생겼을 때 '무시'할 수 있을까? 아니면 '대응'해야 할까?"
- 연결: "프로세서도 마찬가지다. 예외를 감지하고 처리하는 방법을 배우자"
- 감정: 호기심 + 현실성

**불안** (19.2, 파이프라인 복잡도):
- 장면: "아, 파이프라인 5단계 모두에서 예외를 감지해야 한다고?"
- 원인: 동시성 개념 + flush 메커니즘 + 우선순위
- 감정: 초기의 호기심이 불안으로 전환

**이해** (19.2 중반~19.3, 구체적 예시):
- 장면: "아, flush는 결국 valid 비트를 끄는 것이고, 예외 우선순위는 단순한 우선순위 인코더군"
- 이유: 단계별 예시 + 타이밍 다이어그램으로 시각화
- 감정: 불안에서 "아!" 순간의 이해로 전환

**성취감** (19.3~19.4, 통합 이해):
- 장면: "Part 7이 모두 연결되었다! AMBA 버스 위에서 파이프라인이 실행되고, 예외가 발생하면 CSR에 저장되고, 인터럽트로 처리된다!"
- 경험: 5개 장의 개념을 하나의 시스템으로 이해 → 자기효능감 급상승
- 감정: "나도 이제 프로세서 설계자처럼 생각한다"

#### 3. 안심 장치 제시

**메시지 1** (도입에 포함):
"이 장에서는 16개 예외와 11개 인터럽트를 모두 외울 필요가 없습니다. 대신, '어떤 상황에서 예외가 발생하고, 프로세서가 어떻게 대응하는지'의 흐름을 이해하세요. 세부 사항은 참조 테이블을 보면 됩니다."

**메시지 2** (19.2 시작에 포함):
"지금부터 파이프라인에 flush를 추가합니다. 이미 배운 파이프라인이 약간 더 복잡해지는 것이지, 새로운 개념이 아닙니다. '어느 스테이지에서 예외를 감지하는가'만 명확히 하세요."

**메시지 3** (19.2 중반):
"타이밍 다이어그램을 보세요. 예외 발생 → flush → 새 PC 로드는 단 4 사이클입니다. 매우 빠른 처리입니다."

**메시지 4** (19.3 시작에 포함):
"인터럽트는 예외와 거의 같은 메커니즘을 따릅니다. 차이점은 하나: MIE 비트로 '받아들일지 말지' 선택할 수 있다는 것뿐입니다."

**메시지 5** (19.4 시작에 포함):
"이제 Part 7이 완성됩니다. AMBA 버스 위에서 파이프라인이 실행되고, CSR로 제어되고, 예외/인터럽트로 흐름을 제어합니다. Part 8에서는 이 모든 것을 FPGA에 구현할 것입니다."

#### 4. 첫 성공 경로 설계

**1단계: 예외 감지 (가장 쉬움, 성공 보장)**
- 작업: Illegal instruction 신호 생성 (테스트벤치)
- 난이도: ★☆☆☆☆
- 성공 척도: "예외 신호가 정말 생성되었다"
- 심리: "아, 예외도 그냥 신호구나"

**2단계: flush 실행 (중간)**
- 작업: 예외 신호 → flush 신호 → 파이프라인 정지 확인
- 난이도: ★★☆☆☆
- 성공 척도: "파이프라인이 정말 정지했다"
