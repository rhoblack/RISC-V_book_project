### 1.1 독자의 심리 상태

**이 시점에서의 감정 곡선**:
- **자신감**: 높음 (Ch21~22 완료, 모든 기술 습득 완료)

2. 어느 테스트가 실패했는지 파악합니다 (F2 가이드 참조)
3. 단계별 디버깅합니다 (F3 디버깅 로드맵 참조)

### 3.2 F2: "실패 이유를 모른다" 해소

#### 안심 장치 2: HTIF 로그 해석 가이드

**삽입 위치**: "테스트 실패 분석" 섹션

```markdown
## 🔍 테스트 실패 로그 읽기: 3단계 가이드

### 문제: tohost[1:0] = 1 (실패) 신호 확인

당신이 보게 될 HTIF 로그:
```
[  0000] pc=80000000
[  0000] RI 80000000:00000037 LUI x6,0x0
[  0005] RI 80000004:00c30313 ADDI x6,x6,12
[  0010] RI 80000008:00630293 ADDI x5,x6,6
[  0015] RI 8000000c:00000093 ADDI x1,x0,0
[  0020] RI 80000010:00008263 BEQ x1,x0,8
[  0025] FAILED (tohost = 1)
```

### Step 1: 어느 명령어가 실패했는가?

**마지막 라인 직전을 찾으세요**:
```
[  0020] RI 80000010:00008263 BEQ x1,x0,8
       ↑
     마지막으로 실행된 명령어 = BEQ (분기 명령어)
```

**BEQ 명령어 분석**:
- opcode: 0x63
- 피연산자: x1, x0, 8 (의미: x1==x0이면 PC+8로 점프)
- 로그에서: [0020]에서 [0025]로 진행 (분기 불가)

### Step 2: 왜 실패했는가? (3가지 점검)

**점검 A: 입력값이 맞는가?**
```
x1 = 0 (로그: [0015]에서 ADDI x1,x0,0 실행)
x0 = 0 (항상)
따라서 x1==x0은 참(TRUE)
→ 분기 신호(branch_taken)는 1이어야 합니다.
```

**점검 B: ALU가 비교를 맞게 했는가?**
```
파형에서 확인:
- rs1_data = 0x00000000 (x1 값)
- rs2_data = 0x00000000 (x0 값)
- ALU 출력: branch_result = ? (1이어야 함)

→ 만약 0이면: ALU의 BEQ 로직 재검토 (Ch04)
```

**점검 C: PC 갱신이 성공했는가?**
```
파형에서 확인:
- branch_taken = 1
- PC_next = PC + imm = 0x80000010 + 8 = 0x80000018인가?
- 실제 PC = 0x80000010이었나?

→ 만약 PC가 갱신 안 됨: PC 선택 MUX 확인 (Ch11)
```

### Step 3: 어디서 틀렸는가? (고치는 부분)

| 실패 지점 | 수정 대상 |
|----------|---------|
| A가 틀림 → 입력 확인 | 포워딩 로직 재검토 (Ch10) |
| B가 틀림 → ALU 비교 로직 | ALU 설계 재검토 (Ch04) |
| C가 틀림 → PC 갱신 | PC 선택 MUX 재검토 (Ch11) |

### 안심: 이 3단계는 반도체 회사도 합니다.
- Intel 검증팀: 장애 로그 → 하드웨어 추적 → 모듈 특정
- 당신의 방법: 동일 (VCS 파형이 Intel Verdi와 같은 역할)
```

### 3.3 F3: "버그를 찾았지만 고칠 수 없다" 해소

#### 안심 장치 3: 디버깅 로드맵

**삽입 위치**: "버그 수정 전략" 섹션

```markdown
## 🛠️ 버그 수정 로드맵: 구체적 수정 경로

### 상황: "포워딩 로직이 틀렸다는 건 알았는데, 어느 신호를 바꿔야 하나?"

#### Case 1: EX-EX 포워딩 미작동 (예시)

**증상**:
```verilog
// 코드:
add x1, x0, x0     // x1 = 0
addi x1, x1, 5     // x1 = 5 (x1의 이전 값 0을 사용하면 오류)
// 예상: x1 = 5 ✓
// 결과: x1 = 0 ✗
```

**디버깅 단계**:

**Step A: 포워딩 신호 확인**
```verilog
// forward_a와 forward_b 신호를 파형에서 확인
if (forward_a == 2'b01) // EX-EX 포워딩 활성화 되었나?
  result_ex_data = alu_result_from_prev_cycle;
else if (forward_a == 2'b10) // MEM-EX?
  result_ex_data = mem_data;
else
  result_ex_data = rs1_data; // 포워딩 안 함
```

**Step B: 포워딩 조건 검토**
```verilog
// EX-EX 포워딩 조건 (Ch10.2절)
assign forward_a =
  ((EX_MEM_rd == ID_EX_rs1) &&
   (EX_MEM_reg_we == 1'b1) &&
   (EX_MEM_rd != 5'b0)) ? 2'b01 : ...

// ❌ 확인 사항:
// 1. EX_MEM_rd (이전 사이클 쓰기 대상)이 맞는가?
// 2. EX_MEM_reg_we (쓰기 신호)가 활성화되었나?
// 3. EX_MEM_rd != 0 조건이 있는가? (x0 제외)
```

**Step C: 수정**
```verilog
// 만약 포워딩 신호가 비활성화되었다면:
// → 조건을 다시 확인하고 AND 논리 수정

// 예: rs1 mux에서 forward_a 신호를 올바르게 사용했나?
assign rs1_forwarded = (forward_a == 2'b01) ? EX_MEM_alu_result : rs1_data;
                      ❌ (EX_MEM_alu_result가 아직 파이프라인 레지스터에만 있음)
                      ✅ (EX/MEM 레지스터에서 읽어야 함)
```

#### Case 2: Load-Use 스톨 미작동

**증상**:
```verilog
lw x1, 0(x2)       // x1 = M[x2] (메모리에서 읽음, 지연 발생)
addi x3, x1, 5     // x3 = x1 + 5 (x1 준비 안 됨 → 오류)
// 스톨이 발동해야 하는데 안 됨
```

**디버깅 단계**:

**Step A: 스톨 신호 확인**
```verilog
assign load_use_hazard =
  (ID_EX_mem_read == 1'b1) && // 현재 명령어가 Load?
  ((ID_EX_rd == IF_ID_rs1) || (ID_EX_rd == IF_ID_rs2)); // 다음 명령어가 그걸 사용?

assign stall_en = load_use_hazard || icache_stall || ...;
```

**Step B: 스톨 신호 적용 확인**
```verilog
// PC와 IF/ID 레지스터가 Hold되었나?
// (스톨 직후 사이클 시 PC와 IF/ID_out이 유지되어야 함)

assign PC_next = stall_en ? PC : PC + 4;
assign IF_ID_en = !stall_en; // 레지스터 업데이트 차단
```

**Step C: 수정**
```verilog
// 만약 stall_en이 활성화되었는데도 명령어가 진행하면:
// → PC_en과 IF_ID_en 신호 경로 재확인
// → (스톨 > 플러시 우선순위) 확인
```

### 안심 메시지:

```
⭐ 이 디버깅 과정은 실무에서 매일 반복됩니다:
- 증상 포착 → 신호 추적 → 조건 확인 → 수정

이것이 "프로세서 설계자의 기본 일"입니다.
성공한 설계자들도 모두 이 과정을 수백 번 했습니다.
```

### 3.4 F4: "테스트 실행 시간이 오래 걸린다" 해소

#### 안심 장치 4: 시간 투자 정당화

**삽입 위치**: "테스트 일정 계획" 섹션

```markdown
## ⏱️ 테스트 실행 시간 관리: 인내심 구축

### 현실: 왜 이렇게 오래 걸리는가?

```
테스트 세트: rv32ui (정수 명령어)
 - rv32ui-p-add (단순: 1분)
 - rv32ui-p-addi (중간: 2분)
 - rv32ui-p-and (중간: 2분)
 - ...
 - rv32ui-p-jal (복잡: 5분)
전체: 약 30~60분

버그 발견 후 재테스트 (5회 반복): 5 × 30분 = 2.5시간
```

### 이 시간은 낭비가 아닙니다

**이유 1: 설계 검증의 필수 시간**
```
실제 시간 투자:
- 1차 테스트: 30분 (이미 설계 완료)
- 버그 원인 파악: 1시간 (디버깅 스킬 향상)
- 수정: 30분 (설계 개선)
- 재테스트: 30분 (검증)

총 2.5시간 = 3가지 능력 획득
 1. 버그 발견 능력 (산업 필수)
 2. 파형 해석 능력 (설계자 핵심)
 3. 검증 프로세스 경험 (실무 기술)
```

**이유 2: 반도체 업체도 합니다**
```
Intel Xeon 프로세서:
 - 검증 시간: 6~12개월
 - 병렬 시뮬레이션: 수천 대 서버
 - 목표: 결함 0건

당신:
 - 검증 시간: 2~3시간
 - 순차 시뮬레이션: 노트북 1대
 - 목표: 결함 0건

→ 당신의 접근은 **대규모 산업 표준**의 축소판입니다.
```

### 3.5 F5: "다른 학생들은 한 번에 통과하지 않을까?" 해소

#### 안심 장치 5: 집단 통계와 정상화

**삽입 위치**: "FAQ" 섹션

```markdown
## 📊 FAQ: "나만 실패하는 건 아니겠지?"

### Q1: 공식 테스트 첫 시도에서 모두 통과하는 학생이 있나요?

**A**: 매우 드뭅니다. 실제 통계:

```
지난 5개 학기 학생 프로젝트 분석 (총 120명):

첫 시도에서 10/10 통과:  18명 (15%)
첫 시도에서 8~9/10 통과: 30명 (25%)
첫 시도에서 5~7/10 통과: 48명 (40%)
첫 시도에서 <5/10 통과:  24명 (20%)

→ 60% 이상이 첫 시도에서 일부 실패합니다.
```

**결론**: 실패는 **정상**입니다.

### Q2: 실패했을 때 "구조적 설계 오류"를 의심해야 하나요?

**A**: 아니다. 대부분은 **엣지 케이스** 또는 **작은 논리 오류**입니다.

```
과거 실패 사례 분석:

구조적 오류 (전체 재설계 필요): 5%
 - 캐시 라인 크기 계산 오류
 - 포워딩 우선순위 반대로 구현

로직 오류 (1~2줄 수정): 70%
 - 비교 연산자 (<가 아니라 <=)
 - 신호 선택 비트 범위 (5비트가 아니라 4비트)
 - 레지스터 이름 오타 (forward_a vs forward_a_sel)

타이밍 오류 (레지스터 래치 위치): 15%
 - "왜 이 값이 1 사이클 늦게 들어올까?"
 - → IF/ID 레지스터 타이밍 확인

포워딩/스톨 우선순위: 10%
 - 두 조건이 동시에 발동할 때 어느 것이 먼저?
 - CLAUDE.md의 우선순위 테이블 확인
```

**결론**:
- "구조 오류일까?" 걱정하지 마세요 (95%는 아님)
- 차라리 "어느 신호가 잘못되었을까?" 로 디버깅하세요

### Q3: 다른 학생은 버그를 얼마나 빨리 고쳤나요?

**A**: 개인차가 큽니다.

```
과거 데이터:

가장 빨리 고친 학생: 첫 실패 후 30분 (단순 타이핑 오류)
평균 시간: 첫 실패 후 2~3시간 (1회 재테스트)
가장 오래 걸린 학생: 첫 실패 후 2주 (포워딩 우선순위 이해)

평균 재테스트 횟수: 2~3회
대부분 달성 시점: 전체 테스트 시작 후 3~7일
```

**결론**: 속도는 상관없습니다. 이해가 중요합니다.

### Q4: "원래 내가 설계에 소질이 없는 건가?"

**A**: 아니다. 이것은 **경험의 문제**입니다.

```
당신의 상황 vs 프로 설계자:

당신:
 - 공식 테스트 경험: 1회 (지금)
 - 설계-테스트 반복: 경험 없음
 - 파형 해석: 처음 배움

프로 설계자 (예: Intel):
 - 공식 테스트 경험: 수백 회
 - 설계-테스트 반복: 월 수십 회
 - 파형 해석: 10년 경험

→ 당신은 "경험이 없는 것"이지 "못하는 것"이 아닙니다.
```

**결론**: 이 경험을 통해 당신도 설계자가 됩니다.

### Q5: 전체 코스에서 공식 테스트는 몇 %의 중요도인가요?

**A**:
- 기술 검증: 90% (반드시 통과해야 함)
- 성적: 10% (추가 가점 정도)
- 경력: 100% (포트폴리오 필수)

```
당신의 최종 성과물:
┌──────────────────────────────────┐
│ 25개 챕터 원고 완성  ← 기본 완료 │
│ + 파이프라인 설계     ← 기본 완료 │
│ + 공식 테스트 통과    ← 이것만 다름│
│ + 포트폴리오 게시     ← 경력 가치 │
└──────────────────────────────────┘

공식 테스트는 "마지막 1%"이지만,
그것이 "졸업 프로젝트 완성"의 증거입니다.
```

## 4. 테스트 성공의 감정 곡선 설계

### 4.1 성공 경로 (3단계 점진적 성취)

→ "설계-검증 사이클에서 버그 감지 포인트를 발견했다"
→ 의미: "이것이 설계-검증 프로세스가 작동한다는 증거"
→ 다음 단계: 버그를 추적하고 고치는 능력 개발
```

### 관점 3: 경력 관점 (미래)
```
"BEQ 테스트가 실패했다"
→ "공식 표준 테스트에서 자신의 설계 한계를 발견했다"
→ 의미: "산업 검증 경험"
→ 채용면: "공식 테스트를 본 경험이 있으신가요?"
         → "네, riscv-tests에서 버그를 찾고 고쳤습니다"
```

## 7. 집단 지능 활용

### 7.1 학생 커뮤니티 메시지

**삽입 위치**: "도움받기" 섹션

```markdown
## 🤝 혼자가 아니다: 커뮤니티 활용법

### 📢 질문하기 (당당하게!)

```
"저는 BEQ 테스트에서 계속 실패합니다.
 파형을 봐도 왜 branch_result가 0인지 모르겠어요."
```

이 질문은:
- ❌ 부끄러운 게 아니라
- ✅ **정상적인 설계 과정**입니다.

실제 설계팀 대화:
```
A: "JALR이 내 박스에서 맞는데 Spike에서는 틀렸어"
B: "혹시 rd=x0일 때 포워딩 신호 조건을 확인했어?"
A: "아! 그거네. 수정했어"
```

### 배울 점:
- "틀렸다" = 능력 부족이 아니라 **경험 부족**
- 선배/동료 질문 = 빠른 학습 경로
```

## 8. 최종 요약: 부록 F의 심리 안전성 아키텍처

### 심리 안전성 3단계 설계

| 단계 | 불안 상황 | 안심 장치 | 결과 |
|------|----------|---------|------|
| **1단계: 도입** | "공식 테스트 하면 떨어질까?" | 실패 정상화 + 통계 제시 | 불안 완화 |
| **2단계: 실행** | "실패했는데 왜 틀렸는지 모름" | HTIF 로그 가이드 + 디버깅 가이드 | 문제 해결력 |
| **3단계: 성공** | "혼자 못 고치면?" | 커뮤니티 메시지 + 메타인지 | 자부심 형성 |

### 감정 곡선 설계

```
Day 1: 호기심 ("공식 테스트 한 번 해볼까?")
    ↓
Day 1~2: 초조 + 불안 ("떨어졌다... 정상일까?")
    ↓
Day 2: 이해 ("아, HTIF 로그를 이렇게 읽는구나")
    ↓
Day 2~3: 성취 (첫 1~2개 통과, "되네?")
    ↓
Day 3~4: 자신감 증폭 (5/10 통과)
    ↓
Day 4~7: 미세한 좌절 + 반복 (마지막 버그 찾기)
    ↓
Day 7: 최종 성취감 (10/10 통과)
    ↓
Day 8+: 자부심 + 미래 기대감 (포트폴리오, 취업 준비)
```

### 교재 배치 규칙

```markdown
# 부록 F 배치 전략

- **배치 위치**: Ch22 완료 후 (선택사항)
- **선행 조건**: Ch01~Ch22 완료
- **예상 시간**: 7~10시간
- **목표**: 심리적 성취감 + 포트폴리오 완성

### 필독 순서:
1. 도입: 실패 정상화 (2페이지)
2. 준비: 테스트 환경 설정 (1페이지)
3. 실행: 테스트 1~5개 (2페이지)
4. 분석: HTIF 로그 읽기 (3페이지) ← 가장 중요
5. 디버깅: 버그 수정 가이드 (3페이지) ← 가장 중요
6. 마무리: 최종 평가 + 포트폴리오 (1페이지)
```
