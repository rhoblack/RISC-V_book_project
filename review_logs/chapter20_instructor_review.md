```
"합성은 SystemVerilog 코드를 FPGA 프리미티브(LUT, FF 등)의 네트리스트로 변환하는 단계입니다."
→ ✅ 명확하고 간결함. 강의에서 그대로 사용 가능.

"구현은 생성된 네트리스트를 실제 FPGA 칩의 물리 위치에 배치하고 신호 경로를 라우팅하는 단계입니다."
→ ✅ 명확함. 학생들이 즉시 구분 가능.
```
**평가**: ✅ **강의 품질 우수**
- 개념이 3단계로 명확함: RTL 코드 → 네트리스트 → 물리 배치
- 각 단계의 책임이 명확함
- 학생들이 Vivado GUI와 바로 연결 가능

#### 20.2절: "create_clock: 기준 클록 정의"
**설명 단계:**
```
"period 10"은 주파수 100MHz(=1000/10 ns)를 의미합니다.
```
**문제점**:
- 학생 질문: "왜 1000으로 나누나?" (ns→MHz 변환 이유 명시 필요)
- 개선 제안:
```
"period 10"은 10ns를 의미합니다. 이는 주파수로는 1/(10ns) = 1/10^-8s = 100MHz입니다.
또는: 1ns = 10^-9s이므로, 1000MHz = 1ns 주기, 따라서 period[ns] = 1000 / freq[MHz]
```
**평가**: ⚠️ **명확하지만 변환 이유 설명 부족**

#### 20.3절: "Slack 개념"
**정의:**
```
Slack = 제약 지연 - 실제 지연
```
**평가**: ✅ **명확함**
- 하지만 WNS/TNS 약자 설명 부족
- WNS(Worst Negative Slack): 가장 나쁜 음수 slack
- TNS(Total Negative Slack): 모든 위반 경로의 합
- 💡 **강사 팁**: "WNS < 0이면 최소 1개 경로가 실패, TNS는 전체 위반량 합"

#### 20.5절: "최적화 사례: 45MHz → 60MHz"
**학생 예상 질문:**
1. "왜 기본 45MHz인가?" → 명시 부재
2. "Retiming 후 왜 52MHz인가?" → 무작위처럼 보임
3. "FSM Encoding이 3MHz 개선?" → MUX와 FSM의 관계 불명확

**평가**: ⚠️ **진행 명확하지만 인과관계 약함**
- 개선안: "각 Step 후 어느 경로가 개선되었는가?" 명시
- Step 1 → "MUX 지연 4.2ns → 3.5ns로 0.7ns 개선"
- Step 2 → "FSM 디코더 지연 1.2ns → 0.9ns로 0.3ns 개선"

### 2.2 비유 2: "도로 공사의 신호등" (20.3절 Slack)

| 기준 | 평가 | 증거 | 피드백 |
|------|------|------|--------|
| ① 사실과의 매핑 | ⚠️ **부분 정확** | 신호등 주기 60초(제약) vs 통과 시간 65초(실제) | 💡 매핑 주의: "신호등 주기"≠"제약 지연" (개념 혼동 우려) |
| ② 한계 명시 | ✅ **적절** | "온도, 공정편차, 전압에 따라 변함" | 프로세스 편차 반영됨 |
| ③ 오해 유발 여부 | ⚠️ **가능성 있음** | "signal slack"을 도로 신호와 혼동할 여지 | 용어 "signal slack" vs 도로 "신호등"의 혼동 위험 |
| ④ 대안 비유 | 💭 **제안** | 현재: 없음 | "비행기 활주로 이착륙 시간 버짓" 더 정확할 수도 있음 |

**결론**: ⚠️ **비유 개선 권장**
- **문제점**: "신호등 주기"와 "제약 지연"의 개념 매핑이 완벽하지 않음
  - 신호등은 "시간 윈도우"인데, Slack은 "시간 차이"
  - 용어 "신호등"이 "signal"과 혼동 가능

- **개선안**:
```
현재: "신호등 주기가 60초(제약)이지만, 실제 교차로 통과 시간이 65초(실제 지연)면..."
개선: "도로 정체에서 신호등 회전 시간이 60초(제약)인데, 차량을 모두 통과시키려면
      실제로 65초(실제 지연)가 필요하다면, 신호등을 5초 더 길게(slack=-5초) 설정해야 합니다."
```

- **대안 비유** (선택):
```
"비행기 활주로 이착륙": 공항에서 "도착 예상시간 오후 3:00(제약)"인데,
"실제 착륙에 3:05(실제 지연)"가 필요하면, slack=-5분으로 활주로 부족.
```

### 3.1 Top 1: set_multicycle_path 2 vs 1 차이

**문제**: TCL 코드
```tcl
set_multicycle_path 2 -setup ...
set_multicycle_path 1 -hold ...
```
"2와 1이 왜 다른가?"

**현재 원고**: 주석 부재
```
# Setup: 2 cycles (WB에서 시작 → ID에서 래치)
# Hold: 1 cycle
```

**학생 막힘 원인**: "왜 setup은 2인가?" 이유 불명확

**권장 설명 추가**:
```
Set_multicycle_path의 -setup과 -hold 차이:
- setup: 신호가 FF D입력에 도달하는 데 걸리는 클록 수 (스크래치→register 쓰기까지)
- hold: 같은 신호가 FF D입력에서 안정적으로 유지되어야 하는 시간

타이밍 다이어그램:
Cycle 0: WB에서 csr_we_reg 출력 (1사이클 지연)
Cycle 1: mie_reg[*] D입력에 도달 (setup 체크: 2사이클 전체)
Cycle 2: mie_reg[*] 클록 에지에서 래치 (hold 체크: 1사이클)

따라서: setup=2 (WB→ID 1사이클 + 래치까지 1사이클), hold=1 (래치 직후)
```

### 3.2 Top 2: Retiming 정확성 증명

**문제**: "FF를 옮기면서 동작이 정확한가?"

**현재 원고**:
```
"Vivado에서 이 옵션을 활성화하면 회로의 정확성을 유지하면서
자동으로 FF 위치를 재배열합니다."
```
→ "정확성을 유지한다"고 주장하지만, **증명 없음**

**학생 막힘 원인**: "증명이 없으면 불안"

**권장 추가 설명**:
```
Retiming의 정확성:
- Retiming 변환: FF-Q(10ns) → ALU_PART1(10ns)-FF-Q → ALU_PART2(10ns)-FF
- 중요한 성질: "각 FF의 출력 값은 동일함" (타이밍만 다름)
- 이유: Vivado는 FF 위치를 옮길 때, 데이터 플로우의 지연만 조정하고
  연산 결과는 동일하게 유지합니다.
- 검증: 시뮬레이션과 합성 후 파형이 동일해야 함
  (물론 클록 신호로 인해 약 1-2사이클 지연은 있을 수 있음)
```

### 3.3 Top 3: 임계 경로가 왜 MUX(fwd)인가?

**문제**: "파이프라인 어디에서 MUX 병목이 생겼나?"

**현재 원고**:
```
"이것은 EX-EX, MEM-EX, WB-EX 세 개의 포워딩 소스를 다중플렉서로 선택하는 로직입니다."
```
→ **Ch10 포워딩 구조와의 연결 약함**

**학생 막힘 원인**: 파이프라인 전체 구조 리마인더 필요

**권장 추가 설명**:
```
왜 MUX가 병목인가?
- Ch10에서 설계한 포워딩 유닛: ALU 결과 (EX)에서 동시에
  3개 입력(EX-EX, MEM-EX, WB-EX)을 확인하고
  3-to-1 MUX로 선택합니다.
- 3개 입력을 동시에 평가하려면 MUX 깊이가 커야 하며,
  이는 조합 지연을 증가시킵니다.
- 만약 EX-EX가 99% 확률이라면, 2-to-1 MUX (EX-EX vs Others)로
  깊이를 줄여 지연을 감소시킬 수 있습니다.
```

### 3.4 Top 4: LUT vs LUTRAM 지연 차이 정량화

**문제**: "얼마나 빠른가?"

**현재 원고**:
```
"LUTRAM은 조합 읽기(조회가 클록을 기다리지 않음)를 지원하므로,
캐시 데이터처럼 지연이 중요한 경로에 유리합니다."
```
→ 정성적 설명만

**학생 막힘 원인**: "1ns? 10ns? 정량 감이 없음"

**권장 추가 설명**:
```
BRAM vs LUTRAM 지연 비교 (Basys 3 XC7A35T 기준):
- BRAM 동기 읽기: 2-3ns (클록 에지 → 출력)
- LUTRAM 조합 읽기: 0-1ns (주소 → 출력, 클록 무관)
- 차이: 약 2ns

따라서 캐시 데이터가 임계 경로에 포함되면, LUTRAM 선택으로 약 2ns 개선 가능.
```

### 3.5 Top 5: 왜 50MHz 목표인가?

**문제**: "기준이 뭔가?"

**현재 원고**:
```
"최소 50MHz, 목표 65MHz"
```
→ 왜 이 수치인지 명시 부재

**학생 막힘 원인**: "교과서의 자의적 결정?"

**권장 추가 설명**:
```
50MHz 목표 근거:
1. Basys 3 안정성: 온보드 100MHz 클록에서 2분주 = 50MHz는
   설계 검증에 충분한 마진을 제공합니다.
2. 산업 표준: 임베디드 시스템에서 50~100MHz는 일반적인 범위입니다.
3. 교과서 설정: 이 교재에서는 "안정적 동작 50MHz" +
   "성능 개선 65MHz"의 이중 목표를 제시합니다.
```

### 6.2 연습문제별 강의 적용도 세부 평가

#### 문제 1: Remember 수준
```
Retiming, FSM Encoding, Keep Hierarchy 중 면적을 줄이는 데
가장 효과적인 옵션은?
```
**강의 적용도**: ✅ **우수**
- 강의에서 "FSM Encoding은 원-핫(면적) vs 바이너리 선택"으로 설명 가능
- 정답: Keep Hierarchy (평탄화를 피해 면적 유지) 또는 FSM Encoding (바이너리)
- ⚠️ **문제점**: "가장 효과적인"이 모호함 (FSM은 경우에 따라 다름)

#### 문제 2: Understand 수준
```
Basys 3에서 100MHz 클록을 50MHz로 분주하면,
create_clock의 period 값은 몇이 되어야 하고, 그 이유는?
```
**강의 적용도**: ⚠️ **중간**
- 문제: "분주"라는 용어가 추상적 (50MHz는 이미 칩 내부 신호인데?)
- 명확화 필요:
  ```
  "만약 설계 내부에서 100MHz를 2분주하여 50MHz를 만들면,
   XDC에서 create_clock의 period는 20ns이어야 합니다. (1000/50=20)"
  ```
- 개선안: "create_generated_clock" 명시 추가

#### 문제 3: Apply 수준
```
비동기 GPIO 입력 신호를 위한 XDC 제약을 작성하세요. (set_false_path 사용)
```
**강의 적용도**: ✅ **우수**
- 강의 중 "바로 손으로 작성 실습" 가능
- 예상 정답:
  ```tcl
  set_false_path -from [get_ports GPIO_ASYNC] \
    -to [get_pins sync_ff_reg[0]/D]
  ```
- 원고에서 이미 유사 예시 제공 (UART_RX)

#### 문제 4: Analyze 수준
```
타이밍 보고서에서 WNS=-1.5ns, TNS=-3.2ns가 나왔습니다.
이를 개선하는 우선순위 3가지를 제시하세요.
```
**강의 적용도**: ⚠️ **중간-어려움**
- 문제: 해답이 여러 가지 (TNS=-3.2는 약 3개 경로가 위반, 일부만 개선 가능)
- ✅ 강점: 학생이 "WNS만 개선"하는 오류를 방지
- ⚠️ 약점: 구체적 개선 방법이 원고에 "옵션 3가지(MUX, 파이프라인, 메모리)"로만 제시
- 개선안: 예상 정답 추가
  ```
  우선순위 1: MUX 깊이 축소 (가장 직접적)
  우선순위 2: 파이프라인 재삽입 (FF 추가는 여유 있으므로)
  우선순위 3: 메모리 읽기 지연 최소화 (LUTRAM 검토)
  ```

#### 문제 5: Evaluate 수준
```
현재 LUT 75%, BRAM 80%, FF 25% 사용 중입니다.
주파수를 5MHz 향상시키려면, 면적 제약 하에서 어떤 최적화를 우선할까요?
```
**강의 적용도**: ✅ **우수**
- 종합 사고력 평가 가능
- 예상 정답: "BRAM이 80%로 가장 부족 → LUTRAM으로 대체하여 LUT 추가, 지연 감소"
- 또는: "LUT는 75%로 여유 있으므로 파이프라인 재삽입 권장"
- ✅ 강사 입장에서 학생의 트레이드오프 이해도 평가 가능
