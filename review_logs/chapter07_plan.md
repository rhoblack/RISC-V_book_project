## 개요 — Part 3 교육적 포지션

Chapter 07은 단일 사이클(Ch06)과 파이프라인(Ch09~12) 사이의 **교량(bridge) 챕터**다. 독자는 이미 동작하는 CPU를 갖고 있다. 이 챕터의 목표는 "더 빠르게, 더 효율적으로"라는 동기를 실제 하드웨어 구조 변화로 연결하는 것이다.

멀티사이클은 최종 목표가 아니다. **파이프라인의 레지스터 삽입이 왜 필요한지, FSM으로 제어가 왜 바뀌는지, 하드웨어 자원 공유가 어떤 이점을 주는지**를 체감하게 하는 중간 도착점이다.

Part 3 감정 곡선 목표: **이해 심화 → 자신감 축적** (Ch06 대성취 직후, 파이프라인 불안 이전)

### 7.1절 — 단일 사이클의 한계: 왜 개선이 필요한가

#### 핵심 메시지
단일 사이클 CPU는 **가장 느린 명령어(Load)에 맞춰 전체 클럭 주기가 결정**되어, 빠른 명령어(R-type)도 같은 시간을 기다린다. 이 자원 낭비가 멀티사이클 도입의 출발점이다.

#### Ch06와의 연결 포인트
- Ch06.5에서 측정한 Basys 3 합성 결과를 직접 인용: "여러분이 만든 CPU는 약 25~30 MHz에서 동작했습니다"
- Ch06 기술 리뷰어 주석의 임계 경로 분석(Load 명령어 경로: IMEM → 디코더 → ALU → DMEM → WB)을 재활용
- WNS, TNS 개념은 Ch06.5에서 이미 학습 완료 — 여기서는 그 결과가 "왜 나쁜지"를 집중 분석

### 7.2절 — 멀티사이클의 핵심 아이디어: 단계 분할과 자원 공유

#### 핵심 메시지
멀티사이클은 하나의 명령어 실행을 **여러 사이클로 분할**하고, 그 덕분에 단일 메모리와 단일 ALU를 **여러 단계에서 공유**할 수 있다.

#### Ch06와의 연결 포인트
- Ch06은 IMEM과 DMEM을 별도 모듈로 분리(하버드 구조)했다 — 7.2절에서는 "단일 메모리로 통합 가능"한 이유를 설명하며, Princeton 구조 vs 하버드 구조 선택을 데이터패스 레벨에서 다시 논의
- Ch06의 ALU는 명령어 실행에만 사용됐다 — 7.2절에서는 "같은 ALU로 PC+4도 계산"하는 공유 개념 도입

*Basys 3 제약 주의*: BRAM True Dual Port를 사용하면 같은 사이클에 두 포트 동시 접근 가능하나, 교육 목적에서는 "한 사이클에 하나의 메모리 접근"이 멀티사이클 동기 부여에 더 명확함. 두 방식 모두 언급.

#### 핵심 비유/예시

**요리 코스 비유** (TABLE_OF_CONTENTS.md 공식 비유):
- 단일 사이클 = 모든 손님 요리(에피타이저~디저트)를 한 번에 서빙. 가장 많은 코스(Load = 5코스)에 맞춰 모든 테이블의 서빙 간격이 결정됨.
- 멀티사이클 = 한 코스씩 차례로 서빙. 에피타이저를 내오는 동안 다음 테이블 주문을 받을 수 있음.
- *비유의 한계* (교육전문강사 3단계 검증): "이 비유에서는 한 요리사가 한 테이블만 담당합니다. 여러 테이블을 동시에 처리하는 것은 파이프라인에서 다룹니다."

**자원 공유 비유**: 단일 사이클 CPU는 각 단계마다 별도의 계산기(ALU)를 두는 것과 같다. 멀티사이클은 하나의 계산기를 순서대로 빌려 쓴다. 비용은 줄지만, 한 번에 하나의 계산만 가능하다.

### 7.3절 — 멀티사이클 데이터패스 설계

#### 핵심 메시지
멀티사이클 데이터패스는 단일 사이클 대비 **5개의 중간 레지스터(IR, MDR, A, B, ALUOut)를 추가**하여, 각 단계의 출력을 다음 사이클까지 보존한다. 이 레지스터들이 "단계 분할"의 하드웨어 구현체다.

#### Ch06와의 연결 포인트
- Ch06의 단일 사이클 데이터패스(ch06_sec03_single_cycle_datapath.svg)와 7.3절 멀티사이클 데이터패스를 나란히 비교
- 새로 추가되는 요소: ① IR(명령어 레지스터), ② MDR(메모리 데이터 레지스터), ③ A 레지스터(rs1 임시), ④ B 레지스터(rs2 임시), ⑤ ALUOut 레지스터
- 변경되는 MUX: IorD(메모리 주소 선택), ALUSrcA/B(입력 선택 확장), MemtoReg(WB 선택 확장), PCSrc(PC 소스 확장)
- 유지되는 요소: 레지스터 파일, ALU(기능 동일), 즉치수 생성기

#### 핵심 비유/예시

**포스트잇(중간 메모) 비유**: 멀티사이클에서 IR, A, B, ALUOut 레지스터는 "다음 단계로 넘기는 메모"다. 요리사가 각 코스를 준비하면서 "이전 단계에서 계산한 재료 분량"을 포스트잇에 적어 냉장고에 붙여 놓는 것과 같다. 다음 사이클이 시작되면 포스트잇을 보고 이어서 작업한다.

**구체적 예시 (LW 명령어 5사이클 추적)**:
1. 사이클 1 (IF): PC → 통합 메모리 → IR에 저장 ("포스트잇에 명령어 기록")
2. 사이클 2 (ID): IR → 레지스터 파일 읽기 → A, B에 저장 ("rs1, rs2를 포스트잇에")
3. 사이클 3 (EX): A + imm → ALU → ALUOut에 저장 ("주소 계산 결과를 포스트잇에")
4. 사이클 4 (MEM): ALUOut → 통합 메모리 읽기 → MDR에 저장 ("로드 데이터를 포스트잇에")
5. 사이클 5 (WB): MDR → 레지스터 파일 쓰기 ("최종 결과 제출")

### 7.4절 — 단일 사이클 vs 멀티사이클 데이터패스 비교

#### 핵심 메시지
멀티사이클은 **하드웨어 면적을 줄이는 대신 중간 레지스터를 추가**한다. 단일 사이클과 멀티사이클은 서로 다른 트레이드오프를 선택한 설계이며, 어느 쪽이 절대적으로 우월하지 않다.

#### Ch06와의 연결 포인트
- Ch06.5 Basys 3 합성 결과표(LUT 사용량, 최대 주파수)와 7.4절 비교표를 직접 대응시킴
- Ch06의 IMEM + DMEM 분리 구조 vs Ch07의 통합 메모리 비교: LUT/BRAM 사용량 변화
- 중간 레지스터 추가 비용(FF 사용량 증가)과 공유 자원 절감(IMEM+DMEM → 통합 메모리) 상쇄 분석

#### 핵심 비유/예시

**스마트폰 vs 데스크톱 비유**: 단일 사이클은 데스크톱처럼 각 기능에 전용 하드웨어를 배치(빠르지만 부피가 크다). 멀티사이클은 스마트폰처럼 공유 프로세서를 순서대로 사용(작지만 한 번에 하나). 중간 레지스터는 스마트폰의 RAM에 해당—이전 작업 결과를 잠시 보관하는 공간이다.

**정량 비교표** (7.4절 핵심 콘텐츠):

| 항목 | 단일 사이클 (Ch06) | 멀티사이클 (Ch07) |
|------|-------------------|-----------------|
| 메모리 모듈 수 | 2 (IMEM + DMEM) | 1 (통합) |
| ALU 개수 | 1 (데이터 경로) + PC+4 가산기 | 1 (ALU가 PC+4도 계산) |
| 중간 레지스터 | 0 (PC만) | 5 (PC, IR, A, B, MDR, ALUOut) |
| FF 추가 사용량 | — | +5×32 = +160 FF |
| CPI | 1 | R:4, Load:5, Store:4, Branch:3 |
| 최대 클럭 주파수 | ~25~30 MHz (Basys 3) | ~50~60 MHz 예상 (단계 분할 효과) |
| 클럭 주기당 처리 명령어 | 1 | 1/CPI |

*주의*: 클럭 주파수 향상이 CPI 증가를 어느 정도 보상하는지는 Ch08.5에서 CPI 가중 평균 분석으로 다룸 (본 챕터는 데이터패스만 담당).

### 7.5절 — 본 챕터 요약 및 다음 단계

#### 핵심 메시지
Ch07은 멀티사이클 **데이터패스**를 완성했다. 이 CPU는 아직 스스로 동작하지 못한다 — 각 사이클에 어떤 제어 신호를 활성화할지 결정하는 **FSM 제어 유닛이 없기 때문**이다. Ch08에서 그 뇌를 완성한다.

#### 자가 점검 질문 (5개)

1. 멀티사이클에서 IR(명령어 레지스터)이 필요한 이유는 무엇인가? 단일 사이클에서는 왜 IR이 없어도 됐는가?
2. IorD MUX가 선택하는 두 입력은 무엇이며, 각각 어느 단계(IF/MEM)에서 사용되는가?
3. 멀티사이클에서 ALUSrcB에 상수 4가 추가된 이유를 설명하라. 단일 사이클에서 PC+4는 어떻게 계산했는가?
4. 멀티사이클에서 메모리를 단일 모듈로 통합할 수 있는 이유는 무엇인가? Basys 3 BRAM 포트 제약과 어떤 관계가 있는가?
5. A 레지스터와 B 레지스터가 없다면 어떤 문제가 발생하는가? 레지스터 파일 읽기 결과가 ID 단계에서 EX 단계로 넘어가는 동안 무슨 일이 일어나는가?

#### Ch08 예고 문구
> 데이터패스는 완성됐습니다. 하지만 아직 이 CPU는 동작하지 않습니다. 각 사이클마다 "지금 IF 단계인지, ID 단계인지, EX 단계인지"를 기억하고, 그에 맞는 제어 신호를 생성하는 주체가 없기 때문입니다. Chapter 08에서는 유한 상태 기계(FSM)를 이용해 멀티사이클 제어 유닛을 설계합니다. FSM의 각 상태가 파이프라인의 각 스테이지와 어떻게 대응되는지, 그 연결을 확인하는 순간이 파이프라인 이해의 핵심 도약점이 될 것입니다.

## 기술적 주의사항 및 잠재적 이슈

### Critical 수준

**[C1] `ch07_multicycle_datapath.sv` PCSrc 2'b10 인코딩 호환성 문제**
- 현재 코드: `pc_next = {alu_out_reg[31:28], ir_reg[25:0], 2'b00}` — 이는 MIPS 방식의 점프 주소 계산이다. RV32I의 JAL은 J-type PC-relative 주소이므로 `pc_next = pc_reg + imm_ext` 방식이 맞다.
- 조치: `PCSrc=2'b10` 케이스를 `alu_out_reg` (EX 단계에서 PC+imm_J 계산 결과)로 변경하거나, JAL 명령어의 EX 단계에서 올바른 주소를 ALUOut에 저장하도록 FSM 제어 신호를 정의할 것 (Ch08에서 FSM 설계 시 반드시 검토).
- 7.3절 코드 설명 시 해당 케이스에 "Ch08 FSM 설계와 함께 검토 예정" 주석 추가 권장.

**[C2] MDR 인에이블 없음 — 메모리 읽기 외 사이클에서 갱신 위험**
- 현재 코드: `always_ff @(posedge clk) begin mdr_reg <= mem_data_out; end` — 매 사이클 무조건 갱신
- 문제: MEM 단계가 아닌 사이클(IF 단계 등)에서도 `mem_data_out`이 변경되면 MDR에 잘못된 값이 저장될 수 있다.
- 조치: `if (mem_read) mdr_reg <= mem_data_out;` 패턴으로 변경 권장 (인에이블 기반 갱신). 단, IF 단계의 메모리 읽기 결과는 IR로 가고 MDR로 가지 않도록 구분이 필요함 — 이는 FSM 제어 신호 설계(Ch08)와 연계.

### Major 수준

**[M1] 통합 메모리의 바이트 인에이블 미처리**
- `ch07_multicycle_datapath.sv`의 메모리는 워드(32비트) 단위로만 읽기/쓰기한다. RV32I의 SB, SH, LB, LH, LBU, LHU는 바이트/하프워드 접근이 필요하다.
- Ch06의 `data_memory`는 `funct3`을 입력받아 바이트 인에이블과 부호 확장을 처리했다. 7.3절에서 통합 메모리의 바이트 접근 처리 방안을 명시할 것: 최소 구현으로 `funct3` 입력을 메모리 모듈에 추가하거나, MDR에서 WB MUX 사이에 부호 확장 로직을 추가.
- 교재에서 7.3절은 LW/SW(워드 전용) 우선 설명 후, `funct3` 확장을 "심화 구현"으로 병기하는 방식 권장.

**[M2] A/B 레지스터 인에이블 없음**
- 현재 코드: A, B 레지스터는 매 사이클 `rs1_data`, `rs2_data`로 무조건 갱신된다. ID 단계 외의 사이클에서도 갱신이 발생하면, 레지스터 파일에서 잘못된 주소가 읽힐 수 있다 (ir_reg가 이미 올바른 명령어를 담고 있으면 문제없지만, 명시적 인에이블이 더 안전하다).
- 조치: FSM의 ID 상태에서만 A, B 레지스터를 갱신하도록 인에이블 신호 추가 또는 주석으로 설계 의도 명시.

**[M3] Basys 3 BRAM 단일 포트 제약과 Princeton 구조 충돌**
- Basys 3의 BRAM은 기본 설정이 Simple Dual Port다. 통합 메모리를 BRAM으로 추론하면 읽기/쓰기 포트가 분리되어 같은 사이클에 읽기+쓰기가 가능하지만, IF(읽기)와 MEM(읽기)이 같은 사이클에 발생할 수 없다는 멀티사이클 가정이 하드웨어 수준에서 보장되어야 한다.
- 교재에서 "멀티사이클은 소프트웨어(FSM)가 같은 사이클에 IF와 MEM이 동시 발생하지 않도록 보장한다"는 설명 필수.
