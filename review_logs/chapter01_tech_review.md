## Critical Issues

- **[C-1]** 위치: 1.4절 XDC 제약 파일 (line 584)
  **문제**: `rst_n` 신호를 BTNC (U18)에 매핑하였으나, Basys 3의 푸시 버튼은 **눌렀을 때 HIGH(1)**, 뗐을 때 LOW(0)를 출력하는 **액티브 하이(active-high)** 구조이다. 그런데 RTL 코드에서는 `rst_n`을 **액티브 로우** 리셋으로 사용한다 (`if (!rst_n)`). 따라서 보드에 그대로 다운로드하면, **버튼을 누르지 않은 상태가 리셋 상태**가 되어 정상 동작하지 않는다.
  **수정 제안**: 두 가지 방법 중 하나를 선택:
  (1) XDC와 RTL 사이에 리셋 극성 반전(inverter)을 추가하거나,
  (2) RTL에서 `rst_n` 대신 `rst` (액티브 하이)로 변경하거나,
  (3) 본문에서 "보드의 버튼은 액티브 하이이므로, 실제 FPGA 합성 시에는 리셋 극성을 반전해야 한다"는 설명을 명확히 추가한다.
  현재 상태로는 독자가 코드를 그대로 합성하면 동작하지 않으므로 Critical 등급이다.

- **[C-2]** 위치: 1.5절 simple_adder 테스트벤치, 랜덤 테스트의 cout 검증 (line 788)
  **문제**: `cout` 기대값 계산 로직에 문제가 있다.
  ```systemverilog
  (({1'b0, a} + {1'b0, b} + {32'b0, cin}) >> 32)
  ```
  `{1'b0, a}`는 33비트, `{1'b0, b}`는 33비트, `{32'b0, cin}`은 33비트이다. 덧셈 결과도 33비트이므로 `>> 32`로 MSB를 추출하는 논리는 올바르다. 그러나 **SystemVerilog의 연산 비트 폭 규칙**에 따르면, `>>` 연산의 결과가 `check` 태스크의 `exp_cout` (1비트 `logic`)에 전달될 때 하위 1비트만 취해지므로 결과적으로 동작은 맞다. 다만 이것은 우연히 맞는 것이며, 가독성과 안전성을 위해 명시적 비트 선택 `[32]`를 사용하는 것이 바람직하다.
  **수정 제안**: `(({1'b0, a} + {1'b0, b} + {32'b0, cin}) >> 32)` 대신 다음과 같이 변경:
  ```systemverilog
  ({1'b0, a} + {1'b0, b} + {32'b0, cin}) [32]
  ```
  **재분류**: 동작은 올바르므로 Critical에서 **Major로 하향**. 아래 Major에 재기재한다.

## Major Issues

- **[M-1]** 위치: 1.4절 led_blinker.sv 본문 설명 (line 524)
  **문제**: "상승 에지와 하강 에지를 모두 사용하므로 100,000,000이 아닌 50,000,000"이라고 설명하고 있으나, 이 설명은 **부정확**하다. RTL 코드는 `posedge clk`만 사용하며 상승 에지에서만 카운트한다. 50,000,000까지 카운트하면 토글 주기가 0.5초이고, LED 시프트 간격이 0.5초가 된다. 실제로 코드에서 `tick`이 발생하면 LED가 시프트되는 것이므로, **LED가 매 0.5초마다 한 칸씩 이동**하는 것이 맞다. 1Hz "점멸"(on/off 반복)이 아니라 "시프트"이므로, "1Hz로 LED를 점멸"이라는 표현 자체가 약간 부정확하다. 더 중요한 것은, "상승/하강 에지를 모두 사용"한다는 설명이 코드와 일치하지 않는다는 점이다.
  **수정 제안**: "100MHz 클록에서 50,000,000 사이클(0.5초)마다 LED 패턴이 한 칸 시프트된다"로 정정하고, 듀얼 에지 사용 언급을 삭제한다. 또는 COUNT_MAX를 99,999,999로 변경하여 정확히 1초 간격으로 만든다.

- **[M-2]** 위치: 1.5절 simple_adder.sv (line 713)
  **문제**: `cin` 확장 표현이 비직관적이다.
  ```systemverilog
  assign {cout, sum} = a + b + {31'b0, cin};
  ```
  `{31'b0, cin}`은 32비트가 되므로, 좌변 `{cout, sum}`은 33비트인데 우변은 최대 32비트 연산이다. SystemVerilog에서는 좌변의 비트 폭(33비트)에 맞추어 우변이 확장되므로 올바르게 동작하지만, 교육 목적상 `{31'b0, cin}`보다 `{32'b0, cin}`(33비트)으로 명시적으로 맞추거나, 단순히 `cin`만 사용하는 것이 낫다(`cin`은 1비트이므로 자동 확장됨).
  **수정 제안**: `assign {cout, sum} = a + b + cin;`으로 간소화. SystemVerilog에서 `cin`(1비트)은 자동으로 33비트로 zero-extend된다.

- **[M-3]** 위치: 1.5절 테스트벤치 랜덤 테스트 cout 검증 (line 788, C-2에서 이동)
  **문제**: cout 기대값 계산이 가독성이 낮고, `>> 32` 방식은 교육적으로 비트 선택(`[32]`)보다 불명확하다.
  **수정 제안**: `({1'b0, a} + {1'b0, b} + {32'b0, cin})[32]`로 변경.

- **[M-4]** 위치: 1.4절 led_blinker.sv (line 531~566) 및 1.5절 파라미터화 버전 (line 908~935)
  **문제**: 두 버전의 `led_blinker`가 동일한 모듈명으로 존재하여, 독자가 혼동할 수 있다. 또한 1.4절의 비파라미터화 버전은 1.5절의 파라미터화 버전으로 **발전**하는 구조인데, 이 관계가 충분히 명확하지 않다.
  **수정 제안**: 1.4절에서 처음부터 파라미터화된 버전을 제시하거나, 1.5절에서 "1.4절의 코드를 파라미터화하여 개선한다"는 문장을 더 명확히 추가한다.

- **[M-5]** 위치: 1.3절 FSM 예제 (line 433~472)
  **문제**: FSM에서 `WAIT` 상태가 정의(`2'b10`)되어 있지만, `always_comb`의 `case` 문에서 `WAIT` 상태에 대한 전이 로직이 없다. `default`에 의해 `IDLE`로 전이되기는 하지만, 명시적으로 사용하지 않는 상태를 정의한 것은 교육적으로 혼란을 줄 수 있다. 또한 `WAIT` 상태에 진입하는 경로가 없으므로 도달 불가능한 상태(unreachable state)가 된다.
  **수정 제안**: (1) `WAIT` 상태를 활용하는 전이 경로를 추가하거나, (2) 사용하지 않는 상태라면 제거한다. 교육 목적으로 4상태 FSM을 보여주려면, `RUN` → `WAIT` → `DONE` 같은 전이를 추가하는 것이 바람직하다.

- **[M-6]** 위치: 1.4절 테스트벤치 (line 633~686)
  **문제**: 테스트벤치에 실질적인 **자동 검증(assertion/self-checking)** 로직이 없다. `$display`로 LED 값을 출력하지만, 기대값과 비교하는 로직이 전혀 없다. 이는 1.5절의 `simple_adder_tb`가 `check` 태스크로 자동 검증하는 것과 대조적이다. 교육 목적상, 최소한 리셋 직후 `led == 16'h0001`인지 확인하는 assertion이 필요하다.
  **수정 제안**: 리셋 해제 직후 assertion 추가:
  ```systemverilog
  assert (led === 16'h0001)
     else $error("리셋 후 LED 초기값이 16'h0001이 아닙니다: %h", led);
  ```

## Minor Issues

- **[m-1]** 위치: 1.3절 Verilog 스타일 MUX (line 283~296)
  **문제**: Verilog 예제에서 `always @(*)` 사용 시, MUX 로직에서 `sel=1`이면 `a`, `sel=0`이면 `b`를 출력한다. 바로 아래 SystemVerilog 버전도 동일한데, 통상적인 관례와 반대이다(보통 `sel=0`이면 `a`, `sel=1`이면 `b`). 기술적 오류는 아니나, 직관에 어긋날 수 있다.
  **수정 제안**: 관례에 맞게 `sel ? b : a` 또는 `if (sel) y = b; else y = a;`로 변경 고려.

- **[m-2]** 위치: 1.4절 XDC 파일 (line 574~602)
  **문제**: XDC 파일 코드 블록의 language가 `language-systemverilog`로 지정되어 있다. XDC는 Tcl 기반 스크립트이므로 `language-tcl` 또는 별도의 하이라이팅이 더 적절하다.
  **수정 제안**: `<pre><code class="language-tcl">` 또는 일반 텍스트로 변경.

- **[m-3]** 위치: 1.5절 VCS 명령어 (line 828~840)
  **문제**: VCS 명령어 블록도 `language-systemverilog`로 지정되어 있으나, 실제 내용은 셸 명령어이다.
  **수정 제안**: `language-bash` 또는 `language-shell`로 변경.

- **[m-4]** 위치: 1.5절 파라미터화 led_blinker (line 921, 927)
  **문제**: `COUNT_MAX[$clog2(COUNT_MAX+1)-1:0]` 표현이 교육 목적으로는 지나치게 복잡하다. `COUNT_MAX`는 `parameter int`로 선언되었으므로 32비트이고, `counter`는 `$clog2(COUNT_MAX+1)` 비트이다. 비교 시 비트 폭 불일치 경고를 방지하기 위한 슬라이싱인데, Chapter 01 수준의 독자에게는 설명 없이 사용하면 혼란스럽다.
  **수정 제안**: 간단히 `counter == COUNT_MAX`로 쓰고, 비트 폭 경고는 주석으로 설명하거나, 이 기법은 후반부 챕터에서 다루겠다고 언급한다. 또는 `localparam`으로 비트 폭을 미리 계산하여 가독성을 높인다.

- **[m-5]** 위치: 1.5절 파라미터화 led_blinker (line 924)
  **문제**: `counter <= counter + 1'b1;`에서 `1'b1`은 1비트 리터럴이다. `counter`의 비트 폭과 다르므로, 암시적 확장이 발생한다. 동작상 문제는 없으나, 1.4절에서는 `counter + 26'd1`로 폭을 명시했던 것과 일관성이 없다.
  **수정 제안**: 일관성을 위해 하나의 스타일로 통일. `1'b1`이 더 범용적이므로 이쪽으로 통일하되, 1.4절의 `26'd1`도 `1'b1`로 변경하는 것이 좋다.

- **[m-6]** 위치: 전체
  **문제**: "스스로 점검" (line 893, 976)에서 "스스로"는 맞춤법상 "스스로"가 맞지만, 보다 자연스러운 표현은 "스스로" 대신 "자기" 또는 aside 제목에서 "자가 점검"이 더 적합할 수 있다. 이는 기술 리뷰 범위 밖이므로 교육 리뷰어에게 위임한다.

### 총평

Chapter 01은 SystemVerilog 문법, 합성 가능한 코드 작성, 시뮬레이션 환경 구축을 포괄적으로 다루고 있으며, 코드의 IEEE 1800-2017 표준 준수도와 합성 가능성은 높은 수준이다.

**가장 시급한 수정 사항**은 C-1(리셋 극성 문제)이다. Basys 3의 푸시 버튼은 액티브 하이이므로, 현재 코드를 그대로 합성하면 독자가 기대한 동작과 반대로 작동한다. 이 문제는 독자의 첫 FPGA 경험을 좌절시킬 수 있으므로 반드시 수정해야 한다.

그 외 M-1(듀얼 에지 설명 오류)과 M-5(FSM의 WAIT 상태 미사용)도 기술적 부정확 또는 교육적 혼란을 유발할 수 있으므로 수정을 권고한다.

전반적으로 코드의 품질과 설명의 깊이가 우수하며, 위 이슈들을 수정하면 Chapter 01로서의 완성도가 매우 높아질 것이다.
