## 1️⃣ 절별 강의 비유 선정 (6개)

### 1. 17.1 APB 신호 프로토콜

| 항목 | 내용 |
|------|------|
| **비유** | 🚗 **고속도로(AHB) vs 이면도로(APB)** |
| **정확성** | ⭐⭐⭐⭐⭐ |
| **비유 설명** | 코어(AHB)는 빠른 주택지로 이동, 주변장치(APB)는 느린 이면도로로 이동. 속도 다르면 인터페이스가 필요함 |
| **한계 명시** | ⚠️ "실제로 APB는 신호만 다르지, 길의 폭이 더 좁지는 않습니다" |
| **오해 방지** | APB가 "느리다" ≠ "데이터 손실" (신호만 단순함) |
| **복귀** | "신호는 간단하지만 정확성은 100% 필요" |

### 2. 17.2 AHB-to-APB 브리지 FSM

| 항목 | 내용 |
|------|------|
| **비유** | 📋 **요청서 번역 시스템** |
| **정확성** | ⭐⭐⭐⭐ |
| **비유 설명** | AHB 신호(영어 요청서) → FSM(번역가) → APB 신호(한글 지역언어). 여러 신호를 모아 해석 |
| **한계 명시** | ⚠️ "실시간이 아닙니다. 브리지가 상태를 거쳐 천천히 변환" |
| **오해 방지** | AHB 신호 받자마자 APB 신호 나간다 ❌ (1~2 사이클 지연) |
| **복귀** | "FSM의 각 상태가 정확히 신호를 생성하는지가 핵심" |

### 3. 17.3 UART FIFO

| 항목 | 내용 |
|------|------|
| **비유** | 🪑 **대기실(FIFO) - 들어온 순서대로 처리** |
| **정확성** | ⭐⭐⭐⭐⭐ |
| **비유 설명** | 문자 들어올 때마다 대기실의 의자에 앉음. UART 하드웨어가 의자부터 꺼냄. First In, First Out |
| **한계 명시** | ⚠️ "실제 대기실은 크기 제한이 없지만, FIFO는 깊이 고정 (16칸 등)" |
| **오해 방지** | FIFO 가득 차면 "덮어씌운다"? ❌ (오버플로우 처리 필요 또는 대기) |
| **복귀** | "read_ptr, write_ptr 포인터로 구현됨" |

### 4. 17.4 GPIO 방향 제어

| 항목 | 내용 |
|------|------|
| **비유** | 🛣️ **양방향 도로 - 방향 표지판(방향 레지스터)** |
| **정확성** | ⭐⭐⭐⭐⭐ |
| **비유 설명** | GPIO는 입출력 겸용. 시간이 지나면서 용도가 바뀔 수 있으므로, 방향 레지스터로 "지금은 입력일까, 출력일까?"를 정함 |
| **한계 명시** | ⚠️ "신호 드라이브 강도(drive strength)와 풀업/풀다운 개념은 생략" |
| **오해 방지** | GPIO는 기계적으로 방향이 결정되는 게 아님. 소프트웨어 레지스터로 설정 |
| **복귀** | "TRISA(Tristate) 레지스터 = 0이면 출력, 1이면 입력" |

### 5. 17.5 Timer와 비교기

| 항목 | 내용 |
|------|------|
| **비유** | ⏳ **모래시계 + 알람** |
| **정확성** | ⭐⭐⭐⭐ |
| **비유 설명** | 카운터가 계속 증가(모래시계 흘러감). 비교값과 같아지면 알람(신호) 발생 → 재시작 (1주기) |
| **한계 명시** | ⚠️ "실제로는 카운터 리로드 시간(리셋 후 다시 세기 시작까지)이 1사이클 소요" |
| **오해 방지** | Timer는 "정확하게" 1사이클 지연 없이 작동 ❌ (1사이클 = ~20ns@50MHz) |
| **복귀** | "클럭 주파수 × 비교값 = 기간 (50MHz × 100만 = 20ms)" |

## 2️⃣ 강사 팁 (강의 현장에서 직접 사용)

### Tip 1: 신호 암기 비결 (17.1)

**문제**: 학생들이 APB 신호를 외워야 한다고 부담스러워함

**팁**:
> "APB 신호는 이름에서 의미를 읽어요.
> - P = Peripheral (주변장치)
> - PSEL = Peripheral Select (지금 내 신호인가?)
> - PENABLE = 준비됐나? (아직 기다려)
> - PWRITE = 쓰기(1) vs 읽기(0)
> - PRDATA/PWDATA = 읽기 데이터 vs 쓰기 데이터"

**적용 시기**: 17.1 APB 신호 소개 직후

---

### Tip 2: FSM 상태 결정의 비결 (17.2)

**문제**: 학생들이 "이 상태에서는 이 신호가 나가는데, 왜?" 이해 못함

**팁**:
> "AHB 신호를 보고 있다가, PSEL/PENABLE 두 신호가 둘 다 1이 되는 순간이 있어요.
> 그 순간이 '지금 주변장치를 선택하고, 그 주변장치가 준비된 신호'라는 뜻입니다.
> 그때 PADDR, PWRITE, PWDATA를 동시에 전달하세요."

**적용 시기**: 17.2 FSM 상태 3~4개 그렸을 때

---

### Tip 3: UART 송신 흐름 (17.3)

**문제**: UART로 데이터를 보내는 전체 흐름이 복잡해 보임

**팁**:
> "UART 송신은 4단계:
> 1. 프로그램: FIFO에 데이터 삽입 (write_ptr 증가)
> 2. 하드웨어: FIFO가 비어있지 않으면, 자동 꺼내기 (read_ptr 증가)
> 3. UART TX: 데이터를 직렬화해서 보내기 (비트 단위)
> 4. PC: 직렬 포트로 수신 (putty 같은 터미널에 표시)
>
> 개발자는 1번만 하면, 2~4번은 하드웨어가 알아서 해요."

**적용 시기**: 17.3 UART FIFO 구현 후 테스트벤치 실행 전

---

### Tip 4: GPIO 디버깅 3단계 (17.4)

**문제**: GPIO가 안 켜지면 원인을 모르겠다는 학생들

**팁**:
> "GPIO 안 켜져? 체크리스트:
> 1. 주소가 맞나? (CTRL_ADDR 확인)
> 2. WRITE인가? (pwrite=1 맞나?)
> 3. 방향이 OUTPUT인가? (direction_reg에서 해당 비트가 0인가?)
>
> 3단계 순서대로 하나씩 끄고, 어디서 문제인지 파악하세요."

**적용 시기**: 17.4 GPIO 테스트벤치 작성 단계

---

### Tip 5: Timer 주기 계산 (17.5)

**문제**: "Timer를 50ms 주기로 하려면?" 계산이 복잡해 보임

**팁**:
> "공식: 클럭 주파수 × 비교값 = 시간
>
> 예: 50MHz@20ns 클럭, 50ms 주기 원함
> - 50ms = 50,000,000ns
> - 50,000,000ns ÷ 20ns = 2,500,000 사이클
> - compare_reg = 2,500,000 (10진수) = 0x_265_340 (16진수)
>
> 검산: 2,500,000사이클 × 20ns/사이클 = 50,000,000ns = 50ms ✓"

**적용 시기**: 17.5 Timer 설계값 정할 때

---

### Tip 6: 통합 시스템 디버깅 (17.6)

**문제**: 4개 주변장치를 동시에 구동하니 뭐가 문제인지 모르겠음

**팁**:
> "통합 디버깅은 '하나씩 끄기':
> 1. 전체 구동하면 뭔가 안 되거나 느려
> 2. UART만 (GPIO/Timer 끄기) → 동작?
> 3. GPIO만 (UART/Timer 끄기) → 동작?
> 4. Timer만 동작?
> 5. 동작한 놈들 다시 켜기
>
> 이렇게 하면 어느 조합이 충돌하는지 알 수 있어요."

**적용 시기**: 17.6 통합 테스트벤치 실행 단계

## 4️⃣ 반도체 회사 면접 Top 5

### 1️⃣ "APB와 AHB의 차이를 설명해라"

**출제 배경**: 주변장치 설계 경험 평가

**핵심 답변**:
```
AHB (AMBA High-Performance Bus):
- 목표: 코어와 메모리 연결 (고속)
- 신호: HADDR(32bit), HDATA(32bit), HWDATA, HRDATA, HWRITE, HREADY 등 (많음)
- 대역폭: 고대역폭, 단일 사이클 응답 가능
- 용도: CPU ↔ 메모리, 메모리 컨트롤러

APB (AMBA Peripheral Bus):
- 목표: 주변장치 연결 (저속 OK)
- 신호: PADDR(32bit), PDATA(32bit), PWRITE, PSEL[n], PENABLE 등 (적음)
- 대역폭: 제한적 OK
- 용도: 주변장치 (UART, GPIO, Timer, SPI)

차이 요약:
| 항목 | AHB | APB |
|------|-----|-----|
| 속도 | 빠름 | 느려도 됨 |
| 신호 수 | 많음 | 적음 |
| 프로토콜 | 복잡 (다중 마스터 지원) | 단순 (단일 마스터) |
| 응답 | 단일 사이클 가능 | 2사이클 이상 OK |
```

**강사 팁**:
> "APB는 '간단한 주변장치'용이에요. UART(문자만 보내면 됨), GPIO(비트만 쓰면 됨)는 속도가 느려도 상관없죠. 신호를 단순하게 만들어서 칩 면적을 절약해요."

---

### 2️⃣ "AHB-to-APB 브리지 FSM을 그려라"

**출제 배경**: 프로토콜 변환 능력 평가

**핵심 답변** (상태도):
```
상태 5~6개:

IDLE
  ↓ (HSEL & HREADY)
SETUP (PSEL 어설션, PADDR/PWDATA 전달)
  ↓ (1사이클)
WRITE/READ (PENABLE 어설션)
  ↓ (PREADY 대기)
DONE (HRREADY 어설션, 응답 회신)
  ↓ (1사이클)
IDLE

조건:
- HWRITE=1이면 PWRITE=1
- HWRITE=0이면 PWRITE=0
- PREADY=1이면 2상 완료 (WRITE/READ → DONE)
```

**강사 팁**:
> "AHB 신호 받기(HSEL 체크) → APB 신호 발생(PSEL/PENABLE) → APB 응답 기다리기(PREADY) → AHB 응답 돌려주기(HRREADY) 이렇게 4단계면 됩니다."

---

### 3️⃣ "UART FIFO가 가득 찼을 때 어떻게 처리하는가?"

**출제 배경**: 오버플로우 처리 전략 평가

**핵심 답변**:
```
UART FIFO 오버플로우 3가지 처리:

1. 데이터 손실 (버리기):
   - 가장 간단
   - 임베디드(온도 센서 등) 환경 OK
   - 한두 개 데이터 손실 괜찮으면 사용

2. 신호로 알리기 (overflow_flag):
   - overflow_flag = 1이면 가득 찼음
   - 프로그램이 "더 이상 못 쓴다"는 걸 알아채고 대기
   - 가장 현실적 (대부분 이렇게 함)

3. 하드웨어 대기 (busy):
   - FIFO 가득하면 write 요청을 대기 (ready 신호=0)
   - 느리지만 안전
   - 고신뢰 시스템 (항공기, 의료기기)
```

**강사 팁**:
> "대부분 임베디드는 2번 (overflow_flag)으로 처리합니다. 프로그램이 '이거 보내는 데 실패했다'는 걸 알고 재전송하거나 에러 로깅합니다."

---

### 4️⃣ "GPIO와 UART를 동시에 돌리면 문제가 없나?"

**출제 배경**: 버스 공유와 주소 공간 분리 이해도 평가

**핵심 답변**:
```
GPIO와 UART 동시 구동 안전성:

1. 주소 분리:
   - GPIO 주소: 0x4000_1000 (16비트 레지스터 4개)
   - UART 주소: 0x4000_2000 (8비트 레지스터 5개)
   - 겹치지 않음 → 충돌 없음

2. AHB 주소 디코딩:
   - AHB 마스터(CPU)가 주소 보냄
   - AHB 슬레이브(중재기)가 주소 보고 PSEL 신호 결정
   - GPIO PSEL[0]=1, UART PSEL[1]=1 (배타적)

3. 실제 동작:
   - 같은 사이클에 GPIO 읽고 UART 쓸 수 있음
   - 하지만 AHB는 한 번에 한 슬레이브만 응답
   - 우선순위 정해져야 함 (고정 또는 라운드로빈)
```

**강사 팁**:
> "각 주변장치가 고유 주소를 가지니까 충돌이 없어요. 마치 우체국처럼 '이건 UART 부서, 이건 GPIO 부서'라고 구분되는 거죠."

### 5️⃣ "Timer 인터럽트 레이턴시(latency)는?"

**출제 배경**: 실시간 성능 이해도 평가

**핵심 답변**:
```
Timer 인터럽트 레이턴시 (3단계):

Step 1: Timer 신호 발생 (compare_reg == counter)
  ↓ (같은 사이클)
Step 2: CPU가 timer_int 신호 감지 (파이프라인 EX 스테이지)
  ↓ (다음 사이클)
Step 3: CPU 트랩 진입 (PC = interrupt_handler_address)
  ↓ (다음 사이클)

총 레이턴시: 2~3 사이클 (depend on CPU 설계)
@50MHz: 2사이클 = 40ns, 3사이클 = 60ns

참고: Ch19에서 CPU 인터럽트 처리를 배웁니다.
```

**강사 팁**:
> "타이머는 신호만 만듭니다. CPU가 그 신호를 언제 받을지는 다음 장에서 배워요. 지금은 '신호가 정시에 나온다'는 것만 확인하면 됩니다."
