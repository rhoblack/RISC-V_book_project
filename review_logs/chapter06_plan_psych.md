## 1. 챕터 시작 심리 상태 분석

### Ch05 직후 독자의 감정 상태

Chapter 04~05를 완료한 독자는 다음 심리 지형에 서 있다:

**성공 자산 목록 (독자가 이미 보유한 성취감)**
- ALU 10가지 연산 구현 완료 → "하드웨어 연산기를 내 손으로 만들었다"
- 레지스터 파일 설계 완료 → "32개 레지스터를 직접 설계했다"
- 즉치수 생성기 완료 → "명령어 비트 재조합이 실제로 동작한다"
- IMEM / DMEM 설계 완료 → "CPU가 읽고 쓸 메모리가 준비되었다"
- 각 모듈의 테스트벤치에서 "ALL TESTS PASSED" 경험 → 성공 패턴 체화

**내재된 심리적 긴장**
Ch05를 마치는 순간, 독자는 묵직한 질문과 마주한다:

> *"메모리 맵 코드 맨 끝에 'Chapter 06에서 완성' 주석이 달려 있었다. 지금까지 만든 조각들이 다섯 개다. 이것들을 어떻게 하나로 연결하지?"*

이것은 단순한 의문이 아니라 **기대 불안(anticipatory anxiety)**이다. 프로세서 전체 블록 다이어그램을 처음 봤을 때의 충격(불안 지점 #2)이 재활성화될 수 있으며, 동시에 "드디어 완성 단계에 가까워지고 있다"는 흥분이 공존한다.

### Ch06 진입 시 예상 심리

| 심리 요소 | 상태 | 발생 원인 |
|----------|------|---------|
| 자기효능감 | 중상 (↑) | 4개 모듈 성공 경험 누적 |
| 완성에 대한 기대감 | 높음 (↑↑) | "이제 진짜 CPU가 만들어진다" |
| 연결의 복잡성 불안 | 중 (⚠️) | 다섯 모듈을 한 번에 이어야 한다는 압박 |
| 제어 신호에 대한 막연함 | 높음 (⚠️⚠️) | "신호 이름은 들었지만 개수가 얼마나 되는지 모른다" |
| 피보나치 성취 예감 | 잠재적 (↑) | Part 2 마일스톤 예고를 읽었다면 기대감 존재 |

**결론**: Ch06 진입 시 독자는 **"기대와 불안이 50:50으로 공존하는 상태"**다. 이 상태에서 도입부가 불안 쪽으로 기울면 조기 이탈 위험이 있고, 기대 쪽으로 기울면 강력한 학습 몰입이 일어난다. 따라서 Ch06 도입부는 반드시 **"연결의 서사"**로 시작해야 한다.

## 2. 불안 지점 매핑 및 안심 장치 설계

### 불안 지점 A — 6.1절: "명령어가 37개라고요?"

**발생 순간**: 디코더 진리표를 처음 전체 펼쳐 보이는 순간.
"opcode만 있는 게 아니라 funct3, funct7까지 조합해서 37개를 전부 분류해야 한다" 는 사실을 마주하는 순간.

**안심 장치 문구 초안**:

> **[metacognition 박스]**
> 지금 여기서 37개 명령어를 전부 외우실 필요는 없습니다.
> 디코더의 핵심 아이디어는 딱 하나입니다: **"명령어 비트를 보고, 각 부품에게 무엇을 하라고 지시하는가."**
> 나머지는 Chapter 03에서 만든 명령어 레퍼런스 카드를 옆에 펼쳐 두고 한 줄씩 따라가면 됩니다.
> 이 절이 끝날 때쯤 여러분은 "아, 디코더는 사실 큰 case 문이구나"라고 느끼게 될 것입니다.

**추가 장치**: 37개 명령어를 opcode 그룹별(R, I-계산, I-로드, S, B, U-LUI, U-AUIPC, J, I-JALR)로 색상 분류한 SVG를 먼저 제시하고, "오늘 우리가 처리할 그룹"을 순서대로 하이라이트하는 Gradual Reveal 방식 적용.

### 불안 지점 B — 6.2절: 제어 신호 진리표 방대함 (최대 불안 구간, 불안 지점 #3)

**발생 순간**: `ALUSel`, `ImmSel`, `RegWEn`, `MemRW`, `PCSel`, `WBSel` 등의 제어 신호 이름과, 각 명령어 타입별로 이 신호들이 어떤 값을 가져야 하는지를 테이블로 보는 순간.

**핵심 심리 위협**: *"이것을 다 외워야 하나? 설계하다가 신호 하나 잘못 연결하면 어떻게 되는 거지?"*

**안심 장치 문구 초안**:

> **[faq 박스 — ❓ 수강생 단골 질문]**
> **Q**: 제어 신호가 너무 많아서 다 기억하기 힘듭니다. 어떻게 해야 하나요?
> **A**: 기억하실 필요가 없습니다. 이 신호들은 **설계 단계에서 한 번 정하고 나면, 하드웨어가 자동으로 처리합니다.** 인간이 런타임에 일일이 관리하는 것이 아닙니다. 진리표를 작성할 때는 오직 두 가지 질문에만 집중하세요:
> 1. "이 명령어는 레지스터에 결과를 써야 하는가?" → `RegWEn`
> 2. "이 명령어는 ALU에 무엇을 계산하게 해야 하는가?" → `ALUSel`
> 나머지 신호는 이 두 가지를 답하고 나면 자연스럽게 따라옵니다.

> **[tip 박스 — 💡 실무 팁]**
> 진리표를 명령어 유형별(R 타입 → I 타입 → S 타입 → B 타입 → U 타입 → J 타입) 순서로 **분할 작성**하십시오. 한 유형을 완성하면 잠시 멈추고, 그 유형의 신호 패턴을 시뮬레이션으로 확인한 뒤 다음 유형으로 넘어가는 것을 권장합니다. 전체를 한 번에 작성하고 몰아서 디버깅하는 방법은 오류 추적이 극히 어렵습니다.

**진리표 분할 제시 방식**:
- 표를 한 번에 전체 제시하지 않는다.
- R 타입 4행 → 시뮬레이션 확인 → I 타입 12행 → 시뮬레이션 확인 → … 방식으로 "점진적 진리표 완성"을 본문 흐름으로 설계한다.

### 불안 지점 C — 6.3절: "다섯 개 모듈을 한 번에 연결한다"는 압박

**발생 순간**: 단일 사이클 top-level 설계에서 다섯 개 모듈의 포트 연결을 한꺼번에 코딩해야 할 때.
신호 이름이 모듈마다 다르고, 어디에 무엇을 연결해야 하는지 블록 다이어그램을 계속 참조해야 한다.

**안심 장치 문구 초안**:

> **[metacognition 박스 — 🔍 스스로 점검]**
> 이 절에서 작성할 코드는 길어 보이지만, 사실 새로운 논리가 하나도 없습니다.
> 여러분이 Chapter 04~05에서 이미 만든 모듈들을 **선으로 이어주는 작업**입니다.
> 마치 조립된 부품들을 뒤에서 전선으로 연결하는 것처럼요.
> 포트 연결 중 이름이 헷갈린다면, Chapter 04~05의 모듈 포트 목록을 참조하십시오.
> **오늘 새로 만드는 논리는 제어 유닛과 MUX 뿐입니다.**

> **[instructor-tip 박스 — 📌 강사 꿀팁]**
> 수강생들이 top-level 연결 코드를 처음 작성할 때 가장 자주 하는 실수는 신호 방향(input/output) 혼동입니다. 수업에서는 빈 top-level 모듈 템플릿을 먼저 나눠주고, 포트 선언을 채우는 것부터 시작하게 하면 오류 발생률이 크게 줄어듭니다.

### 불안 지점 D — 6.5절: "타이밍 분석이란 무엇인가"

**발생 순간**: Vivado 타이밍 보고서에서 WNS(Worst Negative Slack), TNS(Total Negative Slack) 용어가 처음 등장할 때.
"내 설계가 타이밍을 위반한 건지, 통과한 건지 어떻게 아는 거지?"라는 혼란.

**안심 장치 문구 초안**:

> **[faq 박스 — ❓ 수강생 단골 질문]**
> **Q**: WNS가 음수로 나왔어요. 설계가 잘못된 건가요?
> **A**: WNS(Worst Negative Slack, 최악 슬랙)가 음수라는 것은 **목표 클럭보다 빠르게 동작하기 어렵다**는 의미입니다. 단일 사이클 프로세서에서 이것은 완전히 예상된 결과입니다. 목표를 낮추어 시뮬레이션 주파수에서 동작시키면 됩니다. 오히려 이 수치가 Chapter 07 멀티사이클 프로세서와 Part 4 파이프라인으로 나아가는 강력한 동기가 됩니다: *"이 구조로는 클럭을 빠르게 돌릴 수 없다."*

> **[tip 박스 — 💡 실무 팁]**
> 슬랙(Slack)이란 타이밍 "여유 시간"입니다. 양수이면 여유가 있는 것, 음수이면 부족한 것입니다. 단일 사이클 프로세서에서 임계 경로(Critical Path)는 Load 명령어 실행 경로(IMEM → 디코더 → ALU → DMEM → 레지스터 파일)입니다. 이 경로의 지연 시간이 클럭 주기보다 길면 타이밍 위반이 발생합니다.

### 6.1절 — 명령어 디코더 설계

**감정 목표**: 호기심 유발 + 불안 예방 (진입 성공 경험 확보)

**설계 의도**:
독자는 이 절에서 "큰 case 문"이라는 프레임을 얻어야 한다. 37개 명령어 전체를 보여주되, "우리가 오늘 처음 구현할 명령어 그룹은 R 타입 10개입니다"라고 범위를 좁혀준다. 첫 구현 대상을 R 타입으로 선택한 이유는 funct3/funct7 패턴이 상대적으로 명확하고, Chapter 04에서 ALU를 이미 만든 경험과 직접 연결되기 때문이다.

**첫 실습 성공 설계**:
- R 타입 디코더 코드는 테스트벤치와 함께 제공한다.
- `ADD` 명령어 하나를 올바르게 디코딩하는 첫 시뮬레이션이 즉시 통과되도록 단계별 코드 스캐폴딩(scaffolding)을 적용한다.
- "DECODE OK: ADD" 메시지 출력 → 즉각적 성공 피드백 확보.

**감정 흐름**: 기대(Ch05 성취 → 연결의 순간) → 호기심(디코더의 구조 파악) → 첫 시뮬레이션 성공으로 소성취감

### 6.2절 — 제어 신호 정의

**감정 목표**: 불안 최대 구간 → 분할 정복으로 통제감 회복

**설계 의도**:
이 절은 교재 전체 불안 지점 #3의 핵심 구간이다. 제어 신호 진리표 전체를 한 번에 제시하면 독자는 압도감에 빠진다. 따라서 다음 3단계 분할 전략을 사용한다:

**3단계 분할 전략**:
1. **단계 1 — 신호 하나씩 이해**: `RegWEn`과 `MemRW` 두 신호만 먼저 다룬다. "레지스터에 쓰는가?"와 "메모리에 쓰는가?"라는 직관적 질문으로 신호의 의미를 이해시킨다.
2. **단계 2 — R/I 타입 진리표 완성**: 가장 자주 쓰이는 명령어 유형의 진리표를 먼저 완성하고, 시뮬레이션으로 즉각 검증한다.
3. **단계 3 — 나머지 타입 완성**: S/B/U/J 타입을 순서대로 추가한다. 각 타입마다 "이 타입의 특징은 무엇인가?"라는 안내 질문으로 독자가 스스로 신호 값을 예측하도록 유도한다.

**감정 흐름**: 초기 불안(신호 종류와 개수) → 분할로 통제감 회복 → 각 단계 완성마다 작은 성취감 → 절 말미에 "진리표를 내 손으로 완성했다"는 만족감

### 6.3절 — 단일 사이클 데이터패스 통합

**감정 목표**: 안정화 + "모든 조각이 맞아 들어가는" 경험

**설계 의도**:
이 절은 Ch04~05의 성취물을 수확하는 절이다. 새로운 어려움보다는 "연결의 즐거움"이 전면에 나와야 한다. 코드 길이가 길어 보이지만, 사실 새로운 논리는 거의 없다는 점을 강조한다.

**블록 다이어그램 Gradual Reveal 완성**:
Ch04에서 처음 보여준 전체 데이터패스 SVG(회색 블록 다수)가 이 절에서 마지막으로 모두 파란색으로 채워진다. 이 시각적 완성이 독자에게 강력한 성취 신호를 보낸다.

> **[tip 박스 — 💡 실무 팁]**
> top-level 모듈은 한 번에 작성하지 말고, 먼저 ALU와 레지스터 파일만 연결한 최소 버전을 만들어 컴파일 오류 없음을 확인하십시오. 그 다음 IMEM을 연결하고, 그 다음 DMEM과 제어 유닛을 연결하는 **증분식(incremental) 연결** 방법을 사용하면 디버깅이 훨씬 쉬워집니다.

**감정 흐름**: 연결 작업의 집중감 → 컴파일 성공의 안도감 → "모든 블록이 채워졌다"는 시각적 달성감

**설계 의도**:

**감정 흐름**: 기대 고조 → 시뮬레이션 실행 순간의 긴장 → 파형에서 결과 확인 → 폭발적 성취감 → 다음 여정 기대

### 6.5절 — Basys 3 합성 및 타이밍 분석

**감정 목표**: 현실적 성찰 + 다음 챕터 동기 부여

**설계 의도**:
성취감의 흥분이 가라앉을 무렵, 독자는 현실과 마주한다: "우리가 만든 CPU가 Basys 3에서 얼마나 빠르게 돌아가는가?" 타이밍 분석 결과(20~30MHz 예상)는 그 자체로 실망스러울 수 있다. 이것을 **"한계의 발견이 곧 다음 여정의 출발점"**이라는 서사로 전환해야 한다.

**핵심 메시지**: "단일 사이클 프로세서는 가장 느린 명령어(Load)의 속도에 맞춰 모든 명령어가 같은 클럭으로 돌아갑니다. 이 수치가 낮다는 것은 설계를 잘못한 것이 아닙니다 — **단일 사이클이라는 구조 자체의 본질적 한계**입니다. 이것을 해결하는 것이 Chapter 07과 Part 4의 과제입니다."

**감정 흐름**: 합성 결과 수치에 대한 호기심 → 타이밍 한계 인식 → "그래서 멀티사이클/파이프라인이 필요한 거구나" 깨달음 → 다음 챕터 기대

---

### 6.6절 — 본 챕터 요약 및 다음 단계

**감정 목표**: 성취감 정착 + 자신감 강화

**설계 의도**:
이 절은 단순한 요약이 아니라 **독자의 성장 여정을 거울처럼 보여주는 절**이어야 한다. "당신은 이것들을 해냈습니다"라는 메시지와 함께, 다음 챕터(멀티사이클)가 두렵지 않도록 "이미 아는 것"과 "새로 배울 것"을 명확히 구분해준다.

**감정 흐름**: 완성의 뿌듯함 → 자신감 정착 → 다음 여정에 대한 건강한 기대

## 4. 피보나치 마일스톤 달성 순간 설계

### 6.4절 피보나치 시뮬레이션 순간의 텍스트 설계

**시뮬레이션 실행 직전 도입 문단**:

> 지금까지 Chapter 04에서 ALU와 레지스터 파일을, Chapter 05에서 명령어 메모리와 데이터 메모리를 만들었습니다. 이 절에서는 그 모든 부품을 하나로 연결한 단일 사이클 프로세서에 **실제 RISC-V 프로그램을 실행시킵니다**.
>
> 실행할 프로그램은 피보나치(Fibonacci) 수열입니다: 1, 1, 2, 3, 5, 8, 13, 21, ...
> 이 프로그램은 ADD, BEQ, JAL 명령어를 사용하며, 여러분이 구현한 제어 신호와 데이터패스가 올바르게 동작하는지를 통합적으로 검증합니다.
>
> 시뮬레이션을 실행하고, 파형에서 레지스터 파일의 a0 값이 1 → 1 → 2 → 3 → 5 → 8 → 13 → 21로 변화하는 것을 확인하는 순간 — 그것이 바로 이 책의 첫 번째 대성취입니다.

**파형 확인 순간의 텍스트 설계 (성취 극대화 문구)**:

파형 이미지 하단에 다음 텍스트를 배치한다:

> 파형에서 `a0`의 값이 `0x00000001`, `0x00000001`, `0x00000002`, `0x00000003`, `0x00000005`, `0x00000008`... 순서로 변화하는 것을 확인했다면, 여러분의 CPU는 **정확하게 동작하고 있습니다**.
>
> 잠깐, 지금 이 순간을 의식적으로 느껴 보시기 바랍니다.
>
> 여러분은 방금 **직접 설계한 프로세서 위에서 처음으로 프로그램을 실행**했습니다. Chapter 04에서 시작한 여정이 여기서 하나로 완성되었습니다. ALU가 덧셈을 계산하고, 레지스터 파일이 값을 저장하고, 제어 유닛이 명령어를 해독하고, 메모리가 프로그램을 공급하는 이 모든 동작이 **당신이 작성한 코드에 의해** 이루어지고 있습니다.

**독려 문구 (2~3문장)**:

> 아직 파이프라인도 없고 캐시도 없는, 가장 단순한 형태의 프로세서입니다. 하지만 이것이야말로 모든 현대 고성능 프로세서의 출발점입니다. 앞으로 여러분이 만들게 될 파이프라인 프로세서는 이 구조를 기반으로 성능을 끌어올리는 과정입니다 — 완전히 새로운 설계가 아니라, 오늘 만든 것의 **진화**입니다.

---

### 다음 챕터(멀티사이클)로의 자연스러운 동기 연결

6.5절 타이밍 분석 결과를 활용하여 다음과 같이 연결한다:

> 오늘 Basys 3 합성 결과에서 최대 동작 주파수가 약 20~30MHz로 측정되었습니다. 이 수치의 의미를 생각해 보십시오.
>
> 단일 사이클 프로세서에서 가장 오래 걸리는 명령어는 Load입니다: 명령어 메모리에서 명령어를 읽고 → 레지스터를 읽고 → ALU에서 주소를 계산하고 → 데이터 메모리에서 데이터를 읽고 → 레지스터 파일에 결과를 기록하는 이 전체 경로가 **하나의 클럭 사이클**에 완료되어야 하기 때문입니다.
>
> ADD 명령어는 훨씬 빠르게 끝낼 수 있지만, Load 명령어에 맞춰 같은 긴 클럭 주기를 기다려야 합니다. 이것이 **단일 사이클의 근본적 비효율**입니다.
>
> Chapter 07에서는 이 문제를 해결합니다. 이미 오늘 구현한 데이터패스와 제어 유닛 지식을 그대로 활용하면서 — 새로 처음부터 배우는 것이 아닙니다.

## 5. 자기효능감 관리 전략

### 6.1절 첫 실습의 "반드시 성공" 설계

**전략**: 최소 성공 가능 단위(Minimum Viable Success)로 시작

첫 실습 코드는 다음 조건을 만족해야 한다:

1. **즉시 실행 가능**: 코드 복사 → 파일 저장 → 시뮬레이션 실행의 3단계가 전부여야 한다. 복잡한 빌드 설정 없이.
2. **즉각적 피드백**: 첫 시뮬레이션에서 최소 "DECODE OK: ADD" 한 줄을 출력하도록 설계한다.
3. **오류 불가 구조**: 첫 실습 코드는 완성형으로 제공하되, 독자가 직접 채울 부분은 명확한 주석으로 안내한다. "여기에 ADD의 ALUSel 값을 채워넣으시오 (힌트: Chapter 04 ALU 코드의 `ALU_ADD` 상수 참조)"

**실습 코드 제공 원칙**:
- 6.1절 첫 실습: 디코더 R 타입 부분만 있는 뼈대 코드 + 테스트벤치 (완성형) 제공
- 독자는 case 문 내부의 일부 신호 값만 채운다
- 채우는 즉시 시뮬레이션이 통과하도록 설계

**오류 발생 시 안전망**:

> **[faq 박스 — ❓ 수강생 단골 질문]**
> **Q**: 시뮬레이션에서 DECODE FAIL 메시지가 나옵니다.
> **A**: 이것은 정상적인 학습 과정의 일부입니다. 대부분의 경우 `ALUSel` 값이 Chapter 04의 ALU 코드에서 정의한 상수와 다르기 때문입니다. 두 파일을 나란히 열고 상수 이름을 대조해 보십시오. 디코더와 ALU가 같은 상수를 참조하는지 확인하는 것이 핵심입니다.

### 실패 정상화 문구 배치 지침

진리표 작성 오류와 신호 연결 오류는 이 챕터의 가장 흔한 디버깅 대상이다. 다음 실패 정상화 문구를 6.3절 또는 6.4절 시뮬레이션 디버깅 안내에 포함한다:

> 제어 신호 오류는 경험 있는 설계자도 자주 범하는 실수입니다. 파이프라인 CPU를 설계하는 산업 현장에서도 제어 로직 버그는 가장 흔한 오류 유형 중 하나입니다. 시뮬레이션에서 예상과 다른 파형이 나왔다고 해서 당황하지 마십시오 — 그것이 바로 시뮬레이션의 역할입니다.

### Verdi 파형 분석 유도 장치

6.4절 피보나치 시뮬레이션에서 독자가 파형을 "수동적으로 확인"하는 것에 그치지 않도록, 능동적 분석을 유도하는 질문을 단계적으로 제시한다:

1. "PC 값이 어떻게 변합니까?" → 순차 실행 확인
2. "분기 명령어 BEQ가 실행될 때 PC가 어디로 점프합니까?" → 분기 처리 확인
3. "결과 레지스터(a0)의 값이 예상한 피보나치 수열과 일치합니까?" → 최종 성취 확인

이 3단계 질문 구조는 독자가 파형 속에서 스스로 성취를 발견하도록 유도하며, 발견의 주체가 독자 자신이 됨으로써 성취감이 외부에서 주어진 것이 아닌 **내재적 성취**로 경험된다.
