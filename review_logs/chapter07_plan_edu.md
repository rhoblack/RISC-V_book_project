## 서문: Part 3의 교육적 위치

Ch07은 Part 2(단일 사이클 프로세서)의 완성 직후, Part 4(5단계 파이프라인)의 직전에 배치된다.
이 위치가 갖는 교육적 함의는 크게 두 가지다.

**첫째, 자신감이 최고조인 시점이다.**
Ch06에서 피보나치 수열을 CPU로 실행하는 대성취를 달성한 독자는 "나는 CPU를 만들 수 있다"는 자신감을 보유한 상태로 Ch07에 진입한다. 이 에너지를 소진시키지 않고 방향을 전환하는 것이 Ch07 학습 설계의 핵심 과제다.

**둘째, 파이프라인의 직접적 전제 조건이다.**
멀티사이클에서 단계 분할(stage division)과 자원 공유(resource sharing)를 체감하지 않은 독자는 파이프라인에서 "왜 레지스터를 삽입하는가?"라는 질문에 직관적 답을 내놓지 못한다. Ch07은 파이프라인 레지스터의 필요성을 논리적으로 도출시키는 발판이다.

> **교육심리전문가 주석 (반영)**: "멀티사이클은 단일 사이클 성취 직후 배치되므로 자신감이 높은 시점. FSM 설계는 Verilog 경험자에게 친숙한 패턴이라 심리적 부담이 낮음."
> 이 주석에서 핵심은 **FSM에 대한 선제적 소개를 Ch07에서 담당**해야 한다는 점이다. Ch08에서 FSM 제어 유닛을 구현할 때 독자가 "데이터패스 구조는 이미 알고, FSM만 새로 배우면 된다"는 분리 인식을 가질 수 있도록, Ch07은 데이터패스 설계만 전담한다.

### 총평 및 핵심 경고

**7.3절이 유일한 과부하 위험 구간이다.** A/B 레지스터, ALUOut, MDR, 두 종류의 공유 MUX가 단일 절에 모두 등장할 경우, 독자는 "레지스터가 왜 이렇게 많은가?"라는 혼란에 빠질 수 있다.

**권장 분할 전략**:
- 7.3.1절: IF와 ID/EX 단계에 관련된 레지스터 (PC 레지스터, A/B 레지스터, ALUOut)
- 7.3.2절: MEM/WB 단계에 관련된 레지스터와 MUX (MDR, 공유 메모리 입력 MUX, WB MUX)

각 소절의 시작에 "이번 소절에서 추가할 요소: N개" 명시 → 독자가 현재 작업의 범위를 인지할 수 있음.

## 3. 학습 흐름 설계 (도입→개념→예시→실습→정리)

### 7.1절 — 단일 사이클의 한계

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | Ch06 성취와 한계의 이중 구조 | "여러분의 CPU는 피보나치를 계산했습니다. 그런데 속도는 얼마였나요?" — 성취 기억에서 문제 의식 자연 유도 |
| **개념** | 클럭 주기 = 임계 경로 지연 공식 | `T_clk ≥ t_IMEM + t_Dec + t_ALU + t_DMEM + t_WB` 수식 제시. 단위: ns 단위 실제 Basys 3 타이밍 수치 병기 |
| **예시** | ADD vs LOAD 명령어 임계 경로 비교 SVG | ADD는 IMEM+Dec+ALU만 사용, LOAD는 전체 경로 사용. "ADD가 LOAD 때문에 느려지는" 구조를 시각화 |
| **실습** | 종이 계산 실습 (타이밍 수치 주어질 때 최대 클럭 주파수 계산) | `f_max = 1 / T_critical`. 간단한 수치로 5분 이내 수행 가능한 미니 실습 |
| **정리** | metacognition: "지금까지 이해한 문제는 무엇인가?" | 문제 정의 3문장으로 요약 + 7.2절 예고 문구 |

### 7.2절 — 멀티사이클의 핵심 아이디어

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | 요리 코스 비유 — 비유 → 한계 명시 → 하드웨어 용어 복귀 3단계 | "요리사가 애피타이저를 완성한 뒤 메인 요리로 넘어가듯, CPU도 각 단계를 순서대로 처리합니다. 단, 비유의 한계: 요리사는 한 번에 하나의 손님만 서비스하지만, 파이프라인(Ch09)에서는 여러 명을 동시에 서비스합니다." |
| **개념** | 단계 분할 + 자원 공유 두 아이디어 순차 제시 | 단계 분할: 한 명령어가 여러 클럭 사이클에 걸쳐 실행됨. 자원 공유: 단일 메모리와 단일 ALU를 여러 단계에서 재사용 |
| **예시** | 단일 사이클 vs 멀티사이클 자원 사용 비교 표 | 단일 사이클: IMEM 1개 + DMEM 1개 + ALU 1개 + 분기 덧셈기 1개. 멀티사이클: 메모리 1개(공유) + ALU 1개(공유). 하드웨어 면적 차이 직관적 제시 |
| **실습** | LOAD 명령어의 5사이클 실행 순서를 빈칸으로 채우는 표 완성 | 사이클 1: [  ] → 사이클 2: [  ] → ... → 사이클 5: [  ]. 빈칸에 IF/ID/EX/MEM/WB 단계 동작 기입 |
| **정리** | tip aside: "중간 결과 레지스터가 왜 필요한가?" | "각 단계의 결과를 다음 사이클까지 보존해야 하므로, 단계 경계마다 레지스터가 필요합니다." — 7.3절 진입 동기 |

### 7.3절 — 멀티사이클 데이터패스 설계

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | 단일 사이클 데이터패스 블록 다이어그램(Ch06 재사용)에서 추가할 요소 표시 | "Ch06에서 완성한 데이터패스에 무엇을 추가해야 할까요?" — 기존 지식 재활성화 + 추가 작업 범위 명시 |
| **개념** | 7.3.1: A/B/ALUOut 레지스터 역할 설명 → 7.3.2: MDR + 공유 MUX 설명 | 각 소절: 레지스터 1~2개씩 점진적 추가. Gradual Reveal: 소절마다 데이터패스에 요소 1~2개씩 추가된 SVG 제시 |
| **예시** | LOAD 명령어 실행 시 각 사이클에서 레지스터 값 변화 추적 표 | 사이클별 A/B/ALUOut/MDR 값의 변화를 구체적 수치로 제시 (`A←rs1`, `ALUOut←A+imm`, `MDR←Mem[ALUOut]` 등) |
| **실습** | SystemVerilog 코드 작성 — 빈칸 완성 형태로 A/B 레지스터 선언 및 연결 | 모듈 골격과 포트 선언이 주어지고, `always_ff` 블록 내용만 채우는 방식으로 인지 부담 조절 |
| **정리** | metacognition: "추가된 하드웨어 요소를 목록으로 확인" | 추가된 요소 체크리스트 (A reg ☐, B reg ☐, ALUOut reg ☐, MDR ☐, 공유 메모리 MUX ☐). 독자가 스스로 완성도 확인 |

### 7.4절 — 단일 사이클 vs 멀티사이클 데이터패스 비교

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "두 CPU를 나란히 놓겠습니다" — 비교 프레이밍 | 단일 사이클 블록 다이어그램과 멀티사이클 블록 다이어그램 나란히 배치 |
| **개념** | 하드웨어 면적 절감의 정량적 근거 + 중간 레지스터 도입의 비용 분석 | LUT 사용량 비교(예: 단일 사이클 약 X LUT vs 멀티사이클 약 Y LUT), 레지스터 추가 비용은 4×32=128 FFs |
| **예시** | Vivado 합성 결과 비교 표 (실측값) | 면적(LUT/FF/BRAM), 최대 클럭 주파수(Fmax), 명령어당 사이클 수(CPI) 비교 |
| **실습** | 없음 — 분석 활동으로 대체 | "표를 보고 '멀티사이클이 단일 사이클보다 항상 좋은가?'라는 질문에 3문장으로 답하시오" (개방형 질문) |
| **정리** | interview aside: "멀티사이클 설계의 실무적 의의" + Ch08 예고 | "현대 프로세서는 멀티사이클도 단일 사이클도 아닙니다 — 파이프라인입니다. 하지만 멀티사이클은 FSM 제어, 자원 공유, 단계 분할을 모두 포함하므로 이후 설계의 든든한 기반입니다." |

> **문제 1 — 레지스터 역할 식별**
>
> 멀티사이클 데이터패스에 추가되는 네 가지 중간 결과 레지스터(A, B, ALUOut, MDR)를 각각 한 문장으로 설명하시오.
>
> *기대 답변 핵심*:
> - A 레지스터: rs1에서 읽은 값을 저장하여 다음 사이클(EX)에서 ALU 입력으로 제공
> - B 레지스터: rs2에서 읽은 값을 저장하여 다음 사이클(EX)에서 ALU 입력 또는 메모리 쓰기 데이터로 제공
> - ALUOut 레지스터: ALU의 연산 결과를 저장하여 다음 사이클(MEM 또는 WB)에서 사용
> - MDR(Memory Data Register): 메모리에서 읽은 데이터를 저장하여 다음 사이클(WB)에서 레지스터 파일에 쓰기
>
> *채점 기준*: 각 레지스터가 "어느 단계에서 기록되고, 어느 단계에서 읽히는가"를 명시하면 정답.

### [이해 수준 — 이해(Understand): 차이를 설명할 수 있다]

> **문제 3 — LOAD 명령어 실행 흐름 설명**
>
> 멀티사이클 프로세서에서 `LW x5, 4(x3)` 명령어가 5개 사이클에 걸쳐 실행될 때, 각 사이클에서 어떤 동작이 발생하는지 순서대로 서술하시오.
> (힌트: 어떤 레지스터/메모리에 어떤 값이 기록되는가를 중심으로 기술하시오.)
>
> *기대 답변 구조*:
> 1. 사이클 1 (IF): PC가 가리키는 주소에서 명령어를 공유 메모리에서 읽어 IR(Instruction Register)에 저장. PC ← PC + 4.
> 2. 사이클 2 (ID): IR을 디코딩, rs1(x3) 값 → A 레지스터, 즉치수 4를 부호 확장.
> 3. 사이클 3 (EX): ALU가 A + 4 계산. 결과 → ALUOut 레지스터.
> 4. 사이클 4 (MEM): Mem[ALUOut] 읽기 (공유 메모리 사용). 결과 → MDR.
> 5. 사이클 5 (WB): MDR 값을 rd(x5)에 기록.
>
> *채점 기준*: 5개 사이클의 동작이 올바르고, 중간 레지스터 이름이 정확하면 정답.

### [적용 수준 — 적용(Apply): SystemVerilog 코드를 작성할 수 있다]

> **문제 4 — A/B 레지스터 SystemVerilog 구현**
>
> 아래 빈칸을 채워 A 레지스터와 B 레지스터의 `always_ff` 블록을 완성하시오.
> 조건: 클럭 상승 에지에 동기화, 비동기 리셋 지원.
>
> ```systemverilog
> module reg_ab (
>    input  logic        clk,
>    input  logic        rst_n,
>    input  logic [31:0] rs1_data,   // 레지스터 파일 rs1 출력
>    input  logic [31:0] rs2_data,   // 레지스터 파일 rs2 출력
>    output logic [31:0] a_reg,      // A 레지스터 출력
>    output logic [31:0] b_reg       // B 레지스터 출력
> );
>
>    always_ff @(posedge clk or negedge rst_n) begin
>       if (!rst_n) begin
>          a_reg <= ____;    // (1) 리셋값
>          b_reg <= ____;    // (2) 리셋값
>       end else begin
>          a_reg <= ____;    // (3) ID 단계: rs1 값 래치
>          b_reg <= ____;    // (4) ID 단계: rs2 값 래치
>       end
>    end
>
> endmodule
> ```
>
> *정답*: (1) 32'b0, (2) 32'b0, (3) rs1_data, (4) rs2_data
>
> *채점 기준*: 리셋값이 0이고, 래치 대상이 올바른 입력 신호면 정답. `always_ff` 와 `posedge clk`의 사용이 정확해야 함.

> **문제 5 — MDR 레지스터 + WB MUX SystemVerilog 구현 (도전 문제)**
>
> 멀티사이클 데이터패스에서 WB(Write-Back) 단계의 동작을 구현하시오.
> MDR과 ALUOut 중 wb_sel 신호에 따라 레지스터 파일에 쓸 값을 선택하는 로직을 작성하시오.
> (`wb_sel`: 0이면 ALUOut, 1이면 MDR)
>
> ```systemverilog
> // WB MUX 및 MDR 래치 (빈칸 완성)
> logic [31:0] mdr_reg;
> logic [31:0] wb_data;
>
> // MDR 래치 (MEM 단계에서 기록)
> always_ff @(posedge clk or negedge rst_n) begin
>    if (!rst_n) mdr_reg <= ____;       // (1)
>    else        mdr_reg <= ____;       // (2) 메모리 읽기 데이터 래치
> end
>
> // WB MUX (조합 논리)
> always_comb begin
>    case (wb_sel)
>       1'b0: wb_data = ____;           // (3) R/I/U/J 타입: ALU 결과 사용
>       1'b1: wb_data = ____;           // (4) Load 타입: 메모리 데이터 사용
>       default: wb_data = 32'b0;
>    endcase
> end
> ```
>
> *정답*: (1) 32'b0, (2) mem_read_data, (3) alu_out_reg, (4) mdr_reg
>
> *채점 기준*: MDR은 `always_ff`, WB MUX는 `always_comb` 사용. 신호 이름이 문맥과 일치하면 정답.

### [분석 수준 — 분석(Analyze): 성능 트레이드오프를 분석할 수 있다]

> **문제 6 — 트레이드오프 분석**
>
> 아래 Vivado 합성 결과를 보고 물음에 답하시오.
>
> | 항목 | 단일 사이클 | 멀티사이클 |
> |------|-----------|-----------|
> | LUT 사용량 | 1,850개 | 1,240개 |
> | FF 사용량 | 420개 | 550개 |
> | 최대 클럭 주파수 | 28 MHz | 62 MHz |
> | Load 명령어 CPI | 1 | 5 |
>
> (가) 멀티사이클이 단일 사이클보다 LUT는 적게 사용하지만 FF는 더 많이 사용하는 이유를 설명하시오.
>
> (나) 프로그램이 100% Load 명령어로만 구성된다고 가정하면, 단일 사이클과 멀티사이클 중 어느 것이 실행 시간이 짧은가? 계산 과정을 포함하여 답하시오.
> (단, 명령어 1,000개, 1ns = 10^-9 s 기준)
>
> (다) 일반적인 RISC-V 프로그램(Load 비율 약 20%)에서는 어느 방식이 유리한지 논하시오.
>
> *기대 답변*:
> - (가): LUT 감소는 IMEM/DMEM 분리 → 통합 메모리로 회로 단순화, 덧셈기 2개 → 1개 공유. FF 증가는 A, B, ALUOut, MDR 레지스터 4종(총 128 FF) 추가 때문.
> - (나): 단일 사이클: 1,000 × (1/28MHz) = 35.7 μs. 멀티사이클: 1,000 × 5 × (1/62MHz) = 80.6 μs. → 단일 사이클이 유리.
> - (다): 평균 CPI 계산 필요. Load 20%, 나머지(R/I 등) 80%가 CPI=4라 가정하면 평균 CPI = 0.2×5 + 0.8×4 = 4.2. 멀티사이클: 1,000 × 4.2 × (1/62MHz) = 67.7 μs. 단일 사이클이 여전히 불리하지 않을 수 있으나, Fmax 차이가 극복 가능한 CPI 증가인지가 핵심 논점. (모범 답안보다 논리 구조가 중요함.)
>
> *채점 기준*: (가) LUT/FF 변화의 구체적 원인 명시. (나) 수치 계산 정확성. (다) 트레이드오프를 정성적으로라도 논리 있게 서술하면 부분 점수 인정.

### 학습 연결 메커니즘 4가지

**1. 미완성 아키텍처 효과 (Completion Effect)**

Ch07은 멀티사이클 데이터패스를 완성하지만, 제어 신호를 연결하지 않으므로 CPU가 동작하지 않는 상태로 마무리된다. 이 "미완성" 상태가 Ch08에 대한 자연스러운 필요성과 기대감을 생성한다.

구체적 구현:
```
Ch07.5 (요약 절) 마지막 문장:
"이 데이터패스는 아직 동작하지 않습니다. 모든 부품이 연결되었지만,
 지휘자가 없습니다. Ch08에서 FSM 제어 유닛을 설계하여 지휘자 역할을 부여합니다."
```

**2. 개념 분리를 통한 이중 부담 방지**

FSM 개념을 Ch07에서 데이터패스와 함께 학습하면, 독자는 "데이터패스 이해 + FSM 이해 + 연결 이해"를 동시에 처리해야 한다. Ch07에서 데이터패스를 완전히 소화하면, Ch08에서 FSM 설계에만 인지 자원을 집중할 수 있다.

**3. 사이클 수 직관 형성 → Ch08 상태 전이도 이해 기반**

Ch07에서 "LW는 5사이클, R 타입은 4사이클"을 직관적으로 이해하면(표, SVG 등으로), Ch08에서 상태 전이도를 볼 때 각 상태가 왜 분기되는지 즉시 납득이 된다. 이 사전 직관이 없으면 Ch08 상태 전이도가 단순한 암기 대상으로 전락한다.

**4. 데이터패스 인터페이스 확인 → Ch08 FSM 출력 신호 목록 자연 도출**

Ch07에서 "멀티사이클 데이터패스가 어떤 제어 신호를 필요로 하는가"를 정리하면, Ch08에서 FSM이 생성해야 할 출력 신호 목록이 자동으로 결정된다. 이 연결을 Ch07.5에서 명시적으로 제시한다.

구체적 구현:
```
Ch07.5 aside (tip):
"이 데이터패스를 동작시키려면 아래 제어 신호가 필요합니다.
 Ch08의 FSM은 이 신호들을 상태에 따라 생성합니다:
 - pc_write: PC 갱신 허용
 - ir_write: IR(Instruction Register) 갱신 허용
 - a_write / b_write: A/B 레지스터 갱신
 - alu_out_write / mdr_write: ALUOut/MDR 갱신
 - wb_sel, pc_sel, alu_src_a, alu_src_b: MUX 선택"
```

## 10. 교육 설계자 종합 평가 및 권고사항

### Ch07 학습 설계의 핵심 과제

1. **과소 도전(Under-Challenge) 방지**: Ch06의 대성취 직후이므로 독자의 자신감이 높다. 너무 쉬운 내용만 다루면 지루함이 발생한다. 7.3절의 SystemVerilog 실습(문제 4, 5)으로 적절한 인지 참여를 유지해야 한다.

2. **과잉 예고 방지**: FSM(Ch08) 내용을 Ch07에서 너무 많이 공개하면 Ch08의 학습 동기가 감소한다. "필요성 언급"과 "내용 미공개"의 균형이 중요하다.

3. **7.3절 인지 부하 관리**: 유일한 과부하 위험 구간. 7.3.1 / 7.3.2 소절 분할과 SVG Gradual Reveal 3단계를 반드시 구현해야 한다.

### 기술 저자에 대한 권고사항

1. **7.3절을 반드시 두 소절(7.3.1, 7.3.2)로 분할할 것**: A/B/ALUOut을 먼저, MDR/공유 MUX를 나중에. 두 소절 사이에 "지금까지 추가한 것을 확인합시다" metacognition 박스 1개 배치.

2. **SVG Gradual Reveal 3단계를 선행 제작할 것**: ch07_sec01_single_cycle_reference.svg, ch07_sec03_datapath_step1.svg, ch07_sec03_datapath_complete.svg 순서로 제작. 각 SVG에서 새로 추가된 요소는 파란색(#2563EB) 강조.

3. **FSM 내용은 "예고"로만 제한할 것**: Ch07 본문에서 FSM 상태 전이도, 상태 인코딩, Moore/Mealy 구분을 본격적으로 다루지 말 것. "Ch08에서 설계합니다"로 명확히 위임.

4. **7.4절을 인지 부하 0의 "정리 구간"으로 유지할 것**: 7.4절은 새 개념 없이 비교와 분석만 수행하는 절이다. 새로운 구현 코드를 이 절에 배치하지 말 것.

5. **연습문제 6번 수치를 실제 Vivado 합성 결과로 교체할 것**: 문제 6의 표에 제시된 LUT, FF, Fmax 수치는 현재 예시값이다. 실제 합성을 수행한 후 측정값으로 교체해야 신뢰성 확보.
