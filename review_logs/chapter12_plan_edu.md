### 12.1 구조적 해저드: RV32I에서의 발생 조건

**도입 방식**
- "세 가지 해저드 중 아직 다루지 않은 것이 하나 남았습니다" — 완결 욕구 자극
- Ch10(RAW), Ch11(제어 해저드) 복습 → "그렇다면 하드웨어 충돌은?"
- 비유: 세탁소 비유 확장 — "세탁기 1대에 세탁물과 이불을 동시에 넣으려는 상황"

**핵심 개념 (신규 개념 수: 2개)**
1. 구조적 해저드(Structural Hazard)의 정의: 동일 하드웨어 자원 동시 접근
2. RV32I에서의 발생 조건: 통합 메모리(Princeton)에서 IF와 MEM이 동시 접근 시 충돌

**예시/비유**
- Harvard 구조가 이미 Ch09에서 도입됨 → "여러분이 Ch09에서 IMEM/DMEM을 분리한 결정이 바로 이 해저드를 예방한 것이었습니다" 사후 연결
- RISC-V 스펙이 구조적 해저드를 아키텍처 결정으로 제거한 설계 철학 소개

**실습**
- 없음 (이 절은 이해 수준 — 구현은 이미 완료됨)
- 대신 "스스로 점검" 박스: "Ch07 멀티사이클에서 Princeton 구조를 사용했을 때 구조적 해저드가 없었던 이유는?"

**점검 질문**
- 구조적 해저드가 데이터 해저드와 다른 점은 무엇인가?
- RV32I 파이프라인에서 레지스터 파일에도 구조적 해저드가 발생할 수 있는 경우는?

**인지 부하 평가**: 신규 개념 2개 — 낮음 (기존 구현의 사후 설명). 가장 가벼운 절로 배치 적절.

### 12.2 WB-ID 포워딩 (레지스터 파일 포워딩)

**도입 방식**
- 문제 제기: "MEM/WB 스테이지가 레지스터에 쓰는 동시에, ID 스테이지가 같은 레지스터를 읽는다면?"
- 타이밍 다이어그램으로 WB와 ID가 같은 사이클에 발생하는 상황 시각화
- 비유: "편지를 쓰면서 동시에 그 편지를 읽으려는 상황 — 선생님이 학생에게 답을 적어주는 동시에 학생이 칠판에서 그 답을 보는 것"

**핵심 개념 (신규 개념 수: 3개)**
1. WB-ID 포워딩의 필요 조건: `wb_reg_write && (wb_rd_addr != 0) && (wb_rd_addr == id_rs1 || id_rs2)`
2. 레지스터 파일 내부 포워딩: 동기 쓰기 + 비동기 읽기 LUTRAM에서는 자동 처리될 수도 있음 (FPGA 추론 동작 주의)
3. 명시적 포워딩 MUX 추가: 안전한 구현을 위한 `always_comb` 포워딩 로직

**예시/비유**
- EX-EX(Ch10 2'b01), MEM-EX(Ch10 2'b10)에 이어 WB-ID가 세 번째 포워딩 경로임을 표로 정리
- "Ch10에서 만든 포워딩 유닛에 하나의 경우를 추가하는 것" — 확장 용이성 강조

**실습**
- 포워딩 유닛 수정: `forward_a`, `forward_b` 조건에 WB-ID 케이스 추가
- Vivado LUTRAM 추론 시 자동 처리 여부를 시뮬레이션으로 검증하는 미니 실험

**점검 질문**
- WB-ID 포워딩을 MUX 없이 구현할 수 있는 조건은 무엇인가? (LUTRAM 동시 읽쓰기)
- MEM-EX 포워딩(2'b10)과 WB-ID 포워딩이 동시에 성립할 때 어느 것이 우선인가?

**인지 부하 평가**: 신규 개념 3개 — 보통. Ch10 포워딩 유닛을 확장하는 구조이므로 기존 스키마 활용 가능. 과도하지 않음.

### 12.3 5단계 파이프라인 통합

**도입 방식**
- "지금까지 Ch09~Ch12.2에서 설계한 모든 모듈을 하나의 최상위 모듈로 연결할 시간입니다"
- 전체 모듈 연결 다이어그램(SVG) 제시: 데이터패스 + 포워딩 유닛 + 해저드 감지 유닛 + 분기 유닛
- 감정 관리: "코드가 길지만 대부분은 이미 만든 것들입니다" 안심 문구

**핵심 개념 (신규 개념 수: 2개)**
1. 파라미터화 설계: `parameter DATA_WIDTH = 32` 등으로 재사용성 향상
2. 포트 연결 체계: 신호 이름 충돌 방지 규약, 제어 신호 버스(struct) 활용

**예시/비유**
- "레고 블록을 조립하는 단계 — 개별 블록을 이미 모두 만들었고 지금은 설명서에 따라 연결만 하면 됩니다"
- 모듈 계층 구조 트리: `rv32i_pipeline_top` → 하위 모듈 목록

**실습**
- 순차적 연결 실습: 먼저 포워딩 유닛만 연결 → 해저드 유닛 추가 → 분기 유닛 추가
- 각 단계에서 시뮬레이션으로 동작 확인 (단계별 검증 후 다음 연결)
- 자주 발생하는 포트 연결 오류 목록 제공 (FAQ 박스)

**점검 질문**
- `ctrl_t` 구조체를 파이프라인 레지스터로 전파할 때 주의할 점은?
- WB-ID 포워딩과 EX-EX 포워딩이 동시에 성립하는 시나리오를 만들 수 있는가?

**인지 부하 평가**: 신규 개념 2개 (파라미터화, 포트 규약) — 낮음. 대부분이 기존 모듈 연결. 단계적 구현으로 부하 분산 권장.

## 3. Part 4 마일스톤 연결 — 학습 서사

### Part 4 학습 서사 설계

```
Ch09 — 파이프라인 기초 (선 긋기)
  "멀티사이클 FSM의 각 상태를 동시에 실행하면 파이프라인입니다"
  → 성취: NOP 삽입 파이프라인 동작 확인
  → 감정: 호기심 ("잠깐, 이렇게 단순하다고?") → 곧 불안으로 전환 예고

Ch10 — 포워딩 (첫 번째 위기 극복)
  "RAW 해저드가 파이프라인을 망가뜨린다 — 포워딩으로 해결"
  → 성취: 1~10 합산 x10=55 검증
  → 감정: ⚠️최고 불안 → ★성취 (디버깅 통과)

Ch11 — 분기 처리 (두 번째 위기 극복)
  "루프 명령어가 파이프라인을 혼란시킨다 — flush로 해결"
  → 성취: BNE 루프 1~10 합산 x2=55 검증 (★★ 대성취)
  → 감정: 복잡한 flush/stall 우선순위 → 루프 실행 성공

Ch12 — 완성 (통합과 클라이맥스)
  "마지막 조각을 맞추고, 진짜 알고리즘을 실행하라"
  → 성취: 버블정렬 FPGA 실행 (★★★ 감정적 클라이맥스)
  → 감정: 통합 작업의 낮은 불안 → 버블정렬 성공의 최고조 성취감
```

### 버블정렬 FPGA 실행이 감정적 클라이맥스인 이유

**기술적 완결성**
- 버블정렬은 R 타입(비교), I 타입(로드), S 타입(스토어), B 타입(분기), J 타입(루프 구조) 등 RV32I 핵심 명령어 유형을 모두 포함
- 포워딩(RAW 해저드), 분기 플러시, 구조적 해저드 해결이 동시에 작동해야만 올바른 결과 도출
- 즉, "부품 하나라도 잘못되면 실패하는" 통합 검증 특성 → 성공 시 모든 것이 검증됨

**감정적 구조**
- Ch10의 "합산 성공"은 분기 없는 직선 실행 → 상대적으로 낮은 성취감
- Ch11의 "루프 합산 성공"은 분기 포함 → 더 높은 성취감
- Ch12의 "버블정렬 FPGA 성공"은 실제 하드웨어에서 정렬 알고리즘 완료 → 추상적 코드가 물리 세계에서 작동하는 최초의 경험

**교육적 완결성**
- "Verilog 경험자 → RISC-V 파이프라인 프로세서 설계자"로의 정체성 전환
- 이후 Part 5(캐시), Part 6(AMBA)는 이 기반 위에 쌓는 확장 — Ch12가 기반의 완성점
- "나는 CPU를 만들었다"는 서술 가능한 최초 시점

## 4. 12.4절 실습 설계 — 버블정렬 스캐폴딩

### 스캐폴딩 설계 원칙
- 처음부터 버블정렬 전체를 주지 않는다
- 학생이 성공 경험을 단계적으로 축적하며 자신감을 키운다
- 디버깅 가이드를 사전에 제공하여 좌절 방지

### 단계 1: 2원소 교환 (기초 — 제공)
```
목적: 메모리 로드-스토어 + 조건 분기의 기본 동작 확인
프로그램: mem[0], mem[1] 두 값을 비교하여 교환
완성 코드 제공: 학생은 이 코드를 시뮬레이션으로만 실행
확인 사항: LW, SW, BLT 명령어가 파이프라인에서 올바르게 실행되는가?
```

### 단계 2: n원소 1패스 (중간 — 가이드 후 작성)
```
목적: 내부 루프(i=0~n-2 순회) 구현
가이드 제공: 레지스터 역할 배분 (x1=배열 기저 주소, x2=인덱스, x3=n, x4=임시값)
학생 작성: BLT 루프 조건, 주소 계산 (ADDI로 인덱스 증가), 교환 로직
확인 방법: 1패스 후 가장 큰 원소가 배열 끝으로 이동했는가?
안심 장치: "1패스 검증 성공 = 이미 핵심을 구현한 것"
```

### 단계 3: 완전한 버블정렬 (심화 — 독립 작성)
```
목적: 외부 루프(패스 반복 횟수) 추가
학생 작성: 외부 루프 카운터, 내부 루프 재진입 로직, 최적화 조기 종료(선택)
테스트 배열: [5, 3, 8, 1, 9, 2, 7, 4] → [1, 2, 3, 4, 5, 7, 8, 9]
시뮬레이션 검증: $monitor로 메모리 내용 단계별 출력
```

### 단계 4: FPGA 다운로드 (마일스톤)
```
목적: 실제 하드웨어 동작 확인
제공: XDC 제약 파일, 초기 메모리 값 설정 방법, ILA 설정 가이드
학생 직접: 비트스트림 생성 → Basys 3 다운로드 → 스위치/LED로 정렬 결과 확인
성공 기준: 입력 배열이 오름차순으로 정렬되어 LED/UART에 표시됨
```

### 학생이 직접 하는 부분 vs 제공되는 부분

| 항목 | 제공 여부 | 근거 |
|------|---------|------|
| 2원소 교환 완성 코드 | 제공 | 첫 성공 경험 보장 |
| 레지스터 역할 배분 | 제공 (가이드) | 어셈블리 관례 학습 지원 |
| 내부 루프 작성 | 학생 직접 | 핵심 학습 목표 |
| 외부 루프 작성 | 학생 직접 | 독립 적용 능력 평가 |
| XDC 제약 파일 | 제공 | FPGA 설정은 Ch20에서 심화 예정 |
| ILA 트리거 설정 | 제공 | 디버깅 가이드 차원 |
| 초기 메모리 설정 | 가이드 제공 | `$readmemh` 활용 복습 |
| 조기 종료 최적화 | 선택 도전 | 심화 과제로 제시 |

### 디버깅 가이드 구조 (instructor-tip 박스)
1. 정렬 결과가 전혀 틀린 경우 → 포워딩 유닛 forward_a/b 신호 확인
2. 첫 교환은 맞지만 이후 틀린 경우 → 분기 플러시 타이밍 확인
3. 무한 루프 발생 → BLT 조건과 카운터 증가 로직 확인
4. FPGA에서만 틀린 경우 → 시뮬레이션/합성 차이, 레지스터 초기화 확인

## 5. 12.5절 비교 설계 — 소크라테스식 접근

### 비교 표 제시 순서 설계

일반적인 접근: 표를 먼저 보여주고 설명
→ 문제: 학생은 숫자를 수동적으로 받아들임, "왜 파이프라인인가"를 스스로 발견하지 못함

**권장 접근: 소크라테스식 4단계**

**1단계: 예측 유도 (버블정렬 실행 직후)**
```
질문 박스 제시:
"버블정렬을 성공적으로 실행했습니다. 이제 단일 사이클, 멀티사이클, 파이프라인으로 각각 실행한다면
어느 것이 가장 빠를까요? 그 이유를 먼저 생각해보세요."

→ 잠시 생각할 시간 유도 (1분 예상)
→ 학생의 직관(보통 "파이프라인이 당연히 빠를 것")을 활성화
```

**2단계: 개념 복습 (CPI × 클럭 주파수 분석 틀)**
```
표 1: CPI 비교 (수치 없이 상대적 관계만)
  - 단일 사이클: CPI = 1 (이론) — 그러나 클럭이 느리다
  - 멀티사이클: CPI = 3~5 (명령어 유형별) — 그러나 클럭이 중간
  - 파이프라인: CPI ≈ 1 (이상적) + 해저드 페널티 — 클럭이 빠르다

질문: "CPI만 보면 단일 사이클과 파이프라인이 비슷합니다. 그런데 왜 파이프라인을 쓸까요?"
→ 학생이 "클럭 주파수" 차이를 스스로 떠올리도록 유도
```

**3단계: 데이터 공개 (Vivado 합성 실측치)**
```
표 2: Basys 3 합성 결과 (실측치 기반)

| 지표 | 단일 사이클 | 멀티사이클 | 파이프라인 |
|------|-----------|---------|---------|
| 최대 클럭 (MHz) | ~25 | ~50 | ~100 |
| CPI (버블정렬) | 1.0 | 4.1 | ~1.2 |
| 실행 시간 상대값 | 1.0 (기준) | ~0.82 | ~0.21 |
| LUT 사용량 | ~3,000 | ~2,800 | ~4,200 |
| 설계 복잡도 | 낮음 | 중간 | 높음 |

→ "예측이 맞았나요? 어디서 틀렸나요?" 자기 확인 유도
```

**4단계: 심층 분석 — "언제 파이프라인이 불리한가?"**
```
역발상 질문: "그렇다면 파이프라인이 최선이 아닌 경우는 없을까요?"
  → 면적 제약이 심한 마이크로컨트롤러: 단일 사이클이 유리
  → 실시간 예측 가능한 실행 시간이 필요한 경우: 멀티사이클 또는 단일 사이클
  → 저전력 IoT: 클럭 주파수보다 에너지 효율

→ "도구에는 적합한 용도가 있다" — 절대적 우열이 아닌 트레이드오프 사고 형성
→ 면접 포인트 박스: "파이프라인이 항상 최선인가?" 질문 대응 방법
```

### "왜 파이프라인인가"에 학생이 스스로 도달하게 하는 핵심

학생이 경험하는 인식 과정:
1. "CPI=1이면 단일 사이클과 같은 것 아닌가?" (오개념)
2. 실측치 확인 → 파이프라인이 5배 빠름 (인지 충돌)
3. "클럭 주파수가 4배 높으니 CPI 1.2도 충분히 빠르다" (스스로 해결)
4. "그러면 항상 파이프라인이 최선인가?" (심화 질문으로 연결)

이 과정에서 교사(책)는 질문만 하고, 학생이 표 데이터를 스스로 해석한다.
→ 수동적 지식 습득 → 능동적 분석 경험

**문제 4-1 (해저드 분석)**
다음 버블정렬 내부 루프의 RISC-V 어셈블리 코드에서 발생하는 모든 해저드를 찾고, 각 해저드를 처리하는 하드웨어 메커니즘(포워딩/스톨/플러시)을 표로 정리하라.

```
loop:
  LW   x5, 0(x1)      ; mem[i]

  ADDI x2, x2, 1
```

## 7. 절 순서/구조 개선 제안

### 현재 목차 순서 평가

| 절 | 학습 분량 | 인지 부하 | 학습 서사 흐름 | 평가 |
|----|---------|---------|-------------|------|
| 12.1 구조적 해저드 | 낮음 | 낮음 | "세 번째 해저드 완결" | 적절 |
| 12.2 WB-ID 포워딩 | 중간 | 중간 | "포워딩 유닛 확장" | 적절 |
| 12.3 통합 | 높음 | 낮음~중간 | "조립" | 적절 |
| 12.4 버블정렬 검증 | 높음 | 낮음 (감정 절) | "클라이맥스" | 적절 |
| 12.5 3종 비교 | 중간 | 중간 | "성찰·평가" | 위치 재고 필요 |
| 12.6 요약 | 낮음 | 낮음 | "냉각기" | 적절 |

### 개선 제안 1: 12.5절 위치 — 현재 순서 유지 권장 (단, 도입 보완)

**우려 사항**: 버블정렬 성공(감정 최고조) 직후 12.5절 3종 비교(분석·평가)로 전환 시 감정 낙차
**해결**: 12.5절 도입부에서 "방금 실행한 버블정렬 데이터를 기준으로" 연결하면 감정 연속성 유지 가능
**결론**: 목차 순서는 적절, 전환 문구 설계가 핵심

### 개선 제안 2: 12.1절 분량 최소화

**근거**: 구조적 해저드는 Ch09에서 이미 Harvard 구조로 해결됨 → 새로운 구현이 없음
**제안**: 12.1절을 2~3쪽 분량의 짧은 절로 유지, 나머지 지면을 12.4절(버블정렬)과 12.5절(3종 비교)에 배분
**기대 효과**: 학습자가 "이미 알고 있었던 것의 확인"으로 자신감을 가지고 12.2절로 진입

### 개선 제안 3: 12.3~12.4 사이 "중간 점검" 삽입

**현재 흐름**: 모듈 통합(12.3) → 버블정렬(12.4) — 검증 단계 없이 바로 복잡한 프로그램으로 진입
**제안**: 12.3절 후반에 "최소 검증" 단계 추가
  - 버블정렬 전에 단순 시퀀스(R 타입 5개, 포워딩 포함)로 통합 동작 확인
  - 이 단계를 통과해야 12.4절 진입 → 실패 원인 조기 격리
**기대 효과**: 버블정렬 실패 시 "통합 문제"인지 "버블정렬 코드 문제"인지 빠른 분리 가능

### 개선 제안 4: 12.6절에 "Part 4→Part 5 브릿지" 명시

**제안**: 요약 절에서 "완성된 파이프라인의 병목은 이제 CPU 코어가 아니라 메모리 접근 시간"임을 구체적 데이터로 제시
  - 버블정렬 실행 시 DMEM 접근 횟수 vs 총 사이클 비율
  - "다음 챕터에서 이 메모리 병목을 해결합니다" → Ch13 캐시로 자연스러운 동기 부여
**기대 효과**: Part 5가 "추가 주제"가 아닌 "논리적 다음 단계"로 인식됨

### 결론: 현재 목차 순서는 전반적으로 적절

현재 12.1→12.2→12.3→12.4→12.5→12.6 순서는 다음 흐름에 부합:
- 12.1: 완결(Resolution) — 세 번째 해저드 정리
- 12.2: 보완(Refinement) — WB-ID 포워딩 추가
- 12.3: 조립(Assembly) — 통합
- 12.4: 클라이맥스(Climax) — 버블정렬 FPGA
- 12.5: 성찰(Reflection) — 3종 비교
- 12.6: 마무리(Closure) — 요약 및 예고
