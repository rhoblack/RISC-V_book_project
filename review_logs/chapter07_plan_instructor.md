## 0. 검토 개요

Chapter 07은 Part 3의 첫 챕터로, 단일 사이클 프로세서(Ch04~06)에서 파이프라인(Ch09~12)으로 넘어가는 **교량(bridge) 역할**을 수행한다. 이 챕터의 교육적 성패는 기술적 정확성과 함께, "왜 멀티사이클을 배우는가"에 대한 수강생의 납득이 핵심이다.

수강생의 현재 심리 상태: **Ch06 피보나치 마일스톤 대성취 직후, 자신감 최고조**. 이 자신감이 자만으로 이어지지 않도록 단일 사이클의 한계를 날카롭게 인식시키면서도, 새로운 불안을 최소화하는 균형이 요구된다.

## 1. 수강생 막힘 포인트 Top 5

### [막힘 #1] 단일 사이클의 한계 — "왜 지금까지 만든 게 느린 건지 직관적으로 안 느껴진다" (7.1절)

**막힘 원인 분석**:

Ch06에서 피보나치를 완성한 수강생은 성취감이 충만하다. 그런데 첫 절에서 "이것은 비효율적입니다"라는 말을 들으면, 두 가지 반응 중 하나가 나온다.

- **저항형**: "잘 동작하는데 왜 비효율이라고 하나?" → 학습 동기 저하
- **수용형이지만 추상형**: "그렇군요, 그렇겠네요" → 피상적 이해에 그침

단일 사이클의 핵심 비효율은 **"Load 명령어가 느려서 ADD도 억울하게 기다려야 한다"**는 것인데, 수강생은 Vivado 타이밍 수치(25~35MHz)를 봤어도 그것이 구체적으로 어떤 고통인지를 체감하지 못한다.

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "선생님, 25MHz면 초당 2500만 명령어인데, 그게 왜 느린 건가요? 내가 필요한 프로그램은 잘 돌지 않나요?"

이 질문에 단순히 "성능이 낮아서요"라고 답하면 수강생은 동기 부여를 받지 못한다. **클럭 주파수와 실제 응용 성능 사이의 연결**을 구체적 수치로 보여줘야 한다.

**사전 해소 전략**: 7.1절 도입에서 "단일 사이클 vs 멀티사이클 성능 예고표"를 먼저 제시하고, "왜 이 수치가 나오는지"를 역순(결과 → 원인)으로 설명한다. "비효율"이라는 추상어 대신 **"Load 명령어가 전체 클럭을 인질로 잡는다"**는 구체적 서술이 효과적이다.

**권장 aside 박스**: `<aside class="tip">` — "단일 사이클이 느린 이유: 클럭 주기는 가장 긴 명령어가 결정한다"

### [막힘 #2] "공유"의 개념 — ALU 하나, 메모리 하나를 어떻게 시간을 나눠 쓰는가 (7.2절)

**막힘 원인 분석**:

수강생의 일반적 사고방식: "메모리가 하나라면, 명령어를 읽는 것(IMEM 역할)과 데이터를 읽는 것(DMEM 역할)을 같은 사이클에 할 수 없는 것 아닌가?" → **혼동 포인트**.

단일 사이클에서는 IMEM과 DMEM을 물리적으로 분리했기 때문에 동시 접근이 가능했다. 멀티사이클에서는 이 둘을 하나의 메모리로 통합하고 **시간 분할(time-division multiplexing)**로 해결한다는 개념이 직관적으로 받아들여지지 않는다.

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "메모리가 하나면 같은 사이클에 명령어도 읽고 데이터도 읽을 수 없는 거 아닌가요? 단일 사이클에서는 IMEM, DMEM을 따로 두었잖아요."

이 질문은 구조적 해저드(structural hazard)의 씨앗이기도 하다. Ch12에서 다시 나올 주제를 여기서 직관적으로 심어줄 기회이기도 하다.

**사전 해소 전략**: "같은 사이클 안에 두 가지를 동시에 할 필요가 없기 때문에 하나의 메모리로 충분합니다"라는 핵심 문장을 강조한다. **"멀티사이클에서는 명령어 읽기와 데이터 읽기가 서로 다른 사이클에 일어난다"**를 명시하고, 타이밍 다이어그램으로 어느 사이클에 어느 작업이 이루어지는지 시각화한다.

**권장 aside 박스**: `<aside class="faq">` — "메모리를 하나만 써도 되는 이유 — 시간 분할의 원리"

### [막힘 #3] 중간 결과 레지스터의 필요성 — "왜 A, B, ALUOut, MDR 레지스터가 갑자기 등장하는가" (7.3절)

**막힘 원인 분석**:

단일 사이클에서는 조합 논리가 한 클럭에 쭉 흘렀기 때문에, **"중간에 값을 붙잡아 두는" 레지스터**가 필요 없었다. 멀티사이클에서는 한 명령어가 여러 사이클에 걸쳐 실행되므로, 사이클과 사이클 사이에 중간 계산 결과를 저장해야 한다.

수강생이 혼동하는 이유:
- A, B 레지스터: "왜 레지스터 파일에서 직접 읽으면 안 되나?"
- ALUOut 레지스터: "ALU 결과를 왜 레지스터에 저장하나? 그냥 바로 쓰면 안 되나?"
- MDR (Memory Data Register): "메모리 데이터를 읽는데 왜 또 레지스터에 넣나?"

이들 레지스터의 공통 목적("사이클 경계에서 값을 보존한다")을 한 번에 이해시키지 않으면, 개별 레지스터의 용도를 외우는 방식으로 빠진다.

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "A, B 레지스터에서 레지스터 파일 값을 복사해두는데, 어차피 레지스터 파일은 사이클마다 안 변하잖아요. 왜 굳이 복사하나요?"

이 질문에는 미묘한 함정이 있다. 레지스터 파일은 WB 스테이지에서 **갱신될 수 있다**. 만약 다음 사이클에서 레지스터 파일이 갱신된다면, A/B 레지스터에 보존해두지 않으면 원래 값을 잃게 된다. (파이프라인의 포워딩 문제와 구조적으로 같은 종류의 이슈다.)

**사전 해소 전략**: "클럭 사이클 경계마다 값이 바뀔 수 있는 모든 신호는 저장해야 한다"는 원칙을 먼저 제시한다. A/B 레지스터 → ALUOut → MDR의 순서로, 각 레지스터가 어느 사이클 경계에서 어떤 값을 보존하는지 타이밍 다이어그램과 함께 보여준다. **"이 레지스터들이 나중에 파이프라인 레지스터가 됩니다"**라는 예고는 학습 동기를 높인다.

**권장 aside 박스**: `<aside class="metacognition">` — "중간 결과 레지스터를 왜 넣는가: 사이클 경계에서 값을 지키는 역할"

### [막힘 #4] 멀티사이클 vs 파이프라인 — "이것을 배우면 파이프라인은 따로 또 배워야 하나?" (7.2~7.4절, 전반적)

**막힘 원인 분석**:

수강생이 가장 먼저 품는 근본적 의문: **"멀티사이클은 왜 배우는가? 어차피 파이프라인을 배울 텐데."**

이 불안은 두 가지 형태로 나타난다:
- **현실적 의문**: "업계에서 멀티사이클 CPU를 쓰는 곳이 있나? 없으면 배울 필요가 없는 것 아닌가?"
- **교육적 의문**: "파이프라인을 바로 배우면 안 되나? 멀티사이클이 디딤돌이라는 말을 믿어야 하나?"

이 의문을 해소하지 못하면 7장 전체를 "억지로 해야 하는 것"으로 인식하게 되어 학습 효율이 급락한다.

**막힘 구체화**: 수강생이 속으로 품는 생각

> "교재가 '교량 역할'이라고 하는데, 솔직히 멀티사이클을 건너뛰고 파이프라인으로 바로 가면 안 되는 건가?"

**사전 해소 전략**: 7.1절 또는 챕터 도입부에서 **세 가지 이유를 명시**한다:

1. **개념적 이유**: 파이프라인 레지스터(IF/ID, ID/EX 등)가 멀티사이클의 A/B/ALUOut/MDR 레지스터와 직접 대응된다. 멀티사이클을 이해하면 파이프라인 레지스터가 "왜 거기 있는지" 자연스럽게 이해된다.
2. **실무적 이유**: 저전력 IoT 마이크로컨트롤러, 임베디드 코어에서 실제 사용됨. 면적 대비 성능 트레이드오프가 파이프라인보다 유리한 응용 영역이 존재한다.
3. **학습 구조적 이유**: Ch08 FSM 제어 유닛을 이해하면 "파이프라인의 각 스테이지가 사실 FSM 상태다"라는 핵심 통찰을 얻을 수 있다.

**권장 aside 박스**: `<aside class="faq">` — "멀티사이클을 왜 배우는가 — 파이프라인으로 바로 가면 안 되나요?"

### [막힘 #5] MUX 개수 증가와 데이터패스 복잡도 — "단일 사이클보다 오히려 복잡해 보인다" (7.3~7.4절)

**막힘 원인 분석**:

멀티사이클 데이터패스를 처음 보는 수강생은 직관에 반하는 경험을 한다. "자원을 공유해서 단순해져야 할 텐데, 왜 MUX가 더 많아졌지?"

멀티사이클에서 자원 공유를 위해 추가되는 MUX:
- PC 입력 MUX (ALUOut 또는 PC+4 또는 분기 목표)
- ALU 입력 MUX A (레지스터 파일 A, 또는 PC)
- ALU 입력 MUX B (레지스터 파일 B, 또는 4, 또는 즉치수, 또는 ...)
- 메모리 주소 MUX (PC 또는 ALUOut)

MUX가 증가하는 이유는 **"하나의 하드웨어를 여러 목적으로 재사용하기 때문"**인데, 이것을 먼저 설명하지 않으면 복잡도가 늘어나는 것처럼 보여서 혼란이 온다.

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "멀티사이클이 단일 사이클보다 하드웨어를 아낀다고 했는데, 다이어그램에서 MUX가 더 많아 보여요. 자원을 아끼는 게 맞나요?"

**사전 해소 전략**: 7.3~7.4절에서 "추가된 MUX는 자원 공유를 가능하게 하는 '스위치'다"라는 프레임을 명시한다. **자원 공유로 제거되는 것(별도 IMEM, 별도 DMEM, 별도 덧셈기)과 추가되는 것(MUX, 중간 레지스터)을 나란히 비교하는 표**를 제공하면, 순 이익이 분명해진다.

7.4절의 비교표를 이 맥락에서 미리 예고하는 것도 효과적이다.

**권장 aside 박스**: `<aside class="tip">` — "MUX가 늘어나도 하드웨어가 줄어드는 이유: 공유의 비용과 이득"

### 막힘 #4 해소: 챕터 도입부에서 "3가지 이유"를 명시

**챕터 0절 (도입) 권장 구성** — 수강생이 가장 먼저 읽을 내용:

> Chapter 07을 시작하기 전에, 왜 멀티사이클을 배우는지 세 가지 이유를 먼저 설명합니다. 이 이유를 이해하면 이 챕터 전체가 "억지로 해야 하는 것"이 아니라 "반드시 알아야 할 것"으로 느껴질 것입니다.

### 3.1 제안된 비유 원문 (TABLE_OF_CONTENTS.md)

> **핵심 비유**: 요리 코스 (한 요리사가 한 접시씩 완성) vs 단일 사이클 (모든 재료를 한꺼번에 처리)

### 3.2 매핑 정확도 검증

| 하드웨어 개념 | 요리 코스 비유 매핑 | 정확도 |
|------------|-----------------|:-----:|
| 멀티사이클: 명령어를 여러 사이클에 나눠 실행 | 한 접시를 여러 단계(재료 손질 → 조리 → 플레이팅)로 나눠 완성 | ✅ 정확 |

| 멀티사이클 CPI > 1: 한 명령어에 여러 사이클 | 한 접시에 여러 단계 시간이 필요 | ✅ 정확 |

### 3.3 비유의 한계점 (명시 필요)

**한계 1: 파이프라인과의 혼동 가능성**

요리 코스 비유는 **파이프라인 비유(세탁소 비유, 어셈블리 라인 비유)와 혼동**될 수 있다. 파이프라인에서는 여러 명령어가 동시에 서로 다른 단계에서 실행된다. 요리에 비유하면 "여러 접시를 동시에 서로 다른 조리 단계에서 준비하는 것"이다.

멀티사이클(요리 코스)과 파이프라인(여러 접시 동시 진행)의 차이를 7.1절 또는 7.5절에서 명시하지 않으면, Ch09에서 파이프라인을 배울 때 비유가 충돌한다.

**한계 2: "한 요리사"의 의미가 불명확**

"한 요리사"가 무엇에 해당하는지 명시되지 않으면 오해를 부를 수 있다. "한 요리사" = "하나의 ALU", "하나의 메모리"를 의미한다는 것을 텍스트로 명확히 해야 한다.

**한계 3: 클럭 주기 개념이 매핑되지 않음**

요리 코스 비유에서 "각 조리 단계 시간이 일정하다"는 의미는 자연스럽지 않다. 멀티사이클에서는 **각 사이클이 동일한 클럭 주기를 가진다**는 점이 핵심인데, "단계마다 시간이 다를 수 있다"는 요리의 현실이 비유의 정확성을 해친다.

---

### 3.4 비유 사용 권장 방법 (3단계 프로세스)

교재 비유 검증 원칙에 따라 **정확성 확인 → 한계 명시 → 하드웨어 용어 복귀** 3단계로 사용한다:

**1단계 — 비유 제시**:
> "한 요리사가 여러 코스 요리를 준비한다고 생각해 봅시다. 냄비 하나, 도마 하나로 '재료 손질 → 조리 → 플레이팅'을 순서대로 진행합니다. 멀티사이클 프로세서도 마찬가지입니다: 단 하나의 ALU와 하나의 메모리를 사용하되, 명령어의 각 단계를 별도의 클럭 사이클에 순서대로 실행합니다."

**2단계 — 한계 명시**:
> "단, 이 비유에는 한계가 있습니다. 멀티사이클에서 각 클럭 사이클의 길이는 동일합니다. 요리처럼 조리 단계마다 시간이 다른 것이 아니라, 동일한 길이의 '틱(tick)'으로 진행됩니다. 또한 이 비유는 나중에 배울 파이프라인(여러 명령어를 동시에 서로 다른 단계에서 처리하는 방식)과는 다릅니다."

**3단계 — 하드웨어 용어 복귀**:
> "이제 비유에서 벗어나 하드웨어 관점으로 돌아갑니다. 멀티사이클의 각 사이클은 IF(명령어 인출), ID(디코딩), EX(실행), MEM(메모리 접근), WB(라이트백) 중 하나의 작업을 수행합니다."

---

### 3.5 더 나은 보완 비유 제안

**보완 비유: "공용 장비를 갖춘 작업실"**

요리 코스 비유는 "시간 분할"을 잘 설명하지만, "자원 공유로 인한 면적 절감"을 직관적으로 보여주지 못한다. 다음 보완 비유를 7.2절에 추가한다:

> "학교 실습실을 생각해 봅시다. 단일 사이클 프로세서는 학생마다 개인 공구 세트(드릴, 사포, 도색 도구 등)를 모두 갖추는 것입니다. 비용이 크지만 동시에 모든 작업이 가능합니다. 멀티사이클 프로세서는 공용 드릴 하나, 공용 사포 하나를 두고 학생들이 순서를 기다려 사용하는 것입니다. 비용은 작지만 한 번에 한 학생만 장비를 쓸 수 있습니다."

이 비유는 자원 공유의 **비용(장비 수 감소, 면적 절감)**과 **제약(한 번에 하나씩만 사용)**을 동시에 설명한다.

**매핑 표**:
| 하드웨어 | 보완 비유 |
|---------|---------|
| 단일 ALU | 공용 드릴 한 대 |
| 단일 메모리 | 공용 자재 창고 하나 |
| 사이클마다 다른 작업 | 순서를 기다려 장비 사용 |
| MUX (입력 선택) | 어느 학생이 장비를 쓸 차례인지 결정하는 스케줄 |
| 중간 결과 레지스터 | 내 작업 진행 상황을 노트에 기록해두기 |

### 5.3 구간별 강의 전략 상세

#### 7.1절 (5~30분) — 동기 부여가 핵심

**오프닝 질문** (수강생 참여 유도):
> "여러분이 만든 단일 사이클 CPU의 최대 클럭은 얼마였나요? 그 클럭에서 1초에 몇 개의 명령어를 실행할 수 있나요?"

계산: 30MHz × 1사이클/명령어 = 30MIPS

> "이것이 느린지 빠른지 실감이 안 된다면, 현재 고성능 프로세서는 3~4GHz에서 IPC 4~6로 동작한다는 것을 생각해 보세요. 우리 CPU는 약 100배 이상 느립니다."

단, "100배 느린 이유의 절반은 단일 사이클 구조 때문"임을 강조하고, 나머지는 파이프라인/캐시 부재임을 예고한다.

**강사 라이브 타이밍 다이어그램** (화이트보드 또는 태블릿):
- ADD 명령어: 조합 논리 경로가 짧게 끝나지만 클럭이 끝날 때까지 대기하는 모습
- LW 명령어: 조합 논리 경로가 꽉 차는 모습
- 두 명령어가 같은 클럭 주기를 공유하는 모습

#### 7.2절 (30~60분) — "왜 배우는가"를 해소하는 구간

**수강생 참여 토론**:
> "멀티사이클이 단일 사이클보다 나은 점이 뭔지 지금 당장 설명할 수 있나요?"
> (수강생이 답하게 두고, 불완전한 답변을 교정하며 진행)

**핵심 도식 라이브 작성**:
단일 메모리에 대한 타이밍 다이어그램을 칠판에 직접 그리면서, "IF 사이클의 메모리 읽기"와 "MEM 사이클의 메모리 읽기"가 서로 다른 시간에 일어남을 보여준다.

**"왜 배우는가" Q&A 정면 대응**:
수강생이 묻지 않아도 강사가 먼저 꺼낸다:
> "솔직히 말해서, 여러분 중에 '그냥 파이프라인으로 바로 가면 안 되나'라고 생각하는 분이 있을 것입니다. 그 질문에 직접 답하겠습니다."

3가지 이유를 제시하고, 특히 "파이프라인 레지스터와 멀티사이클 중간 레지스터의 관계"를 미리 예고한다.

---

#### 7.3절 (75~105분) — 라이브 데이터패스 구성

**라이브 SVG 추가 방식** (강의 효과 극대화):

화이트보드 또는 태블릿에 단일 사이클 데이터패스에서 시작하여, 변경 사항을 순서대로 추가한다:

1. IMEM + DMEM → 통합 메모리로 교체 (선 삭제, 새 블록 추가)
2. 중간 레지스터 IR (Instruction Register) 추가 — "IF 결과를 보관"
3. A, B 레지스터 추가 — "ID 결과를 보관"
4. ALUOut 레지스터 추가 — "EX 결과를 보관"
5. MDR 추가 — "MEM 결과를 보관"
6. MUX 추가 — "공유 자원에 대한 입력 선택"

각 단계마다: "왜 이게 필요한가? 없으면 어떻게 되나?"를 질문으로 제시하고 수강생이 답하게 유도한다.

**비유 연결 포인트**:
A 레지스터를 추가할 때: "중간에 완성된 소스를 그릇에 담아두는 것처럼, 이 레지스터가 ID 단계에서 읽은 레지스터 값을 다음 사이클까지 보존합니다."

---

#### 7.4절 (105~115분) — 비교 정리 (빠르게)

**비교표 복습** (슬라이드 또는 판서):
- 단일 사이클에서 제거된 것: IMEM, DMEM, 분기 덧셈기, PC+4 가산기
- 멀티사이클에서 추가된 것: 통합 메모리 1개, 중간 레지스터 4개, MUX 3~4개
- 순 효과: 하드웨어 면적 절감 + 클럭 주파수 향상

"이것이 Chapter 07의 결론입니다. 제어 유닛(FSM)은 Ch08에서 다루겠습니다."

---

#### 7.5절 (115~120분) — 예고와 마무리

**자가 점검 3문항 제시** (수업 종료 후 과제 또는 즉석 확인):
1. 멀티사이클에서 A 레지스터의 역할은 무엇인가?
2. 단일 사이클 대비 멀티사이클의 면적이 작은 이유를 두 가지 이상 설명하라.
3. 멀티사이클 데이터패스에서 MUX가 증가하는 이유를 설명하라.

**Ch08 예고**:
> "Ch07에서 데이터패스를 완성했습니다. 다음 Ch08에서는 이 데이터패스를 제어하는 FSM(유한 상태 기계)을 설계합니다. FSM의 각 상태가 오늘 배운 IF/ID/EX/MEM/WB 사이클에 정확히 대응됩니다. 특히 '하드와이어드 vs 마이크로프로그래밍 제어'는 면접에서 자주 나오는 주제이므로 반드시 이해하고 가야 합니다."

## 7. 면접 연결 포인트 상세 (Ch07 기여분)

### 7.1 면접 빈출 11위 선행 준비 (하드와이어드 vs 마이크로프로그래밍)

TABLE_OF_CONTENTS.md에서 "하드와이어드 vs 마이크로프로그래밍 제어"는 Ch08에서 완성되지만, Ch07에서 그 **기반**을 제공해야 한다.

Ch07에서 수강생이 이해해야 할 선행 개념:
1. 멀티사이클에서 각 사이클마다 다른 제어 신호가 필요하다는 사실
2. 제어 신호를 어떻게 결정하는가 — FSM의 현재 상태로 결정 (하드와이어드)
3. 제어 신호를 메모리에 저장하고 읽어오는 방식 — 마이크로프로그래밍의 기초

**Ch07 7.1절에 다음 `<aside class="interview">` 배치 권장**:

```html
<aside class="interview">
  <h4>🎯 면접 포인트</h4>
  <p><strong>Q: 멀티사이클 프로세서에서 제어 유닛을 구현하는 두 가지 방법은?</strong></p>
  <p><strong>A</strong>:
  <ol>
    <li><strong>하드와이어드(Hardwired) 제어</strong>: 제어 신호를 조합 논리와 FSM으로 직접 구현.
        빠르지만 설계 변경이 어렵다. 현대 고성능 프로세서에서 채택.</li>
    <li><strong>마이크로프로그래밍(Microprogramming) 제어</strong>: 각 상태의 제어 신호를
        마이크로코드 ROM에 저장하고 읽어오는 방식. 설계 유연성이 높지만 속도가 느리다.
        인텔 x86 등 CISC 프로세서에서 역사적으로 채택.</li>
  </ol>
  이 두 방법의 트레이드오프는 Ch08에서 구체적으로 다룹니다.</p>
</aside>
```
