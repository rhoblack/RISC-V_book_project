## 2. Critical 이슈

### 🔴 [C-1] B 타입 및 J 타입 즉치수 비트 재배열 — 본문 설명 누락

**기획 이슈 확인 항목 #4, #5에 해당**

**문제**: 전체 소스 코드 섹션(즉치수 생성기)에는 올바른 인코딩이 구현되어 있습니다.

```
IMM_B: imm = {{19{instr[31]}}, instr[31], instr[7], instr[30:25], instr[11:8], 1'b0};
IMM_J: imm = {{11{instr[31]}}, instr[31], instr[19:12], instr[20], instr[30:21], 1'b0};
```

그러나 본문 6.1절~6.2절 어디에도 B 타입과 J 타입의 즉치수가 왜 비트 순서가 뒤섞인 방식으로 인코딩되는지 설명하지 않습니다. 제어 신호 표(6.2.2절)에서 B 타입은 `imm_sel=B`, J 타입은 `imm_sel=J`라고만 기재되어 있고, 인코딩의 특수성은 전혀 언급되지 않습니다.

**B 타입 즉치수 인코딩 정확성 검증**:
- `instr[31]` → imm[12] (부호 비트), `instr[7]` → imm[11], `instr[30:25]` → imm[10:5], `instr[11:8]` → imm[4:1], LSB=0
- 합계: 19(부호확장) + 1 + 1 + 6 + 4 + 1 = 32비트 ✅ 정확

**J 타입 즉치수 인코딩 정확성 검증**:
- `instr[31]` → imm[20], `instr[19:12]` → imm[19:12], `instr[20]` → imm[11], `instr[30:21]` → imm[10:1], LSB=0
- 합계: 11(부호확장) + 1 + 8 + 1 + 10 + 1 = 32비트 ✅ 정확

**코드 자체는 ISA 스펙에 부합하나, 독자가 "왜 비트 순서가 뒤섞여 있는가?"를 이해하기 위한 설명이 본문에 없습니다.**

RISC-V ISA 스펙(Vol.I, 2.3절)에 따르면 이 비트 재배열은 하드웨어 디코더 설계 시 부호 비트(instr[31])를 모든 즉치수 타입에서 동일한 위치에 두어 부호 확장 회로를 공유할 수 있게 하고, rs1/rs2 필드 위치를 유지하기 위한 의도적 설계입니다.

**조치 권장**: 6.1.2절 또는 6.1.3절에 B/J 타입 즉치수 비트 재배열에 대한 설명을 최소 1단락 추가해야 합니다. 코드 블록 직전에 "왜 instr[7]이 imm[11]에 배치되는가"를 설명하십시오.

### 🔴 [C-2] LUI의 a_sel=0 처리 — 어셈블러 x0 보장 미설명

**기획 이슈 확인 항목 #2에 해당. 기획 문서 [CRITICAL-3] 부분 해결됨.**

**현황**: 6.2.2절 LUI/AUIPC 진리표(line 451)에서 a_sel 칸에 `rs1(0, x0)`이라고 표기했고, 설명 텍스트(line 445)에 "ALU에서 0+imm을 계산하는 방식으로 구현합니다"라고 기재했습니다. 그러나 이 구현이 안전한 이유, 즉 "RISC-V 어셈블러가 LUI 명령어의 rs1 필드를 반드시 x0(5'b00000)으로 채운다"는 스펙 근거가 없습니다.

**문제점**: 독자가 임의의 바이너리 코드(예: `0x12345FB7`와 같이 rs1 필드가 x0가 아닌 LUI 인코딩)를 직접 작성하거나, 비표준 어셈블러를 사용할 경우 `a_sel=0`이지만 rs1_data가 x0의 값(0)이 아닐 수 있습니다. 레지스터 파일은 rs1_addr가 5'd0일 때만 0을 반환하므로(`assign rs1_data = (rs1_addr == 5'd0) ? 32'h0 : regs[rs1_addr]`), rs1 필드가 x0가 아닌 LUI 명령어는 잘못된 결과를 냅니다.

**조치 권장**: 6.2.2절 LUI/AUIPC 설명에 다음 내용을 추가하십시오:
> RISC-V 스펙(Vol.I, 2.4절)에서 LUI 명령어의 rs1 필드는 don't-care이며, 표준 어셈블러(gas, llvm)는 항상 x0으로 채웁니다. 따라서 `a_sel=0`으로 설정하면 레지스터 파일이 항상 0을 반환합니다. 이 구현은 어셈블러가 스펙을 준수함을 전제로 합니다.

## 3. Major 이슈

### 🟡 [M-1] 검증 프로그램 명령어 커버리지 불완전 — 본문에 미언급

**기획 이슈 [MAJOR-2] — 미해결**

6.4절 시뮬레이션 검증은 피보나치 프로그램만을 사용합니다. 피보나치 프로그램이 커버하는 명령어 타입은 ADDI, LUI, ADD, SW, BLT, JAL입니다. 다음 명령어 타입은 6.4절에서 검증되지 않습니다:

- Load 명령어 (LB, LH, LW, LBU, LHU) — 6개 중 0개 검증
- JALR — 0개 검증
- AUIPC — 0개 검증
- B 타입 전체 범위 (BEQ, BNE, BGE, BLTU, BGEU) — 6개 중 1개(BLT) 검증
- 시프트 명령어 (SLL, SRL, SRA, SLLI, SRLI, SRAI) — 0개 검증
- SLT, SLTU, SLTI, SLTIU — 0개 검증
- SB, SH (바이트/하프워드 Store) — 0개 검증

6.4.3절에서 "완전한 RV32I 단일 사이클 프로세서를 설계하고 검증했습니다"라고 단정하는 표현은 과장입니다. 실제로는 6가지 명령어 타입만 커버된 부분 검증입니다.

**조치 권장**: 6.4절에 "피보나치 프로그램은 Part 2 마일스톤 목적의 통합 테스트이며, 전체 37개 명령어 커버리지 검증은 연습문제 또는 별도 단위 테스트를 통해 수행해야 한다"고 명시하십시오. 6.4.3절의 "완전한 검증" 표현을 완화하십시오.

### 🟡 [M-2] br_un 조합 루프 잠재적 경고 — 설명 누락

**기획 이슈 [MAJOR-3] — 부분 해결**

`control_unit` 모듈에서 `br_un` 신호의 흐름은 다음과 같습니다:
1. `instruction_decoder`가 `funct3[1]`을 기반으로 `br_un`을 출력
2. `branch_comparator`가 `br_un`을 입력으로 받아 `br_eq`, `br_lt`를 출력
3. `instruction_decoder`가 `br_eq`, `br_lt`를 입력으로 받아 `branch_taken`을 결정

`br_un`은 `funct3`에서만 계산되고 `br_eq`/`br_lt`에 의존하지 않으므로 진정한 순환 의존성(cyclic dependency)은 없습니다. 그러나 두 모듈이 서로를 참조하는 구조는 일부 시뮬레이터에서 제로-지연 루프 경고를 발생시킬 수 있으며, Vivado 합성 시 `[Synth 8-5935] variable is driven by a combinational loop` 경고가 나타날 가능성이 있습니다.

코드는 기술적으로 올바르나, 교재에서 이 잠재적 경고를 독자에게 미리 안내하지 않습니다.

**조치 권장**: 6.1.3절 또는 6.3절에 다음을 추가하십시오:
> `branch_comparator`의 출력 `br_eq`/`br_lt`는 `instruction_decoder`의 `br_un` 출력에 의존하지 않으므로 순환 의존성이 없습니다. Vivado가 관련 경고를 발생시키면 파형에서 `br_un`이 `funct3`만으로 결정됨을 확인하십시오.

### 🟡 [M-3] 포트 인터페이스 방침 — 독자 혼란 잠재 요소

**기획 이슈 [CRITICAL-1] — 부분 해결**

ch06_single_cycle_top.sv 전체 소스 코드에는 `instruction_memory`, `data_memory`, `register_file`, `immediate_generator`, `alu` 모듈이 모두 인라인 재정의되어 있습니다. 이 모듈들의 포트명과 파라미터가 Ch04/Ch05에서 정의한 원본 모듈과 다릅니다.

예시:
- `register_file`: Ch04 원본 포트 `reg_wr_en` → Ch06에서 `reg_w_en`
- `alu`: Ch04 원본 포트 `operand_a/b`, `alu_ctrl` → Ch06에서 `a`, `b`, `alu_op`
- `immediate_generator`: Ch04 원본 포트 `inst`, `imm_out` → Ch06에서 `instr`, `imm`
- `instruction_memory`: Ch05 원본 파라미터 `ADDR_WIDTH` → Ch06에서 `DEPTH`

6.3절 본문에서 "Ch04~Ch05에서 완성한 모듈을 계층적으로 연결"한다고 설명하지만, 실제 전체 소스 코드는 인터페이스가 변경된 인라인 재정의 버전입니다. 이 불일치에 대한 명시적 설명이 없습니다.

**조치 권장**: 6.3절 도입부 또는 전체 소스 코드 섹션 서문에 다음을 추가하십시오:
> 본 챕터의 전체 소스 코드는 Ch06 통합을 위해 모든 서브모듈의 포트명을 통일된 명명 규칙으로 재정의합니다. Ch04/Ch05 원본 코드와 포트명이 일부 다를 수 있으며, 본 챕터의 코드가 단일 사이클 통합 설계의 최종 기준입니다.

### 🟡 [M-4] 데이터 메모리 주소 계산 — 잠재적 경계 오류

**신규 발견 이슈**

`data_memory` 모듈의 비동기 읽기 로직(line 1491-1492)에서 주소를 다음과 같이 계산합니다:

```
assign rdata = {mem[{addr[31:2],2'b00}+3], mem[{addr[31:2],2'b00}+2],
                mem[{addr[31:2],2'b00}+1], mem[{addr[31:2],2'b00}]};
```

`{addr[31:2],2'b00}+3`에서 `addr[31:2]`는 32비트 신호를 30비트로 축약한 후 덧셈을 수행합니다. 그러나 SystemVerilog에서 부분 선택 연산 결과의 비트 폭은 원래 신호 폭이 아닌 선택된 비트 수로 결정됩니다. 즉 `{addr[31:2],2'b00}`는 32비트이지만, 내부 연산 `addr[31:2]+3`에서 캐리 오버플로가 발생할 경우 상위 비트가 잘릴 수 있습니다.

실질적으로 DEPTH=1024일 때 메모리 크기는 4096바이트이므로 유효 주소 범위 내에서 이 문제가 발생하지 않습니다. 그러나 교육적 정확성을 위해 주소 연산 비트 폭을 명시하는 것이 권장됩니다.

**조치 권장**: 데이터 메모리 설명 시 "교육 목적 단순화 구현이며 정렬된 접근(4바이트 경계)을 가정합니다"를 명시하십시오.

## 4. Minor 이슈

### 🟢 [m-1] 즉치수 생성기 — 본문 설명 없이 소스 코드만 제시

B 타입 및 J 타입 즉치수 생성기 코드(전체 소스 코드 섹션)가 설명 없이 제시됩니다. I, S, U 타입은 직관적이지만 B/J 타입은 그렇지 않습니다. 최소한 각 인코딩 라인 옆에 주석으로 비트 의미를 추가하면 독자의 이해를 도울 수 있습니다.

---

### 🟢 [m-2] 테스트벤치 — `always @(posedge clk)`의 과도한 출력

line 1630-1634의 `always @(posedge clk)` 블록이 리셋 해제 후 매 클록마다 PC, instr, rd_addr, rd_data, reg_w_en을 출력합니다. 120사이클 실행 시 120줄의 출력이 발생합니다. 교육 목적으로는 유용하나, 특정 명령어만 추적하거나 오류 발생 시에만 출력하는 방식을 권장 형태로 주석에 안내하면 더 좋습니다.

---

### 🟢 [m-3] `language-verilog` vs `language-systemverilog` 표기

코드 블록에 `class="language-verilog"`가 사용되었으며, JavaScript(line 1648-1652)가 `language-systemverilog`를 `language-verilog`로 런타임 변환합니다. 실제 코드는 모두 SystemVerilog이므로 소스 HTML에서 직접 `language-verilog`를 사용하는 것이 더 명확합니다(현재 방식도 동작에 문제 없음).

### 🟢 [m-4] typedef enum — 패키지 분리 미안내

`alu_op_t`, `imm_sel_t`, `wb_sel_t`, `pc_sel_t`, `mem_rw_t`가 `ch06_decoder.sv` 파일 최상단에 정의됩니다. 여러 `.sv` 파일에서 공유하려면 `package`로 분리해야 합니다. Ch06 수준에서 패키지 사용은 과도한 추상화일 수 있으나, "이후 챕터에서 package로 분리 예정"을 주석 또는 aside로 안내하면 독자가 파이프라인 챕터 진입 시 혼란을 줄일 수 있습니다.

## 6. 긍정적 평가 사항

1. **FENCE 명시적 NOP 처리 완성**: 기획 단계 Major 이슈였던 FENCE opcode가 `7'b0001111: begin /* NOP */ end`로 `default`와 분리되어 명시적 case에서 처리됩니다. `illegal_instr`가 FENCE에서 세트되지 않습니다. ✅

2. **HTML 이스케이프 처리 완벽**: 모든 `<code>` 블록 내의 `<=`, `>>`, `<<`, `&`, `<`, `>`가 `&lt;`, `&gt;`, `&amp;`로 정확히 이스케이프되어 있습니다. 렌더링 오류 없음. ✅

3. **B/J 타입 즉치수 코드 정확성**: 전체 소스 코드의 `immediate_generator`에서 B 타입 및 J 타입 즉치수 인코딩이 RV32I 스펙과 정확히 일치합니다. ✅

4. **JALR LSB 클리어 올바르게 구현**: `pc_next = alu_result & 32'hFFFF_FFFE` (line 592, 1389)가 정확히 구현되어 있습니다. RV32I 스펙 요구사항 준수. ✅

5. **분기 조건 판정 로직 정확**: BEQ, BNE, BLT, BGE, BLTU, BGEU 6개 분기 명령어의 `branch_taken` 로직이 funct3 코딩 및 스펙과 일치합니다. `br_un = funct3[1]`은 BLTU(funct3=110)와 BGEU(funct3=111)에서 올바르게 1이 됩니다. ✅

6. **기본값 설정으로 래치 방지**: `always_comb` 블록에서 모든 출력에 기본값을 먼저 설정하는 표준 SystemVerilog 관용구가 일관되게 적용되어 있습니다. ✅

7. **레지스터 파일 x0 하드와이어드 0 처리**: `assign rs1_data = (rs1_addr == 5'd0) ? 32'h0 : regs[rs1_addr]`와 쓰기 시 `rd_addr != 5'd0` 조건이 정확히 구현되어 있습니다. ✅

8. **PC_sel 구조 명확**: PC 다음값 선택 로직에서 PC_PLUS4, PC_BRANCH, PC_JALR 세 경우가 명확히 분리되어 있고 `default`에서도 PC_PLUS4로 안전하게 처리됩니다. ✅
