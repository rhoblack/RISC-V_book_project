## 신규 용어 명확도 검토

### 즉시 명확한 용어 ✅

#### 1. **링커 (linker)** — 22.1절
- **첫 등장**: ✅ 명확 (3줄 요약: "C 코드의 어느 부분이 어디로 갈 것인가")
- **설명 명확도**: ⭐⭐⭐⭐⭐
- **이유**:
  - "컴파일러는 코드를 바꾸지만, 링커는 배치한다"는 구분 명확
  - MEMORY vs SECTIONS 이원 구조 명확
  - 건설 설계도 비유가 Verilog 배경자에게 직관적
- **추천**: 그대로 유지. 매우 좋음.

#### 2. **ABI (Application Binary Interface)** — 22.2절
- **첫 등장**: ✅ 명확 ("Calling Convention이라고 합니다")
- **설명 명확도**: ⭐⭐⭐⭐
- **이유**:
  - "ABI" 약자는 정의되지만, "왜 필요한가"는 암묵적
  - 전화 대화 비유가 도움. 다만 "caller-saved vs callee-saved" 구분은 미흡
- **추천 개선**:
  ```
  ABI는 "하드웨어와 소프트웨어가 약속하는 계약"입니다.
  컴파일러가 코드를 생성할 때, "인자는 a0~a7에 넣는다"는 확실한 규칙이 없으면,
  같은 프로세서에서도 함수 호출이 엉망이 됩니다.
  ```
  (이 부분은 선택적 개선이며, 현재도 충분함)

#### 3. **Calling Convention** — 22.2절
- **첫 등장**: ✅ 명확
- **설명 명확도**: ⭐⭐⭐⭐⭐
- **이유**:
  - 테이블로 a0~a7, ra, sp 명확하게 정의
  - 전화 대화 비유가 적절
  - 실제 코드(startup.S)에서 `la sp, __stack_end` 예시로 구체화
- **추천**: 그대로 유지. 훌륭함.

#### 4. **Volatile** — 22.3절 (UART 드라이버)
- **첫 등장**: ✅ 명확 ("이 변수는 컴파일러가 최적화하지 마")
- **설명 명확도**: ⭐⭐⭐⭐
- **이유**:
  - 💡 실무 팁 박스에서 "외부 장치(UART 컨트롤러)가 값을 바꾼다"는 설명 존재
  - Verilog 배경자는 "하드웨어가 레지스터를 바꾼다"는 개념을 알고 있음
  - 따라서 volatile 필요성이 직관적
- **미흡한 점**: 왜 volatile이 필요한지를 더 자세히
  - "컴파일러가 최적화하면 `while (*UART_STATUS & 0x1) == 0`에서 첫 번째 읽기만 하고, 루프를 매번 다시 읽지 않을 수 있다"는 구체적 사례 추가 권장
- **추천 개선**: (선택적)
  ```
  while ((*UART_STATUS & 0x1) == 0) {
      // volatile 없으면, 컴파일러는:
      //   1. UART_STATUS 한 번 읽음 → 0
      //   2. 이게 항상 0이라고 가정 → 무한 루프 최적화!
      // volatile 있으면:
      //   1. 매번 루프마다 UART_STATUS를 다시 읽음
      //   2. 하드웨어 변화 감지 가능
  }
  ```

#### 5. **MMIO (Memory-Mapped I/O)** — 22.3절
- **첫 등장**: ✅ 명확 ("메모리 주소로 하드웨어 제어")
- **설명 명확도**: ⭐⭐⭐⭐
- **이유**:
  - 원격 제어 비유가 직관적
  - UART_BASE = 0x6000_0000 처럼 구체적 주소 제시
  - 포인터 캐스팅 `(volatile uint32_t *)` 문법 설명
- **미흡한 점**:
  - "메모리 주소 0x6000_0000에 접근하면 UART 컨트롤러가 응답한다"는 원리가 **왜**일까?
  - 이것은 FPGA 설계 (메모리 디코더, 어드레스 맵)의 하드웨어 구현 문제인데, 명시적으로 언급 부족
  - Ch15 "메모리 컨트롤러와 캐시 메모리 인터페이스"와의 연결고리 명시 권장
- **추천 개선**: (선택적)
  ```
  MMIO의 비밀 (Ch15 복습):
  당신이 Ch15에서 설계한 메모리 컨트롤러는 어드레스를 확인해서
  "0x0000_0000~0x0000_3FFF는 IMEM으로 라우팅"
  "0x2000_0000~0x2000_7FFF는 DMEM으로 라우팅"
  "0x6000_0000 이상은 주변 장치로 라우팅"
  이렇게 설정되어 있습니다. MMIO도 동일한 원리입니다.
  ```

#### 6. **포인터 캐스팅 문법** — 22.3절
- **첫 등장**: ✅ 명확
  ```c
  volatile uint32_t *uart_tx = (volatile uint32_t *)0x6000_0000;
  ```
- **설명 명확도**: ⭐⭐⭐⭐
- **이유**:
  - 문법을 그대로 제시하고 주석으로 설명
  - Verilog 배경자는 "주소"를 이미 알고 있음 (메모리 어드레스)
  - 포인터 개념도 기본적 이해 있음
- **미흡한 점**: 캐스팅 순서 설명 부족
  ```
  (volatile uint32_t *)0x6000_0000
  ↑ "주소 0x6000_0000을 volatile 포인터로 봐"
  ```
  이 순서를 한 번 더 명시하면 "왜 volatile이 먼저 오나?" 질문 방지

#### 7. **CSR (Control and Status Register)** — 22.3절
- **첫 등장**: ✅ 있음 (timer_init에서 "csrs mie" 언급)
- **설명 명확도**: ⭐⭐⭐⭐
- **이유**:
  - 코드에는 나오지만, 개념 설명은 최소한
  - "(Ch18~19에서 배움)" 주석으로 선행 장 명시
- **추천 개선**: (권장)
  ```
  타이머 인터럽트를 활성화하려면:
  1. TIMER_LIMIT/TIMER_CTRL 레지스터 설정 (하드웨어 요청)
  2. mie(Machine Interrupt Enable) CSR의 MTIE 비트 설정 (소프트웨어 수락)
  3. mstatus CSR의 MIE 비트 설정 (글로벌 인터럽트 활성화)

  자세한 내용은 Ch18~19에서 배운 예외 처리 체계를 복습하세요.
  ```

## 특수 개념: 처음 경험하는 것들

### 1️⃣ **링커 스크립트의 MEMORY vs SECTIONS 구분**

**위치**: 22.1절

**이것이 처음인 이유**:
Verilog 설계자는 "하드웨어 리소스 할당"을 생각해본 적이 있어도 (예: `localparam IMEM_SIZE = 16*1024`),
"소프트웨어 코드가 메모리 주소에 어떻게 배치되는가"는 임베디드 특유의 개념입니다.

**텍스트에서의 처리**:
- ✅ Aside (안심 박스) 있음: "링커 스크립트는 한 번 작성 후 거의 수정하지 않습니다"
- ✅ 비유 명확: 건설 설계도 비유
- ✅ 실습 문제: 메모리 맵 분석 연습

**평가**: ⭐⭐⭐⭐⭐ 매우 명확

---

### 2️⃣ **포인터로 하드웨어 레지스터 접근 (MMIO)**

**위치**: 22.3절

**이것이 처음인 이유**:
Verilog에서는 항상 `always_ff` 블록 내에서 신호를 만들었습니다.
C에서 `*uart_tx = (uint32_t)c;`로 "메모리 주소 값을 쓰면 하드웨어가 반응한다"는 역발상입니다.

**텍스트에서의 처리**:
- ✅ Aside (실무 팁) 있음: volatile 설명
- ✅ 비유 있음: 원격 제어와 TV
- ⚠️ 원리 설명 부분적: "왜 0x6000_0000에 접근하면 UART가 응답하나?"는 암묵적

**평가**: ⭐⭐⭐⭐ 명확하지만, Ch15과의 연결고리 강조 권장

---

### 3️⃣ **타이머 인터럽트와 CSR**

**위치**: 22.3.3절

**이것이 처음인 이유**:
Ch18~19에서 "예외 처리"를 배웠지만, 실제로 "타이머 인터럽트를 설정하려면 어떤 CSR을 어떻게 만질까?"는
응용 수준입니다.

**텍스트에서의 처리**:
- ✅ 코드 제시: `asm("csrs mie, %0")` 등
- ✅ 주석으로 설명: "Ch18~19에서 배움"
- ⚠️ 선행 학습 강제: 명시적으로 "22.3.3을 이해하려면 Ch19 예외 처리를 다시 읽으세요"라는 전제 문구 권장

**평가**: ⭐⭐⭐⭐ 코드는 명확하지만, 선행 요구사항 명시 권장

**추천 개선**: 22.3절 시작 부분에 다음 추가:
```
주의: 22.3.3절(타이머 드라이버)은 Ch18~19의 예외 처리 체계를 이해하고 있어야 합니다.
특히 다음을 복습하세요:
- mie/mstatus CSR의 역할
- mtvec와 인터럽트 핸들러 등록
- mret 복귀 메커니즘

22.3.1(UART)과 22.3.2(GPIO)는 독립적이므로 먼저 완성하고 돌아와도 괜찮습니다.
```

## 코드 예시 명확도

### UART 드라이버
```c
volatile uint32_t *uart_tx = (volatile uint32_t *)(UART_BASE + 0x00);
```

**Verilog 배경자 입장**:
- ✅ 레지스터 주소를 C 포인터로 표현 = 직관적
- ✅ volatile 키워드 = 설명됨
- ⚠️ 포인터 문법 `(volatile uint32_t *)` 순서 = 약간 헷갈릴 수 있음

**평가**: ⭐⭐⭐⭐⭐

---

### 부트스트랩 코드 (startup.S)
```asm
la sp, __stack_end
```

**문제점**:
- 링커 스크립트에서 `__stack_end = ORIGIN(DMEM) + LENGTH(DMEM);` 정의
- 부트스트랩에서 `la sp, __stack_end` 사용
- **연결고리가 명확한가?**

**평가**: ⭐⭐⭐⭐ 충분하지만, "링커 스크립트 심볼을 어셈블리에서 참조하는 방법"을 한 줄 더 강조하면 ⭐⭐⭐⭐⭐

**추천 추가 설명**:
```
주목: __stack_end는 링커 스크립트에서 정의한 "심볼(symbol)"입니다.
빌드 시 링커가 이 값을 계산해서 startup.S의 `la sp, __stack_end`에 대입합니다.
따라서 main() 함수 코드를 수정하지 않아도 메모리 배치를 바꾸면 스택 포인터가 자동으로 조정됩니다!
```

## 처음 학습자가 "어라? 뭐야?" 하는 순간들

### 1. "왜 스택은 감소 방향인가?"
**위치**: 22.1절 (메모리 맵)

**텍스트 현황**:
- "런타임 스택 → DMEM의 최상단부터 감소 방향"라고만 기술

**초보자 반응**:
"IMEM는 0x0000_0000부터 증가하는데, 왜 스택만 최상단(0x2000_7FFF)에서 감소?"

**추천 개선**:
```
RISC-V 규약에서는 스택을 "높은 주소에서 낮은 주소로" 사용합니다.
왜일까요?

메모리 공간을 효율적으로 나누기 위해서입니다:
- 낮은 주소: 코드 (.text) → 힙(동적 할당 영역) → 스택 ← 높은 주소
- 이렇게 배치하면 힙과 스택이 충돌할 때까지 최대한 많이 쓸 수 있습니다.
```

---

### 2. "ABI는 우리가 정해도 되나?"
**위치**: 22.2절 (Calling Convention)

**초보자 반응**:
"테이블에서 a0~a7이 인자라고 했는데, 이건 RISC-V 고정인가? 우리 프로세서는 다르게 할 수 없나?"

**현황**: 명시되지 않음

**추천 추가 문구**:
