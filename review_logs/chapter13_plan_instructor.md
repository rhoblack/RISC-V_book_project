## 1. 수강생 막힘 포인트 Top 5

### 막힘 포인트 1 — Tag/Index/Offset 분리의 직관 부재
**발생 절**: 13.2절 (직접 매핑 캐시 설계)

**왜 막히는가**
기술적 원인: 수강생은 파이프라인까지 "신호 이름 → 기능"의 직접 매핑을 배워왔다. 그러나 주소를 세 필드로 분리하는 이유는 기능이 아니라 **하드웨어 구조의 제약**에서 나온다. "왜 하위 비트가 Offset이고, 중간 비트가 Index이며, 상위 비트가 Tag인지" 납득이 안 되면 이후 모든 주소 계산이 암기로 전락한다.

심리적 원인: "32비트 주소를 3조각으로 나누는 것"이 임의적으로 보인다. 규칙이 있다는 확신이 없으면 불안이 누적된다.

**사전 해소 방법**
교재에 다음 순서로 서술:
1. Offset 먼저 결정: "한 번에 몇 바이트를 가져올까?" (블록 크기 결정) → 하위 `log₂(블록크기)` 비트
2. Index 결정: "캐시에 몇 개의 줄(line)이 있을까?" (Set 수 결정) → 그 다음 `log₂(Set수)` 비트
3. Tag는 나머지: "같은 Index에 들어올 수 있는 다른 주소들을 구별하는 번호"

**강의실 설명 방법**

> "아파트 호수를 생각해 보세요. 101호, 201호, 301호는 모두 '01호'입니다. 여기서 '01호'가 Offset(방 안에서의 위치), '1층/2층/3층'이 Index(어느 캐시 줄), '단지 번호'가 Tag입니다. 같은 Index에 여러 단지의 주소가 들어올 수 있고, 그것을 구별하는 게 Tag의 역할입니다."

추가 강화: 32비트 주소 하나를 색상별로 나눈 SVG(ch13_sec02_address_decompose.svg)를 반드시 제공. 수치 예제를 3개 이상 포함(13.3절 실습 연계).

### 막힘 포인트 2 — Valid 비트의 필요성
**발생 절**: 13.2절 도입부

**왜 막히는가**
기술적 원인: 수강생은 "BRAM은 전원을 켜면 0으로 초기화된다"고 배웠거나 그렇게 가정한다. Valid 비트가 없으면 Tag가 0인 캐시 줄이 "주소 0x0000의 데이터"로 잘못 히트될 수 있다는 시나리오가 직관적으로 떠오르지 않는다.

심리적 원인: "Tag 비교만 하면 충분하지 않나?"라는 생각에서 불필요한 추가 비트처럼 느껴진다.

**사전 해소 방법**
교재에 반례(counter-example) 먼저 제시:
- "Valid 비트가 없다고 가정하자. 전원 인가 직후, Tag 필드가 0으로 초기화된 상태에서 CPU가 주소 0x0000_0000을 요청하면?"
- → Tag 비교: 0 == 0 → Hit! → 쓰레기 데이터가 CPU에 전달됨

이 반례를 보여준 뒤 Valid 비트를 자연스럽게 도입.

**강의실 설명 방법**

> "도서관 책장에 책이 없는 자리에도 '이 자리는 빈 자리입니다'라는 표지판이 있어야 합니다. Tag만 보면 우연히 번호가 일치하는 빈 자리를 채워진 자리로 착각할 수 있습니다. Valid 비트는 바로 그 표지판입니다."

### 막힘 포인트 3 — 충돌 미스(Conflict Miss) 개념
**발생 절**: 13.2절 말미 또는 13.6절 요약

**왜 막히는가**
기술적 원인: 직접 매핑(Direct-Mapped)에서는 같은 Index를 가지는 두 주소가 번갈아 접근되면 매번 미스가 발생한다는 것이 처음에는 비직관적이다. "캐시에 빈 자리가 있는데도 미스가 난다"는 상황이 이해되지 않는다.

심리적 원인: "캐시가 4KB인데 고작 2개의 주소 때문에 성능이 나빠진다"는 사실이 직관과 충돌한다.

**사전 해소 방법**
구체적 수치 예제로 제시:
- 4KB 직접 매핑, 블록 크기 16B, 256개 캐시 줄
- 주소 0x0000_0000 (Index=0) 과 주소 0x0000_1000 (Index=0) 이 번갈아 접근
- 매 접근마다 상대방이 Evict됨 → Miss율 100%
- 동일 예제를 2-way 세트 연관으로 바꾸면 → 두 주소 동시 캐싱 가능

이 예제가 13.6절(요약) 또는 13.2절 말미의 `<aside class="faq">`에 들어가면 효과적이다.

**강의실 설명 방법**

> "2개뿐인 주차 구역이 있는 건물에서, A씨와 B씨가 항상 같은 번호 구역만 고집한다면? 아무리 옆에 빈 자리가 있어도 서로 밀어내야 합니다. 직접 매핑의 충돌 미스는 이와 같습니다. N-way는 해당 구역에 N개의 주차 칸을 두는 것입니다."

### 막힘 포인트 4 — icache_stall과 기존 파이프라인 신호의 연결
**발생 절**: 13.4절 (캐시 미스 처리: Stall 메커니즘)

**왜 막히는가**
기술적 원인: Ch10에서 구현한 `hdu_pc_en`, `if_id_en`, `id_ex_flush` 등의 스톨 신호가 이미 존재하지만, 캐시 미스로 인한 스톨은 **파이프라인 전체를 멈추는** 것이다. 기존 Load-Use 스톨(1사이클, IF-ID 단계만 홀드)과 다르게, `icache_stall`은 `pc_en=0`, `if_id_en=0` 동시에 걸어야 하며 `id_ex_flush`는 오히려 걸면 안 된다는 점이 혼란을 준다.

심리적 원인: "스톨인데 flush를 안 한다"는 것이 Ch11의 패턴과 반대로 느껴진다.

**사전 해소 방법**
교재에 기존 스톨 신호 재사용 방식과 신규 방식을 비교 표로 명시:

| 스톨 원인 | pc_en | if_id_en | id_ex_flush | 비고 |
|----------|:-----:|:--------:|:-----------:|------|
| Load-Use 해저드 (Ch10) | 0 | 0 | 1 (버블 삽입) | ID/EX 경계에 NOP |
| 분기 flush (Ch11) | 1 | flush | flush | 잘못된 명령어 제거 |
| I-Cache 미스 (Ch13) | 0 | 0 | 0 | 전체 정지, 버블 불필요 |

**강의실 설명 방법**

> "영화관에서 상영이 잠시 중단되었을 때, 관객을 퇴장시키는 게 아니라 그냥 멈추는 겁니다. Load-Use 스톨은 '한 명은 나가야 해서' 버블을 넣었지만, 캐시 미스는 '아직 데이터가 안 왔으니까' 모두 기다리는 것입니다."

추가 강화: `icache_stall`이 기존 `hdu_pc_en`와 OR 관계인지 독립 신호인지 명시 필요. 코드에서 `pc_en = hdu_pc_en & ~icache_stall` 방식을 보여줄 것.

### 막힘 포인트 5 — BRAM 1사이클 지연과 1사이클 히트의 역설
**발생 절**: 13.2절 (Basys 3 BRAM 활용)

**왜 막히는가**
기술적 원인: Basys 3 BRAM은 동기(synchronous) 읽기이므로, 요청 클럭 다음 클럭에 데이터가 나온다. 그런데 교재의 목표는 "캐시 히트 시 1사이클 응답"이다. "BRAM을 쓰면 항상 1사이클 지연인데, 어떻게 히트를 1사이클에 처리하나?"라는 질문이 반드시 나온다.

심리적 원인: 파이프라인 레지스터로 배운 "1사이클 = 클럭 엣지 1번"이 BRAM에도 그대로 적용되는 줄 알지만, 파이프라인 구조 안에서는 이를 흡수할 수 있다는 것을 모른다.

**사전 해소 방법**
교재에서 두 가지 구현 방식을 명시적으로 비교:

1. **레지스터 파일 방식 (LUTRAM, 비동기 읽기)**: Tag/Valid 비교 + 데이터 읽기가 같은 클럭에 완료 → 히트 1사이클 가능. 단, 용량 제한.
2. **BRAM 방식 (동기 읽기)**: Tag는 LUTRAM/레지스터에, 데이터는 BRAM에. Tag 비교를 사전 사이클에 수행하거나, 파이프라인 구조에서 사이클이 자연스럽게 흡수됨.

13.2절에서 Basys 3 구현 선택(Tag LUTRAM + Data BRAM 분리)을 명확히 해야 수강생이 "BRAM인데 왜 1사이클이야?"라는 혼란을 겪지 않는다.

**강의실 설명 방법**

> "편의점 계산대에서 점원이 바코드 찍는 순간(Tag 비교)에 이미 상품이 눈앞에 있는 것(데이터 준비)과 같습니다. Tag 확인과 데이터 읽기가 동시에 시작되고, 파이프라인 구조가 이 1사이클을 흡수합니다."

## 2. 비유 제안 및 검증

### 2.1 캐시 전체 비유 평가

#### 후보 A — "책상 위의 자주 쓰는 책 (캐시) vs 책장 (메인 메모리)"

**기술적 사실과 매핑되는 점**
- 책상 위의 책: 용량 작음 + 접근 빠름 → 캐시 속성 정확
- 책장: 용량 크고 접근 느림 → 메인 메모리 속성 정확
- 자주 쓰는 책을 책상에 올려두는 행위 → 지역성 원리 (시간적) 직관적 표현
- 책을 꺼내오는 행위 → 캐시 라인 로드(블록 단위 전송) 비유 가능

**한계점**
- "책 한 권 = 캐시 라인 1개"인지 "책 한 권 = 캐시 전체"인지 모호
- 책상에서 책을 찾는 것이 "Tag 비교"에 해당한다는 것이 명시되지 않으면 매핑이 흐릿해짐
- Write-Back/Write-Through 정책은 이 비유로 설명하기 어려움 (책을 수정하면 원본도 바꿔야 하나?)
- 직접 매핑의 충돌 미스("같은 Index 자리")를 이 비유로 표현하기 어려움

#### 후보 B — "편의점 (캐시) vs 대형마트 (메인 메모리)"

**기술적 사실과 매핑되는 점**
- 편의점: 제품 수 적음 + 가까움 + 빠름 → 캐시 속성 정확
- 대형마트: 제품 수 많음 + 멀음 + 느림 → 메인 메모리 속성 정확
- 편의점 재고 없을 때 대형마트 가서 사 오는 것 → 캐시 미스 후 메모리 접근 직관적
- 편의점이 자주 팔리는 물건만 채워두는 것 → 지역성 기반 캐시 정책 표현

**한계점**
- 편의점 직원이 "무엇이 잘 팔릴지" 예측하는 것은 캐시 교체 정책(LRU 등)에 해당하는데, I-Cache는 교체 정책이 없음(직접 매핑)
- "가게"라는 비유가 수동적 관점(소비자)이어서 CPU가 능동적으로 요청한다는 것이 약함
- DRAM 100~300사이클 대기라는 극단적 비용 차이가 "편의점 vs 대형마트"의 거리감으로는 충분히 전달되지 않음

#### 후보 C — "CPU 옆 메모장 (캐시) vs 서버실의 하드디스크"

**기술적 사실과 매핑되는 점**
- 물리적 거리감이 접근 속도 차이를 직관적으로 설명
- "CPU 옆"이라는 표현이 캐시의 온칩(on-chip) 특성을 암시

**한계점 (심각)**
- 하드디스크는 메인 메모리가 아니라 스토리지(Secondary Storage)임. DRAM과 혼동 유발
- "메모장"이 소용량이라는 것은 맞지만, 구조화된 Tag/Index/Offset 개념과 연결되지 않음
- 이 비유를 쓰면 수강생이 "캐시 = 레지스터 파일과 같은 것?"으로 오해할 수 있음

**최종 추천: 후보 A + 후보 B 조합 사용**

단독으로 사용할 경우 후보 A가 더 적합하나, 두 비유를 목적에 따라 분리 사용하는 것을 강력히 권고한다.

- **13.1절 도입부 (메모리 계층 전체 개요)**: 후보 B (편의점 vs 대형마트) 사용. 계층 구조의 용량/속도 트레이드오프를 직관적으로 전달하기에 적합.
- **13.2절 (직접 매핑 세부 구조)**: 후보 A (책상 위의 책) 변형 사용. 단, "책 한 권 = 캐시 라인 1개"임을 명시하고, Tag 비교를 "표지(제목)를 확인하는 것"으로 확장.
- 후보 C는 사용하지 않는다. DRAM/스토리지 혼동 위험이 있어 교재에서 명시적으로 수정 필요.

### 2.2 지역성 원리 비유

#### 시간적 지역성 (Temporal Locality)
**개념**: 최근에 접근한 메모리 주소에 곧 다시 접근할 가능성이 높다.

**권장 비유**:
> "당신이 오늘 책상 위에서 꺼낸 계산기를 오늘 오후에도 다시 쓸 가능성이 높다. 루프(loop)에서 카운터 변수가 반복적으로 읽히는 것이 바로 시간적 지역성이다."

기술 매핑 정확도: 높음. 루프 카운터 예제를 코드로 병기하면 추상적 비유가 구체화된다.

추가 강화: 버블정렬(Ch12 마일스톤)의 루프 카운터가 시간적 지역성의 대표 사례임을 언급. 수강생이 이미 구현한 코드이므로 "우리가 만든 버블정렬에서 `for` 루프의 인덱스 변수 `i`가 매 사이클 읽힙니다"로 연결하면 친숙도가 높다.

#### 공간적 지역성 (Spatial Locality)
**개념**: 접근한 주소 근처의 주소에도 곧 접근할 가능성이 높다.

**권장 비유**:
> "책의 특정 페이지를 펼치면 앞뒤 페이지도 곧 읽게 된다. 배열을 순회할 때 `arr[i]`를 읽으면 `arr[i+1]`, `arr[i+2]`도 곧 읽힌다. 캐시가 블록(cache line) 단위로 통째로 가져오는 이유가 바로 공간적 지역성 때문이다."

기술 매핑 정확도: 높음. 캐시 라인이 왜 1바이트가 아닌 16~64바이트인지를 이 비유로 바로 설명할 수 있다.

추가 강화: "버블정렬에서 배열 순회가 공간적 지역성의 완벽한 예시"임을 Ch12 연계로 제시. Ch12에서 배열 [64,5,66,...] 을 순회했는데, 이때 인접 원소들이 같은 캐시 라인에 있으면 첫 번째 원소만 미스, 나머지는 모두 히트임을 수치로 보여주면 학습 효과가 높다.

### 2.3 Tag/Index/Offset 비유 — 도서관 비유 구체화 및 한계 명시

#### 비유 구조 (교재 삽입용)

> **도서관에서 책을 찾는 방법으로 이해하는 직접 매핑 캐시**
>
> 거대한 도서관(메인 메모리)에서 책(데이터)을 찾으러 갈 때마다 시간이 오래 걸린다. 그래서 당신의 연구실(캐시)에 일부 책을 가져다 둔다.
>
> - **Index(인덱스) = 책장 번호**: 연구실에 책장이 256개 있다고 하자. 책을 가져올 때 반드시 '책장 번호 = 주소의 중간 8비트'인 자리에 놓아야 한다. 번호 규칙이 정해져 있으므로 찾는 속도가 빠르다.
> - **Tag(태그) = 책의 고유 식별자**: 같은 책장 번호에는 도서관의 서로 다른 구역에서 온 책들이 올 수 있다. 실제로 어느 구역(Tag)에서 온 책인지 표지에 적어두어야 같은 번호 자리의 다른 책과 구별할 수 있다.
> - **Offset(오프셋) = 책 안의 페이지 번호**: 책 한 권(캐시 라인)을 통째로 가져오므로, 그 안의 몇 번째 바이트인지를 알아야 원하는 정보를 찾을 수 있다.

#### 한계점 (교재에 명시 권고)

> **[이 비유의 한계]**
> 실제 캐시와 다른 점이 있습니다.
> 1. 도서관에서는 책 한 권 단위로 가져오지만, 캐시는 고정 크기의 '캐시 라인(블록)' 단위로 가져옵니다.
> 2. 도서관 책장에는 여러 책을 나란히 꽂을 수 있지만, 직접 매핑 캐시의 각 Index 자리에는 단 한 개의 캐시 라인만 들어갑니다. (N-way 세트 연관 캐시는 N개 가능)
> 3. 책을 수정하면 원본 도서관 책도 바꿔야 하는지는 Write 정책(Write-Through vs Write-Back)에 따라 다르며, 이는 Ch14에서 다룹니다.

## 3. 수강생 단골 질문 Q&A (5가지)

### Q1. "BRAM을 쓰면 1사이클 지연인데 어떻게 히트를 1사이클에 처리해요?"

**A**: 좋은 질문입니다. 두 가지 방법이 있습니다.

첫 번째 방법은 **Tag 저장소와 Data 저장소를 분리**하는 것입니다. Tag와 Valid 비트는 LUTRAM(비동기 읽기)에 저장하고, 데이터(명령어 내용)는 BRAM에 저장합니다. Tag 비교는 0사이클에 완료되고, BRAM 읽기는 1사이클이 걸리지만, 파이프라인 구조에서 IF 스테이지가 이미 1클럭을 소비하므로 자연스럽게 흡수됩니다.

두 번째 방법은 **히트 여부를 먼저 확인한 뒤 데이터를 가져오는** 2단계 접근입니다. 하지만 이렇게 하면 히트에도 2사이클이 필요해져 성능이 떨어지므로, 본 교재에서는 첫 번째 방법을 사용합니다.

핵심: BRAM의 동기 읽기와 Tag LUTRAM의 비동기 비교를 **파이프라인 한 스테이지 안에서 병렬 수행**하는 것이 직접 매핑 1사이클 히트의 비결입니다.

---

### Q2. "직접 매핑이 N-way 대비 좋은 점이 있나요?"

**A**: 네, 있습니다. 직접 매핑의 장점은 세 가지입니다.

1. **판정 속도**: 히트 여부를 확인하기 위해 비교해야 할 Tag가 단 1개입니다. 4-way는 4개의 Tag를 병렬 비교해야 합니다. 직접 매핑이 게이트 지연(gate delay)이 가장 짧습니다.
2. **하드웨어 단순성**: MUX와 비교기가 최소화됩니다. 면적과 전력 소모가 적습니다.
3. **예측 가능성**: "이 주소는 항상 이 캐시 줄에 들어간다"는 결정론적(deterministic) 동작 덕분에 캐시 동작을 소프트웨어에서 직접 제어할 수 있습니다. 실시간 시스템에서 최악 실행 시간(WCET) 분석에 유리합니다.

반면 충돌 미스에 취약하므로, 현대 CPU는 대부분 N-way(보통 4-way 또는 8-way)를 사용합니다. I-Cache는 접근 패턴이 비교적 단순(순차 실행)하므로 직접 매핑으로도 실용적 성능을 낼 수 있습니다.

---

### Q3. "캐시 크기를 늘리면 무조건 좋은 거 아닌가요?"

**A**: 그렇지 않습니다. 세 가지 측면에서 트레이드오프가 있습니다.

1. **히트 시간 증가**: 캐시가 커지면 Tag 어레이와 데이터 어레이의 크기가 커지고, 비교/읽기에 걸리는 지연이 늘어납니다. 최대 클럭 주파수(Fmax)가 낮아질 수 있습니다.
2. **면적과 전력**: Basys 3에는 BRAM이 총 50개(36Kb×50=1.8Mb)뿐입니다. I-Cache와 D-Cache에 모두 배정해야 하므로 예산이 한정되어 있습니다.
3. **수확 체감(Diminishing Return)**: 16KB 이상이 되면 미스율 감소 폭이 급격히 줄어듭니다. 4KB I-Cache가 성능 대비 면적 효율이 가장 좋은 시작점입니다.

요약: "더 좋은 캐시"는 "더 큰 캐시"가 아니라 "프로그램의 지역성 패턴에 최적화된 캐시"입니다.

---

### Q4. "미스 페널티가 100~300사이클이라고 하셨는데, 실제로 그 동안 CPU는 완전히 멈추는 건가요?"

**A**: 이 교재의 구현에서는 그렇습니다. `icache_stall`이 HIGH이면 파이프라인 전체가 정지(hold)됩니다. 이를 **스톨(Stall) 방식** 또는 **블로킹(Blocking) 캐시**라고 합니다.

고성능 CPU에서는 다릅니다. 비블로킹(Non-Blocking) 캐시는 미스가 발생해도 다른 명령어를 계속 실행합니다(Out-of-Order Execution). 하지만 이 기법은 파이프라인 구조가 훨씬 복잡해집니다.

교육 목적의 RV32I 파이프라인에서는 스톨 방식이 이해와 검증이 쉽습니다. 미스가 드물게 발생하는 I-Cache에서는 블로킹 캐시도 충분한 성능을 낼 수 있습니다.

---

### Q5. "캐시 미스 시 메모리에서 한 단어(4바이트)만 가져오면 안 되나요? 왜 블록 전체를 가져오나요?"

**A**: 기술적으로는 한 단어만 가져와도 됩니다. 하지만 두 가지 이유로 블록(여러 단어) 단위로 가져옵니다.

1. **공간적 지역성 활용**: 방금 접근한 주소 근처에 곧 다시 접근할 가능성이 높습니다. 미리 여러 단어를 가져오면 이후 접근이 히트됩니다.
2. **메모리 버스 효율**: DRAM은 접근 자체에 큰 초기 지연(latency)이 있습니다. 한번 접근했을 때 버스 대역폭을 최대한 활용해서 연속된 데이터를 한꺼번에 가져오는 것이 단어 단위로 여러 번 접근하는 것보다 훨씬 효율적입니다. DRAM의 Burst Mode가 바로 이를 위한 것입니다.

비유: 편의점이 대형마트에서 물건을 사올 때, 한 개씩 사러 가는 것보다 박스째 가져오는 것이 효율적입니다. 그게 캐시 라인(블록)입니다.

---

## 4. 면접 포인트 — "캐시 구조 비교 (Direct-Mapped vs N-Way)"

### 4.1 면접 빈출 배경

면접 빈출 4위에 해당하는 이 주제는 반도체 설계 직군(삼성 DS, SK하이닉스, Qualcomm, ARM 등)의 초급~중급 레벨에서 거의 필수적으로 출제된다. 단순 암기형 답변이 아니라 "왜 그런 구조를 선택하는지"를 설계 관점에서 설명할 수 있어야 한다.

### 4.2 2~3분 답변 구조 (교재 `<aside class="interview">` 삽입 권장)

---

**[면접 포인트 4] 캐시 구조 비교: Direct-Mapped vs N-Way Set-Associative**

*면접에서 이렇게 말하세요 (2~3분 분량)*

**도입 (30초)**: 구조의 핵심 차이를 한 문장으로

> "두 구조의 핵심 차이는 동일한 Index에 몇 개의 캐시 라인을 저장할 수 있느냐입니다. Direct-Mapped는 1개, N-Way는 N개를 저장할 수 있습니다."

**비교 설명 (60~90초)**: 표로 암기 후 말로 설명

| 항목 | Direct-Mapped | N-Way Set-Associative |
|------|:-------------:|:--------------------:|
| 같은 Index 수용 수 | 1개 | N개 |
| Tag 비교기 수 | 1개 | N개 (병렬) |
| 충돌 미스 | 많음 | 적음 (N배 감소 가능) |
| 히트 시간 | 짧음 | 약간 길음 |
| 교체 정책 | 불필요 | LRU, PLRU 등 필요 |
| 하드웨어 복잡도 | 낮음 | 높음 |

> "Direct-Mapped는 Tag 비교기가 1개이므로 지연이 짧고 하드웨어가 단순합니다. 단, 같은 Index를 갖는 두 주소가 번갈아 접근되면 매번 충돌 미스(Conflict Miss)가 발생합니다. N-Way는 N개의 Tag를 병렬 비교하므로 하드웨어가 복잡해지지만, 충돌 미스가 크게 줄어듭니다."

**실무 적용 (30~40초)**: 어디서 무엇을 쓰는지

> "현대 CPU의 L1 I-Cache는 보통 4-way 또는 8-way를 사용합니다. 단, 접근 패턴이 단순한 임베디드 컨트롤러나 실시간 시스템에서는 Direct-Mapped가 WCET 분석이 쉽다는 이유로 채택되기도 합니다. 저는 본 프로젝트에서 Basys 3 FPGA에 Direct-Mapped L1 I-Cache를 구현했습니다. Tag LUTRAM과 Data BRAM을 분리하여 히트 시 1사이클을 달성하였고, 미스 시 `icache_stall` 신호로 파이프라인을 홀드하는 방식을 적용했습니다."

**핵심 한 줄 정리 (10초)**: 면접관의 기억에 남길 문장

> "Direct-Mapped는 '빠르고 단순하지만 충돌에 약하고', N-Way는 '느리고 복잡하지만 미스율이 낮다'는 트레이드오프입니다."

---

### 4.3 교재에 포함할 추가 면접 키워드

다음 용어들은 `<aside class="interview">` 박스에 포함시킬 것을 권고한다:
- **Cold Miss (Compulsory Miss)**: 처음 접근하는 주소로 인한 미스. 회피 불가.
- **Capacity Miss**: 캐시 용량 자체가 부족해서 발생하는 미스.
- **Conflict Miss (Collision Miss)**: 직접 매핑에서 같은 Index에 매핑되는 주소들의 충돌. N-Way로 해결 가능.
- **3C 미스 (Cold, Capacity, Conflict)**: 면접에서 "캐시 미스의 3가지 종류"로 자주 출제됨.

### 5.3 강의 운영 시 주의사항

1. **13.3절(실습)은 건너뛰지 말 것**: 이 절은 수강생이 추상 개념을 손으로 확인하는 유일한 기회이다. 시간이 부족하더라도 최소 1~2문제는 수업 중에 풀게 해야 13.4절 이후의 코드 이해가 원활하다.

2. **BRAM 지연 논쟁은 사전에 차단할 것**: 2차시 시작 전에 "Tag LUTRAM + Data BRAM 분리" 구조를 칠판/슬라이드에 명시해두면 1차시에서 나온 Q1 질문이 2차시에 반복되지 않는다.

3. **Ch12 버블정렬과 연결할 것**: Ch12의 마일스톤(배열 [64,5,66,...] 정렬)이 공간적 지역성의 완벽한 예시이다. "여러분이 이미 돌린 버블정렬이 캐시 친화적인 코드입니다"라고 언급하면 수강생의 성취감과 새 개념이 연결된다.

4. **충돌 미스 예제는 반드시 수치를 사용할 것**: "같은 Index에 두 주소가 매핑된다"는 설명은 구체적인 예시 없이 강의하면 이해율이 매우 낮다. 위 막힘 포인트 3의 4KB 직접 매핑 수치 예제를 필수 슬라이드로 준비할 것.
