## 3. 학습 흐름 설계

### 챕터 도입 비유: "도서관 서고(DRAM)와 사서 책상(캐시)"

> "상상해보십시오. 여러분이 연구를 위해 매번 지하 서고에서 책을 꺼내야 한다면, 한 권을 가져오는 데 몇 분이 걸릴 것입니다. 그러나 사서가 자주 요청받는 책을 책상 위에 미리 올려두면, 대부분의 요청을 즉시 처리할 수 있습니다. 캐시(Cache)가 바로 이 사서 책상입니다. DRAM(지하 서고)에서 자주 쓰이는 명령어를 SRAM(책상)에 임시 보관하여, 프로세서가 매번 느린 DRAM에 접근하지 않아도 되게 합니다."

**비유의 한계 명시**: "이 비유는 지역성 원리(자주 요청받는 책)를 직관적으로 설명합니다. 그러나 실제 캐시에서는 '어떤 책이 자주 요청될지 사전에 모릅니다' — 대신 최근에 요청된 책들이 곧 다시 요청될 가능성이 높다는 통계적 원리(시간적 지역성)를 활용합니다."

### 13.1절 학습 흐름 — 메모리 계층 구조와 지역성 원리

**도입 → 개념 → 비유 → 코드/SVG → 실습 → 정리**

**도입 (왜 필요한가?)**

- 감정 연결: Ch12 버블정렬 성공 직후 "이제 CPU 코어는 완성됐습니다. 그런데 버블정렬 실행 중 프로세서가 실제 연산에 쓴 시간 대비 메모리를 기다리는 시간이 더 길었다면 어떨까요?" — 파이프라인 완성 성취감에서 새 문제 의식으로 전환
- 구체적 수치 제시: 레지스터(1사이클) vs DRAM(100~300사이클) 접근 지연 → "여러분의 65MHz 파이프라인이 매 LW 명령어마다 300사이클을 기다린다면 실제 CPI는 얼마일까요?" — 경이감 유발

**신규 핵심 개념 (3개)**

1. **메모리 계층(Memory Hierarchy)**: 속도-용량-비용의 역삼각형 구조 (레지스터→L1→L2→LLC→DRAM→저장장치)
2. **시간적 지역성(Temporal Locality)**: 최근에 접근한 데이터는 곧 다시 접근될 가능성이 높다
3. **공간적 지역성(Spatial Locality)**: 최근에 접근한 주소 근처의 데이터가 곧 접근될 가능성이 높다 (캐시 라인 단위 전송의 근거)

**비유**

- 시간적 지역성: "오늘 읽은 책을 책상 위에 그대로 두면 내일도 그 책을 다시 꺼낼 필요가 없다"
- 공간적 지역성: "3장을 읽으면 4장이 궁금해진다 — 한 챕터 전체를 책상에 올려두는 이유"
- 캐시 라인(Cache Line): "한 권씩 가져오지 않고 '챕터 묶음'으로 가져오는 것"

### 13.2절 학습 흐름 — 직접 매핑 캐시 설계

**도입 → 개념 → 비유 → 코드/SVG → 실습 → 정리**

**도입 (왜 필요한가?)**

- "13.1절에서 캐시가 필요한 이유를 이해했습니다. 이제 실제로 어떻게 구현하는지 설계합니다."
- 설계 결정 먼저 공개: "이 교재에서는 가장 간단한 구조인 직접 매핑(Direct-Mapped) 캐시부터 시작합니다. 왜 가장 단순한 것부터 시작하는지는 13.2절 말미에서 설명합니다."

**신규 핵심 개념 (3개)**

1. **직접 매핑(Direct-Mapped)**: 각 메모리 주소가 캐시의 정확히 한 위치에만 저장되는 방식
2. **Tag/Index/Offset 분리**: 32비트 주소를 세 필드로 분리하는 방법 (Offset=블록 내 위치, Index=캐시 라인 선택, Tag=동일 인덱스 중 구분)
3. **Valid 비트**: 캐시 라인이 유효한 데이터를 갖고 있는지 나타내는 1비트 플래그

**비유: 도서관 책 분류 시스템**

- Index → "책장 번호(0~127번 서가)"
- Offset → "해당 서가에서 몇 번째 책(0~31번)"
- Tag → "서가 번호만 보면 어느 서가인지 알 수 있지만, 같은 서가에 여러 책 세트 중 어떤 세트인지 구분하는 라벨"
- Valid 비트 → "이 서가에 책이 실제로 꽂혀 있는가? (부팅 직후 빈 서가)"

**비유의 한계**: "이 비유에서 도서관 서가는 책이 1:1로 대응되지만, 실제 캐시에서는 하나의 인덱스에 매우 많은 메모리 주소가 대응됩니다. Tag는 바로 이 중복 문제를 해결합니다."

**SVG**

- `ch13_sec02_address_decomposition.svg`: 32비트 주소 → Tag(19)/Index(7)/Offset(5) 비트 분리 다이어그램
- `ch13_sec02_direct_mapped_structure.svg`: 128엔트리 직접 매핑 캐시 구조 (Valid + Tag + Data 필드)
- `ch13_sec02_hit_miss_flowchart.svg`: 히트/미스 판정 흐름도 (Index 조회 → Valid 확인 → Tag 비교 → 히트/미스)

**코드**

```systemverilog
// L1 명령어 캐시 기본 구조 (4KB, 직접 매핑)
// 128엔트리 × 32바이트(8워드) 블록
// 주소 분해: [31:13]=Tag(19비트), [12:6]=Index(7비트), [5:2]=Block Offset(4비트), [1:0]=Byte Offset(2비트)
parameter CACHE_ENTRIES = 128;
parameter BLOCK_WORDS   = 8;    // 32바이트 블록 = 8개 워드

logic valid [CACHE_ENTRIES-1:0];
logic [18:0] tag  [CACHE_ENTRIES-1:0];
logic [31:0] data [CACHE_ENTRIES-1:0][BLOCK_WORDS-1:0];
```

**실습**

- 없음 (주소 분해 실습은 13.3절)
- faq aside: "왜 Offset이 Byte 주소 기준이 아닌 Word 주소 기준인가?" — 32비트 RISC-V에서 명령어는 항상 4바이트 정렬이므로 하위 2비트는 항상 00

**정리**

- interview aside: "직접 매핑 vs 세트 연관 vs 완전 연관 — 면접 단골 질문" (구조 비교는 13.6절 연습문제로 심화 예정)

**인지 부하 평가**: 신규 개념 3개. 중간. Tag/Index/Offset이 서로 독립적으로 보이지만 하나의 주소 분해 원리에서 나오므로, 세 개념이 하나의 스키마로 묶임. 실제 부하는 중간 이하.

### 13.3절 학습 흐름 — 직접 해보기: 캐시 주소 분해 연습

**도입 → 개념 → 비유 → 코드/SVG → 실습 → 정리**

**도입 (왜 필요한가?)**

- "13.2절에서 Tag/Index/Offset의 의미를 이해했습니다. 이제 손으로 직접 계산해봅시다. 이 절을 통과하면 '캐시 주소 분해'가 완전히 몸에 익습니다."
- 안심 문구: "종이에 연필로 계산하는 단순한 작업입니다. 프로그래밍이 없어도 됩니다."

**신규 핵심 개념**: 없음 (13.2절 개념의 적용 연습)

**실습 설계: 3단계 스캐폴딩**

**단계 1 — 안내된 계산 (Guide)**

캐시 파라미터: 엔트리=128개, 블록=8워드(32바이트), 주소 32비트
→ Offset: log₂(32) = 5비트 / Index: log₂(128) = 7비트 / Tag: 32-5-7 = 20비트

| 주소 (16진수) | Tag [31:12] | Index [11:5] | Offset [4:2] | 히트/미스? |
|:-----------:|:-----------:|:------------:|:------------:|:---------:|
| 0x0000_0000 | 0x00000 | 0b0000000 | 0b000 | 미스 (초기) |
| 0x0000_0004 | 0x00000 | 0b0000000 | 0b001 | **히트** (같은 블록!) |
| 0x0000_0020 | 0x00000 | 0b0000001 | 0b000 | 미스 (다른 인덱스) |

> "0x0000_0000과 0x0000_0004는 같은 캐시 라인(인덱스 0, 블록)에 속합니다. 첫 번째 접근이 미스이면 블록 전체를 가져오므로, 두 번째 접근은 히트가 됩니다."

**단계 2 — 독립 계산 (Practice)**

주어진 5개 주소에 대해 Tag/Index/Offset을 직접 계산하고 히트/미스를 판정
- 버블정렬 배열 접근 패턴을 실제 주소로 변환하여 제시 (현실감 제공)
- 정답 표 별도 제공 (즉시 피드백)

**단계 3 — 분석 (Think)**

- "버블정렬 내부 루프에서 인접한 두 원소(mem[i], mem[i+1])를 비교할 때, 첫 번째 원소 미스 후 두 번째 원소는 항상 히트인가? 왜 그런가?" → 공간적 지역성 재확인

**실습 결과 기대 효과**

- 종이 계산을 통한 체화 → "이제 캐시 주소 분해는 자동으로 됩니다"
- 공간적 지역성의 실제 효과를 수치로 확인

**시뮬레이션 미니 실습**

- 4개 주소의 히트/미스 시퀀스를 simple SystemVerilog 테스트벤치로 시뮬레이션
- `$display`로 히트/미스 여부 출력 확인
- 목적: "종이 계산과 시뮬레이션 결과가 일치하는지 검증" — 신뢰감 형성

**정리**

- metacognition aside: "이 절을 마친 후 다음 질문에 답할 수 있어야 합니다: ① 주소 0x1000_0000의 Index는? ② 같은 Index를 가진 두 주소가 충돌할 때 어떻게 되는가? (Conflict Miss)"

**인지 부하 평가**: 신규 개념 없음. 낮음. 완전한 실습 절 — 부하보다 성취감 설계가 핵심.

### 13.4절 학습 흐름 — 캐시 미스 처리: Stall 메커니즘

**도입 → 개념 → 비유 → 코드/SVG → 실습 → 정리**

**도입 (왜 필요한가?)**

- "캐시 미스가 발생하면 DRAM에서 데이터를 가져오는 동안 파이프라인은 어떻게 해야 할까요?"
- Ch10/11 선행 지식 활성화: "Ch10에서 Load-Use 스톨을 설계했습니다. 캐시 미스 스톨은 그 연장선에 있습니다 — 단, 1사이클이 아닌 수십~수백 사이클입니다."

**신규 핵심 개념 (2개)**

1. **icache_stall**: 명령어 캐시 미스 시 파이프라인 전체를 홀드하는 제어 신호
2. **캐시 미스 패널티(Miss Penalty)**: 미스 발생 후 DRAM에서 블록을 채울 때까지의 사이클 수

**선행 지식 연결 — "이미 아는 것의 확장"**

| Ch10/11 개념 | Ch13 확장 |
|------------|---------|
| `pc_en = ~stall` (PC 홀드) | `pc_en = ~icache_stall` (캐시 미스 시 PC 홀드) |
| `if_id_en = ~stall` (IF/ID 홀드) | `if_id_en = ~icache_stall` (캐시 미스 시 파이프라인 전체 홀드) |
| Load-Use 스톨: 1사이클 | 캐시 미스 스톨: 미스 패널티만큼 (예: 10~30사이클) |
| `id_ex_flush` (Load-Use 버블) | 캐시 미스 중 새 명령어 인출 없음 (flush 아닌 hold) |

**SVG**

- `ch13_sec04_cache_miss_stall_timeline.svg`: 캐시 미스 발생 → DRAM 접근 → 캐시 라인 채움 → 파이프라인 재개 타이밍 다이어그램
- `ch13_sec04_stall_signal_connection.svg`: icache_stall이 파이프라인 레지스터 enable/flush 신호와 연결되는 제어 패스

**코드 — icache_stall 연동**

```systemverilog
// 파이프라인 최상위 모듈에서 icache_stall 연동
// icache_stall이 1이면 파이프라인 전체 홀드 (새 명령어 인출 중단)
assign pc_en      = ~icache_stall & hdu_pc_en;
assign if_id_en   = ~icache_stall & hdu_if_id_en;
assign id_ex_en   = ~icache_stall;
assign ex_mem_en  = ~icache_stall;
assign mem_wb_en  = ~icache_stall;
// 주의: icache_stall 중에는 flush 신호도 억제 (이미 올바른 명령어를 hold 중)
```

**캐시 미스 처리 FSM (간략화)**

```
IDLE → (히트) → 정상 동작
IDLE → (미스) → MISS_WAIT → (DRAM 응답 완료) → FILL → IDLE
MISS_WAIT 중: icache_stall = 1 (파이프라인 홀드)
FILL: 캐시 라인 갱신 (Tag, Data, Valid=1 업데이트)
```

> "본격적인 캐시 미스 FSM은 Ch15에서 다룹니다. 여기서는 icache_stall 신호가 파이프라인을 어떻게 멈추는지에 집중합니다."

**실습**

- 타이밍 다이어그램 완성 연습: 미스 패널티 N=10사이클일 때 캐시 미스 후 파이프라인 재개까지 몇 사이클이 소요되는가?
- 파이프라인 레지스터의 enable 신호 변화를 직접 채워보기

**정리**

- faq aside: "icache_stall 중에 분기 플러시 신호가 발생하면 어떻게 되는가?" — "캐시 미스 처리 완료 후 플러시를 처리합니다. 우선순위: 캐시 스톨 > 분기 플러시 (스톨 완료 후 올바른 PC에서 재시작)"

**인지 부하 평가**: 신규 개념 2개. 중간. Ch10/11의 스톨 메커니즘을 직접 재활용하므로 체감 부하 낮음.

### 13.5절 학습 흐름 — L1 명령어 캐시 시뮬레이션

**도입 → 개념 → 비유 → 코드/SVG → 실습 → 정리**

**도입 (왜 필요한가?)**

- "캐시 설계와 미스 처리 메커니즘을 구현했습니다. 실제로 얼마나 효과적인지 시뮬레이션으로 측정해봅시다."
- 성취 예고: "이 절을 마치면 '버블정렬 실행 시 캐시 히트율 XX%'를 직접 측정할 수 있습니다."

**신규 핵심 개념 (1개)**

1. **미스 패널티(Miss Penalty) 측정과 히트율(Hit Rate) 계산**: 시뮬레이션 파형에서 히트/미스 카운터를 읽어 히트율을 계산하는 방법

**시뮬레이션 시나리오 설계**

| 시나리오 | 목적 | 예상 결과 |
|---------|------|---------|
| S1: 순차 명령어 실행 (공간적 지역성) | 캐시 라인 채움 후 연속 히트 | 히트율 >85% |
| S2: 루프 실행 (시간적 지역성) | 동일 명령어 반복 → 첫 패스 미스, 이후 히트 | 히트율 >90% |
| S3: 버블정렬 전체 실행 | 현실적 히트율 측정 | 히트율 ~80~90% |
| S4: 캐시보다 큰 코드 (용량 미스) | 캐시 교체로 인한 히트율 저하 | 히트율 <50% |

**SVG**

- `ch13_sec05_hit_miss_waveform.svg`: 히트(1사이클) vs 미스(N사이클+icache_stall) 파형 비교
- `ch13_sec05_miss_penalty_measurement.svg`: 미스 패널티 사이클 수를 파형에서 직접 측정하는 방법

**코드 — 히트/미스 카운터 테스트벤치**

```systemverilog
// 테스트벤치에서 캐시 히트/미스 통계 수집
integer hit_count  = 0;
integer miss_count = 0;

always @(posedge clk) begin
   if (icache_valid_req) begin
      if (icache_hit)  hit_count  <= hit_count  + 1;
      else             miss_count <= miss_count + 1;
   end
end

final begin
   $display("히트율: %0d%%", hit_count * 100 / (hit_count + miss_count));
   $display("총 사이클 (캐시 미스 포함): %0d", cycle_count);
end
```

**실습 — 마일스톤 연결**

- 버블정렬 프로그램을 L1 I-Cache가 연동된 파이프라인에서 실행
- 히트율 측정 및 `cycle_count` 비교: 캐시 없음 vs 캐시 있음
- 예상 결과: "캐시 히트율 ~85%, 총 실행 사이클 약 XX% 감소"
- Part 5 마일스톤 예고: "이것이 13.5절의 부분 마일스톤입니다. Ch15에서 D-Cache까지 완성한 후 전체 캐시 히트율 벤치마크를 수행합니다."

**정리**

- instructor-tip aside: "시뮬레이션에서 히트율이 예상보다 낮을 때 확인 사항: ① 캐시 라인 크기가 너무 작지 않은가? ② 프로그램이 캐시 크기보다 큰가? ③ 초기화 플러시(cold miss)를 고려했는가?"

**인지 부하 평가**: 신규 개념 1개. 낮음. 주로 기존 시뮬레이션 방법론의 응용.

### [기억 — Remember] 문제 1 : 용어 정의

다음 용어를 각각 한 문장으로 정의하시오.

(가) 시간적 지역성(Temporal Locality)

- (다) 캐시 미스 발생 후 주 메모리(DRAM)에서 캐시 라인을 채울 때까지 소요되는 추가 사이클 수

### [기억 — Remember] 문제 2 : 메모리 계층 구조 나열

메모리 계층 구조를 속도가 빠른 순서대로 나열하고, 각 계층의 대표적인 용량 범위를 함께 기술하시오. (레지스터, L1 캐시, L2 캐시, DRAM, SSD 포함)

**기대 답변**:
레지스터(32개, ~1사이클) > L1 캐시(수십 KB, ~4사이클) > L2 캐시(수백 KB~수 MB, ~10사이클) > DRAM(수 GB, ~100~300사이클) > SSD(수 TB, ~수만 사이클)

**채점 기준**: 순서 정확 + 각 계층 용량 범위 대략 일치 시 만점.

### [이해/적용 — Understand/Apply] 문제 3 : 주소 분해

다음 캐시 파라미터를 사용하여 주어진 주소를 Tag/Index/Offset으로 분해하고, 두 접근이 히트인지 미스인지 판정하시오.

**캐시 파라미터**: 총 엔트리 수=128, 블록 크기=32바이트(8워드), 주소=32비트

(가) 처음 접근하는 주소 0x0000_0040 (Tag/Index/Offset 계산 후 히트/미스 판정)
(나) 바로 직후 접근하는 주소 0x0000_0048 (동일 캐시 라인인가?)
(다) 주소 0x0001_0040과 0x0000_0040은 같은 캐시 라인에 저장될 수 있는가? 충돌(Conflict)이 발생하는가?

**기대 답변**:
- Offset: log₂(32) = 5비트 [4:0] / Index: log₂(128) = 7비트 [11:5] / Tag: 32-7-5 = 20비트 [31:12]
- (가) 0x0000_0040: Tag=0x00000, Index=0b0000010, Offset=0b00000 → **첫 접근이므로 미스 (Cold Miss)**
- (나) 0x0000_0048: Tag=0x00000, Index=0b0000010, Offset=0b00010 → **같은 캐시 라인(인덱스 2, 블록 내 2번째 워드) → 히트**
- (다) 0x0001_0040: Tag=0x00001, Index=0b0000010 → **같은 인덱스(2)이나 Tag가 다름 → Conflict 발생** (동시에 저장 불가)

**채점 기준**: Offset/Index/Tag 비트 수 정확, (나) "같은 라인이므로 히트" 설명, (다) Conflict Miss 개념 포함 시 만점.

### [분석 — Analyze] 문제 5 : icache_stall 파이프라인 분석

다음 조건에서 icache_stall이 파이프라인에 미치는 영향을 분석하시오.

**조건**: L1 I-Cache 미스 패널티 = 20사이클, 명령어 캐시 히트율 = 90%, 실행 프로그램 총 명령어 수 = 1000개

(가) 평균 CPI를 계산하시오. (가정: 캐시 미스를 제외하면 CPI=1.2, 모든 미스는 동일한 20사이클 패널티)

(나) icache_stall=1인 동안 파이프라인의 각 레지스터(PC, IF/ID, ID/EX, EX/MEM, MEM/WB) 상태는 어떻게 되는가? (변화 없음/클리어/유지 중 선택)

(다) 미스 패널티를 10사이클로 줄이면 CPI는 얼마나 개선되는가?

**기대 답변**:
- (가) 미스율 = 10% = 0.1. 미스 패널티를 고려한 CPI = 1.2 + (0.1 × 20) = 1.2 + 2.0 = **3.2**
- (나) PC=유지(hold), IF/ID=유지(hold), ID/EX=유지(hold), EX/MEM=유지(hold), MEM/WB=유지(hold) — flush가 아닌 전체 hold
- (다) CPI = 1.2 + (0.1 × 10) = 1.2 + 1.0 = **2.2** → 3.2에서 2.2로 약 **31% 개선**

**채점 기준**: (가) CPI 계산 정확, (나) hold/flush 구분 정확, (다) 개선 계산 및 비율 정확 시 만점.

### [평가 — Evaluate] 문제 6 : 캐시 구조 설계 결정

다음 세 가지 캐시 구조에 대해 주어진 설계 요구사항에 맞게 최적 구조를 선택하고, 근거를 제시하시오.

**세 가지 캐시 구조**:
- A: 직접 매핑 (Direct-Mapped), 하드웨어 가장 단순
- B: 2-way 세트 연관 (Set-Associative), 중간 복잡도
- C: 완전 연관 (Fully Associative), 하드웨어 가장 복잡

**시나리오 1**: Basys 3 FPGA에 탑재할 L1 I-Cache. LUT 예산이 빠듯하고 (전체의 15% 이하), 실행 프로그램이 비교적 단순한 제어 루프 중심이다.

**시나리오 2**: 고성능 프로세서(PC급)의 L1 I-Cache. 캐시 히트율이 성능에 결정적 영향을 미치며, 트랜지스터 예산에 여유가 있다.

(가) 각 시나리오에서 어떤 구조를 선택하겠는가?
(나) 구조 A, B, C 각각의 Conflict Miss 발생 가능성을 비교하시오.
(다) "직접 매핑이 항상 나쁜 선택인가?"라는 질문에 근거를 들어 답하시오.

**기대 답변**:
- (가) 시나리오 1: **A (직접 매핑)** — LUT 예산 제약, 단순 프로그램 패턴에서 충돌 미스 발생 빈도 낮음. 시나리오 2: **B 또는 C** — 히트율 최우선, 면적 여유 있음 (B가 C보다 구현 비용 낮아 일반적 선택)
- (나) Conflict Miss: A > B > C (직접 매핑이 가장 높음, 완전 연관이 없음)
- (다) **정답 없음 — 근거 논리 평가**: "직접 매핑은 하드웨어가 가장 단순하고, 프로그램 패턴에 따라 충분한 히트율을 달성할 수 있습니다. 임베디드 시스템이나 FPGA 구현처럼 면적 제약이 있는 환경에서는 합리적 선택입니다." 또는 "직접 매핑은 Hot Spot 충돌 취약점이 있어 고성능 환경에는 부적합합니다. 최소한 2-way 연관이 권장됩니다." — 어느 쪽이든 근거가 논리적이면 만점.

**채점 기준**: (가) 시나리오별 선택 + 이유 1개 이상. (나) Conflict Miss 순서 정확. (다) 조건부 긍정/부정 형식으로 논리적 근거 제시 시 만점. 단, "항상 나쁘다/항상 좋다"는 단정적 답변은 감점.

Q: 블록 크기를 더 크게 하면 히트율이 올라가지 않나요?

#### 안심 장치 4: 13.5절 — "히트율이 낮아도 괜찮다" (metacognition aside)

```
🔍 스스로 점검

시뮬레이션에서 캐시 히트율이 생각보다 낮게 나왔나요?
그것은 여러분의 구현이 잘못된 것이 아닙니다.

히트율은 다음 중 하나의 원인으로 낮을 수 있습니다:
① Cold Miss: 처음 접근하는 주소는 항상 미스 (초기화 비용)
② Conflict Miss: 직접 매핑에서 같은 인덱스를 사용하는 주소 간 충돌
③ Capacity Miss: 프로그램이 캐시보다 큰 경우

이 중 어떤 원인인지 파악하는 것이 "분석 수준"의 목표입니다.
80% 이상이면 일반적으로 양호한 L1 캐시 동작입니다.
만약 80% 미만이라면, 원인을 분석하여 Ch14(세트 연관)에서 개선하면 됩니다.
완벽하지 않아도 됩니다 — 개선의 여지가 있어야 Ch14가 의미 있어집니다.
```

"이 요구사항에서 A가 나은가, B가 나은가?"

① 각 선택지의 장단점을 파악한다 (분석)
② 주어진 제약 조건과 우선순위를 확인한다

## 8. 감정 곡선 설계

```
13.1절 입장 시: ★★★(Ch12 버블정렬 FPGA 성공 여운)
  → 새 문제 인식: "CPU 코어 완성. 그런데 메모리가 발목을 잡는다?"

  → 도서관 비유로 안심 ("아, 주소를 세 부분으로 나누는 거구나")
  → 이해의 만족감 ("캐시가 이렇게 동작하는구나")
  ↓
13.3절: 평온 + 집중 ("손으로 계산하는 것이 오히려 명확하다")
  → 실습 성공 → 작은 성취감 ★ ("이제 주소 분해는 자동으로 됩니다")
  ↓

  → 이해의 즐거움 ("이미 아는 것을 새 문맥에서 활용하는 기쁨")
  ↓
13.5절: 기대 + 측정의 설렘 ("내 캐시가 얼마나 효과적인지 수치로 확인!")

  ↓
13.6절: ★★ 성취감 귀착 ("L1 I-Cache를 완성했습니다")
  + 미래 호기심 ("D-Cache에는 쓰기 처리가 추가됩니다 — Ch14에서")
```

## 9. Ch13 → Ch14 학습 연결 설계

### 핵심 연결 문장 (13.6절 배치)

> "Ch13에서는 명령어를 가져오는 L1 I-Cache를 완성했습니다. 히트율 ~85%의 직접 매핑 캐시가 파이프라인과 연동되어 동작하는 것을 확인했습니다. 그런데 LW, SW처럼 데이터를 읽고 쓰는 명령어에도 캐시가 필요합니다. 데이터 캐시(D-Cache)는 명령어 캐시와 결정적으로 다른 점이 있습니다 — '쓰기(Write)'를 처리해야 합니다. 쓸 때마다 DRAM에도 반영해야 할까요? 아니면 캐시에만 먼저 쓰고 나중에 DRAM에 반영할까요? 이 선택이 Chapter 14의 Write-Through vs Write-Back 정책입니다."

### 연결 근거

| Ch13 학습 내용 | Ch14 직접 활용 | 연결 강도 |
|--------------|-------------|:-------:|
| Tag/Index/Offset 분리 | D-Cache의 동일 구조 재사용 | 매우 강함 |
| 직접 매핑 기본 구조 | D-Cache에서 2-way 연관으로 확장 | 강함 |
| icache_stall 신호 | dcache_stall 신호와 동일 패턴 | 강함 |
| 히트/미스 판정 로직 | D-Cache에서 Valid + Dirty 비트 추가 | 강함 |
| 캐시 미스 FSM (간략화) | Ch15에서 완전한 미스 처리 FSM으로 확장 | 중간 |
