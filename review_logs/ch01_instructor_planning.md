## 1. 수강생이 막힐 것으로 예상되는 포인트 Top 5

### 막힘 포인트 #1: Vivado 설치 실패 및 환경 설정 오류 (1.2절)

| 항목 | 내용 |
|------|------|
| **발생 이유** | Vivado 설치 파일이 20GB 이상으로 방대하고, Windows 경로에 한글이나 공백이 포함되면 설치가 실패한다. USB 드라이버 미인식, 방화벽 차단, 디스크 용량 부족 등 환경마다 다른 오류가 발생하여 "첫 단추"에서 좌절하는 경우가 매우 흔하다. |
| **해소 방법** | (1) 설치 전 체크리스트를 제공한다: 디스크 여유 공간 50GB 이상, 설치 경로 `C:\Xilinx`(공백/한글 없음), Windows 사용자명 영문 확인. (2) "설치 오류 해결 FAQ" 박스를 1.2절 말미에 배치하고, 주요 오류 코드 5개와 해결법을 표로 정리한다. (3) Appendix E 참조 링크를 명시한다. (4) "설치에 2시간이 걸리는 것은 정상입니다"라는 안심 문구를 배치한다. |
| **등급** | **Critical** — 환경 설정 실패는 1주차 이탈의 가장 큰 원인이다 |

### 막힘 포인트 #2: `logic` 타입과 `reg`/`wire` 차이 혼란 (1.3절)

| 항목 | 내용 |
|------|------|
| **발생 이유** | Verilog 경험자는 `reg`와 `wire`를 구분하는 사고 방식이 이미 체화되어 있다. SystemVerilog의 `logic`이 "둘 다 대체한다"고 하면, 기존 멘탈 모델과 충돌하여 "그러면 합성할 때 reg가 되는 건가 wire가 되는 건가?"라는 혼란이 발생한다. |
| **해소 방법** | (1) 핵심 메시지를 먼저 제시: "`logic`은 합성 도구가 문맥(context)에 따라 자동으로 레지스터 또는 와이어로 추론한다." (2) 비교표 제공: Verilog `reg`/`wire` vs SystemVerilog `logic`의 사용 문맥별 대응. (3) "Verilog에서 `reg`라고 선언했다고 반드시 플립플롭이 되는 것은 아니었다"는 사실을 상기시켜, 기존 개념 자체가 불완전했음을 인식시킨다. |
| **등급** | **Major** — 이후 모든 코드의 기준선이므로 여기서 혼란이 남으면 누적된다 |

### 막힘 포인트 #3: `always_ff` vs `always_comb` vs 기존 `always @(*)` 구분 (1.3절)

| 항목 | 내용 |
|------|------|
| **발생 이유** | Verilog에서는 `always @(posedge clk)`과 `always @(*)`만 구분하면 됐으나, SystemVerilog는 `always_ff`, `always_comb`, `always_latch` 세 가지를 도입했다. 수강생은 "기존 `always`를 그냥 쓰면 안 되나?"라고 생각하며, 새 키워드의 실질적 이점을 체감하지 못한다. |
| **해소 방법** | (1) 잘못된 코드 예시를 먼저 보여준다: `always @(*)`에서 래치(latch)가 추론되는 실수를 Vivado 경고 메시지와 함께 제시. (2) 동일 코드를 `always_comb`으로 바꾸면 **컴파일 에러**가 나서 실수를 조기 발견할 수 있음을 시연. (3) "도구가 당신의 의도를 검증해준다"는 관점으로 설명하면 SystemVerilog 키워드의 가치가 즉시 체감된다. |
| **등급** | **Major** — 면접 빈출 주제(#9)이기도 하므로 확실히 잡아야 한다 |

### 막힘 포인트 #4: XDC 제약 파일과 물리적 핀 매핑 이해 (1.4절)

| 항목 | 내용 |
|------|------|
| **발생 이유** | RTL 설계에 익숙한 수강생도 "논리적 신호 이름"과 "물리적 FPGA 핀 번호"의 연결 개념이 낯설다. XDC 파일의 `set_property PACKAGE_PIN` 문법이 TCL 기반이라 HDL과 완전히 다른 문법 체계이므로 추가적인 혼란이 발생한다. |
| **해소 방법** | (1) Basys 3 보드 사진(또는 SVG)에 LED와 스위치의 물리적 위치를 표시하고, 각 위치에 핀 이름을 라벨링한다. (2) XDC 파일을 "RTL 세계와 물리 세계를 연결하는 번역표"로 비유한다. (3) Basys 3 Master XDC 파일에서 필요한 줄만 주석 해제하는 방식으로 안내하여 처음부터 작성하지 않아도 됨을 알려준다. |
| **등급** | **Minor** — 한 번 이해하면 반복 사용이므로 초기 장벽만 넘기면 된다 |

### 막힘 포인트 #5: 시뮬레이션 파형 해석 능력 부족 (1.5절)

| 항목 | 내용 |
|------|------|
| **발생 이유** | 파형 뷰어(Vivado Simulator 또는 Verdi)에서 신호를 추가하고, 줌/패닝하고, 커서로 시간을 측정하는 기본 조작이 익숙하지 않다. 특히 "시뮬레이션은 돌렸는데 파형에서 뭘 봐야 하는지 모르겠다"는 상태가 흔하다. |
| **해소 방법** | (1) LED 점멸 예제의 시뮬레이션 파형을 스크린샷(또는 SVG)으로 제공하고, "어떤 신호가 어떤 시점에 어떤 값이어야 정상인지"를 화살표로 명시한다. (2) "파형 읽기 3단계 가이드"를 제공: 클럭 확인 → 리셋 해제 시점 확인 → 출력 신호 변화 확인. (3) 시뮬레이션 시간 단위(ns, us)와 실제 시간의 관계를 설명한다. |
| **등급** | **Minor** — 이후 모든 챕터에서 파형을 사용하므로 여기서 기초를 다져야 한다 |

| 비유 | 설명할 개념 | 매핑 상세 | 한계점 |
|------|-----------|----------|--------|
| **운전면허 보유자가 수동 → 자동 변속기로 전환** | Verilog(수동) → SystemVerilog(자동) 전환 | `reg`/`wire` = 클러치/기어 수동 조작, `logic` = 자동 변속기(도구가 알아서 판단). `always_ff`/`always_comb` = 주행 모드(D/R) 명시적 선택. 수동 운전 경험이 있어서 자동이 더 쉬움 | SystemVerilog는 Verilog의 상위 집합이므로 "완전히 다른 차"가 아님. 기존 Verilog 코드도 그대로 동작한다는 점을 명시 |
| **`logic` = 만능 컨테이너** | `logic` 타입이 `reg`와 `wire`를 모두 대체함 | 택배 상자(logic)에 뭘 넣든 배송 가능. 내용물(조합 로직 vs 순차 로직)에 따라 물류 방식(와이어 vs 플립플롭)이 결정됨. 상자 자체가 물류 방식을 결정하는 게 아님 | `logic`으로 대체할 수 없는 경우도 있다: 양방향(inout) 포트는 여전히 `wire` 필요. 이 예외를 명시 |

#### 1.4절 — 첫 번째 합성 실습: LED 점멸

| 비유 | 설명할 개념 | 매핑 상세 | 한계점 |
|------|-----------|----------|--------|
| **프로그래밍의 "Hello, World!"** | LED 점멸이 하드웨어 설계의 첫 번째 성공 경험임을 강조 | `printf("Hello, World!")` = LED ON/OFF. 소프트웨어 개발자가 첫 출력을 확인하듯, 하드웨어 설계자는 첫 LED 점멸로 "내 코드가 실제 하드웨어에서 동작한다"를 확인 | 소프트웨어는 컴파일 → 실행이 수초지만, FPGA는 합성 → 구현 → 비트스트림 생성에 수 분 소요. 인내심 필요 |
| **XDC = RTL 세계와 물리 세계의 번역표** | XDC 제약 파일의 역할 | RTL의 `output logic led` = 논리적 이름, FPGA의 `V17` 핀 = 물리적 위치. XDC가 둘을 연결하는 번역표. 번역표 없이는 신호가 어디로 나가야 하는지 FPGA가 알 수 없다 | XDC는 핀 매핑 외에 타이밍 제약도 포함하지만, 1.4절에서는 핀 매핑만 다루고 타이밍은 Ch06/Ch20으로 미룸 |

## 3. 수강생 단골 질문 예측 (FAQ)

### 3.1 — 1.1절: 이 책으로 무엇을 만드는가

| # | 예상 질문 | 답변 |
|:-:|----------|------|
| 1 | **"5단계 파이프라인은 너무 단순한 거 아닌가요? 요즘 프로세서는 훨씬 복잡하지 않나요?"** | 맞습니다. 현대 상용 프로세서는 10단계 이상의 파이프라인, 비순차 실행, 다중 이슈 등을 사용합니다. 하지만 5단계 파이프라인은 모든 고급 기법의 **기초(foundation)**입니다. 5단계를 완전히 이해하면 10단계는 "스테이지를 더 나눈 것"으로 자연스럽게 확장되고, 비순차 실행도 "순차 실행에서 어떤 제약을 풀었는가"로 이해할 수 있습니다. Part 9(심화)에서 슈퍼스칼라와 비순차 실행 개요를 다룹니다. |
| 2 | **"이 책을 끝내면 취업에 도움이 되나요?"** | 반도체 설계 직군(RTL 엔지니어, 검증 엔지니어, FPGA 엔지니어) 면접에서 가장 많이 출제되는 주제 11개를 이 교재가 모두 커버합니다. 특히 "5단계 파이프라인 그려보세요", "데이터 해저드 해결 방법은?", "캐시 구조를 설명해보세요"는 거의 모든 면접에서 나오는 질문이며, 이 교재에서 직접 설계하고 합성까지 해본 경험은 면접관에게 강력한 인상을 줍니다. |
| 3 | **"RV32I만 구현하면 실제 프로그램을 돌릴 수 있나요?"** | 네. RV32I는 정수 연산의 완전한 기본 명령어 세트(base integer instruction set)입니다. C 언어로 작성된 프로그램(곱셈/나눗셈은 소프트웨어 라이브러리 사용)을 컴파일하여 실행할 수 있습니다. Ch22에서 실제로 C 프로그램을 크로스 컴파일하여 FPGA에서 실행합니다. M 확장(곱셈/나눗셈 하드웨어)은 Part 9에서 선택적으로 다룹니다. |

### 3.2 — 1.2절: 개발 환경 설치 및 검증

| # | 예상 질문 | 답변 |
|:-:|----------|------|
| 1 | **"Vivado 무료 버전(WebPACK/Standard)으로 충분한가요?"** | 네, 충분합니다. Basys 3에 탑재된 XC7A35T는 Vivado Standard Edition(구 WebPACK)의 무료 지원 범위에 포함됩니다. 합성, 구현, 비트스트림 생성, 시뮬레이터 모두 사용 가능합니다. Enterprise Edition은 필요하지 않습니다. |
| 2 | **"VCS/Verdi가 없으면 수업을 따라갈 수 없나요?"** | 아닙니다. VCS/Verdi는 산업계 표준 도구이므로 소개하지만, 모든 시뮬레이션은 **Vivado Simulator(xsim)**로도 동일하게 수행할 수 있습니다. 대학원에서 Synopsys 라이선스가 있으면 VCS/Verdi를 사용하고, 없으면 Vivado Simulator를 사용하면 됩니다. 파형 분석 방법만 도구별로 약간 다를 뿐, 설계 자체는 동일합니다. |
| 3 | **"Mac이나 Linux에서도 할 수 있나요?"** | Vivado는 Linux를 공식 지원합니다(Ubuntu/CentOS). macOS는 공식 지원하지 않으므로 가상 머신이나 듀얼 부팅이 필요합니다. 이 교재는 Windows 기준으로 작성되었으나, Vivado의 GUI 동작은 Windows와 Linux에서 거의 동일합니다. Linux 사용 시 USB 드라이버 설정이 다를 수 있으며, 이는 Appendix E에서 다룹니다. |
| 4 | **"Basys 3 대신 다른 FPGA 보드를 써도 되나요?"** | Xilinx 7 시리즈 FPGA가 탑재된 보드(예: Nexys A7, Arty A7)라면 XDC 파일(핀 매핑)만 변경하여 사용할 수 있습니다. 다만 LED/스위치 수, BRAM 용량, I/O 핀 배치가 다르므로 일부 실습을 조정해야 합니다. Intel(Altera) FPGA 보드를 사용하려면 합성 도구(Quartus)와 제약 파일 형식이 완전히 달라지므로 상당한 수정이 필요합니다. |

### 3.3 — 1.3절: SystemVerilog 필수 문법 복습

| # | 예상 질문 | 답변 |
|:-:|----------|------|
| 1 | **"`logic`을 쓰면 `wire`와 `reg`를 아예 안 써도 되나요?"** | 대부분의 경우 그렇습니다. `logic`은 `wire`와 `reg`를 모두 대체합니다. 단, **양방향(inout) 포트**에는 여전히 `wire`를 사용해야 합니다. 또한 다중 드라이버(multiple driver) 상황에서도 `wire`가 필요합니다. 이 교재의 RV32I 프로세서 설계에서는 양방향 포트를 사용하지 않으므로, 사실상 `logic`만으로 충분합니다. |
| 2 | **"기존 `always @(posedge clk)`을 `always_ff`로 바꾸기만 하면 되나요?"** | 구문적으로는 `always @(posedge clk)` → `always_ff @(posedge clk)`으로 바꾸면 됩니다. 하지만 핵심 차이가 있습니다: `always_ff` 블록 안에서 **비블로킹 할당(`<=`)만 사용해야** 하며, 블로킹 할당(`=`)을 사용하면 합성 도구가 경고 또는 에러를 발생시킵니다. 이것이 바로 SystemVerilog가 의도를 검증해주는 기능입니다. |
| 3 | **"블로킹 할당(`=`)과 비블로킹 할당(`<=`)을 헷갈리면 어떻게 되나요?"** | 합성 결과가 의도와 달라집니다. `always_ff`에서 블로킹을 쓰면 시뮬레이션과 합성 간 불일치(simulation-synthesis mismatch)가 발생할 수 있습니다. **규칙은 단순합니다: `always_ff` 안에서는 `<=` (비블로킹), `always_comb` 안에서는 `=` (블로킹).** 이 규칙만 지키면 됩니다. SystemVerilog 도구가 위반 시 경고를 발생시키므로, `always_ff`/`always_comb`을 사용하는 것이 안전합니다. |
| 4 | **"`always_latch`는 언제 쓰나요?"** | 의도적으로 래치(latch)를 설계할 때 사용합니다. 하지만 **이 교재에서는 래치를 사용하지 않습니다.** FPGA 설계에서 래치는 거의 항상 설계 오류의 징후입니다. Vivado에서 "inferred latch" 경고가 나오면 `always_comb` 블록에서 모든 경우를 커버하지 않았다는 의미이므로, `default` 분기를 추가해야 합니다. |
| 5 | **"`enum`이나 `struct`도 합성되나요?"** | 네, 합성됩니다. `enum`은 FSM 상태 정의에 매우 유용하고(Ch08에서 활용), `struct`는 파이프라인 레지스터를 묶어서 선언할 때 유용합니다(Ch09에서 활용). 다만 `string`, `class`, `queue` 등 시뮬레이션 전용 타입은 합성되지 않습니다. |

## 4. 면접 포인트: `always_ff` vs `always_comb` (1.3절)

### 4.1 면접 질문과 모범 답변

#### 질문 1: "`always_ff`와 `always_comb`의 차이를 설명하시오."

> **모범 답변**:
>
> `always_ff`는 **순차 로직(sequential logic)**을 기술하기 위한 프로시저 블록이며, 반드시 클럭 에지(`posedge` 또는 `negedge`)에 의해 트리거됩니다. 내부에서는 **비블로킹 할당(`<=`)**을 사용해야 하며, 합성 시 **플립플롭(flip-flop)**으로 추론됩니다.
>
> `always_comb`은 **조합 로직(combinational logic)**을 기술하기 위한 프로시저 블록이며, 민감도 리스트가 자동으로 추론됩니다. 내부에서는 **블로킹 할당(`=`)**을 사용해야 하며, 합성 시 **게이트 로직(조합 회로)**으로 추론됩니다.
>
> SystemVerilog 이전의 `always @(posedge clk)`과 `always @(*)`와 동일한 기능이지만, 합성 도구가 **설계자의 의도를 검증**할 수 있다는 점이 핵심 차이입니다. 예를 들어, `always_comb` 블록에서 모든 입력 조합을 커버하지 않으면 래치가 추론되는데, 이때 도구가 경고를 발생시켜 설계 오류를 조기에 발견할 수 있습니다.

#### 질문 2: "`always_comb`에서 래치가 추론되는 조건은?"

> **모범 답변**:
>
> `always_comb` 블록에서 래치가 추론되는 조건은, **`case` 또는 `if-else` 문에서 모든 경우를 커버하지 않아 출력 변수에 값이 할당되지 않는 경로가 존재할 때**입니다. 합성 도구는 값이 할당되지 않은 경로에서 이전 값을 유지해야 한다고 판단하여 래치를 추론합니다.
>
> 해결 방법은 세 가지입니다:
> 1. `case` 문에 `default` 분기를 추가
> 2. 블록 시작부에 모든 출력에 기본값(default value)을 할당
> 3. `unique case` 또는 `priority case`를 사용하여 도구에 완전성(completeness)을 명시
>
> `always_comb`을 사용하면 도구가 이러한 상황을 감지하여 경고를 발생시키므로, 기존 `always @(*)`보다 안전합니다.

#### 질문 3: "블로킹 할당과 비블로킹 할당을 잘못 사용하면 어떤 문제가 생기나요?"

> **모범 답변**:
>
> **시뮬레이션-합성 불일치(simulation-synthesis mismatch)**가 발생합니다.
>
> 구체적으로:
> - `always_ff` 블록에서 **블로킹 할당(`=`)**을 사용하면, 시뮬레이션에서는 문장 순서에 따라 즉시 값이 반영되지만, 합성 도구는 여전히 플립플롭으로 구현하여 한 사이클 지연이 발생합니다. 결과적으로 시뮬레이션 결과와 합성 결과가 다릅니다.
> - `always_comb` 블록에서 **비블로킹 할당(`<=`)**을 사용하면, 시뮬레이션에서 델타 사이클 문제로 의도치 않은 동작이 발생할 수 있습니다.
>
> **규칙**: `always_ff` = `<=` (비블로킹), `always_comb` = `=` (블로킹). 이 규칙을 지키면 시뮬레이션과 합성 결과가 일치합니다.

#### 질문 4: "Verilog의 `always @(*)`와 SystemVerilog의 `always_comb`은 동일한가요?"

> **모범 답변**:
>
> 거의 동일하지만 **세 가지 차이**가 있습니다:
>
> 1. **자동 민감도 리스트**: `always @(*)`는 블록 내에서 읽히는 신호를 민감도 리스트에 자동 포함하지만, 함수 호출 내부의 신호는 누락될 수 있습니다. `always_comb`은 함수 내부 신호까지 포함하여 더 정확합니다.
> 2. **시뮬레이션 시작 시 실행**: `always_comb`은 시뮬레이션 시간 0에서 자동으로 한 번 실행되어 초기값을 설정합니다. `always @(*)`는 입력이 변할 때까지 실행되지 않습니다.
> 3. **의도 검증**: `always_comb`은 블록 안에서 래치가 추론되면 도구가 경고를 발생시킵니다. `always @(*)`는 아무 경고 없이 래치를 추론합니다.
>
> 따라서 신규 설계에서는 항상 `always_comb`을 사용하는 것이 권장됩니다.

1.3절에 다음과 같은 `<aside class="interview">` 박스를 배치할 것을 제안합니다:


## 5. 강사 꿀팁 (절별 `<aside class="instructor-tip">` 배치 제안)

### 1.1절 — 이 책으로 무엇을 만드는가

> **강사 꿀팁**: 전체 조감도(블록 다이어그램)를 1.1절에서 미리 보여줄 때, 수강생이 압도당하지 않도록 "지금 이해하지 않아도 됩니다"를 반드시 명시하십시오. 이 다이어그램은 Ch06, Ch09, Ch12에서 반복 등장하며, 그때마다 새로운 부분이 추가됩니다. 첫 노출의 목적은 "이해"가 아니라 "궁금증 유발"입니다. 강의 현장에서 이 조감도를 A3 포스터로 인쇄하여 강의실 벽에 붙여두면, 학기 중 수시로 "지금 우리는 여기를 만들고 있습니다"라고 가리킬 수 있어 효과적입니다.

### 1.2절 — 개발 환경 설치 및 검증

> **강사 꿀팁**: 환경 설치는 수업 시간에 하지 마십시오. 1주차 수업 **전에** 사전 공지로 "Vivado 설치를 완료하고 오세요"를 안내하고, 수업 시간에는 설치 확인만 진행하십시오. 경험상 수업 시간에 설치를 시작하면 학생마다 오류가 다르게 발생하여 수업이 진행되지 않습니다. 설치 실패 학생을 위한 "오피스 아워 트러블슈팅 세션"을 1주차에 별도로 마련하면 이탈률을 크게 줄일 수 있습니다. 대안으로, 대학 서버에 Vivado가 설치된 원격 데스크톱 환경을 제공하면 설치 문제를 완전히 회피할 수 있습니다.

### 1.3절 — SystemVerilog 필수 문법 복습

> **강사 꿀팁**: 이 절에서 가장 효과적인 교수법은 **"일부러 틀린 코드를 보여주는 것"**입니다. (1) `always_comb`에서 `default` 없이 작성하여 래치 경고가 나는 코드, (2) `always_ff`에서 블로킹 할당(`=`)을 사용하여 시뮬레이션과 합성 결과가 다른 코드를 라이브 시연하면, 수강생이 "왜 SystemVerilog 키워드를 써야 하는가"를 즉시 체감합니다. 올바른 코드만 보여주면 "그냥 외워야 하는 규칙"이 되지만, 틀린 코드를 먼저 보여주면 "나를 보호해주는 도구"가 됩니다.

### 1.4절 — 첫 번째 합성 실습: LED 점멸

> **강사 꿀팁**: LED 점멸 성공은 이 교재의 **첫 번째 마일스톤**이며, 수강생의 동기 부여에 결정적입니다. 가능하면 1주차 수업 시간 내에 최소 한 명의 학생이라도 LED 점멸에 성공하도록 유도하십시오. "실제로 깜빡이는 LED"를 본 순간의 성취감은 이후 수주간의 학습 동력이 됩니다. 합성 시간이 길어서 수업 내 완료가 어려우면, **미리 합성해둔 비트스트림 파일(.bit)을 제공**하여 다운로드만 시키는 방법도 있습니다. 먼저 성공을 경험한 후, 자신의 코드로 합성하는 순서가 심리적으로 효과적입니다.

### 1.5절 — 시뮬레이션 환경 설정

> **강사 꿀팁**: 시뮬레이션 파형 읽기는 이후 20개 챕터에서 반복 사용하는 핵심 기술입니다. 이 절에서 **최소 10분을 투자하여 파형 뷰어 조작을 직접 시연**하십시오: 신호 추가, 줌 인/아웃, 커서 배치, 시간 측정, 2진수/16진수 표시 전환. "파형 뷰어는 하드웨어 설계자의 디버거(debugger)이다"라는 인식을 심어주면, 이후 파형 분석 과제에 대한 거부감이 줄어듭니다. VCS/Verdi를 시연할 수 없는 환경이라면, Vivado Simulator의 파형 뷰어로 동일한 내용을 다룰 수 있습니다.

### 1.6절 — 본 챕터 요약 및 다음 단계

> **강사 꿀팁**: 챕터 마무리 시 **자가 점검 질문 3개**를 제시하고, 수강생이 스스로 답할 수 있는지 확인시키십시오. 답하지 못하는 질문이 있으면 해당 절을 다시 읽도록 유도합니다. 추천 자가 점검 질문: (1) "`always_ff`와 `always_comb`의 핵심 차이 두 가지를 설명하시오" (2) "XDC 파일의 역할을 한 문장으로 설명하시오" (3) "LED 1초 간격 점멸을 위한 카운터 비트 수를 계산하시오". 이 세 질문에 답할 수 있으면 Ch02로 진행할 준비가 된 것입니다.

## 6. 추가 제안 사항

### 6.1 1.1절 전체 조감도 SVG 설계 방향

전체 프로세서 블록 다이어그램을 보여줄 때, 다음 전략을 권고합니다:

| 전략 | 설명 |
|------|------|
| **Gradual Reveal 예고** | 1.1절에서는 전체를 회색(greyed-out)으로 보여주고, 현재 챕터(Ch01)에서 다루는 부분만 컬러로 표시. 이후 챕터에서 해당 영역이 컬러로 "점등"되는 방식 |
| **숫자 라벨링** | 각 블록에 챕터 번호를 작게 표시 (예: ALU 블록에 "Ch04", 캐시에 "Ch13") |
| **복잡도 경고 없음** | "복잡해 보이지만 걱정하지 마십시오" 대신 "이것이 20주 후에 당신이 만들 프로세서입니다"로 호기심을 자극 |

### 6.2 1.3절 Verilog → SystemVerilog 전환 비교표

1.3절에 다음과 같은 비교표를 배치하면 Verilog 경험자의 전환이 매우 수월해집니다:

| Verilog (기존) | SystemVerilog (이 교재) | 변경 이유 |
|---------------|----------------------|----------|
| `reg` / `wire` | `logic` | 문맥에 따라 도구가 자동 추론 |
| `always @(posedge clk)` | `always_ff @(posedge clk)` | 순차 로직 의도를 도구에 명시 |
| `always @(*)` | `always_comb` | 조합 로직 의도를 도구에 명시 + 래치 경고 |
| `integer` | `int` | 32비트 정수, 4-state → 2-state |
| `parameter` | `parameter` / `localparam` | 동일하나, `localparam`으로 로컬 상수 명시 권장 |
| (없음) | `enum` | FSM 상태 정의에 활용 (Ch08) |
| (없음) | `struct` / `typedef` | 파이프라인 레지스터 그룹핑 (Ch09) |
| `$display` | `$display` + `assert` | 자동 검증용 `assert` 추가 (Ch04~) |

### 6.3 시뮬레이션 파라미터 분리 패턴 (1.5절)

LED 점멸 예제에서 시뮬레이션 시간을 줄이기 위해, 다음과 같은 **시뮬레이션 파라미터 분리 패턴**을 1.5절에서 소개하면 이후 모든 챕터에서 활용할 수 있습니다:

```systemverilog
module led_blinker #(
   parameter CLK_FREQ = 100_000_000  // 합성 시 100MHz
)(
   input  logic clk,
   input  logic rst_n,
   output logic led
);
   // ...
endmodule
```

테스트벤치에서:
```systemverilog
led_blinker #(.CLK_FREQ(100)) u_dut (  // 시뮬레이션 시 100으로 축소
   .clk(clk), .rst_n(rst_n), .led(led)
);
```

이 패턴을 "시뮬레이션 가속 기법"으로 소개하면, 수강생이 이후 캐시, 타이머 등 긴 시뮬레이션이 필요한 모듈에서도 자연스럽게 적용할 수 있습니다.
