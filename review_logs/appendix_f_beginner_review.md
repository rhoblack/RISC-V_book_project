## F.2: HTIF 프로토콜 이해

### 이해도 평가
**평가**: ⭐⭐⭐⭐⭐ (매우 명확, 3단계 가이드가 핵심)

### 명확한 부분

1. **HTIF가 무엇인가? (왜 필요한가?)**
   - 문제 정의: Spike(C++)와 설계(SystemVerilog) 간 결과 비교 방법
   - 해결책: tohost에 결과를 쓰고 호스트가 읽는 방식
   - 매우 논리적인 도입부

2. **tohost/fromhost의 역할 (Table)**
   - 주소: 0x80001000 (tohost), 0x80001008 (fromhost)
   - 용도와 읽기/쓰기 방향이 명시됨
   - 표 형식이 직관적

3. **tohost 값의 의미 (Table)**
   - 0x00000001 = 성공 ✅
   - 0x0000_0000 = 진행 중 ⏳
   - 0xNNNN_0000 = 실패 (NNNN은 오류 코드) ❌
   - 예시: 0x00030000 → 오류 코드 0x0003
   - 이 부분이 **가장 중요한 개념**이며 명확함

4. **3단계 디버깅 가이드 (Step A, B, C) — 가장 강력한 섹션**

   **Step A: 마지막 명령어 찾기**
   - HTIF 로그 예시 제공 (BEQ 명령어)
   - 각 로그 라인의 의미 분해:
     - [0020]: 사이클 번호
     - RI: Retired Instruction
     - 80000010: PC
     - 00008263: 기계어
     - BEQ x1,x0,8: 어셈블리
   - 이 부분이 **너무 좋음** — 실제 로그를 읽을 수 있게 됨

   **Step B: 입력값과 조건 확인**
   - 로그에서 x1=0, x0=0 추출
   - BEQ 조건 판정: x1==x0? YES → 분기 발동해야 함
   - 하지만 PC 진행이 PC+4가 아니라 PC+8이어야 하는데...
   - 결론: BEQ 분기 로직이 틀렸다!
   - **매우 구체적이고 추적 가능한 논리**

   **Step C: 파형 확인**
   - 추적할 신호 목록: clk, rst_n, PC, instruction, rs1_data, rs2_data, branch_result, branch_taken, PC_next
   - branch_result 신호 확인 → ALU 오류 추적
   - branch_result는 1이지만 PC_next가 0x80000014라면 → PC MUX 오류
   - **chapter 참조 가능** (Ch04, Ch11)

5. **SVG (app_f_htif_protocol.svg)**
   - 메모리 맵 명확 (0x80000000 프로그램, 0x80001000 tohost, 0x80001008 fromhost)
   - 타겟-호스트 통신 흐름도 명확
   - tohost 값 예시 (0x00000001, 0x00030000, 0x00000000) 시각화
   - ✅ **매우 유용**

## F.4: 테스트 실패 원인 분석

### 이해도 평가
**평가**: ⭐⭐⭐⭐⭐ (매우 명확, 2가지 실제 사례 제공)

### 명확한 부분

1. **실패의 종류: 3가지 분류**
   | 종류 | 예시 | 대응 |
   |------|------|------|
   | 설계 미지원 | M 확장(mul) 미구현 | 🟢 정상, 제외 |
   | 논리 오류 | add 명령 결과 틀림 | 🔴 버그 수정 필수 |
   | 환경 오류 | tohost 쓰기 실패 | 🟡 환경 재검토 |
   - 표가 명확하고 색상 코딩이 우선순위를 직관적으로 전달

2. **실패 분류 의사결정 트리 (SVG app_f_debug_flow.svg)**
   - 플로우차트로 시각화 → 의사결정 과정이 단계적임

3. **Case 1: EX-EX 포워딩 미작동**
   ```systemverilog
   add x1, x0, x0     // x1 = 0
   addi x1, x1, 5     // x1 = x1 + 5 = 5 (포워딩 필요!)
   // 예상: x1 = 5 ✅
   // 결과: x1 = 0 ❌
   ```
   - **매우 구체적인 예제**

   **Step A: forward_a, forward_b 신호 확인**
   - forward_a == 2'b01일 때만 포워딩 동작
   - rs1_forwarded = EX_MEM_alu_result vs rs1_data
   - 파형에서 어떤 값이 선택되는지 확인

   **Step B: forward_a 조건 확인**
   - EX_MEM_rd == ID_EX_rs1 (쓰기 대상 == 읽기 소스?)
   - EX_MEM_reg_we == 1'b1 (레지스터에 쓰는가?)
   - EX_MEM_rd != 5'b0 (x0 제외)
   - **3가지 조건 체크리스트**

   **Step C: 수정**
   - CLAUDE.md의 포워딩 우선순위 참조 (EX-EX > MEM-EX > WB-ID)
   - 또는 rs1_mux가 잘못되었을 가능성
   - **여러 가능성을 제시함**

4. **Case 2: Load-Use 스톨 미작동**
   ```systemverilog
   lw x1, 0(x2)      // x1 = M[x2] (지연!)
   addi x3, x1, 5    // x3 = x1 + 5 (x1 준비 안 됨!)
   ```
   - **실제 파이프라인 해저드**

   **Step A: load_use_hazard 신호 확인**
   - ID_EX_mem_read == 1'b1 (현재가 로드?)
   - (ID_EX_rd == IF_ID_rs1) || (ID_EX_rd == IF_ID_rs2) (다음이 그걸 읽으려고?)
   - stall_en 신호 확인

   **Step B: 스톨 신호 적용 확인**
   - PC_next = stall_en ? PC : PC + 4
   - IF_ID_en = !stall_en
   - **파형에서 확인할 수 있는 관찰 포인트**

   **Step C: 우선순위 확인**
   - flush > icache_stall > load_use_stall
   - CLAUDE.md 참조 (이전 장과 연결!)
   - assign stall_en = load_use_hazard && !flush_en

5. **실전 디버깅 흐름도 (SVG app_f_test_flow.svg)**
   - 테스트 실패 → 로그 분석 → 신호 추적 → 버그 특정
   - 시각적 흐름도

없음 — 2가지 실제 사례가 매우 구체적
