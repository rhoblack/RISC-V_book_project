### 섹션별 학습 목표 일관성

**19.1 파이프라인 구조 핵심 복습**
- 명시적 목표 없음 → 도입 수준 (Remember: 파이프라인 5단계, 스톨/플러시 신호 기억)
- ✓ 적절 (새로운 내용 없음 명시)

**19.2 동기 예외 처리**
- 명시적 목표: L2(Understand) + L1 부분적
- 커버 범위: ID/EX/MEM 스테이지 예외 감지 로직 (코드 3개)
- ✓ 우수 (개념 정의 + 코드 예시)

**19.3 비동기 인터럽트 처리**
- 명시적 목표: L3(Analyze), L1 부분적
- 커버 범위: 3단 마스킹 구조 (사진 + 코드 2개 + 테이블)
- ✓ 우수 (대수식 논리 + 하드웨어 수식)

**19.4 트랩 진입/복귀 메커니즘**
- 명시적 목표: L4(Apply)
- 커버 범위: FSM 상태 정의 (5단계) + CSR 업데이트 시퀀스 (의사코드)
- ✓ 우수 (상태 전이도 + 의사코드)

**19.5 파이프라인과 예외 처리 통합**
- 명시적 목표: L5(Evaluate), L3(Analyze)
- 커버 범위: 정확한 예외 메커니즘 + 우선순위 근거 + CSR 해저드 처리
- ✓ 우수 (타이밍 다이어그램 + 파이프라인 스냅샷 분석)

**19.6 예외/인터럽트 테스트벤치**
- 명시적 목표: L6(Apply)
- 커버 범위: 시나리오 1(ECALL), 시나리오 4(Timer), Assertion 사용법
- ✓ 양호 (실제 코드 예시 있음, 하지만 assertion 상세도 낮음)

**19.7 요약 및 다음 단계**
- 명시적 목표: L5(Evaluate) — 성능 측정
- 커버 범위: 인터럽트 지연시간 + 처리량 계산
- ✓ 우수 (정량적 메트릭)

### 상세 평가

#### Q1: mcause 값 식별 [Remember L1]
```
문제: mcause = 2, 4, 0x8000_0007, 11 → 예외/인터럽트 종류 & 발생 스테이지

기대 답안:
- mcause = 2: Illegal Instruction, ID (19.2 표에 정의)
- mcause = 4: Load Address Misaligned, MEM (19.2 표에 정의)
- mcause = 0x8000_0007: Timer Interrupt (bit31=1), 파이프라인 내부 (19.3 표)
- mcause = 11: ECALL, ID (19.2 표에 정의)

평가:
- ✅ 단순 암기형 (Remember)
- ✅ 과제에서 배운 표를 직접 참조 가능
- ✅ 난이도 적절 (차별화 불필요)
```

#### Q2: 인터럽트 수용 조건 판단 [Understand L2]
```
문제: mstatus.MIE=1, mie.MTIE=1 상태 → timer_irq=1 들어왔을 때:
(a) 인터럽트 수용? (b) mip.MTIP 값? (c) 핸들러 진입 후 mstatus.MIE?

기대 답안:
(a) 수용 (mstatus.MIE=1 AND mie.MTIE=1 AND timer_irq=1)
(b) mip.MTIP=1 (하드웨어 직결, 인터럽트 pending)
(c) mstatus.MIE=0 (trap 진입 시 Trap 설명 참고 → 강제 비활성화)

평가:
- ✅ 이해도 필요 (3단 마스킹 구조 이해)
- ✅ 실제 설계 현황 반영 (mip.MTIP 하드웨어 직결 — Ch18 설명)
- ✅ Ch18-19 통합 이해
- ⚠️ 약점: 정확한 지점 모호 (문제에 "언제"가 없음 → 핸들러 진입 "직전/직후"?)
  - 권장: "(c) 핸들러 진입 직후" 명확화
```

#### Q3: 우선순위 순서 변경 시 파이프라인 분석 [Apply L3]
```
문제: EX > MEM으로 우선순위 역순 설정 → 문제점 + 정확한 예외 위반 설명

기대 답안:
- 문제: MEM 스테이지의 명령어 A(Load Misaligned)와
        EX 스테이지의 명령어 B(동시 예외)가 발생했을 때,
        EX 예외 우선 처리 → A 명령어는 완료되지 않음
- 정확한 예외 위반: "이전 명령어는 완료, 이후만 취소" 위반
  (A는 "나중에" 도착했으므로 취소되어야 하는데 우선순위 상 역전)

평가:
- ✅ 파이프라인 순서의 중요성 이해 필요 (Apply)
- ✅ 타이밍 다이어그램 필요 (19.5 SVG 참조)
- ✅ 정확한 예외 정의 이해 (19.5 전반부)
- 난이도: 중상 (파이프라인 순서 추적 필요)
```

#### Q4: FSM 상태 중 인터럽트 무시 분석 [Analyze L4]
```
문제: trap_taken && state == S_IDLE 조건에서 S_TRAP_MEPC 상태 중
       새 타이머 인터럽트 무시 이유

기대 답안:
- FSM 상태: S_IDLE → S_TRAP_MEPC → S_TRAP_MCAUSE → S_TRAP_MTVEC → S_DONE
- S_TRAP_MEPC 중 trap_taken 신호 발생 → state != S_IDLE 이므로 조건 거짓
- 결과: 새 인터럽트는 수용되지 않음 (비동기 인터럽트가 동기화됨)
- 근거: FSM이 "atomicity 보장" (Trap 진입 시퀀스 중단 불가)

평가:
- ✅ FSM 상태 분석 (19.4 표 참조)
- ✅ 논리 추적 능력 필요 (Analyze)
- ⚠️ 문제점: 원고에 FSM 조건이 명확히 쓰여 있지 않음 ("19_trap_controller.sv" 참조 필요)
  - 권장: 19.4절 또는 연습문제에서 trap_taken && state == S_IDLE 명시
```

#### Q5: 인터럽트 지연시간 vs 핸들러 첫 명령어 평가 [Evaluate L5]
```
문제: 시나리오 4의 타이머 인터럽트 응답 시간 측정 →
      핸들러 첫 명령어 실행까지 전체 지연 시간 비교 →
      100MHz에서 나노초 계산 →
      실시간 응용(10ms 주기) 적합성 평가

기대 답안:
- 응답 시간: 0~1 클럭 (인터럽트 신호 감지 후 다음 클럭에 mip.MTIP 세트)
- Trap 진입: 5사이클 (S_IDLE→MEPC→MCAUSE→MTVEC→DONE)
- 파이프라인 플러시: 최악 5사이클 (모든 스테이지 플러시)
- 핸들러 첫 명령어 실행: ~10~12사이클
- 100MHz: 10ns/사이클 → 100~120ns
- 10ms 주기와 비교: 100ns << 10ms → 충분함 (수천 배 여유)

평가:
- ✅ 정량적 평가 (Evaluate)
- ✅ 실무 사고방식 (성능 기준)
- ✅ 19.7 성능 분석과 연결
- ⚠️ 약점: 문제가 "exception_tb.sv 시나리오 4" 참조 요구
  - 원고에 시나리오 4 상세 설명 필요 (현재 존재하지 않을 수 있음)
  - 권장: 19.6절 테스트벤치에 시나리오 4 명시적 정의
```

### 연습문제 총평

| 항목 | 평가 | 비고 |
|------|------|------|
| 블룸 분포 | ✅ 5수준 균형 | Remember~Evaluate |
| 개수 | ✅ 5개 적절 | 과제 기반 |
| 난이도 | ✅ L1→L5 상승 | 점진적 심화 |
| 원고와 연계 | ✓ 대부분 명확 | Q4/Q5는 참조 필수 |

**개선 권장사항**:
1. **Q2 명확화**: "(c) 핸들러 진입 직후" 명시
2. **Q4 참조**: 19.4절에 `trap_taken && state == S_IDLE` 조건 명시
3. **Q5 보강**: 19.6절 "시나리오 4" 타이머 인터럽트 상세 정의 추가

### ⭐ 우선순위 2: 19.5절 메모리 스택 시각화 강화 (중첩 인터럽트)

- 현재: 타임라인(ch19_sec05_nested_timeline.svg)만 있음

**개선안**:
```
추가 1: 메모리 스택 다이어그램 (주소 라벨 포함)
$sp=0x0000_0100에서 시작:

[초기]
  0x0000_0100 │  empty

[첫 ECALL 진입]
  0x0000_00FC │  mepc[0] (PC of 1st instr)
  0x0000_0100 │  empty
  sp = 0x0000_00FC

[두 번째 TIMER IRQ 진입]
  0x0000_00F8 │  mepc[1] (PC of ECALL handler 재개 PC)
  0x0000_00FC │  mepc[0]
  0x0000_0100 │  empty
  sp = 0x0000_00F8

[MRET 1회 (TIMER 핸들러 복귀)]
  0x0000_00FC │  mepc[0]
  0x0000_0100 │  empty
  sp = 0x0000_00FC

[MRET 2회 (ECALL 핸들러 복귀)]
  0x0000_0100 │  empty
  sp = 0x0000_0100
```

- 타임라인에 mstatus 변화도 명시 (MIE 값의 시간적 변화)

추가 3: 연습문제 추가

```

**근거**:

### ⭐ 우선순위 3: 19.6절 테스트벤치 "시나리오 4" 명시적 정의

**문제**:
- 현재: "시나리오 1(ECALL)" 상세, "시나리오 4(Timer)" 참조만 언급
- 연습문제 Q5가 "시나리오 4" 참조하나 원고에 정의 불명확

**개선안**:
```
추가 1: 19.6절에 "시나리오 4: 타이머 인터럽트 응답 시간 측정" 섹션 명시

시나리오 4 플로우:
1. 초기: CPU 실행 (인터럽트 활성화)
2. 타이머가 도달 → timer_irq=1 (clock 0)
3. Trap 진입 FSM 시작 (clock 1~5)
4. 핸들러 주소 미결정 시 NOP 버블링 (clock 5~7)
5. 핸들러 첫 CSRRS 명령어 IF (clock 8)
6. 핸들러 첫 CSRRS 명령어 WB (clock 12)

응답 시간 = clock 12 - clock 0 = 12 사이클

추가 2: SystemVerilog Assertion으로 응답 시간 자동 검증
// 예:
property timer_irq_response_time;
  @(posedge clk)
    timer_irq |=> ##[0:20] (state == S_DONE && handler_instr_commits);
endproperty
assert property (timer_irq_response_time)
  else $display("Timer IRQ latency exceeded 20 cycles");

추가 3: 테스트벤치에서 실제 응답 시간 측정 코드
always @(posedge clk) begin
  if (timer_irq_event) latency_start <= $time;
  if (handler_instr_commits) latency_end <= $time;
end
```

**근거**:
- 연습문제 Q5가 "시나리오 4" 상정
- L6 목표 "Assertion 사용"과 연계
- 19.7 성능 분석 (실제 측정값 필요)

**위치**: 19.6절 "예외/인터럽트 테스트벤치" (시나리오 1 다음)
