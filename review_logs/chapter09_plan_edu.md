## 서문: Ch09의 교육적 위치

Ch09는 이 교재에서 가장 중요한 전환점이다. Part 3(Ch07~08)에서 완성한 멀티사이클 FSM CPU는 뛰어난 교육 도구였지만, CPI > 1이라는 구조적 한계를 갖는다. Ch09는 독자가 그 한계를 직접 인식하고, "FSM의 각 상태를 동시에 실행하면 어떨까?"라는 직관적 질문에서 출발하여 파이프라인이라는 강력한 아이디어로 도달하는 여정을 설계한다.

이 챕터가 갖는 이중 역할을 명확히 인식해야 한다.

**첫째, Part 4의 진입 챕터이자 개념적 토대다.**
Ch10(데이터 해저드와 포워딩)은 이 교재에서 가장 난이도가 높은 챕터다. Ch09가 파이프라인 구조와 타이밍 다이어그램 읽기를 확실히 정착시켜야만 Ch10에서 해저드 분석이 가능하다. Ch09의 개념적 토대가 흔들리면 Ch10은 커녕 파이프라인 전체가 붕괴한다.

**둘째, Ch08 FSM 학습의 자연스러운 연장이다.**
FSM의 17개 상태는 결국 IF/ID/EX/MEM/WB의 5단계로 수렴된다. 독자는 이미 각 단계가 하는 일을 알고 있다. Ch09는 "알고 있는 것을 동시에 실행한다"는 아이디어만 추가한다. 이 연결이 학습 불안을 최소화하는 핵심 장치다.

> **감정 설계 원칙**: Ch08에서 멀티사이클 CPU 완성의 성취감을 얻은 독자는 "더 빠른 CPU"에 대한 자연스러운 욕구를 갖는다. Ch09는 그 욕구에 정확히 응답하며 시작해야 한다. 파이프라인 레지스터 설계(9.4절)가 기술적으로 단순하지 않으므로, 9.5절에서 NOP 삽입 방식으로 실제 동작을 확인하는 소규모 성취감을 반드시 배치한다.

### 9.1절 학습 흐름 — 멀티사이클에서 파이프라인으로 (핵심 도약)

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | Ch08의 FSM 상태 전이도와 CPI 결과를 직접 인용 | "Ch08에서 완성한 멀티사이클 CPU는 한 순간에 하나의 명령어만 처리합니다. ADD를 실행하는 동안 IF 단계의 하드웨어는 유휴 상태입니다." — 자원 낭비 문제 인식 유도 |
| **개념** | FSM 상태 순차 실행 → 병렬 실행으로의 전환 아이디어 제시 | "IF 단계가 2번째 명령어를 인출하는 동안, EX 단계가 1번째 명령어를 연산한다면?" — 직관적 도약. "이것이 파이프라인의 핵심 아이디어입니다"로 명시 |
| **예시** | 세탁기 비유 → 공장 조립 라인 → 파이프라인 SVG 비교 | 세탁(인출) → 건조(디코딩) → 다림질(실행) 비유. 한계 명시: "세탁물은 순서를 의식하지 않지만, 명령어는 앞 명령어의 결과에 의존할 수 있습니다 — 이것이 해저드입니다" (Ch10 복선) |
| **실습** | 멀티사이클 FSM 상태도와 파이프라인 타이밍 다이어그램 나란히 비교 | SVG: 왼쪽에 FSM 상태 순차도, 오른쪽에 같은 명령어 3개의 파이프라인 타이밍 다이어그램. 독자가 "FSM의 각 사이클 = 파이프라인의 각 칸"임을 직관적으로 확인 |
| **정리** | tip aside: "FSM 상태 1:1 대응 표" | Ch08 FSM 상태 → 파이프라인 스테이지 1:1 대응 표. "S0_IF → IF 스테이지, S1_ID → ID 스테이지..." 형태로 명시하여 선행 지식 활성화 |

> **인지 부하**: 새 개념 2개 (파이프라인 병렬 실행 아이디어, FSM 상태 → 스테이지 전환 관점). 안전 구간.
> **핵심 전략**: 9.1절은 새로운 기술 내용을 최소화하고 "관점의 전환"에 집중한다. 독자가 "나는 이미 각 단계를 알고 있었다. 동시에 돌리는 것이 파이프라인이구나"라는 인식 전환을 경험해야 한다.

### 9.2절 학습 흐름 — 파이프라인 개념과 성능 분석

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "파이프라인이 정말 빠른가?"라는 직접적 질문 | "직관적으로는 5배 빠를 것 같습니다. 실제로 그럴까요? 숫자로 검증해봅시다." — 분석 동기 유발 |
| **개념** | 처리량(throughput) vs 지연(latency) 정의 → CPI=1의 이상적 조건 | 두 지표의 정의와 단위 명시. "파이프라인은 처리량을 늘리지만 단일 명령어의 지연은 멀티사이클보다 길 수 있습니다." 이 역설적 사실을 강조 |
| **예시** | 5단계 파이프라인 타이밍 다이어그램 점진적 읽기 가이드 | ① 가로축/세로축 레이블 설명 → ② 1번 명령어의 경로 추적 → ③ 5번째 사이클에 5개 명령어가 모두 실행 중임 확인 → ④ Steady-state CPI=1 계산 |
| **실습** | 7개 명령어 시퀀스의 타이밍 다이어그램 빈칸 완성 | 첫 4개 명령어의 스테이지가 표시된 상태에서 5~7번 명령어의 스테이지 칸을 채우는 빈칸 완성 |
| **정리** | 성능 공식 유도: `T_exec = N × CPI × T_clk` → 파이프라인에서의 변화 | 멀티사이클: CPI≈4, Fmax≈50MHz → 파이프라인: CPI≈1, Fmax≈100MHz(이상). "이론적으로 4×2=8배 향상 가능" 계산. faq aside: "그럼 실제로 8배 빠른가요?" |

> **인지 부하**: 새 개념 3개 (처리량 vs 지연 구분, 타이밍 다이어그램 읽기, CPI=1 이상적 조건과 실제 차이). 황색 경계.
> **완화 전략**: 타이밍 다이어그램 읽기는 9.2절의 가장 중요한 기능적 목표다. "다이어그램 읽기 가이드"를 4단계 점진적 공개로 설계하여 부하를 분산한다. 처리량/지연 개념은 타이밍 다이어그램 이해 후 자연스럽게 연결한다.
> **주의**: 타이밍 다이어그램 읽기 능력이 정착되지 않으면 Ch10(해저드 분석)에서 치명적 어려움이 발생한다. 이 절에서 충분한 시간을 투자하는 것이 Ch10 학습의 전제 조건이다.

### 9.3절 학습 흐름 — 5단계 스테이지 정의

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | Ch08 FSM 상태표를 5개 그룹으로 묶는 시각화 | "Ch08의 17개 상태는 결국 5개 단계의 반복입니다." — FSM 상태를 IF/ID/EX/MEM/WB 그룹으로 색상 구분한 SVG 제시 |
| **개념** | 각 스테이지별 담당 작업과 사용 자원 정의 | IF: PC 읽기+명령어 인출+PC+4 계산 / ID: 명령어 디코딩+레지스터 읽기+즉치수 생성 / EX: ALU 연산+분기 조건 판단 / MEM: 메모리 읽기/쓰기 / WB: 레지스터 파일 쓰기 |
| **예시** | 스테이지별 사용 모듈 목록 (Ch04~05에서 구현한 모듈과 연결) | "IF 스테이지 = IMEM + PC 레지스터, ID 스테이지 = 레지스터 파일 + 즉치수 생성기 + 디코더, EX 스테이지 = ALU" — 선행 지식 활성화 |
| **실습** | 각 명령어 타입(R/I/S/B/U/J)이 각 스테이지에서 하는 일 표 완성 | 6×5 표에서 일부 칸을 비워두고 독자가 직접 완성. "SW는 WB 스테이지에서 무엇을 하는가?"(아무것도 하지 않음) 확인 |
| **정리** | metacognition aside: "5단계의 순서가 왜 IF→ID→EX→MEM→WB인가?" | 데이터 흐름의 인과적 순서(명령어를 알아야 디코딩 가능, 레지스터 값을 알아야 연산 가능...)를 스스로 설명해보는 성찰 |

> **인지 부하**: 새 개념 1개 (5개 스테이지의 공식적 정의와 담당 자원). 녹색 안전.
> Ch08 FSM 상태에 대한 깊은 이해가 있는 독자에게 9.3절은 "이미 아는 것을 재정리"하는 수준이다. 인지 부하보다 정확한 정리와 용어 통일에 집중한다.

### 9.4절 학습 흐름 — 파이프라인 레지스터 설계

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "스테이지 사이에 정보를 전달하는 방법은?" | "EX 스테이지가 ALU 결과를 WB 스테이지에 전달하려면 어디에 저장해야 할까요?" — 파이프라인 레지스터의 필요성을 독자 스스로 발견하도록 유도 |
| **개념** | 4개 파이프라인 레지스터의 역할 및 저장 내용 정의 | IF/ID: PC, 명령어(IR) / ID/EX: 레지스터 값(A,B), 즉치수, PC, rd 주소, 제어 신호 / EX/MEM: ALU 결과, B(스토어용), rd 주소, 제어 신호 / MEM/WB: 메모리 데이터, ALU 결과, rd 주소, 제어 신호 |
| **예시** | 파이프라인 레지스터 SystemVerilog 선언 코드 점진적 공개 | IF/ID 레지스터 완성 코드 제시 → ID/EX 레지스터 코드 제시 → 독자가 패턴을 파악. "각 레지스터는 해당 스테이지 완료 시점의 스냅샷(snapshot)입니다" 비유 사용 |
| **실습** | EX/MEM 레지스터의 포트 목록 빈칸 완성 | 포트 이름과 비트 폭을 일부 비워두고 독자가 완성. "EX/MEM에 ALU 결과(32비트)와 함께 rd 주소(5비트)가 필요한 이유는?" FAQ 박스 |
| **정리** | Ch08 old_pc_reg → 파이프라인 레지스터 연결 tip aside | "Ch08에서 추가했던 old_pc_reg은 사실상 IF/ID 파이프라인 레지스터의 PC 필드와 같은 역할입니다." — 선행 설계 결정과의 연속성 강조 |

> **인지 부하**: 새 개념 2개 (파이프라인 레지스터 개념과 역할, 각 레지스터가 전달해야 하는 신호 목록). 안전 구간.
> **주의**: 파이프라인 레지스터 설계에서 가장 흔한 오류는 WB 스테이지에서 필요한 정보(rd 주소, 제어 신호)를 EX/MEM까지 전달하지 않는 것이다. "rd 주소는 파이프라인 레지스터를 통해 끝까지 전달되어야 한다"는 규칙을 faq 박스로 강조한다.

### 9.5절 학습 흐름 — 해저드 없는 기본 파이프라인

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "먼저 동작하게 만들고, 나중에 최적화한다" 원칙 제시 | "해저드 해결은 Ch10에서 다룹니다. 이 절에서는 NOP을 삽입하여 의존성이 없는 상태를 만들고, 파이프라인이 실제로 동작하는 것을 먼저 확인합니다." |
| **개념** | NOP 명령어의 정의 및 삽입 전략 | NOP = `ADDI x0, x0, 0` (0x00000013). 데이터 의존 명령어 사이에 충분한 수(최대 3개)의 NOP을 삽입하면 해저드 없이 동작. "이것은 해결책이 아니라 동작 확인을 위한 임시 방편입니다" 명시 |
| **예시** | NOP 삽입 전후 타이밍 다이어그램 비교 | ADD x1, x2, x3 → NOP×3 → AND x4, x1, x5 시퀀스의 타이밍 다이어그램. "NOP 3개 = 3사이클 지연 = 파이프라인 스톨의 수동 버전" 연결 |
| **실습** | 기본 파이프라인 시뮬레이션 실행 | 제공된 NOP 삽입 어셈블리 프로그램(5~7 명령어)을 시뮬레이션. 파형에서 5개 스테이지가 동시에 활성화된 사이클을 찾아 표시 |
| **정리** | 마일스톤 축하 + Ch10 예고 | "5단계 파이프라인이 처음으로 동작했습니다!" 성취 선언. 이어서: "NOP 3개를 삽입하면 성능이 단일 사이클보다도 나빠질 수 있습니다. Ch10에서 NOP 없이 해저드를 해결하는 포워딩을 다룹니다." |

> **인지 부하**: 새 개념 2개 (NOP 삽입 방식, 기본 파이프라인 시뮬레이션 검증). 안전 구간.
> **핵심 설계 의도**: 9.5절의 목표는 완성도 높은 파이프라인이 아니라 **동작하는 파이프라인**이다. 독자는 "내가 만든 파이프라인이 돌아간다"는 성취감을 이 절에서 반드시 경험해야 한다. 이 성취감이 Ch10의 높은 난이도를 견디는 심리적 자원이 된다.

## 멀티사이클 → 파이프라인 전환 설명 전략 (9.1절 핵심 도약)

### 전환의 핵심 장벽

독자가 파이프라인으로 전환할 때 경험하는 핵심 장벽은 두 가지다:

1. **개념적 장벽**: "같은 하드웨어에서 여러 명령어가 동시에 실행된다는 것이 어떻게 가능한가?"
2. **기술적 장벽**: "스테이지 사이에 상태를 어떻게 유지하는가?"

9.1절에서는 개념적 장벽만 다룬다. 기술적 장벽은 9.4절(파이프라인 레지스터)에서 해결한다.

### 전환 설명의 3단계 전략

**1단계 — FSM 상태의 재해석 (관점 전환)**

Ch08 FSM에서 독자는 CPU가 매 사이클마다 하나의 상태에 있다고 배웠다. 이 관점을 전환하는 핵심 질문을 제시한다:

> "FSM이 S0_IF에서 명령어를 인출하는 동안, S2_EX 회로는 무엇을 하고 있는가?"

정답은 "아무것도 하지 않는다"이다. 이 유휴 자원의 존재를 독자가 인식하는 것이 전환의 출발점이다.

**2단계 — 비유 도입 (직관 형성)**

공장 조립 라인 비유 사용:

> "자동차 공장에서 도장(EX) 부서가 A차를 칠하는 동안, 조립(ID) 부서는 B차를 조립하고, 설계(IF) 부서는 C차의 도면을 가져옵니다. 각 부서는 서로 다른 차를 동시에 처리합니다."

한계 명시 필수: "공장에서는 각 차가 독립적이지만, 명령어는 앞 명령어의 결과에 의존할 수 있습니다. 이것이 파이프라인의 핵심 과제인 해저드(hazard, 위험 요인)입니다."

**3단계 — FSM 상태도 → 파이프라인 타이밍 다이어그램 직접 변환**

Ch08 FSM 상태도(순차)와 파이프라인 타이밍 다이어그램(병렬)을 나란히 배치한 SVG를 사용한다:

- 왼쪽: 명령어 3개가 FSM을 순차적으로 통과하는 타임라인 (Ch08 방식)
- 오른쪽: 같은 명령어 3개가 파이프라인을 병렬로 통과하는 타이밍 다이어그램 (Ch09 방식)

독자가 "왼쪽의 각 사이클 = 오른쪽의 각 칸"임을 직접 대응할 수 있도록 색상 코딩을 일치시킨다.

### FSM 상태 → 파이프라인 스테이지 1:1 대응표

| Ch08 FSM 상태 | 파이프라인 스테이지 | 주요 담당 작업 |
|:------------:|:----------------:|-------------|
| S0_IF | IF (Instruction Fetch) | 명령어 인출, PC+4 계산 |
| S1_ID | ID (Instruction Decode) | 디코딩, 레지스터 읽기, 즉치수 생성 |
| S2_EX_R / S3_EX_MEM / S4_EX_BR | EX (Execute) | ALU 연산, 분기 조건 판단 |
| S5_MEM_READ / S6_MEM_WRITE | MEM (Memory Access) | 데이터 메모리 읽기/쓰기 |
| S7_WB_R / S8_WB_LOAD 등 | WB (Write Back) | 레지스터 파일에 결과 쓰기 |

> **tip aside**: "표에서 EX와 WB 스테이지에 여러 FSM 상태가 대응됩니다. 파이프라인에서는 이 분기를 제어 신호(MUX 선택값)로 처리합니다. 하드웨어는 동일하고 제어만 달라집니다."

> **문제 3 — 처리량과 지연의 역설**
>
> 5단계 파이프라인 프로세서에서 단일 명령어(ADD 1개)의 실행 시간(지연, latency)은 파이프라인이 없는 경우보다 길 수 있다. 이 역설적 사실이 발생하는 이유를 설명하고, 그럼에도 파이프라인이 유리한 이유(처리량 관점)를 설명하시오.
>
> *기대 답변*: 파이프라인 레지스터 오버헤드로 인해 각 스테이지의 클럭 주기가 최장 스테이지에 맞춰지며, 5스테이지를 거치므로 단일 명령어 지연 = 5×T_clk이 된다. 단일 사이클(1×T_critical)보다 클 수 있다. 그러나 Steady-state에서 매 사이클마다 하나의 명령어가 완료(CPI=1)되므로 전체 처리량은 크게 향상된다.
>
> *채점 기준*: "지연 vs 처리량" 구분이 명확히 설명되면 정답.

> (나) I1(ADD)가 완료되는 사이클은 몇 번인가?
>
> (다) 이 다이어그램에서 해저드가 발생할 가능성이 있는 명령어 쌍은 어느 것인가? (단, 데이터 의존성이 있다고 가정)
>
> *기대 답변*:
> - (가) I1:EX, I2:ID, I3:IF
> - (나) 사이클 5 (WB 완료)
> - (다) I1→I2: I1의 결과가 필요한 경우 I2(LW)의 ID에서 아직 I1의 WB가 완료되지 않을 수 있음. I2→I3: LW의 MEM 결과가 필요한 경우 추가 해저드 가능.
>
> *채점 기준*: (가)(나) 정답 + (다)에서 적어도 1개 의존 관계 식별 시 만점.

### [적용 — Apply: 코드와 다이어그램을 작성할 수 있다]

> **문제 5 — IF/ID 파이프라인 레지스터 SystemVerilog 구현**
>
> 다음 조건을 만족하는 IF/ID 파이프라인 레지스터를 SystemVerilog `always_ff` 블록으로 구현하시오.
>
> - 저장 신호: `pc_plus4` (32비트), `instruction` (32비트)
> - 동기 리셋(동기 active-high reset): 리셋 시 모든 필드 0으로 초기화
> - 클럭 rising edge에 갱신
> - 레지스터 이름 접두사: `if_id_`
>
> *기대 답변*:
> ```systemverilog
> always_ff @(posedge clk) begin
>     if (reset) begin
>         if_id_pc_plus4    <= 32'b0;
>         if_id_instruction <= 32'b0;
>     end else begin
>         if_id_pc_plus4    <= pc_plus4;
>         if_id_instruction <= instruction;
>     end
> end
> ```
>
> *채점 기준*: `always_ff @(posedge clk)` 정확 사용, 동기 리셋 구현(if(reset)이 always_ff 내부), 신호 이름 접두사 적용.

> **문제 6 — NOP 삽입 어셈블리 프로그램 작성**
>
> 다음 RISC-V 코드 시퀀스에서 데이터 해저드 없이 파이프라인이 동작하도록 필요한 최소 개수의 NOP을 삽입하시오.
>
> ```
> ADD  x1, x2, x3      # x1 = x2 + x3
> SUB  x4, x1, x5      # x4 = x1 - x5  (x1에 의존)
> ```
>
> (가) 필요한 NOP 최소 개수를 쓰시오.
>
> (나) NOP을 삽입한 완성된 코드를 쓰시오.
>
> (다) 이 방식의 문제점을 1~2문장으로 설명하시오.
>
> *기대 답변*:
> - (가) 3개 (ADD의 WB가 사이클 5에 완료, SUB의 ID에서 x1 읽기는 사이클 2 이후이어야 하므로 3사이클 지연 필요)
> - (나) ADD x1, x2, x3 → NOP → NOP → NOP → SUB x4, x1, x5
> - (다) NOP 삽입은 실행 사이클 증가(성능 저하)를 초래하며, 프로그래머/컴파일러가 수동으로 삽입해야 하는 부담이 있다. Ch10의 포워딩으로 해결 가능.
>
> *채점 기준*: (가) 3개 정확. (나) 위치와 개수 정확. (다) 성능 저하 또는 수동 삽입 부담 중 1개 언급 시 정답.

### [분석 — Analyze: 파이프라인 성능을 분석할 수 있다]

> **문제 7 — NOP 삽입 방식의 성능 분석**
>
> 다음 RISC-V 프로그램이 있다.
>
> ```
> LW   x1, 0(x2)      # 메모리에서 x1 로드
> ADD  x3, x1, x4     # x1에 의존 (LW 다음 바로 사용)
> SUB  x5, x3, x6     # x3에 의존
> AND  x7, x5, x8     # x5에 의존
> ```
>
> (가) 데이터 해저드를 회피하는 데 필요한 NOP의 총 개수를 계산하시오. (각 의존 관계별 필요 NOP 수를 분리하여 계산)
>
> (나) NOP 삽입 후 총 명령어 수와 실질적 CPI를 계산하시오. (유효 명령어 4개 기준, NOP는 1사이클 소모)
>
> (다) 이 분석에서 포워딩이 필요한 이유를 숫자로 제시하시오.
>
> *기대 답변*:
> - (가) LW→ADD: 3개(LW는 MEM에서 결과가 나오므로 최소 3사이클 지연 필요) / ADD→SUB: 3개 / SUB→AND: 3개 → 총 9개 NOP
> - (나) 총 명령어 = 4 + 9 = 13. 실질적 CPI = 13/4 = 3.25 (유효 명령어 기준)
> - (다) NOP 삽입으로 유효 CPI가 3.25까지 악화되었다. 포워딩 적용 시 LW→직후 사용을 제외하면 NOP 불필요 → CPI ≈ 1.0~1.25 수준으로 회복 가능.
>
> *채점 기준*: (가) NOP 계산 과정 명시. (나) 수치 정확. (다) 포워딩의 성능 효과를 수치 비교로 제시 시 만점.

## 교육 설계자 종합 평가 및 권고사항

### Ch09 학습 설계의 핵심 과제

1. **9.2절 타이밍 다이어그램 기능 정착 필수**: 타이밍 다이어그램을 읽는 능력은 Ch10~Ch12 전체의 전제 조건이다. 4단계 Gradual Reveal SVG와 즉각적인 빈칸 완성 실습을 반드시 포함한다. 이 절에서 시간을 충분히 투자하는 것이 Part 4 전체의 학습 성패를 결정한다.

2. **9.1절 "관점 전환" 설계**: 9.1절은 기술 내용보다 개념적 연결이 핵심이다. FSM과 파이프라인의 대응을 독자 스스로 발견하게 만드는 유도 질문("EX 회로가 유휴 상태일 때 어떤 낭비가 발생하는가?")을 반드시 배치한다.

3. **9.5절 성취감 의도적 설계**: NOP 파이프라인은 기술적으로 완성도가 낮지만 교육적으로 중요하다. "동작하는 파이프라인을 내가 만들었다"는 경험이 Ch10의 높은 난이도를 견디는 심리적 자원이 된다. 9.5절의 마일스톤 선언 문장과 시뮬레이션 검증 가이드를 정성껏 설계해야 한다.

4. **리셋 전략 일관성 확정**: 기술 리뷰어 주석(TABLE_OF_CONTENTS.md)에서 파이프라인 레지스터의 동기/비동기 리셋 전략을 9.4절에서 확정하도록 요청했다. 9.4절에서 "동기 리셋(synchronous reset) 사용" 결정을 명시하고 이후 챕터에서 동일하게 유지한다.

5. **해저드 복선 관리**: 9.1절 세탁기 비유의 한계 명시, 9.2절 FAQ "실제로 8배 빠른가?", 9.5절 NOP 한계 분석 — 이 세 곳에서 해저드(hazard)라는 단어를 점진적으로 소개하되, 해결은 Ch10으로 명확히 미룬다.

### 기술 저자에 대한 권고사항

1. **9.2절 타이밍 다이어그램 SVG 4종을 먼저 제작하고 집필 시작**: 다이어그램이 명확하면 텍스트 설명이 간결해진다. SVG 없이 텍스트로만 타이밍 다이어그램을 설명하는 것은 불가능하다.

2. **9.4절에서 전달 신호 목록의 설계 근거를 명시**: "왜 이 신호들이 파이프라인 레지스터에 포함되는가?"를 스테이지별 필요 신호 관점에서 설명한다. 특히 제어 신호(reg_write, mem_read 등)가 ID/EX에서 MEM/WB까지 전달되어야 하는 이유를 명확히 한다.

3. **9.5절 NOP 검증 프로그램은 사전 시뮬레이션 확인 필수**: 제공하는 어셈블리 프로그램이 NOP 삽입 후 실제로 정확히 실행됨을 집필 전 시뮬레이션으로 검증한다.

4. **9.6절 Ch10 예고 문장에 "데이터 해저드"와 "포워딩" 용어 첫 등장 병기**: 각각 한국어 설명 병기 — "데이터 해저드(Data Hazard, 앞 명령어의 결과가 필요한 충돌)", "포워딩(Forwarding, 우회 경로를 통한 직접 전달)".

5. **Ch08 소급 수정 없음 원칙 준수**: 9.1절에서 FSM-파이프라인 연결을 설명하더라도 Ch08 원고를 수정하지 않는다. Ch08의 8.7절에 이미 배치된 Ch09 예고 문장이 연결 고리 역할을 하므로 충분하다.
