### 1.2 MESI 개념 설명

**원문** (25.1 "MESI 프로토콜: 4가지 상태"):
> "MESI는 각 캐시 라인이 가질 수 있는 4가지 상태를 정의한다. 각 캐시 라인의 헤더에는 이 상태를 나타내는 비트들이 저장된다: **Modified, Exclusive, Shared, Invalid**"

**평가**: ⭐⭐⭐⭐⭐

**강점**:
- **학생 관점 대입**: "각 캐시 라인의 헤더에" → 학생들이 이미 배운 캐시 구조(Ch13-15)와의 자연스러운 연결
- **명사 강조**: 4가지 상태를 절을 나누지 않고 나열 → 암기 부담 낮음
- **상태 정의가 명확**: 각 상태를 "(조건) + (결과)" 형식으로 설명
  - Modified: "이 캐시가 유일하게 최신 복사본을 보유. 메인 메모리는 오래된 데이터"
  - Exclusive: "이 캐시가 유일하게 이 라인을 보유하나, 메인 메모리와 동일"

### 1.4 코드 설명 품질

**원문** (mesi_tracker.sv):

**평가**: ⭐⭐⭐⭐⭐

**강점**:

#### Q2: "예약(Reservation)은 정말로 하드웨어가... 어떻게?"

**원문에서의 답변 위치**: ✅ 충분함

**원문** (25.2 "LR/SC의 작동 원리"):
> "LR.W(Load-Reserved Word): 메모리 주소에서 32비트 데이터를 읽고, 그 주소에 대해 '**예약(reservation)**'을 설정한다. 예약은 **주소와 코어 ID를 함께 저장**한다."

**코드 설명**:
```systemverilog
// 예약 레지스터
logic        reservation_valid;
logic [31:0] reservation_addr;

always_ff @(posedge clk or negedge rst_n) begin
   if (!rst_n) begin
      reservation_valid <= 1'b0;
      reservation_addr  <= 32'h0;
   end
   else if (ex_lr_w) begin
      // LR.W 실행 → 새로운 예약 설정
      reservation_valid <= 1'b1;
      reservation_addr  <= ex_addr;
   end
```

**평가**: ⭐⭐⭐⭐⭐

**강점**:
- 코드가 정확히 "예약"이 무엇인지 보여줌
- 학생들이 "아, 그냥 플립플롭 2개(valid + address)네?"라고 직관 형성 가능

#### Q3: "Core 0과 Core 1이 동시에 같은 주소에 쓰면 뭐가 되나요?"

**원문에서의 답변 위치**: ✅ 충분함

**원문** (25.1 "MESI 상태 전이의 핵심 시나리오"):
> "시나리오 3: Shared → Modified (로컬 쓰기)
> Shared 상태에서는 다른 캐시도 이 라인을 가지고 있을 수 있다. 쓰기를 하려면 먼저
> 다른 캐시의 복사본을 모두 무효화(invalidate)해야 한다.
> 이를 위해 BusRdX(Read-Exclusive, 쓰기 의도 신호)를 버스에 방송한다."

**평가**: ⭐⭐⭐⭐

**구체적 예제 추가 권장**:
원문에 "시나리오" 섹션 내에 타임라인 표 추가
```
T0: Core 0, Core 1 모두 addr=0x100 읽음 → 둘 다 Shared 상태
T1: Core 0이 addr=0x100에 값 10 기록 시도
    → Core 0: BusRdX 방송
    → Core 1: BusRdX 감지 → Invalid 전이
T2: Core 0: Shared → Modified 전이 (이제 단독 소유)
T3: Core 1이 addr=0x100 읽으려 시도
    → Core 1: LR/BusRd 방송
    → Core 0: BusRd 감지 + Core 1에게 최신값(10) 응답
    → Core 0: Modified → Shared 전이
    → Core 1: Invalid → Shared 전이
결과: 둘 다 최신값(10) 확보!
```

#### Q4: "스핀락으로 계속 루프를 돌면 성능이..."

```
      그럼 메모리 값이 어떻게 됐을 것 같아?"

학생: "아, 바뀌었을 수도 있네요?"

강사: "정답! 그래서 값을 다시 읽어야 하는 거야.
      그래서 LR부터 다시 하는 거다."
```

**효과**:
- 학생이 스스로 깨달음 → 이해도 훨씬 깊음
- "난 이걸 이해했다"는 자신감 형성

## 8. 심화 주제 (학생 질문 시)

학생들이 더 깊이 알고 싶어할 때 대답할 수 있는 내용:

### 주제 1: "Sequential Consistency (SC) vs Total Store Order (TSO)"

**Ch25에서는 다루지 않으나, 면접/대학원 세미나에서 나올 수 있음**

**강사 답변**:
```
Sequential Consistency (SC):
- 모든 메모리 연산이 순차적으로 전역적으로 보임
- 구현이 어려움 (성능 저하)

Total Store Order (TSO):
- Store 이후 Load는 반드시 최신값을 봄
- 하지만 여러 Store는 순서가 재정렬될 수 있음
- Intel x86 기본 메모리 모델

이 프로젝트에서는 MESI가 "캐시 일관성"을 보장하고,
"메모리 일관성"은 프로그래머가 코드로 보장해야 함
(barrier/fence 명령어 사용).
```

### 주제 2: "Acquire/Release Semantics"

**Ch25에서는 다루지 않으나, Lock-Free 구현 시 필수**

**강사 답변**:
```
LR/SC의 "aq"(acquire), "rl"(release) 비트:

- aq=1: "이전 메모리 연산이 모두 완료될 때까지 기다려"
        (acquire barrier)
- rl=1: "이후 메모리 연산이 시작되기 전까지 기다려"
        (release barrier)

예: 스핀락 acquire에서는 LR.aq, SC.rl을 사용하여
    메모리 순서를 보장함.

이것은 고급 주제이지만, Lock-Free를 정확히 구현하려면 필수.
```

### 주제 3: "Directory-Based vs Snooping"

**Ch25에서는 다루지 않으나, 대규모 멀티코어에서 중요**

**강사 답변**:
```
Snooping (이 책에서 다룸):
- 모든 캐시가 모든 버스 신호를 감시
- 코어 수가 증가하면 버스 대역폭 병목
- ~8코어까지 실용적

Directory-Based (고급):
- 메모리 컨트롤러가 "각 라인마다 어떤 캐시가 복사본을 가졌는가"를 기록 (Directory)
- 특정 캐시만 Invalidation 신호를 받음
- 코어 100+개 가능
- Intel, ARM 고급 프로세서 사용

이 프로젝트에서는 snooping으로 단순화했으니,
이것이 확장 포인트임을 언급하면 좋음.
```
