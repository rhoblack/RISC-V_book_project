## 전체 평가

Chapter 08은 17개 상태 FSM 제어 유닛의 설계 의도와 교육적 흐름이 잘 구성되어 있다.
`typedef enum`, `always_ff + always_comb` 이중 블록 패턴, 기본값 선설정 등 산업 표준 패턴을 올바르게 사용하고 있다.
그러나 **Critical 이슈 3건**, **Major 이슈 4건**, **Minor 이슈 2건**이 발견되었다.
특히 Branch 분기 주소 계산 방식의 설계 불일치와 "전체 소스 코드" 섹션의 `branch_taken` 이중 구동 문제는 반드시 수정이 필요하다.

## 🔴 Critical 이슈

### C-1: `branch_taken` 이중 구동 — 전체 소스 코드 섹션 (합성 오류)

**위치**: 전체 소스 코드 섹션 `fsm_controller` 완전 버전 (1629~1661행)

**문제**: 완전 버전 코드에서 `branch_taken`이 두 개의 `always_comb` 블록에서 동시에 구동된다.

```
// 블록 1 (1617~1627행): branch_taken을 funct3으로 계산
always_comb begin
   case (funct3)
      3'b000: branch_taken = alu_zero;
      ...
   endcase
end

// 블록 2 (1629~1661행): branch_taken = 1'b0 로 기본값 설정 후 case에서 미변경
always_comb begin
   {pc_write,...,pc_src} = '0;
   branch_taken = 1'b0;   // ← 여기서 또 구동!
   case (current_state)
      ...   // branch_taken 재설정 없음
   endcase
end
```

SystemVerilog에서 동일 신호를 두 개의 `always_comb` 블록에서 구동하면 **multiple driver 오류**가 발생하며, 시뮬레이터에서는 X(unknown) 또는 경쟁 조건이 생긴다. Vivado 합성은 이를 거부한다.

**수정 방법**: 완전 버전 코드의 출력 로직 블록(두 번째 `always_comb`)에서 `branch_taken = 1'b0` 행을 삭제해야 한다. `branch_taken`은 첫 번째 `always_comb`(funct3 디코딩 블록)에서만 구동한다. `branch_taken`은 Moore FSM 출력이 아닌 순수 조합 로직이므로 이 구조 자체는 허용되지만, 동일 신호의 이중 구동만 제거하면 된다.

### C-2: EX_BR 단계 — 분기 목표 주소 계산 방식의 설계 불일치

**위치**: 8.2.4절 EX_BR 설명(401~427행) 및 8.3.2절 코드(819~827행)

**문제**: 8.2.4절 본문에서는 "ALU가 A-B 비교에 사용 중이므로 분기 주소를 ALU로 계산할 수 없다. 별도 덧셈기(branch_adder)가 필요하다"고 정확하게 설명한다. 그러나 제어 신호 표에서는:

```
pc_src = 01  → PC 소스 = ALUOut (분기 목표 주소)
```

로 되어 있다. ALUOut에는 EX_BR에서 A-B(SUB 결과)가 저장되지, PC+imm_B가 저장되지 않는다. `pc_src=01`로 ALUOut을 분기 주소로 쓰면 **잘못된 주소로 점프**한다.

본문 설명과 제어 신호 표, 그리고 코드(S_EX_BR: `pc_src=2'b01`)가 상호 모순된다. 다음 중 하나를 선택해야 한다:

**옵션 A (권장)**: `pc_src`에 새 값 `2'b10`을 추가하여 branch_adder 출력을 선택하도록 데이터패스를 확장하고 제어 신호 표를 수정한다. 이것이 RISC-V 멀티사이클 표준 구현이다.

**옵션 B**: ID 단계에서 ALU를 사용해 PC+imm_B를 미리 계산하여 별도 레지스터(예: branch_target_reg)에 저장하고, EX_BR에서 이 값을 `pc_src=2'b10`으로 선택한다.

어느 방식이든 현재의 "EX_BR에서 ALU로 A-B를 계산하면서 동시에 ALUOut에 분기 주소가 들어 있다"는 모순은 수정되어야 한다. 현재 코드는 구조적으로 동작할 수 없다.

### C-3: JAL — rd에 쓰는 복귀 주소(PC+4) 값의 정확성 문제

**위치**: 8.2.4절 EX_JAL 설명(468~493행), S14: WB_JAL 제어 신호 표

**문제**: 원고에서 "IF 단계에서 PC가 이미 PC+4로 갱신되었으므로, WB_JAL에서 mem_to_reg=10으로 현재 PC 레지스터 값(이미 PC+4)을 rd에 쓴다"고 설명한다.

이는 설계가 IF 단계에서 PC 레지스터가 PC+4로 갱신되고, 이후 EX_JAL과 WB_JAL 단계까지 그 값이 보존되며, WB_JAL에서 PC 레지스터를 직접 읽어 rd에 쓴다는 것을 의미한다.

그런데 EX_JAL 단계에서:
```
alu_src_a = PC (0)
alu_src_b = imm_J
ALU 계산: ALUOut = PC_current + imm_J
```
여기서 `PC_current`는 IF 단계에서 이미 `PC+4`로 갱신된 값이다. 따라서 **EX_JAL에서 ALUOut = (JAL_PC + 4) + imm_J**가 되어 점프 목표 주소가 4만큼 틀린다.

**올바른 구현**: `alu_src_a`가 현재 PC 레지스터(= 이미 PC+4)를 사용하면, EX_JAL에서는 PC 대신 **원래 JAL 명령어 주소**를 써야 한다. 이를 위해 Ch07 데이터패스에서 PC 값이 IF 단계에서 ALUOut으로 갱신되기 전에 별도 레지스터(old_PC)에 보존되어야 한다. 또는 ID 단계 ALU 입력(alu_src_a=0)이 업데이트된 PC가 아닌 원래 PC를 가리켜야 한다.

Ch07 데이터패스 설계와의 정합성을 확인하고, JAL/AUIPC의 `alu_src_a=0(PC)`가 명령어 주소(JAL_PC)를 의미하는지, PC+4를 의미하는지 명시적으로 정의해야 한다. 만약 Ch07에서 PC 레지스터가 IF에서 PC+4로 즉시 갱신된다면 JAL과 AUIPC는 4바이트 오류가 발생한다.

## 🟡 Major 이슈

### M-1: BLT/BGE와 BLTU/BGEU 구분 — `alu_lt` 신호 한계

**위치**: 8.3.2절 분기 조건 판단 `always_comb` (721~731행)

**문제**: BLT(부호 있는 비교)와 BLTU(부호 없는 비교)가 모두 `alu_lt` 신호 하나를 사용하고 있다:

```
3'b100: branch_taken = alu_lt;   // BLT: rs1 < rs2 (부호)
3'b110: branch_taken = alu_lt;   // BLTU: rs1 < rs2 (무부호)
```

RV32I ISA에서 BLT는 부호 있는 비교, BLTU는 부호 없는 비교다. ALU가 두 개의 다른 플래그(`alu_lt` = 부호 비교 결과, `alu_ltu` = 무부호 비교 결과)를 출력해야 한다. 단일 `alu_lt`로 두 가지를 구분할 수 없다.

**수정 방법**: `alu_ltu` 출력을 데이터패스(ALU)와 FSM 인터페이스에 추가하거나, 또는 "이 교재에서는 BLT/BGE만 구현하고 BLTU/BGEU는 제외"임을 명시해야 한다. 현재는 BLTU/BGEU가 잘못 동작한다는 설명 없이 코드만 있어 독자를 오도할 수 있다.

---

### M-2: AUIPC — `alu_src_a=0(PC)` 값의 정합성 (C-3과 연관)

**위치**: S11: EX_AUIPC 제어 신호 표(459~465행)

**문제**: AUIPC는 "현재 명령어의 PC + imm_U"를 계산해야 한다. 그런데 IF 단계에서 PC가 PC+4로 갱신되었다면, EX_AUIPC에서 `alu_src_a=0(PC)`는 `AUIPC_PC+4`를 의미한다. 결과가 4만큼 틀린다. C-3 이슈와 동일한 근본 원인이다.

**수정 방법**: C-3과 함께 처리. "IF 단계에서 PC 갱신 전 PC 값을 보존하는 별도 레지스터(PC_orig 또는 old_pc)를 Ch07 데이터패스에 추가했음"을 명시하거나, `alu_src_a` 의미를 재정의해야 한다.

---

### M-3: ID 단계 ALU 연산의 모호성

**위치**: 8.2.1절 S1: ID 제어 신호 표(297~305행) 및 코드(765~771행)

**문제**: ID 단계에서 `alu_src_a=0(PC)`, `alu_src_b=10(imm_ext)`, `alu_op=00(ADD)`으로 설정한다. 설명에는 "분기 주소 미리 계산 준비용, 실제 사용 안 함"이라고 명시되어 있다.

이는 두 가지 문제를 유발한다:
1. ALU 연산 결과가 "사용 안 됨"이면 ALUOut 레지스터에 쓰레기 값이 들어가 디버깅 시 혼란을 준다.
2. 만약 branch_adder 없이 ID 단계의 ALUOut(PC+imm_B)을 분기 주소로 활용하는 구조라면(즉, C-2의 옵션 B), 이를 명확하게 설명해야 한다. 현재 설명은 "사용 안 함"이라고 하면서도 C-2 본문에서는 이 방법을 언급하는 등 일관성이 없다.

**수정 방법**: ID 단계 ALU 연산의 결과가 실제로 사용되는지/사용 안 되는지를 명확히 결정하고, 사용한다면 어떻게 사용하는지(예: branch_target으로 활용), 사용 안 한다면 alu_src 값을 기본값(don't care)으로 두어도 됨을 명시해야 한다.

### M-4: 전체 소스 코드 — 축약형 next_state 로직의 SystemVerilog 문법 주의

**위치**: 전체 소스 코드 섹션 (1594~1615행)

**문제**: 축약형 코드에서 S_ID의 중첩 case문이 다음과 같이 작성되어 있다:

```systemverilog
S_ID: case (opcode)
   OP_R: next_state=S_EX_R; OP_I_ALU: next_state=S_EX_I;
   ...
endcase
```

SystemVerilog에서 case 항목의 본문이 `begin...end` 없이 세미콜론으로 구분된 여러 문장을 한 줄에 쓰는 것은 구문 오류다. 각 항목은 하나의 문장만 허용되며, 여러 문장을 쓰려면 `begin...end`가 필요하다. 실제로 이 코드는 "OP_R: next_state=S_EX_R;" 이후 "OP_I_ALU: next_state=S_EX_I;"가 별도 case 항목으로 처리되어야 하는데, 축약 표기로 인해 파서가 올바르게 해석할 수 없다.

**수정 방법**: 축약형 코드를 가독성보다 정확성 우선으로 수정하거나, 이것이 "의사 코드 스타일 요약"임을 독자에게 명시해야 한다. 학습용 교재이므로 실제로 컴파일 가능한 코드만 수록하는 것이 원칙이다.

## 🟢 Minor 이슈

### m-1: 면접 포인트 번호 중복

**위치**: 8.3.2절(887행)과 8.6절(1371행)

**문제**: 두 곳 모두 `면접 포인트 #11`로 표시되어 있다. 8.3.2절은 "하드와이어드 vs 마이크로프로그래밍" 간략 버전, 8.6절은 "완전 버전"이라고 명시되어 있으나 번호가 동일하다. 독자가 "면접 포인트 #11을 찾아가시오"라고 하면 혼란을 겪을 수 있다.

**수정 방법**: 8.3.2절 aside를 "면접 포인트 #11a (요약)"로, 8.6절을 "면접 포인트 #11 (완전 버전)"으로 구분하거나, 8.3.2절 aside는 일반 tip으로 변경하고 8.6절만 #11로 유지한다.

### m-2: 처리량 단위 표기 — MIPS 용어 혼란 가능성

**위치**: 8.5.4절 Fmax 비교 표(1264~1306행)

**문제**: 처리량 단위로 "MIPS(Mega Instructions Per Second)"를 사용하고 있다. 독자 중 일부는 MIPS를 아키텍처 이름(MIPS ISA)으로 혼동할 수 있다. 교재에서 Ch07 메모리 노트(Ch07 주의사항)에 "MIPS 방식 잔재"라는 표현이 나온 맥락에서 특히 혼란 가능성이 있다.

**수정 방법**: "처리량(MIPS, Mega Instructions Per Second)"으로 첫 등장 시 풀어서 표기하거나, "처리량(IPS, 100만 명령어/초)"으로 표기를 통일한다.

## 긍정적 평가

- **Moore FSM 선택 근거 설명**: 글리치(Glitch) 내성, 타이밍 안전성을 명확히 설명. 우수.
- **기본값 선설정 패턴**: 본문 버전 코드에서 모든 신호에 0을 먼저 할당 후 case override 패턴 정확히 구현.
- **Store 명령어 imm_S 처리**: 별도 설명 없이 즉치수 생성기가 올바르게 처리함을 전제. 적절.
- **JALR 하위 비트 클리어 aside**: ISA 스펙을 정확히 언급하고 교재 범위 내 생략 이유 명시. 교육적으로 우수.
- **HTML 이스케이프**: `&lt;=`, `&lt;`, `&gt;`, `&amp;` 전반적으로 올바르게 적용.
- **default 분기**: next_state 로직 및 출력 로직 모두에 default 처리 포함.
- **CPI 분석**: 가중 평균 계산 정확, 멀티사이클의 처리량 열세를 솔직하게 분석.
