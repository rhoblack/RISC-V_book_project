# Chapter 19 — 예외/인터럽트와 파이프라인 통합 (교육심리 기획)

**작성일**: 2026-03-15
**담당**: 교육심리전문가

## 1. 불안 지점 식별 (4개)

**A. 파이프라인 복잡도 증가에 대한 피로감 (매우 높음)**
- Ch09~12에서 파이프라인을 완성하고, Ch13~15에서 캐시를 추가하고, Ch16~17에서 AMBA를 배웠다. 이제 또 파이프라인에 예외/인터럽트를 추가해야 한다.
- 학습자 심리: "또 파이프라인에 뭔가를 추가해야 해? 언제 끝나는 거지?" → **누적 피로감**
- 원인 분석: Part 4에서 해저드/포워딩/flush로 이미 높은 인지 부하를 경험. 같은 구조에 새로운 복잡성이 계속 추가되는 패턴에 대한 저항감.
- 핵심: 이것은 "새로운 학습"이 아니라 "기존 메커니즘(flush)의 재활용"임을 인식시켜야 한다.

**B. 동시성 개념의 추상성 (높음)**
- 파이프라인 5단계에서 5개의 명령어가 동시에 실행되는 중에 예외가 발생한다. "어느 명령어의 예외인가?"가 직관적이지 않다.
- 학습자 심리: "5개 명령어가 동시에 흐르는데, 중간에 예외가 터지면 어떤 것을 살리고 어떤 것을 죽이지?" → **공간적 혼동**
- 원인 분석: 순차 실행 모델에서는 "예외 = 지금 실행 중인 명령어"이지만, 파이프라인에서는 "어느 스테이지의 명령어?"라는 추가 차원이 존재.
- 핵심: "정확한 예외(precise exception)"의 의미를 직관적 비유로 전달해야 한다.

**C. 예외 타입의 정보 과부하 (중간)**
- 16개 예외 타입 + 11개 인터럽트 소스 = 27개 케이스
- 학습자 심리: "이걸 다 외워야 하나? mcause 코드까지?" → **암기 압박**
- 원인 분석: 표 형태로 제시되면 "모두 알아야 한다"는 인상을 줌. 실제로는 구현에서 3~4개만 다룸.
- 핵심: "참조 테이블"로 프레이밍하고, 구현 대상을 명시적으로 좁혀야 한다.

**D. 실무 연관성 불확실 (중간)**
- "왜 프로세서가 예외를 처리해야 하지?" — 소프트웨어 개발자와 달리 하드웨어 설계자는 예외 처리의 필요성을 체감하기 어렵다.
- 학습자 심리: "OS가 처리하는 거 아닌가? 왜 하드웨어에서?" → **동기 상실**
- 원인 분석: 예외 처리의 하드웨어-소프트웨어 경계가 불명확. "하드웨어가 하는 일"과 "소프트웨어가 하는 일"의 역할 분담을 명확히 해야 한다.
- 핵심: "하드웨어가 mepc/mcause를 저장하지 않으면 소프트웨어는 복귀할 곳을 모른다"는 필수성을 강조.

## 2. 감정 곡선 설계

### 호기심 (도입, 19.1)
- **장면**: "당신이 프로세서라면, 실행 중에 '잘못된 명령어'를 만났을 때 어떻게 하겠습니까? 무시하고 계속 갈까요, 아니면 멈추고 누군가에게 알릴까요?"
- **연결**: "프로세서도 선택해야 합니다. 그리고 그 선택을 '어떻게' 하는지가 바로 예외 처리입니다."
- **감정 목표**: 호기심 + 현실감. "프로세서도 에러를 만난다"는 공감을 유도.
- **Ch18 연결**: "Ch18에서 만든 CSR(mepc, mcause, mtvec)이 바로 이 순간을 위한 것이었습니다."

### 불안 (19.2 초반, 파이프라인 + 예외 결합)
- **장면**: "파이프라인 5단계 각각에서 예외를 감지해야 한다고? IF에서도, ID에서도, EX에서도?"
- **원인**: 동시성 × 예외 감지 = 5배의 복잡도라는 착각
- **감정**: 초기 호기심이 "이건 너무 복잡해"로 전환되는 순간
- **설계 의도**: 이 불안은 자연스러운 것. 바로 뒤에 "각 스테이지는 자기 담당 예외 1~2개만 감지한다"는 단순화로 해소.

### 이해 (19.2 중반~19.3)
- **장면**: "아, flush는 Ch11에서 이미 배운 것이고, 예외도 같은 메커니즘이구나. 다만 PC가 mtvec으로 바뀔 뿐이야."
- **이유**: 기존 지식(flush)과 새 개념(예외)의 연결 → 인지 부하 급감
- **전환점**: 타이밍 다이어그램에서 "예외 발생 → flush → mtvec 로드"가 단 4사이클임을 시각적으로 확인하는 순간
- **감정**: "생각보다 단순하네!" → 자신감 회복

### 성취감 (19.3~19.4, Part 7 완성)
- **장면**: "AMBA 버스 위에서 파이프라인이 실행되고, CSR로 제어되고, 예외와 인터럽트로 흐름이 전환된다 — Part 7이 완성되었다!"
- **경험**: 4개 챕터(Ch16~19)의 개별 개념이 하나의 시스템으로 통합되는 "아하!" 순간
- **감정 목표**: "나도 프로세서 설계자처럼 전체 시스템을 이해한다" → 자기효능감 최고점
- **Part 8 예고**: "다음은 이 모든 것을 실제 FPGA에 구현합니다" → 기대감으로 전환

## 4. 첫 성공 경로 설계 (3단계)

**1단계: 예외 감지 — "예외도 그냥 신호다" (가장 쉬움, 성공 보장)**
- **작업**: 테스트벤치에서 Illegal Instruction(존재하지 않는 opcode)을 삽입하고, ID 스테이지에서 `illegal_instr` 신호가 HIGH로 뜨는지 확인
- **난이도**: ★☆☆☆☆
- **성공 척도**: 파형에서 `illegal_instr = 1`을 확인
- **심리적 효과**: "아, 예외도 결국 1비트 신호구나. 특별한 게 아니었어."
- **설계 원칙**: 이 단계에서 실패할 가능성을 0으로 만듦. 테스트벤치가 자동으로 결과를 출력하도록 설계.

**2단계: flush 실행 — "내가 파이프라인을 제어한다" (중간)**
- **작업**: 예외 신호가 발생하면 IF/ID, ID/EX 파이프라인 레지스터가 NOP으로 클리어되는지 확인
- **난이도**: ★★☆☆☆
- **성공 척도**: 파형에서 flush 이후 파이프라인 레지스터가 `32'h0000_0013`(NOP)으로 변경됨을 확인
- **심리적 효과**: "Ch11에서 배운 flush가 여기서도 똑같이 작동한다!" → 기존 지식과의 연결로 자신감 강화
- **설계 원칙**: Ch11 flush와 동일한 메커니즘임을 명시적으로 상기시킴.

**3단계: mepc 저장 및 PC 리다이렉션 — "예외 처리 전체 흐름 완성" (심화)**
- **작업**: 예외 발생 명령어의 PC가 mepc에 저장되고, 다음 사이클에 PC가 mtvec 값으로 변경되는지 확인
- **난이도**: ★★★☆☆
- **성공 척도**: ①mepc에 올바른 PC 값 저장 확인 ②PC가 mtvec으로 점프 확인 ③mcause에 올바른 예외 코드(2 = Illegal Instruction) 기록 확인
- **심리적 효과**: "예외 발생 → flush → CSR 저장 → 핸들러 점프, 전체 흐름을 내가 구현했다!" → 자기효능감 급상승
- **설계 원칙**: 3개의 확인 항목을 순서대로 검증하여 "부분 성공"도 인정. 하나라도 성공하면 다음으로 진행 가능.
