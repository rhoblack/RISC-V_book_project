#### 2.1.5 핵심 시나리오: 4가지 전이 패턴 (p.90-104)

**학습 설계**:
```
시나리오 1: Read Miss → Exclusive 또는 Shared
    ↓ (조건: 다른 캐시 존재 여부)

시나리오 2: Exclusive → Modified (Silent)
    ↓ (다른 캐시 없으므로 버스 신호 없음)

시나리오 3: Shared → Modified (BusRdX 방송)
    ↓ (다른 캐시 무효화 필요)

시나리오 4: Modified → Shared/Invalid (버스 이벤트)
    ↓ (다른 코어가 요청하면 응답 또는 무효화)
```

**복잡도 관리**:
- 🟢 **외재적 부하 낮음**: 각 시나리오가 1-2문장으로 명확
- 🟢 **본재적 부하 관리 필요**: 상태 4개 × 이벤트 4개 = 가능한 전이 16개
  - **현재 전략**: 4가지 주요 시나리오만 강조 ✅ (적절)
  - **추가 가치**: 나머지 전이(불가능하거나 상태 유지)를 SVG 상태도에서 점선으로 표시? (선택적)

#### 2.2.3 작동 원리: LR/SC (p.303-322)

**학습 설계**:
```
LR.W 정의: "메모리 읽기 + 예약 설정 (주소+코어ID)"
    ↓
SC.W 정의: "예약 유효 확인 후 조건부 쓰기"
    ↓
반환값: 0(성공) vs 비영(실패)
    ↓
예약 무효화 3가지 경우:
  1. 다른 코어의 쓰기 (BusRdX)
  2. 같은 코어의 새로운 LR
  3. 컨텍스트 스위칭
    ↓
핵심: "LR과 SC 사이에 코드 있어도 된다" (임의 계산 가능)
```

**복잡도 분석**:
- ✅ **개념적 명확성**: ⭐⭐⭐⭐⭐
  - "예약" = "이 주소가 내 것이라고 주장"
  - "예약 유효성" = "그 사이 다른 코어가 건드리지 않았는가?"
- 🟡 **"Forward Progress Guarantee" 미언급**:
  - RISC-V 스펙: SC가 비결정적으로 실패 가능 (예: 5회 재시도 후에도)
  - **현재**: "비결정적 실패" 언급 없음 → 학생이 "무한 루프?" 질문 가능
  - **개선 제안**: Spinlock 섹션에서 "재시도" 패턴 설명 시 추가

#### 2.2.4 명령어 인코딩 (p.330-369)

**내용**:
```
LR.W 포맷: funct7=0010001, aq, rl, rs2=00000, rs1, funct3=010, rd, opcode=101111
SC.W 포맷: funct7=0011000, aq, rl, rs2, rs1, funct3=010, rd, opcode=101111
```

**평가**:
- ✅ **완전성**: RISC-V ISA 스펙 정확 ✅
- ✅ **교육적 명확성**: 인코딩 예시 제공 (t0←(a0) 형식)
- ✅ **Acquire/Release(aq, rl) 비트**: "기본값"으로 명시 → 심화 학습 연결 ✅
- 🟢 **복잡도 수준**: Verilog 경험 있는 대학원생 대상이므로 적절

#### 2.2.5 LR/SC 실행 유닛 구현 (p.371-474)

**학습 설계**:
```
인터페이스 정의
    ↓
예약 레지스터 (valid + address)
    ↓
주소 일치 판정 (워드 정렬 비교 [31:2])
    ↓
예약 레지스터 관리 (FF)
  - SC 실행 시 해제
  - 스누핑 무효화
  - LR 실행 시 새 예약
    ↓
메모리 인터페이스 및 SC 결과 생성 (조합 논리)
```

**복잡도 분석**:
- **코드 길이**: 102줄 (lr_sc_unit 모듈)
- **논리 명확성**:
  - ✅ **우선순위 명시**: SC > 스누핑 > LR (코드 주석 명확)
  - ✅ **워드 정렬 비교**: [31:2]로 byte offset 무시 ✅
  - 🟡 **주소 [1:0] 무시의 의미**: "왜 [31:2]인가?"
    - 현재: 주석 없음
    - 개선: "바이트 정렬을 무시하는 이유: 단어 단위 예약" 설명 추가 권장

**FAQ 평가** (p.485-489):
```
Q: "SC가 실패해도 예약이 해제되나? 다시 시도할 수는 없나?"
A: "RISC-V 스펙: SC 실행(성공/실패 무관) 후 예약 해제.
    다시 시도하려면 새로운 LR."
```
- ✅ **중요한 명확화**: 학생들의 흔한 오해를 선제 ✅
- ✅ **스펙 정확성**: RISC-V 공식 스펙 인용

#### 2.2.6 스핀락 구현 (p.491-575)

**학습 설계**:
```
C 의사 코드: while(1) { val = LR; if(val != 0) continue; if(SC==0) break; }
    ↓
RISC-V 어셈블리: lr.w → bnez → sc.w → bnez
    ↓
SystemVerilog RTL 개념 설명
    ↓
동작 흐름 (5단계):
  1. LR.W: lock 읽기 + 예약
  2. BNEZ: 잠금 상태면 재시도
  3. SC.W: lock = 0 기록 (실패 시 재시도)
  4. (성공) 임계 영역 진입 (lock = 1로 설정됨)
  5. 작업 완료 후 "SW zero, 0(a0)"로 언락
```

**분석**:

| 단계 | 설명 명확성 | 학생 이해도 예상 |
|------|----------|--------|
| LR 실행 | "읽기 + 예약" ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| BNEZ (첫 번째) | "lock=0이 아니면 스핀" ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| SC 실행 | "lock=0 쓰기 시도" ⭐⭐⭐⭐ | ⭐⭐⭐ (복잡도) |
| BNEZ (두 번째) | "SC 실패하면 LR로" ⭐⭐⭐⭐ | ⭐⭐⭐ (혼동 가능) |
| 언락 | "SW zero로 해제" ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

**학생 막힘 포인트**:
- 🟡 **SC 성공 후 lock이 1이 된다는 설명**: p.565 "lock = 0으로 쓰기 시도 (이 명령어 실행 후 lock이 1이 됨)"
  - **현재**: "이 명령어 실행 후 lock이 1이 됨" ← 잘못된 설명
  - **정정**: "SC.W는 주어진 값(rd=x0=0)을 메모리에 쓰므로 lock = 0이 됨"
  - **임계 영역 진입**: 나머지 코드에서 "lock을 1로 설정"하는 부분이 있어야 함 (현재 없음)
  - **판정**: 🔴 **Critical Error** - 스핀락 동작 설명이 완전하지 않음

**강사 팁 평가** (p.572-575):
```
"왜 재시도하는가" 강조
→ "SC 실패 = 다른 코어가 건드림"
→ "LR부터 다시하는 게 맞다" (메모리 값 변경 가능)
```
- ✅ **교육적 명확성**: ⭐⭐⭐⭐⭐ (정확한 인사이트)
- ✅ **학생 혼동 해결**: LR/SC 의미 명확 ✅

#### 2.2.7 테스트벤치 (p.577-648)

**구조**:
```
시나리오 1: LR → SC 성공 (간섭 없음)
시나리오 2: LR → 스누핑 무효화 → SC 실패
```

**평가**:
- ✅ **명확한 검증**: assert 문으로 성공/실패 조건 검증 ✅
- ✅ **스누핑 시뮬레이션**: snoop_valid/snoop_addr로 다른 코어의 접근 모의
- ✅ **출력 메시지**: 각 시나리오마다 명확한 $display 문

**개선 제안**:
- 💡 시나리오 추가: "같은 코어의 새로운 LR" (예약 대체) 검증

#### 2.2.8 멀티코어 동기화 확장 (p.650-667)

**내용**:
- 뮤텍스: OS 대기 큐 기반 (vs 스핀락의 CPU 낭비)
- 세마포어: 카운터 기반 동기화
- 조건 변수: 특정 조건 대기

**면접 포인트** (p.662-666):
```
Q: "스핀락과 뮤텍스의 차이?"
A: "스핀락 = 루프 반복 (CPU 낭비)
   뮤텍스 = 대기 큐 (휴면)
   짧은 임계 영역: 스핀락 ✓
   긴 임계 영역: 뮤텍스 ✓"
```
- ✅ **정확성**: POSIX 표준과 일치
- ✅ **실무 적용성**: 성능 트레이드오프 명확

#### 2.2.9 Lock-Free 알고리즘 (p.668-722)

**학습 설계**:
```
동기: "락을 사용하지 않고 멀티스레딩 안전성"
    ↓
예: Lock-Free Stack + Compare-and-Swap
    ↓
RISC-V LR/SC 구현 (cas 함수)
    ↓
장점: 성능, 데드락 방지
vs 단점: 복잡성, 불확실성
    ↓
책 범위 밖 (심화 주제)
```

**평가**:
- ✅ **적절한 범위 설정**: "이 책의 범위를 벗어난다" 명시 ✅ (p.722)
- ✅ **연결 고리**: "LR/SC 원리 이해 → 다음 단계로 자연스러운 확장"
- ⭐⭐⭐⭐⭐ **동기 부여**: Compare-and-Swap 예시로 고급 개념 미리 보기

#### 문제 2: 상태 전이 시나리오 (Exclusive → Shared)
```
[이해] Core 0: Exclusive, Core 1: BusRd
→ Core 0과 Core 1의 상태는?
→ Core 0의 버스 동작은?
```
- **블룸 수준**: Understand (2단계)
- **난이도**: 중간
- **정답**:
  - Core 0: Exclusive → Shared
  - Core 1: Invalid → Shared
  - Core 0의 동작: flush 불필요 (Exclusive는 메모리와 동일)
- **채점 용이성**: 🟡 (flush 필요성 판단이 섬세)

**평가**: ⭐⭐⭐⭐ (좋지만 핵심 개념 강조 필요)

- 💡 "flush가 필요한가? 이유는?" 추가 문항

#### 문제 3: T0-T2 시나리오의 MESI 상태 전이
```
[적용] Core 0과 Core 1/2의 초기 상태 → Core 0의 쓰기 까지
```
- **블룸 수준**: Apply (3단계)
- **난이도**: 높음 (여러 상태 추적)
- **정답**:
  - T0: Core 0, 1, 2 모두 읽음 → 상태?
    - 가정: 모두 Miss → Shared (다른 캐시 있음)
  - T1: Core 0 쓰기 → 상태?
    - Core 0: Shared → Modified (BusRdX 방송)
    - Core 1, 2: Shared → Invalid (BusRdX 감시)
  - T2: Core 1 읽음 → 상태?
    - Core 0: Modified (유지)
    - Core 1: Invalid → Shared (Core 0이 flush)

**평가**: ⭐⭐⭐⭐⭐ (실제 상황 추적 능력)

#### 문제 4: LR/SC 주소 불일치
```
[분석] LR.W addr=0x1000, SC.W addr=0x1004
→ SC 성공/실패?
→ 예약 일치 판정 로직 고려
```
- **블룸 수준**: Analyze (4단계)
- **난이도**: 높음
- **정답**:
  - SC 실패 (주소 [31:2] = 0x1000>>2 ≠ 0x1004>>2)
  - 워드 정렬 비교이므로 [1:0] 차이는 무시되나, [3:2] 이상이 다르면 다른 워드
  - 0x1000과 0x1004는 다른 워드 → 실패
- **채점 용이성**: ✅ 명확한 판정 기준

**평가**: ⭐⭐⭐⭐⭐

#### 문제 5: 스핀락 vs 뮤텍스
```
[평가] 임계 영역 100+ 사이클일 때
→ 스핀락 vs 뮤텍스 중 효율적?
→ 에너지, 캐시 일관성 관점
```
- **블룸 수준**: Evaluate (5단계)
- **난이도**: 높음 (트레이드오프 분석)
- **정답**:
  - 뮤텍스 추천
  - 이유: 스핀락은 100+ 사이클 동안 CPU 점유 → 에너지 낭비
  - 뮤텍스는 OS 휴면 → CPU 절약
  - 캐시 일관성: 스핀락의 반복 LR은 BusRd 트래픽 증가 → 뮤텍스가 더 효율적
- **채점 용이성**: 🟡 (정성적 평가, 여러 답 가능)

**평가**: ⭐⭐⭐⭐ (좋은 토론 주제, 채점 기준 명확화 필요)
