## 1. 각 절별 이해도 평가

### 12.1 구조적 해저드: RV32I에서의 발생 조건 ⭐⭐⭐⭐⭐

**평가**: 매우 이해하기 쉬움

- ATM 비유가 구조적 해저드의 본질("하드웨어가 물리적으로 하나뿐인 문제")을 직관적으로 전달.
- 표 형태로 자원별 충돌 조건과 우리 설계 현황을 정리한 것이 탁월. 전체 그림을 한눈에 파악할 수 있음.
- Princeton vs Harvard 구조의 차이를 멀티사이클 CPU(Ch07)와 연결하여 설명한 것이 자연스러움.

- **개선 여지**: 그림 12.1(Princeton 구조 해저드)과 그림 12.2(Harvard 구조 해결)가 SVG 파일로 존재해야 설명을 완전히 이해할 수 있다. 본문 텍스트만으로도 충분하지만, 다이어그램 없이 읽는 상황을 고려하면 "사이클 N+4에 INSTR-1의 MEM과 INSTR-4의 IF가 동시에 접근" 설명이 다소 추상적으로 느껴질 수 있음.

### 12.2 WB-ID 포워딩 (레지스터 파일 포워딩) ⭐⭐⭐⭐⭐

**평가**: 매우 이해하기 쉬움

- "선생님이 칠판에 답을 적는 순간 학생이 칠판에서 읽으려 한다" 비유가 Read-During-Write 상황을 완벽하게 설명.
- "WB-ID 포워딩은 Ch10의 forwarding_unit을 수정하는 것이 아닙니다"라는 안심 문구가 처음부터 제시되어 불필요한 혼란을 예방.
- 포워딩 우선순위 표(EX-EX > MEM-EX > WB-ID)가 전체 포워딩 체계를 명확히 정리.
- 핵심 코드 두 줄과 세 가지 조건 설명이 간결하고 명확.
- FAQ(Write-First 모드 질문)가 실제 의문을 정확히 짚음.
- **개선 여지**: "포워딩 MUX가 개입하기 전 단계"라는 표현이 처음에는 약간 애매하게 느껴짐. "forwarding_unit의 MUX는 EX 스테이지 입력에 위치하지만, WB-ID 충돌은 ID 스테이지에서 발생하므로 forwarding_unit이 개입할 수 없다"는 설명을 한 문장 더 추가하면 완벽할 것.

### 12.3 5단계 파이프라인 통합 ⭐⭐⭐⭐

**평가**: 잘 이해되나 일부 불확실한 지점 존재

- "레고 블록 조립" 비유가 통합 단계의 부담을 크게 낮춰 줌.
- 체크리스트 형태의 통합 전 확인 목록이 실용적이고 현재 위치를 명확히 알 수 있게 해 줌.
- "Ch11과 동일한 포트 연결(포워딩 유닛 수정 없음)" 설명이 예상 불안을 미리 해소.
- 중간 최소 검증 시퀀스를 제공하여 "버블정렬 실패 시 격리" 전략을 알 수 있어 실용적.
- **개선 여지**:
  - `imm_gen`과 `control_unit`이 "Ch11 코드에서 주석 처리되어 있었다"는 언급이 처음 나오는데, 이 사실을 Ch11에서 명시하지 않았다면 독자가 갑자기 혼란스러울 수 있음. Ch11을 직접 집필하지 않은 독자 입장에서 "주석 처리되어 있었다"는 전제가 다소 뜬금없이 느껴짐.
  - 스스로 점검 박스의 질문("`pc_en`, `if_id_en`, `id_ex_flush`, `fwd_a`, `fwd_b` 중 관련된 것을 모두 나열하고 순서를 설명하십시오")이 앞선 장들을 완벽히 기억하지 못하면 답하기 어려울 수 있음. 이 복잡한 질문에 힌트를 하나 더 추가하면 좋겠음.

### 12.4 전체 RV32I 프로그램 실행 검증 ⭐⭐⭐⭐

**평가**: 전반적으로 잘 이해되나 어셈블리 단계 진행이 다소 급함

- 3단계 점진적 접근 방식(2원소 교환 → 내부 루프 → 전체 버블정렬)이 학습 흐름 면에서 이상적.
- 정렬 전후 배열(`[64, 5, 66, 30, 88, 17, 42, 9]` → `[5, 9, 17, 30, 42, 64, 66, 88]`)을 명시적으로 제공하여 목표가 분명.
- BLE가 가상 명령어임을 별도 팁으로 알려주는 것이 실용적이고 중요한 정보.
- **개선 여지**:
  - 단계 2(내부 루프)에서 "가이드 후 작성"이라고 하지만 구체적으로 어디까지 제공하고 어디부터 직접 작성해야 하는지 경계가 불명확. "다음 코드를 완성하라"처럼 빈칸 형태가 있으면 더 명확.
  - 단계 3(전체 버블정렬)의 어셈블리 주석에서 PC 오프셋 값(예: `+0x3C`, `-0x28`, `-0x3C`)이 갑자기 등장. 이 값들을 어떻게 계산하는지 설명이 없어 처음 보는 독자는 어디서 나온 숫자인지 알기 어려움. 한 가지 예시(예: `outer_loop → done` 사이의 바이트 오프셋 계산)를 보여주면 좋겠음.
  - 기계어 초기화 코드(`dut.u_imem.mem[6] = 32'h40B808B3; // SUB x17, x16, x11`) 이후 "// ... (전체 소스 코드 섹션 참조)"로 생략된 부분이 많음. 독자 입장에서 전체 기계어 목록을 보지 않고는 시뮬레이션이 불가능한데, 이 생략이 "지금 이 부분은 참고하지 않아도 된다"는 것인지 "전체 소스 코드 섹션을 보아야 한다"는 것인지 불명확.
  - 테스트벤치 발췌 코드(`repeat(2000) @(posedge clk);`)가 "왜 2000 클럭인가"에 대한 설명 없이 등장. 이전 챕터들에서는 사이클 수 계산 근거를 설명했는데 여기서는 생략됨.

### 12.5 단일 사이클 vs 멀티사이클 vs 파이프라인 3종 비교 ⭐⭐⭐⭐⭐

**평가**: 매우 이해하기 쉽고 흥미로움

- "예측이 맞았습니까?"라는 소크라테스식 질문으로 독자의 사전 예측을 유도한 뒤 실측 데이터를 보여주는 구성이 탁월.
- 실행 시간 = IC × CPI / Fmax 공식이 세 구현의 차이를 수치적으로 명쾌하게 보여줌.
- "파이프라인이 항상 최선인가?" 섹션이 비판적 사고를 길러 줌. 면적, 결정론적 실행, 저전력 세 가지 반례가 설득력 있음.
- 멀티사이클이 Fmax는 2배이지만 CPI가 4배 이상이어서 단일 사이클보다 느리다는 결과가 직관에 반해서 처음에 놀라웠지만, 본문이 이 의외성을 잘 포착하고 있음.
- **개선 여지**: 표의 "실행시간 상대값(~0.82, ~0.22)"이 어떻게 계산되었는지 본문에 수식 전개가 있으면 더 투명. 본문 계산 결과(파이프라인이 단일 사이클 대비 약 2.2배 빠름)와 표의 0.22배(약 4.6배 빠름) 사이의 불일치가 처음 눈에 들어옴. figcaption에서는 "약 4.6배 빠릅니다"라고 하는데 본문은 "약 2.2배"라고 표현 — 이 숫자 차이의 원인(IC 수 차이? 분기 페널티 포함 여부?)을 명확히 설명해야 할 것.

## 2. 전제 지식 점검

### 잘 연결된 부분
- Ch09~Ch11의 핵심 설계 결정(Harvard 구조, EX-EX/MEM-EX 포워딩, flush > stall 우선순위)이 자연스럽게 언급됨.
- Ch10의 `forwarding_unit`이 WB-ID를 처리하지 않는 이유를 명시적으로 설명.
- Ch11의 분기 처리(branch_taken_ex, jal_id, jalr_taken_ex)가 전제 지식으로 사용되는 부분은 MEMORY.md 및 이전 챕터를 읽은 독자라면 이해 가능.

### 잠재적 문제 지점
- **`imm_gen`과 `control_unit` 주석 처리**: Ch11에서 이 두 모듈이 왜 주석 처리되어 있었는지에 대한 설명이 Ch12에만 의존. Ch11을 집필한 에이전트만 이 사실을 알고 있어 독자가 Ch11 원고를 보지 않으면 배경을 알 수 없음. 주석 처리한 이유를 한 문장으로 추가하면 좋겠음 (예: "Ch11에서는 인라인 로직으로 대체하여 모듈 선언을 생략했습니다. Ch12에서는 완전한 모듈 계층을 갖추기 위해 실제 인스턴스화합니다").
- **포워딩 신호 이름**: `fwd_a=2'b10`이 EX-EX, `fwd_a=2'b01`이 MEM-EX라는 할당 관계가 Ch10에서 확정되었는데, Ch12 표에서 그 대응이 다시 명시되어 있어 좋음. 문제없음.
- **`wb_sel` 인코딩(2'b00=ALU, 2'b01=MEM, 2'b10=PC)**: 전체 소스 코드에 등장하는데, 이전 챕터에서 확정된 값이므로 초보자가 갑자기 당황하지는 않음.

## 3. 코드 이해도

### WB-ID 포워딩 코드
- 핵심 두 줄(`assign rs1_data = ...`, `assign rs2_data = ...`)이 간결하고 즉시 이해 가능.
- 세 가지 조건을 번호 매겨 설명한 것이 훌륭.
- **개선 여지**: 전체 소스 코드(ch12_register_file_with_forwarding.sv)에서 `always_ff` 쓰기 블록과 `assign` 읽기 블록이 같이 등장하는데, 초보자가 "동기 쓰기"와 "비동기 읽기"의 동작 타이밍 차이를 이미 알고 있다는 전제가 필요. Ch09에서 이를 배웠으므로 이해 가능하지만, "동기 쓰기 - 비동기 읽기"라는 한 줄 주석이 있어도 좋겠음.

### 버블정렬 어셈블리
- 3단계 점진적 접근이 효과적.
- 단계 1의 2원소 교환은 완전히 이해됨.
- 단계 2의 내부 루프는 레지스터 역할 배분이 명확하여 이해에 도움됨.
- 단계 3의 전체 어셈블리에서 **PC 오프셋 계산 미설명**이 가장 큰 어려움 (특히 점핑 결정 상위 사항: TOP 3에 포함).
- `outer_next: JAL x0, outer_loop # → 0x00C (-0x3C)` — 왜 -0x3C인지 처음 보는 독자에게는 "어떻게 계산했는가"가 불분명.

### 테스트벤치 코드
- `dut.u_imem.mem[]`으로 직접 초기화하는 방식 설명이 간결하고 이전 챕터와 일관됨.
- 검증 출력 형식(PASS/FAIL 텍스트 박스)이 시뮬레이션 결과를 구체적으로 보여 주어 기대감 형성에 효과적.
- **개선 여지**: `repeat(2000) @(posedge clk)` — 2000 클럭이 충분한 이유 설명 필요. 버블정렬의 최악 케이스 사이클 수 계산을 간략히라도 보여주면 독자가 이 숫자를 신뢰할 수 있음.

## 4. SVG 다이어그램 가독성

- 그림 12.1(Princeton 해저드), 12.2(Harvard 해결), 12.3(WB-ID 포워딩), 12.4(완성 파이프라인), 12.5(버블정렬 순서도), 12.6(3종 비교 그래프) — 총 6개 다이어그램이 계획됨.
- SVG 파일이 실제로 존재하는지 확인하지 못한 상태이나, 각 figcaption이 충분히 설명적이어서 내용 이해에 크게 의존하지는 않음.
- **그림 12.4(완성 파이프라인 블록 다이어그램)**: "EX-EX, MEM-EX, WB-ID 세 가지 포워딩 경로와 해저드 제어 유닛이 통합된 완성된 5단계 파이프라인"이라는 설명만으로는 다이어그램이 얼마나 복잡한지 예측 불가. 이 다이어그램이 가장 복잡할 것으로 예상되므로, 본문에서 "이 다이어그램의 어떤 부분을 먼저 확인해야 한다"는 읽기 가이드가 있으면 좋겠음.
- **그림 12.5(버블정렬 순서도)**: figcaption이 "외부 루프(i)와 내부 루프(j)의 조건, 비교, 교환 흐름과 RISC-V 어셈블리 레이블의 대응 관계"라고 설명하고 있어, 어셈블리 레이블과 순서도 블록이 1:1로 매핑되어 있음을 기대할 수 있음. 매핑이 명확하다면 단계 3 어셈블리 이해에 매우 도움될 것.

## 5. 감정 곡선

### 호기심 단계 (챕터 도입, 12.1)
- Ch11에서 x2=55가 나왔던 성취감을 환기하며 시작. "두 조각만 남았다"는 명확한 목표 제시가 강한 동기 부여.
- "감동적인 순간을 경험하게 됩니다"라는 예고가 기대감 형성에 효과적.

### 불안 구간 (12.3 통합, 12.4 버블정렬 어셈블리)
- 12.3에서 긴 변수 선언 목록(전체 소스 코드 섹션의 `logic` 선언들)이 일시적으로 위압감을 줌. 하지만 "레고 블록 조립" 비유와 "이미 여러분이 작성하고 검증한 것들"이라는 안심 문구가 이를 효과적으로 완화.
- 12.4 단계 3의 어셈블리에서 PC 오프셋 숫자들이 나열되는 구간이 가장 불안한 순간. 처음 보는 독자는 "어떻게 이 숫자들을 다 알아야 하지?"라고 느낄 수 있음.
- 기계어 직접 초기화(hex 값들)가 설명 없이 등장하는 구간도 약간 부담스러울 수 있음.

### 이해/성취 단계 (12.4 검증 결과, 12.5 비교, 12.6 마무리)
- [PASS] 메시지와 정렬 결과 출력이 Part 4의 감정적 클라이맥스로 작동. "이것이 하드웨어 설계자가 경험하는 '검증 성공'의 순간입니다"라는 문장이 공감대 형성에 탁월.
- Part 4 완주 인증 박스가 강한 성취감을 제공.
- 캐시 도입 섹션에서 "100사이클 대기 → CPI 폭발"이 경이감과 함께 다음 챕터에 대한 강한 동기를 형성.

### 동기 명확성
- "왜 이것을 배우는가"가 전 절에 걸쳐 일관되게 제시됨. 특히 12.5의 3종 비교가 "왜 파이프라인인가"에 대한 설득력 있는 근거를 데이터로 보여 줌.

## 6. 특히 어려웠던 부분 TOP 3

### TOP 1: 버블정렬 어셈블리의 PC 오프셋 계산 미설명 (12.4절)

> `// BGE x11, x16, +60 (done)` → `// outer_loop (PC=0x00C)` → `// BGE x11, x16, done (PC 0x010 → done 0x04C, +0x3C)`

어셈블리 주석에서 `+60`, `+0x3C`, `-0x28`, `-0x3C` 같은 오프셋 값이 설명 없이 등장한다. 초보자 입장에서는 "이 숫자가 어디서 나왔는가?"라는 질문이 자연스럽게 발생한다. RISC-V B 타입과 J 타입 명령어의 즉치수 인코딩을 이미 Ch04에서 배웠어도, 실제 프로그램에서 레이블을 오프셋으로 변환하는 과정이 명시적으로 설명되지 않아 이해의 공백이 생긴다. 최소한 한 곳(예: `inner_loop → outer_next` 점프의 오프셋 계산)을 단계별로 보여주어야 한다.

### TOP 2: 12.5절 성능 수치 불일치 — "2.2배" vs "4.6배"

> 본문: "파이프라인이 단일 사이클보다 약 2.2배 빠르고"
> figcaption(그림 12.6): "파이프라인이 실행 시간 기준으로 단일 사이클 대비 약 4.6배 빠릅니다"

같은 비교에서 두 가지 다른 숫자가 나온다. 본문 계산(18.5ns vs 40ns → 약 2.16배)과 그래프 figcaption의 4.6배가 왜 다른지 설명이 없다. 처음 읽을 때 "어느 것이 맞는가?" 혼란이 발생한다. IC나 분기 페널티를 포함한 계산인지, 아니면 단순 오류인지 확인이 필요하다.

### TOP 3: 12.3절 `imm_gen`과 `control_unit` 주석 처리 배경 부재

> "Ch11의 rv32i_pipeline_branch에서 imm_gen과 control_unit은 주석 처리되어 있었습니다."

Ch11 원고를 바로 직전에 읽지 않은 독자라면 "왜 주석 처리되어 있었는가?"라는 배경 이해가 없는 상태에서 이 문장을 만나게 된다. Ch11에서 이 두 모듈을 주석 처리한 이유(예: 인라인 로직으로 대체했거나 임시로 생략한 것인지)가 Ch12에서 한 문장으로라도 설명되어야 한다.
