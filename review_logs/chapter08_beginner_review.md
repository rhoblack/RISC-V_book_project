## 절별 이해도 평가

### 8.1절: ⭐⭐⭐⭐⭐ — FSM 개념 도입

도입부의 오케스트라 지휘자 비유가 매우 직관적이다. "데이터패스는 연주자, FSM은 지휘자"라는 구도가
챕터 전체를 관통하는 명확한 멘탈 모델을 제공한다.

- FSM 5요소(S, I, O, δ, λ) 정의를 우리 CPU의 구체적인 값과 바로 연결하여 추상성을 낮춘 점이 우수하다.
- Moore vs Mealy 비교표가 명확하다. "출력이 무엇에 의존하는가"라는 기준을 먼저 제시한 후
  표로 정리하는 구조가 논리적이다.
- FAQ 박스에서 "Moore가 더 느리지 않냐"는 자연스러운 의문을 선제적으로 해소한 점이 좋다.
- 상태 전이도 읽는 법 설명에서 2상태 간단 예시(S0↔S1)를 먼저 제시한 후 17상태로 연결한 점이
  점진적 학습에 효과적이다.
- 명령어별 사이클 수 미리 보기 표(8.1.4)가 전체 구조 파악에 도움이 된다.
  "왜 Branch가 3사이클이지?"라는 궁금증을 유발하고 8.2절을 읽을 동기를 제공한다.

**단, 한 가지 아쉬운 점**: 상태 전이도를 "읽는 법" 설명에서 이중 타원이 초기 상태를 나타낸다고
했지만 실제 그림 8.2(ch08_sec02_fsm_all_states.svg)에서 이중 타원이 사용되는지 본문에 명시되지 않아
독자가 확인하기 어렵다.

### 8.2절: ⭐⭐⭐⭐ — FSM 상태 설계

Gradual Reveal 전략이 효과적으로 구현되었다. "겁먹지 마십시오"라는 안심 문구와
"공통 상태 2개에서 시작"이라는 시작점 제시가 불안 관리에 기여한다.

- 데이터패스 추적 3단계 방법(metacognition 박스)이 모든 상태 설계의 일관된 도구로 제공되어 좋다.
- 각 상태마다 "이유" 열이 있는 제어 신호 표가 단순 암기가 아닌 이해를 유도한다.
- Step 구조(1→2→3→4)로 17개 상태를 점진적으로 추가하는 방식이 압도감을 효과적으로 줄인다.

**어려운 부분 1 — S1(ID) 단계의 ALU 연산 용도 모호함**:
ID 단계에서 alu_src_a=0(PC), alu_src_b=10(imm_ext)으로 설정하는데,
"분기 주소 미리 계산 준비용, 실제 사용 안 함"이라는 설명이 혼란스럽다.
"그러면 왜 설정하는가?"라는 의문이 남는다.
이 계산 결과가 실제로 어디에도 사용되지 않는다면, 기본값(0)으로 두면 안 되는가?
이유를 더 명확히 설명할 필요가 있다.

**어려운 부분 2 — EX_BR 단계의 별도 덧셈기(branch_adder) 개념**:
"데이터패스에 별도의 덧셈기(branch_adder)를 추가해야 합니다"라고 했지만,
이 덧셈기가 Ch07의 데이터패스 어디에 추가되었는지, 언제 추가되었는지가 명확하지 않다.
branch_adder 없이 이 구현이 실제로 동작하는지 독자가 의문을 가질 수 있다.
코드(8.3절 S_EX_BR)에는 "분기 목표(PC+imm_B)는 별도 덧셈기로 계산하여 ALUOut에 저장"이라는
주석만 있고 실제 연결이 없어, 코드가 완전하지 않다는 인상을 준다.

**어려운 부분 3 — JAL의 PC+4 저장 방식**:
"IF 단계에서 이미 PC는 PC+4로 갱신되었으므로, WB_JAL 단계에서 mem_to_reg=10으로
현재 PC 레지스터 값(이미 PC+4)을 rd에 씁니다"는 설명이 다소 불명확하다.
IF 단계에서 PC가 갱신된다면, EX_JAL 단계의 alu_src_a=0(PC)에서 입력되는 PC는
이미 PC+4인가, 아니면 원래 JAL 명령어 주소인가?
PC 레지스터의 타이밍 문제가 초보자에게는 혼란을 줄 수 있다.

### 8.3절: ⭐⭐⭐⭐ — SystemVerilog 구현

- `typedef enum`의 세 가지 이점(가독성, 오타 방지, 유지보수성)을 FAQ로 설명한 점이 좋다.
  특히 파형 뷰어에서 이름이 표시된다는 실무적 이점이 설득력 있다.
- always_ff + always_comb 이중 블록의 역할 분리(순차/조합) 설명이 명확하다.
- 기본값 선설정 패턴과 래치 경고의 관계를 Tip 박스에서 미리 설명하고,
  코드에서 "래치 방지" 주석으로 재확인하는 이중 설명이 효과적이다.

**어려운 부분 4 — 전체 소스 코드 섹션의 압축된 코드**:
8.3.2절의 설명용 코드와 전체 소스 코드 섹션의 코드가 다르다.
전체 소스 코드에서 `{pc_write, ..., pc_src} = '0; branch_taken = 1'b0;` 형태로
concat 기본값 초기화를 사용했는데, 이것이 앞의 개별 할당 방식과 다르다.
또한 전체 소스 코드의 S_ID 상태에서 `alu_src_b=2'b10;`만 설정하고 `alu_src_a`나 `alu_op`는
설정하지 않는데(기본값 0 사용), 이것이 8.2.1절 설명의 값과 달라 혼란을 줄 수 있다.

**어려운 부분 5 — branch_taken의 Moore FSM 예외 처리**:
코드 주석에 "Moore FSM의 예외: branch_taken은 입력 의존이지만..."이라고 했다.
이것이 Moore FSM 원칙 위반 아닌가? 초보자는 "그러면 엄밀히 Mealy FSM인가?"라고
의문을 가질 수 있다. 설계상 타협점을 더 명시적으로 설명해야 한다.

### 8.5절: ⭐⭐⭐⭐⭐ — 성능 비교

- "멀티사이클이 단일 사이클보다 항상 느린가요? 그렇지 않습니다"로 시작하여
  기대와 다른 결과(실제로는 더 느림)를 드라마틱하게 보여주는 구성이 인상적이다.
- CPI 계산식(CPI_avg = Σ(CPI_i × 비율_i))과 구체적 숫자 계산(4.1)이 명확하다.
- Fmax/CPI 비교표에서 3방식(단일/멀티/파이프라인)을 한 눈에 비교할 수 있어 좋다.
- "멀티사이클의 진정한 가치는 처리량이 아니라 자원 절감과 교육적 단계"라는
  솔직한 결론이 교재 신뢰도를 높인다.
- IPC와 CPI의 역수 관계 설명이 간결하고 명확하다.

## 어려운 부분 구체적 지적

1. **ID 단계 ALU 계산 목적 불명확** (8.2절, p.6): alu_src_a=PC, alu_src_b=imm_ext 설정이
   "실제 사용 안 함"이면서도 설정하는 이유가 불명확하다.

2. **Branch 전용 덧셈기 미완성** (8.2.4절, S9): branch_adder의 데이터패스 연결이
   설명되지 않아 구현 코드만으로는 분기 주소 계산이 불가능하다.
   독자가 "이 코드를 그대로 합성하면 동작하는가?"라는 의문을 가질 수 있다.

3. **JAL 단계의 PC 타이밍** (8.2.4절, S13~S14): IF에서 PC가 이미 PC+4로 바뀐 후
   EX_JAL에서 "alu_src_a=PC"가 어느 PC를 의미하는지 혼란스럽다.
   PC_old(JAL 주소)인지 PC_new(PC+4)인지 명시가 필요하다.

4. **전체 소스 코드 concat 초기화** (전체 소스 코드 섹션): 설명용 코드와
   전체 소스 코드의 초기화 방식 불일치가 독자를 혼란스럽게 한다.

5. **branch_taken Moore FSM 예외 처리** (8.3.2절): 별도 always_comb 블록에서
   branch_taken을 입력(funct3)에 의존하여 생성하는 것이 Moore FSM 원칙과 충돌하는 것처럼 보인다.
   더 명확한 설명이 필요하다.

## 설명 없이 등장한 용어

- **글리치(Glitch)** (8.1.2절): "순간적인 신호 변동"이라는 설명이 괄호 안에 제공되어 있어 양호함.
- **Fmax** (8.1.2절 FAQ): 최대 클럭 주파수를 의미한다는 설명 없이 등장.
  처음 나오는 위치이므로 "최대 클럭 주파수(Fmax)"로 병기 필요.
- **imm_U, imm_J, imm_B, imm_S, imm_I** (8.2절 전반): 각 타입별 즉치값 표기를
  처음 사용할 때 "U-type 즉치값(imm_U)"처럼 명시하면 좋겠으나, 이전 챕터(Ch06)에서
  이미 설명되었다면 괜찮다.
- **MIPS** (8.5.4절): 성능 단위 "Millions of Instructions Per Second"의 약어.
  CPI 표에서 갑자기 사용. 프로세서 제품명(MIPS 아키텍처)과 혼동 가능하므로
  최초 등장 시 "MIPS (백만 명령어/초)"로 병기 권장.
- **μop** (8.6절): 마이크로오퍼레이션의 약어. 본문에 "마이크로오퍼레이션(μop)"으로 병기되어 있어 양호.
- **Out-of-Order 실행** (8.5절 면접 포인트): 한글 설명 없이 등장. 초보자에게는
  "비순서 실행(Out-of-Order)"처럼 병기가 필요.
- **Multiple Issue** (8.5절 면접 포인트): "다중 발행(Multiple Issue)"으로 한글이 앞에 오고 있어 양호.
- **branch_adder** (8.2.4절): 별도 덧셈기 이름이 코드 외에는 설명되지 않음.
  데이터패스 그림이나 설명에서 이 요소가 어디에 추가되는지 안내 필요.

## 종합 이해도: ⭐⭐⭐⭐ (4/5)

전체적으로 Ch07의 데이터패스 지식을 전제로 하여 FSM 제어 유닛을 설명하는 구조가 논리적이다.
Gradual Reveal 전략이 17개 상태의 압도감을 효과적으로 줄이며, 각 상태마다 이유 열이 있는
제어 신호 표가 이해를 돕는다. always_ff + always_comb 이중 블록 패턴 설명도 명확하다.

감점 요인:
- Branch 전용 덧셈기(branch_adder) 미완성 — 독자가 이 코드를 실제로 합성할 수 없음
- JAL의 PC 타이밍 설명 불명확
- ID 단계 ALU 설정 목적 불명확
- 설명용 코드와 전체 소스 코드 불일치

이 네 가지를 수정하면 ⭐⭐⭐⭐⭐ 수준에 도달할 수 있다.

## 개선 제안

### 필수 수정 (Must Fix)

1. **Branch 덧셈기 처리 방안 명시**: EX_BR 상태 설명에 "분기 목표 주소 계산은 ID 단계에서
   ALU로 미리 계산(PC+imm_B)하고 별도 레지스터에 저장하는 방식을 사용한다"는 구체적 설계 결정을
   명시하거나, branch_adder 연결을 top 모듈 코드에 추가해야 한다.
   현재 코드로는 분기가 실제로 동작하지 않을 수 있다.

2. **JAL/JALR에서 alu_src_a=PC의 PC 값 명시**: "EX_JAL에서 alu_src_a=0(PC)는
   IF 단계 시작 시점의 PC, 즉 JAL 명령어의 주소(PC_old)이다. IF 단계에서 PC는 PC+4로
   갱신되었지만, ALU 입력 A MUX의 PC 포트는 현재 PC 레지스터(= PC+4)가 아닌
   원래 PC를 별도로 래치한 값을 사용한다" — 또는 데이터패스 설계에서 이를 어떻게 처리하는지 명시.

3. **Fmax 최초 등장 시 풀어쓰기**: "최대 클럭 주파수(Fmax, Maximum operating Frequency)"로
   8.1.2절 FAQ 첫 등장 위치에서 병기.

4. **MIPS 단위 최초 등장 시 병기**: "백만 명령어/초(MIPS, Millions of Instructions Per Second)"로
   8.5.4절 처리량 표에서 첫 등장 위치에 병기. 아키텍처 이름인 MIPS와 혼동을 방지하는 주석 추가.

### 권장 수정 (Should Fix)

5. **ID 단계 ALU 계산 목적 보강**: "ID 단계에서 ALU 설정은 향후 최적화를 위한 준비이며,
   현재 교재 구현에서는 ALUOut 값이 사용되지 않아 기본값과 동일하다. 단, alu_src_a=PC,
   alu_src_b=imm_ext를 설정해 두면 나중에 분기 목표를 여기서 계산하는 최적화 시 수정이 최소화된다"
   와 같은 설명 추가.

6. **branch_taken Moore FSM 예외 명확화**: "엄밀히 말하면 branch_taken은 입력(funct3)에 의존하므로
   Mealy 출력이다. 하지만 branch_taken은 pc_write_cond와 AND되어 최종 PC 쓰기를 제어하며,
   이 AND 게이트를 FSM 외부로 분리하여 FSM 본체는 여전히 Moore 원칙을 유지한다"는
   설명 추가.

7. **전체 소스 코드와 설명용 코드 일관성**: 전체 소스 코드 섹션 도입부에
   "이 코드는 설명용 코드를 압축한 버전입니다. concat 초기화(`'0`)는 개별 초기화와 동일하게 동작합니다"
   라는 안내 추가.
