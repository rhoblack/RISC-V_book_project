## 0. 검토 개요

Chapter 08은 Part 3의 완결 챕터로, Ch07에서 설계한 멀티사이클 데이터패스를 "지휘"하는 FSM 제어 유닛을 완성한다. 이 챕터의 교육적 성패는 세 가지 축에 달려 있다.

1. **FSM 설계 자체**: Verilog 경험자에게 FSM은 친숙한 패턴이다. 단, 이중 always 블록 패턴(`always_ff` + `always_comb`)과 상태별 출력 신호를 혼동 없이 구현하는 것이 핵심이다.
2. **멀티사이클 전체 통합**: 데이터패스(Ch07)와 FSM 제어 유닛(Ch08)이 결합되어 처음으로 완전한 RV32I CPU가 동작하는 마일스톤. 수강생의 성취감이 집중되는 구간이다.
3. **파이프라인으로의 연결 고리**: FSM 각 상태(IF/ID/EX/MEM/WB)가 파이프라인의 각 스테이지와 1:1 대응된다는 통찰을 이 챕터에서 심어야, Ch09(파이프라인 기초)의 진입 장벽이 현저히 낮아진다.

수강생의 현재 심리 상태: **Ch07 데이터패스 완성 후 "이제 FSM만 붙이면 되겠구나"라는 자신감 지속 상태**. FSM은 Verilog 수업에서 이미 다뤄본 패턴이므로 심리적 부담이 낮다. TABLE_OF_CONTENTS.md의 "에너지 비축 구간" 설계 의도와 정확히 맞아떨어지는 상태이다.

## 1. 비유 검증

### 비유 1: 교통 신호 제어기 (Moore FSM)

**기술적 매핑**:

| 하드웨어 개념 | 교통 신호 비유 | 정확도 |
|------------|-------------|:-----:|
| FSM 상태 (IF, ID, EX, MEM, WB) | 신호등 상태 (적색, 황색, 녹색, ...) | ✅ 정확 |
| 상태 전이 (next_state 로직) | 타이머 또는 감지기에 따른 신호 전환 | ✅ 정확 |
| 상태 출력 (제어 신호) | 각 신호 상태에서의 출력 (정지/진행 신호) | ✅ 정확 |
| Moore FSM: 출력이 현재 상태만으로 결정 | 신호등이 현재 상태에 따라 색상 출력 (입력 무관) | ✅ 정확 |
| 명령어 타입에 따른 상태 분기 | 도로 상황에 따른 신호 패턴 변경 | ⚠️ 부분 |
| 상태 전이 조건 (`opcode`, `funct3`) | 감지기(차량 유무)에 해당 | ✅ 정확 |

**비유의 한계 (반드시 명시)**:

1. **상태 수 불일치**: 교통 신호는 보통 3~4개 상태이지만, 멀티사이클 FSM은 명령어 타입에 따라 10개 이상의 상태를 갖는다. 수강생이 "신호등처럼 단순하겠지"라고 기대하다가 실제 상태 전이도를 보면 복잡도에 충격을 받을 수 있다.

2. **동일 사이클 길이 표현 어려움**: 교통 신호는 각 상태의 유지 시간이 다를 수 있지만(30초 적색, 20초 녹색), 멀티사이클 FSM의 각 상태는 정확히 한 클럭 사이클을 차지한다. 이 차이가 명시되지 않으면 "각 FSM 상태의 지속 시간이 다르다"는 오해로 이어진다.

3. **Moore vs Mealy 구분의 교통 신호 표현 한계**: 교통 신호는 순수 Moore FSM이지만, 실제 제어 유닛의 일부 구현은 Mealy 방식을 섞을 수 있다. 비유가 Moore FSM에 고정되어 있어, Mealy에 대한 설명이 필요할 경우 비유를 교체해야 한다.

**결론**: 사용 권장. 단, "상태 수가 훨씬 많고, 각 상태는 정확히 1클럭 사이클을 차지한다"는 두 가지 한계를 비유 직후에 명시할 것. Moore FSM 설명에 집중하고, Mealy FSM 설명 시에는 별도 비유 사용.

### 비유 2: 지휘자

**기술적 매핑**:

| 하드웨어 개념 | 지휘자 비유 | 정확도 |
|------------|----------|:-----:|
| FSM 제어 유닛 | 지휘자 | ✅ 정확 |
| 데이터패스 모듈 (ALU, 레지스터 파일, 메모리) | 악기 섹션 (현악, 관악, 타악) | ✅ 정확 |
| 클럭 사이클 (박자) | 지휘봉의 박자 | ✅ 정확 |
| 상태별 제어 신호 | 각 박자에서 어떤 섹션이 연주할지 지시 | ✅ 정확 |
| 명령어 (악보) | 지휘자가 읽는 악보 | ✅ 정확 |
| 명령어 타입별 상태 분기 | 악보에 따라 연주 순서 변경 | ✅ 정확 |
| 데이터패스가 실제 연산을 수행 | 악기 섹션이 실제로 소리를 냄 | ✅ 정확 |

**비유의 한계 (반드시 명시)**:

1. **동시 연주 불가 표현**: 지휘자는 여러 악기 섹션이 동시에 연주하도록 지시할 수 있지만, 멀티사이클 FSM의 각 사이클에서는 한 번에 하나의 단계만 수행된다. 단, 같은 사이클 내에서 레지스터 읽기와 ALU 입력 선택 등이 동시에 일어나므로, "같은 박자에서 여러 신호가 동시 출력된다"는 것은 정확하다. 혼동이 올 수 있으므로 명시 필요.

2. **파이프라인과의 혼동 위험**: 파이프라인을 "여러 악기 섹션이 동시에 서로 다른 악보를 연주하는 것"으로 비유할 경우, 이 지휘자 비유와 충돌 가능성이 있다. 파이프라인 설명 시 비유를 교체하거나 명확한 구분 문장 필요.

3. **FSM 상태 전이의 동적 결정 표현 한계**: 지휘자는 악보대로 고정적으로 지휘하지만, FSM은 명령어 타입에 따라 상태 경로를 동적으로 선택한다. "악보의 종류(장르)에 따라 연주 순서가 달라진다"는 보조 설명으로 해결 가능.

**결론**: 사용 적극 권장. 직관적이고 시각적이며, "지휘자는 연주하지 않고 지시만 한다(FSM은 연산을 하지 않고 제어 신호를 출력한다)"는 핵심을 명확하게 전달한다. 파이프라인 비유와의 충돌 방지를 위해 Ch08에서는 이 비유를, Ch09에서는 다른 비유("여러 명령어가 동시에 서로 다른 스테이지")를 사용하는 것을 권장.

| 하드와이어드 제어 | 요리사가 레시피를 외워서 실행 | ✅ 정확 |

**비유의 한계 (반드시 명시)**:

2. **Ch07 비유와의 중복**: Ch07에서 이미 "코스 요리" 비유를 사용했다. 조리 순서표 비유는 유사한 도메인이므로 수강생에게 새로운 통찰을 주기 어려울 수 있다.

3. **병렬성 표현 어려움**: 레시피는 선형 순서이지만, 하드웨어에서는 같은 사이클 내 여러 신호가 동시 출력된다.

**결론**: 8.6절 마이크로프로그래밍 설명에 제한적으로 사용 권장. "레시피를 외워서 실행 = 하드와이어드", "레시피를 책에서 읽어 실행 = 마이크로프로그래밍"의 대비가 탁월하다. 전체 FSM 설명의 주 비유로는 부적합. 지휘자 비유를 주 비유로 사용하고, 조리 순서표 비유는 8.6절 보조 비유로 배치할 것.

## 2. 수강생 막힘 포인트 예측

### [막힘 #1] FSM의 세 가지 always 블록 패턴 혼동 — "어느 블록에 무엇을 쓰는가?" (8.3절)

**막힘 원인 분석**:

Verilog 경험자는 FSM을 구현해봤지만, 구현 패턴이 제각각이다. 일반적인 혼동 유형:

- 1-always 패턴: 상태 전이와 출력을 모두 하나의 `always` 블록에서 처리
- 2-always 패턴: `always_ff`(상태 레지스터) + `always_comb`(next_state + output)
- 3-always 패턴: `always_ff`(상태 레지스터) + `always_comb`(next_state) + `always_comb`(output)

SystemVerilog에서 합성 가능한 패턴은 이 중 **2-always 또는 3-always**이다. 1-always 패턴은 래치(latch)를 생성할 수 있어 합성 문제가 발생한다.

수강생이 이전에 배운 패턴이 다르면, 교재의 패턴이 "틀린 것 같다"는 혼동이 생긴다.

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "선생님, 저는 Verilog에서 FSM을 always 블록 하나에 다 넣었는데 동작했어요. 왜 교재는 두 개로 나누나요? 더 복잡한 거 아닌가요?"

> "always_comb 블록에서 case(state)로 출력 신호를 결정하는데, default를 빼면 래치가 생긴다고 Vivado가 경고합니다. 왜 그런가요?"

**사전 해소 전략**: 8.3절 도입부에서 FSM 구현 패턴 3가지를 표로 비교하고, "이 교재에서는 2-always 패턴을 사용하는 이유"를 명시한다. `always_comb`의 완전 할당 규칙(모든 경우에 모든 출력 신호를 할당해야 래치가 생기지 않음)을 예제 코드와 함께 설명한다.

**권장 aside 박스**: `<aside class="instructor-tip">` — "FSM 패턴 3가지 중 합성 가능한 패턴과 그 이유"

### [막힘 #2] 상태별 제어 신호 배정 — "어떤 상태에서 어떤 신호를 켜야 하는가?" (8.2절)

**막힘 원인 분석**:

멀티사이클 FSM에서 각 상태(IF, ID, EX, MEM, WB)에서 활성화해야 할 제어 신호가 10개 내외이다. 수강생이 각 상태별 제어 신호를 처음 보면:

- "신호가 너무 많다" — 인지 과부하
- "어떤 원칙으로 신호를 켜고 끄는지 모르겠다" — 원리 미파악
- "외워야 하는 것처럼 느껴진다" — 잘못된 학습 전략으로 빠짐

핵심은 "각 상태에서 데이터패스의 어느 부분이 활성화되어야 하는지를 타이밍 다이어그램에서 추적하면, 제어 신호는 자연스럽게 결정된다"는 것이다.

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "IF 상태에서 `mem_read=1`을 켜야 한다는 건 알겠는데, `alu_src_a`는 왜 PC를 선택해야 하고, `alu_src_b`는 왜 4를 선택해야 하나요? 어디서 이걸 유도하나요?"

**사전 해소 전략**: "제어 신호 설계의 3단계 방법론"을 8.2절 시작 시 제시한다:

1. 해당 상태에서 데이터가 어느 경로로 흘러야 하는지 데이터패스 SVG에서 추적한다.
2. 그 경로를 따라 각 MUX의 선택 신호를 결정한다.
3. 활성화해야 할 레지스터/메모리 제어 신호를 결정한다.

이 방법론을 IF 상태에 대해 예시로 완전히 보여준 다음, ID, EX, MEM, WB를 수강생이 직접 유도하도록 연습 문제를 배치한다.

**권장 aside 박스**: `<aside class="metacognition">` — "제어 신호를 외우지 말고 유도하는 방법"

### [막힘 #3] 명령어 타입별 상태 경로 분기 — "왜 R-type은 4사이클이고 Load는 5사이클인가?" (8.2절)

**막힘 원인 분석**:

R-type: IF → ID → EX → WB (4사이클)
Load: IF → ID → EX → MEM → WB (5사이클)
Store: IF → ID → EX → MEM (4사이클)
Branch: IF → ID → EX (3사이클)
Jump: IF → ID → EX → WB (4사이클, Branch와 유사하지만 WB 필요)

이 경로의 차이가 왜 발생하는지, 그리고 FSM에서 이 분기를 어떻게 구현하는지를 이해하지 못하면 상태 전이도를 단순히 외우는 수준에 머문다.

수강생이 특히 혼동하는 지점:

- Store는 레지스터에 쓰지 않으므로 WB 상태가 없다 → 이해하기 쉬운 편
- Branch는 PC 갱신만 하므로 WB 상태가 없다 → 이해하기 쉬운 편
- **R-type과 Load/Store 분기**: EX 이후, `opcode`에 따라 MEM으로 갈지 WB로 바로 갈지 결정 → 혼동 발생
- **JAL/JALR의 상태 경로**: Ch07 final_approval에서 지적된 `pc_src` 재정의 이슈가 있음 (Ch08에서 해결 필요)

**막힘 구체화**: 수강생이 물어볼 전형적 질문

> "EX 상태 다음에 어떤 명령어는 MEM으로 가고 어떤 명령어는 WB로 바로 가는데, FSM 코드에서 이 분기를 어떻게 구현하나요? next_state 로직에서 opcode를 확인하나요?"

**사전 해소 전략**: 8.2절에 "명령어 타입별 상태 경로 지도" SVG를 배치한다. 각 명령어 타입의 상태 경로를 색상으로 구분하여 한눈에 비교할 수 있게 한다. FSM 코드에서 `opcode` 기반 상태 분기 로직을 IF 상태 직후와 EX 상태 직후에 대해 명시한다.

**권장 aside 박스**: `<aside class="faq">` — "R-type과 Load의 사이클 수가 다른 이유 — 상태 경로 비교"

### [막힘 #4] Moore FSM vs Mealy FSM 선택 — "어떤 것을 써야 하나?" (8.1절)

**막힘 원인 분석**:

수강생이 Moore와 Mealy를 이론적으로 배웠더라도, "멀티사이클 제어 유닛을 실제로 구현할 때 어느 것을 써야 하는가"에 대한 실무적 답이 없으면 혼동이 생긴다.

Moore FSM을 쓰면:
- 출력이 현재 상태만으로 결정 → 예측 가능하고 타이밍이 안정적
- 상태 수가 많아질 수 있음

Mealy FSM을 쓰면:
- 출력이 현재 상태 + 현재 입력으로 결정 → 상태 수를 줄일 수 있음
- 조합 논리 경로가 길어져 타이밍 마진이 줄어들 수 있음

교재에서는 Moore FSM을 선택하는 것이 적합하지만, 그 이유를 명시하지 않으면 수강생은 "왜 Mealy를 안 쓰나요?"라고 질문한다.

**막힘 구체화**:

> "교수님, Moore FSM과 Mealy FSM 중 어느 게 더 좋은 건가요? 교재에서는 Moore만 쓰는데, 실무에서도 Moore만 쓰나요?"

**사전 해소 전략**: 8.1절에서 Moore/Mealy 선택 기준을 "합성 가능성 + 타이밍 안전성" 관점에서 설명한다. 멀티사이클 제어 유닛은 Moore FSM이 적합한 이유를 타이밍 다이어그램으로 보여준다. 단, "실무에서는 Mealy도 사용하며 상태 수를 줄이는 경우가 있다"고 언급하여 지식 완결성을 확보한다.

**권장 aside 박스**: `<aside class="faq">` — "Moore vs Mealy — 왜 멀티사이클 제어 유닛에 Moore FSM을 선택하는가"

---

### [막힘 #5] JAL/JALR 처리 — "점프 명령어의 FSM 상태 경로는?" (8.2~8.3절)

**막힘 원인 분석**:

Ch07 final_approval에서 이미 지적된 이슈: JAL은 `pc_src=2'b01`(ALUOut)을 사용하며, JALR은 `A + imm_I` 계산 후 하위 1비트를 클리어해야 한다. 이 세부 사항을 FSM 상태 전이도와 제어 신호 테이블에 정확히 반영하지 않으면, 수강생이 JAL/JALR의 상태 경로를 이해하기 어렵다.

수강생이 특히 혼동하는 것:
- JAL과 JALR의 상태 경로 차이 (JAL: IF→ID→EX→WB, JALR: IF→ID→EX→WB이지만 EX에서 다른 ALU 연산)
- `rd`에 `PC+4`를 저장하는 WB 동작이 R-type WB와 같은 상태를 공유할 수 있는지

**사전 해소 전략**: JAL과 JALR을 별도 행으로 분리한 "명령어별 상태/제어 신호 진리표"를 8.2절에 배치한다. Ch07 final_approval의 인수인계 사항을 반영하여 `pc_src` 재정의를 명확히 한다.

**권장 aside 박스**: `<aside class="instructor-tip">` — "JAL과 JALR의 FSM 처리 — Ch07 데이터패스와의 연결"

```html
<aside class="faq">
  <h4>❓ 수강생 단골 질문</h4>
  <p><strong>Q</strong>: Moore FSM과 Mealy FSM의 차이가 뭔가요? 멀티사이클 제어 유닛에 왜 Moore FSM을 쓰나요?</p>
  <p><strong>A</strong>:</p>
  <ul>
    <li><strong>Moore FSM</strong>: 출력(제어 신호)이 현재 상태(state)만으로 결정됩니다. 입력(opcode 등)은 상태 전이에만 영향을 줍니다.</li>
    <li><strong>Mealy FSM</strong>: 출력이 현재 상태와 현재 입력 모두에 의해 결정됩니다. 상태 수는 줄일 수 있지만, 조합 논리 경로가 길어집니다.</li>

</aside>
```

### Q&A #2 — 8.3절 배치 권장

```html
<aside class="faq">
  <h4>❓ 수강생 단골 질문</h4>
  <p><strong>Q</strong>: <code>always_comb</code> 블록에서 <code>default</code>를 쓰지 않으면 왜 Vivado가 래치 경고를 내나요?</p>
  <p><strong>A</strong>: <code>always_comb</code> 블록은 조합 논리를 기술하는 블록입니다. 조합 논리에서 래치(latch)가 생기는 것은 출력 신호가 모든 입력 조합에 대해 명시적으로 할당되지 않았을 때입니다. 예를 들어, <code>case(state)</code>에서 특정 상태에 대한 처리가 누락되면, 해당 상태에서 출력 신호는 이전 값을 유지해야 합니다 — 이것이 래치입니다.</p>
  <p>해결 방법은 두 가지입니다:</p>
  <ol>
    <li><code>case</code> 문 진입 전에 모든 출력 신호에 기본값을 할당합니다 (권장).</li>
    <li><code>case</code> 문에 <code>default</code> 브랜치를 추가하여 모든 신호를 할당합니다.</li>
  </ol>
  <p>이 교재에서는 방법 1을 사용합니다. <code>always_comb</code> 블록 시작 시 모든 제어 신호를 0으로 초기화한 뒤, <code>case(state)</code>에서 필요한 신호만 1로 설정합니다. 이 방식이 코드 가독성과 안전성 모두에서 우수합니다.</p>
</aside>
```

### Q&A #3 — 8.5절 배치 권장

```html
<aside class="faq">
  <h4>❓ 수강생 단골 질문</h4>
  <p><strong>Q</strong>: CPI가 1보다 크면 단일 사이클보다 느린 거 아닌가요? 멀티사이클이 단일 사이클보다 빠르다는 게 이해가 안 됩니다.</p>
  <p><strong>A</strong>: CPI(Clock Per Instruction, 명령어당 사이클 수)만 보면 멀티사이클이 불리해 보이지만, 전체 실행 시간은 다음 식으로 결정됩니다:</p>
  <p><code>실행 시간 = 명령어 수 × CPI × 클럭 주기</code></p>
  <p>멀티사이클에서는 CPI가 증가하지만 클럭 주기가 단축됩니다. 예를 들어:</p>
  <ul>
    <li>단일 사이클: CPI=1, 클럭 주기=33ns (30MHz) → 명령어당 33ns</li>
    <li>멀티사이클 R-type: CPI=4, 클럭 주기=10ns (100MHz) → 명령어당 40ns</li>
    <li>멀티사이클 Load: CPI=5, 클럭 주기=10ns (100MHz) → 명령어당 50ns</li>
  </ul>
  <p>이 예에서 R-type은 멀티사이클이 약간 느리지만, Load는 단일 사이클(33ns)보다 오히려 느립니다. 즉, 멀티사이클의 이득은 조건부입니다. 실제 클럭 주파수 향상 비율이 CPI 증가 비율보다 클 때, 그리고 명령어 믹스에 빠른 명령어(Branch 3사이클)가 많을 때 멀티사이클이 유리합니다. 이 트레이드오프 분석이 8.5절의 핵심 내용입니다.</p>
</aside>
```

## 4. 면접 포인트: 하드와이어드 vs 마이크로프로그래밍

### 4.1 면접 질문 및 모범 답안 가이드

```html
<aside class="interview">
  <h4>🎯 면접 포인트 #11 (반도체/설계 직군 빈출)</h4>
  <p><strong>Q: 하드와이어드 제어(Hardwired Control)와 마이크로프로그래밍 제어(Microprogramming Control)의 차이를 설명하고, 각각의 장단점을 비교하시오.</strong></p>

  <p><strong>핵심 답변 구조 (3분 이내)</strong>:</p>

  <p><strong>1. 정의</strong></p>
  <ul>
    <li><strong>하드와이어드 제어</strong>: FSM과 조합 논리 회로로 제어 신호를 직접 생성. 현재 상태와 명령어 opcode에 따라 제어 신호가 즉시 결정됨.</li>
    <li><strong>마이크로프로그래밍 제어</strong>: 각 상태의 제어 신호를 마이크로코드 ROM에 저장. 현재 상태를 ROM 주소로 사용하여 제어 신호를 읽어옴. 제어 신호의 집합을 마이크로명령어(microinstruction)라고 부름.</li>
  </ul>

  <p><strong>2. 장단점 비교</strong></p>
  <table>
    <tr><th>항목</th><th>하드와이어드</th><th>마이크로프로그래밍</th></tr>
    <tr><td>속도</td><td>빠름 (ROM 읽기 없음)</td><td>느림 (ROM 접근 1사이클 추가)</td></tr>
    <tr><td>설계 복잡도</td><td>높음 (조합 논리 직접 설계)</td><td>낮음 (ROM 내용만 수정)</td></tr>
    <tr><td>유연성/수정 용이성</td><td>낮음 (회로 재설계 필요)</td><td>높음 (ROM 내용만 수정)</td></tr>
    <tr><td>면적</td><td>작음 (단순 ISA)</td><td>큼 (ROM 추가)</td></tr>
    <tr><td>적합 ISA</td><td>RISC (단순, 고정 길이)</td><td>CISC (복잡, 가변 길이)</td></tr>
  </table>

  <p><strong>3. 실제 사례</strong></p>
  <ul>
    <li><strong>하드와이어드</strong>: ARM Cortex-M, RISC-V 코어, MIPS R3000</li>
    <li><strong>마이크로프로그래밍</strong>: 인텔 x86 초기 구현. 현대 x86은 하드와이어드로 마이크로 연산을 처리하고, 복잡한 x86 명령어만 마이크로코드 ROM으로 처리하는 하이브리드 방식.</li>
  </ul>

  <p><strong>4. RV32I에서의 선택 근거</strong></p>
  <p>RV32I는 37개의 고정 길이(32비트) 명령어만을 가지며, 모든 명령어가 단순한 패턴을 따릅니다. 따라서 하드와이어드 제어가 적합합니다. 마이크로프로그래밍을 선택하면 ROM 접근 오버헤드가 추가되어 성능 손실이 발생하며, 유연성 이점을 활용할 ISA 복잡도도 없습니다.</p>
</aside>
```

### 4.2 면접 답변 시 흔한 실수

강의에서 반드시 짚어줄 수강생 실수 패턴:

1. **"마이크로프로그래밍이 느리다고만 말하고 ROM 읽기 오버헤드를 설명 못함"** → ROM 접근이 추가 지연/사이클을 발생시키는 구체적 이유를 설명해야 함.
2. **"현대 x86이 마이크로프로그래밍만 쓴다고 오해"** → 현대 x86은 하이브리드. 단순 명령어는 하드와이어드로 처리하고 복잡한 명령어만 마이크로코드로 처리함.
3. **"RISC vs CISC 차이를 언급하지 않음"** → 마이크로프로그래밍이 CISC에서 선호된 역사적 이유를 반드시 포함해야 완성도 있는 답변이 됨.
4. **"하드와이어드를 설명하면서 FSM이라고만 하고 구체적 구현 언급 없음"** → "현재 상태와 opcode를 입력으로 받아 조합 논리 회로로 제어 신호를 즉시 출력"이라는 구체적 설명 필요.

### 5.4 강사 주의 사항: 수강생이 가장 많이 막히는 순간

1. **8.3절 `always_comb` 출력 블록 작성 시**: `default` 없이 코드를 작성하면 Vivado가 래치 경고를 낸다. 강사가 의도적으로 먼저 실수를 보여준 뒤 수정하는 방식이 효과적이다.
2. **8.4절 파형 분석 시**: 상태 레지스터가 실제로 IF→ID→EX→WB 순서로 전이하는 것을 파형에서 확인할 때, 상태 인코딩이 binary인지 one-hot인지에 따라 파형 읽는 방법이 다르다. 사전에 파라미터로 상태 이름을 정의해두면 파형 분석이 쉬워짐을 보여줄 것.
3. **8.5절 성능 비교 계산 시**: 수강생이 "멀티사이클이 단일 사이클보다 느릴 수도 있다"는 결과를 보면 당혹감을 느낄 수 있다. "이것이 파이프라인이 필요한 이유"로 프레이밍하여 Ch09 동기 부여로 연결할 것.

## 6. 파이프라인 연결 고리 설명 가이드

### 6.1 핵심 통찰: "멀티사이클 FSM 상태 = 파이프라인 스테이지"

이 통찰은 Ch09 진입의 핵심 열쇠이다. 8.7절(요약 및 다음 단계)에서 반드시 다음 방식으로 전달해야 한다.

**Step 1 — 멀티사이클 FSM 상태도 제시**:

```
명령어 1: IF → ID → EX → WB
명령어 2:              IF → ID → EX → WB
명령어 3:                        IF → ID → EX → WB
```

멀티사이클에서는 명령어 1이 완전히 끝난 후에야 명령어 2가 시작됨을 사이클 타이밍 다이어그램으로 보여준다.

**Step 2 — "동시에 실행하면 어떻게 되는가" 질문 제기**:

> "명령어 1이 EX 상태에 있을 때, IF 하드웨어는 놀고 있습니다. 명령어 2를 지금 IF 단계에서 시작할 수 없을까요?"

**Step 3 — 파이프라인 타이밍 다이어그램 제시**:

```
명령어 1: IF → ID → EX → WB
명령어 2:      IF → ID → EX → WB
명령어 3:           IF → ID → EX → WB
명령어 4:                IF → ID → EX → WB
```

> "이것이 파이프라인입니다. FSM의 각 상태가 동시에 실행되는 것입니다. 단, 이를 위해 각 상태의 결과를 다음 상태로 전달하는 레지스터가 필요합니다 — 이것이 파이프라인 레지스터입니다."

**Step 4 — 멀티사이클 중간 레지스터와 파이프라인 레지스터 대응 제시**:

| 멀티사이클 중간 레지스터 | 파이프라인 레지스터 | 역할 |
|---------------------|------------------|------|
| IR (Instruction Register) | IF/ID 레지스터 | IF에서 읽은 명령어를 ID로 전달 |
| A, B 레지스터 | ID/EX 레지스터의 rs1, rs2 필드 | ID에서 읽은 레지스터 값을 EX로 전달 |
| ALUOut 레지스터 | EX/MEM 레지스터의 alu_result 필드 | EX 결과를 MEM으로 전달 |
| MDR | MEM/WB 레지스터의 mem_data 필드 | MEM에서 읽은 데이터를 WB로 전달 |

> "Ch07에서 만든 중간 레지스터들이 사실 파이프라인 레지스터의 원형이었습니다. Ch09에서는 이 레지스터들을 분리하여 여러 명령어가 동시에 사용하도록 확장합니다."

---

### 6.2 강의 현장에서의 감정 곡선 관리

파이프라인 연결 고리 설명 시 수강생의 반응 예측:

- **"아, 그래서 Ch07이 필요했구나!"** — 이 반응이 목표. 멀티사이클 학습의 교육적 의의가 사후 정당화됨.
- **"파이프라인이 생각보다 어렵지 않겠는데요?"** — 이 반응은 과도한 자신감으로 이어질 수 있음. "파이프라인에는 해저드(Hazard)라는 새로운 도전이 있습니다"로 적절히 조율할 것.
- **"그럼 Ch07~08을 안 배워도 파이프라인은 이해할 수 있을 것 같은데요?"** — 이 반응에는 "해저드 해결이 핵심이고, 해저드를 이해하려면 각 스테이지에서 무슨 일이 일어나는지 알아야 합니다. 그것을 FSM으로 정확히 배웠습니다"로 응답.
