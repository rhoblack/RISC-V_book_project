## 2. 이슈 충돌 해결 기록

### 충돌 1: EX/MEM 레지스터 — 연습문제 유도 vs. 전체 소스 포함

- **기술 리뷰어**: 전체 소스 코드 절에 `ex_mem_reg.sv` 구현 코드를 포함해야 함 (Critical)
- **초보자 독자**: 연습문제로 유도하는 의도인지 누락인지 불명확함
- **교육 설계자**: 9.4절에서 핵심 신호 목록이라도 제시하면 학습 흐름이 완결됨

**편집장 결정**: **정확성 우선** — 전체 소스 코드 절에 `ex_mem_reg` 구현 코드를 포함한다. 9.4절에서는 "EX/MEM과 MEM/WB 레지스터도 동일한 패턴으로 구현합니다. 독자가 직접 구현 실습 후, 전체 소스 코드 절의 참고 구현을 확인하십시오"라는 안내 문구로 교육적 의도를 유지한다.

---

### 충돌 2: `mem_wb_reg` flush 포트 — 포트 추가 vs. 설계 근거 명시

- **기술 리뷰어**: 포트를 추가하거나 생략 근거를 명시 (Critical)
- **교육심리전문가**: 9.4절 FAQ에 이미 'flush 포트 미사용 이유'가 설명되어 있음 (PASS 판정)

**편집장 결정**: 심리적 안전성 설계(FAQ 박스 존재)와 기술 정확성(설계 일관성)을 동시에 충족하는 방향을 채택한다. **기존 FAQ 박스를 확장하여** "MEM/WB 레지스터는 분기 flush의 전파 경계 밖에 있습니다 — MEM 스테이지까지 진행된 명령어는 완료를 허용하는 것이 일반적 설계 관행입니다"를 추가한다. flush 포트는 추가하지 않으며, 이 설계 결정을 명시적으로 문서화한다.

---

### 충돌 3: LO-7 — 새 학습 목표 추가 vs. LO 수 조정

- **교육 설계자**: LO-7 추가 또는 LO-6 분리 (Major)
- **나머지 리뷰어**: 이슈 없음

**편집장 결정**: LO-6("파이프라인 해저드의 존재를 인식하고 해결 방향을 설명할 수 있다")을 두 개로 분리하여 LO-6과 LO-7로 구성한다. 추가 분량 없이 기획 문서 정합성을 회복하는 가장 간결한 방법이다.

### [Critical] 반드시 수정할 사항 — 2건

#### C-2: `mem_wb_reg` flush 포트 — 설계 근거 명시

**위치**: 9.4절 `mem_wb_reg` 코드 직후의 FAQ aside 박스

**수정 방향**: 기존 FAQ aside("flush 포트를 선언해놓고 왜 Ch09에서 사용하지 않나요?")에 다음 내용을 추가한다.

> 추가할 설명 요지: "MEM/WB 레지스터에는 flush 포트를 선언하지 않습니다. MEM 스테이지까지 진행된 명령어는 이미 데이터 메모리 접근을 완료하였으므로, 이를 취소하는 것은 설계상 허용하지 않습니다. 분기 예측 실패 시 flush 대상은 IF/ID, ID/EX, EX/MEM 레지스터이며, MEM/WB는 flush 경계 밖에 있습니다. 이것은 의도적 설계 결정입니다."

**검증 기준**: `if_id_reg`(flush 있음), `id_ex_reg`(flush 있음), `ex_mem_reg`(flush 있음 — C-3 추가 후), `mem_wb_reg`(flush 없음, 설계 근거 FAQ에 명시) 형태의 일관된 패턴이 완성되어야 한다.

---

#### C-3: `ex_mem_reg` 구현 코드 추가

**위치**: 전체 소스 코드 절 (`ex_mem_reg.sv` 섹션 신규 추가)

**수정 방향**: 전체 소스 코드 절에 `ex_mem_reg.sv` 완전한 SystemVerilog 구현을 추가한다. `mem_wb_reg.sv`와 동일한 패턴(`always_ff`, 동기 리셋, NOP 버블 처리)을 따르며, EX/MEM 레지스터가 전달해야 하는 필드(alu_result, mem_write_data, rd_addr, ctrl_t의 MEM/WB 관련 필드, pc_plus4, branch_taken 등)를 포함한다.

**9.4절 안내 문구 수정**: "EX/MEM과 MEM/WB 레지스터도 동일한 패턴으로 구현합니다. 각 레지스터가 전달해야 하는 필드 목록은 그림 9.7을 참조하십시오."를 다음과 같이 수정한다.

> "EX/MEM과 MEM/WB 레지스터도 동일한 패턴으로 구현합니다. 먼저 그림 9.7을 참조하여 각 필드 목록을 파악하고, 직접 구현해보십시오. 참고 구현은 챕터 말미 **전체 소스 코드** 절에 포함되어 있습니다."

**검증 기준**: 전체 소스 코드 절의 코드를 복사하여 Vivado/VCS에서 컴파일 오류 없이 시뮬레이션이 완료되어야 한다.

### [Major] 강력 권고 수정 사항 — 4건

#### M-3: 분기 명령어 처리 — NOP 4개 필요 또는 테스트 제외 명시

**위치**: 9.5절 해저드 설명 부분, NOP 계산 FAQ aside 박스

**수정 방향**: 기존 "NOP 개수 = (결과를 쓰는 스테이지) - (결과를 읽는 스테이지) - 1" FAQ aside에 다음 내용을 추가한다.

> 추가할 설명 요지: "분기 명령어(BEQ 등)는 MEM 스테이지에서 `branch_taken`이 확정됩니다. 이 시점까지 이미 3개의 명령어가 파이프라인에 진입하므로, NOP만으로 안전한 실행을 보장하려면 분기 명령어 뒤에 NOP **4개**가 필요합니다. (C1: BEQ IF, C2: BEQ ID + I+1 IF, C3: BEQ EX + I+1 ID + I+2 IF, C4: BEQ MEM + 확정 — 이미 3개 진입.) 이 챕터의 테스트벤치에서는 분기 명령어를 제외하고 R타입·I타입 명령어만으로 검증합니다. 분기 해저드 해결은 Ch11에서 다룹니다."

#### M-4: `alu_src_a` 비트 폭 불일치 — 1비트 단순화 이유 명시

**위치**: 9.4절 `ctrl_t` typedef 설명 본문, 또는 해당 코드 직후 FAQ/tip aside

**수정 방향**: `alu_src_a`가 1비트로 선언된 코드 근처에 다음 설명을 추가한다.

> 추가할 설명 요지: "Ch08 멀티사이클 CPU에서 `alu_src_a`는 2비트(`2'b00`=PC, `2'b01`=old_pc_reg(JAL/AUIPC용), `2'b10`=A레지스터)였습니다. 파이프라인에서는 `old_pc_reg`가 불필요합니다. PC 값이 IF/ID → ID/EX 레지스터를 통해 EX 스테이지까지 전달되므로, EX 스테이지에서 PC를 직접 사용할 수 있습니다. 따라서 `alu_src_a`를 1비트(`0`=rs1_data, `1`=pc_id_ex)로 단순화합니다."

#### M-REG: 레지스터 파일 쓰기/읽기 타이밍 정책 명시

**위치**: 9.3절 WB 스테이지 설명 또는 9.4절 동기 리셋 전략 설명 직후

**수정 방향**: 레지스터 파일의 타이밍 정책을 다음과 같이 명시한다.

> 추가할 설명 요지: "본 설계에서 레지스터 파일은 **동기 쓰기(synchronous write), 비동기 읽기(asynchronous read)**로 구현합니다. WB 스테이지의 쓰기는 클럭 상승 에지에서 이루어지고, ID 스테이지의 읽기는 조합 논리로 이루어집니다. 동일 사이클에 같은 레지스터에 쓰기(WB)와 읽기(ID)가 발생할 경우, 이 구현에서는 **write-then-read** 방식을 사용합니다 — 쓰기가 완료된 후 조합 논리 읽기 경로에 반영됩니다. 이 가정 하에 NOP 3개 삽입으로 데이터 해저드가 해결됩니다."
