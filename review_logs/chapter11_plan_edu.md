## 서문: Ch11의 교육적 위치

Ch11은 Part 4의 두 번째 해저드 챕터다. Ch10에서 독자는 "데이터 해저드"라는 첫 번째 고비를 넘고, 포워딩 파이프라인이 NOP 없이 동작하는 성취감(★★★★★)을 경험했다. Ch11은 그 성취감이 아직 남아있는 시점에 새로운 문제를 제시한다.

**Ch11이 Ch10과 다른 점:**

- Ch10의 데이터 해저드는 "결과가 늦게 온다"는 문제였다 — 포워딩이라는 하드웨어 우회로로 해결됐다.
- Ch11의 제어 해저드는 "다음 명령어를 모른다"는 문제다 — 이미 인출한 명령어를 **버려야** 한다는 점에서 질적으로 다른 해결 전략이 필요하다.

이 질적 차이가 Ch11 교육 설계의 핵심이다. 독자는 "포워딩처럼 데이터를 전달하면 되지 않을까?"라는 직관을 먼저 갖고, 그것이 왜 통하지 않는지를 타이밍 다이어그램으로 이해한 후, 플러시(Flush)라는 새로운 전략을 자연스럽게 수용하게 된다.

**기술 리뷰어 확정 사항 (chapter11_plan_tech.md 반영)**:

- **분기 판정 위치**: EX 스테이지 → **2사이클 버블** (IF/ID + ID/EX 동시 플러시)
  - Ch09의 MEM 판정(3사이클) 방식에서 Ch11에서 EX 판정(2사이클)으로 전환 명시 필수
- **JAL 처리**: ID 스테이지 → **1사이클 버블** (IF/ID만 플러시, ID/EX는 정상 통과)
- **JALR 처리**: EX 스테이지 → **2사이클 버블** (IF/ID + ID/EX 동시 플러시)
- **BNE 지원**: `funct3` 기반 `branch_unit` 모듈 필수 (BEQ만 처리하면 BNE 오류 발생)
- **플러시 우선순위**: `flush > en` (Ch09/Ch10 확정 패턴 유지)

이 기술 결정들이 교육 설계의 구체적 인지 부하 분석과 감정 곡선 설계에 직접 영향을 미친다.

**Ch11의 감정 설계 목표:**

```
호기심 (분기 해저드가 뭐가 다른가?) →
불안 (플러시와 스톨을 동시에 처리해야 한다?!) →
이해 (우선순위 규칙으로 정리된다) →
성취감 (분기 명령어가 있는 실제 루프 코드가 동작한다!)
```

불안 지점 #5 ("플러시와 스톨 동시 처리")가 이 챕터의 핵심 도전 구간이며, 이에 대한 안심 장치로 **우선순위 결정 규칙 표**를 11.3절에서 명시적으로 제공한다.

### 인지 부하 총평

**11.2절, 11.3절, 11.5절, 11.6절이 연속 황색 구간이다.** Ch10의 황색 구간(10.2~10.4절 연속 3절)에 비해 더 많은 절이 황색 판정을 받는다는 점에 주의가 필요하다. 다만 다음의 완화 요인이 있다:

1. **11.3절**: Ch10에서 이미 `id_ex_flush`를 경험한 독자에게 `if_id_flush`는 "같은 메커니즘의 확장"으로 인식된다. 신규 개념의 체감 부하는 판정 기준보다 낮다.
2. **11.5절**: "선택 구현" 표시가 있어 학습 필수 압박이 낮다. 개념 이해만 하고 구현은 생략 가능한 절로 명시한다.
3. **11.6절**: JAL 처리는 단순하고(ID 단계에서 처리), JALR의 복잡성만 별도로 집중 설명한다.

**추가 권고**: 11.2절 후반(ID 단계 분기 판정)과 11.5절(동적 예측)에서 aside를 적극 활용하여 선택적 심화 내용을 본문에서 분리한다.

## 3. 학습 흐름 설계

### 도입 비유: "날씨 예보관 — 맞으면 빠르고, 틀리면 취소"

> "기상청 예보관이 내일 날씨를 '맑음'으로 예측했다고 가정합시다. 우산 제조사는 이 예보를 믿고 창고 정리를 시작했습니다. 그런데 다음 날 비가 온다면? 창고 정리 작업을 취소해야 합니다. 파이프라인의 Predict-Not-Taken 전략은 이와 같습니다. 분기 명령어를 만나면 '분기하지 않을 것'이라고 예측하고, 그 다음 명령어를 미리 인출합니다. 예측이 맞으면 1사이클도 낭비되지 않지만, 예측이 틀리면 이미 인출한 명령어를 취소(플러시)해야 합니다."

**비유의 한계 명시**: "이 비유는 정적 예측의 핵심을 잘 설명합니다. 그러나 현실의 날씨 예보관은 과거 날씨 이력을 활용합니다. 이것이 동적 분기 예측(11.5절)의 아이디어입니다 — 과거 분기 결과를 기록해두었다가 다음 예측에 활용합니다."

### 점진적 복잡도 증가 경로

```
[11.1절] 문제 정의: "분기 명령어가 파이프라인에 왜 문제인가?"
          → 데이터 해저드와의 질적 차이 인식
          → 타이밍 다이어그램으로 분기 판정 지연 문제 관찰 (Ch09 MEM 판정 기준 3사이클 버블)
               ↓
[11.2절] 페널티 감소: "더 빨리 판정할수록 버블이 줄어드는가?"
          → MEM(3사이클 버블) → EX(2사이클 버블) 이동 비교
          → EX 단계 처리가 하드웨어 복잡도와 버블 감소의 균형점임을 이해
               ↓
[11.3절] 플러시 설계: "잘못 인출한 명령어를 어떻게 취소하는가?"
          → if_id_flush 신호 설계
          → 플러시/스톨 동시 상황의 우선순위 규칙 확립
               ↓
[11.4절] 정적 예측: "항상 플러시하지 않아도 되는 방법은?"
          → Predict-Not-Taken 전략
          → CPI 영향 정량 분석
               ↓
[11.5절] 동적 예측 (선택): "예측 정확도를 더 높일 수 있는가?"
          → 2-bit 포화 카운터 + BHT
          → Basys 3 구현 가능성 검토
               ↓
[11.6절] JAL/JALR: "무조건 점프는 어떻게 처리하는가?"
          → JAL: ID 단계에서 처리 (포워딩 없음)
          → JALR: rs1 포워딩 필요 → EX 해저드 가능
               ↓
[11.7절] 통합 검증: "모든 제어 해저드 시나리오가 올바르게 동작하는가?"
          → 분기 성공/실패 × JAL/JALR × 중첩 해저드 시나리오 망라
```

#### 11.2절 학습 흐름 — 분기 결과를 EX 스테이지에서 처리

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "Ch09에서의 MEM 판정 방식과 페널티" 환기 | "Ch09에서 기본 파이프라인은 MEM 스테이지에서 분기를 판정했습니다(3사이클 버블). Ch11에서는 EX 스테이지로 이동하여 2사이클로 줄입니다. 어떻게 가능할까요?" — Ch09→Ch11 전환의 경위를 명시 |
| **개념** | MEM/EX 단계별 분기 판정 시 버블 수 비교 | MEM: 3사이클 버블(IF+ID+EX 모두 플러시), EX: 2사이클 버블(IF+ID 플러시). EX 단계에서 ALU `zero` 신호가 즉시 확정되므로 EX 판정 가능. `branch_taken_ex = ctrl_ex.branch && zero_ex` (BEQ 기준) |
| **예시** | EX 단계 분기 판정 SVG — 2사이클 버블 타이밍 다이어그램 | BEQ가 EX(C3)에서 taken 확정 → C4 시작 시 PC=분기 타겟. C3까지 인출된 I+1(ID 단계)과 I+2(IF 단계) 무효 → **IF/ID + ID/EX 동시 플러시**. BNE를 위해서는 `funct3` 기반 `branch_unit` 모듈 필요 |
| **실습** | ID 단계 분기 판정 가능성 검토 (aside로 분리) | `<aside class="tip">` — ID 단계 이동 시 1사이클 버블 가능하지만 추가 비교기 하드웨어 필요, 포워딩 의존성 시 스톨 추가 가능. "EX 단계가 교재의 기본 구현" 확정 |
| **정리** | faq aside: "EX 단계 처리면 2사이클 버블인데, 이를 왜 감수하는가?" | MEM 판정(3사이클) 대비 1사이클 개선. ID 판정은 하드웨어 추가 대비 이득이 제한적(분기 taken 비율에만 영향). EX 단계가 하드웨어 복잡도와 성능의 균형점임을 설명 |

> **인지 부하**: 새 개념 3개. 황색 주의.
> **완화 전략**: "Ch09에서 이미 MEM 판정으로 기본 파이프라인을 구성했다"는 선행 지식 위에서 "EX 판정으로의 전환"을 설명하면, 완전히 새로운 개념이 아니라 "최적화 이동"으로 인식된다. ID 단계 분기 판정은 aside로 분리하여 본문 복잡도를 낮춘다.
> **기술 리뷰어 확정 사항**: 버블 2사이클(IF/ID + ID/EX 동시 플러시), `branch_unit` 모듈로 BEQ/BNE/BLT/BGE/BLTU/BGEU 처리, 교재 메인은 BEQ/BNE — BLT 이상은 aside 처리.

#### 11.3절 학습 흐름 — Flush 메커니즘 설계

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | Ch10 `id_ex_flush` 재환기 | "Ch10에서 Load-Use 스톨 시 `id_ex_flush=1`로 ID/EX 레지스터를 버블로 교체했습니다. 제어 해저드에서도 같은 전략을 사용하되, 이번에는 IF/ID 레지스터도 함께 flush합니다." |
| **개념** | `if_id_flush` + `id_ex_flush` 동시 활성화 메커니즘 | 분기 taken 시: (1) EX/MEM 단계의 `branch_taken` 신호 감지, (2) `if_id_flush=1`로 IF/ID를 NOP으로 교체, (3) `id_ex_flush=1`로 ID/EX를 NOP으로 교체. 동시에 PC를 분기 타깃으로 변경 |
| **예시** | **플러시/스톨 동시 처리 우선순위 규칙 표** (불안 지점 #5 안심 장치) | "플러시와 스톨이 동시에 요구되면 어떻게 되는가?" — 규칙 표: ① Load-Use 스톨 중 분기 → **플러시 우선** (스톨 취소, 플러시 실행), ② 분기 플러시 중 스톨 신호 → **무시** (플러시 완료 후 다음 사이클에 정상 처리) |
| **실습** | `always_comb` 플러시 제어 로직 구현 | `branch_taken` 신호에서 `if_id_flush`, `id_ex_flush` 생성. Ch10의 `stall` 신호와의 우선순위 연산(`branch_taken`이 `stall`을 override하는 조건) |
| **정리** | faq aside: "플러시된 명령어의 부수 효과(side effect)는 어떻게 되는가?" | "NOP으로 교체된 명령어는 레지스터/메모리에 아무것도 쓰지 않으므로 부수 효과가 없습니다." 정확한 예외(Precise Exception)와의 연결 복선 |

> **인지 부하**: 새 개념 3개. 황색 주의.
> **완화 전략**: `if_id_flush`의 체감 부하를 "Ch10 `id_ex_flush`의 확장"으로 프레이밍하는 것이 핵심이다. 우선순위 규칙 표는 불안 지점 #5의 핵심 안심 장치이므로 시각적으로 명확하게 설계되어야 한다.
> **Ch09 연결**: Ch09에서 `if_id_flush=0`으로 예약해둔 포트가 드디어 사용되는 순간임을 명시. "3챕터 전에 미리 준비한 포트가 지금 빛난다"는 설계 연속성의 성취감을 활용한다.

#### 11.4절 학습 흐름 — 정적 분기 예측: Predict-Not-Taken

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "항상 flush하면 성능이 얼마나 손해인가?" | 분기 명령어 비율 20%, taken 비율 50%라면 CPI = 1 + 0.2 × 0.5 × 2 = 1.2. "실제로는 not-taken이 많다 → 항상 not-taken으로 가정하면 taken일 때만 2사이클 flush 발생" |
| **개념** | Predict-Not-Taken 전략 + CPI 계산 (페널티 2사이클 기준) | 기본 동작: 분기 명령어를 만나도 PC+4를 계속 인출. 분기 결과가 EX에서 확인됐을 때 taken이면 **2사이클 flush**, not-taken이면 아무것도 하지 않음. **CPI = 1 + (분기 비율) × (taken 비율) × 2** |
| **예시** | 루프 코드에서 taken/not-taken 비율 분석 | `for(i=0; i<10; i++)` 루프에서 BNE는 9번 taken, 1번 not-taken → taken 비율 90%. CPI 영향: 분기 비율 20%면 CPI = 1 + 0.2 × 0.9 × 2 = 1.36. 이 경우 Predict-Not-Taken의 효율이 낮음 → 동적 예측의 필요성 동기 부여 |
| **실습** | CPI 계산 연습 | 명령어 믹스 주어졌을 때 분기 비율과 taken 비율로 CPI 계산 (페널티 2사이클 공식 적용) |
| **정리** | interview aside: "정적 예측 vs 동적 예측 — 면접 단골 질문" | 두 전략의 하드웨어 복잡도, 구현 비용, 예측 정확도를 3줄 표로 정리 |

> **인지 부하**: 새 개념 2개. 녹색 안전.
> **핵심 전략**: 11.3절의 황색 구간 후 11.4절이 녹색인 것은 중요한 리듬 설계다. CPI 계산이 포함되어 있지만, Ch08 멀티사이클에서 CPI 분석 경험이 있는 독자에게는 친숙한 방법론이다. **페널티를 1사이클이 아닌 2사이클로 정확히 설정**해야 한다 — 기술 리뷰어 확정(EX 판정 = 2사이클 버블)을 반영한 수치다.

#### 11.5절 학습 흐름 — 동적 분기 예측 (선택 구현)

#### 11.6절 학습 흐름 — JAL/JALR 처리

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "분기 처리가 완성됐다. 점프 명령어는 어떻게 처리하는가?" | "BEQ/BNE 등 조건부 분기는 EX 단계에서 처리합니다. JAL과 JALR은 조건 없이 항상 점프합니다 — 더 빨리 처리할 수 있지 않을까요?" |
| **개념** | JAL(ID 단계) vs JALR(EX 단계) 처리 차이 | JAL: 타깃 = PC + imm_J → ID 단계에서 즉시 계산 가능 → 0사이클 페널티 가능 (IF/ID flush 1회만). JALR: 타깃 = rs1 + imm_I → rs1 값이 필요 → EX 단계에서 처리 필요. rs1이 직전 명령어 결과이면 EX 해저드 발생 가능 |
| **예시** | JALR EX 해저드 시나리오 타이밍 다이어그램 | "ADD x1, x2, x3; JALR x0, x1, 0" — ADD의 EX 결과가 JALR의 EX 입력 rs1로 필요. Ch10 포워딩 유닛이 이미 이 경우를 처리 (EX-EX 포워딩 적용). 단, 포워딩 조건 확인 필수 |
| **실습** | Ch10 포워딩 유닛 JALR 지원 확인 | 기존 `forwarding_unit`의 조건이 JALR의 rs1에도 적용되는지 확인. `reg_write` 조건과 `rd != x0` 조건 검토 |
| **정리** | faq aside: "JALR의 목적 레지스터(rd)에도 포워딩이 필요한가?" | rd=x0(ret pseudo-instruction)이 일반적. rd≠x0(서브루틴 리턴 주소 저장)이면 WB 단계에서 정상 처리. 포워딩 필요 여부 명시 |

> **인지 부하**: 새 개념 3개. 황색 주의.
> **완화 전략**: JALR 처리의 핵심을 "Ch10 포워딩 유닛이 이미 처리한다"는 관점으로 제시하면, 독자가 새 하드웨어를 설계한다는 부담 없이 기존 설계의 완결성을 확인하는 경험이 된다. 새로 설계하는 것이 아니라 "이미 만든 것이 작동함을 확인"하는 절로 포지셔닝한다.
> **기술 리뷰어 주석 반영**: JALR의 rs1 포워딩 의존성과 EX 해저드 가능성을 타이밍 다이어그램으로 명시.

#### 11.7절 학습 흐름 — 제어 해저드 테스트벤치

| **정리** | metacognition aside: "Ch10 마일스톤과 Ch11 마일스톤의 차이" | "Ch10은 NOP 없이 실행했습니다. Ch11은 분기 명령어로 루프를 제어합니다. 이제 프로세서가 '알고리즘'을 실행할 수 있게 되었습니다." |

> **인지 부하**: 새 개념 2개. 녹색 안전.
> **핵심 전략**: 11.7절의 루프 테스트는 Ch10 마일스톤의 자연스러운 확장이다. "언롤 코드를 루프로 바꿔도 같은 결과가 나온다"는 확인이 이 절의 성취감이다.

### [기억 — Remember: 정의를 말할 수 있다]

> **문제 1 — 제어 해저드 정의**
>
> 다음 용어를 각각 한 문장으로 정의하시오.
> (가) 제어 해저드(Control Hazard)
> (나) 분기 페널티(Branch Penalty)
> (다) Predict-Not-Taken
>
> *기대 답변*:
> - (가) 분기/점프 명령어로 인해 다음 인출할 명령어 주소가 확정되지 않아 파이프라인에서 발생하는 성능 저하 현상.
> - (나) 분기 명령어의 결과가 확정될 때까지 파이프라인이 기다리거나 잘못 인출한 명령어를 버리면서 발생하는 낭비 사이클 수. (이 교재에서 EX 판정 기준 2사이클)
> - (다) 분기 명령어를 만나면 '분기하지 않는다(not-taken)'고 가정하고 PC+4를 계속 인출하는 정적 예측 전략.
>
> *채점 기준*: 각 정의에 핵심 키워드(분기/점프, 성능 저하/낭비 사이클, 정적 예측/not-taken 가정) 포함 시 만점. (나)에서 "2사이클" 언급 시 가점.

### [이해 — Understand: 차이를 설명할 수 있다]

> **문제 2 — MEM 단계 vs EX 단계 분기 판정 비교**
>
> 분기 판정을 MEM 단계에서 수행하는 방식(Ch09 초안)과 EX 단계에서 수행하는 방식(Ch11 확정)을 비교하시오.
>
> (가) 각 방식에서 분기 버블 사이클 수와 플러시 대상 파이프라인 레지스터를 구하시오.
> (나) EX 단계 판정 시 BEQ는 `zero` 신호로 처리할 수 있지만, BNE 처리에 추가로 필요한 것은 무엇인가?
> (다) 이 교재에서 EX 단계 처리를 채택한 이유를 MEM 판정 대비 구체적 장점과 함께 서술하시오.
>
> *기대 답변*:
> - (가) MEM 단계: 3사이클 버블 (IF/ID + ID/EX + EX/MEM 플러시). EX 단계: **2사이클 버블** (IF/ID + ID/EX 동시 플러시).
> - (나) `funct3` 신호. BEQ는 `zero=1`일 때 taken, BNE는 `zero=0`일 때 taken으로 조건이 반대. `funct3[2:0]` 값에 따라 분기 조건을 구분하는 `branch_unit` 모듈이 필요.
> - (다) MEM 판정 대비 1사이클 버블 감소 (3→2사이클). EX 단계에서 ALU 비교 결과(`zero`, `negative` 등)가 즉시 확정되므로 별도 지연 없이 판정 가능. 기존 EX 단계 포워딩 MUX와 연동되어 의존성 있는 피연산자도 정확히 처리.
>
> *채점 기준*: (가) 버블 수치 정확 + 플러시 대상 명시. (나) funct3/branch_unit 언급. (다) 성능 이득과 구현 방법 2가지 이상 정확 시 만점.

### [적용 — Apply: 플러시 제어 로직을 구현할 수 있다]

> **문제 3 — Flush 제어 로직 SystemVerilog 구현**
>
> 다음 조건을 만족하는 파이프라인 제어 로직을 `always_comb`로 구현하시오.
>
> - `branch_taken_ex`: EX 스테이지에서 분기 taken이 확정된 신호 (BEQ/BNE 기준)
> - `jal_taken_id`: ID 스테이지에서 JAL 타겟으로 점프 확정 신호
> - `jalr_taken_ex`: EX 스테이지에서 JALR 타겟으로 점프 확정 신호
> - `load_use_stall`: Load-Use 해저드 감지 신호 (Ch10)
> - `if_id_flush`: IF/ID 레지스터를 NOP으로 교체
> - `id_ex_flush`: ID/EX 레지스터를 NOP으로 교체
> - `if_id_en`: IF/ID 레지스터 동결 (0이면 동결)
> - `pc_en`: PC 동결 (0이면 동결)
> - **우선순위 규칙**: `branch_taken_ex`/`jalr_taken_ex`가 `load_use_stall`보다 우선. `jal_taken_id`도 stall보다 우선.
> - **주의**: JAL은 IF/ID만 플러시 (ID/EX는 JAL 명령어 자체가 통과해야 rd=PC+4 저장)
>
> *기대 답변*:
> ```systemverilog
> always_comb begin
>    // 기본값
>    if_id_flush = 1'b0;
>    id_ex_flush = 1'b0;
>    if_id_en    = 1'b1;
>    pc_en       = 1'b1;
>
>    if (branch_taken_ex || jalr_taken_ex) begin
>       // 분기/JALR 플러시 우선 (stall 무시) — 2사이클 버블
>       if_id_flush = 1'b1;
>       id_ex_flush = 1'b1;
>    end else if (jal_taken_id) begin
>       // JAL: IF/ID만 플러시 (ID/EX는 JAL 명령어 자체 통과 필요) — 1사이클 버블
>       if_id_flush = 1'b1;
>       // id_ex_flush = 0 유지
>    end else if (load_use_stall) begin
>       // Load-Use 스톨 (분기/점프 없을 때만)
>       if_id_en    = 1'b0;   // IF/ID 동결
>       pc_en       = 1'b0;   // PC 동결
>       id_ex_flush = 1'b1;   // ID/EX 버블
>    end
> end
> ```
>
> *채점 기준*: 기본값 설정, `branch_taken_ex`/`jalr_taken_ex` 우선 처리(2사이클 flush), `jal_taken_id` 처리(IF/ID만, ID/EX 유지), `load_use_stall` 처리, flush/en 신호 올바른 조합 모두 만족 시 만점. JAL에서 `id_ex_flush=0` 유지가 핵심.

### [분석 — Analyze: 타이밍 다이어그램으로 중첩 해저드를 분석할 수 있다]

> **문제 4 — 중첩 해저드 타이밍 분석**
>
> 다음 RISC-V 코드를 Predict-Not-Taken 파이프라인(EX 단계 분기 판정, 2사이클 버블)으로 실행할 때를 분석하시오.
>
> ```
> LW   x1, 0(x2)      # I1
> BEQ  x1, x3, TARGET  # I2: x1에 의존 (Load-Use)
> ADD  x5, x6, x7     # I3: Predict-Not-Taken으로 인출됨
> AND  x8, x9, x10    # I4: Predict-Not-Taken으로 인출됨
> TARGET: SUB x11, x12, x13  # I5: 실제 실행 대상
> ```
>
> (가) I1→I2 사이에 Load-Use 스톨이 몇 사이클 발생하는가? 발생 이유를 타이밍 관점에서 설명하시오.
> (나) I2가 BEQ이고 taken(분기 성공)이라고 하자. I3와 I4는 어떻게 처리되는가?
> (다) Load-Use 스톨과 분기 플러시가 동시에 요구될 수 있는 사이클이 있는가? 있다면 어떤 제어 신호가 우선 적용되는가?
> (라) 전체 실행에서 "낭비"된 사이클(스톨+플러시)의 합계를 구하시오.
>
> *기대 답변*:
> - (가) 1사이클 스톨. LW의 MEM 단계에서 x1 값이 생성되지만, BEQ의 EX 단계 시작 시점에 아직 준비되지 않음. 1사이클 기다리면 MEM/WB 단계 완료 후 MEM-EX 포워딩으로 전달 가능.
> - (나) I3와 I4는 Predict-Not-Taken으로 인출되었지만, BEQ taken 확정 시 **`if_id_flush=1`, `id_ex_flush=1`로 2개의 버블이 삽입됨** (I3, I4 모두 NOP으로 교체). I5(TARGET)부터 정상 실행.
> - (다) Load-Use 스톨 처리 사이클에서 stall이 활성화된 직후, BEQ가 EX 단계에서 taken 확정될 때 동시에 요구될 수 있다. 이 경우 **`branch_taken_ex` 우선 규칙** 적용: `if_id_flush=1`, `id_ex_flush=1`으로 flush 처리 (PC는 분기 타겟으로 변경, stall에 의한 PC 홀드는 무시됨).
> - (라) Load-Use 스톨 1사이클 + BEQ taken 플러시 **2사이클** = 총 **3사이클** 낭비.
>
> *채점 기준*: (가) 1사이클 + 이유 명시. (나) 2개 버블 flush 명시. (다) 분기 우선 규칙 적용. (라) **3사이클** 합계 정확 시 만점 (1+2=3, 2사이클 버블 반영).

### [평가 — Evaluate: 동적 예측 도입 여부를 판단할 수 있다]

> **문제 5 — 동적 분기 예측 도입 여부 설계 결정**
>
> 다음 두 가지 설계 옵션에 대해 Basys 3 Artix-7(LUT 20,800개) 기반 RV32I 파이프라인 프로세서의 맥락에서 평가하시오.
>
> - **옵션 A**: Predict-Not-Taken (추가 하드웨어 없음, EX 판정 기준 페널티 **2사이클**)
> - **옵션 B**: 2-bit BHT, 256 엔트리 (약 512 비트 FF 추가, Basys 3에서 약 256 FF + ~16 LUT)
>
> (가) 분기 taken 비율이 30%인 일반적인 프로그램에서 두 옵션의 CPI를 비교하시오. (분기 명령어 비율 = 전체의 20%, **페널티 = 2사이클**)
>
> (나) 분기 taken 비율이 80%인 루프 중심 프로그램에서 두 옵션의 CPI를 비교하시오.
>
> (다) BHT의 FF 사용량(256 FF)이 전체 Basys 3 FF 예산(41,600개)에서 차지하는 비율을 계산하고, 이 비율이 허용 가능한 수준인지 판단하시오.
>
> (라) 여러분이 설계자라면 어떤 옵션을 선택하겠는가? 성능, 하드웨어 복잡도, 개발 일정을 고려하여 근거를 제시하시오.
>
> *기대 답변*:
> - (가) **옵션A**: CPI = 1 + 0.20 × 0.30 × **2** = **1.12**. **옵션B**: BHT 예측 정확도 가정 85% → 실제 miss = 0.20 × 0.30 × 0.15 = 0.009, 페널티 2사이클 × 0.009 = 0.018, CPI ≈ **1.018**. 차이: 1.12 vs 1.018.
> - (나) **옵션A**: CPI = 1 + 0.20 × 0.80 × **2** = **1.32**. **옵션B**: taken miss = 0.20 × 0.80 × 0.15 = 0.024, CPI ≈ 1 + 0.024 × 2 = **1.048**. 루프 중심에서 BHT 효과 큼 (1.32 → 1.048, 약 20% CPI 개선).
> - (다) 256 / 41,600 = **0.62%**. 허용 가능(1% 이하). BHT는 LUTRAM 또는 FF로 구현 가능하므로 Basys 3 리소스 부담 미미.
> - (라) 정답 없음. 평가 기준: ① 루프 중심 프로그램이면 BHT 도입 시 CPI 개선 효과가 크므로 정당화 가능, ② 개발 일정이 촉박하면 옵션 A 선택 후 추후 확장 전략도 합리적, ③ 리소스 부담이 0.62%이므로 BHT 도입 비용은 낮음. 어느 선택이든 근거를 논리적으로 제시하면 만점.
>
> *채점 기준*: (가)(나) 수치 계산 정확 (**페널티 2사이클** 반영 필수). (다) FF 비율 계산 정확. (라) 성능, 복잡도, 일정 중 2가지 이상 근거 포함 시 만점.

### Ch11 학습 설계의 핵심 과제

**1. 11.1절에서 "질적 차이" 명확히 전달**

데이터 해저드와 제어 해저드의 차이는 단순한 해저드 종류의 차이가 아니다. "결과가 늦게 온다(포워딩으로 해결 가능)"와 "다음 명령어 자체를 모른다(취소가 필요)"는 질적으로 다른 문제다. 이 차이를 11.1절에서 명확히 전달해야 11.3절 플러시 메커니즘이 "왜 이런 방법을 써야 하는가"에 대한 납득감을 갖고 받아들여진다.

**2. 11.3절 우선순위 규칙 표는 불안 지점 #5의 핵심 안심 장치**

"플러시와 스톨이 동시에 발생하면?"이라는 질문은 독자에게 복잡한 조합 논리를 상상하게 만들고 불안을 유발한다. 이 불안을 해소하는 가장 효과적인 방법은 **규칙을 명시적 표로 제공**하는 것이다. 규칙 표의 형식은 다음을 따른다:

| 상황 | branch_taken | load_use_stall | 적용 동작 |
|------|:------------:|:--------------:|---------|
| 분기만 | 1 | 0 | 플러시 실행 |
| 스톨만 | 0 | 1 | 스톨 실행 |
| 동시 발생 | 1 | 1 | **플러시 우선** (스톨 무시) |
| 없음 | 0 | 0 | 정상 진행 |

이 표를 SVG(`ch11_sec03_flush_stall_priority.svg`)로 제작하여 본문에 배치한다.

**3. 11.5절은 "선택 구현"으로 명시하되 개념 설명은 필수**

동적 예측은 Basys 3 구현이 가능하지만 개발 일정과 복잡도를 고려하면 선택 사항이다. 그러나 "동적 예측이 존재한다", "2-bit 포화 카운터의 원리", "BHT의 개념"은 반도체 면접에서 필수 질문으로 다루어진다. 따라서 이 절은 구현을 선택으로 하되, 개념 설명은 충분히 포함한다.

**4. 11.6절은 "새 설계" 아닌 "기존 설계 확인"으로 포지셔닝**

JALR 처리의 포워딩은 Ch10에서 이미 설계한 포워딩 유닛이 처리한다. 이 절에서 독자가 "새로운 하드웨어를 설계해야 한다"는 부담을 느끼지 않도록, "Ch10의 포워딩 유닛이 JALR도 처리함을 확인"하는 검증 절로 포지셔닝한다.

**5. 11.7절 루프 테스트는 Ch10 마일스톤의 자연스러운 업그레이드**

Ch10 마일스톤(언롤 합산)과 Ch11 마일스톤(루프 합산)이 동일한 수학적 결과(sum=55)를 생성하도록 설계한다. "언롤로 했던 계산을 루프로 했는데 같은 답이 나온다"는 확인이 파이프라인의 정확성을 직관적으로 증명한다. 이 "업그레이드" 내러티브가 Ch11의 성취감 설계다.

### 기술 저자에 대한 권고사항

1. **11.3절 우선순위 규칙을 코드 주석에도 반영**: `always_comb` 블록 내부에 "// branch_taken이 load_use_stall보다 우선 (11.3절 규칙 표 참조)"와 같은 주석을 포함하여 코드와 설명의 연결성을 높인다.

2. **11.2절 SVG는 2-panel 구성 권장**: MEM(3사이클 버블) vs EX(2사이클 버블) 분기 판정의 버블 수를 한 SVG에서 나란히 비교하는 타이밍 다이어그램을 제작한다. 각 판정 위치에서 플러시되는 파이프라인 레지스터를 색으로 강조하면 독자가 한눈에 차이를 파악할 수 있다.

3. **11.5절 BHT 스켈레톤 코드에 포트 주석 완비**: 선택 구현 절이므로 독자가 혼자 완성할 수 있도록 포트 선언과 상태 정의에 상세한 한국어 주석을 포함한다.

4. **11.7절 루프 테스트 어셈블리 코드 사전 검증 필수**: 루프 코드가 Ch11 플러시 파이프라인에서 실제로 sum=55를 계산하는지 시뮬레이션으로 검증한다. 특히 루프 종료 분기(BNE/BEQ)의 taken/not-taken 동작과 flush 타이밍을 확인한다.

5. **`ch11_sec03_flush_stall_priority.svg`의 배치 우선순위 최상**: 이 SVG는 불안 지점 #5의 핵심 안심 장치이므로 절의 중간에 배치하고, 표의 각 행을 색으로 구분(정상=흰색, 플러시=파란색, 스톨=황색, 동시발생=빨간색→파란색 우선)하여 시각적으로 즉시 이해 가능하게 설계한다.
