## 서문: Ch08의 교육적 위치

Ch08은 Part 3의 완성 챕터다. Ch07에서 데이터패스를 완전히 구축한 독자는 "부품은 다 갖췄는데 CPU가 아직 동작하지 않는다"는 불완전함을 인식하고 있다. Ch08은 그 불완전함을 해소하는 순간, 즉 **FSM 제어 유닛을 붙여 멀티사이클 CPU가 처음으로 동작하는 성취**를 설계한다.

이 챕터가 갖는 이중 역할을 명확히 인식해야 한다.

**첫째, Part 3의 마일스톤 달성 챕터다.**
FSM CPU가 완성되어 처음으로 실제 RV32I 프로그램을 실행하는 순간(8.4절 통합 시뮬레이션)이 Part 3의 감정적 정점이다. Ch06에서 피보나치를 단일 사이클로 실행한 것과 대칭되는 성취로 설계해야 한다.

**둘째, Part 4(파이프라인)의 직접 발판이다.**
멀티사이클 FSM의 각 상태(IF/ID/EX/MEM/WB)는 파이프라인의 각 스테이지와 1:1 대응된다. 독자가 "FSM 상태를 동시에 돌리면 파이프라인"이라는 연결을 Ch08에서 직관적으로 이해해야 Ch09 진입이 자연스럽다. 이 연결은 9.1절에서 명시적으로 다루지만, 씨앗은 Ch08에서 심어야 한다.

> **감정 설계 원칙**: Ch07에서 "지휘자가 없는 CPU"로 끝났으므로, Ch08은 "지휘자(FSM)를 붙이자"는 설레는 출발로 시작해야 한다. 처음에는 FSM 설계의 복잡성(상태 전이도, 명령어별 분기)이 작은 불안을 유발하지만, 체계적 접근(Moore FSM 2블록 패턴, 절별 점진적 구현)으로 이를 이해로 전환한다.

### 8.1절 학습 흐름 — Moore/Mealy FSM 원리

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | Ch07.5의 "지휘자가 없다" 문장을 직접 인용 | "Ch07은 이 데이터패스가 아직 동작하지 않는다고 끝맺었습니다. 지금 그 지휘자를 설계합니다." — 완결 욕구 자극 |
| **개념** | Moore FSM vs Mealy FSM 구조 비교 | 출력 결정 기준의 차이를 1개 SVG로 명확히 시각화. 멀티사이클 제어가 Moore FSM을 쓰는 이유: 상태에만 의존하므로 글리치(Glitch) 없는 안정적 출력 가능 |
| **예시** | 신호등 FSM (Moore) vs 버튼식 교차로 FSM (Mealy) 비유 | 친숙한 일상 예시로 Moore/Mealy 차이 직관화. 이후 "멀티사이클 제어 유닛은 신호등 방식" 연결 |
| **실습** | 종이 실습: 3상태 FSM 상태 전이도 그리기 | IF→ID→EX 3개 상태만으로 단순화한 FSM을 종이에 그리고 Moore 출력 함수를 표로 작성. 10분 이내 수행 가능 |
| **정리** | metacognition aside: "FSM과 디코더의 차이를 설명할 수 있는가?" | 단일 사이클은 조합 논리 디코더, 멀티사이클은 순차 논리 FSM — 이 대비를 정리 |

> **인지 부하**: 새 개념 2개 (Moore FSM 구조, Mealy FSM 구조). 안전 구간.
> 신호등 비유는 교육전문강사가 검증해야 할 핵심 비유다: 정확성 확인 → 한계 명시 → 하드웨어 용어 복귀 3단계 필수.

### 8.2절 학습 흐름 — 5단계 FSM 상태 설계

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | Ch07의 "LW는 5사이클" 직관을 상태도 언어로 전환 | "Ch07에서 LW가 5사이클에 걸쳐 실행됨을 보았습니다. 이제 그 5개 사이클을 5개 FSM 상태로 정의합니다." — 선행 지식 활성화 |
| **개념** | 전체 상태 목록 제시 후 명령어별 경로 분기 설명 | 상태 열거(S0:IF, S1:ID, S2:EX_R/I, S3:EX_MEM, S4:EX_BR, S5:MEM_READ, S6:MEM_WRITE, S7:WB_R, S8:WB_LOAD 등). 상태가 많아 보이지만 "IF/ID는 공통, EX부터 분기"라는 패턴 명시 |
| **예시** | Gradual Reveal — 명령어 타입별 상태 경로 SVG 4단계 | ① IF→ID 공통 경로, ② +R타입 경로(IF→ID→EX_R→WB_R), ③ +Load 경로 추가, ④ +Store/Branch/JAL 경로 완성. 각 단계 SVG에서 새로 추가된 경로만 파란색 강조 |
| **실습** | Store 명령어(SW)의 상태 경로를 빈칸으로 채우기 | SW의 실행 단계(IF→ID→EX_ADDR→MEM_WRITE)를 표에서 빈칸 완성. 각 상태에서 활성화되는 제어 신호도 함께 기입 |
| **정리** | 상태 수 결정 근거 요약 + 8.3절 예고 | "상태 설계는 완료했습니다. 이제 이 설계를 SystemVerilog 코드로 변환합니다." — 8.3절 직결 동기 |

> **인지 부하**: 새 개념 3개 (FSM 상태 전이도 전체 구조, 명령어별 분기 경로, 각 상태의 제어 신호 집합). 황색 경계. Gradual Reveal이 필수적이며 4단계 SVG 공개로 부하를 분산한다.
> **주의**: Ch08 전체에서 인지 부하가 가장 높은 절이다. 교수 설계 상 8.2절과 8.3절 사이에 충분한 정리 구간을 배치해야 한다.

### 8.3절 학습 흐름 — SystemVerilog 구현

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | 8.2절 상태 전이도와 코드 대응 관계 제시 | "상태 전이도의 각 요소가 코드의 어느 부분에 대응하는지 먼저 보겠습니다" — 전체 구조 파악 후 세부 작성 |
| **개념** | `always_ff` 블록 (상태 레지스터) + `always_comb` 블록 (출력 함수) 이중 구조 설명 | 두 블록의 역할 분리를 명확히: `always_ff`는 상태 전이, `always_comb`는 제어 신호 생성. 이 패턴이 Moore FSM의 표준 구현 방식임을 강조 |
| **예시** | IF 상태의 완성 코드 → ID 상태 코드 순서로 점진적 제시 | 코드를 상태 하나씩 추가하며 보여줌. 각 추가 부분에 한국어 주석 및 "이 줄이 하는 일" 설명 병기. JAL/JALR의 pc_src 처리 포함 (`pc_src=2'b01`로 수정, Ch07 C1 이슈 해소) |
| **실습** | WB_R 상태의 `always_comb` 출력 블록 빈칸 완성 | `reg_write`, `wb_sel`, `pc_write` 신호값을 빈칸으로 제시. EX 단계 결과를 레지스터에 쓰는 WB 상태의 신호 조합을 추론하여 기입 |
| **정리** | Ch08 FSM 코드 전체 구조 요약 SVG | `always_ff` 블록 ↔ `always_comb` 블록 ↔ 출력 신호 목록의 관계를 하나의 박스 다이어그램으로 요약. "전체를 보면서 각 부분의 위치를 확인하십시오" |

> **인지 부하**: 새 개념 2개 (FSM 이중 블록 패턴, 상태별 제어 신호 집합의 코드 표현). 안전 구간.
> 8.2절에서 상태 설계를 완료했으므로 8.3절은 "이미 설계된 내용을 코드로 번역하는" 과정이다. 새로운 개념 학습 부담이 낮고 구현 숙련도 향상이 주목표다.

### 8.5절 학습 흐름 — 성능 비교 (CPI 분석)

**도입 → 개념 → 예시 → 실습 → 정리**

| 단계 | 구현 방법 | 세부 사항 |
|------|----------|---------|
| **도입** | "더 빠른가, 더 느린가?" 질문으로 시작 | "멀티사이클 CPU가 완성되었습니다. 그런데 실제로 단일 사이클보다 빠른가요?" — 분석 동기 유발 |
| **개념** | CPI 개념 정의 → 명령어별 CPI 계산 → 가중 평균 CPI | `CPI = Σ(CPI_i × freq_i)` 공식 제시. R/I:4, Load:5, Store:4, Branch:3, JAL:3, JALR:4 수치 근거(상태 수)와 함께 설명 |
| **예시** | 단일 사이클 vs 멀티사이클 성능 비교 시나리오 3가지 | ① Load-heavy 프로그램, ② Branch-heavy 프로그램, ③ 일반 RISC-V 프로그램(Load 20% 가정). 각 시나리오에서 `T_exec = N × CPI × T_clk` 계산으로 우열 결정 |
| **실습** | 주어진 프로그램 프로파일에서 가중 평균 CPI 계산 | 명령어 믹스 표(R:40%, Load:15%, Store:10%, Branch:20%, 기타:15%)가 주어질 때, 가중 평균 CPI와 총 실행 시간을 계산하는 2~3단계 계산 문제 |
| **정리** | interview aside: "파이프라인이 등장하는 이유" | "멀티사이클은 Fmax를 높였지만 CPI>1입니다. 파이프라인은 Fmax를 유지하면서 CPI를 1에 가깝게 만드는 방법입니다." — Ch09 진입 동기 |

> **인지 부하**: 새 개념 2개 (CPI 개념 및 계산, 가중 평균 CPI를 통한 성능 비교). 안전 구간.
> **주의**: TABLE_OF_CONTENTS.md에 명시된 대로, 이 절의 성능 비교는 시뮬레이션 기반으로 한정한다. FPGA 합성 결과를 이용한 클럭 주파수 비교는 Ch12.5에서 다룬다.

### 총평

**8.2절이 이 챕터의 유일한 주의 구간이다.** 멀티사이클 FSM의 상태 전이도는 명령어 타입(R/I/S/B/U/J) 수만큼 분기 경로가 있어 시각적으로 복잡하다. 독자가 전체 상태도를 한꺼번에 보면 압도감을 느낄 수 있다.

**핵심 완화 전략**: "IF→ID는 모든 명령어 공통"이라는 패턴을 먼저 강조하고, 분기는 ID 이후부터만 발생함을 명시한다. 이후 Gradual Reveal로 명령어 타입별 경로를 순차 추가한다.

> **문제 2 — Moore vs Mealy FSM 적용 근거**
>
> 멀티사이클 CPU의 제어 유닛을 Mealy FSM으로 구현하면 어떤 문제가 발생할 수 있는가? Moore FSM이 선택된 이유를 제어 신호의 안정성(Glitch) 관점에서 설명하시오.
>
> *기대 답변 핵심*: Mealy FSM은 입력(IR 내용 등)이 변할 때마다 출력이 즉시 변화 → 조합 논리의 글리치가 제어 신호에 전파되어 데이터패스 오동작 위험. Moore FSM은 상태만으로 출력 결정 → 상태 전이 완료 후 안정된 출력 보장.
>
> *채점 기준*: "글리치" 또는 "입력 신호 변화에 의한 순간 오동작" 개념이 포함되면 정답.

> **문제 3 — JALR 명령어 상태 경로 설명**
>
> JALR 명령어가 실행될 때 거치는 FSM 상태 경로를 순서대로 나열하고, 각 상태에서 수행되는 작업을 설명하시오. 특히 JALR과 JAL의 상태 경로가 어떻게 다른지 비교하시오.
>
> *기대 답변 핵심*:
> - JALR: IF → ID → EX(A+imm_I, 결과 하위 1비트 클리어) → WB(pc_src=ALUOut, rd=PC+4)
> - JAL: IF → ID → EX(PC+imm_J, pc_src=ALUOut) → WB(rd=PC+4)
> - 차이점: JALR은 기저 주소로 rs1(레지스터 값)을 사용, JAL은 PC를 사용. JALR은 하위 1비트 클리어 필요.
>
> *채점 기준*: 두 명령어의 상태 경로 차이와 하위 1비트 클리어 이유 설명 포함 시 정답.

### [분석 — Analyze: 성능 트레이드오프를 분석할 수 있다]

> **문제 6 — CPI 분석 및 성능 비교**
>
> 어떤 RISC-V 프로그램이 1,000개의 명령어로 구성되며, 명령어 종류별 비율은 다음과 같다.
>
> | 명령어 유형 | 비율 | 멀티사이클 CPI |
> |-----------|------|:------------:|
> | R 타입 (ADD, SUB 등) | 35% | 4 |
> | I 타입 Load (LW) | 20% | 5 |
> | S 타입 Store (SW) | 10% | 4 |
> | B 타입 Branch (BEQ, BNE) | 25% | 3 |
> | J 타입 JAL | 10% | 3 |
>
> 단일 사이클 프로세서: Fmax = 25 MHz (모든 명령어 CPI = 1)
> 멀티사이클 프로세서: Fmax = 60 MHz
>
> (가) 멀티사이클 프로세서의 가중 평균 CPI를 계산하시오.
>
> (나) 각 프로세서의 총 실행 시간(μs)을 계산하시오. `T_exec = N × CPI × T_clk`
>
> (다) 이 프로그램에서 어느 프로세서가 더 빠른가? 만약 Load 명령어 비율이 50%로 늘어난다면(R 타입이 5%로 감소) 결론이 바뀌는가?
>
> *기대 답변*:
> - (가) 가중 평균 CPI = 0.35×4 + 0.20×5 + 0.10×4 + 0.25×3 + 0.10×3 = 1.40+1.00+0.40+0.75+0.30 = 3.85
> - (나) 단일 사이클: 1000 × 1 × (1/25MHz) = 40 μs. 멀티사이클: 1000 × 3.85 × (1/60MHz) = 64.2 μs. → 단일 사이클이 더 빠름.
> - (다) Load 50% 시: 가중 평균 CPI = 0.05×4 + 0.50×5 + 0.10×4 + 0.25×3 + 0.10×3 = 0.20+2.50+0.40+0.75+0.30 = 4.15. 멀티사이클: 1000×4.15÷60MHz = 69.2 μs. 여전히 단일 사이클이 빠름. 멀티사이클이 유리해지려면 Branch 비율이 매우 높아야 함(CPI=3인 명령어 비중 증가 필요).
>
> *채점 기준*: (가) 계산 과정 명시. (나) 수치 정확도. (다) 단순 결론 제시가 아닌 "명령어 믹스가 성능 결과를 결정한다"는 논리가 포함되면 부분 점수 인정.

## Ch08→Ch09 학습 연결 설계

> "멀티사이클 CPU는 한 순간에 한 명령어만 처리합니다. S0_IF에서 명령어를 인출하는 동안 S2_EX, S5_MEM_READ에 있는 데이터패스 자원은 유휴 상태입니다. 만약 S0_IF의 명령어를 인출하는 동시에 이전 명령어의 S2_EX를 실행하고, 또 다른 이전 명령어의 S5_MEM_READ를 수행할 수 있다면? 그것이 파이프라인입니다."

## 교육 설계자 종합 평가 및 권고사항

### Ch08 학습 설계의 핵심 과제

1. **8.2절 상태 전이도 충격 관리**: 전체 FSM 상태 전이도는 명령어 타입별 분기로 복잡하다. Gradual Reveal SVG 4단계 + "IF→ID 공통" 패턴 강조 + faq aside로 3중 완화가 필수다.

2. **8.4절 성취감 극대화**: Part 3의 감정적 정점. CPU가 처음 동작하는 순간의 성취감을 의도적으로 설계한다. 검증 프로그램의 결과가 시각적으로 확인 가능해야 하며, "이것이 당신이 만든 CPU입니다" 선언 문구를 배치한다.

3. **Ch07 인수인계 이슈 완전 해소**: `pc_src=2'b01`(JAL), JALR 하위 1비트 클리어, `mem_read` IF/MEM 분리 — 이 3가지를 8.2~8.3절에서 명시적으로 처리하고 "Ch07 최종 승인서에서 보류된 이슈가 여기서 해소됩니다"라는 문구로 완결감 제공.

4. **8.6절 과도한 확장 방지**: 마이크로프로그래밍은 800자 이내로 엄격히 제한. 코드 구현 실습 없음.

### 기술 저자에 대한 권고사항

1. **8.2절을 두 소절(8.2.1 공통 경로, 8.2.2 명령어별 분기)로 분할 고려**: 상태 설계가 너무 밀도 높을 경우 절 중간에 "지금까지 추가한 상태: N개" metacognition 박스 삽입.

2. **8.4절 검증 프로그램을 반드시 사전 실행 확인**: 제공하는 어셈블리 코드가 Ch08 FSM에서 실제로 정확히 실행됨을 집필 전 시뮬레이션으로 검증.

3. **8.5절 CPI 수치의 근거 명시**: R:4, Load:5, Store:4, Branch:3 수치는 상태 수에서 직접 계산됨을 수식으로 보여줄 것. "CPI = 해당 명령어의 FSM 상태 수"라는 연결이 핵심.

4. **8.7절 Ch09 연결 문장 필수 배치**: 위의 핵심 연결 문장을 반드시 포함. Part 4 진입 동기 유발의 핵심 역할.

5. **Ch07 최종 승인서 인수인계 항목 체크리스트 작성 후 집필**: 5개 항목(PCSrc, JALR, MDR FSM 분리, reg_dst, 메모리 접근 종류) 중 Ch08에서 처리할 항목을 먼저 정리.
