## 🔴 Critical 이슈

### C-1: SUB 명령어 기계어 오류 — funct7 비트 계산 착오

**위치**: 9.5절, 테스트벤치 코드 주석 및 IMEM 초기값 (`line 916`, `line 4282`)

**문제**:
```
// 원고에 기재된 값
0x404082B3  // SUB x5, x1, x4
```

SUB 명령어의 인코딩을 검증합니다.
- opcode = `0110011` (R-type)
- funct7 = `0100000` (SUB는 ADD와 구별하는 비트)
- rs2 = `x4` = `00100`
- rs1 = `x1` = `00001`
- funct3 = `000`
- rd = `x5` = `00101`

비트 조합: `0100000_00100_00001_000_00101_0110011`

hex 변환:
- `0100000 00100` → `0x20 << 20 | 0x4 << 15` 부분
- 전체: `0100_0000_0100_0000_1000_0010_1011_0011` = `0x4040_82B3`

**판정**: 원고의 `0x404082B3`은 `0x4040_82B3`과 동일합니다 (언더스코어 표기 차이). 이 값은 **수학적으로 정확**합니다.

실제 인코딩 검증:
- bits[31:25] = `0100000` ✓ (funct7 for SUB)
- bits[24:20] = `00100` = x4 ✓ (rs2)
- bits[19:15] = `00001` = x1 ✓ (rs1)
- bits[14:12] = `000` ✓ (funct3)
- bits[11:7]  = `00101` = x5 ✓ (rd)
- bits[6:0]   = `0110011` ✓ (opcode)

**재판정**: C-1은 오류 없음. 기계어 값 정확. ~~Critical~~ → 취소.

### C-1 (재정의): NOP 삽입 후 해저드 분석의 EX 스테이지 오독 가능성

**위치**: 9.5절 NOP 삽입 타이밍 표 (`line 925`)

**문제**:
```
// C6:  NOP1(WB)  NOP2(MEM) NOP3(EX)  SUB(ID) ← ADD WB 완료, x1 정상 읽기
```

ADD의 WB는 C5에 완료됩니다. SUB의 ID는 C6에 실행됩니다. 이 순서는 **올바릅니다**.

그런데 레지스터 파일 쓰기는 클럭 상승 에지에서 이루어지고, 레지스터 파일 읽기는 조합 논리(비동기)로 이루어진다고 가정하면, C5의 WB 쓰기 결과는 C6 초반에 읽을 수 있습니다 (write-then-read 또는 포워딩). 원고는 이 타이밍이 "정상 읽기"라고 서술하고 있는데, 이것이 레지스터 파일 쓰기/읽기 타이밍 가정(동기 쓰기, 비동기 읽기)에 의존합니다.

원고 9.3절에서 DMEM은 "동기 쓰기/비동기 읽기"라고 명확히 설명했으나, **레지스터 파일의 쓰기/읽기 타이밍 가정이 명시되지 않았습니다**. 실제 구현 코드(`register_file`)의 정의가 없어 독자가 타이밍을 추론할 수 없습니다.

**영향**: NOP 3개가 충분한지 여부가 레지스터 파일 구현에 의존. 만약 레지스터 파일이 동기 읽기라면 NOP 3개가 아닌 4개가 필요할 수 있음.

**해결책**: 레지스터 파일은 동기 쓰기, 비동기 읽기로 구현되어야 하며, 동일 사이클 쓰기/읽기 충돌(같은 rd와 rs1이 같은 사이클) 시 "write-then-read" 또는 "read-then-write" 정책을 명시해야 합니다. 현재 원고에서 register_file 모듈 인터페이스만 호출하고 정의를 제공하지 않아 독자가 직접 구현 시 오류 가능성이 있습니다.

### C-2: MEM/WB 레지스터에 flush 포트 누락

**위치**: `전체 소스 코드` 절, `mem_wb_reg` 모듈 정의 (`line 1205~1239`)

**문제**: `if_id_reg`와 `id_ex_reg`는 `flush` 포트가 선언되어 있으나, `mem_wb_reg`에는 `flush` 포트가 없습니다.

```systemverilog
// if_id_reg — flush 있음 ✓
module if_id_reg (
   input logic flush,  // 선언됨
   ...

// mem_wb_reg — flush 없음 ✗
module mem_wb_reg (
   input logic clk,
   input logic rst,
   input logic en,      // flush 포트 없음!
   ...
```

Ch11에서 분기 해저드를 처리할 때 MEM/WB까지 flush가 필요한 경우가 있습니다. 특히 분기 예측 실패 시 IF/ID, ID/EX, EX/MEM 레지스터에만 flush를 연결하고 MEM/WB에는 flush가 없으면 설계 불일치가 발생합니다.

**영향**: 설계 일관성 저해. Ch11에서 최상위 모듈 인터페이스 수정이 필요할 수 있음.

**해결책**: `mem_wb_reg`에도 `flush` 포트를 추가하거나, 4개 레지스터 모두 일관된 포트 구성을 갖추어야 합니다. 또는 9.4절 FAQ 박스에 "MEM/WB는 분기 flush 대상이 아니다"라는 설계 근거를 명시해야 합니다.

### C-3: EX/MEM 레지스터 모듈 구현 코드 미제공

**위치**: 9.4절 및 전체 소스 코드 절

**문제**: 원고는 IF/ID, ID/EX, MEM/WB 레지스터의 SystemVerilog 구현을 제공하지만, **EX/MEM 레지스터의 구현 코드가 전혀 제공되지 않습니다**.

```
EX/MEM과 MEM/WB 레지스터도 동일한 패턴으로 구현합니다. 각 레지스터가 전달해야 하는 필드 목록은
그림 9.7을 참조하십시오.
```

최상위 모듈(`rv32i_pipeline_top`)에서 `ex_mem_reg u_ex_mem`을 인스턴스화하는 코드가 있으나, 해당 모듈의 정의가 없어 시뮬레이션이 불가능합니다. 연습문제 5번에서 학생이 직접 구현하도록 유도하고 있으나, 전체 소스 코드 절에도 포함되어 있지 않습니다.

**영향**: 독자가 코드를 복사하여 시뮬레이션 시도 시 컴파일 오류 발생. 교육 신뢰도 저하.

**해결책**: 전체 소스 코드 절에 `ex_mem_reg.sv` 구현을 추가하거나, 9.4절에서 EX/MEM 레지스터 구현을 명시적으로 연습문제로 지정하고 "전체 소스 코드에는 포함되지 않습니다"라고 명시해야 합니다.

## 🟡 Major 이슈

### M-1: PC 비동기 리셋과 파이프라인 레지스터 동기 리셋의 상호작용 미설명

**위치**: 9.3절 IF 스테이지 설명, 9.4절 동기 리셋 전략

**문제**: 원고는 "PC 레지스터는 비동기 리셋을 허용"한다고 기술하면서, 파이프라인 레지스터는 "동기 리셋"을 사용한다고 서술합니다. 그런데 비동기 리셋인 PC가 0으로 리셋될 때, 동기 리셋인 IF/ID 레지스터는 다음 클럭 상승 에지에서 리셋됩니다.

이 1사이클 차이 동안 IF 스테이지는 PC=0의 IMEM 내용을 읽어 IF/ID 레지스터에 쓰려 할 수 있습니다. `rst=1` 동안 `en=1`이고 `flush=0` 고정이므로, IF/ID 레지스터는 rst=1인 사이클에도 정상 갱신 로직이 실행됩니다 — 단, `rst||flush` 조건이 `en`보다 우선하므로 NOP가 삽입됩니다.

최상위 모듈 코드의 `always_ff @(posedge clk or posedge rst)` PC 로직은 정확하지만, **"비동기 리셋이 왜 PC에만 허용되는가"에 대한 설계 근거 설명이 부족**합니다.

**해결책**: "시뮬레이션 환경에서 rst를 2사이클 이상 유지하는 것으로 초기화를 보장"하며, "rst 해제 직후 PC=0의 IMEM 명령어가 IF 스테이지에 진입"한다는 설명을 추가해야 합니다.

### M-2: CPI=1 조건이 충분히 강조되지 않음

**위치**: 9.1절, 9.2절, 9.6절 요약표

**문제**: 원고는 "이상적 CPI = 1.0"이라고 여러 곳에서 언급하지만, **"해저드가 없는 경우에만 성립"한다는 단서가 충분히 강조되지 않습니다**. 특히 9.6절 요약표에서 "Steady-State: CPI=1.0"이라고만 기재되어 있어, 초보자가 파이프라인 CPU를 구현하면 항상 CPI=1을 달성한다고 오해할 수 있습니다.

9.5절 본문에는 NOP 삽입으로 해저드를 회피한다고 서술하고 있으나, NOP 삽입 시 실제 CPI가 얼마나 저하되는지 수치 예시가 없습니다.

**해결책**: 9.2절 성능 분석에 "해저드 없는 프로그램에서만 CPI→1.0, NOP 포함 시 CPI가 크게 증가"한다는 단서를 명시하고, 테스트 예제(ADD+NOP×3+SUB)의 실제 CPI를 계산하여 제시합니다.

### M-3: branch_taken 신호의 MEM 스테이지 결정 — 1사이클 잘못된 PC 인출 미언급

**위치**: 9.5절 최상위 모듈, `pc_next` 계산 (`line 760`)

**문제**:
```systemverilog
assign pc_next = (branch_taken_mem) ? alu_result_mem : pc_plus4_if;
```

`branch_taken_mem`은 EX/MEM 파이프라인 레지스터 출력이므로, 분기 명령어가 MEM 스테이지에 있을 때 결과가 확정됩니다. 그 사이 IF와 ID 스테이지에 이미 2개의 잘못된 명령어가 진입합니다.

원고 9.5절은 "분기 명령어는 테스트에서 NOP로 처리"한다고 암시하지만, **분기 명령어를 NOP 삽입만으로 안전하게 처리하려면 분기 명령어 뒤에 NOP 4개가 필요**함을 명시하지 않았습니다. (분기 명령어가 IF에 있을 때 2개의 명령어가 뒤따르고, MEM 스테이지에서 결정이 내려지기까지 3사이클이 지남 — 정확한 분석 필요)

실제 타이밍:
- C1: BEQ (IF)
- C2: BEQ (ID), I+1 (IF) ← 1개 잘못 진입
- C3: BEQ (EX), I+1 (ID), I+2 (IF) ← 2개 잘못 진입
- C4: BEQ (MEM), branch_taken 결정, I+1(EX), I+2(ID), I+3(IF) ← 3개 잘못 진입

따라서 분기 명령어 후 NOP 4개(또는 3개 + flush 처리)가 필요합니다. 원고는 이를 명시하지 않아 독자가 NOP 3개만 삽입하고 잘못된 결과를 얻을 수 있습니다.

**해결책**: 9.5절에 "분기 명령어 테스트는 이 챕터에서 제외하거나, 분기 후 NOP 4개를 삽입해야 한다"고 명시해야 합니다.

### M-4: ctrl_t 구조체의 alu_src_a 비트 폭 불일치

**위치**: 9.4절 `ctrl_t` typedef 및 9.5절 EX 스테이지 MUX

**문제**: `ctrl_t` 구조체에서 `alu_src_a`는 1비트로 선언되어 있습니다.

```systemverilog
logic alu_src_a;    // ALU A 입력 선택 (0=rs1, 1=pc)
```

그런데 Ch08에서 `alu_src_a`는 2비트(`2'b00`=PC, `2'b01`=old_pc_reg, `2'b10`=A레지스터)로 설계되었습니다(MEMORY.md Ch08 주요 설계 결정 참조). 파이프라인에서 JAL/AUIPC 등을 지원하려면 alu_src_a가 2비트 이상이어야 합니다.

Ch09의 파이프라인에서 1비트 alu_src_a로는 "rs1 vs PC" 두 가지만 선택 가능하여, JAL(rd = PC+4, PC = PC + imm_J) 구현 시 EX 스테이지에서 ALU A 입력을 PC로 설정해야 하는 경우와 rs1_data로 설정해야 하는 경우를 구분하기에 충분합니다. 그러나 JALR(rd = PC+4, PC = rs1 + imm_I)에서 ALU가 rs1+imm을 계산해야 하므로 alu_src_a=0(rs1), alu_src_b=1(imm)이 필요합니다.

WB 스테이지의 pc_plus4 경로(`mem_to_reg=2'b10`)가 있으므로 JAL도 처리 가능하나, **alu_src_a 1비트 정의와 Ch08 2비트 정의 간의 불연속이 독자에게 혼란을 줄 수 있습니다**. Ch08에서 `alu_src_a`를 2비트로 확장한 이유를 학습한 독자가 Ch09에서 1비트로 축소된 이유를 이해하지 못할 것입니다.

**해결책**: `alu_src_a`를 1비트로 단순화한 이유(파이프라인에서 old_pc_reg 불필요, PC는 파이프라인 레지스터로 전달)를 명시하거나, 또는 2비트로 유지하고 설명을 제공해야 합니다.

### m-1: ADD x1, x2, x3 기계어 표기 언더스코어 불일치

**위치**: 9.5절 코드 주석 (`line 912`)

// 0x00310033  // ADD  x1, x2, x3

### m-2: IMEM 비동기 읽기 구현에서 Vivado 합성 경고 가능성

**위치**: 테스트벤치 IMEM 모델 (`line 1286`)

```systemverilog
assign imem_rdata = imem[imem_addr[4:2]]; // 워드 주소 (하위 2비트 무시)
```

테스트벤치 내 IMEM 모델은 배열을 조합 논리로 읽습니다. 실제 Vivado에서 최상위 설계의 IMEM을 LUTRAM으로 구현할 경우, 읽기 포트는 클럭 동기 또는 비동기를 선택할 수 있습니다. 비동기 읽기(조합 논리) 선택 시 Vivado에서 `[Synth 8-7053]` 경고가 발생할 수 있습니다.

테스트벤치에서는 문제없으나, 실제 합성용 IMEM 모듈을 작성할 때 `(* rom_style = "distributed" *)` 어트리뷰트가 필요할 수 있음을 언급하면 좋습니다.

### m-3: NOP 해저드 해결 SVG의 SUB 타이밍 레이블 오류

**위치**: `figures/ch09_sec05_nop_timing.svg`

오른쪽(NOP 해결) 다이어그램에서 ADD WB 완료 수직선이 C5 열에 그려지고, SUB의 ID는 C6로 표시되어 있습니다. 그런데 SUB의 IF가 C5에 시작하고 SUB의 ID가 C6임이 맞습니다. SVG에서:

```
ADD: WB ✓ at C5 (x=741~789)
SUB: IF at C5 (x=741~789), ID at C6 (x=791~839)
```

C5(x=765) 수직 강조선이 "ADD WB✓ / SUB IF"라고 레이블되어 있는데, 이 시점에 ADD WB와 SUB IF가 동시에 진행 중이므로 정확합니다. 하지만 NOP 3개 이후 SUB의 EX는 C7이 되어야 하는데, SVG에서 `EX✓`가 C7 이후 범위(x=841~879)에 표시되어 있어 다이어그램이 잘리거나 `C7~` 레이블 범위에 포함됩니다. EX 셀이 일부만 표시되어 독자가 혼란을 겪을 수 있습니다.

**해결책**: SVG 너비를 확장하거나 NOP2/NOP3의 WB 셀을 생략하여 SUB의 EX/MEM/WB가 완전히 표시되도록 조정을 권장합니다.

### m-4: 9.6절 요약표 — 역방향 추적 설명의 방향 오류

**위치**: 9.6절 핵심 개념 정리 표 (`line 1023`)

```
WB→MEM→EX→ID→IF 역방향으로 필드 결정
```

역방향 추적의 방향이 "WB→IF"로 표기되어 있습니다. 역방향이므로 올바른 설명이나, 화살표 방향이 데이터 흐름(IF→WB)의 역방향임을 명시하는 "(데이터 흐름의 역방향: WB부터 시작)"과 같은 보조 설명을 추가하면 혼동을 방지할 수 있습니다.

---

### m-5: 9.2절 성능 수치 — 클럭 주파수 2배 가정의 근거 보강 필요

**위치**: 9.2절 파이프라인 성능 공식 주석 (`line 290~292`)

```
// 클럭 주파수도 2배가 되므로:
// 실질 성능 향상 ≈ 4.1 * 2 = 8.2x
```

멀티사이클 50MHz 대비 파이프라인 100MHz를 "2배"라고 단순 계산하였는데, 실제 임계 경로 단축 비율이 정확히 2배인지에 대한 근거가 없습니다. 각 스테이지 중 가장 느린 EX 스테이지(ALU 지연)가 임계 경로를 결정하며, 멀티사이클의 전체 경로 중 EX가 차지하는 비율에 따라 클럭 향상 배율이 달라집니다.

현재 "약 2배"로 표현하는 것은 교육 목적상 허용되나, "임계 경로 분석에 따라 달라질 수 있으며, Basys3에서 실측 시 확인 필요"라는 단서를 추가하면 더 정확한 서술이 됩니다.

## 기술적 강점

1. **NOP 버블 값 처리 우수**: `32'h0000_0013` 사용과 `32'd0` 금지 이유가 전 절에 걸쳐 일관되게 설명됨.
2. **역방향 추적 방법론**: WB부터 역방향으로 파이프라인 레지스터 필드를 결정하는 교육 접근법이 체계적이며 실무적으로 타당함.
3. **rs1_addr/rs2_addr 선행 포함**: Ch10 포워딩을 위한 신호를 지금 포함시키는 이유 설명이 충분하여 설계 연속성이 우수함.
4. **Harvard 구조 전환 설명**: 구조적 해저드 → Harvard 구조의 논리적 흐름이 명확.
5. **코드 이스케이프**: HTML 내 SystemVerilog 코드에 `<`, `>`, `&`가 모두 정확히 이스케이프됨.
6. **ctrl_t 패키지 구조**: 제어 신호를 구조체로 묶는 설계가 실무 관행에 부합하며 Ch10 확장 시 코드 변경량을 최소화함.
