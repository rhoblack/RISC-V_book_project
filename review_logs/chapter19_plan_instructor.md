### 비유 1: "응급실 트리아지(Triage)" — 예외와 인터럽트의 차이, 인터럽트 우선순위

**실생활 장면**
응급실에는 두 종류의 환자가 옵니다. 첫 번째는 의사가 수술하다가 "수술 도구가 없다"처럼 치료 행위 자체에서 발생한 문제(동기 예외)입니다. 두 번째는 진료 중에 구급차 사이렌 소리가 들려오는 것처럼 외부에서 갑자기 들어오는 긴급 상황(비동기 인터럽트)입니다.

트리아지 간호사는 중증도에 따라 처치 순서를 결정합니다. 외상(MEI, 최우선) > 내출혈 의심(MSI) > 발열(MTI, 타이머) 순서로 처리합니다. 중요한 것은, 이미 진행 중인 수술(완료된 명령어)은 멈추지 않고, 대기 중인 환자들(파이프라인 후속 명령어)을 내보내는 것입니다.

**하드웨어 매핑**
| 비유 요소 | 하드웨어 요소 |
|----------|------------|
| 수술 중 발생한 도구 문제 | 동기 예외 (Illegal Instruction, Misaligned) |
| 구급차 사이렌 (외부 유입) | 비동기 인터럽트 (외부 IRQ, 타이머 IRQ) |
| 트리아지 간호사 | exception_unit의 우선순위 결정 조합 로직 |
| MEI > MSI > MTI 처치 순서 | 인터럽트 우선순위 (MEI > MSI > MTI) |
| 이미 완료된 수술 | 예외 명령어 이전의 정상 완료 명령어 |
| 대기실 환자 내보내기 | 파이프라인 플러시 (후속 명령어 취소) |

**비유의 한계 (명시 필요)**
응급실에서는 환자를 "나중에 다시 처리"할 수 있습니다. 그러나 파이프라인에서 플러시된 명령어는 트랩 핸들러 종료 후 mepc 주소로 복귀하여 재실행됩니다. "내보낸 환자를 다시 데려온다"는 개념이 추가됩니다.

### 비유 2: "비행기 블랙박스(Black Box) + 자동 조종 장치 긴급 해제" — 트랩 진입/복귀 시퀀스

**실생활 장면**
비행기에 이상 상황이 발생하면 두 가지 일이 동시에 일어납니다. 블랙박스(mepc, mcause)가 현재 상황을 기록하고, 자동 조종(인터럽트 인에이블, mstatus.MIE)이 비활성화되어 기장이 수동 조종(트랩 핸들러)으로 전환합니다. 비상 처리가 끝나면 기록된 데이터를 바탕으로(mepc → 복귀 주소) 자동 조종이 재활성화됩니다(MRET).

블랙박스가 기록 중인데 새로운 이상 신호가 쏟아지면 기록이 덮어써집니다. 그래서 자동 조종을 먼저 끄고(MIE 클리어) 블랙박스 기록을 안전하게 마친 후 이상 원인 코드를 저장하는 것입니다.

**하드웨어 매핑**
| 비유 요소 | 하드웨어 요소 |
|----------|------------|
| 블랙박스 | mepc (복귀 PC 저장), mcause (예외 코드 저장) |
| 자동 조종 비활성화 | mstatus.MIE ← 0 (인터럽트 전역 마스크) |
| 수동 조종 (기장 개입) | 트랩 핸들러 실행 (PC ← mtvec) |
| 자동 조종 재활성화 | MRET 후 mstatus.MIE ← MPIE 복원 |
| 새 이상 신호가 기록을 덮어씀 | 중첩 트랩(nested trap)으로 mepc 파괴 |

**비유의 한계 (명시 필요)**
비행기 블랙박스는 연속 기록이지만, RISC-V mepc는 단 하나의 PC 값만 저장합니다. 중첩 트랩을 지원하려면 mscratch 레지스터를 사용하여 소프트웨어가 컨텍스트를 스택에 저장해야 합니다(본 교재 범위 밖 — Part 9 심화 주제).

### 비유 3: "도미노 줄 쓰러뜨리기 중단" — 정확한 예외(Precise Exception) 보장

**실생활 장면**
도미노 5개가 차례로 쓰러지고 있습니다(파이프라인 5단계에 명령어가 흐릅니다). 세 번째 도미노가 쓰러지는 순간 "금지 구역 침범"(동기 예외)이 감지되었습니다. 규칙은 명확합니다: 이미 쓰러진 도미노 1번, 2번은 그냥 두고(이전 명령어 완료), 아직 쓰러지지 않은 4번, 5번은 손으로 잡아 세웁니다(이후 명령어 취소). 예외가 처리된 후에는 3번 도미노부터 다시 시작합니다(mepc로 복귀 재실행).

이것이 정확한 예외입니다. "정확하지 않은 예외"는 4번이 이미 쓰러진 후에야 3번의 문제를 발견하는 것으로, 어떤 도미노까지 무효인지 알 수 없어 시스템 상태를 신뢰할 수 없게 됩니다.

**하드웨어 매핑**
| 비유 요소 | 하드웨어 요소 |
|----------|------------|
| 도미노 5개 | 파이프라인 5단계(IF/ID/EX/MEM/WB)에 흐르는 명령어들 |
| 세 번째 도미노 침범 | MEM 스테이지에서 감지된 Load Misaligned 예외 |
| 이미 쓰러진 1~2번 (그대로) | WB/MEM 완료 명령어 (취소 불가) |
| 4~5번 잡아 세우기 | EX/ID/IF 스테이지 명령어 플러시 |
| 3번부터 재시작 | mepc에 저장된 예외 명령어 PC로 MRET 복귀 |

**비유의 한계 (명시 필요)**
비동기 인터럽트는 "도미노가 쓰러지는 도중 외부에서 누군가 손을 올리는" 상황입니다. 이때 mepc에는 "현재 진행 중인 가장 오래된 명령어의 다음 PC"를 저장합니다(인터럽트 수용 시점 이전 명령어들은 이미 정상 완료되었으므로). 동기 예외와 mepc 저장 기준이 다름을 학생들에게 반드시 구분시켜야 합니다.

### 비유 4: "공항 보안 검색대 우선순위 레인" — 동기 예외 우선순위 (MEM > EX > ID)

**실생활 장면**
공항 보안 검색대에서 세 개 레인에 동시에 문제가 발생했습니다. MEM 레인에서는 가방에서 금속이 감지되어 경보가 울리고(심각), EX 레인에서는 탑승권 정보 불일치(중간), ID 레인에서는 서류 누락(경미)이 발생했습니다. 보안요원은 가장 뒤쪽(MEM) 레인의 문제부터 처리합니다 — 왜냐하면 그 레인의 승객이 "더 많이 처리된" 상태이기 때문입니다. 먼저 처리된 것이 우선입니다.

**하드웨어 매핑**
파이프라인에서 MEM 스테이지의 명령어는 ID 스테이지 명령어보다 먼저 실행을 시작했으므로 프로그램 순서상 앞의 명령어입니다. 정확한 예외는 프로그램 순서상 "가장 먼저" 예외를 발생시킨 명령어를 처리해야 하므로 MEM 우선입니다.

**비유의 한계 (명시 필요)**
실제로는 "여러 스테이지에서 동시 예외 발생"보다 "한 스테이지에서만 예외 발생"이 훨씬 빈번합니다. 우선순위 로직은 동시 발생이라는 엣지 케이스를 올바르게 처리하기 위한 방어적 설계입니다.

### 비유 5: "회사 내선전화 전달 규칙" — mstatus.MIE + mie + mip 3단 마스킹

**실생활 장면**
회사에 긴급 전화가 걸려왔습니다. 전화가 연결되려면 세 가지 조건이 모두 충족되어야 합니다:
1. 회사 전체 전화 교환기가 켜져 있어야 합니다(mstatus.MIE = 1: 전역 인에이블).
2. 해당 부서의 내선 전화가 활성화되어 있어야 합니다(mie 비트 = 1: 개별 인터럽트 마스크).
3. 실제로 전화가 걸려오고 있어야 합니다(mip 비트 = 1: pending 상태).

세 조건 중 하나라도 0이면 전화는 연결되지 않습니다.

**하드웨어 매핑**: `인터럽트 수용 = mstatus.MIE AND mie[해당 비트] AND mip[해당 비트]`

### "아하!" 포인트 1: 예외와 인터럽트는 처리 방식이 다른 이유 (19.2~19.3절)

**설명 전략**
학생들이 "왜 예외와 인터럽트를 따로 나눠 처리하나?"라고 묻기 전에 먼저 물어보세요:

> "여러분이 직접 밥을 먹다가 젓가락을 떨어뜨린 경우(예외)와, 밥 먹다가 핸드폰이 울린 경우(인터럽트)를 생각해보세요. 둘 다 '지금 하던 일을 멈춘다'는 공통점이 있는데, 차이가 있나요?"

학생들이 "핸드폰은 언제 울릴지 모른다"고 답하면 이렇게 연결합니다:

> "맞습니다. 예외는 특정 명령어가 실행될 때만 발생합니다(재현 가능). 인터럽트는 어느 순간이든 발생할 수 있습니다(비결정적). 파이프라인에서 이 차이가 중요한 이유는 — 예외는 '어느 명령어에서 발생했는가'를 정확히 알 수 있지만, 인터럽트는 '어느 명령어가 완료되는 시점에 수용할 것인가'를 하드웨어가 결정해야 하기 때문입니다."

### "아하!" 포인트 2: 트랩 진입 시퀀스의 순서가 왜 중요한가 (19.4절)

**설명 전략**
트랩 FSM 다이어그램을 보여주면서 먼저 "틀린 순서"로 설명하세요:

> "만약 MIE를 마지막에 끈다고 해봅시다. mepc에 복귀 주소를 저장하는 도중, 타이머 인터럽트가 새로 들어옵니다. 그러면 mepc가 덮어써집니다. 우리가 돌아가야 할 주소가 사라진 것입니다."

학생들의 표정에서 "아!" 하는 반응이 나오면 바로 이어서:

> "그래서 S_TRAP_MEPC 상태에서 mepc를 저장하기 전에, 현재 트랩 FSM이 동작 중임을 표시(trap_active)하여 새 트랩 수용을 막는 것입니다. 이 순서 하나가 무한 트랩 루프와 정상 동작의 차이입니다."

### "아하!" 포인트 3: 정확한 예외가 왜 어려운가 (19.5절)

**설명 전략**
파이프라인 타이밍 다이어그램(`ch19_sec05_precise_exception.svg`)을 슬라이드에 띄우고 다음 시나리오를 단계별로 진행하세요:

> "사이클 5에서 파이프라인에 무슨 일이 벌어지고 있나요? — IF에는 명령어 D, ID에는 C, EX에는 B, MEM에는 A가 있습니다. 이 순간 A가 Misaligned Load 예외를 발생시킵니다. 질문: 이 시점에 B는 EX 연산을 완료했습니까?"

학생들이 "예"라고 답하면:

> "그렇습니다. B는 이미 EX 연산 결과가 파이프라인 레지스터에 저장되어 있습니다. 하지만 아직 MEM 접근을 하지 않았으므로 메모리에 부작용을 남기지 않았습니다. WB도 하지 않았으므로 레지스터에도 결과를 쓰지 않았습니다. B, C, D는 모두 플러시해도 아무 흔적이 없습니다. 이것이 정확한 예외가 RV32I 파이프라인에서 구현 가능한 이유입니다."

이어서:

> "만약 Out-of-Order 프로세서라면? B가 A보다 먼저 WB를 완료했을 수도 있습니다. 그때 정확한 예외는 훨씬 복잡해집니다. RV32I 순서 실행 파이프라인은 이 점에서 훨씬 단순합니다."

### "아하!" 포인트 4: CSR 해저드가 왜 일반 해저드와 다른가 (19.5절)

**설명 전략**
칠판에 두 개의 경로를 나란히 그립니다:

```
[일반 RAW 해저드]  ADD x1, x2, x3 → ADD x4, x1, x5
                   EX→EX 포워딩 경로 존재 (레지스터 파일 외부 우회)

[CSR RAW 해저드]   CSRRW x0, mstatus, x1 → CSRRS x2, mstatus, x0
                   CSR은 레지스터 파일과 별도 포트 — 포워딩 경로 없음!
```

> "Ch10에서 만든 포워딩 유닛은 범용 레지스터 파일(x0~x31)을 위한 것입니다. CSR은 완전히 별도의 읽기/쓰기 포트를 사용합니다. 그래서 CSR 해저드 처리를 위한 별도 경로가 필요합니다 — 또는 가장 간단한 해결책은 CSR 명령어를 만나면 무조건 2사이클 스톨을 삽입하는 것입니다."

## 자주 묻는 질문 예측

### Q1: "인터럽트는 '언제든' 발생한다고 했는데, 클럭 중간에 발생하면 어떻게 됩니까?"

**예상 시점**: 19.3절 비동기 인터럽트 개념 설명 직후

**답변**:
실제 하드웨어에서 인터럽트 신호는 클럭에 무관하게 들어옵니다. 그러나 파이프라인은 인터럽트를 클럭 엣지(스테이지 경계)에서만 "수용"합니다. 인터럽트 신호가 들어오면 `mip` 레지스터에 pending 비트가 세워지고, 파이프라인은 다음 클럭 엣지에서 이 pending 비트를 확인하여 수용 여부를 결정합니다. 즉, 실제 발생 시점과 수용 시점 사이에는 0~1 클럭 주기의 차이가 있습니다. 이것이 인터럽트 응답 시간(latency)의 최소 단위입니다.

`<aside class="faq">` 박스로 원고에 삽입 권고.

### Q2: "예외가 MEM 스테이지에서 감지되면, EX 스테이지의 명령어는 이미 ALU 연산을 완료했는데 그 결과는 어떻게 됩니까?"

**예상 시점**: 19.5절 정확한 예외 설명 중

**답변**:
EX 스테이지 명령어의 ALU 연산 결과는 EX/MEM 파이프라인 레지스터에 저장되어 있습니다. 플러시 명령이 내려지면 이 파이프라인 레지스터가 버블(bubble)로 교체됩니다. ALU 연산 자체는 조합 로직이고 부작용이 없습니다 — 레지스터 파일에 값이 쓰여지는 것은 WB 스테이지에서만 일어납니다. 따라서 EX 스테이지 명령어를 플러시해도 아키텍처 상태(레지스터 파일, 메모리)에는 아무 변화가 없습니다. 이것이 In-Order 파이프라인에서 정확한 예외가 가능한 핵심 이유입니다.

### Q3: "mepc에 저장되는 값이 예외 명령어 PC입니까, 아니면 예외 명령어의 다음 PC입니까?"

**예상 시점**: 19.4절 트랩 진입 시퀀스 설명 중

**답변**:
동기 예외와 비동기 인터럽트에 따라 다릅니다.

- **동기 예외**: mepc = 예외를 발생시킨 명령어의 PC. MRET 후 해당 명령어부터 재실행됩니다(재시도 의미). 단, ECALL과 EBREAK는 트랩 핸들러가 완료를 의미하므로 소프트웨어가 mepc += 4 후 MRET하는 것이 관례입니다.

- **비동기 인터럽트**: mepc = 인터럽트가 수용된 시점에 완료되지 않은 가장 오래된 명령어의 PC. MRET 후 해당 명령어부터 재실행됩니다(중단 지점 재개 의미).

이 구분을 표로 정리하여 원고 19.4절에 배치 권고.

### Q4: "MRET를 실행할 때 특권 수준이 없는 M-mode 전용 구현에서 MPP 처리를 생략해도 됩니까?"

**예상 시점**: 19.4절 MRET 설명 후, 또는 19.7절 자가 점검 질문 토론 중

**답변**:
본 교재의 구현은 M-mode 단일 특권 수준만 지원합니다. RISC-V 스펙에서 MPP 필드는 MRET 실행 시 이전 특권 수준(Machine/Supervisor/User)으로 복원하는 역할을 합니다. M-mode 전용 구현에서는 항상 M-mode로 복귀하므로 MPP 처리를 생략해도 동작에 문제가 없습니다. 단, 이 단순화를 소스 코드 주석과 원고에 명시해야 합니다. Linux 같은 운영체제를 탑재하려면 S-mode, U-mode 추가 구현이 필요하며 이때 MPP 처리가 필수입니다.

`<aside class="interview">` 박스 삽입 권고: "면접 빈출 — '인터럽트 처리 시 특권 수준 전환을 어떻게 구현했는가?'"

### Q5: "예외 처리 로직이 파이프라인 타이밍에 미치는 영향은 어느 정도입니까?"

**예상 시점**: 19.5절 통합 설명 완료 후, 또는 19.6절 테스트벤치 실습 후

**답변**:
기술 저자 기획안에 따르면 예외 처리 유닛(`exception_unit`)과 트랩 컨트롤러(`trap_controller`) 추가로 약 200~300 LUT 증가가 예상됩니다. 임계 경로에 대한 직접적 영향은 제한적이나, `exception_unit`의 우선순위 결정 조합 로직이 MEM 스테이지 지연에 소량 추가될 수 있습니다. Ch20(FPGA 합성 최적화)에서 `report_timing`으로 직접 확인하는 실습이 이어집니다. "설계 선택의 비용을 측정하는 것" 자체가 엔지니어의 역량임을 강조하세요.

"오늘 우리가 만들 기능을 설명하기 전에, 질문 하나 드리겠습니다."

"여러분 스마트폰에서 앱을 쓰다가 전화가 오면 어떻게 됩니까?"

*학생 답변 유도: "전화 화면으로 전환됩니다"*

"맞습니다. 그런데 그게 당연한 게 아닙니다. CPU 입장에서는 지금 인스타그램 앱의 화면 렌더링 루틴을 정확히 어느 줄까지 실행했는지, 스택에 어떤 값들이 쌓여 있었는지, 어느 레지스터에 어떤 값이 있었는지 — 이 모든 것을 정확히 기억해야 전화가 끝난 후 인스타그램을 '끊긴 지점 그대로' 재개할 수 있습니다."

*칠판에 간단히:*
```
인스타 실행 중 → 전화 수신 → 전화 처리 → 인스타 재개
                    ↑                            ↑
                  mepc 저장                   MRET
```

"오늘 우리가 만드는 것이 바로 이것입니다. 그런데 우리 프로세서에는 난이도를 높이는 요소가 하나 있습니다."

*다시 학생들을 바라보며.*

"우리 프로세서는 5단 파이프라인입니다. 지금 이 순간에도 5개 명령어가 동시에 처리 중입니다. 전화가 오는 순간, 이 5개 명령어 중 몇 개는 완료해야 하고, 몇 개는 취소해야 합니다. 어디까지 완료하고 어디서부터 취소해야 할지 — 이것을 '정확한 예외(precise exception)'라고 합니다."

*Ch19 절 구성 슬라이드 전환.*

"19.1절에서 여러분의 기존 파이프라인 지식을 30초만 확인하겠습니다. 그리고 19.5절에서 오늘의 핵심 도전을 함께 풀어봅시다."

---

**도입부 설계 의도**:
- 스마트폰 전화 수신이라는 즉각적으로 친숙한 경험으로 시작
- 칠판 판서로 mepc/MRET의 역할을 추상적 수준에서 먼저 제시
- "5단 파이프라인"이라는 기존 지식과의 연결 고리 제시
- "정확한 예외"라는 핵심 용어를 직관적 언어로 미리 소개
- 총 5분 이내, 슬라이드 없이 시작하여 집중도 극대화

## 판서/시각화 전략

### 판서 포인트 1: 트랩 진입 시퀀스 5단계 (19.4절)

칠판 왼쪽에 세로 순서로 작성합니다. 각 단계는 색깔 마커로 구분합니다 (파란색=CSR 쓰기, 빨간색=제어 흐름 변경).

```
트랩 발생!
① mepc ← 예외 명령어 PC          [파란색]
② mcause ← 예외/인터럽트 코드    [파란색]
③ mtval ← 추가 정보 (주소 등)    [파란색]
④ mstatus.MIE ← 0 (인터럽트 마스크) [빨간색, 강조]
⑤ PC ← mtvec (핸들러로 점프)     [빨간색, 강조]
───────────────────────────
핸들러 실행
───────────────────────────
MRET 실행!
① mstatus.MIE ← mstatus.MPIE    [빨간색]
② mstatus.MPIE ← 1              [파란색]
③ PC ← mepc (원래 위치로 복귀)  [빨간색, 강조]
```

학생들에게 "이 순서를 외우지 않아도 됩니다 — 왜 이 순서인지만 이해하면, 스펙을 보면 항상 유도할 수 있습니다"라고 안심시킵니다.

### 판서 포인트 2: 정확한 예외 파이프라인 스냅샷 (19.5절)

슬라이드(`ch19_sec05_precise_exception.svg`)와 병행하여 칠판에 실시간으로 그립니다.

```
사이클 N에서의 스냅샷:

IF   | 명령어 D (아직 fetch 중)     → [플러시]
ID   | 명령어 C (decode 중)         → [플러시]
EX   | 명령어 B (ALU 연산 완료)     → [플러시]
MEM  | 명령어 A ← 예외 발생 ★       → [exception_unit 감지]
WB   | 명령어 Z (정상 완료)         → [그대로 진행]
```

화살표와 색깔 마커로 "플러시 경계선"을 명확히 표시합니다. 이 그림을 그리면서 "MEM 이전(WB)은 완료, MEM 이후(EX~IF)는 취소"라는 규칙을 반복합니다.

### 판서 포인트 3: 3단 인터럽트 마스킹 게이트 (19.3절)

슬라이드 도식 외에 칠판에 AND 게이트 직렬 연결을 즉석 작성합니다.

```
timer_irq ──────────────────────┐
                                AND ─── AND ─── 인터럽트 수용
mie[MTI 비트] ──────────────────┘       │
                                        │
mstatus.MIE ────────────────────────────┘
```

"이 세 조건이 모두 1이어야 합니다. 하나라도 0이면 타이머 인터럽트는 무시됩니다. 소프트웨어에서 `cli` (clear interrupt) 명령이 mstatus.MIE를 0으로 만들어 모든 인터럽트를 한번에 막는 이유가 이것입니다."

면접 빈출 순위 #8 — "예외와 인터럽트 처리 흐름" 대응

### 면접 예상 질문 1: "5단계 파이프라인에서 예외가 발생하면 어떻게 처리합니까?"

**모범 답변 구조 (학생들에게 제시)**:
1. 예외 감지 스테이지(ID/EX/MEM)를 먼저 밝힌다.
2. 감지 스테이지 이후 명령어들은 플러시됨을 언급한다.
3. mepc에 예외 명령어 PC 저장 후 mtvec로 점프한다고 설명한다.
4. MRET로 mepc로 복귀한다고 마무리한다.

**강조 포인트**: "정확한 예외(precise exception) 보장"이라는 용어를 반드시 언급하고, "이전 명령어 완료, 이후 명령어 취소"라는 정의를 말할 수 있으면 가점.

### 면접 예상 질문 2: "동기 예외와 비동기 인터럽트의 차이는 무엇입니까?"

- 동기 예외: 특정 명령어 실행의 직접적 결과, 재현 가능, mepc = 예외 명령어 PC
- 비동기 인터럽트: 외부 이벤트, 비결정적 발생, mepc = 수용 시점 이후 재개할 PC

### 긍정적 평가
1. **비유 사전 준비**: 기술 저자 기획안에서 "응급실 트리아지"와 "비행기 블랙박스" 비유가 이미 제시되어 있습니다. 두 비유 모두 강의 현장에서 활용 가능한 수준이며, 본 기획안에서 비유의 한계점 명시와 하드웨어 매핑 표를 추가하여 완성하였습니다.
2. **7절 난이도 곡선**: 교육 설계 기획안의 "완만 상승(19.1~19.2) → 가파른 상승(19.3~19.4) → 최고점(19.5) → 하강(19.6~19.7)" 구조는 강의 현장에서 시간 배분을 직관적으로 결정하는 데 매우 유용합니다.
3. **고의 버그 실습**: 교육 설계 기획안의 "고의 버그가 포함된 exception_unit.sv 수정" 실습은 19.5절 이해 확인에 가장 효과적인 분석 수준 활동입니다.

### 강사 관점의 추가 권고

**권고 1 — 19.4절 FSM MIE 클리어 시점 기술 검토 요청**
교육 설계 기획안(장벽 2)에서 이미 지적된 사항이나, 강사 관점에서도 동일한 우려를 표명합니다. 현재 기술 저자 기획안의 FSM에서 `S_TRAP_MSTATUS`(MIE 클리어)가 마지막 상태로 배치되어 있습니다. 강의 현장에서 "MIE를 가장 먼저 끄는 것이 안전하다"고 가르치는 것과 코드 구현 사이에 불일치가 발생할 수 있습니다. 기술 리뷰어가 FSM 상태 순서를 최종 확정한 후, 강사용 설명 스크립트를 FSM 순서에 맞게 조정할 것을 권고합니다.

**권고 2 — 19.6절 테스트벤치 실습에 "응답 시간 측정" 강조**
타이머 인터럽트 응답 시간(Interrupt Latency) 측정은 실무 면접에서 자주 나오는 주제입니다. `$time / CLK_PERIOD` 측정 방법과 함께 "이 파이프라인에서 타이머 인터럽트 최소 응답 시간은 몇 사이클입니까? (정답: 약 4~5사이클 — 파이프라인 플러시 + 트랩 FSM 처리)"를 학생들에게 직접 측정하게 하는 활동을 추가할 것을 권고합니다.

**권고 3 — 챕터 마무리에 "전체 여정 회고" 추가**
Ch19는 Part 1~7에서 배운 모든 것(ISA, 데이터패스, 파이프라인, AMBA, CSR)이 하나로 통합되는 챕터입니다. 19.7절 요약에서 "이 챕터를 완성하면 RV32I 파이프라인 프로세서의 하드웨어가 완성됩니다"라는 달성감 문구와 함께, 의존성 맵(TABLE_OF_CONTENTS.md의 기술 의존성 맵 중 Part 7까지)을 단순화한 버전을 삽입할 것을 권고합니다. 학생들이 지금까지 쌓아온 여정을 시각적으로 확인하는 것이 강한 성취감을 유발합니다.
