## 상세 평가

### 1. CSR 개념 도입 (MMIO/일반 레지스터와 연결)

**평가: 매우 우수**

18.1절 도입부에서 "Ch09~Ch12에서 만든 5단 파이프라인의 x0~x31 범용 레지스터"를 먼저 상기시킨 뒤, CSR이 왜 필요한지(보안, 실수 방지)를 구체적으로 제시합니다. 이미 배운 내용에서 출발하므로 낯섦이 크게 줄어듭니다.

CSR vs MMIO 비교는 FAQ aside에서 명확하게 처리되어 있습니다:
- CSR = 코어 내부, 전용 명령어, 1사이클
- MMIO = AHB 버스, 메모리 주소 공간, 버스 중재 필요

다만 처음 읽는 독자 입장에서 "lw/sw로 절대 접근할 수 없다"는 문장은 강하게 인지되지만, 왜 그런지(인코딩이 다름, SYSTEM opcode)에 대한 설명이 18.1절 내에서 바로 이어지면 더 좋을 것 같습니다. 현재는 18.1절 하단의 "CSR 명령어는 I-타입 인코딩"에서 처리되지만, 도입부와 약간 거리가 있습니다.

### 2. 7개 CSR 3그룹 청킹의 인지 부하 감소 효과

**평가: 우수**

"7개 CSR을 역할별로 세 그룹으로 묶으면 훨씬 쉽게 기억할 수 있습니다"라는 안내 문구와 함께 그룹 A/B/C로 명확히 분류한 것은 효과적입니다.

특히 그룹 B의 시나리오 기억법: "예외 발생 → mtvec 조회(어디로?) → mepc 저장(어디서 왔나?) → mcause 기록(왜?)"는 3개 CSR을 하나의 흐름으로 묶어주어 기억 부하를 현저히 낮춥니다.

그러나 그룹 C의 명칭이 "인터럽트 제어 (2개) + 임시 저장 (1개)"로 이질적인 두 범주를 억지로 묶은 느낌이 있습니다. mscratch는 기능적으로 그룹 B(예외 처리 보조)에 더 가깝습니다. 독자 입장에서 "왜 mscratch가 mie, mip와 같은 그룹인가?"라는 의문이 생길 수 있습니다.

### 3. mip 조합 논리 합성 설명의 이해 가능성

**평가: 보통 (개선 필요)**

"mip는 레지스터로 저장하지 않고 하드웨어 입력에서 직접 조합 논리로 합성합니다"라는 설명은 개념적으로 중요하지만, 처음 접하는 독자에게는 직관적이지 않습니다.

코드 라인 바로 위에 "왜 레지스터가 아닌가?"에 대한 1~2문장 설명이 있으면 좋겠습니다. 현재 본문에는 "소프트웨어가 직접 쓸 수 없다"는 결과만 나오고, "물리적으로 flip-flop이 없고 외부 신호가 직결된다"는 하드웨어 구현 의미는 생략되어 있습니다.

`assign mip_wire = {20'h0, ext_irq, 3'h0, timer_irq, 3'h0, sw_irq, 3'h0};` 코드에서 비트 위치(20개, 3개, 3개, 3개)의 합이 32인지를 독자가 즉시 확인하기 어렵습니다. 주석에 `// 총 32비트: [31:12]=0, [11]=MEIP, [10:8]=0, [7]=MTIP, [6:4]=0, [3]=MSIP, [2:0]=0` 형태의 설명이 추가되면 코드를 처음 보는 독자의 이해가 크게 향상됩니다.

### 4. W1C/WPRI 용어 설명 여부

**평가: 양호 (부분적 설명)**

WPRI는 18.2절에서 "Write Preserved, Read Ignored — 예약 비트"로 명시적으로 설명되어 있습니다. 좋습니다.

WARL(Write Any value, Read Legal values)은 mepc, mtvec 설명에서 사용되지만, 첫 등장 시 괄호 안에 한글 설명이 없습니다. "WARL — 입력값을 무시하고 허용값만 읽힘"이라는 설명이 mtvec 표 주석에 있지만, 이것이 첫 등장임을 독자가 인지하기 어렵습니다.

W1C(Write-1-to-Clear)는 본문에 등장하지 않습니다. mip.MTIP는 실제로 타이머 신호가 LOW가 될 때 자동으로 클리어되는 방식이어서 W1C는 아니지만, 실무에서 W1C 개념을 접할 것이므로 간단한 언급이 있으면 좋겠습니다.

RORL(Read-Only, Read Legal values)이라는 용어가 전체 소스 코드 주석에 갑자기 등장합니다(`// CSR_MIP: 소프트웨어 쓰기 무시 (RORL — 하드웨어 직결)`). 이 용어는 본문에서 설명된 적이 없습니다. 삭제하거나 설명을 추가해야 합니다.

### 5. 코드의 우선순위 구조(trap_en > mret_en > csr_we) 설명

**평가: 우수**

18.2절에서 "모듈 구조는 세 가지 블록으로 나뉩니다: ① 읽기 MUX, ② 쓰기 데이터 계산, ③ 레지스터 갱신(우선순위: trap_en > mret_en > csr_we)"라는 사전 예고가 있습니다.

실제 always_ff 코드에서도 `// 우선순위: rst_n(최우선) > trap_en > mret_en > csr_we` 주석이 명시되어 있습니다.

이 우선순위의 이유(왜 trap_en이 csr_we보다 높아야 하는가?)에 대한 설명이 본문 텍스트에 추가되면 더 좋겠습니다. 현재는 우선순위가 "무엇"인지는 알 수 있지만 "왜"인지는 독자가 스스로 추론해야 합니다.

## 추가 발견 사항

### 용어 첫 등장 시 한국어 병기 누락
- "SYSTEM opcode" — 본문에 등장하지만 한글 설명 없음
- "Zicsr 확장" — 18.3절 첫 등장 시 설명 없음 ("RISC-V 공식 CSR 명령어 확장" 정도의 설명 필요)
- "베어메탈(bare-metal)" — 18.1절에서 괄호 없이 사용 (사실 bare-metal 자체가 영어이므로 허용 가능하나, 한국어 설명 추가 권장)

### SVG 다이어그램 효과
- 그림 18.1(특권 수준 계층), 18.2(CSR 맵), 18.3(명령어 인코딩) 참조 구조는 적절합니다. 특히 그림 18.2가 7개 CSR의 비트 필드를 시각화한다면 독자의 이해에 큰 도움이 됩니다.

### 테스트벤치 접근성
- 18.4절 3단계 실습은 난이도가 잘 조절되어 있습니다. csr_write/csr_read task를 먼저 제공하고 그것을 이용하는 구조가 좋습니다.
- 그러나 `u_csr.mstatus_reg[3]`처럼 DUT 내부 신호를 직접 참조하는 코드는 시뮬레이터 의존적인 문법임을 주석으로 알려주면 좋습니다.

## 개선 제안 (우선순위)

1. **🔴 필수**: RORL 용어를 본문에서 설명하거나 전체 소스 코드 주석에서 제거하십시오. 설명 없이 등장하는 약어는 초보자의 혼란을 유발합니다.

2. **🔴 필수**: mip_wire 코드에 비트 위치를 명시하는 상세 주석을 추가하십시오. `{20'h0, ext_irq, 3'h0, timer_irq, 3'h0, sw_irq, 3'h0}`의 각 필드가 몇 비트인지 독자가 계산하지 않고도 알 수 있어야 합니다.

3. **🟡 권장**: mip가 "왜 레지스터가 아닌 조합 논리인가"에 대한 1~2문장 설명을 코드 직전에 추가하십시오 (하드웨어 직결 = 외부 신호 = flip-flop 없음).

4. **🟡 권장**: WARL의 첫 등장 시점을 명확히 하고 괄호 안에 한글 설명을 추가하십시오.

5. **🟡 권장**: mscratch가 왜 그룹 C(인터럽트 제어)에 포함되는지에 대한 한 문장 설명을 추가하십시오. ("인터럽트 핸들러 진입 직후 사용하는 레지스터이므로 그룹 C에 포함")

6. **🟢 선택**: trap_en > mret_en > csr_we 우선순위의 이유를 한 문장으로 설명하십시오. ("트랩은 동기/비동기 이벤트이므로 소프트웨어 명령어보다 먼저 처리해야 합니다")

7. **🟢 선택**: Zicsr 확장에 대한 간단한 설명(한 줄)을 18.3절 시작 시 추가하십시오.

## 최종 의견

Chapter 18은 CSR이라는 낯선 개념을 기존 지식(x0~x31, MMIO, Ch17 타이머)과 연결하여 진입 장벽을 크게 낮춘 잘 설계된 챕터입니다. 3그룹 청킹, 시나리오 기억법, 3단계 실습은 모두 효과적입니다.

초보자 이해도 승인 기준(⭐⭐⭐ 이상)을 충족합니다. 단, RORL 용어 미설명 및 mip_wire 비트 위치 주석 부재는 🔴 필수 수정이 필요합니다. 수정 후 ⭐⭐⭐⭐⭐ 달성 가능합니다.
