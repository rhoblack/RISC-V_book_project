# Appendix A 초보자 독자 평가

## 이해도 종합 평가: ⭐⭐⭐⭐ (4/5)

---

### 강점

1. **타입별 색상 코딩이 탁월하다.** R-Type(파랑), I-Type(초록), S-Type(노랑), B-Type(빨강), U-Type(보라), J-Type(분홍) — 6가지 타입이 시각적으로 즉시 구분되어, 37개 명령어 표에서 원하는 타입을 빠르게 찾을 수 있다.

2. **A.1 명령어 표의 구조가 명확하다.** 각 타입별 헤더 행에 opcode 값이 함께 표시되어, 디코더 설계 시 opcode → 타입 매핑을 한눈에 파악할 수 있다. "동작" 열의 간결한 수식(예: `rd = rs1 + rs2`)이 명령어 의미를 즉시 전달한다.

3. **A.2 비트 필드 다이어그램이 8개 SVG로 제공된다.** 6가지 타입의 비트 레이아웃을 그림으로 보여주어, 텍스트만으로는 파악하기 어려운 필드 위치를 직관적으로 이해할 수 있다.

4. **A.3 즉치수 재배열의 FAQ가 매우 유용하다.** "왜 즉치수를 순서대로 저장하지 않나요?"라는 질문은 초보자가 실제로 가장 궁금해하는 부분이며, 답변이 하드웨어 설계 관점(부호 확장 회로 공유, MUX 입력 공유)에서 명쾌하다.

5. **A.4 ABI 레지스터 표의 색상 범례가 좋다.** Caller-saved(노랑), Callee-saved(파랑), 특수 레지스터(보라)로 구분되어 호출 규약을 시각적으로 학습할 수 있다.

6. **A.5 의사 명령어 표가 실용적이다.** "의사 명령어 → 실제 명령어" 매핑이 테스트벤치 .hex 파일 작성 시 즉시 참조 가능하다. `nop = addi x0, x0, 0 = 0x00000013` 같은 정보가 디버깅에 직접 도움이 된다.

7. **부록 끝의 "이 부록의 목적" 문구가 좋다.** 독자가 "언제 이 부록을 써야 하는가?"를 명확히 알 수 있다 (디코더 설계 Ch06, 파이프라인 디버깅 Ch09~12, 테스트벤치 작성 시).

---

### 약점 (개선 제안)

1. **A.1에서 `opcode`, `funct3`, `funct7` 용어가 설명 없이 등장한다.** 첫 문단에서 "opcode, funct3, funct7 조합으로 명령어를 식별한다"고 하지만, 이 세 필드가 각각 무엇을 의미하는지 간략한 정의가 없다.
   - 권장: 첫 문단에 "(opcode: 명령어 종류를 구분하는 7비트 코드, funct3: 세부 연산을 구분하는 3비트, funct7: 추가 구분 7비트)" 형태의 괄호 설명 추가

2. **A.1 표에서 I* 표기(SLLI, SRLI, SRAI)의 의미가 불분명하다.** 타입 열에 "I*"라고만 되어 있고, 왜 별표가 붙는지 본문에서 설명이 없다. 아래 "핵심 포인트" aside에서 간접적으로 언급하지만, 표 자체에서 각주가 필요하다.
   - 권장: 표 아래에 "I* = I-Type이지만 funct7 필드를 시프트 방향 구분에 사용" 각주 추가

3. **A.3 B-Type/J-Type 즉치수 재배열 공식이 압축적이다.** `imm = {inst[31], inst[7], inst[30:25], inst[11:8], 1'b0}` 같은 공식은 Verilog 비트 연결 문법을 아는 독자에게는 괜찮지만, 구체적인 숫자 예시가 없어서 실제 명령어에 적용하기 어렵다.
   - 권장: BEQ 명령어 하나를 예시로 들어 32비트 → 즉치수 추출 과정을 단계별로 보여주면 이해도가 크게 향상될 것

4. **A.4에서 "Caller-saved"와 "Callee-saved"의 의미가 핵심 포인트 aside에서만 설명된다.** 표 자체에는 "호출 규약" 열에 Caller-saved/Callee-saved라고만 되어 있고, 이것이 왜 필요한지는 aside를 읽어야 알 수 있다.
   - 권장: 표 바로 위 본문에 "함수 호출 시 누가 레지스터를 백업할 책임이 있는가를 정하는 규약" 한 줄 추가

5. **`sext()`, `zext()` 함수 표기가 설명 없이 사용된다.** A.1 표의 동작 열에서 `sext(imm)`, `zext(M[...])` 같은 표기가 반복 등장하지만, 부호 확장(sign extension)과 제로 확장(zero extension)의 정의가 부록 내에 없다.
   - 권장: A.1 표 위 또는 아래에 "sext() = 부호 확장(최상위 비트를 32비트까지 복사), zext() = 제로 확장(상위 비트를 0으로 채움)" 한 줄 추가

---

### 설명 없이 등장하는 용어

- [ ] **opcode** — 명령어 종류를 구분하는 7비트 코드. A.1 첫 문단에서 사용되나 정의 없음.
- [ ] **funct3 / funct7** — 세부 연산을 구분하는 추가 필드. 마찬가지로 정의 없음.
- [ ] **immediate (즉치수)** — A.2 제목에서 "즉치수"로 번역되어 있으나, A.1 표에서는 `imm[11:0]`으로만 등장.
- [ ] **sext() / zext()** — 부호 확장 / 제로 확장 함수. A.1 동작 열에서 반복 사용되나 정의 없음.
- [ ] **ABI** — A.4 제목에 등장. 본문에 "(Application Binary Interface)"로 괄호 설명이 있어 양호.
- [ ] **shamt** — A.1 표의 SLLI/SRLI/SRAI에서 등장. 시프트 양(shift amount)의 약어이나 설명 없음.

---

### SVG 이해도 평가

- 8개 SVG(그림 A.1~A.8)는 비트 필드 위치를 시각적으로 명확히 보여주어, 텍스트만으로는 이해하기 어려운 필드 배치를 보완한다.
- 특히 A.7(B-Type 재배열)과 A.8(J-Type 재배열)은 화살표로 비트 이동 경로를 보여주어 조립 공식 이해에 필수적이다.
- SVG 없이 텍스트만으로 비트 재배열을 이해하기는 매우 어려우므로, **SVG는 필수**로 판단.

### 최종 판정: ✅ 승인 가능 (개선 권장사항 선택적 적용)

부록 A는 RV32I 명령어 레퍼런스로서 충분한 참조 가치가 있다. 색상 코딩, SVG 다이어그램, FAQ가 잘 구성되어 있으며, 디코더 설계와 디버깅 시 즉시 활용 가능하다. opcode/funct3/funct7/sext/zext 용어 정의와 B-Type 재배열 단계별 예시를 추가하면 ⭐⭐⭐⭐⭐가 될 수 있다.
