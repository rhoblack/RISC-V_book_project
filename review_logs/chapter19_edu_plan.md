### 도입 (호기심 유발, 19.1)

**질문**: "프로세서가 실행 중에 문제가 생기면 어떻게 될까?"

**시나리오**: "프로그래머가 실수로 존재하지 않는 명령어를 넣었다. 파이프라인에는 이미 5개 명령어가 동시에 흐르고 있다. 어떤 명령어까지 실행하고, 어떤 명령어를 취소해야 할까?"

**연결**: Ch12에서 완성한 파이프라인 + Ch18에서 배운 CSR → 이제 이 둘을 연결하는 "마지막 퍼즐 조각"

**기대 설정 문구**:
> "이 장은 총 7개 절로 나뉩니다. 먼저 파이프라인을 복습(19.1)하고, 동기 예외(19.2)와 비동기 인터럽트(19.3)를 순서대로 배운 후, 트랩 메커니즘(19.4)과 파이프라인 통합(19.5)을 거쳐 검증(19.6)하고 마무리(19.7)합니다. **이 장을 완료하면, Part 7(AMBA+CSR+예외)이 모두 완성됩니다.**"

### 개념 (단계적 확대)

**1단계 — 파이프라인 복습 (19.1)**: 안전 구간
- Ch12 파이프라인 구조를 1페이지로 요약
- 이미 배운 스톨(load-use, icache, dcache)과 플러시(분기) 메커니즘 재확인
- **핵심 메시지**: "예외/인터럽트 처리는 '새로운 종류의 플러시'입니다. 메커니즘은 이미 알고 있습니다."

**2단계 — 동기 예외 (19.2)**: 새 개념 도입, 그러나 패턴은 익숙
- 예외 = "명령어 실행 중 발생하는 오류"
- 각 스테이지별 감지 대상:
  - IF: 명령어 접근 오류 (Instruction Access Fault)
  - ID: 불법 명령어 (Illegal Instruction)
  - EX: 주소 미정렬 (Misaligned Address) — 계산 후 감지
  - MEM: 메모리 접근 오류 (Load/Store Access Fault)
  - 어디서든: ECALL/EBREAK (ID에서 디코딩)
- **안심 문구**: "각 스테이지에서 감지하는 예외는 1~2종류뿐입니다. 전체를 한번에 외우지 마세요."

**3단계 — 비동기 인터럽트 (19.3)**: 예외와 유사한 패턴 확장
- 인터럽트 = "외부에서 오는 신호" (예외와 달리 명령어와 무관)
- mie/mip 비트 매칭: `pending[i] = mie[i] & mip[i] & mstatus.MIE`
- 우선순위: MEI(11) > MSI(3) > MTI(7) — 우선순위 인코더
- **안심 문구**: "인터럽트는 예외와 거의 같은 메커니즘을 따릅니다. 차이점은 하나: MIE 비트로 '받아들일지 말지' 선택할 수 있다는 것뿐입니다."

**4단계 — 트랩 메커니즘 (19.4)**: 진입/복귀의 구체적 절차
- 트랩 진입: mepc ← 예외 발생 PC, mcause ← 원인 코드, mstatus.MPIE ← MIE, mstatus.MIE ← 0, PC ← mtvec
- 트랩 복귀 (MRET): PC ← mepc, mstatus.MIE ← MPIE, mstatus.MPIE ← 1
- **비유**: "응급실 트리아지 — 환자(예외) 도착 → 현재 상태 기록(mepc/mcause) → 치료(핸들러) → 퇴원(MRET)"

**5단계 — 파이프라인 통합 (19.5)**: 최고 난이도, 핵심 절
- 정확한 예외(precise exception): 예외 명령어 이전 = 완료, 이후 = 취소
- 예외 신호를 WB 스테이지까지 전파 → WB에서 최종 판단 → flush
- CSR 해저드: CSR 명령어 직후 예외 발생 시 처리
- **안심 문구**: "지금부터 배우는 것은 '이미 배운 파이프라인에 예외를 추가하는 것'입니다. flush 메커니즘은 Ch11에서 이미 구현했습니다. 그 확장입니다."

### 예시 (구체적 시나리오)

1. **Illegal Instruction 시나리오**: `0xFFFFFFFF` 명령어가 ID에서 감지 → 예외 신호 전파 → WB에서 flush 결정 → mepc에 해당 PC 저장 → mtvec으로 점프
2. **Timer Interrupt 시나리오**: mip.MTIP=1 & mie.MTIE=1 & mstatus.MIE=1 → WB 완료 시점에서 인터럽트 수락 → 다음 명령어 PC를 mepc에 저장 → mtvec으로 점프
3. **동시 예외 시나리오**: IF에서 접근 오류 + EX에서 미정렬 → EX 예외가 "프로그램 순서상 먼저" → EX 예외만 처리

### 실습 (동작 검증, 19.6)

**첫 성공 경로** (난이도 순):
1. 예외 감지 확인 (★☆☆☆☆): 테스트벤치에서 Illegal Instruction 신호가 생성되는지 확인
2. flush 동작 확인 (★★☆☆☆): 예외 신호 → 파이프라인 플러시 → 모든 valid 비트 클리어
3. 트랩 진입 확인 (★★★☆☆): mepc 저장, mcause 기록, PC→mtvec 리다이렉션
4. Timer Interrupt 응답 (★★★☆☆): mip/mie 설정 → 인터럽트 수락 → 핸들러 진입

### 정리 (통합 학습, 19.7)

- Part 7 통합 조감도: AMBA 버스(Ch16~17) 위에서 파이프라인이 실행 → CSR(Ch18)로 제어 → 예외/인터럽트(Ch19)로 흐름 전환
- Part 8 예고: "다음은 이 모든 것을 Basys 3 FPGA에 실제로 구현합니다"
- 감정 곡선 목표: **"나도 이제 프로세서 설계자처럼 생각한다"**

**전략 5: 비유의 3단계 활용 → 한계 명시 → 하드웨어 용어 복귀**
- 예외 ≈ "파이썬 try-except" → 한계: "하드웨어는 스택 추적 없이 즉시 점프" → 하드웨어 용어로

## 4. 연습문제 설계 (총 5개, L2~L4 분포)

### L2 (이해) — 2문제

**문제 1**: 예외와 인터럽트의 차이점을 3문장 이내로 설명하시오.

> **정답**: (1) 예외(동기)는 명령어 실행 중 발생하는 오류이고, 인터럽트(비동기)는 외부 장치에서 오는 신호이다. (2) 예외는 항상 즉시 처리해야 하지만, 인터럽트는 mstatus.MIE 비트로 수락/거절을 선택할 수 있다. (3) 둘 다 mtvec으로 점프하여 핸들러에서 처리된다.
>
> **채점 기준**: 동기/비동기 구분(1점), MIE 제어 가능성 언급(1점), 공통 처리 경로 언급(1점) = 3점 만점

**문제 2**: mcause[31]=1일 때 의미하는 바를 설명하고, mcause=0x8000_0007일 때 어떤 이벤트인지 답하시오.

> **정답**: mcause[31]=1은 인터럽트를 의미한다(0이면 예외). mcause=0x8000_0007에서 [31]=1이므로 인터럽트이며, 하위 코드 7은 Machine Timer Interrupt(MTI)이다.
>
> **채점 기준**: [31] 비트 의미(1점), 인터럽트 판별(1점), MTI 식별(1점) = 3점 만점

### L3 (적용) — 2문제

**문제 3**: Illegal Instruction 예외가 IF 스테이지에서 감지될 수 없는 이유를 설명하고, 실제로 감지되는 스테이지와 그 근거를 제시하시오.

> **정답**: IF 스테이지는 메모리에서 명령어 비트 패턴을 가져올 뿐, 디코딩하지 않는다. 명령어가 유효한지 판단하려면 opcode/funct3/funct7을 해석해야 하므로, ID 스테이지에서 디코더가 인식하지 못하는 인코딩을 감지한다.
>
> **채점 기준**: IF의 역할 한정 설명(1점), ID 디코딩 필요성(1점), 구체적 필드 언급(1점) = 3점 만점

**문제 4**: Timer Interrupt가 발생했을 때, 프로세서가 인터럽트를 수락하기 위해 충족해야 하는 3가지 조건을 CSR 비트로 명시하시오.

> **정답**: (1) mip.MTIP = 1 (타이머 인터럽트 대기 중), (2) mie.MTIE = 1 (타이머 인터럽트 허용), (3) mstatus.MIE = 1 (글로벌 인터럽트 활성화). 세 조건이 모두 참일 때 인터럽트를 수락한다.
>
> **채점 기준**: mip.MTIP(1점), mie.MTIE(1점), mstatus.MIE(1점) = 3점 만점

### L4 (분석) — 1문제

**문제 5**: 파이프라인에서 IF 스테이지의 명령어가 접근 오류 예외를 발생시키고, 동시에 EX 스테이지의 명령어가 주소 미정렬 예외를 발생시켰다. (a) 어떤 예외를 먼저 처리해야 하는지와 그 이유, (b) 나머지 예외의 처리 방법, (c) 이를 구현하기 위한 하드웨어 설계 고려사항을 서술하시오.

> **정답**:
> (a) EX 스테이지의 미정렬 예외를 먼저 처리한다. 이유: 프로그램 순서(program order)상 EX의 명령어가 IF의 명령어보다 먼저 실행된 것이므로, 정확한 예외(precise exception) 보장을 위해 먼저 발생한(=프로그램 순서상 앞선) 예외를 우선한다.
> (b) IF의 명령어는 EX 예외 처리 시 flush되므로, IF 예외는 자연스럽게 취소된다. 핸들러가 복귀(MRET)하면 해당 명령어가 재실행되어 같은 예외가 다시 발생할 수 있다.
> (c) 각 스테이지에서 예외 신호를 파이프라인 레지스터에 태깅하여 WB까지 전파하고, WB에서 "가장 오래된 명령어"의 예외만 처리한다. 이를 위해 예외 비트와 예외 코드를 파이프라인 레지스터에 추가해야 한다.
>
> **채점 기준**: (a) EX 우선 + 프로그램 순서 근거(2점), (b) flush에 의한 취소 + 재실행 가능성(2점), (c) 파이프라인 레지스터 태깅 + WB 판단(2점) = 6점 만점

## 5. 학습 흐름의 "점프 포인트" 관리

### 절간 연결 설계

**19.1 → 19.2 (복습에서 새 개념으로)**:
> "파이프라인의 플러시는 분기 예측 실패 때 이미 경험했습니다. 이제 '분기가 아닌 다른 이유'로 플러시해야 하는 상황을 배울 것입니다 — 그것이 바로 예외입니다."

**19.2 → 19.3 (동기에서 비동기로)**:
> "예외는 명령어가 직접 발생시키므로 '언제' 발생하는지 정확히 알 수 있습니다. 하지만 인터럽트는 외부에서 '아무 때나' 올 수 있습니다. 프로세서는 이 예측 불가능한 신호를 어떻게 처리할까요?"

**19.3 → 19.4 (개념에서 메커니즘으로)**:
> "이제 예외와 인터럽트가 '무엇'인지 알게 되었습니다. 다음 질문: 프로세서가 실제로 어떤 절차를 밟아 현재 작업을 중단하고 핸들러로 전환하는가? Ch18에서 배운 CSR들이 여기서 핵심 역할을 합니다."

**19.4 → 19.5 (메커니즘에서 통합으로)**:
> "트랩 메커니즘의 각 단계를 이해했습니다. 하지만 실제 파이프라인에서는 5개 명령어가 동시에 실행 중입니다. '어느 명령어의 예외를 처리하고, 어느 것을 취소할 것인가?' — 이것이 정확한 예외의 핵심입니다."

**19.5 → 19.6 (이론에서 검증으로)**:
> "설계가 완성되었습니다. 이제 실제로 동작하는지 시뮬레이션으로 확인합시다. 예외 신호가 정말 생성되는지, flush가 정확히 동작하는지, mepc에 올바른 주소가 저장되는지 눈으로 확인할 것입니다."

**19.6 → 19.7 (검증에서 종합으로)**:
> "개별 컴포넌트(파이프라인, AMBA 버스, CSR, 예외/인터럽트)를 모두 배우고 검증했습니다. 이제 Part 7의 전체 그림을 조망하고, Part 8에서의 FPGA 구현을 준비합니다."

## 7. 추가 교육 설계 고려사항

### "예외 처리의 추상성" 구체화 전략

예외 처리는 학습자에게 추상적으로 느껴지는 주요 원인 3가지와 대응:

| 추상성 원인 | 구체화 전략 |
|-----------|-----------|
| "예외가 언제 발생하는지 감이 안 온다" | 테스트벤치에서 의도적으로 예외 유발 → 시뮬레이션 파형으로 "눈에 보이는" 예외 |
| "flush가 실제로 무슨 일을 하는지 모르겠다" | valid 비트 변화를 파형 뷰어에서 직접 관찰 → "켜져 있던 비트가 꺼진다" |
| "mepc/mcause가 왜 필요한지 와닿지 않는다" | "핸들러가 끝나면 어디로 돌아갈까?" 질문 → mepc 없으면 복귀 불가 시연 |

### 파이프라인 복잡도 단계적 소화 전략

**원칙**: "한 번에 하나만 추가"

1. **19.2**: 파이프라인 + 예외 감지만 (flush는 아직 안 함)
2. **19.4**: 예외 감지 + 트랩 진입 메커니즘 (CSR 업데이트)
3. **19.5**: 감지 + 트랩 + flush + 정확한 예외 (전체 통합)

각 단계에서 이전 단계의 코드를 **확장**하는 방식으로, 매번 전체를 새로 설계하지 않음.
