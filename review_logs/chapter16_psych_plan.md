## 2. 불안 지점 #6 상세 분석

### 🔴 **불안 지점 #6-1: 신호 암기 부담**
**발생 시점**: 16.3절 신호 정의 테이블
**심리 프로필**:
- "HADDR, HTRANS, HWRITE, HWDATA, HRDATA, HREADY, HRESP, HSIZE, HBURST..."
- "이것들을 다 알아야 하나요?"
- "외우지 못하면 설계를 못 하는 건가?"

**근본 원인**:
- 신호 개수 많음 (마스터↔슬레이브 간 최소 15개)
- 신호 이름의 의미가 영어 약자 (H=AHB, ADDR=Address 등)
- "신호 1개를 놓치면 프로토콜 오류"라는 불안감

**안심 전략**:
```
전략 1: 신호 그룹화
- 그룹 1: 주소 신호 (HADDR 1개) → "이전 Ch15와 동일"
- 그룹 2: 제어 신호 (HTRANS, HWRITE, HSIZE, HBURST) → "읽기/쓰기 결정"
- 그룹 3: 데이터 신호 (HWDATA, HRDATA) → "명령어와 데이터 이동"
- 그룹 4: 응답 신호 (HREADY, HRESP) → "프로토콜 핸드셰이크"

→ "4개 그룹만 이해하면 신호 15개를 제어할 수 있습니다"

전략 2: 비유
- "AMBA AHB = 고속도로 통행 규칙"
  * HADDR = 목적지
  * HTRANS = 차량 유무 (IDLE/NONSEQ/SEQ/BUSY)
  * HREADY = 톨게이트 열림 신호
  * 모든 차가 다 규칙을 알아야 하는 것처럼, 신호도 모두 필요

→ 하지만 "당신이 설계자로서 이해해야 할 것은 마스터의 역할뿐"

전략 3: 메타인지 박스 (16.3절)
<aside class="metacognition">
🔍 **신호를 암기할 필요가 없습니다**
- 이 신호표를 꼭 외워야 한다고 생각하면 곤란합니다
- 16.3절을 읽으면서 "어? 이 신호는 뭐지?"라고 물어보는 것은 **매우 정상**입니다
- 16.5절(마스터 설계)로 넘어가면서, 당신은 **자연스럽게 신호를 익히게 될 것**입니다
- 지금은 "어떤 종류의 신호가 있는지 인식하기"만 하세요
</aside>
```

### 🔴 **불안 지점 #6-2: 프로토콜 규칙의 추상성**
**발생 시점**: 16.4절 타이밍 다이어그램 (프로토콜 규칙)
**심리 프로필**:
- "HREADY가 LOW일 때 HADDR을 유지해야 한다?"
- "NONSEQ 다음에는 왜 SEQ만 가능한가?"
- "이 규칙이 왜? 합리적 근거가 뭔가요?"

**근본 원인**:
- **비직관적 규칙**: 파이프라인의 "왜"와 달리, 표준은 "그냥 그렇게"
- **타이밍 다이어그램의 복잡성**: 5-6개 신호가 동시에 움직임
- **멀티 클록 사이클**: 1절 내에 3-4개 타이밍 시나리오 제시

**안심 전략**:
```
전략 1: 규칙의 "왜"를 설명
- "HREADY=LOW일 때 HADDR을 유지하는 이유"
  → "슬레이브가 '아직 처리 중이니 기다려'라고 신호하는 것"
  → Ch15의 WAIT_GRANT와 동일한 개념!

→ "당신은 이미 이 패턴을 Ch15에서 봤습니다"

전략 2: 타이밍 다이어그램 읽기 가이드
- "파형을 처음부터 끝까지 읽으려 하지 마세요"
- "3가지 신호(HTRANS, HWRITE, HREADY)만 먼저 추적하세요"
- "다음 번 읽을 때는 3개 신호를 더 추가하세요"

→ "점진적으로 복잡도를 늘리는 것이 올바른 읽기 방식입니다"

전략 3: 메타인지 박스 (16.4절)
<aside class="metacognition">
🔍 **파형을 완벽히 이해하지 못해도 괜찮습니다**
- 타이밍 다이어그램은 교재에서 **가장 추상적인** 그림입니다
- 파이프라인보다 읽기 어렵다고 느껴도 정상입니다
- 지금 이해하지 못한 부분은 16.5절(설계)에서 **자연스럽게 명확해질 것**입니다
- 설계하다가 "아, 그래서 이 규칙이 필요했구나!"라고 깨닫는 것이 정상 학습 과정입니다
</aside>

전략 4: "알고리즘 기반" 타이밍 설명
- 다이어그램만이 아니라, "이 상황에서 마스터는 이렇게 행동한다"는 pseudo-code 제시
- 예: "HREADY==0이면 {HADDR 유지, HWRITE 유지, 다음 클록 대기}" 같은 표현
```

#### **16.4절: 타이밍 다이어그램 + 메타인지**
```html
<h2>16.4 AHB 프로토콜 규칙과 타이밍</h2>

<aside class="tip">
💡 <strong>타이밍 다이어그램을 읽는 올바른 순서</strong>

<strong>1단계 (당신의 수준)</strong>: HTRANS, HWRITE 2개 신호만 추적
<pre>
클록 1: HTRANS=NONSEQ (새 접근 시작)
클록 2: HTRANS=SEQ (연속 접근)
</pre>

<strong>2단계 (다음 주차)</strong>: HREADY도 추가로 추적
<pre>
HREADY=1이면: 준비됨
HREADY=0이면: 기다려
</pre>

<strong>3단계 (마스터 설계할 때)</strong>: 나머지 신호도 추적
<pre>
HSIZE(몇 바이트?), HBURST(얼마나 연속?)
</pre>

→ **점진적으로 복잡도를 늘리는 것이 올바른 읽기입니다**
</aside>

<aside class="metacognition">
🔍 <strong>파형을 완벽히 이해하지 못해도 괜찮습니다</strong>

- 타이밍 다이어그램은 교재에서 **가장 추상적인** 그림입니다
- 파이프라인 다이어그램보다 읽기 어렵다고 느껴도 정상입니다
- **지금 이해하지 못한 부분은 16.5절(마스터 설계)에서 명확해질 것입니다**
- 설계하다가 "아, 그래서 이 규칙이 필요했구나!"라고 깨닫는 것이 정상 학습 과정입니다

다음 일주일 후 이 섹션을 다시 읽으면, 훨씬 이해가 빠를 것입니다.
</aside>

<!-- NONSEQ→SEQ 상태 설명 -->
<h3>16.4.1 HTRANS와 상태 규칙</h3>

<p>
<strong>규칙: NONSEQ 다음에는 SEQ만 가능하다</strong>
</p>

<p>
왜일까요? "그냥 ARM의 규칙이라서"가 아닙니다.
</p>

<aside class="instructor-tip">
📌 <strong>이 규칙의 "왜"를 설명하면</strong>

하드웨어 관점에서 버스를 공유하는 여러 마스터가 있습니다.
- 마스터 A: 주소 0x1000 접근
- 마스터 B: 주소 0x2000 접근

만약 마스터 A가 중간에 주소를 바꾸면 (0x1000 → 0x1004 → 0x1100),
슬레이브는 "지금 어느 주소를 읽고 있는가?"를 추적하기 어려워집니다.

따라서 규칙:
- **NONSEQ**: "다음 주소는 완전히 새로운 접근입니다" → 주소 변경 OK
- **SEQ**: "마지막 주소 다음입니다" → 주소는 자동 증가 (마스터가 제어 불가)

이렇게 하면 슬레이브가 "아, NONSEQ니까 모든 신호를 다시 읽어야지"라고 판단할 수 있습니다.

**당신은 이미 Ch15에서 유사한 패턴을 봤습니다**: 버스트 전송 중에는 주소가 자동 증가되고,
새로운 요청이 들어오면 대기해야 했습니다.
</aside>
```

#### **16.5절: 마스터 설계 + 성공 경험**
```html
<h2>16.5 AHB 마스터 설계</h2>

<p>
Ch15를 다시 기억해보세요.
당신의 메모리 컨트롤러는 이렇게 작동했습니다:
</p>

<pre><code class="language-systemverilog">
// Ch15: 메모리 컨트롤러 (마스터 역할)
if (icache_miss) {
  arbiter_req_i = 1;  // 메모리 접근 요청
  addr_o = icache_addr;  // 주소 제공
  wr_en_o = 0;  // 읽기
  // 메모리 응답 대기...
}
</code></pre>

<p>
이제 같은 로직을 <strong>AHB 신호로만 표현</strong>하면 됩니다:
</p>

<pre><code class="language-systemverilog">
// Ch16: AHB 마스터 (동일한 로직)
if (req) {
  haddr = src_addr;      // HADDR에 주소 제공
  hwrite = 0;            // 읽기 (HWRITE=0)
  htrans = NONSEQ;       // 새 접근 시작
  hsize = WORD;          // 32비트 데이터
  // HREADY를 기다렸다가...
  if (hready) {
    data_o = hrdata;     // HRDATA에서 데이터 읽기
  }
}
</code></pre>

<aside class="tip">
💡 <strong>당신은 이미 마스터 역할을 했습니다</strong>

Ch15의 "메모리 접근 요청 → 대기 → 응답 처리" 패턴이 마스터입니다.
지금 하는 것은 **그 패턴에 표준 이름을 붙이기만** 하는 것입니다.
</aside>
```

#### **16.6절: 슬레이브 설계 + 대칭성**
```html
<h2>16.6 AHB 슬레이브 설계</h2>

<p>
마스터를 설계했으니, 슬레이브는 어떨까요?
</p>

<p>
슬레이브도 비슷합니다. 다만:
- 마스터: "요청을 제출한다"
- 슬레이브: "요청에 응답한다"

차이는 방향뿐입니다.
</p>

<aside class="tip">
💡 <strong>마스터-슬레이브 = 대칭</strong>

마스터가 HADDR, HWRITE를 제공하면,
슬레이브는 HRDATA, HREADY로 응답합니다.

이미 Ch15에서 경험한 "버스 매개변수 교환"입니다.
이름만 표준으로 바뀐 것이고,
논리는 동일합니다.
</aside>
```

#### **16.7절: 통합 + 성취**
```html
<h2>16.7 마스터-슬레이브 통합</h2>

<p>
마스터와 슬레이브를 연결하면, 당신의 프로토콜이 동작합니다.
</p>

<pre><code class="language-systemverilog">
// CPU (AHB 마스터)
ahb_master cpu_master (
  .haddr(haddr),
  .hwrite(hwrite),
  .hwdata(hwdata),
  .hrdata(hrdata),
  .hready(hready)
);

// 메모리 (AHB 슬레이브)
ahb_slave memory_slave (
  .haddr(haddr),
  .hwrite(hwrite),
  .hwdata(hwdata),
  .hrdata(hrdata),
  .hready(hready)
);

// 메모리 컨트롤러 (버스 중재기)
ahb_arbiter arbiter (
  .hready(hready)
);
</code></pre>

→ **성취감**: "표준 프로토콜을 구현했다"
→ **실무 자신감**: "이제 ARM 설계 문서를 읽을 수 있다"
```
