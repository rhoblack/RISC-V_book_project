### 18.1절: 특권 수준과 CSR 레지스터

**예상 감정**: 낯섦 + 가벼운 불안
- "특권 수준이라는 개념 자체가 처음이라 추상적으로 느껴질 것"
- "CSR이 일반 레지스터와 어떻게 다른지 감이 오지 않음"

**완화 전략**:
1. **기존 지식 브리지**: 학습자가 이미 구현한 32개 범용 레지스터(x0~x31)와 대비하여 CSR을 "프로세서 상태를 저장하는 특수 레지스터"로 소개. "여러분이 Ch09에서 만든 레지스터 파일과 주소 공간이 분리되어 있다는 점만 다릅니다"라는 문구로 친숙화.
2. **MMIO 연결**: Ch17에서 구현한 MMIO 개념 — "특정 주소에 접근하면 특수 동작이 발생한다" — 를 CSR의 12비트 주소 공간에 연결. "CSR도 일종의 내부 MMIO입니다"라는 비유로 낯선 개념의 저항감 완화.
3. **목적 명확화**: "운영체제가 없는 베어메탈(bare-metal) 환경에서도 인터럽트를 처리하려면 하드웨어가 최소한의 상태 정보를 기억할 장소가 필요합니다"라는 동기 문구 삽입.

**목표 감정 상태**: 낯섦이 완전히 해소되지는 않더라도 "일단 읽어보자"는 호기심 유지

### 18.2절: 핵심 CSR 구현

**예상 감정**: 압도감(불안 최고점)
- "mstatus만 해도 비트가 수십 개인데 이걸 다 구현해야 하나?"
- "RISC-V 스펙 문서를 열어보면 표가 가득 나오는데..."
- "각 비트의 이름이 왜 이렇게 영어 약어인가?"

**완화 전략**:
1. **범위 명시 (가장 중요)**: 절 첫머리에 굵은 글씨로 "이 절에서는 7개만 구현합니다: mstatus, mtvec, mepc, mcause, mie, mip, mscratch" 명시. 전체 CSR 주소 공간(4096개)이 있음을 인정하되 "지금 당장 필요한 것만 집중합니다"라는 범위 확정으로 압도감 차단.
2. **비트 선택 기준 명시**: mstatus에서도 이 챕터에서 실제로 사용하는 비트(MIE, MPIE, MPP)만 먼저 설명하고, 나머지 비트는 별도 aside 박스에 "참조용"으로 분리. "오늘 당장 외울 필요 없습니다"라는 문구 명시.
3. **누적 인정**: "이 절이 챕터에서 가장 건조한 부분입니다. 당장 모두 이해되지 않아도 괜찮습니다. 18.4절 실습을 마친 후 다시 돌아오면 비트 하나하나가 왜 필요한지 보일 것입니다."

**목표 감정 상태**: 압도감을 인정하되 "7개만, 필요한 비트만"이라는 닻(anchor)으로 안정화

### 18.3절: CSR 명령어 구현

**예상 감정**: 집중 + 미묘한 혼란
- "CSRRW, CSRRS, CSRRC... 왜 세 가지나 필요한가?"
- "원자적 읽기-수정-쓰기가 파이프라인에서 어떻게 보장되는가?"

**완화 전략**:
1. **연산 패턴 단순화**: 세 명령어를 "쓰기(Write)", "비트 설정(Set)", "비트 클리어(Clear)"로 먼저 이름 붙이고, 이후 정식 명칭을 연결. 패턴을 먼저 파악하면 이름이 자연스럽게 따라옴.
2. **원자성 불안 예방**: "CSRRW의 원자적 동작은 파이프라인에서 복잡한 문제를 일으킬 수 있습니다. 이 챕터에서는 CSR 전용 실행 단계(1사이클 완료)로 단순화하여 구현합니다. 파이프라인 해저드 처리는 Ch19에서 다룹니다"라는 문구로 불안을 다음 챕터로 이연.
3. **즉각적 연결**: CSRRS rs1=x0 패턴을 "레지스터를 건드리지 않고 CSR만 읽는 관용구"로 명명하여 실용적 쓰임새를 먼저 보여줌.

**목표 감정 상태**: "이렇게 쓰는 거구나"라는 이해 감각 획득

## 동기 유지 전략

### 전략 1: 지금까지 만든 것이 살아남는다는 연속성 강조

Ch17에서 구현한 `timer_irq` 신호가 `mip.MTIP`(비트 7)에 직접 연결된다는 점을 18.1절 도입부에서 명시. "여러분이 지난 챕터에서 만든 타이머의 인터럽트 신호가 바로 이 레지스터로 들어옵니다"라는 문구는 학습자가 과거 작업의 의미를 재발견하게 한다.

**삽입 위치**: 18.1절 도입부, mip 설명 직전

### 전략 2: 명확한 종착점 예고

"이 챕터를 마치면 어떤 예외가 발생했는지(mcause), 어디서 발생했는지(mepc), 핸들러는 어디 있는지(mtvec)를 하드웨어가 자동으로 기록하는 프로세서를 갖게 됩니다. Ch19에서는 소프트웨어가 이 정보를 읽어 예외를 처리하는 과정을 완성합니다."

**삽입 위치**: 18.1절 첫 단락

### 전략 3: 마일스톤 시각화

18.4절 시뮬레이션 파형에서 CSR 주소 공간에 값이 기록되고 읽히는 장면을 "하드웨어가 처음으로 자신의 상태를 기억하는 순간"으로 프레이밍. 단순한 레지스터 읽기/쓰기가 아니라 "프로세서 지능의 기반"이라는 의미 부여.

**삽입 위치**: 18.4절 실습 전 도입 문단

### 전략 4: RISC-V 생태계 연결

"Linux 커널, FreeRTOS 등 모든 RISC-V 기반 운영체제는 이 챕터에서 구현하는 CSR을 통해 하드웨어와 대화합니다. 여러분이 지금 만드는 것은 소프트웨어 생태계 전체를 가능하게 하는 기반입니다."

**삽입 위치**: 18.1절 특권 수준 설명 직후, aside class="tip"으로 포함

## 자기효능감 설계

### 첫 실습(18.4절)의 단계별 성공 보장

**핵심 원칙**: 첫 번째 실습은 반드시 성공해야 한다. 실패 시 전체 챕터에 대한 자신감이 무너진다.

#### 단계 1: CSR 쓰기 확인 (가장 단순)
```
목표: mstatus에 0x88 쓰기
성공 조건: $display("[PASS] mstatus = 0x00000088") 출력
예상 소요 시간: 3~5분
```
이 단계는 실패할 여지가 거의 없도록 테스트벤치를 완전히 제공한다. 학습자가 "복사 → 시뮬레이션 실행 → PASS 확인"의 성공 경험을 먼저 쌓도록 설계.

#### 단계 2: CSR 읽기 확인
```
목표: CSRRS x1, mstatus, x0 실행 후 x1 값 확인
성공 조건: [PASS] x1 = 0x00000088
```
단계 1에서 쓴 값을 읽는다는 인과관계로 "내가 쓴 게 맞다"는 검증 경험 제공.

#### 단계 3: 인터럽트 마스킹 확인
```
목표: mstatus.MIE = 0 상태에서 mip.MTIP 설정 후 인터럽트 발생 안 함 확인
성공 조건: [PASS] 인터럽트 마스킹 확인
```
가장 복잡한 단계를 마지막에 배치. 이미 두 번의 성공을 경험한 후이므로 동기 수준이 높은 상태.

**각 단계 후 즉각 피드백**: `$display("[PASS] ...")` 또는 `$display("[FAIL] 예상값: %h, 실제값: %h", expected, actual)` 형태로 명확한 피드백 제공.

**범위 보호 문구**: 18.4절 첫머리에 "이 실습에서는 파이프라인 해저드나 예외 처리 흐름은 다루지 않습니다. CSR 레지스터가 올바르게 읽히고 쓰이는지만 확인합니다. 복잡한 통합은 Ch19에서 다룹니다."

> "이 챕터를 처음 읽으면서 CSR 비트 하나하나가 모두 이해되지 않았을 수 있습니다. CSR은 한 번 읽어서 완전히 파악하는 내용이 아닙니다. Ch19에서 실제 예외 처리 흐름을 구현하면서 이 챕터로 다시 돌아오면, 각 비트가 왜 그 자리에 있는지 자연스럽게 이해됩니다. 지금은 '이런 레지스터들이 있고 대략 이런 역할을 한다'는 감각만으로 충분합니다."
