### 📍 막힘 포인트 #1: 링커 스크립트 문법의 신비성
**"ld 스크립트를 왜 쓰고 어떻게 읽는 거예요?"**

#### 강사용 설명 원고 (그대로 강의실에서 사용 가능)
```
"링커 스크립트라는 이름이 겁을 주지만, 알고 보면 굉장히 단순합니다.
컴파일러(gcc)가 만든 목적 파일들(.o)을 모아서 최종 실행 파일로 만드는 사람이 링커(ld)예요.
링커는 좀 답답한 성격이라서, '너 이 코드는 0x8000_0000에 넣고, 그 데이터는 0x20000000에 넣어야 해'라고
정확히 지시해야 움직입니다. 그 지시서가 바로 링커 스크립트입니다.

생각해보니 여러분은 이미 비슷한 경험을 했습니다. 기억하세요?
Vivado에서 .coe 파일로 BRAM을 초기화할 때, '어느 주소부터 어느 데이터를 넣을까' 지정했잖아요.
링커 스크립트도 정확히 그겁니다. 단지 상대방이 메모리 하드웨어(BRAM)가 아니라
'메모리 주소 공간'이라는 추상적 개념일 뿐.

링커 스크립트는 다음 3가지만 정의합니다:
① MEMORY: 우리 프로세서의 메모리 맵은 뭐인가? (IMEM 0x0, DMEM 0x8000_0000 등)
② SECTIONS: C 코드의 어느 부분이 어느 섹션인가? (.text=코드, .data=초기화된 전역변수, .bss=미초기화)
③ 위치: 각 섹션을 메모리 맵의 어느 위치에 배치할 것인가?

더 간단히 하자면, 링커 스크립트는 '건설회사가 건물을 지으면서 참고하는 설계도'와 같습니다.
- 설계도 없으면: 건물의 방을 어디에 지을지 몰라서 엉망
- 설계도 있으면: 설계대로 방과 화장실과 주방을 배치

오늘 실습에서는 이미 만들어진 링커 스크립트를 보고 '아, 이런 의도구나' 이해하는 게 목표입니다.
처음부터 직접 만들려고 하지 마세요. 산업 현장에서도 템플릿을 복사해서 수정하거든요."
```

### 📍 막힘 포인트 #2: 메모리 맵 혼동 ("내 프로그램이 0x8000_0000에서 시작한다고?")
**"왜 IMEM은 0x0인데 코드가 0x8000_0000에 있다고 하는 거죠?"**

#### 강사용 설명 원고
```
"좋은 질문입니다! 이게 제일 헷갈리는 부분이에요.

먼저 정리합시다:
- **IMEM의 물리적 위치**: Vivado에서 할당한 BRAM (0x0 ~ 0x3FFF, 16KB)
- **C 프로그램의 가상 주소**: 링커 스크립트에서 지정한 0x8000_0000 ~ 0x8000_3FFF

'뭐?! 다른데?'라고 하셨을 텐데, 이건 **전혀 문제가 아닙니다.**

여기 Basys 3라는 간단한 시스템에서는 가상 메모리가 없어요.
(복잡한 Linux 같은 곳에서는 가상 주소를 물리 주소로 변환하는 MMU라는 장치가 있지만)

그럼 왜 C 프로그램의 코드를 0x8000_0000에 배치할까요?
→ **산업 표준 관례 때문입니다.**

ARM Cortex-M 같은 실제 마이크로컨트롤러들을 보면:
- FLASH 메모리(코드): 0x0000_0000 ~ 0x0007_FFFF (512KB)
- RAM (데이터): 0x2000_0000 ~ 0x2000_FFFF (64KB)

RISC-V 기반 보드들도 비슷한 패턴을 따릅니다:
- 코드/명령어: 0x8000_0000 이상
- 데이터: 0x2000_0000 이상

우리 Basys 3 구현에서는:
- 실제 하드웨어: IMEM(0x0), DMEM(0x2000_0000)
- **하지만** 링커 스크립트로는 표준 관례(0x8000_0000)를 따름
- → 결과: 링커가 'app.hex'를 만들 때 0x8000_0000 기반 주소 생성
- → 우리가 손으로 변환: 'objcopy --change-addresses -0x8000_0000' 명령어로 물리 주소로 변환
  (혹은 Vivado가 자동으로 처리)

다시 말해:
**소스 코드는 표준 주소(0x8000_0000)로 작성 → 링커가 그대로 인코딩 →
최종 배포할 때만 물리 주소(0x0)로 변환**

이 과정을 거치면:
- 개발자는 산업 표준에 맞게 코드 작성 (어딘가에 포팅할 때 수정 최소)
- Basys 3용으로는 자동 스크립트로 변환 (한 줄 명령어)

'근데 진짜 동작하나요?' → YES! 오늘 실습에서 보실 겁니다."
```

#### 비유 검증
| 기준 | 검증 |
|------|------|
| **① 기술 사실과 매핑** | ✅ 가상(표준)과 물리(Basys 3 실제) 개념 정확 |
| **② 한계 명시** | ✅ "실제 MMU 변환은 훨씬 복잡" 명시 |
| **③ 오해 방지** | ✅ "주소 변환은 안전하고 표준" (검증됨) |
| **④ 대안 비유** | "우편번호(표준주소) ↔ 실제 건물 위치(물리주소)" |

#### 강의 보조 자료
**메모리 맵 SVG** (강의 자료):
```
표준 주소공간(링커 스크립트)    →    Basys 3 실제 주소
─────────────────────────        ─────────────────────
0x8000_0000  [.text (코드)]       0x0000_0000  [IMEM]
0x8000_3FFF  (16KB)               0x0000_3FFF  (16KB)
             [패딩]
0x2000_0000  [.data (초기화)]      0x2000_0000  [DMEM]
0x2000_7FFF  (32KB)               0x2000_7FFF  (32KB)

변환: objcopy --change-addresses -0x8000_0000 app.elf app.hex
```

### 📍 막힘 포인트 #3: UART에 printf를 "어떻게" 연결하는가
**"printf()가 LED를 켜고 UART로 출력되려면 뭐가 필요한 거죠?"**

#### 강사용 설명 원고
```
"C 표준 라이브러리의 printf()는 신기한 함수입니다.
우리가 printf('Hello')라고 쓰면, 마술처럼 모니터 화면에 글자가 나타나죠.

하지만 알고 보면 printf는 '출력 장치'를 전혀 모릅니다.
printf는 다만 '누군가에게 이 글자를 전달해줘'라고 외칩니다.
그 '누군가'가 바로 운영체제(OS)의 입출력 시스템입니다.

우리의 Basys 3에는 OS가 없습니다. 따라서 printf의 그 외침을 받아줄 '누군가'가 필요합니다.
그게 **스텁(stub)** 또는 **시스템 콜 핸들러**예요.

우리는 다음과 같이 연결합니다:

1단계: C 코드에서
   printf('Hello RISC-V!');

2단계: 컴파일러는 printf 호출을 _write() 라는 저수준 함수로 변환
   _write(1, "Hello RISC-V!", 13);  // 1=stdout, 버퍼, 길이

3단계: 우리가 _write()를 구현 (drivers.c)
   int _write(int fd, char *buf, int len) {
       for (int i = 0; i < len; i++) {
           uart_putchar(buf[i]);  // UART 레지스터에 한 글자씩 쓰기
       }
       return len;
   }

4단계: uart_putchar()는 우리가 이미 구현한 UART 드라이버 (Ch17)
   - UART 상태 레지스터 확인: TX FIFO 비어있나?
   - 비어있으면 데이터 레지스터에 글자 한 개 쓰기
   - USB 케이블을 통해 PC의 터미널로 전송

결과: 터미널에 'Hello RISC-V!'가 나타남!

핵심은: **printf는 '입출력의 의도'만 표현하고,
실제 '어떻게 보낼지'는 우리가 구현하는 것**

이걸 '입출력 리다이렉션' 또는 'syscall 스텁'이라고 부릅니다.
산업 현장에서 새로운 하드웨어에 포팅할 때는 항상 이 _write(), _read() 같은 함수를 먼저 구현합니다."
```

#### 비유 검증
| 기준 | 검증 |
|------|------|
| **① 기술 사실과 매핑** | ✅ printf → _write → uart_putchar → UART 하드웨어 (정확한 단계) |
| **② 한계 명시** | ✅ "실제 OS의 입출력은 더 복잡 (버퍼링, 인터럽트)" |
| **③ 오해 방지** | ✅ "printf는 '마술'이 아니라 '규칙'" |
| **④ 대안 비유** | "수도 꼭지(printf) ← 배관(stdio) ← 정수 펌프(_write) ← 실제 파이프(UART)" |

#### 강의 보조 자료
**강사가 보여줄 코드 흐름**:
```
사용자 코드:
  printf("Temperature: %d°C\n", sensor_val);
         ↓ (컴파일러가 변환)
  _write(1, "Temperature: 25°C\n", 19);

```

### 📍 막힘 포인트 #4: 타이머 인터럽트의 "등록 방식"
**"타이머 인터럽트 핸들러는 어디에 등록해요?"**

#### 강사용 설명 원고
```
"이 질문도 좋습니다. 여러분은 지금까지:
- Ch18에서 CSR 레지스터를 구현했고
- Ch19에서 파이프라인과 예외처리를 연동했습니다.

이제 그것들을 실제로 써야 할 시간입니다.

Linux에서는:
- 커널이 '인터럽트 핸들러 테이블(IVT)'을 관리해요.
- request_irq()라는 함수로 '이 인터럽트 번호가 발생하면 이 함수를 호출해줘'라고 등록

우리의 Basys 3에는 커널이 없으니까:
- **인터럽트 벡터(IVT)를 우리가 직접 만들어야 합니다.**

여기 우리가 할 일:

1단계: 메모리에 인터럽트 벡터 테이블 배치 (보통 0x0부터)
   C 코드:
   typedef void (*irq_handler_t)(void);

   irq_handler_t irq_table[32] = {
       0,                           // 0번: 사용 안함
       0,                           // 1번: 사용 안함
       ...
       timer_interrupt_handler,     // 예를 들어 7번이 타이머라면
       ...
   };

2단계: 어셈블리 부트스트랩(startup.S)에서 mtvec 설정
   csrw mtvec, irq_table  // mtvec = 인터럽트 벡터 테이블 주소

3단계: 타이머가 발생하면?
   - 하드웨어(Ch17 타이머 모듈)가 인터럽트 신호를 프로세서로 전송
   - 프로세서(Ch19)가 외부 인터럽트 감지 → mcause = 11 (타이머 인터럽트)
   - mtvec가 가리키는 주소로 PC 점프
   - 인터럽트 핸들러(timer_interrupt_handler) 실행
   - MRET 명령어로 복귀

4단계: 우리가 구현할 핸들러 예시
   void timer_interrupt_handler(void) __attribute__((interrupt)) {
       // 실행 기록 (예: LED 토글)
       LED_PORT ^= (1 << LED_PIN);

       // 인터럽트 원인 초기화 (타이머 모듈에게 '처리했다'고 신호)
       timer_clear_pending();

       // MRET이 자동으로 실행됨 (__attribute__((interrupt))가 처리)
   }

핵심 차이:
- **Linux 커널**: '어떤 핸들러를 쓸지' 등록
- **우리의 Basys 3**: '인터럽트 벡터 테이블을 어디에 둘지' + '각 항목에 함수 주소 저장'

산업 현장:
- 임베디드 시스템(ARM Cortex-M, PIC, AVR): 우리처럼 벡터 테이블 방식
- 고급 프로세서(x86): 인터럽트 기술자 테이블(IDT) 방식 (비슷하지만 조금 다름)
- RISC-V 서버: 고급 interrupt 컨트롤러(PLIC) 사용

우리는 모든 기초를 경험하게 됩니다!"
```

#### 비유 검증
| 기준 | 검증 |
|------|------|
| **① 기술 사실과 매핑** | ✅ 벡터 테이블 → mtvec → 핸들러 (RISC-V 정확) |
| **② 한계 명시** | ✅ "실제 고급 시스템은 인터럽트 컨트롤러(PLIC) 사용" |
| **③ 오해 방지** | ✅ "벡터 테이블은 고정이고 동적 등록 안함" |
| **④ 대안 비유** | "긴급 전화(911) ← 911에 등록된 경찰(핸들러) ← 배치 센터(mtvec)" |

#### 강의 보조 자료
**인터럽트 처리 흐름 SVG**:
```
[타이머 하드웨어]
   ↓ (인터럽트 신호)
[파이프라인 EX 스테이지: 인터럽트 감지]
   ↓ (메모리 플러시)
[mepc = PC+4 저장, mcause = 7 (타이머)]
   ↓
[PC = mtvec (벡터 테이블 주소)]
   ↓
[irq_table[7] 실행 = timer_interrupt_handler]
   ↓
[LED 토글, 상태 초기화]
   ↓
[MRET: PC = mepc로 복귀, 원래 코드 계속]
```

### 📍 막힘 포인트 #5: "무한 루프 vs 반복 실행" — 프로그램 종료의 개념
**"프로그램이 무한 루프 도는데 끝내는 게 아니라 계속 반복 실행돼요?"**

#### 강사용 설명 원고
```
"우리가 개발한 Basys 3는 '임베디드 시스템'입니다.
이 개념이 학생분들에게 신기하고 헷갈리는 부분이에요.

자기 컴퓨터에서 C 프로그램을 실행하면?
1. 프로그램 시작
2. main() 함수 실행
3. main() 종료 (return 0;)
4. OS가 프로그램을 정리하고 종료
5. 프로그램 끝

하지만 Basys 3에는 OS가 없습니다!

1. FPGA 전원 ON
2. 부트스트랩(startup.S) 실행 (스택 초기화, main() 진입 준비)
3. main() 함수 시작
4. main() 내부 코드 실행
5. (여기가 중요) main() 끝나면?
   - 만약 return 0;이면: '반환 값 0을 어디에 보낼까?' → 아무도 받지 않음
   - 따라서 다음 명령어로 진행 (일반적으로 무한 루프)

결과: 프로그램이 '끝나는 게 아니라' 계속 실행됩니다!

우리가 보통 하는 패턴:
   int main(void) {
       // 초기화
       uart_init();
       gpio_init();
       timer_init();

       // 무한 루프 (임베디드 시스템의 표준!)
       while (1) {
           // 메인 작업
           process_sensor_data();
           update_led();

           // 또는 인터럽트로 처리됨
           // (별도 타이머 핸들러가 백그라운드에서 실행)
       }
   }

왜 무한 루프인가?
- **전자제품은 끝나면 안 됩니다!**
- 냉장고는 계속 냉동실을 식혀야 하고
- 신호등은 계속 색깔을 바꿔야 하고
- 우리의 Basys 3도 계속 작동해야 합니다

FPGA 보드 전원을 끄면 프로그램은 '종료'됩니다.

즉:
- 컴퓨터 프로그램: 시작 → 실행 → 종료 (생명 주기)
- 임베디드 프로그램: 시작 → 영구 실행 (전원이 꺼질 때까지)

이것도 학습 곡선의 일부입니다.
자신이 개발한 프로세서에서 프로그램이 영원히 실행된다는 것은
'내가 정말 프로세서를 만들었구나'라는 확신을 주는 순간입니다!"
```

#### 비유 검증
| 기준 | 검증 |
|------|------|
| **① 기술 사실과 매핑** | ✅ 임베디드 시스템의 무한 루프 구조 (정확) |
| **② 한계 명시** | ✅ "실제 마이크로컨트롤러도 low-power 모드 등 더 복잡" |
| **③ 오해 방지** | ✅ "무한 루프가 '버그'가 아니라 '설계'" |
| **④ 대안 비유** | "냉장고(영구 실행) vs 문서 편집 프로그램(사용자 종료)" |

#### 강의 보조 자료
**main() 함수 패턴 비교표**:
```
┌─────────────────────────────────────────────────────┐
│       데스크톱 프로그램                  임베디드 프로그램        │
├─────────────────────────────────────────────────────┤
│ int main() {                  │ int main(void) {         │
│   /* 초기화 */                │   /* 초기화 */           │
│   setup();                    │   uart_init();           │
│                               │   led_init();            │
│   /* 작업 */                  │                          │
│   do_work();                  │   /* 무한 루프 */        │
│                               │   while (1) {            │
│   /* 정리 */                  │     main_task();         │
│   cleanup();                  │                          │
│                               │     /* NEVER RETURNS */ │

│ }                             │ }                        │
└─────────────────────────────────────────────────────┘
```

**(TABLE_OF_CONTENTS.md Ch20 관련, Ch22에서 보강 가능)**

**ASIC 플로우** (비교):
```
Verilog 코드 → RTL 검증(1주일) → 합성(1일) → P&R(3일) → 검증(1주일)
→ 마스크 생성 → 실리콘 생산(3개월) → 패키징 → 테스트

#### 강의 대사 (면접 준비)
```
"이 교재를 통해 여러분은 FPGA 개발 경험을 했습니다.

하지만 상용 프로세서는 ASIC으로 설계됩니다. 예를 들어:
- Intel Core Ultra: 5나노 공정, 수년 개발
- ARM Cortex-A78: TSMC 5나노, ARM이 IP 공급, 고객사가 통합
- RISC-V: SiFive, BOOM... 등 여러 회사가 ASIC 설계

FPGA의 장점:
① 빠른 반복 (15분) → 초기 아이디어 검증에 좋음
② 저렴한 장비 (Basys 3: 10만원)
③ 재프로그래밍 가능 (같은 보드로 여러 디자인)

ASIC의 장점:
① 진정한 고속화 (GHz 동작)
② 전력 효율 (FPGA의 1/10)
③ 대량 생산 (칩당 가격 저렴)

ASIC의 단점:
① 개발 시간 (3개월+)
② 비용 (수백만 달러)
③ 마스크 비용 (수십억 원)

산업 현장의 패턴:
- 스타트업: FPGA로 프로토타입 → VC 펀딩 → ASIC 개발
- 대기업: 자체 ASIC 개발 + FPGA 검증 병렬 진행

면접관의 의도:
'당신은 FPGA 프로토타이핑과 ASIC 양쪽의 차이를 이해하는가?'

추천 대답:
'이 교재를 통해 FPGA의 빠른 반복성을 경험했습니다.
실제 상용 프로세서의 경우:
1. RTL 설계는 비슷하지만
2. 합성(Synopsys Design Compiler), P&R(Cadence Innovus)이 전문가 수준 필요
3. 검증은 FPGA(Xilinx Vivado)와 달리 STA(Static Timing Analysis),
   포멀 검증(Formal Verification), DFT(Design For Test) 등이 추가됨
4. 실리콘 기술은 우리가 직접 다루지 않지만,

### 📌 면접 주제: "링커 스크립트가 필요한 이유"
**→ 메모리 계층의 이해 (Ch5~Ch15 연결)**

#### 강의 대사
```
"링커 스크립트는 단순한 설정 파일처럼 보이지만,
실제로는 **메모리 아키텍처에 대한 완전한 이해**가 담겨 있습니다.

이 교재에서 우리는:
- Ch5: 메모리 구조 (IMEM=명령어, DMEM=데이터)
- Ch13~15: 캐시 계층 설계
- Ch22: 실제 메모리 배치

링커 스크립트는 이 모든 것을 연결하는 '계약서'입니다.

예를 들어 우리의 링커 스크립트에서:
- .text는 IMEM(0x8000_0000)에 배치
- .data는 DMEM(0x2000_0000)에 배치
- .bss는 DMEM의 .data 뒤에 배치

이것은:
① 하버드 구조(IMEM/DMEM 분리)를 반영하고
② 캐시 설계(I-Cache/D-Cache)를 고려하고
③ 메모리 컨트롤러의 중재 규칙을 감안합니다

면접관의 의도:
'메모리 계층을 정말 이해하나?'

추천 대답:
'링커 스크립트는 소프트웨어 입장에서 메모리 아키텍처를 표현한 것입니다.
우리가 설계한 파이프라인의 하버드 구조(명령어/데이터 분리)가
소프트웨어의 .text/.data 분리와 정확히 맞아떨어집니다.
이것은 하드웨어와 소프트웨어가 협력하는 좋은 예입니다.'"
```

### 📌 면접 주제: "타이머 인터럽트"
**→ Ch18~19의 예외 처리 실전 응용**

#### 강의 대사
```
"이 교재에서 타이머 인터럽트는 예외 처리의 '최종 실전'입니다.

우리가 학습한 순서:
- Ch18: CSR (제어 상태 레지스터)만 → 하드웨어 이해
- Ch19: 파이프라인 + CSR + 예외처리 → 통합
- Ch22: 실제 코드 + 링커 + 드라이버 → 운영

면접에서의 질문:
① 'CSR의 mtvec는 무엇인가?'
   → '인터럽트 핸들러의 주소를 저장하는 레지스터'

② 'mcause는 어떻게 설정되는가?'
   → '하드웨어(인터럽트 컨트롤러)가 예외 코드를 기록하는 레지스터'

③ 'MRET 명령어의 역할은?'
   → '메모리에 저장된 mepc(예외 발생 주소)로 되돌아가는 명령어'

④ '왜 타이머 인터럽트가 중요한가?'
   → '실시간 시스템의 기초. 정확한 시간 측정과 신뢰성 있는 작업 스케줄링 가능'

이 교재에서는:
- 타이머가 일정 시간마다 인터럽트 발생
- 프로세서가 현재 명령어를 중단하고 핸들러로 점프
- 핸들러가 LED 토글 등의 작업 수행
- MRET으로 원래 코드로 복귀

이것이 바로 '멀티태스킹의 기초'입니다.
고급 OS에서는 이 타이머 인터럽트를 이용해 여러 프로세스를 교대로 실행(context switching)합니다.'"
```

### A. 링커 스크립트 템플릿 (주석 포함)
```ld
/* ch22_linker.ld — RV32I 링커 스크립트 (주석 추가 강사용) */

/* MEMORY: 우리 Basys 3의 메모리 지도 정의
   표준 주소(링커가 사용)
*/
MEMORY {
    IMEM (rx) : ORIGIN = 0x80000000, LENGTH = 16K   /* 명령어 메모리 */
    DMEM (rwx) : ORIGIN = 0x20000000, LENGTH = 32K  /* 데이터 메모리 */
}

/* SECTIONS: C 코드의 어느 부분이 어디로 갈까? */
SECTIONS {
    /* 코드 섹션 → IMEM으로 */
    .text : {
        *(.text*)           /* 모든 .text 섹션 */
        *(.rodata*)         /* 읽기전용 데이터 (상수) */
    } > IMEM

    /* 초기화된 데이터 → DMEM으로 */
    .data : {
        *(.data*)
    } > DMEM

    /* 미초기화 데이터 → DMEM으로 (메모리만 예약, 값은 0) */
    .bss : {
        *(.bss*)
        *(COMMON)
    } > DMEM

    /* 스택 포인터 초기값 (DMEM 끝) */
    __stack_end = ORIGIN(DMEM) + LENGTH(DMEM);
}
```

**강사 설명 포인트:**
- `ORIGIN`: 섹션의 시작 주소 (0x8000_0000 = 표준 RISC-V 관례)
- `LENGTH`: 섹션의 크기 (16K = 명령어 16KB, 32K = 데이터 32KB)
- `rx`/`rwx`: 권한 (r=읽기, w=쓰기, x=실행)
- `> IMEM/DMEM`: "이 섹션을 어느 메모리 영역에 넣을 것인가"

### C. 드라이버 코드 (복사해서 바로 사용)

#### UART 드라이버 (ch22_drivers.c 에서 발췌)
```c
/* UART printf 연결 — 이것이 강사 설명 #3의 핵심 */

// 저수준 UART 쓰기 함수
int uart_putchar(int c) {
    // UART 레지스터 확인: TX FIFO 비어있는가?
    while (*(volatile int *)UART_STATUS & 0x10) {
        // 비트 4가 1 = TX FIFO FULL, 대기
    }
    // FIFO가 비어있으면 데이터 쓰기
    *(volatile int *)UART_DATA = c & 0xFF;
    return c;
}

// printf가 호출하는 시스템콜 스텁
int _write(int fd, char *buf, int len) {
    int i;
    for (i = 0; i < len; i++) {
        if (buf[i] == '\n') {
            uart_putchar('\r');  // Windows 호환
        }
        uart_putchar(buf[i]);
    }
    return len;
}

// 사용자 코드에서:
// printf("Temperature: %d°C\n", 25);
// → _write() 호출 → uart_putchar() 반복 호출 → USB 전송 → 터미널에 출력!
```

**강사 설명:**
> "보이는 것처럼 복잡하지 않죠?
> printf는 내부적으로 _write()라는 함수를 호출합니다.
> 우리가 _write()를 구현하면 printf가 '마술처럼' UART로 보냅니다."

#### 타이머 인터럽트 핸들러 (ch22_main.c 에서 발췌)
```c
/* 타이머 인터럽트 핸들러 — 이것이 강사 설명 #4의 핵심 */

// 인터럽트 발생 시 자동으로 호출됨 (__attribute__((interrupt)) 지정)
void timer_interrupt_handler(void) __attribute__((interrupt)) {
    // 실행 기록: LED 토글
    led_toggle();

    // 타이머 인터럽트 플래그 초기화 (중요: 다시 인터럽트 받을 수 있도록)
    timer_clear_pending();

    // MRET은 __attribute__((interrupt))가 자동으로 삽입
    // (메모리에 저장된 mepc로 복귀)
}

// main()에서 설정
void main(void) {
    uart_init();
    gpio_init();
    led_init();
    timer_init();  // 타이머 시작 & 인터럽트 활성화

    // 무한 루프
    while (1) {
        // 메인 작업 (예: 센서 읽기)
        printf("Main thread running\n");

        // 백그라운드: 타이머 인터럽트가 주기적으로 발생
        // (현재 명령어가 중단되고 timer_interrupt_handler 실행)
    }
}
```

**강사 설명:**
> "핵심은 __attribute__((interrupt))라는 GCC 속성입니다.
> 이것을 붙이면 컴파일러가 자동으로 MRET을 삽입합니다.
> 따라서 우리는 '언제 돌아갈 것인가'를 신경쓸 필요 없습니다."

### D. 최종 데모 프로그램 전체 (복사 가능)
```c
/* ch22_main.c — 최종 데모 프로그램 */

#include "ch22_drivers.h"

// 글로벌 변수 (DMEM에 배치됨)
volatile int timer_count = 0;
volatile int led_index = 0;

// 타이머 인터럽트 핸들러
void timer_interrupt_handler(void) __attribute__((interrupt)) {
    timer_count++;

    // 1000ms마다 LED 토글 (타이머가 1000마다 발생한다고 가정)
    if (timer_count >= 10) {
        timer_count = 0;
        led_toggle_at(led_index);
        led_index = (led_index + 1) & 0xF;  // LD0~LD15 순환
    }

    timer_clear_pending();
}

int main(void) {
    // 초기화
    uart_init();
    gpio_init();
    led_init();
    timer_init();

    // 부팅 메시지
    printf("\n");
    printf("===============================================\n");
    printf("  Hello RISC-V! Welcome to Chapter 22\n");
    printf("  Processor: RV32I 5-stage Pipeline\n");
    printf("  FPGA: Xilinx Basys 3 (XC7A35T)\n");
    printf("===============================================\n");
    printf("\n");

    // 모드 선택
    printf("Select mode:\n");
    printf("  [1] Manual LED control (press buttons)\n");
    printf("  [2] Timer interrupt (auto-blink)\n");
    printf("  [3] Performance report\n");
    printf("> ");

    // 사용자 입력 (간단한 버전: 기본 모드 2)
    int mode = 2;

    if (mode == 1) {
        printf("Press button 0 to toggle LD15\n");
        while (1) {
            if (button_pressed(0)) {
                led_toggle_at(15);
                printf("LED toggled!\n");
                delay(100);  // 디바운싱
            }
        }
    } else if (mode == 2) {
        printf("Timer interrupt mode active\n");
        printf("LED blinks automatically\n");
        while (1) {
            // 메인 루프는 아무것도 하지 않음
            // 타이머 인터럽트가 백그라운드에서 LED 토글
            printf("Timer: %d ms\n", timer_count * 100);
            delay(1000);
        }
    } else if (mode == 3) {
        printf("Performance Report:\n");

        // CSR에서 성능 카운터 읽기
        unsigned long cycles = read_csr(mcycle);
        unsigned long instrs = read_csr(minstret);
        float cpi = (float)cycles / (float)instrs;

        printf("  Cycles: %u\n", cycles);
        printf("  Instructions: %u\n", instrs);
        printf("  CPI: %.2f\n", cpi);
        printf("  Clock Speed: 50 MHz\n");
        printf("  I-Cache Hit: 98.5%%\n");
        printf("  D-Cache Hit: 97.2%%\n");

        while (1) {
            // 루프 종료 없음 (Basys 3는 "끝나지 않는" 프로그램)
        }
    }

    return 0;  // 도달 불가능 (while(1))
}
```

**사용 방법:**
1. 크로스컴파일: `riscv32-unknown-elf-gcc -mcmodel=medany -O2 -c ch22_main.c -o main.o`
2. 링킹: `riscv32-unknown-elf-ld -T ch22_linker.ld main.o -o app.elf`
3. 바이너리 변환: `riscv32-unknown-elf-objcopy -O binary app.elf app.bin`
4. Vivado로 로드 & 실행

## VII. 강사 팁 & 트러블슈팅

### 🔴 흔한 오류 #1: "printf가 아무것도 출력 안 해요"
**원인:** `_write()` 함수 미구현 또는 링커 에러
**해결:**
1. `ch22_drivers.c`가 컴파일되었는가? (Makefile 확인)
2. UART 초기화 (`uart_init()`)가 호출되었는가?
3. 보드의 USB가 연결되었는가? (터미널에서 `/dev/ttyUSB0` 확인)

### 🔴 흔한 오류 #2: "타이머 인터럽트가 발생하지 않아요"
**원인:** mtvec 설정 미완료 또는 mie(인터럽트 활성화) 누락
**해결:**
1. 부트스트랩(startup.S)에서 `csrw mtvec, %0` 확인
2. `__attribute__((interrupt))`가 붙어있는가?
3. CSR mie의 MTIE(타이머 인터럽트) 비트가 1인가?

### 🔴 흔한 오류 #3: "프로그램이 메모리 오버플로우"
**원인:** 스택과 힙이 충돌 (32KB DMEM이 부족)
**해결:**
1. 전역 배열 크기 줄이기
2. 동적 할당(malloc) 최소화
3. 스택 포인터 위치 확인 (linker.ld의 `__stack_end`)
