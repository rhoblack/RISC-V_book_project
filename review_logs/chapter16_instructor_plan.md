- Ch15 자체 프로토콜의 한계 3가지(확장성/재사용성/검증)는 강사 입장에서 판서하기 좋은 구조

### 16.2절: AMBA 버스 패밀리와 AHB-Lite 신호 체계

**강의 현장에서 쓸 문장**:
> "세 가지 버스를 복잡도와 성능의 2차원으로 이해하세요.
> - **APB**: 타이머나 GPIO 같이 느린 장치 (Ch17에서 다룹니다)
> - **AHB-Lite**: 우리가 배울 것. 메모리처럼 빠르지만 단일 마스터
> - **AXI4**: 스마트폰처럼 복잡한 시스템에서 여러 마스터가 동시에 접근 (선택 주제)
>
> 이 표 (Ch15 vs AHB 신호 대응)를 보면, 우리가 배운 개념이 '새것'이 아니라 '표준화된 것'임을 알 수 있어요."

**평가: ⭐⭐⭐⭐ (개념 이해 양호, 신호 일대일 대응 명확)**
- 신호 대응표는 강의 중 비교 설명에 최적화됨
- 다만 HTRANS[1:0]의 4가지 상태(IDLE/BUSY/NONSEQ/SEQ) 설명이 16.3에서 나오므로, 여기서는 "신호 갯수와 역할에만 집중"하는 것이 좋음

**강사 추가 설명 포인트**:
> "HWDATA가 HADDR보다 1사이클 늦는 것(표에서 보이지 않지만)은 파이프라인 때문입니다.
> Ch09에서 배운 5스테이지 파이프라인처럼, AHB도 '주소 페이즈'와 '데이터 페이즈'를 분리합니다.
> 이건 16.4 타이밍 다이어그램에서 명확히 드러날 거예요."

### 16.3절: AHB-Lite 11개 핵심 신호

**강의 현장에서 쓸 문장**:

>    → 실제 데이터 전송과 준비 상태를 나타내는 신호
>
> 각 신호는 '왜' 필요한지를 이해하면 외울 필요 없이 자연스럽게 나옵니다."

**강사 팁**:
> "HREADY를 '수갑'이라고 생각하세요. HREADY=0일 때 Master(자동차)는 주소를 변경할 수 없습니다.
> 마치 손이 묶인 것처럼. Slave(신호등)가 '아직 준비 안 됐다'고 Master를 멈춰놓는 겁니다."

### 16.4절: AHB-Lite 타이밍 다이어그램

**강의 현장에서 쓸 문장**:
> "이 파형은 무섭게 보이겠지만, 실은 '춤'이에요. Master와 Slave가 정해진 스텝을 밟는 거죠.
> 파형을 왼쪽에서 오른쪽으로 천천히 따라가면서:
>
> 1️⃣ Master가 주소를 내보낸다 (HADDR = 0x1000, HTRANS = NONSEQ)
> 2️⃣ Slave가 데이터를 준비한다 (내부적으로)
> 3️⃣ Master가 주소를 다음 것으로 바꾼다 (파이프라인!)
> 4️⃣ Slave가 이전 주소의 데이터를 내보낸다 (HRDATA = 0x1234)
>
> 이것을 3단계로 배웠어요:
> - 단순: 모든 신호가 깔끔한 경우
> - BUSY: Master가 요청을 보냈는데 다음 사이클에 보낼 게 없을 때
> - HREADY LOW: Slave가 늦어서 데이터 페이즈가 지연될 때"

**평가: ⭐⭐⭐⭐⭐ (파형 단계별 설명 강의 최적화)**

**강사용 보조 자료 (칠판 그리기)**:
```
가장 간단한 경우: 1사이클 읽기

CLK        |___|___|___|___|
HTRANS     |IDLE|NONSEQ|SEQ|
HADDR      |    |0x1000|0x1004|
HRDATA     |    |   [지연됨]   |0x1234|
HREADY     |  1  |  1  |  1  |

"주소가 한 사이클 앞서가고, 데이터가 한 사이클 뒤따라옵니다 (파이프라인!)"
```

### 16.5절: AHB Master FSM 설계

**강의 현장에서 쓸 문장**:
> "Ch15에서 우리 캐시의 miss 핸들러가 어떻게 메인 메모리에 요청했는지 기억하세요?
> 그 요청 로직을 AHB 신호로 '번역'하는 것이 Master FSM입니다.
>
> 상태는 네 가지:
> - IDLE: 아무것도 하지 않음

> - DONE: 전송 완료
>
> 각 상태에서 'HREADY가 높으면 진행, 낮으면 대기'하는 한 가지 규칙만 기억하면 돼요."

**평가: ⭐⭐⭐⭐ (FSM 역할 명확, 코드 앞 개념 설명 적절)**

### 16.6절: AHB Slave (SRAM) 구현

**강의 현장에서 쓸 문장**:
> "Slave의 역할은 '수동적'입니다. Master의 요청을 받고 반응만 하면 되니까요.
> 읽기: HADDR를 받으면 → 메모리에서 꺼내서 → 다음 사이클에 HRDATA로 보냄

>
> 핵심은 '데이터가 항상 1사이클 뒤'라는 것입니다. 이건 Slave가 BRAM을 사용하기 때문이에요.
> (BRAM은 주소를 받은 다음 사이클에 데이터를 출력합니다)"

## II. 핵심 비유 개발 및 검증

### 비유 #1: "버스는 합의의 춤" (AHB 프로토콜 규칙)

**기술 사실**: Master와 Slave가 신호를 주고받는 순서가 표준화되어 있음
- HREADY=0일 때 Master가 주소를 변경할 수 없음
- 데이터가 항상 주소보다 1사이클 늦음
- 각 신호는 HCLK의 상승 에지에서만 변함

**비유**:
> "춤을 생각해봅시다. 남자가 여자를 이끌되, 정해진 스텝을 따라야 합니다.
> 춤 중간에 갑자기 여자가 다른 방향을 보면 안 되죠.
> AHB도 마찬가지입니다.
> - Master(춤꾼)는 정해진 순서(HTRANS→HADDR→HWDATA)로 신호를 보냅니다.
> - Slave(파트너)는 그 신호에 정확히 반응합니다 (HRDATA 타이밍 유지).
> - HREADY는 '다음 스텝을 할 준비 되셨나요?'하는 신호예요."

**검증**:
| 항목 | 결과 |
|------|-----|
| ① 기술 사실과 매핑 | ✅ Master/Slave 신호 순서와 춤의 스텝이 정확히 대응 |
| ② 한계 명시 | ✅ "춤은 예술이지만 AHB는 공학" + "감정이 필요하지만 프로토콜은 규칙만" |
| ③ 오해 방지 | ✅ "춤처럼 우아해 보이지만 실제로는 컴퓨터가 정확히 계산하는 것" |
| ④ 대안 비유 | ✅ "신호등과 자동차" - Master(자동차) ↔ Slave(신호등) 관계 명확 |

**강의 중 사용 방법**:
- 16.1절 도입: "왜 규칙이 필요한가?" → 춤 비유
- 16.4절 타이밍: "파형이 복잡하게 보이지만, 사실 춤처럼 정해진 리듬"

---

### 비유 #2: "HREADY는 수갑" (웨이트 스테이트)

**기술 사실**: HREADY=0일 때 Master가 주소/제어 신호를 변경할 수 없음

**비유**:
> "HREADY=0이 되는 순간, Master의 손이 묶입니다. 마치 수갑이 채워진 것처럼.
> Slave가 '아직 준비가 안 됐어, 잠시만 대기해'라고 하는 신호예요.
> - HREADY=1: 손이 자유로움 → 다음 신호를 내보낼 수 있음
> - HREADY=0: 손이 묶임 → 현재 신호를 그대로 유지해야 함"

**검증**:
| 항목 | 결과 |
|------|-----|
| ① 기술 사실과 매핑 | ✅ HREADY LOW = Master 신호 동결 (정확) |
| ② 한계 명시 | ✅ "수갑은 이유가 없지만, HREADY는 Slave의 준비 부족이라는 기술적 이유" |
| ③ 오해 방지 | ✅ "이것은 버그가 아니라 정상적인 프로토콜 규칙" |
| ④ 대안 비유 | ✅ "신호등 빨강" - Master(자동차) 정지 + 신호등이 녹색될 때까지 대기 |

**강의 중 사용 방법**:
- 16.3절 HREADY 신호 설명 → 수갑 비유로 직관성 확보
- 16.4절 타이밍 분석 → "언제 수갑이 채워질까?" 게임처럼 진행
- 16.5절 Master FSM → "상태 전이는 HREADY가 1일 때만 일어난다" 연결

### 비유 #3: "AMBA는 칩 내 고속도로" (AHB vs APB)

**기술 사실**:
- AHB: 고성능, 복잡도 높음, 메모리 버스용
- APB: 저속, 단순, 주변 장치 버스용
- AXI: 초고성능, 비순서 전송, 멀티마스터

**비유**:
> "칩 내 통신을 도로에 비유하면:
> - **APB는 시골길**: 속도는 느리지만 구조가 간단 (농장에서 마을까지)
> - **AHB는 고속도로**: 속도 빠르고 복잡한 규칙 (서울 강남대로)
> - **AXI는 초고속 네트워크**: 자동차들이 제각각 움직이면서도 충돌 안 함 (인터넷처럼)
>
> 우리 프로젝트는 고속도로(AHB)를 선택했어요. 메모리는 빨라야 하니까요."

**검증**:
| 항목 | 결과 |
|------|-----|
| ① 기술 사실과 매핑 | ✅ 각 버스의 특성(속도/복잡도/용도)과 도로 구분이 정확 |
| ② 한계 명시 | ✅ "도로 메타포는 물리적 위치를 전제하지만, 칩 내 신호는 전자적" |
| ③ 오해 방지 | ✅ "세 버스 모두 각자의 목적에 최적화되어 있다" |
| ④ 대안 비유 | ✅ "우편 배송 방식" - 편지(APB) vs 택배(AHB) vs 공중 배송(AXI) |

**강의 중 사용 방법**:
- 16.2절 AMBA 패밀리 설명 → 도로 메타포로 포지셔닝 시각화
- 16.7절 중재 기능 → "고속도로의 톨게이트처럼 여러 Master를 조절"

## III. 수강생 막힘 포인트 Top 3 & 대답 준비

### 막힘 포인트 #1: HTRANS의 4가지 상태

**학생의 질문**: "왜 NONSEQ와 SEQ를 구분해야 하나요? 그냥 주소하고 데이터만 보내면 안 돼요?"

**강사 대답 (그대로 사용 가능)**:
> "좋은 질문입니다! HTRANS[1:0]의 4가지 상태를 봅시다:
> - **IDLE** (2'b00): 아무 요청 없음 (Master가 쉬고 있음)
> - **BUSY** (2'b01): 요청이 있는데, 아직 주소는 안 보냄 (다음 사이클을 기다리는 중)
> - **NONSEQ** (2'b10): 점프 주소 (캐시 미스처럼 주소가 연속이 아님)
> - **SEQ** (2'b11): 순차 주소 (다음 메모리 위치)
>
> 왜 Slave가 이것을 알아야 할까요?
>
> Slave(SRAM)는 이 정보로 최적화를 할 수 있거든요:
> - SEQ를 보면? '다음에 올 주소를 미리 준비해둘까?' (프리페치)
> - NONSEQ를 보면? '어? 점프네. 준비된 거 버리고 새로 준비해야겠다'
>
> 실제 고급 캐시(L2, L3)는 SEQ를 보고 미리 로드합니다.
> 우리 Basys 3의 SRAM은 간단하니까 그냥 '신호를 받고 반응'하지만,
> 산업 현장의 고급 메모리들은 이 신호를 보고 성능을 최적화합니다."

**FAQ 박스 추가 위치**: 16.3절 HTRANS 설명 직후

---

### 막힘 포인트 #2: "HWDATA가 HADDR보다 1사이클 뒤인 이유"

**학생의 질문**: "왜 데이터를 미리 보내지 않고 기다렸다가 보내요? 그럼 느려질 텐데?"

**강사 대답 (파이프라인 연결)**:
> "이건 처음에는 이상해 보이지만, 사실 **최고의 설계**입니다!
>
> Ch09에서 배운 파이프라인을 기억하세요?
> 파이프라인은 각 스테이지를 병렬로 처리해서 성능을 올렸어요.
>
> AHB도 같은 원리입니다:
> - 1사이클: Master가 주소를 보냄 (ADDRESS PHASE)
> - **동시에**: Slave는 이전 주소의 데이터를 꺼내는 중
> - 2사이클: Master가 새 주소를 보냄 (다음 ADDRESS)
> - **동시에**: Slave는 이전 주소의 데이터를 응답 (DATA PHASE)
>
> 만약 데이터를 미리 보낸다면?
> Slave: '주소 받았어 → 데이터 꺼냈어' (두 사이클 소요)
> Master: '아 이제 다음 주소 보낼게' (대기만 함)
> → 효율성 떨어짐!
>
> 하지만 AHB는 주소와 데이터를 **동시에 다루므로** 파이프라인이 됩니다:
> 매 사이클마다 새 주소가 들어오고, 이전 데이터가 나간다 = 최고 효율!"

**Tip 박스 추가 위치**: 16.4절 타이밍 다이어그램 직후
**메타인지 박스**: "따라서 AHB의 '1사이클 지연'은 버그가 아니라 성능 최적화입니다"

### 막힘 포인트 #3: "Master FSM 상태 전이는 HREADY가 1일 때만 일어난다"

**학생의 질문**: "HREADY가 0이면 FSM이 멈추는 거예요?"

**강사 대답**:
> "정확히요! 그게 HREADY의 아이디어입니다.
>
> 생각해봅시다:
> - HREADY=1 → Slave가 준비됨 → 다음 상태로 진행
> - HREADY=0 → Slave가 준비 안 됨 → **현재 상태에 머무름**
>
> 예를 들어, Master의 ADDR 상태:
> ```
> always_ff @(posedge clk) begin
>    if (current_state == ADDR && hrdy == 1'b1)
>       next_state = DATA;  // 진행
>    else if (current_state == ADDR && hrdy == 1'b0)
>       next_state = ADDR;  // 대기
> end
> ```
>
> 마치 신호등의 빨강처럼:
> - 녹색: 자동차 진행
> - 빨강: 자동차 정지 (상태 유지)
>
> 이것이 자동으로 이루어지니까 프로토콜이 강력합니다.
> Slave가 느리든 빠르든, 문제없이 작동해요."
