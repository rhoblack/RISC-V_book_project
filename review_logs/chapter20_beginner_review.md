## 막힘 포인트 Top 3 (진단 & 완화책)

### Top 1: 🔴 "Slack 개념이 추상적"
**진단**:
- 도로 신호등 비유는 물리적 직관을 제공하나, FPGA 타이밍의 "시간 관계"를 명확히 하지 못함
- "Slack = 제약 - 실제 지연" 공식은 맞지만, **왜 이 순서**인지 (제약이 먼저인지) 명확 진술 부재
- WNS=-3.456ns 예제에서 "음수가 왜 위반"인지 한 문장 더 필요

**현재 설명**: 225-231행
```
Slack = 제약 지연 - 실제 지연
예: 10ns 제약에서 실제 9ns → slack=1ns (여유)
    실제 12ns → slack=-2ns (위반)
```

**완화책**:
- ✅ 이미 방향은 맞음. 다만 SVG(시간축)를 추가하면 "제약 영역 vs 초과 영역" 시각화 가능
- ✅ 추천 SVG 내용: "파란 영역(허용범위 10ns), 빨간 영역(실제 경로 12ns), 겹친 부분(Slack=-2ns)"

### Top 2: 🟡 "FSM Encoding 개념이 직관적 아님"
**진단**:
- 68-72행에서 원-핫(FF 많음, 디코더 복잡) vs 바이너리(FF 적음, 디코더 간단) 설명은 정확
- 그러나 **어느 상황에서 어느 것을 선택하는가**에 대한 가이드 부재
- 20.5 Step 2에서 "바이너리로 변경하면 LUT 60 감소"라고만 함 (왜 감소하는지 설명 부재)

**현재 설명**: 68-72행
```
원-핫: 상태당 FF 1개, 디코더 복잡
바이너리: 상태당 log2(N) FF, 디코더 간단
```

**완화책**:
- ✅ 현재: "속도가 중요하면 원-핫, 면적이 중요하면 바이너리"
- 추천: 20.5 Step 2에 한 문장 추가 — "바이너리는 디코더가 간단하므로 조합 경로 길이가 짧아져 LUT 감소"

### Top 3: 🟡 "20.2 XDC 제약이 여전히 추상적"
**진단**:
- create_clock 예제는 명확 (10.0 = 100MHz)
- set_input_delay/set_output_delay 예제도 명확 (3.0ns max, 0.5ns min)
- 그러나 **이 값들을 어떻게 결정하는가** (설계 문서? 측정?) 명확하지 않음
- set_false_path 예제는 있지만, "false path를 과다 사용하면 위험"(Q&A)만으로는 부족

**현재 설명**: 155-168행
```
# GPIO 입력: 외부 신호가 30% 클록 기준으로 안정
set_input_delay -clock clk100 -max 3.0 [get_ports GPIO_IN]
```

**완화책**:
- ✅ 현재: set_input_delay 직후 "일반적으로 PCB 라우팅 + 센서 지연"이라 설명함. 좋음.
- 추천: "Basys 3 보드 사양서에서 GPIO 세트업 타임이 3ns이므로 이 값 사용" 같은 구체 출처 언급 (없으면 "설계 경험/시뮬레이션으로 결정" 코멘트 추가)
