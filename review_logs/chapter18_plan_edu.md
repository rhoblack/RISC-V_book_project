### 블룸 분류 배분 근거

- **L2 × 3개**: CSR은 새로운 레지스터 공간이므로 이해 단계가 충분히 확보되어야 L3·L4로 진입할 수 있다. 기억/이해 목표를 3개로 설정하여 개념 기반을 다진다.
- **L3 × 2개**: SystemVerilog 구현은 이전 챕터(Ch09~Ch12)의 파이프라인 구현 경험을 전이(transfer)할 수 있는 적용 수준 목표다.
- **L4 × 2개**: 인터럽트 마스킹 설계와 파이프라인 인터페이스 설계는 여러 CSR 간의 관계를 분석해야 하므로 분석 수준이 적절하다.
- **L5·L6 제외(본문)**: 평가·창조 수준은 연습문제(5번·6번)에서 다루며, 본문 목표에서는 의도적으로 제외하여 인지 부하를 조절한다.

## 18.2절 인지 부하 상세 완화 전략

18.2절은 7개 CSR을 순서대로 나열하면 "스펙 암기"처럼 느껴질 수 있다. 다음 전략으로 덩어리화(chunking)한다.

### 전략 1: 역할별 3그룹 분류 후 순차 제시

```
그룹 A — 상태·제어 (1개)
  mstatus  : 프로세서 전체 동작 상태 스위치

그룹 B — 예외 처리 루틴 (3개)
  mtvec    : 핸들러 진입 주소
  mepc     : 복귀 주소 (예외 발생 시점 PC)
  mcause   : 예외 원인 코드

그룹 C — 인터럽트 제어 (2개) + 임시 저장 (1개)
  mie      : 인터럽트 활성화 마스크
  mip      : 현재 계류 중인 인터럽트 상태
  mscratch : 핸들러 임시 저장 공간
```

그룹 B의 3개 CSR은 "예외 발생 → mtvec 조회 → mepc 저장 → mcause 기록"이라는 하나의 시나리오로 묶어 제시하면 관계성이 명확해진다.

### 전략 2: 기존 지식과 명시적 연결

| CSR | 연결할 기존 지식 | 연결 문장 예시 |
|-----|----------------|--------------|
| mstatus | 일반 레지스터의 상태 플래그 (RISC-V에는 flags 레지스터가 없다는 사실) | "ARM의 CPSR, x86의 EFLAGS와 같은 역할이지만 RISC-V는 CSR로 분리한다" |
| mtvec | 메모리 맵 I/O 기저 주소 (Ch16 AHB) | "AHB 버스에서 디바이스 기저 주소를 설정한 것처럼, 예외 핸들러의 기저 주소를 등록하는 레지스터다" |
| mepc | 파이프라인의 PC 레지스터 (Ch09) | "파이프라인에서 매 사이클 갱신되는 PC를 '예외 발생 순간'에 스냅샷으로 저장한다" |
| mcause | 디버거의 예외 코드 개념 | "시스템 콜에서 에러 코드를 반환하는 것처럼, 예외 원인을 번호로 인코딩한다" |
| mie / mip | 인터럽트 마스크 레지스터 (일반적 마이크로컨트롤러 경험) | "mie는 '수신 허용 목록', mip는 '현재 수신함'이다" |
| mscratch | 스택 포인터 임시 저장 관용구 | "핸들러 진입 직후 sp를 mscratch에 백업하는 패턴이 RISC-V ABI 표준이다" |

### 전략 3: 비트 필드 표를 정적 암기가 아닌 구현 출발점으로 활용

비트 필드 표 다음에 바로 SystemVerilog 구현 코드를 제시한다. "표의 각 행이 곧 코드의 각 필드 선언"임을 화살표로 연결하면 표를 암기 대상이 아닌 코드 설계도로 인식하게 된다.

## 연습문제 6문항

### 문항 1 — L1 기억 (Remember)

**문제**: 다음 빈칸을 채우시오.
- RISC-V의 CSR 주소 공간은 총 ____비트이며, 최대 ____개의 CSR을 정의할 수 있다.
- mstatus 레지스터에서 전역 인터럽트 활성화 비트 MIE는 비트 ____에 위치한다.

**정답**: 12비트 / 4096개 / 비트 3

**의도**: 수업 전 예습 확인 또는 수업 직후 즉각 점검용. 단순 사실 확인이지만 후속 문항의 전제 지식이 된다.

---

### 문항 2 — L2 이해 (Understand)

**문제**: mtvec 레지스터의 MODE 필드가 0(Direct)일 때와 1(Vectored)일 때, 외부 인터럽트(MEIP) 발생 시 프로세서가 점프하는 주소를 각각 계산하시오. mtvec = 32'h0000_1000이라 가정한다.

**정답**:
- Direct(MODE=0): BASE = 0x0000_1000, 점프 주소 = 0x0000_1000
- Vectored(MODE=1): BASE = 0x0000_1000, MEIP 원인 코드 = 11(0xB), 점프 주소 = BASE + 4×11 = 0x0000_102C

**의도**: 단순 정의 암기에서 벗어나 모드 차이를 실제 주소 계산으로 확인. 비유(119 전화번호) 이후 구체적 수식 적용 연습.

---

### 문항 3 — L3 적용 (Apply)

**문제**: 아래 어셈블리 코드에서 실행 후 t0와 mstatus의 MIE 비트 값을 예측하시오. 실행 전 mstatus = 32'h0000_0000, t0 = 32'hDEAD_BEEF라고 가정한다.

```asm
li   t1, 0x8         # t1 = 0x0000_0008 (MIE 비트 마스크)
csrrs t0, mstatus, t1  # mstatus의 MIE 세트, 이전 값을 t0에 저장
```

**정답**: t0 = 32'h0000_0000 (CSRRS 실행 전 mstatus 값), mstatus.MIE = 1

**의도**: CSRRS의 "원자적 읽기 후 OR 쓰기" 동작을 코드 추적으로 검증. 특히 t0에 저장되는 값이 "쓰기 전" 값임을 확인시킨다.

---

### 문항 4 — L4 분석 (Analyze)

**문제**: 다음 조건에서 인터럽트가 실제로 서비스되는지 분석하시오.
- mstatus.MIE = 1
- mie = 32'h0000_0080 (MTIE 비트만 세트)
- mip = 32'h0000_0880 (MEIP와 MTIP 동시 계류)

어떤 인터럽트가 처리되며, 다른 인터럽트가 무시되는 이유를 mie와 mip의 관계식으로 설명하시오. 또한 두 인터럽트를 모두 처리하려면 mie를 어떻게 수정해야 하는가?

**정답**:
- 처리 조건: `mstatus.MIE & (mie & mip) != 0`
- 현재 `mie & mip` = 0x0000_0080 & 0x0000_0880 = 0x0000_0080 → MTIP(타이머)만 처리됨
- MEIP(bit 11)가 mip에 있어도 mie.MEIP(bit 11)가 0이므로 마스킹되어 무시됨
- 두 인터럽트 모두 처리: mie = 32'h0000_0880 (MEIP + MTIP 비트 모두 세트)

**의도**: mie "AND" mip의 관계를 논리적으로 분석. 인터럽트 마스킹이 단일 MIE 비트가 아닌 두 단계(전역 MIE + 개별 mie)로 이루어짐을 파악.

---

### 문항 5 — L5 종합/평가 (Evaluate → 실질적 설계 수준)

**문제**: 현재 구현된 csr_unit에 하드웨어 성능 카운터 2개를 추가하려 한다.
- mcycle (CSR 주소 0xB00): 클럭 사이클 수 카운트 (64비트이나 RV32I에서는 하위 32비트만 구현)
- minstret (CSR 주소 0xB02): 완료된 명령어 수 카운트

다음 설계 결정에 대한 근거를 제시하고 SystemVerilog 선언부를 작성하시오:
1. mcycle은 매 클럭 자동 증가해야 하므로 CSR 쓰기 로직에서 어떻게 처리해야 하는가?
2. minstret 증가 시점은 언제이며, 파이프라인의 어느 신호를 사용해야 하는가?
3. 두 카운터를 CSRRW로 초기화(0으로 쓰기)할 수 있어야 한다면, 자동 증가와 명시적 쓰기 간의 우선순위를 어떻게 결정하는가?

**평가 기준**:
- 자동 증가 vs 명시적 쓰기 충돌 처리의 논리적 일관성 (예: 명시적 쓰기 우선)
- minstret 증가 시점: WB 스테이지 valid 신호 또는 `~stall & ~flush` 조건
- SystemVerilog 코드 문법 정확성

**의도**: Ch15에서 구현한 성능 카운터(cycle_cnt, instr_cnt)를 CSR 인터페이스로 확장하는 설계 문제. 기존 지식(Ch15)과 새 지식(CSR)을 통합하여 새로운 구조를 만든다.

---

### 문항 6 — L6 창조/평가 (Create/Evaluate)

**문제**: 5단 파이프라인에서 CSR 명령어(CSRRW)가 EX 스테이지에서 실행되고, 그 결과가 같은 사이클의 ID 스테이지에서 읽으려 한다고 가정하자.

(a) 이 상황이 데이터 해저드(data hazard)를 유발하는 이유를 파이프라인 다이어그램으로 설명하시오.

(b) 다음 두 해결 방안 중 어떤 방식이 더 적절한가? 근거를 제시하시오.
  - 방안 1: 포워딩(forwarding)으로 CSR 값을 ID 스테이지에 전달
  - 방안 2: 소프트웨어적으로 CSR 명령어 후 2 NOP를 삽입하도록 컴파일러/어셈블러에 요구

(c) RISC-V 스펙(Volume I, Section 1.6)은 CSR 명령어를 "즉시 가시적(immediately visible)"으로 규정한다. 이 스펙 요구사항이 하드웨어 포워딩을 강제하는가, 아니면 소프트웨어 NOP도 허용하는가? 교재 수준에서의 설계 선택을 정당화하시오.

**평가 기준**:
- 파이프라인 해저드 원인 설명의 정확성
- 두 방안의 장단점 비교 (면적/복잡도 vs 성능 손실/컴파일러 의존성)
- RISC-V 스펙 해석의 논리적 일관성

**의도**: 가장 높은 수준의 문항. CSR 해저드는 이 교재에서 명시적으로 다루지 않는 고급 주제이므로, 학습자가 기존 포워딩 지식(Ch10)을 새 맥락에 적용하고 스펙 문서를 해석하는 능력을 평가한다.

## 비유/예시 평가 및 확정

### 비유 1: CSR = 자동차 계기판

**원래 비유**: 속도·연료·온도 → 처리 중인 상태 정보

**평가**:
- 장점: 친숙하고 직관적. "읽기 전용 정보 표시"라는 수동적 이미지를 전달함
- 문제: CSR은 읽기와 쓰기가 모두 가능하며, 일부 CSR(mstatus, mtvec)은 제어 목적으로 사용된다. 계기판은 "쓰기" 개념이 약함
- 한계 명시 필수: "계기판은 운전자가 값을 바꿀 수 없지만, CSR은 소프트웨어가 값을 읽고 쓸 수 있다는 점에서 다르다"

**확정**: 도입부(18.1절)에서만 사용. "계기판 → 읽기" 이미지로 CSR 존재 이유를 설명한 후, 즉시 "제어판(control panel)" 비유를 추가하여 쓰기 가능성을 보완한다.

---

### 비유 2: mstatus = 신호등 제어기 (MIE = 교통 허용/차단)

**평가**:
- 장점: MIE 비트의 "전역 인터럽트 on/off" 의미를 잘 전달함
- 문제: mstatus는 MIE 외에도 MPIE, MPP 등 여러 필드를 포함하므로 신호등은 단일 필드 비유로 축소될 수 있음
- 오해 가능성: "신호등 = mstatus 전체"로 오해하면 안 됨

**개선**: mstatus 전체를 "도시 전체 교통 통제 센터"로 비유하고, MIE 비트만 "도시 진입 허가 스위치"로 표현한다. mie/mip와의 관계를 설명할 때는 "진입 허가 스위치(MIE) AND 개별 도로 허가(mie) AND 실제 차량 대기(mip)"의 3단계로 확장한다.

**확정**: 수정 비유 사용. 한계 문장: "이 비유는 MIE 비트의 전역 제어 역할을 설명하기 위한 것이며, mstatus의 다른 필드(MPIE, MPP 등)는 별도로 다룬다."

---

### 비유 3: mtvec = 119 신고 전화번호

**평가**:
- 장점: "어디로 달려가야 하는지" 주소(address) 개념 전달이 매우 직관적
- 기술 매핑: mtvec = 핸들러 기저 주소 → 119 = 응급 서비스 진입점. 매핑 정확함
- 한계: 전화번호는 하나이지만 Vectored 모드에서 mtvec는 원인별로 다른 오프셋을 사용함

**개선**: Direct 모드를 먼저 "119" 단일 번호로 설명한 후, Vectored 모드를 "119-1(화재), 119-2(구급), 119-3(구조) 내선 번호"로 확장한다. 이렇게 하면 MODE 필드 변화에 따른 동작 차이도 자연스럽게 연결된다.

**확정**: 개선 비유 사용. 가장 성공적인 비유로 판단하여 18.1절 도입부에 배치한다.

---

### 비유 4: CSRRW = 주민등록증 교체

**평가**:
- 장점: 원자적 교체(atomic swap)의 핵심 — 읽고 동시에 새 값으로 바꾼다 — 을 잘 표현
- 기술 매핑: "이전 주민번호 확인(read) + 새 번호로 교체(write)"가 한 번에 발생 = 원자성

**문제**:
- "주민등록증 번호는 바꿀 수 없다"는 현실 상식과 충돌. 학습자가 순간 혼란을 겪을 수 있음
- CSRRS, CSRRC와 구분이 어려움 (주민등록증 비유는 CSRRW에만 적용 가능)

**대안 비유**: "ATM 인출 + 잔액 확인"
- ATM에서 돈을 인출하면, 인출 금액이 반영된 **잔액을 동시에 확인**한다
- 인출(새 값 쓰기)과 잔액 확인(이전 값 읽기)이 하나의 트랜잭션으로 묶인다
- CSRRS는 "잔액에 보너스를 더하면서 기존 잔액을 영수증에 출력" 으로 확장 가능

**확정**: 주민등록증 비유를 보조로 유지하되, ATM 비유를 주 비유로 사용한다. 한계 명시: "실제 ATM과 달리 CSRRW는 쓰기 실패가 없으며, 인터럽트 컨텍스트에서도 분할 불가능하다."

---

### 추가 비유 제안: mie/mip 관계 = 우편함

- **mie**: 수신 허용 목록 (어떤 종류의 우편물을 받을지 설정)
- **mip**: 현재 우편함에 도착해 있는 우편물 목록
- **mstatus.MIE**: 우편함 잠금장치 (잠기면 배달원이 집 앞에 와도 문을 열 수 없음)
- 처리 조건: `mstatus.MIE = 1(잠금 해제) AND mie[x] = 1(해당 우편 수신 허용) AND mip[x] = 1(실제 우편 도착)`

이 비유는 18.2절에서 mie와 mip를 함께 설명할 때 3단계 조건을 시각적으로 연결하는 데 효과적이다.

## 집필 시 주의 사항

### 기술 정확성

1. **CSR 주소**: RISC-V 스펙 Volume II (Privileged Architecture) 기준으로 주소 사용
   - mstatus: 0x300, mie: 0x304, mtvec: 0x305, mscratch: 0x340, mepc: 0x341, mcause: 0x342, mip: 0x344
2. **WARL 필드 처리**: mtvec.MODE 같은 WARL(Write Any Read Legal) 필드는 구현 시 불법 값 필터링 필요. 단순화를 위해 Mode[1:0] 중 2'b10, 2'b11은 2'b00으로 강제 처리한다는 주석을 코드에 포함할 것
3. **원자성 구현**: CSRRW는 단일 사이클 내에서 read와 write가 완료되어야 함. 파이프라인에서는 EX 스테이지에서 동시 처리되도록 설계
4. **mstatus.MPIE 처리**: mret 명령어 구현은 Ch19에서 다루므로, Ch18에서는 MPIE 저장 로직만 구현하고 mret는 언급만 한다

### 전이 지식 활용

5. **기존 코드 연결**: Ch09~Ch12의 `rv32i_pipeline_complete` 파라미터(`DATA_WIDTH`, `ADDR_WIDTH`, `RF_DEPTH`)와 동일한 명명 규칙을 사용
6. **포워딩 해저드 예고**: 18.3절에서 CSR 해저드 문제를 "연습문제 6번 예고"로 간략히 언급하되, 교재 범위(Ch18)에서는 소프트웨어 NOP 삽입을 단순화 정책으로 채택함을 명시

### 난이도 조절

7. **18.2절 분량 분배**: 7개 CSR을 단일 절에서 모두 다루므로, 절을 가상의 소절(18.2.1~18.2.3)로 구조화하되 HTML 헤딩은 `<h3>`으로 처리하여 h2 절 번호 체계를 유지
8. **미니 실습(18.4절) 설계 원칙**:
   - 반드시 성공할 수 있도록 코드 전체를 제공하고 파형 결과 사진(SVG) 포함
   - "확인해야 할 신호 3가지"를 체크리스트로 제공
   - 오류 발생 시 가장 흔한 원인 2가지를 aside.faq 박스에 미리 포함
9. **용어 첫 등장 규칙**: CSR, Machine Mode, Zicsr, WARL, MRET 등 새 용어는 첫 등장 시 반드시 "한글(영문)" 형식으로 병기

### 연계 챕터 관리

10. **Ch19 예고 분량**: 18.5절에서 "예외 및 인터럽트 처리(Ch19)"를 1문단(200자 내외)으로만 예고. mret 동작, 예외 벡터 진입 순서 등은 Ch19에서 상세히 다룬다는 안내로 학습자의 기대를 관리
