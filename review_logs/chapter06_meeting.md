## 1. 이슈 통합 목록 (우선순위별)

### Tier 1 — 즉시 수정 필수 (Critical/P1)

**[T1-1] B 타입 및 J 타입 즉치수 비트 재배열 — 본문 설명 누락**
- 이슈: 전체 소스 코드의 immediate_generator에 `IMM_B`, `IMM_J` 인코딩이 올바르게 구현되어 있으나, 왜 비트 순서가 뒤섞이는지(부호 비트 공유, rs1/rs2 필드 위치 보존을 위한 의도적 설계) 본문 6.1.2절~6.1.3절 어디에도 설명이 없음.
- 출처: 기술 리뷰어 [C-1]
- 수정 방향: 6.1.2절 또는 6.1.3절에 B/J 타입 즉치수 비트 재배열 이유를 1단락 추가. "왜 instr[7]이 imm[11]에 배치되는가", "부호 비트 instr[31]을 모든 타입에서 동일 위치에 유지하는 설계 의도" 설명 포함.

**[T1-2] LUI의 a_sel=0 처리 — 어셈블러 x0 보장 근거 미설명**
- 이슈: 6.2.2절 LUI/AUIPC 설명에서 "ALU에서 0+imm을 계산"이라고 기술하나, 왜 rs1 필드가 항상 x0(0)임을 보장할 수 있는지 RISC-V 스펙 근거가 없음. 비표준 어셈블러 또는 직접 작성한 바이너리에서 rs1 필드가 x0이 아닌 경우 잘못된 결과가 발생함.
- 출처: 기술 리뷰어 [C-2], 초보자 독자 [막힘 4], 교육 설계자 (진리표 개선 가능 사항)
- 수정 방향: 6.2.2절 LUI/AUIPC 설명에 "RISC-V 스펙(Vol.I, 2.4절)에서 LUI의 rs1 필드는 don't-care이며, 표준 어셈블러(gas, llvm)는 항상 x0으로 채운다. 따라서 a_sel=0 설정 시 레지스터 파일이 항상 0을 반환한다. 이 구현은 어셈블러가 스펙을 준수함을 전제로 한다"는 내용 1~2문장 추가.

**[T1-3] control_unit 래퍼 구조 미설명 — 6.1절 → 6.3절 전환 혼란**
- 이슈: 6.1절에서 `instruction_decoder` 모듈을 설명한 후, 6.3절 top-level 코드에서 갑자기 `control_unit`이라는 다른 모듈이 등장함. `control_unit`이 `instruction_decoder`와 `branch_comparator`를 감싸는 래퍼임을 설명하는 문장이 6.3절 어디에도 없음. `rs1_addr`, `rs2_addr`, `rd_addr`가 `control_unit`의 출력인지도 불명확.
- 출처: 초보자 독자 [P1, 막힘 1], 기술 리뷰어 [M-3] (부분)
- 수정 방향: 6.3절 시작 부분 또는 6.3.1절 도입에 "`instruction_decoder`와 `branch_comparator`를 하나의 `control_unit` 래퍼로 묶어 top-level에서 사용한다. `control_unit`은 레지스터 주소(`rs1_addr`, `rs2_addr`, `rd_addr`)와 `funct3`도 추출하여 제공한다"는 설명 1단락 추가.

**[T1-4] branch_comparator 모듈 소개 누락**
- 이슈: 6.1절 디코더 코드에서 `br_eq`, `br_lt`가 입력 포트로 선언되어 있으나, 누가 이 신호를 생성하는지(branch_comparator 모듈)에 대한 설명이 6.1~6.3절 어디에도 없음. 전체 소스 코드 섹션에 가서야 알 수 있음.
- 출처: 초보자 독자 [P1], 기술 리뷰어 [M-2] (br_un 흐름)
- 수정 방향: 6.1절 또는 6.2절에 분기 비교기(branch_comparator) 모듈을 간단히 소개하는 1~2문장 추가. "분기 비교기는 rs1_data와 rs2_data를 비교하여 br_eq, br_lt를 출력한다. 이 신호는 instruction_decoder에 입력되어 branch_taken을 결정한다"와 같은 수준으로 충분.

**[T1-5] 6.4절 스스로 점검 — 레지스터 이름 오류**
- 이슈: 6.4절 "스스로 점검" aside에서 "t0(x5), t1(x6) 등의 레지스터 값이 피보나치 수열과 일치합니까?"라고 기술하나, 피보나치 프로그램은 x10(a0), x11(a1), x12(a2) 등을 사용함. t0(x5), t1(x6)은 해당 프로그램에서 사용하지 않는 레지스터.
- 출처: 초보자 독자 [막힘 5, P1]
- 수정 방향: "t0(x5), t1(x6)"을 "x10(a0), x11(a1) 값이 각각 55, 89인지 확인하십시오"로 수정.

### Tier 2 — 수정 권장 (Major/⚠️)

**[T2-1] 6.4.3절 검증 커버리지 과장 — "완전한 검증" 표현**
- 이슈: 6.4.3절에서 "완전한 RV32I 단일 사이클 프로세서를 설계하고 검증했습니다"라는 표현이 있으나, 피보나치 프로그램은 ADDI, LUI, ADD, SW, BLT, JAL 6종만 커버. Load 명령어, JALR, AUIPC, 시프트 명령어, SLT 계열, SB/SH 등 다수 미검증.
- 출처: 기술 리뷰어 [M-1]
- 수정 방향: 6.4.3절의 "완전한 검증" 표현 완화. "피보나치 프로그램은 Part 2 마일스톤 목적의 통합 테스트이며, 전체 37개 명령어 커버리지 검증은 연습문제 또는 별도 단위 테스트를 통해 수행해야 한다"고 명시.

**[T2-2] 6.3절 포트 인터페이스 불일치 — 방침 미명시**
- 이슈: 전체 소스 코드의 서브모듈 포트명이 Ch04/Ch05 원본과 다름 (예: `reg_wr_en`→`reg_w_en`, `operand_a/b`→`a/b`, `inst`→`instr` 등). 6.3절 본문에서는 "Ch04~Ch05에서 완성한 모듈을 계층적으로 연결"한다고 하나 실제는 인라인 재정의 버전.
- 출처: 기술 리뷰어 [M-3]
- 수정 방향: 6.3절 도입부 또는 전체 소스 코드 섹션 서문에 "본 챕터의 전체 소스 코드는 Ch06 통합을 위해 모든 서브모듈의 포트명을 통일된 명명 규칙으로 재정의한다. Ch04/Ch05 원본 코드와 포트명이 일부 다를 수 있으며, 본 챕터의 코드가 단일 사이클 통합 설계의 최종 기준이다"를 명시.

**[T2-3] br_un 신호 흐름 — 잠재적 시뮬레이터 경고 미안내**
- 이슈: `instruction_decoder`와 `branch_comparator`가 서로를 참조하는 구조로 인해 일부 시뮬레이터에서 제로-지연 루프 경고 가능. 코드 자체는 순환 의존성이 없으나 독자가 경고를 맞닥뜨릴 경우 당황할 수 있음.
- 출처: 기술 리뷰어 [M-2], 초보자 독자 (br_un 순환 의혹)
- 수정 방향: 6.3절 control_unit 설명 부분에 "`branch_comparator`의 출력 `br_eq`/`br_lt`는 `instruction_decoder`의 `br_un` 출력에 의존하지 않으므로 순환 의존성이 없다. Vivado가 관련 경고를 발생시키면 파형에서 `br_un`이 `funct3`만으로 결정됨을 확인하라"는 안내 추가.

**[T2-4] 6.2절 Branch 진리표 "조건부" 모호 표기**
- 이슈: 6.2.2절 Branch 타입 진리표에서 `pc_sel` 열이 "조건부"로만 표기됨. 어떤 신호에 의해 결정되는지 독자가 알 수 없음.
- 출처: 초보자 독자 [막힘 3, P2], 교육 설계자 (진리표 소폭 개선 가능 사항)
- 수정 방향: "조건부"를 "branch_taken=1이면 PC_BRANCH, 0이면 PC_PLUS4"로 명시.

**[T2-5] 6.3절 Gradual Reveal 부재 — SVG 완성본 일괄 제시**
- 이슈: 6.3절에 완성된 데이터패스 SVG 하나만 제시되어 독자가 아직 설명되지 않은 연결까지 한꺼번에 처리해야 하는 인지 부하가 발생.
- 출처: 교육 설계자 [H-1], 교육심리전문가 (항목 3)
- 수정 방향: 즉시 적용은 방안 B(주목 유도 텍스트 추가). SVG 아래에 "위 데이터패스를 한꺼번에 이해하려 하지 마십시오. 아래 순서대로 각 연결을 하나씩 추적하십시오: ① PC→IMEM, ② IMEM→제어유닛, ③ ALU-A/B MUX, ④ WB MUX, ⑤ 메모리 경로"라는 텍스트 추가. SVG 3단계 분할은 다음 버전에서 처리.

**[T2-6] 6.2절 도입부 안심 선언 누락**
- 이슈: 7개 진리표 나열 시작 전에 "이것을 다 외워야 하나?"라는 독자 불안을 사전 차단하는 선언이 없음.
- 출처: 교육심리전문가 [우선순위 1]
- 수정 방향: 6.2절 진리표 나열 직전에 "이 절의 진리표들은 암기 목록이 아닙니다. 각 명령어가 데이터패스를 어떻게 통과하는지를 추적하면 자연스럽게 도출됩니다. 총 7개 명령어 그룹이며 패턴은 크게 3가지입니다. 지금은 전체 흐름 이해에 집중하십시오"라는 문장 추가.

**[T2-7] JALR LSB 클리어 이유 — 본문 설명 없음**
- 이슈: 6.3절 PC MUX 코드에서 `PC_JALR: pc_next = alu_result & 32'hFFFF_FFFE;`가 코드 주석으로만 설명되고, RISC-V 스펙에서 이 규정을 요구하는 이유가 본문에 없음.
- 출처: 초보자 독자 [막힘 2, P2]
- 수정 방향: 6.3절 PC MUX 설명 시 "JALR의 목표 주소는 RISC-V 스펙에 따라 LSB를 반드시 0으로 클리어해야 한다. 이는 주소가 항상 짝수(명령어 2바이트 또는 4바이트 경계)가 되도록 보장하기 위함이다"라는 1문장을 본문에 추가.

**[T2-8] 6.4절 도입 문장 누락**
- 이슈: `<h2>6.4 단일 사이클 통합 시뮬레이션</h2>` 직후 바로 `<h3>6.4.1 피보나치 프로그램 준비</h3>`로 시작. 절 도입 내러티브 없음.
- 출처: 교육 설계자 [H-2]
- 수정 방향: 6.4절 h2 태그 직후에 "이제 우리가 설계한 CPU를 실제로 실행해볼 시간입니다. 하드웨어 설계의 진짜 보람은 시뮬레이터의 파형에서 원하는 값이 나타나는 그 순간입니다"와 같은 2~3문장 도입 내러티브 추가.

**[T2-9] 6.3절 코드 블록 직전 안도 문장 누락**
- 이슈: top-level 코드 블록 직전 전환 지점에서 심리적 압박 발생 가능. 독자가 수십 줄 코드 전부를 처음부터 이해해야 한다는 부담감을 느낄 수 있음.

**[T2-10] 데이터 메모리 주소 연산 단순화 전제 미명시**
- 이슈: `data_memory`의 `{addr[31:2],2'b00}+3` 연산에서 정렬된 접근(4바이트 경계)을 가정하는 단순화 구현임이 명시되지 않음.
- 출처: 기술 리뷰어 [M-4]
- 수정 방향: 데이터 메모리 설명 시 "교육 목적 단순화 구현이며, 정렬된 접근(4바이트 경계)을 가정합니다. 비정렬 접근은 이 구현에서 지원하지 않습니다"를 명시.

### Tier 3 — 검토 사항 (Minor)

## 2. 충돌 해결

### 충돌 A: 6.1.3절 인지 부하 — 분할 여부

- **교육 설계자 의견**: 6.1.3절이 enum 5개 + 포트 12개 + always_comb + case 문을 단일 절에서 다루어 인지 부하 7~8개 수준. 절 분리 또는 enum 일부를 전체 소스 코드 섹션으로 이관을 권장.
- **교육심리전문가 의견**: 6.1절 첫 실습 설계가 자기효능감 이론에 부합하며 단계적 구조가 양호하다고 평가. 현재 구조에 만족.
- **초보자 독자 의견**: 코드 이해도는 ⭐⭐⭐⭐⭐로 평가.

**편집장 판단**: 인지 부하 수치(7~8)는 교육 설계자의 지적이 타당하나, 초보자 독자와 교육심리전문가 모두 현재 구조를 긍정적으로 평가했음. Tier 1~2 이슈들이 해결되면 전반적 이해도 향상이 예상됨. 절 분리는 다음 버전 과제로 유보. **현재 버전에서는 절 구조 유지하되, T2-6(6.2절 안심 선언), T2-9(6.3절 안도 문장) 추가로 인지 부하를 간접 완화**.

### 충돌 B: 6.4.3절 성취감 강도

- **교육심리전문가 의견**: 성취감 텍스트가 절제되어 있으므로 성취 확인 단락(3~4문장)을 추가해야 함. [우선순위 2]
- **교육 설계자 의견**: 현재 구조에서 성취 요소가 갖추어져 있음. 1~2문장 추가면 충분. [Low Priority]

**편집장 판단**: 정확성 기준 충족 여부와 무관하게, 심리적 안전(이 프로젝트의 핵심 가치 중 하나)을 위해 추가 성취 문장 삽입이 적절. 단, 분량 균형을 위해 2~3문장으로 제한. Tier 3([T3-6])으로 분류하되 강력 권고.

### 충돌 C: 포트 인터페이스 불일치 처리 방식

- **기술 리뷰어 의견**: 6.3절 도입부 또는 전체 소스 코드 서문에 방침 명시 [M-3]
- **초보자 독자 의견**: 6.3절 시작 시 control_unit 래퍼 설명이 더 시급 [P1]

**편집장 판단**: 두 이슈는 별개. [T1-3]으로 래퍼 구조 설명을 먼저 처리하고, [T2-2]로 포트명 불일치 방침을 추가. 중복 아닌 상호 보완.
