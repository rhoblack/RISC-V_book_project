# Ch19 Phase 1 기획 — 교육전문강사 Briefing

## 역할 정의

교육전문강사로서 당신은:
- 설명 품질: "강의 실제 현장에서 그대로 읽고 설명할 수 있는가?"
- 비유 검증: ① 기술 사실과 정확히 매핑되는가? ② 한계 명시? ③ 오해 유발하지 않는가? ④ 대안 비유가 있는가?
- 수강생 막힘 포인트 예측: Top 5 자세히 분석
- 면접 연결 포인트: "이 개념이 실무/면접에서 어떻게 쓰일까?"
- 데모/실습 제안: Basys 3 FPGA에서 직접 시연 가능한가?

---

## Ch19 기술 배경

**교육 목표:**
학생이 "인터럽트의 우선순위는 어떻게 결정되는가?"를 정확히 설명할 수 있도록

**핵심 개념:**
1. **우선순위 인코더** (Priority Encoder)
   - 입력: 8개 interrupt 소스 (MEIP, MTIP, MSIP, SEIP, STIP, SSIP, UEIP, UTIP)
   - 출력: 1개 cause_code (3~4비트)
   - 정책: 고정 우선순위 (이 책에서)

2. **벡터화 주소** (Vectored Address)
   - 계산: mtvec[31:2] + (cause << 2)
   - 의미: 각 인터럽트별 핸들러의 서로 다른 주소

3. **중첩 인터럽트** (Nested Interrupt)
   - Handler 내부에서 또 다른 interrupt 가능
   - MPIE를 통한 상태 저장/복구

#### 막힘 포인트 #1: "우선순위 인코더는 뭐고, 왜 필요한가?"

**학생이 막히는 이유:**
- interrupt는 "1개씩 순서대로 온다"고 생각 (오류)
- 실제로는 여러 개가 동시에 신호 가능
- "그럼 어떤 걸 먼저 처리하지?"라는 question 발생
- 하드웨어 동시성과 소프트웨어 순차처리의 gap

**강사 팁 (현장 설명):**
```
"여러분 응급실을 생각해보세요. 응급실에 환자가 들어올 때:
 - 심정지 환자 (최우선)
 - 심한 외상 (2번)
 - 약간의 골절 (3번)
 - 감기 (4번)

이런 식으로 우선순위가 고정되어 있습니다.
프로세서도 마찬가지입니다. 여러 개의 interrupt 신호가 동시에 들어와도,
하드웨어가 우선순위 규칙에 따라 '이 interrupt가 가장 중요해'라고 판단해서
그것만 처리하는 거죠. 이게 바로 '우선순위 인코더'입니다."
```

**대안 설명 (처음이 안 되면):**
```
비유 2: 신호등
- 차량의 움직임이 4가지 동시에 신호 가능
  (차량 진행, 교통경찰 신호, 신호등, 수동 주행)
- 규칙: 신호등 > 교통경찰 > 차량 순서
- 하드웨어: 인코더가 "신호등이 가장 높아"라고 판단

비유 3: 은행 우대 고객
- VIP, 일반, 신규 고객 동시 대기
- 규칙: VIP > 일반 > 신규
- 창구는 항상 가장 우선 고객부터 호출
```

**위험도:** ⭐⭐⭐⭐⭐ (극높음 — 이 개념이 못 통하면 이후 진행 불가)

**검증 질문:**
- "응급실 비유가 뭘 놓치고 있을까?"
  → 답: 응급실은 사람의 선택, 프로세서는 고정 규칙 (한계 명시 필수)

#### 막힘 포인트 #2: "cause << 2는 왜? 왜 4를 곱하는 거야?"

**학생이 막히는 이유:**
- (cause << 2) = cause × 4 라는 걸 알아도
- "왜 4일까?"를 모름
- 비트 시프트 자체는 익숙하지만, 왜 이걸 여기서 쓰는지 모호

**강사 팁 (현장 설명):**
```
"좋은 질문입니다. 왜 4일까요?

생각해보세요. 프로세서 메모리는 32비트 = 4바이트 단위로 움직입니다.
각 interrupt handler의 주소를 저장할 때,

- Handler 0 @ 주소 0x1000
- Handler 1 @ 주소 0x1004 (0x1000 + 4)
- Handler 2 @ 주소 0x1008 (0x1000 + 8)
- Handler 3 @ 주소 0x100C (0x1000 + 12)

이렇게 4바이트씩 띄어서 저장됩니다.

그래서 cause 번호를 주소로 바꾸려면:
  주소 = base + cause × 4
      = base + (cause << 2)

여기서 << 2는 × 4를 빠르게 계산하는 비트 시프트입니다."
```

**대안 설명:**
```
메모리 맵 그리기:
  0x1000: Handler 0 (cause=0)
  0x1004: Handler 1 (cause=1)  ← 차이는 4 = 1 × 4
  0x1008: Handler 2 (cause=2)  ← 차이는 4 = 2 × 4
  0x100C: Handler 3 (cause=3)  ← 차이는 4 = 3 × 4

규칙: Address = 0x1000 + (cause × 4)
         = 0x1000 + (cause << 2)
```

**위험도:** ⭐⭐⭐ (중간)

**검증 질문:**
- "만약 128비트 ISA라면? 16을 곱해야 하나?"
  → 답: 맞음! ISA에 따라 달라짐 (32비트=×4, 64비트=×8, 128비트=×16)

#### 막힘 포인트 #3: "중첩 인터럽트에서 mepc와 mcause를 어떻게 보존하지?"

**학생이 막히는 이유:**
- mepc, mcause는 각각 1개 레지스터
- 첫 번째 interrupt → mepc1, mcause1 저장
- 두 번째 interrupt → mepc2, mcause2 저장
- 그럼 mepc1, mcause1은?? 어디 간 거야??
- 답: 메모리 스택에 저장해야 함 (하드웨어가 아니라 소프트웨어가)

**강사 팁 (현장 설명):**
```
"여기서 매우 중요한 포인트입니다.

먼저 이해해야 할 것: mepc와 mcause는 각각 '1개'의 레지스터입니다.

Interrupt 1이 발생하면:
  mepc = PC1 (첫 번째 interrupt 지점)
  mcause = cause1

이 시점에서, Handler가 실행되는 중에 Interrupt 2가 또 발생하면:
  mepc = PC2 (덮어씀!)
  mcause = cause2 (덮어씀!)

그럼 PC1, cause1은 어디 갔을까요?
→ Handler 코드가 프로세서에게 '나 이제 수락할 준비 됐어'라고 신호하기 전에,
   C 코드에서 직접 메모리 스택에 PC1, cause1을 저장해야 합니다!

이게 스택의 역할입니다."
```

**그림으로 설명:**
```
Handler 진입:
  메모리[sp-4] = mepc (저장)
  메모리[sp-8] = mcause (저장)
  메모리[sp-12] = mstatus (저장)
  sp -= 12

Nested interrupt 발생:
  mepc = PC2 (덮어씀)
  mcause = cause2 (덮어씀)

Handler 종료:
  sp += 12
  mstatus = 메모리[sp-12] (복구)
  mcause = 메모리[sp-8] (복구)
  mepc = 메모리[sp-4] (복구)
```

**위험도:** ⭐⭐⭐⭐⭐ (극높음)

**검증 질문:**
- "그럼 MPIE는? 왜 따로 저장하지 않아도 되나?"
  → 답: MPIE는 현재 mstatus에 자동으로 저장되므로, mstatus 전체를 스택에 보관하면 됨

#### 막힘 포인트 #4: "MRET는 일반 RET와 뭐가 다르지?"

**학생이 막히는 이유:**
- RET는 함수 호출에서 돌아올 때
- MRET는 interrupt에서 돌아올 때
- 둘 다 "돌아온다"는 점은 같은데?
- "차이가 뭐지?"라는 의문

**강사 팁:**
```
"좋은 질문입니다. 둘 다 '이전 상태로 돌아간다'는 점은 같습니다.

하지만 돌아가면서 하는 일이 다릅니다:

RET (함수 복귀):
  PC ← 스택에서 꺼낸 반환 주소
  (그게 끝!)

MRET (interrupt 복귀):
  PC ← mepc (interrupt 지점으로 복귀)
  MIE ← MPIE (이전 interrupt 활성화 상태 복구)
  MPIE ← 1 (다음 interrupt 준비)

핵심은: MRET는 단순히 주소만 복구하지 않고,
        interrupt 활성화 상태까지 함께 복구합니다."
```

**위험도:** ⭐⭐⭐ (중간)

---

#### 막힘 포인트 #5: "우선순위가 고정되어 있다는 게... 그럼 중요한 interrupt를 나중에 처리할 수도 있다는 거야?"

**학생이 막히는 이유:**
- "우선순위가 고정"이라는 말이 옳지 못함
- "왜 못 바꾸지? 소프트웨어에서 바꾸면 되지 않나?"
- 설계 선택과 ISA 스펙의 차이 모호

**강사 팁:**
```
"핵심 질문입니다. 이번 책에서는 우선순위를 '고정'으로 설계했습니다.
하지만 실제 프로세서들은 다릅니다:

RISC-V (이 책):
  - 우선순위는 ISA로 고정
  - MEIP > MTIP > MSIP (정해짐)
  - 바꿀 수 없음

ARM Cortex-M:
  - 우선순위를 소프트웨어로 제어 가능
  - Priority Level을 0~256 중에 선택 가능
  - 더 유연하지만 복잡

이 책에서 고정으로 한 이유는:
  1) 간단함 (학습 목표에 집중)
  2) RISC-V ISA 스펙 준수

실무에서는 설계 목표에 따라 선택하면 됩니다."
```

**위험도:** ⭐⭐⭐⭐ (높음 — 메타인지와 연결)

### Task 2: 실생활 비유 5개 제안 + 검증

**비유 설계 원칙:**
- ① 기술 사실과 정확히 매핑
- ② 한계 명시 (비유가 모든 걸 다 설명할 수 없다)
- ③ 오해 유발하지 않기
- ④ 대안 비유 제시

**비유 1: 우선순위 인코더 = 응급실 트리아주**

```
매핑:
  interrupt 신호 → 환자
  우선순위 규칙 → 트리아주 기준 (생명 위험도)
  cause 코드 → 환자 분류 색상 (빨강/주황/노랑/녹색)
  선택된 interrupt 처리 → 빨강부터 처리

정확도: ⭐⭐⭐⭐ (높음)

한계:
  - 응급실은 '사람의 선택'이지만, 프로세서는 '하드웨어 회로'
  - 응급실은 우선순위를 바꿀 수 있지만, ISA는 못함
  → "프로세서의 우선순위는 훨씬 엄격합니다"라고 명시

대안:
  - 신호등 (차량 신호 우선순위)
  - 은행 우대고객 (고정 규칙)
```

**비유 2: 벡터화 주소 = 책의 목차**

```
매핑:
  mtvec BASE = 책의 시작 주소
  cause 번호 = 챕터 번호
  cause << 2 = 각 챕터의 페이지 오프셋
  최종 주소 = 해당 챕터의 시작 페이지

예:
  0x1000: Handler의 시작 주소
  cause=0: 0x1000 + 0 = 0x1000
  cause=1: 0x1000 + 4 = 0x1004
  cause=2: 0x1000 + 8 = 0x1008

정확도: ⭐⭐⭐⭐ (높음)

한계:
  - 책은 가변 길이이지만, 프로세서는 고정 4바이트
  → "메모리 주소는 4바이트 정렬입니다"

대안:
  - 영화관 상영실 (각 영화=각 handler)
  - 도서관 섹션 (각 섹션=각 cause)
```

**비유 3: 중첩 인터럽트 = 함수 호출 스택**

```
매핑:
  첫 번째 interrupt → 함수 A 호출
    → 반환 주소(mepc) 스택 저장
  두 번째 interrupt → 함수 B 호출 (A 내부)
    → 반환 주소(mepc) 스택 저장
  B 종료 → 반환
  A 종료 → 반환

정확도: ⭐⭐⭐⭐⭐ (극높음)

한계:
  - 함수는 호출자 권한 유지, interrupt는 권한 변경 (MIE 비트)
  → "추가로 interrupt 활성화 상태도 저장해야 합니다"

대안:
  - 전화 걸기 (첫 통화 - 두 번째 통화(첫 통화 중) - 복구)
```

**비유 4: MPIE = 저장된 복사본**

```
매핑:
  mstatus[MIE] = 현재 interrupt 활성화 상태
  mstatus[MPIE] = 이전 상태의 백업

  interrupt 발생:
    MPIE ← MIE (현재 상태 백업)
    MIE ← 0 (interrupt 비활성)

  Handler:
    MIE ← 1 (다시 활성, 중첩 허용)

  MRET:
    MIE ← MPIE (백업에서 복구)

정확도: ⭐⭐⭐⭐⭐ (극높음)

비유: 휴대폰 벨소리
  현재 상태(MIE): 벨소리 ON
  백업(MPIE): 영화관 들어가기 전 상태 저장
  interrupt: 영화관 들어가면서 벨소리 OFF
  Handler: 영화 도중 긴 호출 → 벨소리 ON (중요하면)
  복구: 영화 끝나고 원래 상태(ON)로 복구
```

**비유 5: 고정 우선순위 = 신호등의 규칙**

```
매핑:
  RISC-V의 고정 우선순위 = 신호등의 '신호 규칙'
  바꿀 수 없음 = 신호등 규칙은 버튼으로 못 바꿈
  (바뀌려면 엔지니어가 신호 시스템을 재설계해야 함)

정확도: ⭐⭐⭐⭐⭐ (극높음)

한계:
  - 신호등은 교통 상황에 따라 조정 가능
  - 프로세서도 일부(mie 비트)는 소프트웨어 제어 가능
  → "RISC-V에서 우선순위 순서는 바꿀 수 없지만,
      전체 interrupt를 활성/비활성할 수는 있습니다"
```

### Task 3: 면접 연결 포인트 5개

**목표:** 학생이 "이게 현실 면접에서 나올 법한 개념이군"을 깨닫도록

**포인트 1: "인터럽트 우선순위는 왜 고정할까?"**
```
면접 질문: "프로세서 설계할 때 interrupt 우선순위를 어떻게 결정하나요?"

교육 답변:
  - RISC-V: 우선순위는 ISA로 고정 (MEIP > MTIP > MSIP)
  - ARM: 동적으로 제어 가능
  - 선택 기준: 성능 vs 유연성 trade-off

강사 팁: "이 질문이 나오면 '고정이 더 간단하고 빠르지만 덜 유연하고,
         동적이 더 유연하지만 복잡하다'는 답을 해주세요."
```

**포인트 2: "중첩 인터럽트에서 deadlock 위험은?"**
```
면접 질문: "중첩 인터럽트를 사용할 때 주의할 점은?"

교육 답변:
  - A handler 내에서 B interrupt 발생
  - 스택에서 A의 상태 저장
  - B 처리 후 A 복구
  - 스택 오버플로우 위험 (깊은 중첩)
  - Priority inversion 위험 (낮은 우선순위가 높은 우선순위 block)

강사 팁: "실무에서는 중첩 깊이 제한, priority ceiling protocol 등을 씁니다."
```

**포인트 3: "실무에서는 interrupt를 어떻게 사용하나?"**
```
면접 질문: "임베디드 시스템에서 interrupt 실제 사용 사례?"

교육 답변:
  - Timer interrupt: 주기적 작업 (스케줄러)
  - I/O interrupt: 데이터 수신 (UART, Network)
  - 외부 interrupt: 센서 입력 (GPIO)

강사 팁: "본인이 만든 프로젝트에서 interrupt 경험을 얘기하면 좋습니다."
```

**포인트 4: "ARM vs RISC-V의 interrupt 차이?"**
```
면접 질문: "ARM과 RISC-V의 interrupt 처리 방식 차이?"

교육 답변:
  - ARM: Nested Vectored Interrupt Controller (NVIC)
    * 우선순위 동적 제어 (Priority Level 0~255)
    * 우선순위 inversion 방지 기제 지원

  - RISC-V: 고정 우선순위
    * 더 간단함
    * ISA 스펙으로 고정됨

강사 팁: "이 비교 질문이 나오면 '각각의 설계 철학' 차이를 설명해주세요."
```

**포인트 5: "MRET와 일반 RET의 차이?"**
```
면접 질문: "왜 MRET가 별도로 필요한가?"

교육 답변:
  - RET: 주소만 복구
  - MRET: 주소 + interrupt 활성화 상태 복구
  - 권한 레벨도 함께 복구 (mpv bits)

강사 팁: "RISC-V privileged level의 이해와 연결되는 개념입니다."
```
